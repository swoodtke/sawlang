The lexer already has the token (used in `[T; N]`), so nothing new is lexed; the type-position meaning is untouched because a `;` inside `[ ]` in a TYPE is not in statement position.\n\n**R2 — `;` is a SEPARATOR, never a terminator.** A `;` followed by a newline, by `}`, by EOF, by another `;`, or a `;` at the start of a line is a clean error: ``a `;` joins two statements on one line; it does not end one — remove it`` (Saw has no statement terminators; that stays true). Anything else is ``two statements on one line need a `;` between them`` with a fixit naming the two statements' first tokens. Every entry gets a row in the errors pin.\n\n**R4 — `[T; N]`, the repeat literal `[v; N]` and nothing else keep their `;`.** Both are inside brackets where no statement can start.\n\n**R5 — STYLE (the skill ruling, lenient form): a brace body is ONE LINE or FULLY BROKEN, never half-way.** Either the whole body sits on the brace's line (`if done { return }`, `{ c in c = c + n; c }`), or the opening brace ends its line, every statement has its own line, and the closing brace stands alone. `{ help()` + newline + `return }` is the shape the rule exists to catch, and it stays DISALLOWED BY STYLE even though the grammar accepts it (R3 does not refuse it — the newline is a legal separator).
