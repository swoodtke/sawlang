Why\n\nTwo things, one earned by design 275 U3 and one older.\n(a) After U3, `borrows -> X` means two different things: design 141's \"lends a PLACE of X\" and U3's \"returns a VALUE of borrowing-struct type X that carries a borrow\". Same signature shape, disambiguated only by looking up whether X is declared `borrows struct` somewhere else — the reader-visibility doctrine's exact complaint. With `borrows -> &T` for a lend the signature says which: a `&T` result IS the place, a struct result is a value carrying one. And the rule unifies with the field rule U3 ruled: a reference type may appear in a RETURN position only under a `borrows` signature, and in a FIELD only under a `borrows struct` — one sentence, one check.\n(b) Design 141 made every lend writable at the use site's discretion (\"one `&self` declaration, the use site picks shared vs exclusive\"). An accessor AUTHOR therefore cannot express a read-only lend at all. The user's ruling reverses the default: the DECLARATION states the maximum mode, the use site narrows within it.\n\n## 1. The rules (RULED)\n\nR1. RETURN TYPE = the window's MAXIMUM mode. `borrows -> &var T` may open shared or exclusive windows; `borrows -> &T` opens shared only, and a write through it (`g.at(4).weight += 1`, `v[i] = x` through a `&T` subscript accessor, `&var g.at(4)` as an argument) is a compile error naming the accessor and its declared mode, with a fixit naming `-> &var T`. Conditional lends: `-> &var T?` / `-> &T?`. The bare `borrows -> T` spelling on a lend-shaped body (one that `lend`s) is a parse-time/typecheck-time ERROR with a fixit naming `-> &T` — no silent acceptance of both spellings (no-degradation doctrine). `borrows -> S` where `S` is a `borrows struct` stays the U3 value-returning form (this brief does not build it; it only leaves the spelling free).\nR2. RECEIVER MODE BOUNDS RETURN MODE. `-> &var T` REQUIRES `&var self`: an exclusive place cannot be projected from a shared receiver (design 106's no-upgrade rule one position over). `&var self borrows -> &T` is legal (an accessor that mutates its own bookkeeping in a prologue/epilogue but lends read-only). `&self borrows -> &var T` is the teaching error, fixit naming `&var self`. `lend self.x` inside a `-> &T` accessor lends shared; inside `-> &var T`, exclusive-capable.\nR3. THE USE SITE STILL NARROWS. A read through a `&var T` lend opens a SHARED window; two shared windows on one root compose; a write opens the exclusive one. Unchanged from design 141 for every use site that is within the declared maximum.\nR4. RECEIVER NARROWING (the `let` receiver rule). A `borrows` accessor declared `&var self` may be used SHARED on an immutable (`let`) binding: the shared use borrows the receiver shared, and the compiler checks the accessor BODY under that mode — if the body writes `self` anywhere OUTSIDE the lent place (a prologue counter, an epilogue update, a `self.x = …` beside the `lend`), the accessor is EXCLUSIVE-ONLY and a shared use on a `let` receiver is an error naming the mutating line (\"accessor `at` mutates its receiver at L:C, so it needs an exclusive receiver\"). Determined by the body, so inferred (doctrine: infer what is determined); the alternative — a second read-only accessor beside every writable one — is the duplication design 141 was written to avoid, and would break `let v = [1, 2]; print(v[0])` the day Vector's subscript says `&var self`. Ordinary (non-`borrows`) `&var self` methods are UNCHANGED: on a `let` receiver they stay an error.\nR5. ONE RULE FOR REFERENCE TYPES OUTSIDE PARAMETERS. `&T`/`&var T` is legal as a return type iff the function is `borrows` (it is the lend); as a struct field iff the struct is `borrows struct` (U3 builds that half; this brief adds the return half and writes the sentence once in the spec so U3 only adds its clause). Everywhere else a reference type in a non-parameter position keeps today's error.\n\n## 2.
