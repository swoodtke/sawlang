## Description

**Soundness gap: a multi-threaded `TaskGroup` passed to a helper escapes the Send-on-frames gate** (documented in the spec, TaskGroup section: "`threads:` is tracked on the group's binding, not yet through an opaque helper it is passed to"; found again by A17b, SL-579).

A17b's `coro.spawn-not-send` traces a spawn's group operand back to `TaskGroup.init(threads:)` in the spawner's own MIR. Tracing stops at a parameter, a field or a call result, so:
```saw-fragment
func fan_out(group: &TaskGroup) { group.spawn(work_with_a_nonsend_local()) }
func main() { let g = try TaskGroup(threads: 4) catch { return }; fan_out(&g) }
```
spawns a frame holding a non-`Send` value onto a worker thread. That is a data race the gate exists to prevent. A safety guarantee with a hole needs a conformance row (obligation 3), so the fix brief writes it first.

**Options (needs the user's ruling):**
- **(a) Conservative:** a spawn into a group whose origin is not traced (a parameter, a field, a returned group) is ALWAYS gated. It's simple and sound, but it over-refuses a single-threaded group handed to a helper whose frames aren't `Send`. A sweep would count the affected corpus programs first.
- **(b) In the type:** `TaskGroup(threads:)` yields a distinct type (for example a type parameter or a separate `ThreadedTaskGroup`), so a helper's parameter type states it and the gate keys on the type. It's reader-visible and an API change across std, spec and corpus.
- **(c) Inferred:** a function that spawns into a group parameter carries "spawns into parameter N" in its summary, and the check fires at the caller where the group's `threads:` is known, with the chain (1a's style). It's precise and needs no API change, but it's more compiler work, and a group stored in a field still needs (a) or (b).

**Lead lean:** (a) now (sound, cheap; the sweep shows its cost), then (c) if the over-refusal bites. Related: A17b gates `threads: 1` as Stage 0 does, while the spec says `threads: 1` stays the single-threaded engine. That's to be settled in the same ruling (does A17a's pool run `threads: 1` on a separate worker thread?).
