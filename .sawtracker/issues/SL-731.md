**Diagnosed by p763 (SL-763), a duplicate of SL-731: sawc2 is WRONG in both rows.** It leaks a value moved into an earlier argument when a later operand exits early. The sync twin leaks too, so this isn't coroutine-specific.

**Mechanism, confirmed from `sawc2 mir --dump`:**
```
bb0: _1 = move _2;  _4 = move _1;  _5 = call min.fail()
bb2: _6 = call sink_rev [move _4, copy (_5 as Ok).0]
bb3: _0 = Err(...); drop(_5); drop(_1); return;     // no drop(_4)
```
The argument temporary `_4` holds the moved value and is never registered with the scope. An early exit's unwind (`unwind_to`) drops only scope-registered entries, so `_4` is never dropped. The class is any early exit (`try`, `return`, `break`) while later operands are still being evaluated. UNVERIFIED: the exact call site (probably `temp_of` plus `op_move` with no `own_temp`).

**Lead reading (reversible, put to the user Oct 16): sawc2's drop order in `coro_try_landing_relinquishes_by_position` rows 5b and 9 is the spec's; the file's EXPECT-OUTPUT records Stage 0's.**

p731 stopped at step 4. The fix drops every value exactly once (`leaks --atExit` 0), and this row stays `wrong` on ORDER only:
- 5b `try { n = sink_rev(move r, try fail()) } catch { print("handled") }`: sawc2 `drop kept`, `handled`; the file wants `handled`, `drop kept`.
- 9 `sink4(try a(), move r, try b(), move q)`, `b` fails: sawc2 `drop kept`, `drop second`; the file wants the reverse.

The authorities:
- The spec's Argument Evaluation Order: arguments are evaluated left to right, and a by-value argument is moved "at evaluation time". So `move r` happens before `try fail()`, and the moved value is then a temporary of the statement.
- The spec's Temporaries rule: a temporary is destroyed at the end of its statement. On the error edge, that is before the `catch` block runs and before the function's locals (`q`) drop.
- Design 147 C (DF-133a, the user's fork (i)): "the hoist preserves source evaluation order". Stage 0 exempts "plain identifier reads" from the lift as unobservable, but a `move` of an owning value is observable through the drop order on the error edge. So Stage 0's order departs from 147's own ruling. The file's comment ("a pure `move` operand stays where it was written") describes that exemption, not a language rule.

**So:** rewrite the program's EXPECT-OUTPUT and the comment for rows 2, 5 and 9 to the spec's order. The row moves to `stage0-wrong`, and SL-731 lands with it.
