## Description

LEAK. Extracting a payload out of a FRESH TEMPORARY, inline, never releases the
extracted value: the payload's `deinit` does not run and its memory is never
freed. Both extraction forms are affected — the Result `try!`/`try?` family and
the Optional `!` — while the same extraction out of a BOUND value is correct.
Found Sep 9 by SL-210 (design 267 unit A) while writing the control row of the
SL-219 pin; NOT introduced by that unit, and not fixed there (SL-210 is
behavior-preserving).

## Measured evidence

Compiles clean, exit 0. `Res` is NoCopy with a printing `deinit`; every value
built below should print exactly one `drop`.

    struct Res { w: Int }
    extension Res: NoCopy { func deinit(&var self) { print("drop {self.w}") } }
    enum Bad { case Nope }
    extension Bad: NoCopy {}

    func made(n: Int) -> Result<Res, Bad> { Res(w: n) }
    func maybe(n: Int) -> Res? { Res(w: n) }
    func plain(n: Int) -> Res { Res(w: n) }

    func main() {
        print("A {(try! made(1)).w}")   // try! over a temporary
        print("B {maybe(2)!.w}")        // `!` over a temporary
        print("C {plain(3).w}")         // a plain temporary, no extraction
        let d = try? made(4)
        print("D {d!.w}")               // extraction out of a BOUND value
        print("end")
    }

Observed:

    A 1
    B 2
    C 3
    drop 3        <- the plain temporary is released
    D 4
    end
    drop 4        <- the bound value is released
    (exit 0)

`drop 1` and `drop 2` NEVER RUN. Four values built, two released.

## The class (obligation 4)

The two rows that leak are exactly the two where a payload is EXTRACTED from a
temporary inline; the two that are correct are the ones where either no
extraction happens (`plain(3).w`) or the container is a named binding whose
scope registers a cleanup (`let d = ...` then `d!`). So the axis is
TEMPORARY + EXTRACTION, and it holds across both container kinds — Result and
Optional — which is what makes it a class rather than a `try` quirk.

MECHANISM, as far as this unit probed it: the extraction hands an owned value
out of a container temporary, and the statement's temporary bookkeeping tracks
the CONTAINER it registered, not the value the extraction produced. The
container is consumed by the extraction and the payload is adopted by nobody,
so no cleanup is registered for it on any path. SL-210's decision ledger
records the boundary as expected — `take / adopt-temporary` — so the FRONT half
is answering correctly and the gap is on the cleanup-registration side, which
puts it with SL-213 (unit D, the codegen half) rather than with SL-218/SL-219.
That attribution is a HYPOTHESIS from the probe matrix, not a read of the
emission path; whoever picks this up should confirm it before scoping.

## Relationship to the neighbours

Not SL-218 or SL-219, which are the opposite error at the same boundary: those
are an ALIASING subject judged as a temporary (a double free), this is a
genuine temporary whose extracted payload nobody releases (a leak). One is the
producer question answered wrong, the other is the cleanup question not asked.
They should be swept together — the payload-extraction boundary is one row of
design 267's inventory and both faces of it are wrong — but they are distinct
fixes.

## Pin

None added by SL-210: the unit's two pins (V86/V87) are the double-free pair,
and a leak needs an oracle a `deinit`-counting example cannot give on its own
(the program exits 0 with the right output). The natural oracle is the `gmgate`
lane or an explicit built-vs-dropped counter; scoping that is this issue's
first task. The SL-219 pin's CONTROL row names this issue so the control is not
read as asserting the temporary path is correct.
