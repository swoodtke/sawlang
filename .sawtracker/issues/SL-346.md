## Description

Found by the lead's design 275 U3 validation (Sep 22); PRE-EXISTING on main for a range `for`, and design 275 U3 makes a collection `for` meet the same refusal (its back-edge is charged now, per the ruling that retired the op-budget skip).

## The finding

A VALUE-position loop (`break <value>`) in a DRIVEN body whose body does NOT suspend is refused with a message about a call the author never wrote:

```saw
func find_driven() -> Int? {
    yield_now()
    let found = for i in 0..3 { if i > 1 { break i } }
    found
}
// error: coroutine transform: suspending call to `yield_now` in `find_driven`
// appears in a nested/expression position; only a top-level `let x =
// yield_now(...)` or `yield_now(...)` statement is supported
//   --> ...:7:17   (the `for`)
```

The `yield_now` it names is design 127's SYNTHESIZED op-budget yield at the loop's back-edge, not the author's line-6 call; the anchor is the `for`. The refusal itself is sound (a suspension-spanning loop does not support `break <value>` — the shape table's rule) but nothing on the page says so, and the hint ("write a top-level `let x = yield_now(...)`") cannot be followed.

## What is owed

Route the refusal through `coro_shapes.py`'s REFUSE row for the value-position spanning loop with a message that names the mechanism: a loop in a task body spans the op-budget yield the compiler inserts at its back-edge, so its value cannot be produced by `break <value>`; the ways out are a `var` result written in the body with a plain `break`, or a `sync` helper. Pin both spellings (range `for`, collection `for`) in one errors example; K136's `break <value>` driven cell is the row that records the bound today.
