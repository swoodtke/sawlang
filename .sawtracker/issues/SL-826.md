## Description

**One file reached by two import spellings becomes two modules** (SL:hazards S27; the SL-425 sweep, c7; main and seed alike).

In a package laid out as `src/`, built with `--module-path ident=src`, `import layout` and `import ident.sub.user` (which itself imports `ident.layout`) both reach `src/layout.saw`. That gives:
- **a silent wrong answer:** a static bumped once through each spelling reads `1`, because there are two statics;
- **two types for one struct:** ``expected `&ident.layout.Slot` ... found `&layout.Slot` ``.

The dependency face works (`1 2`).

Module identity must be the FILE (its canonical path), not the spelling that reached it. Either both spellings name one module, or the second spelling is refused with a diagnostic naming both. Which one is a design question for the brief: is `import layout`, inside a package, legal at all when the package's own name is `ident`?

**Obligation 4:** every way a file can be reached:
- a relative module name;
- the package-qualified name;
- `--module-path` aliases (two names for one directory);
- a symlinked directory;
- the std root reached as a module path.

**Retires:** the subset checker's `import-allowlist` (S27 part).

**Two notes for patch 2, neither blocking:**
1. **A symlink loop is `Unknown` with errno 62 (ELOOP).** It's reported with its errno, so nothing is hidden, but `SystemErrorKind` has no name for it. If the resolver surfaces a canonical failure to users (`import.std-path` and the like), a looping link in a module path will read as "other error". 2. **macOS accepts a trailing slash on a regular file**, resolving `file.txt/` to the file, where glibc gives ENOTDIR. If patch 2 canonicalizes `--module-path` directories, the two hosts will differ on a path naming a file with a trailing slash. Worth a probe on Linux there, or a check in the resolver that the result is a directory.

Requested changes on patch SL-826.p2 (revision 1) (its test run was cancelled)

**Air: SL-826.p2 needs changes. Five stages' acceptance checks fail on `Path.canonical`.** Reproduced on 8048ced15 plus r1:

```
typecheck acceptance compiler/driver/src/main.saw: ERROR member.unknown compiler/resolve/src/loader.saw:54:28 `std.path.Path` has no method `canonical` this module can see
```

The same line fails for every unit program, in the `typechecker`, `mir`, `eval`, `drops` and `borrowck` steps. `mono` and `coro` pass. The patch's run.py list (resolver, std, seed, units, golden, subset, fixture_whitespace, programs, census) didn't include these.

**Cause:** each stage's acceptance check runs sawc2 over the compiler's own source with no `--std-root`. For instance, `typecheck_lane.check_acceptance` calls `sawc2(["--check", "--notes", "--summaries"] + package_args() + entries)`, and sawc2's default std root is the frozen `sawc/std` (SL-818). `Path.canonical` lives only in the new std, by the user's ruling that lifted the intersection rule. So this is the first compiler-source use of a new-std-only API, and these checks are the intersection rule's last remnant: SL-839 retired every Stage 0 run over the compiler's source but left these reading the frozen std.

**The fix:** give each stage's compiler-source acceptance check `--std-root std`. That's `typecheck_lane`, `mir_lane`, `eval_lane`, `borrowck_lane` and `drops_lane` (and whatever `mono`/`coro` share, if they pass only by not reaching `loader.saw`). It belongs in this patch, or in a small SL-839 follow-up that lands first.

**Everything else I checked is good:**
- **The seed:** the pin 5937a11aa holds SL-686.p1 (0e9455da7) and SL-826.p1 (49968b640) and is on main. `seed.py check` reproduces 46 files, path-free; the 5 detector cases pass.
- **Identity, under the new compiler:**
  - a module reached through a symlink is ONE module (`1 2` from one `unsafe static var`);
  - `import mods.Counter` against `counter.saw` is `import.case-mismatch` on this case-insensitive volume;
  - a missing module keeps `import.unknown-module`;
  - a `--module-path` naming a file with a trailing slash (which macOS `realpath` accepts) is a clean `import.unknown-module`, so my patch-1 divergence note doesn't bite.
- **One note, not blocking:** a symlink LOOP where a module file should be is reported as `no module mods.loopy (looked for …/loopy.saw)`. The file exists and the loop is the cause (ELOOP, my patch-1 note), so a follow-up that names the cause would be "never hide errors" proper.
