## Description

Found by the SL-355 implementer (it blocks SL-355 unit 3, the ruled Atomic wake word). I reproduced it on main 8d2c0563.

**Repro.** `.build/scratch/atomic_ptr_index.saw`, with `p: UnsafePointer<Atomic<Int>>` from `GlobalAllocator().alloc`:
```saw
p[0].store(5)
print(p[0].load())             // prints 0, not 5
p[0].compare_exchange(5, 9)    // false; the value stays 0
```

**Probed positions:**
| Receiver | Result |
|---|---|
| `p[0].store(v)` (direct pointer-index receiver) | WRONG: the store is lost |
| `pc[0].n.store(7)` (field of a pointer-indexed struct) | correct, reads back 7 |
| a static `COUNTER.store(3)` | correct |

**Mechanism (as the implementer named it; confirm before fixing).** `_receiver_storage_pointer` in codegen/calls.py resolves a receiver to its storage address for `&self` and `&var self` calls, but has no `ArrayIndex` case. A pointer-index receiver therefore falls back to evaluating the element by value into a temporary, and the method runs on that temporary. A plain `&self` read on a trivial type gives the right answer from a copy, which hides the bug. Any interior-mutability type (Atomic; any cell-carrying type, since design 186) silently loses its write.

**Sweep owed (obligation 4).** Every receiver shape that reaches this helper and its siblings:
- `p[i]` over UnsafePointer and UnsafeMutablePointer;
- a `Vector` place `v[i]` and a `Data` place;
- a `borrows` accessor place;
- a tuple index;
- `&var self` methods on the same shapes (does a mutating method also lose its write through `p[0].m()`?);
- SpinLock and Mutex, whose lock word is a cell;
- the coroutine-transform path, if receivers are re-lowered there.

**Pin.** The table above as EXPECT rows, plus the SL-355 shape (a CAS through `p[0]` from two threads).

This blocks SL-355 unit 3 (ruling R5, the atomic CAS latch).
