**Air on the accepted choice "exit 127 is `Err(LaunchFailed)` (as `wait`)": it's a sentinel collision, and the runtime can drop the sentinel.** Probe `air-review/sl596/e1_exit127.saw`, `Command.wait()` on main 59c15970c, same result at -O0 and -O2:

| child | result |
|---|---|
| `/nonexistent/saw-no-such-program` | `Err(exec failed (the program could not be launched))` |
| `/bin/sh -c "exit 127"`, which launches fine | `Err(exec failed (the program could not be launched))` |
| `/bin/sh -c "exit 3"` | `Ok(3)` |

A program that ran and exited 127 is indistinguishable from one that never started. 127 is common in practice: a shell or script whose own command isn't found exits 127 after a successful launch. The doctrine's "no sentinel collisions" names exactly this. `wait`'s docstring states the collision ("A program that itself exits 127 reads as `LaunchFailed` too"), and `output()` would inherit it.

**Why the sentinel exists:** `runtime/common/proc.saw` launches with `fork` + `execvp`, and a child whose exec fails `_exit(127)`s, "which std maps back to a launch failure". The sentinel can't be separated after the fact.

**The usual fix, inside the runtime's spawn:** a status pipe opened with `O_CLOEXEC` before the fork.
- In the child, after a failed `execvp`, `write` the errno to the pipe, then `_exit`. `write` is async-signal-safe.
- In the parent, close the write end and `read`. EOF means the exec succeeded, since the pipe closed on exec, so the exit status is the program's own, 127 included. Four bytes are the exec's errno, classified like any other: `ENOENT` → not found, `EACCES` → permission denied.

That removes the sentinel and also recovers the cause that `LaunchFailed` hides today. It's a change to both runtime trees and the spawn seam's contract (`ABI.md`), so it belongs in its own issue, not this port. But it's the reason I wouldn't build `output()`'s contract on top of the 127 rule.

**Air: SL-596.p1 approved, with two findings for their own issues.** Reviewed on origin/main 5524f47db plus r1; probes in `air-review/sl596p/`.

**The behaviour matches the docs at -O0 and -O2** (`o1_behaviour.saw`, in a group task):
- `sh -c "echo hi; exit 3"` → `"hi\n"`, code 3, `success()` false;
- `yes | head -c 2000000` → length 2,000,000, code 0, so the drain reads everything with no pipe-full stall;
- `kill -9 $$` → code 137;
- `printf '\377'` → `Err(output failed (invalid argument))`, as documented;
- `merge_stderr()` on `echo a; echo b >&2; echo c` → `"a\nb\nc\n"` in write order.

The non-UTF-8 and exit-127 choices are the lead's and SL-798's. The four `stage0-wrong` annotations name SL-596 and the frozen std's `Result<CommandOutput?, AllocError>`.

**Finding 1: a cancel during the wait phase leaves a zombie per call** (`o2_cancel_zombies.saw`).
- The setup: each child closes its stdout at once (`exec >&-; sleep 0.3`), so the drain ends; the task is cancelled 50 ms in; after 20 rounds and a pause past every exit, `waitpid(-1, WNOHANG)` reaps the leftovers.
- The result: `interrupted 20 of 20; zombies left for nobody: 20` at -O0 and -O2.
- The cause: `output()`'s cancel paths and its drain-failure path call `__saw_rt_proc_release`, which makes one `waitpid(WNOHANG)` and frees the record. A child still alive then exits into a zombie nobody collects.

The spec's ruling is "the child keeps running", which this keeps. "Unreaped" is a step beyond it: a long-running server that cancels `output()` calls leaks a process-table entry per cancel. `wait()` never had this, since it always reaps.

A std-only fix fits the ruling: keep a released-but-alive job on a locked orphan list instead of releasing it, and sweep the list with `__saw_rt_proc_try_wait` at each spawn (or each `output`/`wait`). The child keeps running and is still collected. Pin: `o2` reading 0.

**Finding 2: the spec's std overview no longer matches std.process** (LANGUAGE_SPEC.md §9, "Standard Library Overview").
