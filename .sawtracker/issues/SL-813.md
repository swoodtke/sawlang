## Description

**Port `std.json` to the new std: `JsonValue`, its parser and its writer.** The new std has no `std.json`; the module table in `compiler/resolve/src/loader.saw` (`load_new_std_modules`) lists none. This blocks the corpus rows SL-596 registered (K30, K27 and the json rows) and sawtracker's build under sawc2: a scratch probe on Oct 22 got sawtracker through parse and resolve with only `VoidTask` renamed and json stubbed.

**Scope (lead call, reversible):** the `JsonValue` tree only. That means the seven cases, `parse(text:max_depth:max_size:)`, `to_json_string()`, and the `is_`/`as_` accessors. It is what sawtracker uses: 92 `JsonValue.` uses, plus parse and `to_json_string`, and no serde. Stage 0's `JsonEncoder`/`JsonDecoder` serde conformances wait for a serde port, a separate issue to be filed when this lands; the parser and writer here are written so those can sit on top of them later.

**The design questions the brief settles at step 1:**
- **Shared accessors.** Stage 0's `as_array()`/`as_object()` take `&var self` with no shared version, so every read borrows exclusively. In the probe that was most of sawtracker's 231 `mutability.immutable` errors. Give them a shared version (`@synthesize(shared)` or a `&self` overload).
- **Lending a payload from a match.** sawc2 refused Stage 0's body `match self { case Array(items) -> { lend items } }` under `&var self` ("`items` is a pattern's binding, which is never written"). DF-146d says a borrowing `match` arm may lend its payload binding. Probe whether this is a sawc2 gap (then file it) or a rule (then the port spells it the ruled way).
- **Errors.** `DecodeError` carries the offset and a fault, `EncodeError` carries a fault, and both implement `Error` through `Printable.format`. Allocation failure follows the allocator policy (`Result`, never a panic).
- **Limits.** `max_depth` and `max_size` are kept, with Stage 0's defaults.
- **Floats.** Writing a `Float` goes through the new std's float formatting (design 253's Ryū). Say whether that exists in the new std or is a dependency.

**Pins:** a round trip of every case; each `DecodeFault`, by offset; the depth and size limits; interior NUL and non-ASCII text, escapes and surrogate pairs; allocation refusal under the denial allocator; the corpus rows that move (baseline recorded).

**Files:** `std/json.saw` (new), the loader's std table, `compiler/tools/std_cone.py`'s inputs if it needs them, the run-lane pins, `corpus_diff.tsv`. The gate runs std_cone, seed, units, golden, subset and fixture_whitespace.

**Scope addition (design conversation with the user, Oct 22): `String.c_string`, the String-to-C boundary.** It replaces Stage 0's `s as UnsafePointer<Int8>` cast, which sawc2 refuses, and the spec's closure-based `withCString`, whose paragraph is rewritten to this.

```saw
/// Lends the string's bytes as a C string, or `None` when the string holds a NUL byte.
public func c_string(&self) unsafe borrows -> &UnsafePointer<Int8>?
```

- **The body:** scan for a NUL; `return None`, or `lend self.bytes`. There is no copy: every String block ends in a NUL.
- **Call sites:** `if borrow let p = path.c_string() { … } else { … }`, and `borrow line.c_string()!` as an argument, which panics on an interior NUL.
- **`File.opened`** switches to it, which drops its hand-rolled NUL-checking copy. The same goes for any other std site that copies a path for C.
- **When SL-814 (fallible lends) lands,** `c_string` moves to `Result<&UnsafePointer<Int8>, InteriorNulError>`.
- **Pins:** both forms; the interior-NUL path; moving or reassigning the String inside the window, refused. Step 1 probes whether sawc2 already handles a conditional lend of a pointer field and the `borrow …!` value read at an extern argument.

Approved patch SL-813.p1 (revision 1)

**Air: SL-813.p1 approved.** Reviewed r1 on origin/main 4d99a98be.

**`String.c_string` lends a terminated pointer for every source** (`s1`, `strlen` through `borrow s.c_string()!` against `len()`, -O0 and -O2, ASan clean):
- empty, a literal, the head, middle and tail of a substring, an empty substring;
- an interpolation, `Int.to_string`, `Float.to_string`;
- a small and a 1000-byte builder.

The lend's soundness rests on the String layer's invariant that every block is `{ refcount, len, bytes, NUL }` and never written after it's built, so a substring is a new block, never a view. Both hold in `std/string.saw`.

**`JsonValue.parse` over 53 inputs** (`j1`; -O0, -O2 and ASan output identical, no reports):
- every accepted input writes, re-parses and re-writes to the same text: escapes, `\u` with surrogate pairs, raw UTF-8, `\u0000`, nesting, duplicate keys (the last wins), `5e-324`, `Int.min`/`Int.max`, and past-`Int` integers as `Float`;
- every malformed one is refused with an offset and a fault: trailing commas, leading zeros, `+1`, `.5`, `1.`, `1e`, `NaN`, `Infinity`, single quotes, raw control characters, bad and short escapes, lone surrogates, unquoted keys, missing colons, unclosed containers, truncated literals, a BOM, empty and blank input;
- `depth-65`, and nesting 5000 deep for arrays and objects, stop at `TooDeep` at the 64th level, with no recursion past it.

**Corpus and records:**
- 12 rows → pass, none → `wrong`, and the new refusals sit at their real gaps (serde names, the conditional-lend MIR face, `Map`'s writable `[]`).
- `hello.ll` moves by renumbering only.
- `sawc2.cone` gains exactly what `File.opened` now calls (`String.c_string`, `index_of`, `Optional.is_some`).
- No `std/` or `compiler/` source imports `std.json`, so the seed, which has no `json` loader line, is unaffected.
- The `due` program `string_c_string_absent_path` is a typed `backend.not-yet` pin, and Stage 0 can't parse it, so it has no record pair.

**Gates:**
- `run.py --only subset,std_cone,std,resolver,typechecker,programs,sanitize` passes.
- `gmgate` is green after the moves.

**Two notes, neither blocking:**
1. `1e400` and `-1e400` parse, as infinities, but the same library's writer then refuses the value (`write refused … no representation in this format`). `DecodeFault.OutOfRange` exists, so refusing at the parse would keep every parsed tree writable. That's the lead's call.
2. On the `coro_conservative_callee_*` pair, the loss is narrower than "no longer exercises the closure path". Each file covers TWO families. `sl306mod.Folder.apply`, a user method calling a function value, still reaches the conservative rule. Only the std family, `JsonValue.to_json_string`, is now vacuous, and its `EXPECT-IR-ABSENT: __Frame_JsonValue__write` passes trivially. The files' header comments still describe JSON's writer as "a recursion inside a `Vector.each` closure", which is now untrue, worth fixing whenever those files are next touched.
