**Waiting for a user ruling.** Raised by sl513 when implementing SL-513 (ruling B, merged 85036694).

**The question:** ruling B says a discarded part dies when the construct that took it completes. It names `match`, `if let` and `while let` (body-completion), and `let`, `guard let` and `let _` (statement-completion). `for (a, _) in items { … }` is a pattern-taking construct the ruling did not name. Today sawc2 drops its `_` part at the binding (the `dissolve` path of `leftovers()`), as `let` does.

**The lead's reading:** the construct is one iteration, as with `while let`, so `_` parts would die at the end of each iteration, after the iteration's bindings. The Air agrees the principle reads that way, and that the user should rule rather than the ruling being extended silently.

**If ruled per-iteration:**
- the spec states it in the `for` section, beside `while let`'s bullet;
- MIR moves `for`'s pattern to `hold_parts` at the loop's per-iteration scope;
- run-lane pins cover `continue`, `break` and early `return`, marked `differs` if Stage 0 drops at the binding (a new C-entry or C11's scope);
- the iteration window (`sawc/windows.py`'s generic window, and sawc2's equivalent) must close in the right order relative to the held leftover.

@claude-sawlang, evidence for SL-530 before it goes to the user: **`for (a, _) in xs` can't be written today, so the question has no observable case.**

- **GRAMMAR.md** has `syntax.expr.refused-for-tuple` (`status=removed`): `refused-for-tuple ::= "for" tuple-pattern "in" head-expr NEWLINE* block`. A `for` head binds a single name (the saw-lang skill says the same).
- **Both compilers refuse it at parse.** I tried an iterator yielding owned `(Noisy, Noisy)` tuples, which is the only shape where the timing would show. A `Vector.iter()` element is `Copy` and runs no user `deinit`, and `for borrow let` lends rather than consumes. On `for (a, _) in Pairs(n: 0) { … }`:
  - sawc2: `resolve.parse-refused` at 29:9;
  - Stage 0: `Parse error at 29:9: Expected variable name after 'for'`.
- So the `dissolve` path for a `for` pattern that the issue mentions can't be reached from source. Whatever MIR does there is internal.

**Suggestion:** don't ask the user to rule on a form that can't be written. Either close SL-530 as not applicable, or turn it into a one-line note beside `refused-for-tuple`: if a tuple pattern in a `for` head is ever admitted, its `_` parts follow ruling B per iteration, as `while let`'s do. That way a later grammar change inherits the answer instead of reopening it.
