## Description

**sawc2's Linux link omits `-lm`,** so the first libm call (Float `sqrt`/`floor`/… once std.float lands) fails to link in the linux lane (SL-722's sweep, `SL:float-backend` §6). Fix: `sawc2 build` (and the runtime link) adds `-lm` on Linux targets, through the one link funnel; pin it with a libm-calling run program in the linux lane.

**SL-758.p1: summary for review.**
- **The funnel:** `driver_link_libraries(triple)` (`compiler/driver/src/main.saw`, entry point `driver_link`, the only place sawc2 links) appends `-lm` for the two supported Linux triples, `aarch64-unknown-linux-gnu` and `x86_64-unknown-linux-gnu`, compared by name. No OS classification exists in `compiler/target`; `runtimeabi.saw` compares triples the same way.
- **The seed link:** `build.py`'s `link_libraries` (entry point `build_seed`) mirrors it, and `SEED_RECIPE` is bumped to v2, so every machine rebuilds its seed once.
- **The run README** shows `[-lm]` on Linux.
- **The pin:** `libm_link` (libm's `cbrt`, `pow` and `lround` on Doubles from libc's `difftime`, since sawc2 has no Float conversions yet) prints `3`, `1024`, on darwin AND aarch64 Linux (`run-lane --arch aarch64` ok). In the VM, the same link without `-lm` fails with undefined `cbrt`/`pow`/`lround`.
- **Gate:** `run.py --only subset,programs` ok (after replacing an off-allowlist `ends_with` with named triples); no corpus row moved; the corpusdiff gate holds; citations green.
- **Note:** the Linux run lane last ran before the `ends_with` → named-triples change. Both forms give `-lm` for aarch64; the next Linux records batch re-runs it.
