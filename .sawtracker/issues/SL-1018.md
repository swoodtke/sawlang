The probe below, built with sawc at 857d7fcd2-era std (the SL-1003 review tree), prints `write to the second file FAILED: write failed (invalid descriptor)`.

```saw
import std.data.{Data}
import std.file.{File}
import std.path.{Path}

struct W { f: File, n: Int }
@synthesize extension W: ExplicitCopy {}

func make_and_copy() unsafe -> W {
    let w = W(f: try! File.create(path: Path(s: ".../first.txt")), n: 1)
    let c = w.copy()
    move c                      // `w` dies here and closes descriptor N
}

func main() unsafe {
    let c = make_and_copy()
    let g = try! File.create(path: Path(s: ".../second.txt"))   // reuses N
    let _ = move c              // the copy's deinit closes N again: g's file
    var d = Data()
    let _ = d.push(value: 65)
    match g.write(data: move d) {
        case Ok(n) -> print("write to the second file: ok, {} byte(s)", n),
        case Err(e) -> print("write to the second file FAILED: {}", e),
    }
}
```

- The synthesized `copy()` duplicates `File`'s `descriptor` bitwise. `File` is `NoCopy` (std/file.saw:320) and has no copy of its own, so there is nothing correct it could call.
- Both copies' deinits then close the same number. The second close lands on whatever the number names by then. Here that's another `File` the program holds, so its writes fail with EBADF. Had the number been reused once more before the write, they would land in the wrong file.
- So this is a resource-safety hole, not only an unchecked assertion. The Vector case runs clean, as you found, because `Vector`'s copy is real.

Since it touches a safety guarantee, the fix brief owes its conformance rows first. The row could be: a `@synthesize` copy-policy conformance is refused when a member's own policy can't supply it, naming the member, with File and Vector members, an enum payload, a generic instantiation and a tuple. **Implementation detail (lead, Nov 12): a `@synthesize` copy policy joins the derivation funnel, so it is refused at its head when a member cannot supply the copy.**

**The hole (the Air's c3 above):** `struct W { f: File, n: Int }` with `@synthesize extension W: ExplicitCopy {}` builds, and the derived `copy()` duplicates `File`'s descriptor bitwise; both deinits close it. That is a double close of an unrelated file, a resource-safety hole.

**The rule (spec, "The Copy Trait Family" and "Synthesized conformances").** A declared copy policy with no `copy()` body is an assertion that the members qualify:
- `@synthesize extension T: Copy {}`: every stored field, and every case payload of an enum, meets `Copy` (so a `Vector` member is refused: a silent transfer would spend a deep copy nothing names).
- `@synthesize extension T: ExplicitCopy {}`: every one meets `ExplicitCopy` (every `Copy` type does; a `NoCopy` member such as `File`, `Box` or `Mutex` does not).
- A member whose type names a type parameter meets it only through a bound, on the type or on the extension's head.
- A conformance with a hand-written `copy()` is not checked: that body is the author's.

**Where: the DERIVATION FUNNEL** (`compiler/typecheck/src/checks.saw`, `check_derivations` → `check_derivation`, ENTRY POINT `tc_check_derivations`). Today it checks only `@synthesize`d `Serialize`/`Deserialize`, with `satisfies(t, c.trait_decl, d, c.ext, c.module, in_test)` per stored field and the refusal `synthesize.member` (`refuse_underivable`). `satisfies` already answers `Copy` and `ExplicitCopy` from the tier table, with the extension's conditions in scope (`tier.saw`: `nominal_satisfies`, `tier_is_copy`, `param_satisfies`), so the copy policies need no new judgement, only to be asked.

**The change.**
1. `compiler/typecheck/src/conform.saw`, `derived_requirement(at)`: also answer for a conformance whose trait is `self.known.copy` or `self.known.explicit_copy`, returning the `copy` requirement when its status is `TcStatusKind.Synthesized`. Read how the status rows record `copy` for each of the two traits before writing the test (dump them for `std/process.saw`'s `CommandByteOutput` and `std/data.saw`'s `DataIterator`); if the `parent == c.trait_decl` test doesn't hold for one of them, STOP and report what the rows hold.
2. `checks.saw`, `check_derivation`: for a copy policy,
   - a struct: each stored field, judged on `self.member_type(t)` (an interior-mutability cell contributes its payload's tier, as `classify` reads it), must `satisfies` the conformance's trait;
   - an enum: each case's each payload parameter, the same way (the serde branch's `check_raw_backing` stays serde-only);
   - refuse through `refuse_underivable`, which for an enum payload says "case `NAME`'s payload of type `T`" where a struct says "field `NAME` of type `T`". Rule id `synthesize.member`, at the conformance's head, one refusal per blocking member.
3. Rewrite the funnel's leading comment: it now covers `Serialize`, `Deserialize`, `Copy` and `ExplicitCopy`; Equatable, Comparable and Hashable stay lazy (mono's `synthesize.unmet-member` at the comparison, which the spec's Equality section states). Keep the ENTRY POINTS list.
4. No MIR, mono or std change.
