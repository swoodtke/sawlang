```saw
import std.data.{Data}
import std.file.{File}
import std.path.{Path}

struct W { f: File, n: Int }
@synthesize extension W: ExplicitCopy {}

func make_and_copy() unsafe -> W {
    let w = W(f: try! File.create(path: Path(s: ".../first.txt")), n: 1)
    let c = w.copy()
    move c                      // `w` dies here and closes descriptor N
}

func main() unsafe {
    let c = make_and_copy()
    let g = try! File.create(path: Path(s: ".../second.txt"))   // reuses N
    let _ = move c              // the copy's deinit closes N again: g's file
    var d = Data()
    let _ = d.push(value: 65)
    match g.write(data: move d) {
        case Ok(n) -> print("write to the second file: ok, {} byte(s)", n),
        case Err(e) -> print("write to the second file FAILED: {}", e),
    }
}
```

**Implementation detail (lead, Nov 12): a `@synthesize` copy policy joins the derivation funnel, so it is refused at its head when a member cannot supply the copy.**

**The hole (the Air's c3 above):** `struct W { f: File, n: Int }` with `@synthesize extension W: ExplicitCopy {}` builds, and the derived `copy()` duplicates `File`'s descriptor bitwise; both deinits close it. That is a double close of an unrelated file, a resource-safety hole.

**The rule (spec, "The Copy Trait Family" and "Synthesized conformances").** A declared copy policy with no `copy()` body is an assertion that the members qualify:
- `@synthesize extension T: Copy {}`: every stored field, and every case payload of an enum, meets `Copy` (so a `Vector` member is refused: a silent transfer would spend a deep copy nothing names).
- `@synthesize extension T: ExplicitCopy {}`: every one meets `ExplicitCopy` (every `Copy` type does; a `NoCopy` member such as `File`, `Box` or `Mutex` does not).
- A member whose type names a type parameter meets it only through a bound, on the type or on the extension's head.
- A conformance with a hand-written `copy()` is not checked: that body is the author's.

**Where: the DERIVATION FUNNEL** (`compiler/typecheck/src/checks.saw`, `check_derivations` → `check_derivation`, ENTRY POINT `tc_check_derivations`). Today it checks only `@synthesize`d `Serialize`/`Deserialize`, with `satisfies(t, c.trait_decl, d, c.ext, c.module, in_test)` per stored field and the refusal `synthesize.member` (`refuse_underivable`). `satisfies` already answers `Copy` and `ExplicitCopy` from the tier table, with the extension's conditions in scope (`tier.saw`: `nominal_satisfies`, `tier_is_copy`, `param_satisfies`), so the copy policies need no new judgement, only to be asked.

**The change.**
1. `compiler/typecheck/src/conform.saw`, `derived_requirement(at)`: also answer for a conformance whose trait is `self.known.copy` or `self.known.explicit_copy`, returning the `copy` requirement when its status is `TcStatusKind.Synthesized`. Read how the status rows record `copy` for each of the two traits before writing the test (dump them for `std/process.saw`'s `CommandByteOutput` and `std/data.saw`'s `DataIterator`); if the `parent == c.trait_decl` test doesn't hold for one of them, STOP and report what the rows hold.
2. `checks.saw`, `check_derivation`: for a copy policy,
   - a struct: each stored field, judged on `self.member_type(t)` (an interior-mutability cell contributes its payload's tier, as `classify` reads it), must `satisfies` the conformance's trait;
   - an enum: each case's each payload parameter, the same way (the serde branch's `check_raw_backing` stays serde-only);
   - refuse through `refuse_underivable`, which for an enum payload says "case `NAME`'s payload of type `T`" where a struct says "field `NAME` of type `T`". Rule id `synthesize.member`, at the conformance's head, one refusal per blocking member.
3. Rewrite the funnel's leading comment: it now covers `Serialize`, `Deserialize`, `Copy` and `ExplicitCopy`; Equatable, Comparable and Hashable stay lazy (mono's `synthesize.unmet-member` at the comparison, which the spec's Equality section states). Keep the ENTRY POINTS list.

**Reviewer note on the implementation detail (Air, Nov 12): one sibling the member rule cannot see. It needs a ruling before dispatch.**

The mechanism behind c3 is "a derived `copy()` duplicates a value whose release can't be duplicated". A `NoCopy` member is one way there. The type's own hand-written `deinit` over trivial members is another, and the rule in the detail accepts it, since every member qualifies:

```saw
struct Res { id: Int }

@synthesize extension Res: ExplicitCopy {
    func deinit(&var self) {
        print("release {}", self.id)
    }
}

func main() {
    let a = Res(id: 1)
    let b = a.copy()
    print("copied {}", b.id)
}
```

On origin/main today it builds and prints `copied 1`, `release 1`, `release 1`. With `id` a descriptor and the body a `close`, that is c3's double close with no `File` in sight: the spec's own `Res { fd: Int }` example plus `@synthesize`.

It isn't always wrong. A type whose members are all retained (`Arc`, `String`) and whose `deinit` only reports can want exactly this. So it is a choice, not an obvious refusal:
- **(a)** it stays the author's assertion, and the spec says so: `@synthesize` beside a hand-written `deinit` asserts that the `deinit` is right to run once per copy; or
- **(b)** `@synthesize` of a copy policy is refused when its conformance carries a hand-written `deinit`, and the author writes `copy()` too.

Either way the unit's matrix owes the cell: an accepted golden under (a), a refusal fixture under (b).

Probe: `.build/scratch/air-review/queue_nov12/synth_copy_own_deinit.saw` on the Air.

**User ruling (Nov 12, relayed by the lead), on the Air's note above: choice (b). A `@synthesize`d copy policy is refused when its conformance writes its own `deinit`.**

The user: "sure - refuse it - @synthesize is for trival types."

**Lead's reading of its scope (say so if it is wrong):** the ruling settles the case the Air raised, a derived `copy()` beside a hand-written `deinit`. It does not withdraw what the spec already derives over owning members: `@synthesize extension Snapshot: ExplicitCopy {}` over a `Vector<Int>` and a `String` field stays legal (the spec's own example), because each member's own `copy()` and release are the compiler's to pair. The hand-written `deinit` is the one thing a memberwise copy can't pair.

**Amendment to the implementation detail (this unit's design is otherwise unchanged).**

*The rule.* A conformance to `Copy` or `ExplicitCopy` that is `@synthesize`d (its `copy` requirement is `Synthesized`) and whose extension body writes `deinit` is refused at the conformance's head. The author writes `copy()` by hand beside the `deinit`, or removes the `deinit`.

*Where.* The same place as the member check: `check_derivation` in `compiler/typecheck/src/checks.saw`, for a copy policy, BEFORE the member loop. Whether the `deinit` is hand-written is read off the conformance's status rows: the `Deinit` requirement (`self.is_implicit(requirement)` identifies it, `conform.saw`) has a written body when its status is the hand-written kind and not the implicit synthesized one. Dump the status rows of the Air's program first to see which `TcStatusKind` a written `deinit` carries; if a written `deinit` can't be told from the implicit one there, STOP and report the rows.

*Refusal.* Rule id `synthesize.deinit` (the `synthesize` family exists; no lane change). Message:

> cannot derive `copy` for `Res`: its `ExplicitCopy` conformance writes a `deinit`, and a member-by-member copy would make a second value that `deinit` runs for; write `copy()` beside it, where what the `deinit` releases can be duplicated or shared, or remove the `deinit`

One refusal; when it fires, the member loop doesn't run for that conformance.
