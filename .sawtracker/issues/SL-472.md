The user's ruling (Oct 9, in the session; quoted, since agents can't post kind=ruling): 'For a non escaping closure capturing the vec by ref would be the correct behavior imo. For an escaping closure no captures should be modifiable ever.' The lead's reading of it as one rule: a by-value or move capture is a let binding inside the closure body, in every closure. The only way a closure changes outside state is a reference capture ([&var x]), which only a non-escaping closure may take.

Found: both compilers accept an escaping closure that moves in a Vector and writes v[0] = v[0] + 1. Copies of the closure (let g = f) then share and change the 'immutable' env: Stage 0 prints 2 3 4 for f(), g(), f(). The cause is that a capture takes its source binding's mutability, and design 132's lost-write rule carves out an index into a heap-backed container.

Scope:
(1) LANGUAGE_SPEC: replace design 132's 'assigning to a by-value capture' rule and its Vector carve-out with 'captures are let'. State the non-escaping [move v] idiom (var w = move v), and say that escaping closures keep no mutable captured state (Arc<Mutex<T>> is the way to change state across calls).
(2) Typecheck: a by-value or move capture is an immutable root in SL-462's place_verdict funnel (mutability.immutable), so x = v, x += v, x.f = v, v[i] = y, a &var self call and &var x of a capture are all refused by the one funnel. Design 132's separate check is deleted, with no second copy.
(3) The lead's readings, to confirm with the user: (a) &self interior-mutability methods (Mutex.lock, Atomic) on a captured value stay legal; (b) writes to a captured UnsafePointer's pointee stay legal, as SL-462's raw-pointer row.
(4) Tests: a matrix of capture kinds (plain, move, copy) x write kinds x closure kinds (escaping, non-escaping), plus the 2-3-4 program as a refusal fixture, the [&var v] non-escaping write accepted, and a nested non-escaping [&var x] of an outer capture refused.
