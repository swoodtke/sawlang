## Description

**User decision: which constants may be written directly as a const generic ARGUMENT?** Two forms the spec's text reaches for and GRAMMAR.md's generic-list grammar does not take. Raised by SL-457's design pass (its Q6) and by the lead's reading of the spec for its unit U3 (Nov 14). Neither blocks SL-457: U3 goes ahead with today's grammar.

**The grammar today** (GRAMMAR.md §5.2, `syntax.rule.generic-arg-value`): a generic argument that starts with an integer, `-`, `sizeof` or `alignof` is a value; one that parses as a type and is followed by `+ - * / %` is re-read as a value (`Ring<N + 1>`); otherwise it is a type, "and a bare name such as `N` is decided against the parameter it fills". No shift or bit operator (the list is closed by `>`), no cast, no call but the two layout queries.

**Form 1: a path that names a constant, as the whole argument.** `Buf<E.A>` (a raw-backed case), `cap<Int8.max>()` (an integer limit).
- Today: `type.argument-kind` / `type.not-a-type` / `name.undefined`. The rule decides only a BARE name against its parameter; a module-qualified static already works by an extension of it.
- `Buf<E.A + 0>` is re-read as a value by the rule above, and folds once U3 lands. A named `static` works today.
- Options: **(A)** decide any path against the parameter it fills: one that binds a static, a raw-backed case or an integer limit fills a value parameter. GRAMMAR's rule text widens from "a bare name" to "a path". **(B)** keep it a type; the author writes `E.A + 0` or names a static.
- Lead's recommendation: (A). A case is a constant by the spec's own words ("a backed case is a compile-time constant usable as an array length"), and telling a reader to write `+ 0` is the kind of thing the doctrine says an API should not ask.

**Form 2: an alias construction, `Buf<Count(8)>`.**
- LANGUAGE_SPEC "Distinct aliases": "the construction of a constant expression is itself a constant expression ... so it is accepted wherever a constant is", with a status note that "an array length, a repeat count and a const generic argument accept it only once those positions are folded by the same evaluator". The user's ruling of Oct 10 (SL-457 c3) says an alias constructor over a constant is a constant expression "in every constant position".
- A length and a repeat count take it since SL-457's U2a and U2b. A generic argument cannot: `Count(8)` is a call, and the generic-list grammar has no call but `sizeof`/`alignof`, so it is `resolve.parse-refused` before any folder sees it.
- Options: **(A)** the generic-list grammar admits an alias construction as a value atom (`NAME(const-expr)` where NAME is an alias of an integer type; it cannot be told from a generic type application by syntax alone, `Buf<Count(8)>` against `Buf<Pair(8)>`... so the decision is made against the parameter, as for a bare name). **(B)** the spec's sentence is narrowed: in a generic argument, an alias construction goes through a `static` (`static EIGHT: Count = Count(8)`, `Buf<EIGHT>`), as a shift does, and the Oct 10 ruling is read as "every position whose grammar is the constant grammar".
- Lead's recommendation: (B). The generic list is deliberately a small grammar (the shift ruling), a `static` is one line, and (A) puts a second kind of call in type-argument position.

**What U3 does meanwhile:** no grammar change; both forms keep today's refusals; the spec's two sentences are left as they are with their status notes pointing here.
