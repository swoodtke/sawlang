## Description

USE-AFTER-FREE: `Mutex(value: move v)` at a heap-owning payload FREES the payload at construction. Found on MAIN (`da84578e`) while building design 275 U3's ruled `Mutex` conformance row.

REPRO (main, exit 0, no diagnostic):

```saw
import std.mutex.{Mutex}

func main() {
    var v: Vector<Int> = [1, 2, 3]
    let guarded = Mutex(value: move v)
    print(guarded.lock({ items in items[0] }))   // prints garbage
}
```

`items.len()` reads 3 — the length word survives — and `items[0]` reads through a buffer pointer whose allocation was already released, so the value is whatever the allocator left there. Nondeterministic across runs.

MECHANISM (obligation 4). `Mutex<T>.init(value: T)` is

```saw
public init(value: T) unsafe -> Mutex<T> {
    Mutex<T>(state: UnsafeMutableInterior(0),
             value: UnsafeMutableInterior(value))
}
```

and the emitted `Mutex_init_value` reads:

    %value.1 = alloca %Vector
    store %Vector %value, %Vector* %value.1
    %value.dropflag = alloca i1
    store i1 1, i1* %value.dropflag          ; design 42: registered for cleanup
    %value.2 = load %Vector, %Vector* %value.1
    %.5 = insertvalue %Mutex undef, i64 0, 0
    %.6 = insertvalue %Mutex %.5, %Vector %value.2, 1     ; the payload moves IN
    %value.needsdrop = load i1, i1* %value.dropflag        ; …and the flag is STILL 1
    br i1 %value.needsdrop, label %drop.value, ...
    drop.value:
      call void @Vector_deinit(%Vector* %value.1)          ; the buffer is freed here
    ret %Mutex %.6                                         ; …and returned anyway

An `init`'s by-value parameter is registered for scope-exit cleanup and the flag is cleared by whatever CONSUMES it. Here the consumer is `UnsafeMutableInterior(value)` — a cell CONSTRUCTOR whose argument is the payload — and the transfer into it is not recognised as the move that retires the parameter, so the parameter is released at the end of the init body while its bytes have already been copied into the returned struct.

CLASS — every constructor whose parameter is consumed only by an `UnsafeMutableInterior(...)` construction, at every heap-owning payload:
- `Mutex<Vector<Int>>`, `Mutex<Data>`, `Mutex<String>`, `Mutex<Map<..>>` — measured on `Vector`;
- `Once<T>`'s `set` path and `SpinLock<T>`'s own initializer are the neighbours to probe (they take the same shape);
- a USER type following the design-186 interior-mutability idiom (`struct Counter { cell: UnsafeMutableInterior<Int> }` with an `init`) is the same shape, and is only invisible at `Int` because a trivial payload has no `deinit` to run.
A payload with no `deinit` (`Mutex<Int>`, `Mutex<Bool>`) is unaffected, which is why the whole corpus passes: every `Mutex` in the tree guards a trivial or refcount-free payload.

WHY IT SURFACED NOW: design 275 U3's ruled conformance row is "a `for` over the guarded collection inside `lock` is a sync window and works" — the first program in the tree to put a heap-owning container inside a `Mutex`.

PIN: `examples/conformance/K141_mutex_guarded_for_is_sync.saw` (XFAIL, citing this issue). Its XPASS flip is the validation; the paired REFUSAL half (a suspension inside a `lock` body is refused by the `sync`-body rule) is `examples/errors/mutex_guarded_for_suspends.saw` and passes today.
