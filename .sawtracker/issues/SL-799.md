## Description

**A cancelled `Command.output()` leaves an unreaped zombie per call** (the Air, SL-596.p1 review; probe `air-review/sl596p/o2_cancel_zombies.saw`: `interrupted 20 of 20; zombies left for nobody: 20` at -O0/-O2). `output()`'s cancel paths and its drain-failure path call `__saw_rt_proc_release`, which does ONE `waitpid(WNOHANG)` and frees the job record; a child still alive then exits into a zombie nobody collects. The spec rules "the child keeps running" on a cancel, which this keeps, but a server that cancels `output()` calls leaks a process-table entry per cancel. (`wait()` always reaps.)

**Fix (std-only, within the ruling):** a released-but-alive job goes on a locked ORPHAN LIST instead of being freed, and the list is swept with `__saw_rt_proc_try_wait` at each spawn (or each `output`/`wait`), reaping exited children and freeing their records. The child still runs and is still collected. Check every other path that calls `proc_release` (obligation 4). Pin: `o2` reads 0.

Also from the same review, for SL-596's doc pass: the spec's §9 std overview still describes Stage 0's `std.process` (`run()`, `ProcessError`, `ProcessError.cancelled()`, `env(name:value:)`), whereas the new std has `wait()`, `SystemError.Interrupted` on a cancel, and no `env`. Reconcile the overview with the shipped surface.

**Air: SL-799.p1 approved.** Reviewed on origin/main 22b9bbb11 plus r1, at 20 runs per level each:
- **The pin** `process_output_cancel_reaps_child`: `interrupted 20 of 20`, `zombies left for nobody: 0`. My SL-596 `o2` read 20 before.
- **`o3_sweep_keeps_running`** (mine, `air-review/sl799p/`): ten cancels whose children sleep 300 ms and ten whose children sleep 1.5 s, then a spawn at about 600 ms and another after 1.5 s. The result is 0 zombies after each sweep. The first sweep reaps the exited orphans and KEEPS the running ones, which the second reaps. The keep-in-order compaction and the free-on-empty both hold.
- **My SL-596 `o2`**, which spawns nothing after its last cancel, now reads **7**. Those are the children that exited after the final spawn, which nothing has swept yet. That's the documented contract ("a later spawn reaps it once it has exited"), bounded by the cancels within one child's lifetime. No longer a leak that grows with every cancel.
- **`o1_behaviour`** is unchanged: exit codes, the 2 MB capture, 137, non-UTF-8, and merge order.

**The code:**
- `process_abandon` reaps a child that already exited and orphans a live one.
- The sweep only polls, so the `Mutex` is never held across a wait; a contended lock blocks a task's thread for one poll pass, as the spec's `Mutex` note allows.
- Both cancel paths come after the drain's EOF, so an orphan's held read end is harmless.
- An allocation refusal falls back to the old release for that one child.
- The drain-failure path's plain release is documented and filed as SL-800.
