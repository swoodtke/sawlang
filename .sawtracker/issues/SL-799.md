## Description

**A cancelled `Command.output()` leaves an unreaped zombie per call** (the Air, SL-596.p1 review; probe `air-review/sl596p/o2_cancel_zombies.saw`: `interrupted 20 of 20; zombies left for nobody: 20` at -O0/-O2). `output()`'s cancel paths and its drain-failure path call `__saw_rt_proc_release`, which does ONE `waitpid(WNOHANG)` and frees the job record; a child still alive then exits into a zombie nobody collects. The spec rules "the child keeps running" on a cancel, which this keeps, but a server that cancels `output()` calls leaks a process-table entry per cancel. (`wait()` always reaps.)

**Fix (std-only, within the ruling):** a released-but-alive job goes on a locked ORPHAN LIST instead of being freed, and the list is swept with `__saw_rt_proc_try_wait` at each spawn (or each `output`/`wait`), reaping exited children and freeing their records. The child still runs and is still collected. Check every other path that calls `proc_release` (obligation 4). Pin: `o2` reads 0.

Also from the same review, for SL-596's doc pass: the spec's §9 std overview still describes Stage 0's `std.process` (`run()`, `ProcessError`, `ProcessError.cancelled()`, `env(name:value:)`), whereas the new std has `wait()`, `SystemError.Interrupted` on a cancel, and no `env`. Reconcile the overview with the shipped surface.

**Implementation detail (lead, Nov 12): what is left of SL-799 is the probe's flake; the std fix landed in p1 and the spec half is done.**

**State.**
- The orphan list landed as SL-799.p1 (`std/process.saw`: `process_abandon`, `process_sweep`, `orphans_push`, `orphans_sweep`).
- The spec's std overview no longer names `ProcessError`, `run()` or `env(name:value:)` (the SL-1000 spec review rewrote it), so the issue's second half is closed.
- Open: `compiler/tests/run/probes/process_output_cancel_reaps_child.saw` is load-sensitive. On Nov 11 the server gate for SL-1058.p1 r2 failed only on it, at -O2, printing `zombies left for nobody: 1`.

**Mechanism (UNVERIFIED until step 1 reproduces it).** The probe decides "every child has exited" by the end of file on the children's pipe (`await_exits`). A process closes its descriptors during exit BEFORE it becomes waitable, so the end of file can arrive while one child is still not a zombie. The one sweeping spawn then polls that orphan with `__saw_rt_proc_try_wait`, finds it running and keeps it; the child becomes a zombie a moment later, and `leftovers()` (`waitpid(-1, WNOHANG)`) counts it. std did nothing wrong: its contract is "a later spawn reaps it once it has exited", and the probe swept once, too early.

**The fix is in the probe alone; `std/` does not change.** The probe must stop inferring "exited" from the pipe and instead observe "reaped", which needs each child's pid:
1. Each child reports its pid instead of the byte `x`: the shell line becomes `exec 1>&-; printf '%s\n' $$ >&2; read gate` (`$$` is the spawned `/bin/sh` itself, the direct child). One short line is one atomic pipe write, and rounds launch one child at a time.
2. `look()` parses the stream: decimal digits accumulate, a newline completes one pid. The count of completed pids replaces the byte count `STARTED` (`await_started(round + 1)` keeps its meaning). The pids are kept in a collection `main` owns and passes down by `&var` (a `Vector<Int32>`, or a fixed `[Int32; 20]` plus a count); a partial line must survive between two `look()` calls, so the accumulator lives beside the collection, not in a local.
3. `await_exits()` stays as it is: the end of file still bounds the wait for the children to start exiting.
4. The single sweeping spawn becomes a loop with the probe's usual deadline (`DEADLINE_TICKS` ticks of `TICK_MS`): spawn and `wait()` the `exit 0` sweeper (each spawn runs `process_sweep`), then test every recorded pid with `kill(pid, 0)` (`extern "C" { func kill(pid: Int32, signal: Int32) -> Int32 }`). A pid that still answers 0 exists, running or zombie; -1 means it has been reaped. Leave the loop when every pid answers -1; sleep one tick and go round otherwise; at the deadline `panic("{} children were never reaped within 10 s", remaining)`.
5. The two `// prints:` lines and the final `leftovers()` line stay. After the loop std has reaped all twenty, so `leftovers()` reads 0 by construction and now only guards against a child nobody tracked.
6. Rewrite the header comment's last sentences to say what is observed: the sweep is repeated until no recorded pid exists, because a child's descriptors close before it can be waited on. Present tense, no history (CLAUDE.md "Code comments").

**Why this is deterministic.** Nothing but std reaps the orphans until the final line, so a real leak (std never reaping an exited orphan) keeps `kill(pid, 0)` at 0 forever and ends in the deadline panic, and the early-sweep race can no longer produce a wrong count. A pid being reused inside the loop's milliseconds is not a practical risk.

**Expected outcomes.**
- Before the change, under load, at least one run in a few thousand prints `zombies left for nobody: 1` (the SL-975 method: 200 runs at a 1-minute load average above 20; `.build/scratch/p975/probe_stall.py` in the main checkout is the earlier harness). If it does not reproduce in 3,000 runs per level, record the counts and go on: the change removes the race by construction.
- After the change: 3,000 runs per level under the same load, every run printing exactly the two stated lines.
- A mutation check: with `process_sweep()`'s call in `Command.spawned` commented out in a scratch copy of std (`--std-root`), the probe ends in the deadline panic, not in a pass. Don't commit the mutation.
- Files changed: the probe only. `compiler/tests/run/` goldens (`hello.ll` and the others) must not move.

**Closing.** When this lands the issue closes; SL-800 keeps the drain-failure remainder.
