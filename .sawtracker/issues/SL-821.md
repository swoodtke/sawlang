## Description

**A wait that blocks the thread without driving it hangs when that thread's own cooperative tasks are what it waits for.** Found by p809 (SL-809 step 1, Oct 22), in probes `c1_sync_main_pool_join` and `c1c_thread_body_pool_join`. A non-suspending `main` (or a `Thread.spawn` body) joins a pool task, and that task receives from a cooperative sender on the joining thread.

`await_task`, with `sweeps == 0`, blocks in `pthread_cond_wait`, so the ready sender never runs. The pool workers' deadlock walk correctly sees the sender as runnable, so nothing is reported, and the program hangs.

Controls:
- `c1b`, the same with a suspending `main`, joins correctly (`joined 5`);
- `c1d`, with no cooperative task at all, gets the deadlock report.

The spec says such a join blocks the thread. It doesn't say what happens when the thread's own ready tasks are what the join needs. "Never hide errors": a silent hang is the worst outcome.

**Options (a language/runtime decision):**
- **(a)** A blocking wait DRIVES when its thread owns live cooperative tasks. c1 then works. This changes the spec's "blocks the thread" wording for that case.
- **(b)** The deadlock walk counts a thread's cooperative frames as blocked while that thread sits in a wait that doesn't drive. c1 then becomes a deadlock report naming the waits.

**Scope once ruled:** the obligation-4 sweep over every blocking wait (pool join, `Thread.join` from a sync context, `Mutex` waits?, a blocking channel op from sync code), the fix, and pins from p809's c1 probes (in SL-809's worktree history).

**Air, for the ruling: (a) is the consistent choice, because a sync context's cooperative join already drives.** In my SL-797 probes (`air-review/sl797/x2_one_thread.saw`, `x3_two_threads.saw`, clean on main since SL-793), a `Thread.spawn` body (no task, no suspension) does `TaskGroup()`, spawns, and calls `h.join()`. That join DRIVES the thread's own group until the task finishes. It doesn't block the thread on the task. SL-806 made the background group per-thread on the same principle: a thread's cooperative tasks run on that thread and nowhere else.

So today, in a sync context:
- a cooperative `Task.join()` drives the thread's own tasks;
- a POOL `Task.join()` blocks in `await_task`'s `pthread_cond_wait`, even when the pool task is waiting on one of those tasks: c1's hang.

(a) puts the pool join on the same footing as the cooperative join: when the joining thread owns live cooperative tasks, the wait drives them, which is SL-793's design D extended from "on an executor thread" to "on a thread that owns cooperative tasks". The program then does what it was written to do, and no wait that could finish is reported as a deadlock.

(b) would report c1 as a deadlock, but it isn't one: the thread holds the runnable sender and simply declines to run it. Under the confirmed SL-809 wording ("no task anywhere can run"), that report would be false, since a task CAN run if the thread drives.

For the sweep under (a): `Thread.join` from a sync context (its blocking twin is thread context by definition, so it may keep blocking, but if the thread owns live cooperative tasks the same hang shape applies), a pool group's teardown (SL-806's `drive_on_exit` already drives on a driving thread; extend it to "owns cooperative tasks"), and `Mutex` (it stays blocking by the spec's documented rule, with a window that never holds a suspended task, so it can't be this shape).
