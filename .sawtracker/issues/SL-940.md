## Description

**sawc refuses every use of `FuncPointer`, and a static cannot hold a function value, though the spec calls `FuncPointer` implemented.**

Found by SL-933 (p933b's probes, in `.build/scratch/p933b/ops_static_*`, `ops_funcpointer_*`).

**What fails** (`sawc build -O0 --no-hidden-alloc`, hosted; all are typecheck refusals):
- A struct field of type `FuncPointer` gives `name.undefined: cannot find FuncPointer in scope`. The resolver lists the name (`compiler/resolve/src/prelude.saw`), but the typechecker has three not-yet refusals: "a function passed as a `FuncPointer`", "a closure where a `FuncPointer` is expected", and "calling a `FuncPointer`" (`compiler/typecheck/src/bodies.saw`).
- A static initialized with a named function, or a capture-free closure, gives `static.not-constant`.
- A plain function-value field in a static also gives:
  - `static.immortal`, since a closure type may own an environment;
  - `static.not-sync`, on the `let` static.

**Why it matters:** an operations table (a set of function values reached only through one installer) should be a constant static, so a program that never calls the installer links none of the functions, and installing it allocates nothing. std uses heap-slot tables instead:
- `PANIC_REPORT`/`install_panic_report`;
- after SL-933, Channel's `GateEngine`, TaskGroup's `PoolEngine` and `OFFLOAD_CHECK`.

Each costs a one-time allocation and an extra failure path (`AllocError`/`ChannelError.Alloc`).

**Acceptance:**
- `FuncPointer` works per the spec: declarable, assignable from a named function or a capture-free closure, and callable.
- A static (or `unsafe static var`) of a struct with `FuncPointer` fields is const-initializable from named functions. This must work under `--freestanding --no-hidden-alloc` too.
- `nm` shows that a function named only by such a static is not linked when nothing reaches the static.
- Then convert the four std tables above to statics, and drop their allocations and failure paths.

**Air: SL-940.p1, changes requested.** One defect, in the refusal message. Every refusal it guards is correct, and everything I ran through a `FuncPointer` works. Reviewed r1 on eaea726ce.

**The defect: `funcpointer.not-sync`'s fix-it can't be followed for two kinds of function.** The check (`bodies.saw`, the `declares_blocking(d) || effects & SYNC == 0` branch) always says "`X` is not declared `sync`, so it cannot be a `FuncPointer`: a code address has no frame for a suspending body to run out of … Declare it `func X(...) sync`".
- **A `blocking` function** (`sl940p/x3_blocking.saw`, `func slow(n: Int) blocking -> Int`) gets that text. But the reason is that it blocks, not that it suspends, and the fix-it can't be written: `func slow_sync(n: Int) sync blocking -> Int` is a parse error (`syntax.rule.effect-slot`). The spec already words this case: "A blocking function cannot be taken as a function value".
- **An `extern "C"` function** (`sl940p/o1_ownership.saw` with `labs`) gets the same fix-it, and `func labs(x: Int) sync -> Int` inside the extern block is a parse error too (`x1_extern_sync.saw`). Yet a plain extern is `sync`-callable: `func through(x: Int) sync -> Int { labs(x) }` compiles, runs, and coerces to a `FuncPointer` (`x2_extern_in_sync.saw`, prints `9` and `4`).

Either way, each class needs its own message and a fixture:
- **blocking:** name `blocking` as the reason, with no fix-it that asks for `sync`.
- **extern:** either take a plain (non-`blocking`) extern in (see the question below), or refuse it with text that works, such as "wrap it in a `sync` function".

**A question for the user, not a blocker:** should a plain `extern "C"` function coerce to `FuncPointer`? Passing a C function as a C callback (`free` as a destructor, `strcmp` as a comparator) is the classic use. Form 2's "declared `sync`" can't apply to an extern, since no extern can be declared `sync`, and the spec doesn't mention externs. Today a wrapper is the only route.

**What passes** (`sl940p/o1_ownership.saw`): ASan at -O0 and -O2, identical output, clean.
- **By value through a pointer:**
  - an owning `String` in and out (`hey!`);
  - a NoCopy moved in, dropped exactly once inside the callee (`drop res 1` before `consumed 10`);
  - a NoCopy returned, dropped once at scope end;
  - an ExplicitCopy round trip with **no** copy made.
- **By reference:** a `&var Int` bumped (`42`) and a `&Res` read.
- **Containers and sources:**
  - `static TABLE: [FuncPointer<…>; 4]` from three named functions and a literal, indexed at run time, plus a function returning `TABLE[i]` (`60`);
  - `FuncPointer?` holding `Some`/`None`, and a `Vector` of a named function and a literal;
  - an `@export … sync` function.
- **Calls:** a generic `apply<T>(p: FuncPointer<(T) sync -> T>, x: T)` (`42`); two named functions give distinct `address()`es; a pointer called from a `TaskGroup` task after a `yield_now()` (`100`).

**Notes, not blocking:**
- An `@export` function not declared `sync` is refused, though export checking already proves it suspension-free. That's consistent with the spec's "declared `sync`", so it's just a remark.
- A `static func` as Form 2 (`Math.negate`) is `slice.not-yet` (`syntax.expr.member`). If the user means static members as named functions, that's SL-950's territory.
