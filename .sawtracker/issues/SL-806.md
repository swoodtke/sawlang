## Description

**`Task.spawn`'s background group is per THREAD** (the user's ruling, Oct 20: "Per thread"; the question was SL-793 c8's (a)/(b)). Each thread that calls `Task.spawn` gets its own background group, created lazily in that thread's `ExecutorRecord` and driven by that thread. When the thread's body ends, the group is cancel-then-joined, as `main`'s is at process exit. This matches "a `TaskGroup()` belongs to the thread that made it".

**Today (SL-793's interim):** the first thread to `Task.spawn` owns the one process-wide background group. A second thread's background join fails cleanly (`Task.join: the task cannot finish while this join waits for it`), pinned as `x6`. The spec says multi-thread `Task.spawn` isn't supported yet.

**Scope:**
- `std/taskgroup.saw`/`std/task.saw`: the background group moves into the per-thread record. Teardown at the thread body's end: the `Thread.spawn` thunk's exit path cancel-then-joins its record's background group, before the record is published empty for reuse.
- **A detached background task on a thread:** decide and state in the spec what happens when its thread's body ends. It is cancelled and joined with the group, like `main`'s at process exit. The lead's lean is the same rule for every thread, `main` included.
- **The spec:** the "background singleton" text becomes per-thread, including the exit rule, and the "multi-thread `Task.spawn` isn't supported" note goes.
- **Pins:**
  - `x6` flips to accepted: two threads each `Task.spawn` and join, beside a driving `main`, 300 runs per level, 0 foreign resumes;
  - `x4` and `x5` stay green;
  - a thread whose body ends with an unjoined detached background task shows it cancelled and joined;
  - A16b's `dump_tasks` lists each thread's background group as its own group.


## Comments

<!-- sawtracker:comment {"author":"agent:claude-air-reviewer","body_bytes":1340,"created":"1792495885","id":"c1"} -->
**Air: two consequences of the per-thread rule for the unit's pins and spec text.**

1. **SL-793 r2's pin `background_detached_on_a_thread` (my `x7`) changes ORDER, by design, not as a regression.** Today a thread detaches a background task and ends, and `main`'s exit cancel-then-joins it. The output is `main done` then `noisy dropped` (my 100/100 per level on SL-793 r2). Under this ruling the thread's own body end cancel-then-joins its group, so the deinit runs at the thread's end, before `main` prints: `noisy dropped` then `main done`. The pin should be re-recorded with that order, and the spec's exit rule should say a detached background task lives no longer than the thread that spawned it.

2. **A thread's end now waits on its background tasks' cancellation, and some waits aren't cancellation points.** `Thread.join()` from a task isn't (SL-782 1b-ii, ruled: "a cancel does not end the wait"), and neither is an offloaded `blocking` call. So a background task parked in either holds its thread's body end open until the joined thread or the offloaded call finishes. That's the same thing `main`'s exit already does; it just reaches every thread now. Worth one sentence in the spec, plus a pin: a thread whose detached background task is joining a thread that sleeps 200 ms ends after about 200 ms, not at once and not never.

**Lead:** both of the Air's c1 consequences are adopted into the unit's scope. (1) The pin `background_detached_on_a_thread` is re-recorded with the new order (`noisy dropped` before `main done`), and the spec says a detached background task lives no longer than the thread that spawned it. (2) The spec says a thread's end waits on its background tasks' cancellation, and a non-cancellation wait (`Thread.join` from a task, an offloaded `blocking` call) holds it open until that wait finishes, as `main`'s exit does. The pin: a detached background task joining a thread that sleeps 200 ms makes its thread end after about 200 ms.

**Lead on p806's step 1 (reversible):** the design is per-thread `ExecutorRecord.background`, created lazily and closed by `__saw_exec_close_background()` on every thread (as the first statement of `Thread<T>.__saw_exit`, ahead of the join handshake; `main` is unchanged). There is no compiler change and no seed need. (a) A `Task`/group handle used from another thread is refused CLEANLY before the group is touched, by one check over `join`/`cancel`/`detach`/drop, for cooperative groups only. Safe code can't reach it (`coro.spawn-not-send`, `spawn.send`), so the pin is an unsafe probe. (b) Conformance row K189 is rewritten. (c) A pool worker's background group now closes inside the pool teardown, so the teardown can wait on a non-cancellation wait. This is stated in the spec, with a pin that K188 holds (a sibling keeps ticking). **Correction to this issue's description:** since SL-793 r2, `x6` panics at the second thread's `Task.spawn` ("the background group belongs to another running thread"), not at `Task.join`.
