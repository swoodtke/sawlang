## Description

**Question for the project owner (low; from the review of SL-1134, Nov 15): may a closure literal called where it is written capture by borrow?** Today `{ [&a] in a.len() }()` is refused with `capture.escaping-borrow`, and a `move` of a capture out of such a literal with `capture.escaping-consume`: the compiler judges every closure literal that is not passed straight to a non-escaping parameter as escaping. A literal called where it is written cannot outlive its statement, so neither refusal protects anything in that position.

**Options:** (a) keep the rule as it is (one rule for every literal; a reader never asks where a literal sits); (b) a literal that is the callee of a call where it is written is non-escaping, so it may capture by borrow and move a capture out, as a closure passed to a non-escaping parameter may. **Lead's recommendation: (b)**, only if a real program wants it; nothing in sawlang or sawos calls a capturing closure in place today (both trees were searched for SL-1134), so it can wait for a use.

Related: SL-1134.

**The project owner's word (Nov 15, typed in the lead's session): "re sl-1137 - i assume you mean something like 'let foo = { ... closure captures by borrow ... }()'? if so, then yes, that should be allowed."** Ruled: option (b).

**The rule, as ruled:** a closure literal that is the callee of a call where it is written, `let foo = { [&a] in a.len() }()`, is non-escaping: it cannot outlive its statement, so it may capture by borrow (`[&a]`, `[&var n]`), as a closure passed straight to a non-escaping parameter may. Only the literal as the callee is covered; the call's RESULT is an ordinary value (a borrow it captured cannot leave in the result, by the usual rules).

**What this issue now is: one unit, detailed by the lead before dispatch.** Where the escaping judgement is made (the funnel that decides a literal escapes, and its positions), the position matrix (in place with and without arguments, in parentheses, nested, as an `if`/`match` scrutinee, in a generic and a task body; and the refusals that must stay: a literal bound with `let f = {..}` and called later, a literal passed to an escaping parameter), whether `[move x]` out of such a literal changes too (`capture.escaping-consume`), the spec's closure-capture text and the saw-lang skill, and the borrow checker's rows for the borrow the capture holds over the call. Lands after SL-1134 (the same position's drop).

**The owner's clarification (Nov 15, typed): "so for your example, isn't that returning a reference from the clsoure? that shouldn't be allowed - but using the reference in the closure is fine, right?"** Agreed, and the lead's answer:

- `{ [&a] in a.len() }()` does not return a reference: `len()` reads through the borrow and returns an `Int`, a value. That is the allowed shape: the capture is USED inside the body.
- **Returning the borrow is refused**, as it is everywhere (a reference is a parameter, never a returned value): `{ [&a] in a }()` returns `a` itself, so it is refused with the existing rule's diagnostic; it must not be read as "returns a copy of `a`". The same for a body whose value is a lend of the capture (`{ [&v] in v[0] }()` with a non-Copy element: refused, as a place read by value; a Copy-tier element is copied out, as anywhere).
- The unit's matrix carries both as rows: the body using the borrow and returning a value (accepted), and the body returning the borrow or a place through it (refused, with the diagnostic the same shape gets as a function's return).
