## Description

**Question for the project owner (low; from the review of SL-1134, Nov 15): may a closure literal called where it is written capture by borrow?** Today `{ [&a] in a.len() }()` is refused with `capture.escaping-borrow`, and a `move` of a capture out of such a literal with `capture.escaping-consume`: the compiler judges every closure literal that is not passed straight to a non-escaping parameter as escaping. A literal called where it is written cannot outlive its statement, so neither refusal protects anything in that position.

**Options:** (a) keep the rule as it is (one rule for every literal; a reader never asks where a literal sits); (b) a literal that is the callee of a call where it is written is non-escaping, so it may capture by borrow and move a capture out, as a closure passed to a non-escaping parameter may. **Lead's recommendation: (b)**, only if a real program wants it; nothing in sawlang or sawos calls a capturing closure in place today (both trees were searched for SL-1134), so it can wait for a use.

Related: SL-1134.

**The project owner's word (Nov 15, typed in the lead's session): "re sl-1137 - i assume you mean something like 'let foo = { ... closure captures by borrow ... }()'? if so, then yes, that should be allowed."** Ruled: option (b).

**The rule, as ruled:** a closure literal that is the callee of a call where it is written, `let foo = { [&a] in a.len() }()`, is non-escaping: it cannot outlive its statement, so it may capture by borrow (`[&a]`, `[&var n]`), as a closure passed straight to a non-escaping parameter may. Only the literal as the callee is covered; the call's RESULT is an ordinary value (a borrow it captured cannot leave in the result, by the usual rules).

**What this issue now is: one unit, detailed by the lead before dispatch.** Where the escaping judgement is made (the funnel that decides a literal escapes, and its positions), the position matrix (in place with and without arguments, in parentheses, nested, as an `if`/`match` scrutinee, in a generic and a task body; and the refusals that must stay: a literal bound with `let f = {..}` and called later, a literal passed to an escaping parameter), whether `[move x]` out of such a literal changes too (`capture.escaping-consume`), the spec's closure-capture text and the saw-lang skill, and the borrow checker's rows for the borrow the capture holds over the call. **The owner's clarification (Nov 15, typed): "so for your example, isn't that returning a reference from the clsoure? that shouldn't be allowed - but using the reference in the closure is fine, right?"** Agreed, and the lead's answer:

- `{ [&a] in a.len() }()` does not return a reference: `len()` reads through the borrow and returns an `Int`, a value. That is the allowed shape: the capture is USED inside the body.
- **Returning the borrow is refused**, as it is everywhere (a reference is a parameter, never a returned value): `{ [&a] in a }()` returns `a` itself, so it is refused with the existing rule's diagnostic; it must not be read as "returns a copy of `a`". The same for a body whose value is a lend of the capture (`{ [&v] in v[0] }()` with a non-Copy element: refused, as a place read by value; a Copy-tier element is copied out, as anywhere).
- The unit's matrix carries both as rows: the body using the borrow and returning a value (accepted), and the body returning the borrow or a place through it (refused, with the diagnostic the same shape gets as a function's return).

**The design pass is done (Nov 16; an Opus pass with a prototype): `.build/scratch/p1137d/design.md`, `proto.diff` and the proposed tests under `proposed/` beside it, in the lead's checkout.** One funnel decides escaping (`TcProgram.closure_escapes`, `compiler/typecheck/src/bodies.saw`, writing `closure_escaping[k]` that every stage reads); the change is one predicate, `in_place_callee` (a closure that is its call's callee, through parentheses, does not escape), called from that funnel. 32 accepted cells and every refusal that must stay are measured; no position was found where a borrow outlives its statement; borrowck, drops, mono, coro and llvm need no change.

**The owner's rulings on the design's questions (Nov 16, in the lead's session):**
- **Q1 = copy out, like a function.** `{ [&a] in a }()` returns a copy of a Copy-tier `a`, as `func f(a: &String) -> String { a }` does (the literal's type is `() -> String`, no reference leaves); a non-Copy `a` is refused (`transfer.implicit-copy`). This corrects the lead's c2 answer, which called it a returned borrow.
- **Q2 = yes, like a non-escaping argument closure.** An in-place literal may consume a `[move x]` capture; V174's two output lines swap order (each value still released exactly once, before the next statement).
- **Q3 = accept.** Two in-place literals borrowing one root in one argument list are accepted, as argument closures are today.

**The lead's reading of the stop condition:** the prototype changes the IR of exactly the two corpus programs that hold an in-place capturing literal (V174 and its -O2 twin): the ruling itself moves that literal's environment from the heap to the frame. That is the ruled change, not a regression; the unit records V174's new baseline.
