## Description

Sockets the runtime creates (`rt_tcp_listen`, `rt_tcp_accept`, `rt_tcp_connect_start`) are not opened with `FD_CLOEXEC`, so every child a Saw program spawns through `Command` inherits the listening socket and every client connection open at fork time.

Observed in sawtracker (recorded as ST-SAW-17 in its SAW_NOTES): each `git` and each `sh -c` test command the server spawns inherits the accepted HTTP connection. Server-side that is invisible, since the response carries `Content-Length` and the server closes its own copy. Client-side it depends on the reader: a client that reads to EOF does not see EOF until every inherited copy of the fd closes, that is, until the test command exits. Measured: a `patch add` that starts an 8-second gate run takes 8.25 s to return; a gate that never finishes hangs the client. Killing the server also does not free the port while an orphaned child still holds the inherited listener.

Expected: runtime-created sockets are close-on-exec (`SOCK_CLOEXEC` at `socket()`/`accept4()`, or `fcntl(FD_CLOEXEC)` on macOS where `accept4` is unavailable), matching what every other runtime does by default. A child that genuinely needs an inherited socket is the exception and should opt in.

No standalone reproducer yet; the shape is: listen, accept one connection, spawn `sh -c 'sleep 5'` from the handler, write a `Content-Length` response, close the stream, and observe that a client reading to EOF waits the full five seconds. Sawtracker works around it in its tests by using clients that honor `Content-Length`.
