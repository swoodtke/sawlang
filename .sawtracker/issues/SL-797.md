## Description

**`EXEC_HEAD` is process-wide, so a thread that drives its own cooperative `TaskGroup()` may sweep OTHER threads' cooperative frames** (found by SL-793's design, agent p793; UNVERIFIED). The executor's list of registered cooperative groups (`EXEC_HEAD`, `std/taskgroup.saw`) is one process-wide list. A `Thread.spawn` body, or a pool task, that drives a `TaskGroup()` of its own runs `sweep`/`exec_run` over that list, so it may resume a frame that belongs to another thread's cooperative executor (main's, say). That's a data race on the frame and a violation of task confinement (D6: a frame runs on one thread at a time).

**First, confirm:** a probe with two threads each driving its own `TaskGroup()` of ticking tasks; record which thread resumes which frame (`Thread.current`-style identity printed from each task), under repeat runs.

**If confirmed, the fix direction:** cooperative registration is per thread (a thread-local executor head, via the per-thread mechanism SL-793 adds as a runtime seam), so a sweep only touches its own thread's groups. A `TaskGroup()` belongs to the thread that made it.

**Obligation 4:** the mechanism is "process-wide executor state where the design says per-thread". Sweep the executor's other statics (`IN_EXECUTOR`, `LIVE_THREADS` is legitimately global, the reactor's singleton, the background `Task.spawn` group) and classify each as correctly global or should be per-thread.
