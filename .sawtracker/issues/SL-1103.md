## Description

**Filed by the sawos lead for the sawlang lead.** Hit while designing sawos's image builder (SO-95, tracker doc `SO:images-and-packaging`, section 11) and by the sawos reviewer. Run against sawlang 0.23.0, hosted on macOS arm64.

- **Tried (reproduced).** Two `sawc-stage2` compiles of the same kernel
  source with the same `-o k.o`, started together, eight times (sixteen
  runs). The reviewer saw the same with two `blade build --force` in one
  package, which run two `sawc` to one `.o`.
- **What happened.** 7 of 16 runs failed with one of:
  ```
  sawc build: cannot remove .../race/k.o.tool: unlink ".../race/k.o.tool"
    failed (not found)
  sawc: cannot open .../race/k.o.tool: open ".../race/k.o.tool" failed
    (not found)
  ```
- **Expected.** Two builds to one path are a mistake, but the failure
  should say so. Better still: the scratch file named per process, so the
  output is simply last-writer-wins, or a lock on the output naming the
  other build.
- **Why.** sawos's runner and builder run many compiles in parallel. A
  collision there is a sawos bug, and it should read as one, not as a
  missing file.
- **How badly.** Nice to have. sawos's fix is to never compile twice to one
  path (the design's rule 9.2).

**Implementation detail (lead, Nov 14).**

**The mechanism (obligation 4).** `sawc build` captures a tool's output through a scratch file named from the output path alone: `driver_captured` in `compiler/driver/src/main.saw` writes `OUT.tool`, reads it and removes it. Two builds to one `-o` share that name, so one removes the file the other is about to read or remove, which is the reported pair of messages. The same naming, swept by reading the driver: `OUT.features.ll` (`driver_check_feature_names`: written, compiled by clang, removed) is a second transient scratch file with the same hazard. The kept products are a different case and are NOT changed by this unit: `OUT.ll` (the IR left beside the output), the per-unit `.ll` and objects of a split build under its directory, and the output itself; two builds of one source write the same bytes there.

**The change.** A transient scratch file's name carries a per-process token, so two builds never share one: `OUT.<token>.tool` and `OUT.<token>.features.ll`. The token is `driver_cache_token()` (random bytes from `/dev/urandom`, else the time), which the object cache and the front cache already use for their temporaries. It is made once per `sawc build` and handed to both places (read how `driver_build` reaches `driver_captured`'s callers, every one of which passes `out`; one helper that spells a scratch path from `out`, the token and a suffix, so no third scratch file can be named without it; its docstring lists its ENTRY POINTS). Nothing else about the capture changes: the file is still beside the output and still removed.
- Sweep to do before the change and to report: every path the driver writes and later removes (`File.remove` in `compiler/driver/src/`), and every path made by appending a suffix to `out`. Each is either transient (gets the token) or kept (listed, unchanged).
- With the scratch files apart, two builds to one path are last-writer-wins on the kept products.

**Step 0:** the report's race, as a script in the evidence directory: N pairs of `sawc build` of one small program to one `-o`, started together (hosted, `-c` and a linked executable both; and one pair with `--target-features` on a cross target if a cross clang is recorded, for the feature probe). Count failures and keep each failing run's output. Expected today: a large share fail with `.tool` messages. If none fails in 100 pairs, STOP (the race does not reproduce here).

**After:** the same loop, 200 pairs of each kind: every run exits 0 and no `*.tool` or `*.features.ll` is left in the directory. **If a run still fails, STOP and report its output and which file it names**: a torn kept product (`OUT.ll` read by the other build's clang while half written) would be the next mechanism, and making those writes atomic is the lead's call, not this unit's.

**Pin.** A test the lanes run without a race: after one `sawc build -o OUT` the directory holds no file whose name ends `.tool` or `.features.ll` (so a scratch file that is not removed fails), and a build whose output directory already holds a file named `OUT.tool` succeeds and leaves that file alone (so the old shared name is not used). Put it where the driver's own behaviour is tested (read `compiler/tests/run.py` for the step that builds programs and checks the driver's files: the `programs` step's driver checks or the run lane's probe list; add it to the smallest existing one). The race loop itself is evidence, not a lane test (it is timing).

**Docs.** None, unless a document names `OUT.tool` (grep `\.tool` in `LANGUAGE_SPEC.md`, `README.md`, `compiler/README.md`, `TESTING.md`); if one does, quote the change.

**Stops.** A scratch file is read by something outside the driver by its name (build.py, a lane, Blade): grep `\.tool` and `features\.ll` over `compiler/tools`, `compiler/tests`, `tools`, `blade/src`. The token cannot reach a caller without changing a function other stages call. The seed (`compiler/seed/`) would need to change.

**Gate.** `compiler/tests/run.py --only seed,units,golden,subset,fixture_whitespace,std,comments,programs`; `tools/battery.sh citations`.

**Files expected:** `compiler/driver/src/main.saw`, one test file or lane under `compiler/tests/`. Anything else is a stop.

**This defect failed the server's gate today (lead, Nov 14): priority raised, and one lane item added to the unit.**

**What happened.** SL-1098.p1 (a Blade-only patch) failed its test run in the `coro` step and, as a consequence, in `parallel_order` (log: `.build/scratch/p1098/r3_server_test.log` in the lead's checkout):
```
coro injection compiler/tests/coro/parks/verify_records.saw: does not compile: sawc build: the linker .../usr/bin/ld () is older than Xcode 15's, which has the `-reproducible` ...
... then 'coro injection compiler/tests/coro/parks/verify_records.saw: does not compile: sawc: cannot open /Users/shawn/Projects/s...'
```
The empty `()` is the linker's version read back empty from `OUT.tool`, and the second run could not open the same file: two `sawc build` runs wrote `.build/coro-lane/verify_records` at once. The `coro` step builds each `parks/` program to that fixed path (`check_park_injections` in `compiler/tests/coro/coro_lane.py`), and `parallel_order` (`calls_overlap=True`) runs the coro lane again, more than once, while the main run's `coro` step may still be running. A retest was requested.

**Added to the unit (item B, after the driver change):**
- `check_park_injections` builds each program into a directory of the run's own (`tempfile.mkdtemp` under `.build/coro-lane/`, removed when the check ends, success or failure), so two runs of the lane never write one executable. `.build/coro-lane/std`, the fixed path `parks/verify_records.saw` names, stays where it is: read how it is made (the function whose docstring names it) and say in the report whether two runs making it at once can tear it; if they can, STOP and report, since that path is spelled in a tracked source.
- **The same hazard, swept (obligation 4):** every lane that `parallel_order` runs more than once or beside the main run (`STAGE_STEPS`, `FIXPOINT_LANES`, `ONLY_STEP` in `compiler/tests/parallel_order.py`) is read for a build to a fixed output path; each is listed with its path and given a per-run directory the same way.
- Evidence: the `coro` step run twice at once from two shells (two `run.py --only coro` need the suite lock, so instead call `coro_lane.check_park_injections` from two processes with a small script, 20 rounds): no failure after; at least one failure in 20 rounds before, if the race shows on this machine (if it does not show in 20 rounds, say so and keep the change).

**Gate, added:** `coro` and `parallel_order` join the `--only` list.

**Files, added:** `compiler/tests/coro/coro_lane.py`, and any other lane the sweep names.
