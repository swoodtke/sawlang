## Description

Filed without a standalone reproducer at the sawlang lead's request: the finding is presumed a class, and the io_tok propagation seam gives a concrete mechanism to sweep. Suspected family: SL-208/DF-300e — a timed park one frame deeper than the loop that owns it plausibly registers its token/timer against the wrong frame's wake word.

Observed in sawtracker's full server against sawlang main 5755f60b. Factoring the SL-204 timed read into a helper one frame deeper than the read loop —

    func read_chunk(stream: &TcpStream, secs: Int) -> Result<Data, common.Failure>

— called from the loop in `http.read_request` (itself reached from a connection-worker task; the accept loop runs in the driving frame with `accept(timeout: Duration.secs(1))`) produces: the server accepts exactly ONE connection that parks on a read, then is never scheduled again — no further accepts, and the accept loop's own 1s timed accept NEVER expires again either. Closing the idle client sockets releases everything instantly (reactor tears down the parked set). The frame is not slow; it is unscheduled.

Bisected one change at a time against a baseline build; NOT accounted for by: the timed read itself, the SignalWatch task, holding worker handles in Vector<VoidTask>, or moving the accept loop into a spawned task. Inlining read_chunk back into read_request — same reads, one frame shallower — fixes it completely (70 simultaneous silent connections accepted; a request is answered as soon as the idle deadline frees a worker).

Non-reproducing reduction (important negative data): a standalone program with 64 worker tasks parked on timed reads, a signal watcher, startup subprocesses, nested driven frames, and the same three-deep read chain accepts everything, in BOTH the driving-frame and spawned-task shapes. So the precondition looks like reactor state (multiple parked fds + the timer wheel), not call shape alone.

Live manifestation: sawtracker ST-25 adoption work; the full server + tests/integration.py's 70-idler block reproduces it deterministically if src/http.saw's reads are re-factored into a helper (see sawtracker SAW_NOTES ST-SAW-14 for the shipped rule: every stream.read/listener.accept park lives in the frame that owns its loop). Happy to re-run any instrumented build against that setup.
