## Description

Filed without a standalone reproducer at the sawlang lead's request: the finding is presumed a class, and the io_tok propagation seam gives a concrete mechanism to sweep. Suspected family: SL-208/DF-300e — a timed park one frame deeper than the loop that owns it plausibly registers its token/timer against the wrong frame's wake word.

Observed in sawtracker's full server against sawlang main 5755f60b. Factoring the SL-204 timed read into a helper one frame deeper than the read loop —

    func read_chunk(stream: &TcpStream, secs: Int) -> Result<Data, common.Failure>

— called from the loop in `http.read_request` (itself reached from a connection-worker task; the accept loop runs in the driving frame with `accept(timeout: Duration.secs(1))`) produces: the server accepts exactly ONE connection that parks on a read, then is never scheduled again — no further accepts, and the accept loop's own 1s timed accept NEVER expires again either. Closing the idle client sockets releases everything instantly (reactor tears down the parked set). The frame is not slow; it is unscheduled.

Bisected one change at a time against a baseline build; NOT accounted for by: the timed read itself, the SignalWatch task, holding worker handles in Vector<VoidTask>, or moving the accept loop into a spawned task. Inlining read_chunk back into read_request — same reads, one frame shallower — fixes it completely (70 simultaneous silent connections accepted; a request is answered as soon as the idle deadline frees a worker).

Non-reproducing reduction (important negative data): a standalone program with 64 worker tasks parked on timed reads, a signal watcher, startup subprocesses, nested driven frames, and the same three-deep read chain accepts everything, in BOTH the driving-frame and spawned-task shapes. So the precondition looks like reactor state (multiple parked fds + the timer wheel), not call shape alone.

Live manifestation: sawtracker ST-25 adoption work; the full server + tests/integration.py's 70-idler block reproduces it deterministically if src/http.saw's reads are re-factored into a helper (see sawtracker SAW_NOTES ST-SAW-14 for the shipped rule: every stream.read/listener.accept park lives in the frame that owns its loop). Happy to re-run any instrumented build against that setup.

STANDALONE REPRO ACHIEVED, and the mechanism is narrowed to one edge. This corrects the issue's "precondition looks like reactor state" reading (the peer's `sample(1)` reached the same conclusion independently, from the other side).

## The trigger is a CONJUNCTION, not depth and not reactor state

A suspending call is silently NOT discovered when ALL of these hold:

  * the callee is a **plain free `func`** (not a method, not a generic), AND
  * it is **not `public`** (module-private), AND
  * the **caller's body lives in an IMPORTED module** and is spliced into the entry module for frame building.

Drop any one of the three and it works. That is why the issue's standalone reduction did not reproduce: it was single-file, so there was no imported body, and reactor state was never the variable.

## Discovery matrix (measured, `__saw_drive_steps` counts Pending resumes; 1 = the suspension survived, 0 = it was silently dropped)

    E1  entry fn    -> entry-module private free fn      steps=1   OK
    E2  entry fn    -> 2 entry-module private free fns   steps=1   OK
    S0  imported fn suspends DIRECTLY                    steps=1   OK   (SL-208's fixed cell)
    S1  imported fn -> its own PRIVATE free fn           steps=0   BROKEN
    S2  imported fn -> its own extension METHOD          steps=1   OK
    S3  imported fn -> 2 of its own private free fns     steps=0   BROKEN

## The socket repro, and the 2x2 that isolates it

Four servers, identical except for where the read loop and its helper live. Oracle: 70 idle connections, then one real request; the server prints a tick on every expiry of its own `accept(timeout: Duration.secs(1))`.

    read loop's module   helper frame   frame for helper   frame for std read   blocking __saw_exec_park_io   verdict
    entry                no (depth 2)   n/a                YES                  0                             PASS
    entry                yes (depth 3)  YES                YES                  0                             PASS
    imported             no (depth 2)   n/a                YES                  0                             PASS
    imported             yes (depth 3)  NO                 NO                   1                             WEDGE

The wedging build's `--emit-ir` has no `__Frame_read_chunk` and no `__Frame_TcpStream_read$OL$Duration` at all, plus one `call void @__saw_exec_park_io` — the codegen out-of-frame fallback (`sawc/codegen/calls.py:575-597`), which registers the fd and then BLOCKS THE OS THREAD. All three passing builds emit zero such call sites. That is the whole wedge: the blocked thread is the executor's, so nothing else in the process runs.

## Why every observed face follows from that one fact

Server trace from the wedging build (t=0 is process start; 20s read timeout, 1s accept timeout):

    [  0.00] port=54443
    [  0.05] accepted 1          <- worker 1 parks ... and blocks the executor thread
    [ 20.05] accepted 2..17      <- exactly when worker 1's 20s read deadline expires
    [ 68.05] accepted 18..33
    [ 69.05] tick 1

No ticks at all while blocked — main's 1s accept deadline cannot fire because main's frame is not being resumed by anyone. Instrumenting `__saw_exec_run_inner` phase 2 confirms it directly: the scan runs once (reporting main's accept frame correctly, `dl` set, `rem_ns=999997000`), then after `accepted 1` phase 2 is NEVER REACHED AGAIN. The scheduler is not making a bad poll-bound decision; it is not running at all. (Instrumentation reverted; worktree clean.)

This matches the peer's `sample(1)`: 1604/1604 samples in one stack, `read_chunk$m$src_http` as a plain call with no frame, down into `__saw_rt_reactor_poll` -> `kevent`.

Timed vs untimed is irrelevant, as the peer found: the fallback passes deadline 0 for an untimed `io_wait`, which is `poll(-1)` — it blocks until that one fd is ready, i.e. forever for an idle peer. The timed variant merely bounds the damage at the read timeout.

## Two findings, not one

1. **The classification miss.** A module-private free function called from a spliced imported body is not discovered as a suspending callee, so no frame is built for it or for anything below it.

2. **The failure MODE is a silent degradation, and that is separately wrong.** Designs 96/101/104 promise that a suspending call embeds or errors cleanly, never silently blocks. Here it silently blocks, and in the non-io case (`yield_now`) it silently DROPS the suspension (steps=0) — a task that should cede never does, with nothing said at compile time or run time. Whatever the classification fix is, the out-of-frame blocking-park fallback being reachable from inside a task context looks like it should be a refusal or a runtime detection in its own right. Worth its own issue.

## The mechanism, exactly

`coro_transform.py:11425-11428` builds the table of imported free functions the SL-208 splice may draw from:

    imported_free_fns = {}
    for _f in (getattr(imported_ast, 'functions', None) or []):
        if _f.name not in funcs_by_name and _f.name not in imported_free_fns:
            imported_free_fns[_f.name] = _f

**Keyed by `_f.name` — the UNMANGLED name.** The effect graph keys a free function differently: `typechecker/effects.py:431` uses `("fn", getattr(func, 'mangled_symbol', None) or func.name)`. And design 249 stamps a `$m$<module>` tag on a MODULE-PRIVATE free function only (`typechecker/registration.py:1379-1384` via `_module_private_symbol`; a `public` one gets no tag, `registration.py:1349-1353`).

So at the closure walk's edge-follow (`coro_transform.py:11583-11592`):

    if (not is_fn_edge and t.suspends
            and isinstance(e.target, tuple) and e.target[0] == "fn"
            and e.target[1] in imported_free_fns):
        if _splice_imported_free_fn(e.target[1]) is not None:
            is_fn_edge = True

`e.target[1]` is `read_chunk$m$src_http` while the table holds `read_chunk`. The test is False, the splice is declined, `is_fn_edge` stays False, and the edge falls off the end of the loop body (`:11601-11604` enqueues only `is_fn_edge` or an int method id) — **with no diagnostic**.

Measured directly (temporary instrumentation, since reverted):

    [SL280] imported_free_fns: ['s1_entry', 's1_helper', 's5_helper', 's7_entry', 's7_helper', 's8_helper', 's9_helper']
    [SL280]   s1_helper: name='s1_helper' mangled_symbol='s1_helper$m$sibmod' visibility=PRIVATE
    [SL280]   s7_helper: name='s7_helper' mangled_symbol=None            visibility=PUBLIC
    [SL280] edge s7_entry -> s7_helper:            suspends=True is_fn_edge=False in_imported=True   <- spliced, works
    [SL280] edge s1_entry -> s1_helper$m$sibmod:   suspends=True is_fn_edge=False in_imported=False  <- DECLINED

Note the private helper's body IS present in `imported_ast` — it is simply filed under a different key than the graph edge uses. This is a keying mismatch, not a visibility policy, and not a missing body.

That also explains the rest of the matrix in my previous comment: METHOD callees are enqueued by `_scan_method_callees(func.body)`, which runs unconditionally on every joining body (`:11535`) and keys on `node_id`, so S2/S4 (a qualified `mod.f()` parses as a MethodCall) are immune; GENERIC callees get `_promote_joining_body` (`:11457`, added by SL-208 review r1 finding 2), so S6 is immune. The plain private free-function edge is the one path with neither.

## A SECOND, INDEPENDENT GATE

`structurally_susp_fns` (`:11391-11412`) is design 96's fallback for "a free function whose only suspension is a buried std method call" — precisely the `read_chunk` shape. It is computed by iterating `funcs_by_name`, i.e. **the ENTRY module only**, and it is computed **before the walk starts**, while bodies are spliced in mid-walk (`:11511`, `:11591`). It is read once, at `:11599`. So an imported helper can never be in it, whatever the keying does. Any fix must address the phase ordering as well as the key.

## Why I did not land a fix: measured fan-out

I applied the minimal keying fix (register by `mangled_symbol or name`) and measured. It does not hold:

1. **`internal compiler error: read_chunk$m$sl280http`** on the real socket shape. With `SAW_DEBUG=1` the traceback is `llvmlite.ir._utils.DuplicatedNameError` out of `codegen/core.py:3557 _declare_function` via `core.py:2511 self._declare_function(func, name_override=func.mangled_symbol)`. The spliced clone and the imported module's own emission of the same private function collide on one LLVM symbol. `_splice_imported_free_fn` (`:11430-11455`) appends the clone to `program.functions` with its `mangled_symbol` intact; for a PUBLIC callee there is no tag and nothing collided, which is why SL-208 never met this.

2. **`error: 'self' can only be used inside methods`** on a spliced private helper whose parameter is a REFERENCE to an imported struct — `func s8_helper(w: &Widget) -> Int { yield_now()  w.n + 1 }`, reported at `w.n + 1`. A separate latent bug in the splice preprocessing that only becomes reachable once private helpers are spliceable at all. This is the shape closest to the real `read_chunk(stream: &TcpStream, secs: Int)`, so it is on the critical path, not a curiosity.

3. A third keying inconsistency downstream, which I did not reach but which the code reading found: `_classify_call` (`:5160`) tests `fc.name not in self._suspends` and emits `{'callee': fc.name}` (`:5171`) — the PLAIN name — while `closure`/`self._suspends` hold graph keys. `_is_suspending_expr` (`:9320`) uses `resolved_symbol` instead. So the call-site classifier and the closure walk disagree about what names a callee.

That is four sites that must move together (effect-graph key, `imported_free_fns`, the splice's registration + codegen emission dedupe, `_classify_call`), plus the `structurally_susp_fns` phase ordering, plus the reference-parameter splice bug. That is a brief, not a patch.

## Proposed fix shape (for the brief)

**Obligation 1 says this rule is a funnel.** "What key names this callee's frame?" is currently answered independently in at least four places and they disagree. The fix is ONE function — `_callee_frame_key(call_or_edge)` — whose docstring NAMES its entry points (effect-graph edge, `imported_free_fns` lookup, `_splice_imported_free_fn` registration, `_classify_call`, `_callee_fb`), with every site routed through it. The bug is the absence of that funnel; patching the one site that failed today reproduces the same class at the next one.

Then, in the same brief:
* the splice must not re-emit a symbol the imported module already emits (rename the clone, or dedupe the emission — decide which is the invariant);
* `structurally_susp_fns` must be recomputed for, or extended by, each body as it joins the closure, not once over the entry module beforehand;
* the reference-parameter splice bug (face 2) needs its own root cause.

**Obligation 4 matrix, already measured, is the test plan** — the 12 rows in my previous comment (E1/E2 entry controls, S0-S9), plus the 2x2 socket matrix, plus the two faces above as their own rows.

## Second finding, separable: the failure MODE

Independent of the classification fix: a suspending call the transform declines to reach degrades SILENTLY. `_analyze_nesting`'s own docstring concedes this (`:1775-1786`): *"the closure walk follows an edge only when it can name and build a frame for the target, so a suspending callee it declines to reach ... is in `nodes` and not in `closure`"* — and today that costs a blocked executor thread, not a diagnostic. Designs 96/101/104 promise a suspending call embeds or errors cleanly and NEVER silently blocks. Concretely: the out-of-frame park fallback (`codegen/calls.py:575-597`) is correct for a genuinely sync caller and catastrophic when reached from inside a task, and nothing distinguishes the two. Worth its own issue — a refusal at compile time where the caller is in the driven closure, or a runtime detection ("parking outside a frame while an executor is live"). Note the existing carve-out this must not break: blade's dependency resolver relies on a suspending callee never being embedded (`:1781-1784`).
