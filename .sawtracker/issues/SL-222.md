## Description

Building sawtracker against main 88fa56ba fails with: 'coroutine transform: move of a frame local in a nested tail-expression of driven open_store is not supported; move it in a return statement instead'.

The refusal is over-broad. parse_block (sawc/parser/statements.py:60) unconditionally promotes a block's final ExpressionStatement into Block.final_expr - including a DISCARDED void call at the end of a loop body - and _FrameBuilder._lower_block_body_in_place (sawc/coro_transform.py:7860-7875) then refuses any __saw_forget that tail owes. The with-a-value justification in the _lower_block_in_place docstring does not apply to a discarded tail, and _norm_block's DF-158b branch (coro_transform.py:4276-4286) already demotes a void FUNCTION-BODY tail for exactly this reason; the nested case never got the same treatment. Suggested fix: when the tail is void or the block's value is discarded, demote final_expr to an ExpressionStatement and append the forgets.

Three ingredients are each load-bearing (drop any one and it compiles): an ITERATOR for loop (range for desugars differently), an early return inside the block, and an &-borrow of the moved local (address-taken => legacy drop-flag encoding; slot-encoded locals move fine). Newly REACHED by SL-208's cross-module transform, but the defect predates it.

Reproducer: sawtracker repros/coro_tail_move.saw + repros/coro_tail_move_mod.saw (compile the entry file; two-file, module-qualified suspending call). Worked around in sawtracker ST-13 by prefixing the four open_store call sites with 'let _ =' (a LetStatement can host the forget).

Location: sawc/coro_transform.py:7926-7927, the statement-position TryExpr/catch lowering, together with _relinquish_before_exits at 7295-7299.

The new clear at the start of the catch correctly relinquishes the operand's moved value. But the unconditional trailing `_forgets(forgets)` still runs after the whole try. If the catch reinitializes the moved local and falls through, that trailing clear erases the replacement's cleanup claim. The claim being cleared is no longer the original one, so this second clear is not a harmless no-op.

Exact-patch reproducer:

```saw
import std.task.{yield_now}
struct Res { name: String }
extension Res: NoCopy {
    func deinit(&var self) { print("drop {}", self.name) }
}
struct Bad { why: String }
extension Bad: Error {
    func format(&self, into: &var StringBuilder) { try! into.append(self.why) }
}
func note(r: &Res) -> Int { r.name.len() }
func consume(r: Res) -> Result<Void, Bad> { Bad(why: "fail") }
func run(items: Vector<Int>) -> Int {
    yield_now()
    for i in items.iter() {
        var r = Res(name: "old")
        if note(&r) + i < 0 { return -1 }
        try consume(move r) catch { r = Res(name: "new") }
    }
    1
}
func main() { print(__saw_drive(run([1]))) }
```

Expected: `drop old`, `drop new`, `1`. Revision 4 prints only `drop old`, `1`, exiting 0. Removing the suspension and driving wrapper produces the expected three lines. Reinitializing and then returning from the catch also produces all three lines, because that path skips the trailing clear. An additional post-statement read of the replacement compiles but panics with `force unwrap of None`. The exact unpatched base rejects the tail-shaped reproducer with the nested-tail-move diagnostic, so this remains a failure in the newly enabled path.

Please clear the old claim once between operand evaluation and catch dispatch, or make the success/no-catch clear path-specific; do not clear again after a catch can establish a new claim. Keep the operand-success path covered. Add catch-fallthrough reinitialization and subsequent-use/drop tests alongside the now-passing early-exit matrix.
