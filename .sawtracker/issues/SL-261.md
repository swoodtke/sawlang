## Description

`&`/`&var` into an array ELEMENT addresses a materialized COPY whenever the container's base is not one of four forms the reference path happens to know. The write is silently discarded (exit 0, no diagnostic) for two of the missing bases and is an internal compiler error for the third. NO COROUTINE IS INVOLVED in any cell below -- this is plain synchronous code.

Repro (single file, measured on origin/main c9991092; every cell writes +7 into an element holding 1, so 8 is correct and 1 is a lost write):

  struct Doc { n: Int }
  func set_one(d: &var Doc, k: Int) { d.n = d.n + k }

  func optional_base() -> Int {                  // observed 1, wanted 8
      var o: [Doc; 3]? = [Doc(n: 1); 3]
      set_one(&var o![1], 7)
      o![1].n
  }
  func tuple_base() -> Int {                     // observed 1, wanted 8
      var t: ([Doc; 3], Int) = ([Doc(n: 1); 3], 0)
      set_one(&var t.0[1], 7)
      t.0[1].n
  }
  func through_var_ref(a: &var [Doc; 3], k: Int) { set_one(&var a[1], k) }
                                                 // INTERNAL COMPILER ERROR:
                                                 // Type of #1 arg mismatch:
                                                 // %"Doc"* != [3 x %"Doc"]*

The WRITE spelling of the same place is correct in every cell (`o![1].n = ...` gives 8), which is the tell: a BORROW and a WRITE of one place disagree about where that place is.

MECHANISM (confirmed against -O0 IR, not hypothesised): codegen carries TWO base-to-pointer dispatches. `_get_lvalue_pointer` (calls.py) is the write path's funnel and answers every base form -- Identifier incl. a reference-typed one (which it LOADS first), static, `self`, MemberAccess, ArrayIndex, TupleIndex, ForceUnwrap. The reference path (`_generate_reference_expr`, operators.py) kept a PRIVATE `_get_array_element_pointer` with a smaller set -- Identifier, `self`, MemberAccess, nested ArrayIndex -- ending in a fallback whose own comment states the defect: "Fallback: materialize the container (won't propagate mutations)". A base outside the small set is stored into a fresh `arr_tmp` alloca and the element GEP addresses THAT; the reference-typed identifier is worse, since its alloca's pointee is already a pointer, so the GEP strides by whole arrays and reaches LLVM as a type mismatch.

Emitted -O0 IR for the optional cell, which is the whole bug in four instructions:

  %unwrapped = extractvalue {i1, [3 x Doc]} %arr, 1
  store [3 x Doc] %unwrapped, [3 x Doc]* %arr_tmp
  %elem_ptr = getelementptr [3 x Doc], [3 x Doc]* %arr_tmp, i64 0, i64 1
  call void @set_one(Doc* %elem_ptr, i64 %k)

SAME MECHANISM AS SL-226, WHICH IS ITS COROUTINE FACE: the transform rewrites a frame-resident local `arr` into `self.arr!`, so EVERY `&var arr[i]` in a suspending body takes the ForceUnwrap base and lands in the fallback. Filed separately because these faces need no suspension at all and a reader hunting the sync bug would never look at a coroutine issue.

FIXED ON THE SL-226 BRANCH by the same one-line change that fixes SL-226: `_generate_reference_expr`'s ArrayIndex arm now calls `_get_element_pointer` (which composes through `_get_lvalue_pointer`) and the private duplicate is deleted, so one funnel answers both families. Pinned by examples/ref_into_array_element_addresses_real_storage.saw (7 cells incl. the two arms that already worked, so the fix is pinned as a widening and not a swap). Close this together with SL-226 when that lands.
