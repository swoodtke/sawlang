## Description

Root cause under SL-230, isolated by measurement on Sep 10 2026. SL-230 has
the whole-compile phase table; this issue is the one mechanism that explains
most of it.

## The finding

Compiling the sawtracker server takes 115 s. 93 s of that is one
`TargetMachine.emit_object` call, and **THREE compiler-synthesized functions
are 71 s of it** — 62% of the entire compile:

| function | isolated emit cost | distinct frame offsets addressed | frame bytes |
|---|---|---|---|
| `__Frame_run_store_resume` | **30.7 s** | 1464 | 55,800 |
| `__Frame_response_resume` | **22.2 s** | 1434 | 54,864 |
| `__Frame_dispatch_resume` | **18.3 s** | 1422 | 54,440 |
| `__Frame_serve_resume` | 6.1 s | 684 | 25,312 |
| `__Frame_mutate_patch_resume` | 4.0 s | 773 | 28,312 |
| `__Frame_open_store_resume` | 2.2 s | 584 | 21,296 |
| `__Frame_mutate_resume` | 2.2 s | 465 | 17,096 |

Measured twice, stable to ~3% (30.67 / 31.73 s for the top row). "Isolated
emit cost" is the module's emit time with only that function's body present,
minus the all-stubbed floor (0.28 s).

## The cost is QUADRATIC in the coroutine frame's slot count

Not in function size, and not in block count — both were tested and neither
predicts it:

* `__Frame_mutate_patch_resume` is the BIGGEST function in the module (30,727
  IR lines, 5,394 blocks) and costs 4.0 s. `__Frame_run_store_resume` is
  smaller (22,210 lines, 3,889 blocks) and costs 30.7 s.
* `__vtdtor$__Frame_run_store` is 19,752 lines and costs **0.12 s**.
* Splitting every oversized basic block into <=400-instruction chunks
  (inserting unconditional branches, semantics-preserving) changed the whole
  module's emit time by **-3.3%, i.e. not at all** — so scheduling-region size
  is not the driver either. That was a hypothesis this issue tested and
  discarded.

What does predict it is the number of distinct byte offsets addressed off the
frame pointer: 1464 -> 30.7 s, 684 -> 6.1 s, 465 -> 2.2 s. `(1464/684)^2 =
4.6` against a measured ratio of 5.0.

The pass profile agrees. `llc -O2 -time-passes` on the isolated
`__Frame_run_store_resume`:

    28.6%  Greedy Register Allocator
    18.7%  Live Interval Analysis
    17.0%  Early Machine Loop Invariant Code Motion
    14.8%  Machine Instruction Scheduler
     8.0%  AArch64 Instruction Selection
     7.3%  Live Variable Analysis

Register allocation plus live-range analysis is 54.6%, and both are
superlinear in the number of live intervals — which is what a frame slot
becomes. (`-regalloc=fast` recovers only 23%, so this is the whole post-ISel
cluster, not one replaceable pass.)

NOTE: an earlier `-time-passes` run in SL-230 named the Machine Instruction
Scheduler as the dominant pass. That run profiled
`__Frame_mutate_patch_resume`, which turns out to be one of the CHEAP
functions; the profile above is the expensive one and supersedes it.

## Why the frames are this big

`Slot<T>` is `struct Slot<T> { v: T? }` and `Slot.empty()` is `Slot<T>(v:
None)`. The unoptimized `__Frame_run_store_resume` opens with a single basic
block of 2,679 instructions containing **592 inline `Slot<T>.empty()` calls** —
155 `Slot<String>`, 100 `Slot<Result<CommandOutput, Failure>>`, 100
`Slot<Optional<CommandOutput>>`, 69 `Slot<CommandOutput>`, and so on — one per
frame slot. The frame reaches 55,800 bytes for one coroutine.

That count is what a slot-per-live-temporary-per-suspend-point layout
produces. Nothing appears to reuse a slot across disjoint live ranges.

## Fix direction (not implemented here)

Slot COLORING — reuse one frame slot for temporaries whose live ranges do not
overlap, the same problem LLVM's own coroutine lowering and Rust's async
generators solve at frame-layout time. Because the back-end cost is roughly
quadratic in slot count, halving the slots should cut the back end by ~4x,
and the back end is 80% of this compile.

Two smaller, independent observations from the same measurement:

* The all-slots-empty prologue is ~592 calls writing `None` tags in one basic
  block. A `None` tag is a constant, so the whole prologue could be a bulk
  zero/constant initialization of the slot region.
* A 55,800-byte frame is also a runtime cost (allocation and cache behaviour),
  not only a compile-time one.

## What does NOT help

* Parallel/split object emission: the cost is ADDITIVE, not module-wide
  superlinear — the 12 giants' isolated costs sum to 90.2 s against 93.5 s for
  the whole module. Splitting would cut WALL time to roughly `floor +
  max(giant)` = ~31 s but leaves total CPU unchanged, because one function
  alone is 30.7 s. (This corrects the "~93 s -> ~13 s" ceiling estimated in
  SL-230 before the per-function costs were measured.)
* Keeping the O1 inliner out of the frame bodies: the UNOPTIMIZED module still
  costs 79.3 s, so the inliner's growth is worth only ~15%.

Filed by the compile-performance investigation. No implementation proposed.
