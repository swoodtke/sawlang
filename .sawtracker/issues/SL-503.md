A trait requirement with its own generic parameters (`trait T { func feed<S: Source>(&var self, s: S) }`) passes every sawc2 stage through drops. GRAMMAR.md says such requirements parse and "a later stage refuses them", but no stage does.

**Owed:**
- Read the spec's trait-requirement text to confirm the refusal; GRAMMAR.md is the spelling authority, not the meaning one. If the spec admits generic requirements, GRAMMAR's sentence is stale instead, so say which.
- Then refuse at the requirement with a stable rule id, or fix GRAMMAR.
- Sweep a default body with generic parameters, a generic requirement satisfied by a generic method, and calls through a bound and through `any Trait`.

@claude-sawlang, on tcb2c's c2: **GRAMMAR §3.4 isn't stale. It records a user ruling.** Generic requirements are refused, so sawc2's typecheck is the side that diverges.

- **The ruling.** The sentence and its divergence row (`syntax.decl.requirement | … | refuses them | later | Traits; SL-400 c6`) both cite SL-400 c6, the user's Sep 25 ruling on SL:grammar r1's questions. It includes **Q23: "the grammar accepts generic parameters on trait requirements. Type checking refuses them for now, as today."** The refusal is therefore ruled meaning, not a spelling claim that GRAMMAR overreached on.
- **The spec doesn't admit them.** "Object safety (v1)" lists the things that block erasure, and "a method with its own generic type parameters" is one of them. It names a blocker; it doesn't make the form legal for requirements. The spec shows method-level generics only on extension methods (`Vector.map<U>` and `fold<Acc>`, under "Method-level generic type parameters"), and no trait requirement anywhere has them. While Q23 refuses the form, that object-safety clause has nothing to apply to, so the two texts don't conflict and the precedence question doesn't arise.
- **Confirmed on main's sawc2** (built from SL-496's merged tree), with probe `generic_req.saw`: `trait Feeder { func feed<T>(&self, x: T) -> Int }`, met by `P` and called as `f.feed(true)` through `<F: Feeder>`. `typecheck`, `borrowck` and `drops --check` all exit 0. Stage 0 refuses it at parse (`Expected LPAREN, got LT`), which is the "as today" in Q23.
- **So SL-503's first branch is owed.** Refuse at the requirement, with a stable rule id and a message saying generic requirements aren't supported yet. Sweep the shapes in c1: a generic default body, and a requirement met by a generic method (the refusal should land once, at the requirement, and the conformance shouldn't add a second error). Then do the corpus recount from the brief. `.build/scratch/b2c/gr.saw` is the right probe to flip into the refusal pin.
- **Effect on SL-510.** With the requirement refused, a trait with a generic requirement never reaches erasure. That makes SL-510's generic reason, and its `effect.any-suspends` misreport, unreachable for now. The other three object-safety reasons are still owed: `Self` in a parameter or return type, associated types, and marker traits. SL-510 stands with those three.
- **"For now" is the user's to lift.** If you want generic requirements admitted, that's a re-ruling of Q23, not a GRAMMAR edit.
