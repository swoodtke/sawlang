A trait requirement with its own generic parameters (`trait T { func feed<S: Source>(&var self, s: S) }`) passes every sawc2 stage through drops. GRAMMAR.md says such requirements parse and "a later stage refuses them", but no stage does.

**Owed:**
- Read the spec's trait-requirement text to confirm the refusal; GRAMMAR.md is the spelling authority, not the meaning one. If the spec admits generic requirements, GRAMMAR's sentence is stale instead, so say which.
- Then refuse at the requirement with a stable rule id, or fix GRAMMAR.
- Sweep a default body with generic parameters, a generic requirement satisfied by a generic method, and calls through a bound and through `any Trait`.

tcb2c (batch B2c), on settling this: **the spec admits a generic requirement, so GRAMMAR's "a later stage refuses them" is stale.** Per the brief, I've left GRAMMAR unchanged and reported back.

- LANGUAGE_SPEC, "Object safety (v1)", lists "a method with its own generic type parameters" as one of the things that make a trait non-erasable. A generic requirement is therefore legal: it makes its trait a bound only, never an `any`. Nothing in the Traits section refuses one.
- GRAMMAR.md §3.4 ("A trait requirement takes generic parameters as a method does, and a later stage refuses them") and its divergence row (`syntax.decl.requirement | parses generic parameters on a trait requirement | refuses them | later | Traits; SL-400 c6`) are the stale text. Stage 0 doesn't parse the form at all (`Expected LPAREN, got LT`).
- sawc2's behaviour matches the spec's admission: a generic requirement, a generic default body, a generic method meeting it, and a call through a bound all check and lower. Probe: `.build/scratch/b2c/gr.saw` in the tcb2c worktree.
- What's actually missing is the object-safety refusal. `&any Sink` for a trait with a generic requirement is accepted, or refused for the wrong reason (`effect.any-suspends`), and so is a `Self`-naming method. Filed as **SL-510**.
