## Description

**The ESP32-S3 target is in the compiler and stated in three spec sentences; the rest of the user-facing docs don't mention it.** The docs convention (design 125): a feature updates LANGUAGE_SPEC.md, the saw-lang skill and README.md. As of v0.22.0:
- LANGUAGE_SPEC.md names the triple in the target list, has the paragraph beginning "`xtensa-esp-unknown-elf` is the ESP32-S3", and the profile summary line. It does not say that `--target-features` ADDS to the triple's default on this target, what the atomics answer is in a reader's terms (word atomics inline; `-s32c1i` turns them into `__atomic_*_4` calls the image must supply), or what a freestanding image owes (ATOMCTL, literals before text), unless that paragraph already does: read it first and add only what is missing.
- The saw-lang skill (`.claude/skills/saw-lang/SKILL.md`) and README.md don't mention Xtensa.
- Blade's `[sos]` manifest keys are documented nowhere a user would look. `blade/src/sosimg.saw` is the only statement of them: the `[sos.<triple>]` sections, each key, the refusal of `mcpu`, the environment variables `SOS_CLANG` and `SOS_LD`.

**Goal:** a reader can find, without reading compiler source: which targets `sawc --freestanding` takes; what each 32-bit target assumes of the CPU; and how a Blade package describes a freestanding image.

**Read first:** the saw-docs skill (it governs every sentence here); LANGUAGE_SPEC.md's freestanding sections (search "is the ESP32-S3", "riscv32-unknown-none-elf", "--target-features"); README.md's CLI and freestanding parts; the skill's freestanding section; `blade/README.md` if present and `blade/src/sosimg.saw` (`load_sos_config`, `read_toolchain_fields`, `toolchain_defaults`, every `SosError` message); `compiler/target/src/layout.saw` (`target_effective_features`, `target_cpu`, `target_native_atomics`); `tests/freestanding/README.md` (how the suite's row builds and boots: the source of the facts about a flash image, not text to copy).

**Implementation.**
1. Step 0: a table of every fact you intend to state, each with where you verified it (a source line or a command you ran and its output). A sentence with no row is not written. Build one small freestanding object for the triple and one with `--target-features` to confirm the add-to-default rule in the `.ll`'s attribute group; quote the real text.
2. LANGUAGE_SPEC.md: complete the Xtensa paragraph with what step 0 shows is missing. Rules are stated as rules; nothing about sawos, QEMU, or how this repository tests it.
3. A new spec subsection (or the place the spec already describes Blade manifests, if there is one: search "Saw.toml") for the `[sos]` table: the per-target sections, each key with its type and meaning, what is refused and the real diagnostic text, the two environment variables. Every key and message comes from `sosimg.saw`.
4. The saw-lang skill: the freestanding section gains the target list with one line per target, and the Xtensa defaults in two or three lines. README.md: the freestanding paragraph names the targets; no more.
5. Fenced examples follow the repository's docverify rules (read `compiler/tests/run.py`'s `docs` step and an existing fenced TOML or shell block in the spec before writing one): a `saw` fence must compile; a manifest is a `toml` fence.

**Out of scope.** No code change. No claim about hardware: everything here is verified under emulation, so the text says what the compiler emits and assumes, never that a board was run.

**Tests and gate.** `compiler/tests/run.py --only seed,fixture_whitespace,docs,comments` under the suite lock; `tools/battery.sh citations grammarcorpus` (the spec is a `grammarcorpus` input).

Requested changes on patch SL-1077.p1 (revision 1) (its test run was cancelled)

**Changes requested (rev 1): two sentences say something a run here contradicts. Everything else I could run is as written.** Both fixes are a line each.

**1. The skill: "`--freestanding --target` takes ... or the host's own ELF triple".** On this macOS host, whose own triple is the refused Mach-O one, `sawc build --freestanding --target aarch64-unknown-linux-gnu -c` and `--target x86_64-unknown-linux-gnu -c` both exit 0 and write an AArch64 and an x86-64 ELF object. The driver takes every triple `target_triples()` lists except the Mach-O one, so the two Linux triples belong in the list by name.

**2. The spec, the last paragraph of "Image manifests": "For `xtensa-esp-unknown-elf` the C compiler is Espressif's clang".** Blade does not find it. With `SOS_CLANG` and `SOS_LD` unset, the example manifest's shape (`native = "hal/boot.S hal/support.c"`) fails:
```
   Compiling image v0.1.0 (sosimg, xtensa-esp-unknown-elf)
error: clang failed
error: unknown target CPU 'esp32s3'
```
The Saw half built (sawc finds Espressif's clang by itself, as Profiles says), which is what makes a reader expect the same here. With both variables naming Espressif's `clang` and `ld.lld` the same package builds `.build/xtensa-esp-unknown-elf/image.sosimg`. The sentence should say the two variables have to name them.

**Should change in the same revision, your call:**
- **The literal rule, which you asked me to check.** Your wording holds, and by direction, not distance: with the literals placed right after the code the link fails at 7,864 bytes, `relocation R_XTENSA_SLOT0_OP out of range: 7864 is not in [-262141, ...]`. But "before" is not enough: with the literals before the code and 0x40010 bytes between, the same error (`-264212 is not in [-262141, ...]`); with 0x30000 between it links. So `l32r` reaches a literal at most 262,141 bytes back, and the advice as written (every `.literal` ahead of every `.text`) stops linking once an output section's code passes that. One pattern for both, `*(.literal .literal.* .text .text.*)`, keeps the object's own order, each `.literal.NAME` just before its `.text.NAME`, and links here.
- **`priorities` is typed "table", and only the inline spelling works.** `[sos.priorities]` with `low = 2` is read as a machine: `[sos]: this package builds for several machines — pass --target (this manifest declares priorities, xtensa-esp-unknown-elf)`. Say "inline table" here; the reading itself is a Blade finding for an issue (its own comment calls the table `[sos.priorities]`).

**Verified as written** (origin/main + rev 1, its own `sawc` and a Blade built by it):
- All nine refusal rows: the manifest each row describes, then `blade build`; Blade's text equals the row's after `Saw.toml [sos]: `, nine of nine. `could not launch clang` and `could not launch ld.lld`, each with a variable naming no program. The key table's defaults and the C compiler's arguments, against `toolchain_defaults`, `load_sos_config` and `native_compile_arguments`.
- The two attribute lines, byte for byte, in every attribute group, freestanding or not.
- Xtensa atomics: 8 `s32c1i` and no `__atomic_*` by default and under `+fp`; under `-s32c1i` none, and exactly the five `__atomic_*_4`. riscv32: the five under `+m,+c`, none under `+m,+a,+c`.
- Soft-float: exactly the 19 routines defined on xtensa by default and under `+fp`, on riscv32 `+m,+a,+c` and on aarch64 by default; none on riscv32 `+f,+d` or aarch64 `+neon,+fp-armv8`.
- `.literal.NAME` beside `.text.NAME`, 108 `l32r`. aarch64's default list and its replacement. `sawc: unknown target T`; the Mach-O refusal.
- The `@section` clause: reached with two instances, both are defined in the section and in `@llvm.used`; reached with none, no instance exists while a plain placed function beside it is kept.
