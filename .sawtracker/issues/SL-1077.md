## Description

**The ESP32-S3 target is in the compiler and stated in three spec sentences; the rest of the user-facing docs don't mention it.** The docs convention (design 125): a feature updates LANGUAGE_SPEC.md, the saw-lang skill and README.md. As of v0.22.0:
- LANGUAGE_SPEC.md names the triple in the target list, has the paragraph beginning "`xtensa-esp-unknown-elf` is the ESP32-S3", and the profile summary line. It does not say that `--target-features` ADDS to the triple's default on this target, what the atomics answer is in a reader's terms (word atomics inline; `-s32c1i` turns them into `__atomic_*_4` calls the image must supply), or what a freestanding image owes (ATOMCTL, literals before text), unless that paragraph already does: read it first and add only what is missing.
- The saw-lang skill (`.claude/skills/saw-lang/SKILL.md`) and README.md don't mention Xtensa.
- Blade's `[sos]` manifest keys are documented nowhere a user would look. `blade/src/sosimg.saw` is the only statement of them: the `[sos.<triple>]` sections, each key, the refusal of `mcpu`, the environment variables `SOS_CLANG` and `SOS_LD`.

**Goal:** a reader can find, without reading compiler source: which targets `sawc --freestanding` takes; what each 32-bit target assumes of the CPU; and how a Blade package describes a freestanding image.

**Read first:** the saw-docs skill (it governs every sentence here); LANGUAGE_SPEC.md's freestanding sections (search "is the ESP32-S3", "riscv32-unknown-none-elf", "--target-features"); README.md's CLI and freestanding parts; the skill's freestanding section; `blade/README.md` if present and `blade/src/sosimg.saw` (`load_sos_config`, `read_toolchain_fields`, `toolchain_defaults`, every `SosError` message); `compiler/target/src/layout.saw` (`target_effective_features`, `target_cpu`, `target_native_atomics`); `tests/freestanding/README.md` (how the suite's row builds and boots: the source of the facts about a flash image, not text to copy).

**Implementation.**
1. Step 0: a table of every fact you intend to state, each with where you verified it (a source line or a command you ran and its output). A sentence with no row is not written. Build one small freestanding object for the triple and one with `--target-features` to confirm the add-to-default rule in the `.ll`'s attribute group; quote the real text.
2. LANGUAGE_SPEC.md: complete the Xtensa paragraph with what step 0 shows is missing. Rules are stated as rules; nothing about sawos, QEMU, or how this repository tests it.
3. A new spec subsection (or the place the spec already describes Blade manifests, if there is one: search "Saw.toml") for the `[sos]` table: the per-target sections, each key with its type and meaning, what is refused and the real diagnostic text, the two environment variables. Every key and message comes from `sosimg.saw`.
4. The saw-lang skill: the freestanding section gains the target list with one line per target, and the Xtensa defaults in two or three lines. README.md: the freestanding paragraph names the targets; no more.
5. Fenced examples follow the repository's docverify rules (read `compiler/tests/run.py`'s `docs` step and an existing fenced TOML or shell block in the spec before writing one): a `saw` fence must compile; a manifest is a `toml` fence.

**Out of scope.** No code change. No claim about hardware: everything here is verified under emulation, so the text says what the compiler emits and assumes, never that a board was run.

**Tests and gate.** `compiler/tests/run.py --only seed,fixture_whitespace,docs,comments` under the suite lock; `tools/battery.sh citations grammarcorpus` (the spec is a `grammarcorpus` input).

**One more spec sentence rides on this unit (the Air's approval of SL-934.p1 r2, Nov 12).** The `@section` paragraph says "A placed function or static is emitted and kept through the optimizer whether or not anything reaches it". Add that clause to the paragraph (the mono golden `section_roots`'s header and the worklist comment in `compiler/mono/src/worklist.saw` state the rule; `compiler/tests/run/probes/section_function_generic.saw` pins it).
