## Description

**Refuse a parameter declared with a visibly `Void` type** (the user's ruling, Oct 16; it extends SL-772's every-binding-position rule).

The user: "i don't think we need to support 'foo(v: Void)' - i can't think of a usecase for it - and if we discover one, we can loosen the restriction."

**Scope:**
- A function, method or `init` parameter whose declared type is `Void` (`func takes(v: Void)`) is refused at the signature, with the same rule family as SL-772 (`type.void-binding` or a sibling `type.void-parameter`; say which) and a hint to drop the parameter.
- A closure parameter whose type is `Void`, written or inferred from an expected `(Void) -> R`, is refused when it binds a NAME. `{ _ in … }` is the spelling.
- **Unchanged:** a type-parameter-typed parameter stays legal at `T = Void` (instantiation uniformity), so `func foo<T>(v: T)` called as `foo(v: nothing())` compiles. A function TYPE naming `Void` in a parameter position (`(Void) -> Int` as a type) is not a binding, and stays legal unless the user says otherwise.

**Evidence (the Air, SL-772's review):**
- sawc2 accepts `func takes(v: Void) -> Int` called as `takes(noop())` (prints 1).
- It also accepts `apply({ v in 2 })` through a declared `(Void) -> Int` (prints 2).
- Stage 0 hits an internal compiler error on both.

**Pins:**
- refusal fixtures for a function, a method, an `init`, and a named closure parameter;
- accepted: `{ _ in 2 }` through `(Void) -> Int`, and `foo<T>(v: T)` at `T = Void`.
- **Spec:** one clause in "Binding a `Void` expression" (parameters bind names too).
