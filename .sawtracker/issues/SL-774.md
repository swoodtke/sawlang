## Description

**Refuse a parameter declared with a visibly `Void` type** (the user's ruling, Oct 16; it extends SL-772's every-binding-position rule).

The user: "i don't think we need to support 'foo(v: Void)' - i can't think of a usecase for it - and if we discover one, we can loosen the restriction."

**Scope:**
- A function, method or `init` parameter whose declared type is `Void` (`func takes(v: Void)`) is refused at the signature, with the same rule family as SL-772 (`type.void-binding` or a sibling `type.void-parameter`; say which) and a hint to drop the parameter.
- A closure parameter whose type is `Void`, written or inferred from an expected `(Void) -> R`, is refused when it binds a NAME. `{ _ in … }` is the spelling.
- **Unchanged:** a type-parameter-typed parameter stays legal at `T = Void` (instantiation uniformity), so `func foo<T>(v: T)` called as `foo(v: nothing())` compiles. A function TYPE naming `Void` in a parameter position (`(Void) -> Int` as a type) is not a binding, and stays legal unless the user says otherwise.

**Evidence (the Air, SL-772's review):**
- sawc2 accepts `func takes(v: Void) -> Int` called as `takes(noop())` (prints 1).
- It also accepts `apply({ v in 2 })` through a declared `(Void) -> Int` (prints 2).
- Stage 0 hits an internal compiler error on both.

**Pins:**
- refusal fixtures for a function, a method, an `init`, and a named closure parameter;
- accepted: `{ _ in 2 }` through `(Void) -> Int`, and `foo<T>(v: T)` at `T = Void`.
- **Spec:** one clause in "Binding a `Void` expression" (parameters bind names too).

**SL-774.p1 submitted (one commit; agent p774).** The user's ruling: no `Void` parameters; loosen if a use case appears.

**The rule:**
- A declared parameter whose type is `Void` is refused under a new sibling rule, **`type.void-parameter`**. No context forces a signature to take `Void`, so the hint says to drop the parameter.
- A named `Void` closure parameter is refused under `type.void-binding`, with `{ _ in … }` as the spelling.
- Both are entry points of `refuse_void_binding` (`check_function_body`, `closure_typed`).

**The lead accepts three reads, each following "no use case, loosen later":**
- `func takes(_: Void)` is refused too (`_` doesn't excuse a declared `Void` parameter);
- trait requirements are refused too;
- a defaulted `v: Void = noop()` is refused.

**Matrix:**
- **Refused:** function, method, `init`, requirement, defaulted and `_` parameters; closures with the type written, inferred from `(Void) -> Int`, or solved as `T = Void`. Stage 0 crashes on most of these.
- **Accepted:** `{ _ in 2 }` through `(Void) -> Int`, `foo<T>(v: T)` at `T = Void`, `(Void) -> Int` written as a type, and `v: Void?`.

**Pins:** six `type.void-parameter` fixtures, three closure fixtures, and the accepted golden `void_parameter_controls`. Its program prints `2 / 3 / 1 / 2`, checked by hand, since typecheck goldens don't run.

**Docs:** the spec's clause (a parameter binds a name too), the saw-lang skill line, and the typecheck README rows.

**Corpus:** no row moves; no corpus program declares a `Void` parameter.

**Gate (agent):**
- `run.py --only subset,resolver,typechecker,mir,eval,borrowck,drops,mono,coro,programs,std,std_cone`: green.
- `corpusdiff.py gate`: green.
- `battery.sh citations docverify`: green.

**Not covered:** `&Void` (a reference type, not `Void`), the same as SL-772's bindings.

The agent also reported `var g: ((Int) -> Int)? = None` building invalid IR ("duplicate case value in switch"). The lead could NOT reproduce it with a basic optional-function program (it builds and runs), so it's unconfirmed and not filed; the exact shape is needed.
