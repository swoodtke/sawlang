## Description

**Design: a join inside a task is a suspension point, so a driven task's join parks instead of sweeping nested.** Required by the owner's SL-1150 ruling (Nov 17): under a runtime that owns the background group, a join that cannot complete PARKS the joining task and the drive returns. SL-1150 is HELD until this is designed and built (the owner, Nov 17).

**Why it is a design:** `Task.join` is a sync function (`compiler/typecheck/src/stdsuspension.saw` row `TC_STD_SYNC`); inside a task it runs a nested sweep (`exec_run`), and a frame can only park at a suspension point. SL-1150's round (`.build/scratch/p1150r/` in the lead's checkout: `handle_across_park.log`, the design note) found that making it one changes: every caller of `join` becomes suspending (Saw infers suspension through calls, so a sync `main` that joins becomes a suspending one); a `sync` function that joins is refused; and a task holding a `Task` handle across a suspension is refused today (`coro.spawn-not-send: ... Task<Int> is held across a suspension but is not Send`).

**To design (Opus, with a prototype; the owner rules the language questions):**
- The join's two shapes: a suspension point inside a task (park on the joined task's completion, woken by it), and the nested sweep where no executor turn is running (a sync `main`, a thread body): one `join` that is a suspension where it can be and a sweep where it must, or two spellings. What the inferred-suspension rule makes of each caller, measured over the tree and sawos (the census).
- The Send rule for a `Task` handle held across a suspension (same thread; the handle's group lives on that thread).
- `Thread.join`, a group's teardown, `TaskGroup` joins: the same question for each.
- Hosted behaviour: what changes for a program that joins today (output, ordering, deadlock reports), with a hosted comparison.
- The SL-1150 cases (f355's two join shapes) and the suite rows; the spec.

Lands before SL-1150. Related: SL-1150, design 242 (the Thread/Task split).

**The design pass (Nov 24; `.build/scratch/p1161d/design.md` in the lead's checkout; std-only prototype `p1161d/D/proto.diff`; census and hosted comparison beside it).**

**Owner rulings (Nov 24):**
- **Q1/Q2: one `join`, a pair** (std's third, after `Channel.receive` and `Thread.join`).
  - Inside a task it parks until the joined task finishes.
  - Its `blocking` twin runs today's nested sweep in thread context.
  - A sync `main` that joins becomes a suspending `main` (`func main() blocking` keeps the sweep).
  - A `sync` function, a non-`blocking` `deinit`, a closure body, a lock window or an `@export` that joins gets the existing diagnostic.
- **The Send rule: `Task` and `TaskGroup` are thread-bound.** A spawned task may hold one it made across a suspension, but never receive one as a root parameter or result. The rule is the same in every group form (SL-788's "same check"). A pool keeps such a task on the worker that made it.
- **Teardown: T2.** A group local in a suspending function parks at its scope end, before its `deinit`, so the drive never waits. It gets its own unit (U4) with its census.
- **"Hosted behaviour is unchanged" covered only the deadlock report** standing down under an owning runtime. Hosted joins follow the same rule as freestanding.

**Lead's acceptance of the design's other defaults:**
- `Thread.join` is unchanged.
- A pool task's join keeps the nested sweep, decided at run time. When the prototype parked it, 8 pool probes hung, because a pool worker never runs its own background group.
- A join is not a cancellation point.
- A task parked on a join counts as waiting in the deadlock walk.
