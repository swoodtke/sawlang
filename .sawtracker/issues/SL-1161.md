## Description

**Design: a join inside a task is a suspension point, so a driven task's join parks instead of sweeping nested.** Required by the owner's SL-1150 ruling (Nov 17): under a runtime that owns the background group, a join that cannot complete PARKS the joining task and the drive returns. SL-1150 is HELD until this is designed and built (the owner, Nov 17).

**Why it is a design:** `Task.join` is a sync function (`compiler/typecheck/src/stdsuspension.saw` row `TC_STD_SYNC`); inside a task it runs a nested sweep (`exec_run`), and a frame can only park at a suspension point. SL-1150's round (`.build/scratch/p1150r/` in the lead's checkout: `handle_across_park.log`, the design note) found that making it one changes: every caller of `join` becomes suspending (Saw infers suspension through calls, so a sync `main` that joins becomes a suspending one); a `sync` function that joins is refused; and a task holding a `Task` handle across a suspension is refused today (`coro.spawn-not-send: ... Task<Int> is held across a suspension but is not Send`).

**To design (Opus, with a prototype; the owner rules the language questions):**
- The join's two shapes: a suspension point inside a task (park on the joined task's completion, woken by it), and the nested sweep where no executor turn is running (a sync `main`, a thread body): one `join` that is a suspension where it can be and a sweep where it must, or two spellings. What the inferred-suspension rule makes of each caller, measured over the tree and sawos (the census).
- The Send rule for a `Task` handle held across a suspension (same thread; the handle's group lives on that thread).
- `Thread.join`, a group's teardown, `TaskGroup` joins: the same question for each.
- Hosted behaviour: what changes for a program that joins today (output, ordering, deadlock reports), with a hosted comparison.
- The SL-1150 cases (f355's two join shapes) and the suite rows; the spec.

Lands before SL-1150. Related: SL-1150, design 242 (the Thread/Task split).

**Changes requested, revisions 4 and 5** (r5 is r4 rebased; the diff is unchanged). r4 fixes my three r3 hangs, and its new pins fail on r3 as they should. **1. A teardown inside a `Mutex` window resumes pinned frames on top of the window.**

The shape: a pool task opens `borrow var c = shared.value().lock() { ... }`, and inside the window a `TaskGroup` with a live task is torn down. The teardown waits in place, and on r4 that sweep's `resume_bound` resumes every ready frame bound to the worker. A frame that takes the same lock panics. A frame whose wait depends on a thread blocked on the lock hangs, and nothing reports it, since that thread counts as running.

The pinned frames need hold nothing across a sleep. In the "b" probes each task sleeps first, then makes a group and joins its child, which v0.24.3 builds and r4 marks thread-bound. Runs at -O0 (on r4, r3 and v0.24.3, unless noted):

| `lockwin_teardown_b`: a `sync` helper drops a cooperative group | **panic 20/20** | pass 20/20 | pass 10/10 |

- **A sample of a hung `lockwin_thread_sender_b` run** shows `holder` inside its window → `TaskGroup.deinit` → `exec_run` → `sweep_passes` → `resume_bound` → `waiter` → `Task.join` → `__join_wait` → `exec_run` → … → `idle` → `kevent`, with all four sender threads in `Mutex.acquire`.

**The mechanism.** `check_window_calls` refuses a call in a `borrows(sync)` window only when it may suspend. A `sync` helper never suspends, and an implicit teardown is not a call, but both can wait in place by driving the executor. `resume_bound` has no exception for a thread holding a lock window.

**The class came in at r1; r4 widens it.** `lockwin_coopchild.saw` (the holder's own `Task.spawn` children, run inside the window's sweep) hangs 6/6 on r3 and 6/6 on r4. **The patch's text says this cannot happen:**
- **`Mutex.lock`'s doc:** "That wait always ends: the window cannot suspend, so the holder is a thread or a task inside a window that runs to its end without ceding".
- **K206 as amended:** "the routes that reach the run-time panic are the two names for one lock and a static reached from a helper". The table above is a third route.
- **SL-1156.p6 r2:** its `drives` bit does not close it either; that compiler builds both "b" probes.

**Please fix the mechanism, not the probe.** Inside a lock window, a wait that drives either must not happen, or must not run other frames. Two directions:
- the window fence refuses a driving wait at every position: a teardown in the window's body, one in a `sync` helper at any depth, a pool's teardown, and the other drive points in your census;
- or the sweep runs no other frame while its thread holds a window, and whatever then waits on the lock is reported rather than hung.

Either way, please add a position matrix with a pin per row (the four above plus the cooperative route), and bring K206 and `Mutex.lock`'s doc to whatever holds.

The spec's sentence "an exclusive root's window does not suspend, and on one thread no other task runs inside it" (Lending a static, the second bullet) is a guarantee the compiler states, so it governs.
