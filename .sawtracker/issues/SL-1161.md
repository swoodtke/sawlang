## Description

**Design: a join inside a task is a suspension point, so a driven task's join parks instead of sweeping nested.** Required by the owner's SL-1150 ruling (Nov 17): under a runtime that owns the background group, a join that cannot complete PARKS the joining task and the drive returns. SL-1150 is HELD until this is designed and built (the owner, Nov 17).

**Why it is a design:** `Task.join` is a sync function (`compiler/typecheck/src/stdsuspension.saw` row `TC_STD_SYNC`); inside a task it runs a nested sweep (`exec_run`), and a frame can only park at a suspension point. SL-1150's round (`.build/scratch/p1150r/` in the lead's checkout: `handle_across_park.log`, the design note) found that making it one changes: every caller of `join` becomes suspending (Saw infers suspension through calls, so a sync `main` that joins becomes a suspending one); a `sync` function that joins is refused; and a task holding a `Task` handle across a suspension is refused today (`coro.spawn-not-send: ... Task<Int> is held across a suspension but is not Send`).

**To design (Opus, with a prototype; the owner rules the language questions):**
- The join's two shapes: a suspension point inside a task (park on the joined task's completion, woken by it), and the nested sweep where no executor turn is running (a sync `main`, a thread body): one `join` that is a suspension where it can be and a sweep where it must, or two spellings. What the inferred-suspension rule makes of each caller, measured over the tree and sawos (the census).
- The Send rule for a `Task` handle held across a suspension (same thread; the handle's group lives on that thread).
- `Thread.join`, a group's teardown, `TaskGroup` joins: the same question for each.
- Hosted behaviour: what changes for a program that joins today (output, ordering, deadlock reports), with a hosted comparison.
- The SL-1150 cases (f355's two join shapes) and the suite rows; the spec.

Lands before SL-1150. Related: SL-1150, design 242 (the Thread/Task split).

Requested changes on patch SL-1161.p1 (revision 3) (its test run was cancelled)

**Changes requested.** K227 admits shapes that hang on a worker pool, and one of them is a real deadlock the runtime never reports.

A compiler without this patch (main plus SL-1170) refuses the first three probes below with `coro.spawn-not-send` ("local `t` of type `Task<Int>` is held across a suspension"). With the patch they build and hang. Each control passes. I built and ran these myself at -O0 with a 10 s limit; a first-pass agent's larger tallies agree, including hangs that lasted 120 s with no CPU.

**1. A frame pinned to a worker starves while that worker waits inside a join** (`pinsweep2_bound.saw`, f451).
- **The shape:** in `TaskGroup(threads: 2)`, eight feeder tasks each hold a `Task.spawn` handle across a 30 ms sleep, then send. A ninth task joins a cooperative child that receives all eight.
- **Result:** 5/5 hang. The same program without the held handle passes 5/5 in 0.03 s.
- **Mechanism:**
  - `worker_turn` treats a slot bound to another worker as busy (`s.bound != 0 && s.bound != record`).
  - A pool task's `Task.join` waits in place: a sweep of its worker's cooperative groups, or `await_task`'s condition wait.
  - Neither resumes that worker's own pool slots, so a feeder pinned to the joiner's worker never runs again.
  - K227's "resumes it only on the worker that first resumed it" is what pins it. No row says a pinned frame still makes progress while its worker waits.

**2. A pool task that waits on a child it made hangs** (`heldchild_group_pool2.saw`, f452).
- **The shape:** a task of `TaskGroup(threads: 2)` makes a `TaskGroup()`, spawns a child that sends, then receives. 5/5 hang; the same body on a cooperative host passes 5/5.
- **The starvation is older:** the base compiler builds a variant that detaches its child (`heldchild_detach2_pool2`), and it hangs 3/3 there too. But K227 now admits the direct shape.
- **The patch's own probe misses it:** `thread_bound_handles_held_across_suspension.saw` runs `held_over_receive` only on `coop`, a cooperative group.

**3. A deadlock among pinned tasks goes unreported under `main() blocking`** (`walk_bound_t4_blocking.saw`, f453).
- **The shape:** four tasks of `TaskGroup(threads: 4)` each hold a `TaskGroup()` across a `receive()` nobody sends to, and `main() blocking` joins them.
- **Result:** 10/10 hang silently. With a plain `main`, 10/10 report the deadlock.
- K200 and K226 say such a deadlock "is reported by the deadlock walk".
- **Mechanism:**
  - `worker_turn` counts a parked slot bound to another worker as busy.
  - `pool_wait` walks only when no slot is busy.
  - A blocking `main` waits in `await_task`'s condition wait, which never walks.
  - The agent found that it takes stuck frames pinned to two or more workers: one stuck task is reported 60/60.

**What I'd ask:** for each of the three, either make it work (a worker waiting in place still runs the frames bound to it, and the walk counts a parked bound slot as parked), or refuse it in the checker. Give each shape a run case, and make K227's text say which.

**4. Text.**
- **K200's new headline** ("a `join()` made by a suspending `main` or a spawned task parks the joiner") is false for a pool task, which K226 itself says "runs that task in place". `inv_host_pool_afirst.saw` (f454) shows the difference: the same body finishes 5/5 hosted by a cooperative task and panics "deadlock" 5/5 hosted by a pool task.
