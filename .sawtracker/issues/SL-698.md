**A test-only `main` is the entry point of a normal build.** Found by SL-644's root sweep (agent t644roots).

```saw
@test func main() { print("test main") }
```

`sawc2 build --std-root std` builds it (rc 0), the binary prints `test main`, and `nm` shows `T _main` and `t _saw p_main.main()`. The `@test { func main() { … } }` group spelling does the same. With a production `main` beside it, the build is refused as `overload.indistinguishable` at the test-only `main`: a name clash, not test-only isolation.

**Mechanism (from reading, unverified):** mono's `add_roots` (`compiler/mono/src/worklist.saw`) finds the entry point with `tc.top_decl(entry, "main")`, a by-name lookup in the entry module's top table that doesn't filter test-only declarations. It is the one root mono picks by plain name lookup. The sweep found every other root kind closed: exports (SL-631), lang items (std only), task and drive roots and statics (refused earlier as `test.only-reference`), and test-only members and conformances (absent from the binary).

**Expected (SL:testing):** a normal build emits no test-only declaration, so a program whose only `main` is test-only has no entry point in a normal build. Whether that is a refusal ("no `main`", as a program without one gets) or something else is for the fix to match against the existing no-`main` behaviour. A test-only `main` beside a production one should not clash in a normal build, since the test-only one doesn't exist there. Check how Stage 0 and the spec treat both shapes.

**Pins:** both spellings, as an XFAIL pin citing this issue until the fix, then the expected refusal. Plus the clash case.

**m698main: fixed in commit 5a5b1ea5d in the worktree, not submitted.** Both spellings reproduced on main (c4ea336a3): `@test func main` and `main` in an `@test { }` group built, ran and printed. The sweep also found a worse shape: a production `main()` beside a test-only overload `main(x: Int)`, in either spelling, ran the test-only one. `top_decl` returns the newest declaration of the name, and the clash rule doesn't apply because the two are distinguishable.

**Decisions:**
- **Only `main` is test-only:** the program now reads exactly as one with no `main` at all, `INVARIANT mono the entry module declares no \`main\` with a body`. That no-`main` output is an INVARIANT line, not a refusal with a rule, so I didn't pin it as one. Filed as SL-707, with `main` with parameters, overloaded production `main`s and a bad return type: the entry-point rule has no checker in sawc2.
- **A test-only twin of a production `main`:** the `overload.indistinguishable` refusal stands. It's the general rule for any test-only twin (`overload.indistinguishable.test-only`): a test build holds both, so no call from test code could pick one. SL-631's `export.duplicate.test-only` rests on the same reading, and SL-626 doesn't change it, since its per-overload filter governs who may *call* an overload, not whether two declarations clash.

**The fix:** `TcProgram.top_decl` (`compiler/typecheck/src/program.saw`) passes test-only declarations over and names its entry points: `add_roots`, `exec_entry`, `resolve_spawn`, `coro_context_shape` and `find_known`.

**Sweep (lookups by name that decide emitted code):**

| lookup | test-only reaches a normal build? | evidence |
|---|---|---|
| mono `add_roots`: `main` | yes, fixed | probes above |
| mono `exec_entry`: `__saw_exec_*` in std.taskgroup | yes, fixed | std copy with `@test` on `__saw_exec_task_box`: built and emitted it, now `mono.not-yet … declares no \`__saw_exec_task_box\`` |
| mono `TaskProvenance`, coro `TaskContext`, typecheck `find_known` | no: production std names them | std copies: `test.only-reference` |

| member lookups by name (`deinit_member`, `format`, `copy`) | no | `deinit.outside-policy`, SL-630/640/659's rules |
| a sidecar `main` | not reachable | sawc2 loads no `*.test.saw` |
