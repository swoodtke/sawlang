**A test-only `main` is the entry point of a normal build.** Found by SL-644's root sweep (agent t644roots).

```saw
@test func main() { print("test main") }
```

`sawc2 build --std-root std` builds it (rc 0), the binary prints `test main`, and `nm` shows `T _main` and `t _saw p_main.main()`. The `@test { func main() { … } }` group spelling does the same. With a production `main` beside it, the build is refused as `overload.indistinguishable` at the test-only `main`: a name clash, not test-only isolation.

**Mechanism (from reading, unverified):** mono's `add_roots` (`compiler/mono/src/worklist.saw`) finds the entry point with `tc.top_decl(entry, "main")`, a by-name lookup in the entry module's top table that doesn't filter test-only declarations. It is the one root mono picks by plain name lookup. The sweep found every other root kind closed: exports (SL-631), lang items (std only), task and drive roots and statics (refused earlier as `test.only-reference`), and test-only members and conformances (absent from the binary).

**Expected (SL:testing):** a normal build emits no test-only declaration, so a program whose only `main` is test-only has no entry point in a normal build. Whether that is a refusal ("no `main`", as a program without one gets) or something else is for the fix to match against the existing no-`main` behaviour. A test-only `main` beside a production one should not clash in a normal build, since the test-only one doesn't exist there. Check how Stage 0 and the spec treat both shapes.

**Pins:** both spellings, as an XFAIL pin citing this issue until the fix, then the expected refusal. Plus the clash case.
