## Description

**A `constexpr` function that suspends is accepted** (found by p859, the SL-859 sweep, Oct 23; repro `.build/scratch/p859_evidence/inv/i30_constexpr.saw`).

`func f() constexpr -> Int { yield_now(); 1 }` builds and prints 1. SL:architecture and GRAMMAR's effect slot say `constexpr` implies `sync`: a compile-time-evaluable function can't suspend. Callers still treat `f` as may-suspend (i31 is refused twice), so nothing unsound was observed, but the declaration's contract isn't checked.

**Fix:** `constexpr` folds into the `sync` effect at the declaration, so the body's suspension gives `effect.sync` (or a `constexpr`-named variant) at the suspending call, and callers then see `f` as `sync`. Pins: the refusal at the suspending call, and a `constexpr` called from a `sync` function, now accepted.

**Air, pre-review of SL-862.** Probed with `sawc` at v0.18.0 (4ab60f12c, -O0). The probes are in `.build/scratch/air-review/sl862/` on the Air.

**1. No const position can reach a suspending `constexpr` today, so "nothing unsound" holds there too.** With `func f() constexpr -> Int { yield_now(); 1 }`:
- `static X: Int = f()` and `static_assert(f() == 1, …)` are `static.not-constant` ("a call runs only at run time").
- `[Int; f()]` / `[0; f()]` are `slice.not-yet`.

That matches the spec, where calls of const functions are still "(planned)" under Compile-Time Evaluation. The only thing to fix now is the declaration's contract, as the issue says.

**2. The pin "a `constexpr` called from a `sync` function, now accepted" would pass today, so it can't show the fix.** `func k() constexpr -> Int { 3 }` called from `func s() sync -> Int { k() + 1 }` builds and prints `4` (`c3_sync_caller.saw`). Effect inference already sees `k` as sync. The flip is the other side:
- the suspending `constexpr`'s declaration (or its suspending call) refused;
- a `sync` caller of a `constexpr` whose suspension is only through a callee: `func g() constexpr -> Int { h() }` with `h` suspending. That's refused at `g`'s body after the fix, and accepted at the caller.

**3. Obligation 4: suspension is one of several effects a `constexpr` body isn't checked against.** All of these build and run (`c4_body_effects.saw`, output `io at compile time?` then `1 1 true 0 0 0`):

| `constexpr` body | today |
|---|---|
| `print(…)` | accepted, prints at run time |
| `Vector<Int>()` + `push` | accepted |
| an `extern "C"` call (`getpid`) | accepted |
| a `blocking` extern call (`usleep`) | accepted |
| a `static` `Atomic` `load()` / `store()` | accepted |

GRAMMAR's effect slot specifies only "implies `sync`", and the spec hasn't designed what a compile-time body may do yet. So I'm not calling these bugs. They're the open questions for the planned const-function design, and an `effect.sync`-only fix leaves them all accepted. Worth a line in the fix brief saying which are in scope (likely just `sync`, per GRAMMAR) and which wait for that design, so a later reader doesn't take the narrow fix for the whole contract.

The suspension-through-a-callee case (`g` above) is the same `sync` rule reaching the body transitively. It belongs in this fix's matrix: a direct `yield_now()`, a suspending callee, a `Channel.receive`, and an `.await`-shaped `Task.join` inside the `constexpr`.
