## Description

**Soundness: sawc2 accepts a declared `Send` or `Sync`, which the spec makes derivation-only.** Found by the Air on SL-659.

**Evidence** (sawc2 at main; the Air's `send_forged.saw` and `sync_forged.saw`):

```saw
struct Buf {
    raw: UnsafePointer<Int>
}

extension Buf: Send {}

func need<T: Send>(x: &T) {}
```

`extension Buf: Send {}` on a raw-pointer holder typechecks clean, and production code then passes a `Buf` to `need<T: Send>`. The same goes for `extension Buf: Sync {}` with a `T: Sync` bound. That's a safe-code assertion of thread-safety that bypasses every check `UnsafeSend`/`UnsafeSync` make: a field that blocks the derivation must be unsafe-typed, and asserting one where the derivation already succeeds is refused.

**Stage 0 refuses both,** as the spec says (`Send`/`Sync` stay derivation-only): "cannot explicitly implement `Send`: it is a marker trait derived structurally by the compiler".

**Mechanism, presumed a class (obligation 4):** sawc2 has no refusal of a declared conformance to a trait the spec makes derivation-only, so every such trait takes the same unguarded path. Sweep every trait the spec lists as derived structurally, or as automatic-only, and probe a hand-written conformance for each: `Send`, `Sync`, and whatever else the sweep finds, for example the automatic `Equatable`/`Hashable` of a trivially copyable type versus a declared one with `@synthesize`, and the Copy tier. Pin each refusal against Stage 0's wording, and note any trait where a declaration is legal.

**Related:** SL-659's rule (a) puts `UnsafeSend`/`UnsafeSync` in the policy set (defining file only). This issue is separate: it's a missing refusal in every file.

**Reproduced** at main 41a2d2606 (Stage 1, `typecheck --check`): `extension Buf: Send {}` on a raw-pointer holder checks clean and meets `need<T: Send>`, and the same goes for `Sync`. Stage 0 refuses both.

**The matrix** (sawc2 before the fix / Stage 0 / spec):

| trait | sawc2 before | Stage 0 | spec |
|---|---|---|---|
| `Send` | accepted, meets `T: Send` | "cannot explicitly implement `Send`: it is a marker trait derived structurally by the compiler" | derivation-only, "explicit `extension X: Send` is rejected" |
| `Sync` | accepted, meets `T: Sync` | the same, for `Sync` | the same |
| `Deinit` | refused, `conformance.deinit` | refused (as "declares a deinit but no copy policy") | not declarable on its own (The Deinit trait) |
| `Copy` (automatic tier) | accepted | accepted | declarable: the empty `@synthesize` form is an assertion, a body is the retain hook |
| `Equatable`, `Hashable` (automatic for a trivially copyable type) | accepted with `@synthesize` | accepted | declarable; "`@synthesize` applies only where a conformance is written" |
| `ExplicitCopy`, `Comparable`, `Printable`, `Error`, `Iterator`, `NoCopy`, `NoMove`, `ZeroInit`, `UnsafeSend`, `UnsafeSync` | declarable | declarable | declarable (each with its own rules) |

So the derivation-only set is `Send`, `Sync` and `Deinit`. The positions probed for `Send`/`Sync`: a plain head, a conditional generic head, an enum, both in one head, beside `@synthesize`, a test-only extension, a test group, and a type whose members derive it anyway. Before the fix sawc2 accepted all of them; Stage 0 refuses every one it can parse.

**The fix:** one funnel, `check_derived_conformances` (`compiler/typecheck/src/conform.saw`, entry point `tc_check_derived_conformances`). It runs on the conformance table right after it's collected, which holds every written conformance. `Send`/`Sync` are refused as `conformance.derived-only`, using Stage 0's wording plus the `UnsafeSend`/`UnsafeSync` way out. `Deinit`'s refusal, `conformance.deinit`, moves into the same funnel unchanged. The refused conformance is left in the table, so it adds no `type.bound` cascade. No consumer in std, compiler, libs, blade or the corpus writes one; the only hits are Stage 0's own refusal test, `errors/send_explicit_conformance.saw`, and its corpus copy. corpusdiff's baseline row for that copy (`wrong`, "accepts a refusal test") should move to `pass` at the next `--baseline` run.

**Pins:**
- conformance row K154;
- refusal fixtures `conformance.derived-only` (bare, `.sync`, `.derivable`, `.generic`, `.enum`, `.one-extension`, `.synthesize`, `.test-only`, `.test-group`) and `conformance.deinit.test-only`;
- golden `thread_assertions`, the control: `UnsafeSend`/`UnsafeSync` past an unsafe-typed field meet `T: Send`/`T: Sync`, a holder derives both, and a conditional assertion holds at a qualifying argument.

**Needs a ruling: a user trait that refines a derivation-only trait.** sawc2 grants a parent through a conformance to the child (`declares_conformance` checks `trait_refines`), so this forges `Send` the same way, with no `Send` written:

```saw
trait Shippable: Send { func tag(&self) -> Int }
struct Buf { raw: UnsafePointer<Int> }
extension Buf: Shippable { func tag(&self) -> Int { 1 } }
func need<T: Send>(x: &T) {}
func relay(b: &Buf) { need(&b) }    // sawc2 accepts; Stage 0: `Buf` does not satisfy `Send`
```

`trait Closeable: Deinit {}` with `extension Handle: Closeable { func deinit … }` is the `Deinit` face. Both compilers accept it, and on both the `deinit` never runs (the program prints `7 7` and no deinit line), which is the design-131 shape a copy policy exists to prevent. The spec is silent on a user trait refining `Send`, `Sync` or `Deinit`, and Stage 0 answers differently: it accepts the conformance, grants nothing, and also refuses `T: Shippable` as implying `Send` in a generic body. Three readings:

1. **The parent is a requirement, not a grant** (Rust's supertrait reading). The conformance to `Shippable` is legal only where `Buf` derives `Send`, checked at the header under its bounds, and `T: Shippable` implies `T: Send` in a generic body. `Deinit` as a parent would need the type's copy policy.
2. **Refuse the conformance** to any user trait that refines a derivation-only trait, which is the conservative choice.
3. **Refuse the trait declaration** `trait X: Send` itself, outside the builtin `UnsafeSend`/`UnsafeSync`/`NoCopy`/`ExplicitCopy`.

I'd take reading 1 for `Send`/`Sync`, since it keeps `T: Shippable` meaningful, and reading 2 or 3 for `Deinit`. It's not built here.

**Air, on the refinement question (for the user's ruling).** Both faces reproduce at main 41a2d2606 (`.build/scratch/air-review/sl659/refine_send.saw`, `refine_deinit.saw` on the Air):
- `trait Shippable: Send`, conformed to by a raw-pointer `Buf`, then `need<T: Send>(&b)`: sawc2 accepts it; Stage 0 refuses with "type `Buf` does not satisfy the `Send` bound".
- `trait Closeable: Deinit` with a `func deinit` in `Handle`'s conformance: **both** compilers build it and print `7 7`, and the `deinit` never runs. A hand-written teardown is silently dropped on both compilers.

**My lean: reading 1 for `Send`/`Sync`, reading 3 for `Deinit`.**
- **`Send`/`Sync`, reading 1** (the parent is a requirement, not a grant). In ordinary Saw refinement, a child conformance supplies the parent's requirements (`extension E: Error { func format … }` makes `E` Printable). A derivation-only parent has no requirements to supply, only a structural fact, so the child can't grant it, and it should be checked at the header: `Buf: Shippable` is legal only where `Buf` derives `Send` (or asserts `UnsafeSend`, under SL-675's legality rules). Keeping `T: Shippable` ⇒ `T: Send` in generic bodies is what makes such a trait worth writing; Stage 0 refusing that implication is its own inconsistency, not a reason to copy it.
- **`Deinit`, reading 3** (refuse `trait X: Deinit` at the trait). `Deinit` isn't declarable, and design 131 puts a hand-written `deinit` inside a copy-policy conformance. So a trait refining it can only be met by the shape a policy exists to prevent, and today that shape loses the teardown silently. One refusal at the trait declaration says so once, where the author wrote the mistake, instead of at every conformance. Stage 0 has the same silent drop, so it wants an SL:hazards entry at landing.

**The user's ruling, Oct 14, on the refinement route:** reading 1, "Requirement, not grant". A user trait that lists `Send` or `Sync` as a parent requires it of its conformers and never grants it: `extension Buf: Shippable {}` is legal only where `Buf` derives `Send` (checked at the conformance, under its bounds), and `T: Shippable` implies `T: Send` in a generic body. For `Deinit` as a parent, the recommendation the user accepted with it: refuse `trait X: Deinit` outright, since a `deinit` belongs to the type's copy policy.

**s673derive: the ruling is built, in two commits** (`ffc8564a3`, then `c4077c3f1`), rebased on origin/main 982654492 and not submitted.

- **Requirement, not grant.** `conformance_grants` (conform.saw) is the one answer to whether a conformance gives its type a trait: `Send` and `Sync` come only from themselves or from `UnsafeSend`/`UnsafeSync`, and any other parent through the refinement. `declares_conformance` and `unmet_sync_condition` read it. A bound `T: Shippable` still meets `T: Send` in a generic body (`generic_grants`, unchanged).
- **The check at the conformance.** The derived-only funnel, `check_derived_conformances`, moved to checks.saw because it needs bound satisfaction. It checks each conformance to a trait refining `Send` or `Sync` under the extension's conditions, as code that may use the conformance sees it, and refuses it as `conformance.derived-parent`, naming the parent and the blocking field or payload.
- **`Deinit` as a parent.** A user trait listing `Deinit` as a parent is refused as `trait.deinit-parent`; `NoCopy` and `ExplicitCopy` are the only traits that may.
- **Pins:** conformance row K155; fixtures `conformance.derived-parent` (bare, `.sync`, `.generic`, `.enum`, `.chain`, `.test-only`) and `trait.deinit-parent`; goldens `derived_parents` and `derived_parent_grants_nothing`. `derived_parents` holds the accepted rows (a plain, a conditional, a bounded-parameter and an enum conformer, a chain reaching `Send` and `Sync`, `UnsafeSend` beside the refining trait) and the generic bodies. sawc2 builds and runs it. `derived_parent_grants_nothing` shows that a refused conformance leaves the type short of a `T: Send` bound.
- **Gate:** `run.py --only typechecker,fixture_whitespace,subset,units,std` and `battery.sh citations`, both green on the rebased tree.
- **Stage 0 diverges on three points,** which may want an SL:hazards entry. It accepts `trait X: Deinit`. It accepts a conformance to `Shippable` on a non-`Send` type, though it grants nothing. And it refuses `T: Shippable` as `T: Send`.
- **The spec text** for the ruling (spec, Send and Sync, and The Deinit trait) is not written here.
- **For SL-675:** a user trait refining `UnsafeSend` now grants nothing and requires a derived `Send`. The assertion's "one position" fence should refuse such a trait outright.
