## Description

**Soundness: sawc2 accepts a declared `Send` or `Sync`, which the spec makes derivation-only.** Found by the Air on SL-659.

**Evidence** (sawc2 at main; the Air's `send_forged.saw` and `sync_forged.saw`):

```saw
struct Buf {
    raw: UnsafePointer<Int>
}

extension Buf: Send {}

func need<T: Send>(x: &T) {}
```

`extension Buf: Send {}` on a raw-pointer holder typechecks clean, and production code then passes a `Buf` to `need<T: Send>`. The same goes for `extension Buf: Sync {}` with a `T: Sync` bound. That's a safe-code assertion of thread-safety that bypasses every check `UnsafeSend`/`UnsafeSync` make: a field that blocks the derivation must be unsafe-typed, and asserting one where the derivation already succeeds is refused.

**Stage 0 refuses both,** as the spec says (`Send`/`Sync` stay derivation-only): "cannot explicitly implement `Send`: it is a marker trait derived structurally by the compiler".

**Mechanism, presumed a class (obligation 4):** sawc2 has no refusal of a declared conformance to a trait the spec makes derivation-only, so every such trait takes the same unguarded path. Sweep every trait the spec lists as derived structurally, or as automatic-only, and probe a hand-written conformance for each: `Send`, `Sync`, and whatever else the sweep finds, for example the automatic `Equatable`/`Hashable` of a trivially copyable type versus a declared one with `@synthesize`, and the Copy tier. Pin each refusal against Stage 0's wording, and note any trait where a declaration is legal.

**Related:** SL-659's rule (a) puts `UnsafeSend`/`UnsafeSync` in the policy set (defining file only). This issue is separate: it's a missing refusal in every file.
