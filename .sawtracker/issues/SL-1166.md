## Description

**A task's frame has a compile-time maximum size, set per target profile, raised with `--max-task-frame=SIZE`.** Owner direction (Nov 18): a task frame is heap-allocated, and sawc lays it out itself (the coroutine transform, before LLVM), so its exact size is known at compile time and does not vary with `-O`. A limit turns an oversized frame into a clean compile error instead of a failure at spawn. Thread stacks are left alone: they fault at run time through the known mechanisms, and this issue does not add a stack-frame limit.

**Design (lead's, from the owner's direction; open points marked):**
- **Flag:** `--max-task-frame=SIZE`. SIZE is bytes, or a number with a binary suffix (`KiB`, `MiB`, `GiB`). It follows sawc's long-flag style (`--codegen-units`, `--no-hidden-alloc`) and the docs' vocabulary (task, suspending function, never "coroutine").
- **Per package:** a Blade `[package]` key, as `no-hidden-alloc` is (SL-1154), handed to sawc for each build.
- **What is measured:** the frame the runtime allocates for a task, which is a task root's frame (`Task.spawn`, `group.spawn`, a suspending `main`, the background group) including every suspending callee frame laid out inside it. Each suspending function's own frame is reported as blame.
- **The error** names the root and its total size, and the largest contributors (which locals or nested callee frames add the bytes, each with its size), so the reader can see what to shrink. Rule id: OPEN (a new `task.frame-size`, or under `constant.overflow`'s family; prefer a new id, since this is a policy, not an overflow).
- **Defaults per target profile, from measurement:** hosted and freestanding differ by orders of magnitude (the ESP32-S3 has ~512 KB SRAM). UNIT 1 measures before any default is set: the largest task frames in std, Blade, `libs/`, the corpus, the freestanding suite and sawos (`sawc coro --layouts`; report each root's frame and the top ten across the tree, per target). The lead proposes defaults with headroom from those numbers; the owner rules them.
- **Relation to SL-1116:** the target-`Int` bound (overflow) stays the hard ceiling; this is the policy limit below it, checked on a frame that already fits. Relation to SL-1163 (object size): separate, since a frame is not a declared type.

**Units:**
1. Measurement (a sweep, no change).
2. The rule: the check at the frame layout (`coro_lay_out_frame`, after SL-1116's funnel), the flag, the Blade key, the error with contributors, the defaults as ruled, and fixtures for an over-limit root, a raised limit accepting it, a nested callee's frame blamed, the Blade key, and a freestanding target's default.
3. Docs: LANGUAGE_SPEC.md (the limit and the flag), README's CLI list, the saw-lang skill.

Lands after SL-1116 (it uses its checked frame arithmetic). Related: SL-1116, SL-1154, SL-1163.

**Unit 1, the measurement (Nov 18; scripts and dumps in `.build/scratch/s1166/` in the lead's checkout):** about 6,100 runs of `sawc coro --layouts`, one at a time, peak 198 MB, no build.

**How a root shows:**
- A task root prints as `NAME task root (size S align A, lower bound L)`. Suspending callees are embedded by value as `child` slots, so S is the whole heap allocation. The packer is tight: at most 8 bytes over the lower bound.
- A suspending `main` is not boxed: its frame is on the C entry's stack, and a drive site allocas its own. Mains are stack, outside this issue (thread stacks are left alone).
- `coro` takes no `-O`, so the layout cannot vary with optimisation.

**Task roots (heap):**

|---|---|---|---|---|---|---|
| hosted programs | arm64 | 2,232 | 48 | 152 | 376 | 1,384 (excluding the one deliberate test) |
| hosted programs | riscv32 = xtensa | 2,210 | 28 | 80 | 224 | 692 |
| freestanding suite | riscv32 / xtensa | 8 | | | | 52 |

- **The one large root** is `tests/corpus/coro_frame_over_65535_nonconstant_values.saw`, written to be big: 524,328 bytes on arm64 and 262,164 on 32-bit, from a `[UnsafePointer<Int>; 65536]` local across a `yield_now`.
- **The largest std contributors** (arm64 / 32-bit):
  - `Command.output`: 280 / 168
  - `TcpStream.write(String)`: 248 / 152
  - `TcpStream.connect`: 192 / 136
  - `TcpStream.read`: 192 / 128
  - a `TaskGroup` local: 184 / 92
- **Not measured:** sawos's Blade packages (they need per-package module paths), programs that need `--runtime-provider`, and a few refused probes.

**Side finding:** `Result` wrappers stay resident in a frame across suspensions beside their unwrapped values. In K68's `main`, `Result<TaskGroup, AllocError>` is 192 bytes across three suspensions. The mechanism is UNVERIFIED (a copied-only local never stops being initialised?).

**Lead's proposed defaults, for the owner's ruling:**
- hosted: 64 KiB, about 45 times the largest ordinary root;
- freestanding: 4 KiB, about 40 times the largest freestanding root and 6 times the largest 32-bit hosted root.

The deliberate test then states `--max-task-frame=1MiB` in its `COMPILE-FLAGS`.

**Owner ruling (Nov 18):**
- **Defaults:** hosted 1 MiB, freestanding 4 KiB. That is lenient on hosted and small on freestanding, where it matters more. The deliberate 512 KiB corpus test fits under the hosted default and needs no flag.
- **Scope:** per image. The check runs at compile time for each linked program, and the root package's setting (flag or Blade key) governs every task in it, dependencies included. Recording the image's largest frame for a loader check is a possible later follow-up, not part of this issue.

Unit 2 (the rule) is dispatched after SL-1116 lands; it builds on SL-1116's checked frame arithmetic.

**Lead's note with p1 (Nov 18): unit 2, the rule, as the owner ruled** (defaults of 1 MiB hosted and 4 KiB freestanding; per image; the root package governs). The measurement is unit 1's comment. Evidence: `.build/scratch/p1166/` in the worktree.

- **What is limited:** every task root a cooperative spawn site reaches (`MirCallKind.Spawn`, Singleton and Group: `Task.spawn`, `group.spawn` and the background group), all boxed by `__saw_exec_task_box`.
  - A drive site's root (stack, `coro/src/drive.saw`) and a suspending `main` are NOT limited (`accepted.main-frame-not-limited`, a 2,000,016-byte `main`).
  - `Thread.spawn` is untouched.
  - No exported suspending entry boxes a frame.
- **The limit:** one funnel, `coro_task_frame_limit` (`compiler/coro/src/taskframe.saw`): the flag's value, or else 1 MiB hosted and 4 KiB freestanding by the profile.
- **The rule:** `task.frame-size`, checked after the layout (`coro_check_task_frames`, from the lowering and from `coro --layouts`), once per root at its first spawn site.
  - It names the root, its size, the limit and `--max-task-frame`.
  - It lists the four largest slots; a child shows as "the frame of `inner` 70016 bytes".
- **The flag:** `--max-task-frame=SIZE` (bytes, or `KiB`/`MiB`/`GiB`), parsed once in `driver_task_frame_size` for `build` and `coro`. Bad spellings exit 2, naming the flag; 41 spellings are pinned in `coro_lane.py`. `sawc coro` also takes `--freestanding`.
- **Blade:** `[package] max-task-frame = "64KiB"`, a string in the flag's own spelling, passed for the root package only, in `build`, `test` and the `[sos]` image site.
  - Blade checks the shape (digits plus an optional suffix), since `blade test` builds a shell string. sawc judges zero and overflow.
  - The lane covers refusal at build and test, a larger key building, a rebuild on change, bad spellings, and a dependency's key ignored.
- **Fixtures:** in `compiler/tests/coro/refuse_layout/`, all `coro --layouts` only, nothing near the limit built:
  - hosted over the limit;
  - raised by the flag;
  - exactly at the limit;
  - one past the limit;
  - freestanding over the limit (riscv32);
  - the child frame named.
  
  SL-1116's `accepted.frame-quarter` (a 2^62-byte frame) now states `--max-task-frame` for its edge.
- **Corpus:** `coro --layouts` over all 1,808 top-level `tests/corpus/*.saw` programs finds no `task.frame-size`. The 524,328-byte test stays accepted.
- **Docs:** LANGUAGE_SPEC.md, README, Blade's README, the saw-lang skill, the coro README and CLAUDE.md's usage line.
