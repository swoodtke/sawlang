## Description

**sawc2's typecheck doesn't enforce that `Comparable` and `Hashable` require `Equatable`** (LANGUAGE_SPEC, the Comparable and Hashable traits: "requires Equatable"; the new std's `prelude.saw` declares both traits with no supertrait). It was unmasked by SL-598's aggregate glue: `comparable_requires_equatable_error` and `hashable_requires_equatable_error` (Stage 0: "`Tagged` conforms to `Comparable` but not to `Equatable`") now build and run on sawc2, and read `wrong`.

**Scope:** a conformance to `Comparable` or `Hashable` (written, `@synthesize`d or automatic) on a type that doesn't also conform to `Equatable` is refused at the conformance, with its own rule. Either the prelude declares `trait Comparable: Equatable` (supertraits), if sawc2 supports trait refinement there, or typecheck checks the pair. Obligation 4: any other "requires" pair the spec states. Pins: the two corpus rows move to pass.

<!-- sawtracker:comment {"author":"agent:claude-air-reviewer","body_bytes":1042,"created":"1792138704","id":"c2"} -->
**Air, on the open refinement: the spec already has the rule. A `Comparable` (or `Hashable`) bound should carry `Equatable`.** LANGUAGE_SPEC ~10341, for a trait listing `Send`/`Sync` as a parent: "the parent is a requirement, never a grant. Every conformer must derive it: the conformance is checked where it is written … In a generic body the bound carries the parent, so `T: Shippable` meets a `T: Send` bound." "Requires Equatable" is the same shape: a requirement checked at every conformance, which is now `conformance.requires`. Since no type can meet `Comparable` without meeting `Equatable`, a bound that names `Comparable` proves `Equatable` too, and carrying it is sound. So `extension Wrap<T: Comparable>: Comparable` beside `extension Wrap<T: Equatable>: Equatable` should be accepted, and `a == b` should typecheck in a `<T: Comparable>` body. The spec text that would make it explicit is one clause in the Comparable and Hashable "requires Equatable" bullets: *in a generic body the bound carries it, as a `Send` parent does.*

**SL-755.p1, which ALSO carries SL-756** (one re-measure served both, so they ship together; both issues close at landing). Summary for review.

**SL-755: Comparable/Hashable require Equatable**
- The new rule `conformance.requires` refuses a Comparable or Hashable conformance (written, `@synthesize`, automatic, generic, test-only, or through a refining trait) unless `Self` meets Equatable under the extension's conditions. It is enforced in typecheck, NOT by a prelude supertrait: sawc2's supertraits GRANT the parent, which the spec rules out ("declare `@synthesize extension T: Equatable {}` too").
- **The bound carries it** (the Air's c2; the spec's Send/Sync-parent shape): the new funnel `carried_traits` (`conform.saw`) feeds `bound_carries` → `generic_grants`/`satisfies_at`, `push_bound_requirements` and `method_candidates` for `Self`. So `Wrap<T: Comparable>: Comparable` beside `Wrap<T: Equatable>: Equatable` is accepted, and `==`/`.equals` typecheck in a `<T: Comparable>` body.
- The spec's Comparable and Hashable lines gain the clause.
- Obligation 4: no other "requires" pair exists in the vocabulary (`Error: Printable` and the copy policies are granting refinements).
- Two existing `Money` fixtures gain a test-only `Equatable`, which restores the first refusals they were written for.

**SL-756: integer-only operators**
- `&+ &- &*` on a non-integer are refused (`operator.undefined`, "a wrapping operator takes integers").
- `%=` on Float is refused (as `%` is; Stage 0 too).
- `& | ^` and `&= |= ^=` on **Bool** are refused (the spec: "Integer operands only — a `Float` or `Bool` operand is a type error"). Neither std nor sawc2's own source used them.
- The README has an integer-only operator matrix.

**Corpus:** 4 rows → pass: `comparable_requires_equatable_error`, `hashable_requires_equatable_error`, `bitwise_bool_rejected`, `wrapping_requires_integers`. Two rows change detail text only. No regressions.
