Approved patch SL-563.p1 (revision 1)

**Approved, with one sequencing requirement for A8b.** Built on 41a2d2606 with `--3way`, against main at the same commit, at -O0 and -O2, and with Stage 0. The probe is `.build/scratch/air-review/sl563/pin_addr.saw` on the Air.

**A frame-resident `NoMove` value and a `TaskGroup` across a suspension.** A `Task.spawn`ed function holds a `NoMove` `Pinned` (whose `deinit` prints its own address) and a `TaskGroup()` across a `yield_now`:
- patch, -O0: `before at 4344389536 | group count 0 | after resume | deinit 7 at 4344389536 | joined 7`;
- patch, -O2: the same with its own address, again equal before and at `deinit`;
- Stage 0: the same shape (`before at X … deinit 7 at X`);
- main: refused, since `TaskGroup` has no `init` there.

So at the frame position, teardown runs where the value lives, which is SL-662's class answered for frames.

**The `deinit`:**
- it takes `(&self) as UnsafePointer<TaskGroup> as Int` as the group's identity for `exec_run` and `unregister`, which is right exactly when `deinit` runs at the group's home;
- a group nothing was spawned into skips the sweep;
- the panic for a group torn down under one of its own running tasks names the cause.

I agree with the reversible decisions.

**The sequencing requirement (A8b, not this patch).** Through SL-662, `drop_in_place` relocates its pointee, so a `TaskGroup` behind a `Box`, `Vector` or `Map` runs that `deinit` at a stack copy. `me` is then the copy's address, the real group stays linked in the scheduler list, and its storage is freed. Today no safe code can register a task in a user group: tasks enter only through std's unsafe `__saw_spawn`, as the std lane's programs do. So an empty group's relocated teardown is harmless, and this patch exposes nothing. The first unit that adds `group.spawn` (A8b) makes the hole reachable from safe code. **A8b should depend on SL-662's fix** (or refuse a `TaskGroup` behind `Box`/`Vector`/`Map` until it lands); please record that dependency on A8b.
