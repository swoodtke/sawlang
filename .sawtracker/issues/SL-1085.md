## Description

**Three small findings from the review of the ESP32-S3 docs (SL-1077.p1, the Air, Nov 12), none in the docs themselves.**

## 1. Blade reads `[sos.priorities]` as a machine

`priorities` under `[sos]` works only as an inline table (`priorities = { low = 2 }`). Written as its own table:
```toml
[sos.priorities]
low = 2
```
Blade answers `Saw.toml [sos]: this package builds for several machines — pass --target (this manifest declares priorities, xtensa-esp-unknown-elf)`: every subtable of `[sos]` is taken for a `[sos.<triple>]` machine, and Blade's own comment in `blade/src/sosimg.saw` calls the table `[sos.priorities]`. In TOML the two spellings are the same value, so both must read the same.
- **Mechanism to confirm:** where `load_sos_config` enumerates `[sos]`'s subtables as machines, with no exclusion for the keys `[sos]` itself owns.
- **The class:** any other `[sos]`-level key whose value is a table (today only `priorities`; check), and any `[sos.<name>]` that is no known triple, which should be refused by name, not counted as a machine.
- **Fix:** the machine tables are the subtables that are not `[sos]`'s own keys; a subtable that is neither a key nor a triple `target_triples()` knows is an error naming it. Pins in `blade/tests/` (the dotted-table spelling builds; an unknown subtable is refused) and a fixture beside `blade/tests/fixtures/sosxtensa_mcpu/`.

## 2. Blade does not find Espressif's clang for an Xtensa image

`sawc` finds Espressif's clang by itself (`~/.espressif`, `$IDF_TOOLS_PATH`). Blade's C half uses `SOS_CLANG` or plain `clang`, so `blade build --target xtensa-esp-unknown-elf` with a `native` unit and the variables unset fails after the Saw half has built:
```
error: clang failed
error: unknown target CPU 'esp32s3'
```
The docs now say the variables must name the tools. The expected thing is that Blade finds what sawc finds.
- **Question for the lead before dispatch:** sawc learns its clang per target from the runtime manifest beside it. Blade could ask sawc (is there a `sawc` query for a target's recorded clang? if not, one line of output from a new subcommand or flag), which keeps ONE funnel for "which clang compiles for T". It should not re-implement the search.
- The linker likewise: the `ld.lld` beside that clang, when `SOS_LD` is unset.
- The variables stay as overrides.

## 3. The freestanding suite's Xtensa link script orders every literal before every text

`tests/freestanding/hal/xtensa/link.ld` lists `*(.literal .literal.*)` and then the text sections. `l32r` reaches a literal at most 262,141 bytes before it (the Air measured: 0x30000 between links, 0x40010 does not), so that order stops linking once an output section's code passes about 256 KiB. The suite's cases are far smaller, so nothing fails today. The pattern that keeps each `.literal.NAME` just ahead of its `.text.NAME` is `*(.literal .literal.* .text .text.*)`, and the spec now recommends it; our own script should be the example of it.
- Change the script (every output section that holds code), run the row: expected 41 passed, unchanged.
- sawos has its own Xtensa link script; the sawos lead has been told (chat).

**Gate for all three:** `tools/blade_lane.py`, `tools/freestanding_runner.py` and `tools/test_freestanding_runner.py`, `compiler/tests/run.py --only seed,fixture_whitespace,comments`, `tools/battery.sh citations`, under the suite lock.

**Item 2: Blade asks `sawc` which tools compile for a target. One funnel.**

`sawc` already knows, per target, the clang that compiles for it: the `clang PATH` line of the runtime record beside the binary (`sawc-runtime.txt` for the host, `sawc-runtime-TRIPLE.txt` for another target; `compiler/tools/build.py` writes them, and for an `xtensa-` triple that clang is Espressif's). Blade's C half uses `SOS_CLANG` or plain `clang`, which is wrong on this machine for every bare-metal target (Apple's clang has no RISC-V or Xtensa backend), and its linker default is wrong for Xtensa (`unsupported e_machine value: 94`).

- **A new query, `sawc tools [--target TRIPLE]`.** It prints the tools recorded for the target, one per line, as `NAME PATH`:
  - `clang PATH`: the record's clang. Always printed.
  - `ld.lld PATH`: printed only when a file named `ld.lld` exists in that clang's directory (Espressif ships one there, and so does a Homebrew LLVM). Nothing is searched for beyond that directory.
  - `objcopy PATH`: when the record has the line.
  Exit 0. With no `--target` it answers for the host. For a target with no record it prints the SAME refusal `sawc build --target T` prints for that case (read `driver_build`'s "has no clang configured" path and reuse its text through one function, don't copy the string) and exits 1. An unknown triple is `sawc: unknown target T`, as elsewhere.
  - Read the record through the functions `sawc build` uses (`driver_read_runtime`, `driver_read_target_runtime`, `driver_parse_manifest`); no second parser.
  - It is listed in `sawc --help` beside `sawc runtime`.
- **Blade** (`blade/src/sosimg.saw`, `sos_clang` and `sos_ld`, and their callers in `builder.saw`): the variable wins when set. Otherwise Blade runs the compiler command it already uses (`SAWC`, else `sawc`: read `builder.saw`'s funnel for it and go through it) with `tools --target TRIPLE` and takes the `clang` line, and for the linker the `ld.lld` line. When the query fails, prints no such line, or the compiler is too old to have the command, Blade falls back to today's defaults (`clang`, `ld.lld`), so nothing that builds today stops building. `sos_clang` and `sos_ld` take the target as a parameter; the query runs once per build, not once per native unit.
