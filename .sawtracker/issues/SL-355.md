## Description

# The park word is established before readiness is armed, and propagated by MERGE — never re-stored after a wake

Lead-authored fix brief for SL-353 (the lost-wake stall). Sweep evidence: SL-353's sweep-report comment (reproducer, ordering table, fixes A/B measured). PRIORITY HIGH: a hang in any multithreaded group whose tasks park on io or offloads — the battery's irdet lane is the in-tree victim (SL-350's battery stalled on it). RULINGS OWED from the user before dispatch, marked below.

## 0. The mechanism (obligation 4: a CLASS, probed)
ONE funnel, TWO stores, wrong order and wrong merge. The reactor token is the ROOT frame's `__wake` word (`coro_transform.py:8149-8154`). (1) Both io-park lowerings ARM readiness first (`_emit_blk_call` `:7900-7904`; `io_wait`/`io_wait_until` `:6983-6987`) and write the park value -1 second (`_suspend_to` → `:6742-6743`), so a concurrent poller can latch 0 (`reactor.saw:177-181`) in between and the leaf store erases it. (2) The nested `Pending` propagation COPIES `sub.__wake` → `self.__wake` (`:8140-8143`) once per frame in the chain, after the arm, re-storing a child's -1 over a latched 0 — the DOMINANT clobber, which is why reordering the leaf alone (fix A) is measured insufficient. The MT re-scan re-reads the word but never re-arms, and the kevent was `EV_ONESHOT`, so the loss is permanent. Reproduced on the offload path and the `std.net` path; sleep, channel, cancel and join parks are not exposed (the table says why per path).

## 1. The rules
**R1 — established once, before the arm.** The park value is written through the ROOT token BEFORE readiness is registered — in `__saw_exec_io_register` itself (the one arm funnel), so no lowering can arm first. Every readiness store is then strictly later than the park store.
**R2 — propagated by merge.** The nested `Pending` propagation never overwrites a root word that is not -1: a child's -1 is NOT re-stored; other wake reasons (deadline, cancel, wake-word values ≥ 0) propagate as today.
**R3 — never re-stored after.** `_suspend_to` at an io park writes nothing the register funnel has already written (the `write_wake=False` shape), so the ordering rule has exactly one writer per park.
**R4 — the funnel's docstring names its clients** (obligation 1): `_emit_blk_call`, the `io_wait`/`io_wait_until` lowering, the token-less sync path (`codegen/calls.py:593-596`, token = 0, exempt and says why), and the propagation arm. A battery-lane check (the `corodiscovery`/`corototality` pattern) fails on any io-park site that arms outside the funnel or stores the park word after it.
**R5 — RULING OWED (a): the wake word's memory model.** Today the word is a plain frame field read and written from several threads with no atomics (`taskgroup.saw:358-366` documents the choice for the latch read). Fix B as prototyped writes through a raw token unsynchronized and makes `__saw_exec_io_register` `unsafe`. Options: (i) keep the plain word and rely on R1-R3's ordering (measured 0/480 in scratch; a data race in the C++ sense remains); (ii) make the wake word an `Atomic<Int>` with the poller's latch a CAS(-1 → 0) and the propagation a CAS-guarded merge — the sound answer under design 186's doctrine, at the cost of atomics on every park/poll and a frame-layout change (bt-table/frame-layout instruments, `--emit-frame-layout` consumers). The lead recommends (ii) unless the user rules the ordering argument sufficient for v1.
**R6 — never hide errors (the secondary finding).** The arm discards `kevent`'s return at `reactor.saw:105/118/142/150` and `__saw_exec_io_register` returns `Void`; a failed arm becomes this bug's exact signature. The funnel reports a failed arm (a `Result`/status the executor turns into a panic naming the fd and the errno — a failed registration is a runtime invariant violation, not a recoverable condition), so the two failure modes are distinguishable forever after.
