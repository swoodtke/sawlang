## Description

A diagnostic wart turned up by SL-265 (design 271). The behaviour is correct and
deliberate; only the wording is wrong, and it is wrong in a way that teaches the
reader the opposite of the rule.

A direct `.copy()` on an automatic-Copy-tier receiver is refused:

```saw
struct Rec { text: String }        // design 159: automatic Copy tier

func main() {
    let a = Rec(text: "x")
    let b = a.copy()               // error
}
```

```
error: type `Rec` is not Copy; `.copy()` requires a trivially-copyable, Copy,
or ExplicitCopy type
```

`Rec` IS Copy — that is the whole of design 159, and `let b = a` one line up
compiles and retains. The refusal itself is right: `.copy()` is the
`ExplicitCopy` spelling, the silent tier needs no ceremony, and nothing at that
call site asked for a duplicate. But the message asserts a false fact about the
type, and the hint lists three categories one of which the receiver is in.

This is the "inconsistency" SL-265 was filed around: the reporter read the direct
refusal as evidence that the generic bound was wrong to admit the type, when the
bound is right (design 219: every Copy type satisfies `T: ExplicitCopy`) and the
defect was in the lowering. A message that said so would have pointed at the
lowering a lot sooner.

## Suggested wording

Say the tier and say why the spelling is refused rather than denying the tier —
something in the shape of: "`Rec` is on the Copy tier, so a copy is implicit:
write `let b = a`. `.copy()` is the spelling for the ExplicitCopy tier, where
the ceremony is what makes the duplicate visible."

Not fixed by design 271, which is a codegen change and deliberately touches no
diagnostic.
