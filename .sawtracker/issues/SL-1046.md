Found by the SL-1044 spec review (F8, lead probe). sawc names the entry module after its file's stem, so an entry file named like a dependency TAKES that dependency's module identity, and the dependency becomes unreachable:

- `dep/lib.saw`: `public func only_in_dep() -> Int { 7 }`.
- `app/wire.saw`: `import wire as w` and `print(w.only_in_dep())`, built with `--module-path wire=dep`.
- Result: `import.unknown-symbol`: "`only_in_dep` is not defined in `wire`". `import wire` resolved to the entry file itself. With a `read` in both files, `w.read` names the entry's private `read` (`visibility.private`).
- The same program saved as `app/main.saw` builds and prints `7`.

Probe: `.build/scratch/f8probe/` (sawc at main 0cab22184).

The spec ("Link symbols and linkage") gives the entry module the EMPTY module tag precisely so that "every real module path renders at least one character, so the empty tag is the one spelling no module can take, and a module literally named `root` stays a different module from the entry one". sawc's symbols (`saw wire.read(n: Int)`) carry the stem, so the same conflation would reach the linker if resolution let both through.

**Expected:** the entry module's identity is one no dependency can take. Sweep before fixing: an entry stem equal to a std leaf (`time.saw`, `data.saw`), to a Blade dependency, and to the package name of a `lib.saw` root; and whether `sawc test` or Blade's builds hit the same.
