## Description

**std's `Hasher` spreads differences in high bits badly; give `finish` a proper final mixing step.** USER DIRECTION (Nov 5): fix it.

**The weakness:** `Hasher` (`std/prelude.saw`) is FNV-1a: `write_int` xors then multiplies by the FNV prime, and `finish` folds the high half into the low. A multiply never carries a difference downward. So keys that differ only in high bits, or in the top bit, collide in the low bits a table indexes by, and probe in long runs. This is the same weakness the Air found in 4a2's image digest (SplitMix64 fixed that one).

**Found by:** SL-970's census. Debug-location keys with the line in bits 20–39 made the llvm stage superlinear: 3,200 / 6,400 / 12,800 / 25,600 keys took 77 / 331 / 1,335 / 4,265 ms. SL-970 unit 5 keys them around it in the compiler, but every user `Map`/`Set` of such keys has the same problem.

**The fix:** `finish` applies a full-avalanche finalizer (SplitMix64's or murmur3's fmix64) to the state. `write_int` may stay FNV or move to a per-word mix; measure both.

**Consequence:** every `Map`/`Set` iteration order changes. The spec says iteration order is unspecified (LANGUAGE_SPEC, "Iteration order is UNSPECIFIED"), so a program or test that depends on it is wrong. The census finds every place where that order reaches output: corpus and run-lane programs, and anything sawc itself emits (IR, dumps, diagnostics).
