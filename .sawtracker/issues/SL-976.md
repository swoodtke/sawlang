## Description

**std's `Hasher` spreads differences in high bits badly; give `finish` a proper final mixing step.** USER DIRECTION (Nov 5): fix it.

**The weakness:** `Hasher` (`std/prelude.saw`) is FNV-1a: `write_int` xors then multiplies by the FNV prime, and `finish` folds the high half into the low. A multiply never carries a difference downward. So keys that differ only in high bits, or in the top bit, collide in the low bits a table indexes by, and probe in long runs. This is the same weakness the Air found in 4a2's image digest (SplitMix64 fixed that one).

**Found by:** SL-970's census. Debug-location keys with the line in bits 20–39 made the llvm stage superlinear: 3,200 / 6,400 / 12,800 / 25,600 keys took 77 / 331 / 1,335 / 4,265 ms. SL-970 unit 5 keys them around it in the compiler, but every user `Map`/`Set` of such keys has the same problem.

**The fix:** `finish` applies a full-avalanche finalizer (SplitMix64's or murmur3's fmix64) to the state. `write_int` may stay FNV or move to a per-word mix; measure both.

**Consequence:** every `Map`/`Set` iteration order changes. The spec says iteration order is unspecified (LANGUAGE_SPEC, "Iteration order is UNSPECIFIED"), so a program or test that depends on it is wrong. The census finds every place where that order reaches output: corpus and run-lane programs, and anything sawc itself emits (IR, dumps, diagnostics).

**SL-976.p1: the Hasher mixes every bit, and nothing depends on hash order**

- **The hash** (`std/prelude.saw`):
  - `finish` is SplitMix64's finalizer (user ruling).
  - `write_int` folds each product's high half into its low half: `m = (state ^ n) &* PRIME; state = m ^ (m >> 32)`. That is the census's recommendation, approved by the lead.
  - LANGUAGE_SPEC's "Hashing" section and the doc comments say so.
  - Measured in unit 1: keys differing only in high bits (SL-970's debug-location shape) insert about 650x faster; random keys cost about +4 ns per insert; the two-word state collisions the census found are gone.
- **JSON** (user ruling): `write_object` writes keys in byte order, and `std/JSON.md` says so. The new pin `tests/corpus/json_value_object_key_order.saw` builds one object in four insertion orders, plus a parsed document and a nested one, and gets the same text each time.
- **Programs that printed iteration order** keep what they pin, with no hash order recorded:
  - `aggregate_map_keys` sorts.
  - `V72_std_visitors_lend` (both copies) counts drops.
  - `set_nocopy_key_error` sorts.
  - `json_map_keys` sorts its keys. Its `sync` `Serialize` can sort since SL-981.
- **Digest pins** compare each digest with a hasher fed the exact words by hand, so they pin the feed under any `finish`. Under the old hasher, all 57 feeds reproduce Stage 0's recorded digests. `hash_feed.mir` is re-recorded.
- **Stage 0 records:** regenerated by v0.18.0 on darwin and in the Linux VM (aarch64), for the five run-lane programs and the `string_hash` pair.
- **Nothing passes by chance:** the run lane and the corpusdiff gate give identical results unsalted and under two salted orderings.
- **corpusdiff:**
  - `V72` and `set_nocopy_key_error` are now judged by their own directives;
  - `json_value_object_key_order` is new;
  - all 2,676 programs hold.
- **Compiler output:** unchanged. No pass iterates a std Map or Set, and 2,687 inputs gave identical IR under both hashes (unit 1).
- **Gates:** `run.py --only seed,units,golden,subset,fixture_whitespace,std,programs`, corpusdiff and docverify passed.
