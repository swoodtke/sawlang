## Description

BRIEF (RULED Sep 20 2026, user; lead-written, lives in this issue rather than designs/; r2 folds codex's review, c1): `borrows` signatures name the lent reference and its mode — `borrows -> &T` / `-> &var T` (and the `?` twins), `&self` / `&var self` bounding it. QUEUED after design 275 U2 (SL-318.p6) lands and BEFORE U3 dispatches, because U3 writes the borrowing-struct spec text and its K rows against whatever spelling is current.

## 0. Why

Two things, one earned by design 275 U3 and one older.
(a) After U3, `borrows -> X` means two different things: design 141's "lends a PLACE of X" and U3's "returns a VALUE of borrowing-struct type X that carries a borrow". Same signature shape, disambiguated only by looking up whether X is declared `borrows struct` somewhere else — the reader-visibility doctrine's exact complaint. With `borrows -> &T` for a lend the signature says which: a `&T` result IS the place, a struct result is a value carrying one. And the rule unifies with the field rule U3 ruled: a reference type may appear in a RETURN position only under a `borrows` signature, and in a FIELD only under a `borrows struct` — one sentence, one check.
(b) Design 141 made every lend writable at the use site's discretion ("one `&self` declaration, the use site picks shared vs exclusive"). An accessor AUTHOR therefore cannot express a read-only lend at all. The user's ruling reverses the default: the DECLARATION states the maximum mode, the use site narrows within it.

## 1. The rules (RULED; R4/R6/R7 tightened per codex c1)

R1. RETURN TYPE = the WINDOW's MAXIMUM mode. `borrows -> &var T` may open shared or exclusive windows; `borrows -> &T` opens shared only, and a write through it (`g.at(4).weight += 1`, `v[i] = x` through a `&T` subscript accessor, `&var g.at(4)` as an argument) is a compile error naming the accessor and its declared mode, with a fixit naming `-> &var T`. Conditional lends: `-> &var T?` / `-> &T?`. The bare `borrows -> T` spelling on a lend-shaped body is an ERROR with a fixit naming `-> &T` — no silent acceptance of both spellings (no-degradation doctrine). `borrows -> S` where `S` is a `borrows struct` stays the U3 value-returning form (this brief does not build it; it only leaves the spelling free).
R2. RECEIVER MODE BOUNDS RETURN MODE. `-> &var T` REQUIRES `&var self`: an exclusive place cannot be projected from a shared receiver (design 106's no-upgrade rule one position over). `&var self borrows -> &T` is legal (an accessor that mutates its own bookkeeping but lends read-only). `&self borrows -> &var T` is the teaching error, fixit naming `&var self`.
R3. THE USE SITE STILL NARROWS the WINDOW. A read through a `&var T` lend opens a SHARED window; two shared windows on one root compose; a write opens the exclusive one. Unchanged from design 141 for every use site within the declared maximum.
R4. THE LENT VALUE's MODE and the RECEIVER's REQUIRED ACCESS are TWO facts (codex point 1). The window mode is R1/R3. The receiver access an accessor REQUIRES at a call is a property of its BODY: SHARED-ELIGIBLE if the shared specialization of the body (R6) type-checks as an ordinary `&self` body under the existing receiver rule (`typechecker/statements.py`'s "a `&var self` method / a write reached through a `&self` receiver" check — no mutation of `self` outside the lent place survives the fold); EXCLUSIVE-ONLY otherwise (a prologue counter, an epilogue update, a `self.x = …` beside the `lend`, a `&var self` method call on self — anything the fold does not remove). This is CHECKED AT EVERY CALL SITE, not only on `let` receivers: a shared use of a shared-eligible `&var self` accessor borrows the receiver SHARED (so it works on a `let` root and two such windows compose); a use of an exclusive-only accessor borrows the receiver EXCLUSIVELY even when the WINDOW it opens is read-only — so it is refused on a `let` root naming the mutating line, and TWO concurrent read-only windows through an exclusive-only accessor on one `var` root CONFLICT (two exclusive receiver borrows), exactly as two `&var self` calls would. Two read-only results never imply two compatible receiver borrows. The eligibility is RECORDED on the declaration as a DECLARED annotation field (design 126 contract, `astgraft` lane), computed once from the specialized body, so IMPORTED and GENERIC accessors (per instantiation, since the fold's outcome can depend on the instantiation) carry it to their callers — never re-derived by a syntactic "writes self" scan at the use site. Ordinary (non-`borrows`) `&var self` methods are UNCHANGED: on a `let` receiver they stay an error.
R5. ONE RULE FOR REFERENCE TYPES OUTSIDE PARAMETERS. `&T`/`&var T` is legal as a return type iff the function is `borrows` (it is the lend); as a struct field iff the struct is `borrows struct` (U3 builds that half; this brief adds the return half and writes the sentence once in the spec so U3 only adds its clause). Everywhere else a reference type in a non-parameter position keeps today's error.
R6. `#lend_var` IS LIFTED INTO `&var self` ACCESSORS (codex point 2). Today the constant is forbidden in a `&var self`-declared accessor because that spelling was exclusive-only at every use. Under R1-R4 the writable accessors — `Vector.[]`, `Data.[]` (the copy-on-write gate lives under `#lend_var`), every `&var self -> &var T` — move to that spelling and still compile as TWO specializations through the EXISTING design-179 machinery: the shared one folds `#lend_var = false` and REMOVES what it gated, the exclusive one folds `true`. R4's eligibility is computed on the SHARED specialization AFTER the fold, so an exclusive-only CoW branch (`if #lend_var { self._make_ready(...) }`) does not make ordinary reads exclusive: `let frozen = load(); print(frozen[0])` keeps working with no separation and no `var`. The rule "`#lend_var` is a compile error in a `&var self` accessor" is DELETED from the spec; the rule "outside a `borrows` body it is an error" stays. An accessor that never names it compiles once, as before. NO new syntactic scan: eligibility = "does the specialized shared body pass the ordinary permission rules".
R7. FORWARDED LENDS carry the OUTER window's mode (codex point 3). Today `lend other[i]` reaches the inner accessor EXCLUSIVELY whichever specialization runs, because `lend X` hands `X` over as `&var X` (spec: "a shared read of a nested copy-on-write buffer will copy"). Under R1-R3 the inner call is made with the OUTER window's mode: inside the SHARED specialization the inner accessor is invoked shared (its `&T` window, its shared specialization, no CoW separation), inside the EXCLUSIVE one exclusively. Two refusals fall out and are rows: an outer `-> &var T` accessor whose lend is backed by an inner `-> &T` accessor is an error at the outer `lend` (no upgrade — the inner cannot supply an exclusive place; fixit: declare the inner `-> &var T` or lend your own storage); an outer `-> &T` accessor forwarding through an inner `-> &var T` accessor never upgrades it (the inner is called shared, and the inner's R4 receiver requirement applies to the forwarded receiver: an exclusive-only inner accessor makes the outer exclusive-only too, propagated through the recorded eligibility). The spec sentence about the nested CoW copy is replaced by the new rule.

## 1. ONE DIVERGENCE FROM THE RULED BRIEF — the lead should rule

R6 says two things that cannot both hold, and I built the one that makes R7 true as written. **The split key is the DECLARED MODE, not the presence of `#lend_var`.**

R6: "make the specialization split key on 'the accessor names `#lend_var`' rather than on the receiver spelling" and, one sentence later, "An accessor that never names it compiles once, as before."
R7: "inside the SHARED specialization the inner accessor is invoked shared … inside the EXCLUSIVE one exclusively."

A forwarding accessor that never names `#lend_var` has no shared specialization for R7 to speak about, so under the literal key R7 is unimplementable for it — and worse, R4 then makes EVERY such accessor exclusive-only, because its single `&var` lend borrows `self.inner` exclusively and that is a mutation through the receiver like any other. `Outer.[]` in `lend_var_coro_and_forwarding.saw` is exactly that shape and would have stopped working on a `let` root.

What I built: a `borrows -> &var T` accessor compiles as two specializations (it is precisely the declaration a use site may open either way), a `borrows -> &T` one compiles once. `#lend_var` keeps its meaning unchanged — it NAMES the specialization being compiled — and the always-constant rule survives, re-keyed with the split: `#lend_var` in a `-> &T` accessor is always false and is the same error design 179 gave for the receiver spelling it used to key on (`errors/lend_var_in_shared_lend_accessor.saw`, the repurposed `lend_var_in_var_self_accessor.saw`).

Cost, measured: the shared copy of a `-> &var T` accessor is a second body checked and emitted. Nothing in the final binary for an accessor used one way only (unreferenced internal functions are DCE'd); the `bench` lane's checksums and timings are unchanged and the whole battery is green. If the lead prefers the literal key, R7's K129 cell 1 and the `lend_var_coro_and_forwarding` outcome flip back, and the report's OPEN moves there.

Two derived rules I wrote because the ruling's mechanism required them, both flagged:
- `#lend_var` in a `borrows -> &T` accessor is an error (the design-179 rule re-keyed off the receiver onto the mode, same reason: an always-constant gate reads as a live decision).
- R2 is checked after the receiver validation, so `&self ... borrows -> &var T` gets the mode error and a by-value `self` still gets the receiver error first.
