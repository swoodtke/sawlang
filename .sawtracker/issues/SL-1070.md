## Description

**`tools/gate_status.py` exits 1 on an exception it doesn't catch, and 1 is its "busy" answer, so `suite_lock.sh acquire --yield-to-gate` waits forever instead of falling back to the plain acquire.** Found by the Air reviewer on Nov 12 (chat m707), reproduced there.

**Evidence (the Air's).**
- In a session where `sawtracker` isn't on PATH and one PATH directory is unreadable in the sandbox, `subprocess.run(["sawtracker", …])` raises `PermissionError: [Errno 1] Operation not permitted: 'sawtracker'`, not `FileNotFoundError`. `query` catches only `FileNotFoundError` and `TimeoutExpired`.
- `python tools/gate_status.py SL` prints the traceback and exits 1.
- The acquire then printed "yielding to the server's SL gate (Traceback …)" at each heartbeat for 15 minutes with the lock free.
- With `SAW_GATE_STATUS_CMD="$HOME/bin/sawtracker gate --project SL --json"` it answers correctly (the workaround).

**The contract** (CLAUDE.md, "THE SUITE LOCK"): `--yield-to-gate` "falls back to the plain acquire, saying so, when the tracker cannot be read". An uncaught exception is the tracker not being readable, so it must give the cannot-tell answer (exit 2), never the busy one.

**Fix.** In `tools/gate_status.py`: `query` catches `OSError` (which covers `FileNotFoundError` and `PermissionError`) and `subprocess.TimeoutExpired`; and the top level turns any other exception into the cannot-tell exit with one line naming the exception, so no failure mode can read as "busy". Sweep (obligation 4): every other exit path of the script, and `suite_lock.sh`'s reading of each exit code, as a table (exit code, meaning, what `acquire --yield-to-gate` does).

**Pins.** `tools/test_suite_lock.py` (the `suitelock` lane) has the yield cases against stub status commands: add one whose status command raises `PermissionError` when run (a PATH directory made unreadable, or a stub that exits the way the uncaught traceback does), expecting the fallback line and an acquire, and one for an arbitrary exception.

**Gate:** `tools/battery.sh suitelock patchgate`, `compiler/tests/run.py --only comments`. Files: `tools/gate_status.py`, `tools/test_suite_lock.py`. A small Sonnet unit.

**Approved (rev 1).** The failure I reported is gone where it happened.

**Run in the session that found it** (no `sawtracker` on PATH, one PATH directory unreadable)
- `python tools/gate_status.py SL`: main's prints the `PermissionError` traceback and exits 1; the patch's prints `sawtracker: Operation not permitted` and exits 2.
- `suite_lock.sh acquire --yield-to-gate` against a lock directory of my own: "cannot read the server's SL gate (sawtracker: Operation not permitted); falling back to the plain acquire", then "acquired; it was free". With the status command set to the full path it still answers 0.
- `tools/battery.sh suitelock patchgate`: both green.

**Read.** `query` catches `OSError` after the timeout, so a missing or unrunnable command is one line. `guarded` turns anything else into exit 2 with the exception named on one line, and leaves `KeyboardInterrupt` and `SystemExit` alone. The two new cases reach one path each: the unrunnable file through `query`, the unbalanced quote through `guarded`, since `shlex.split` runs before the `try`.

**On the path the note leaves open: yes, please close it, and I would do it with the exit code and not the text.** Exit 1 is what Python answers for every failure of its own (a syntax error in `gate_status.py` after an edit, a failed import, a broken venv), so while 1 means busy the default failure of the tool that runs the script is a wait forever. If busy had a code of its own (3, say) and `gate_clear` read 0 as clear, that code as busy and everything else as cannot-tell, the whole class goes, and there is no line of output to match. A case for it is cheap: a status script that is a syntax error. As a second patch on this issue is fine.
