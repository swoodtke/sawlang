## Description

**`blade build` answers "up to date" after a change to several things the build reads: a source in a subdirectory of `src`, a native C or assembly unit, a dependency's manifest, the compiler, the tool variables.** Found by SL-1098's agent (Nov 13) while adding the linker script to the freshness hash (which SL-1098 fixes; before it, editing the script also left the old image in place).

**The mechanism.** `Builder.build_hash` (`blade/src/builder.saw`) hashes `Saw.toml`, `Saw.lock`, a constant marker (`sawc-1`) and, through `append_dir_saw`, the `*.saw` files DIRECTLY inside `src` and each dependency's `src`. `is_up_to_date` compares that with the stamp. Anything the build reads that is not in the hash can change without a rebuild.

**Not covered** (the agent's list; the first is read from the code and SL-1098's `--module-path` walk, which had to recurse, and none is yet shown by a run):
- `*.saw` files below the top level of `src`, the package's or a dependency's. A package with `src/net/tcp.saw` that edits it gets `Finished ... (up to date)` and the old binary.
- the native C and assembly units an image's `native` key names;
- a dependency's `Saw.toml`;
- the compiler: a new sawc leaves every package "up to date" (the marker is a constant);
- `SOS_CLANG`, `SOS_LD` and `SAWC`, which choose the tools.

**To do first.** Show each by a run (build, change the one thing, build again, quote the `Finished` line), starting with the nested source, which is the one an ordinary package hits. Then name the rule: the hash covers every file the build reads and the identity of every tool it runs, gathered in ONE place the builder's readers go through (obligation 1), so a new input cannot be read without being hashed.

**Notes for the design.** sawc has its own caches keyed on content, so a rebuild that changes nothing is cheap; Blade's stamp only decides whether to ask. The compiler's identity can be `sawc --version` plus the binary's digest (as the front cache's key does). `Directory.exists` answers true for a regular file (SL-1094), so a tree walk uses `Directory.list` as the directory test until std has `is_dir`.

**Priority.** A silent stale build is the kind of error the doctrine says never to hide; the nested-source case is the one to confirm first.

**Implementation detail for unit U2 (lead, Nov 14): `sawc --build-id`, and Blade hashing it.** Ruled by the project owner (comment above). U1 is on main: Blade's up-to-date hash holds the first line of `<compiler> --version`, so a rebuilt development compiler or an edited `std/` with an unchanged version still reads as up to date. This unit closes that.

**1. `sawc --build-id` (the driver, `compiler/driver/src/main.saw`).**
- Prints ONE line on standard output, 64 hexadecimal digits, and exits 0: a SHA-256 over everything of the toolchain that decides what `sawc build` produces from a given source, and nothing else:
  - the digest of the running binary (`Env.executable_path()`, read whole), as `driver_front_key` already computes for the front cache;
  - the std root it would compile against (the default beside the checkout or the binary, or `--std-root DIR` when given: the flag is accepted after `--build-id`): every file `driver_front_std_files` lists, by relative path and content, in a fixed order. NOT the root's absolute path: two checkouts with the same bytes have the same identity;
  - each runtime record beside the binary (`sawc-runtime-<triple>.txt`, the files that say which clang, linker and runtime objects a target uses): by name and content, and the content of each runtime object a record names, so a rebuilt runtime changes the identity;
  - the values of the environment variables the driver reads that change the output of a build: `SAWC_CODEGEN_UNITS` and `SAWC_LTO` (each as `NAME=value` or `NAME unset`). The cache switches (`SAWC_CACHE_DIR`, `SAWC_OBJECT_CACHE`, `SAWC_FRONT_CACHE`, `SAWC_CACHE_ENTRIES`, `SAWC_FRONT_VERIFY`) are not part of it. **Sweep to do first:** every environment read in the driver (`driver_environment`, `Env.get`), each classified "changes what a build produces" or not, in a table; a variable the lead did not list that changes the output joins the identity, and the report says so.
  - a leading format line (`sawc-build-id 1`), so the recipe can change without two recipes colliding.
- A part that cannot be read (no executable path, an unreadable std file) is an error on standard error and exit 1; nothing is printed on standard output.
- It is one funnel, `driver_build_id`, whose docstring lists what it covers and its ENTRY POINTS; where it shares a computation with `driver_front_key` (the binary's digest, the std file list), both call one function, never two copies.
- `sawc --help`, LANGUAGE_SPEC.md's command-line list and CLAUDE.md's "Compiler usage (dev)" block each gain the line: `sawc --build-id [--std-root DIR]`: an identity of the compiler, the std it compiles against and its runtime records, for a build tool's freshness check.
- Cost: say what one call takes on this machine (it reads the binary and std; `sawc build` already pays the same for its front key). If it is over 100 ms, STOP and report the number: Blade calls it once per build.

**2. Blade (`blade/src/builder.saw`).**
- `compiler_identity()`, beside `compiler_version()`: runs `<compiler_command()> --build-id` once per build. Exit 0 with one non-empty line: that line is the identity. A usage refusal (the driver's usage exit status, which an older `sawc` gives for a flag it does not know): the identity is the version line, as today, so an older compiler keeps working. Any other failure: the build is never up to date (the hash is "", as for an unreadable version).
- `build_hash` takes the identity where it takes the version today; its docstring's line for the compiler says which it is. The marker becomes `blade-hash-3;`.
- The help text, README and the spec's paragraph, which say "a compiler whose version is unchanged ... is not tracked", say instead that the compiler, its std and its runtime are tracked through `sawc --build-id` when the compiler has it. The header-of-a-native-unit limit stays.

**Pins.**
- The run lane (`compiler/tests/run/run_lane.py`, a custom check beside `check_scratch_files`): `sawc --build-id` prints one line of 64 hexadecimal digits and exits 0; twice in a row the same; with `--std-root` naming a copy of `std/` the same as without, and with one byte of one std file in the copy changed, another; with `SAWC_LTO` set to another value, another; with `SAWC_CACHE_DIR` set to another directory, the same.
