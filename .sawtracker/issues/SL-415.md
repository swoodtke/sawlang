## Description

**User ruling (relayed by the lead, Sep 26):**
- A named function becomes an ordinary function value. It lands after self-hosting, and is not in the bootstrap subset.
- Unbound method references stay open.
- Bound method values are out.

## 1. A named function as a function value (ruled in, post-self-hosting)
`v.map(doubled)` and `let f: (Int) -> Int = doubled`: a function's name used where a function type is expected.

**The precedent** is `FuncPointer<F>` Form 2 (LANGUAGE_SPEC, "Function pointers"). A non-generic `sync` named function already converts to a `FuncPointer`, and the expected type picks among its overloads. This extends the same idea to ordinary function types, `sync` or not.

**Sound and cheap.** A named function captures nothing, so it needs no environment, allocates nothing and carries no borrow. That also puts it outside `--no-hidden-alloc`'s concerns.

**An expected type is required.** A parameter, an annotation, a field initializer or a `return` supplies it. It selects among overloads and infers generic arguments. With no expected type it is an error, with the fixit `{ f($0) }` ("explicit where inference would guess").

**The effects must fit.** The function's `unsafe`/`sync` effects must fit the target function type; a `sync` function fits a type that may suspend. A generic function needs its type arguments to be determined by the expected type.

**The spec's wording changes.** "Functions are not first-class values" becomes "named functions convert to function values where a function type is expected; methods are not values".

**Not needed before then.** `{ doubled($0) }` works today and compiles to the same thing.

## 2. An unbound method as a function (open)
`Point.length` as `(&Point) -> Float`: the receiver's mode becomes the first parameter's type. `consumes` and `borrows` methods cannot be expressed, because a function type may not be `consumes`. Revisit when real code asks for it.

## 3. A bound method as a value (out)
`obj.method` without a call would have to carry the receiver. By reference, it would store a reference in a value, which Saw forbids because it has no lifetimes. By copy or move, it would silently copy or consume `obj`. A closure (`{ obj.method($0) }`) keeps the capture visible. The spec should say this is excluded by design.

## Work, after self-hosting
- **The spec:** the rewording above, plus a "Named functions as values" subsection that cites FuncPointer Form 2.
- **GRAMMAR.md:** likely nothing, because a bare name is already an expression; check.
- **Resolution and typecheck:** a name that resolves to a function, in an expected-function-type position, converts to a function value. That conversion is one funnel with named positions (obligation 1).
- **Conformance and tests:**
  - overload selection by the expected type;
  - generic inference;
  - the no-expected-type error;
  - an effect mismatch;
  - a method name refused as a value.
