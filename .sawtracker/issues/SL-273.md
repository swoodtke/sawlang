## Description

Found while writing design 272 unit 2's tests (Sep 12 2026). PRE-EXISTING and unrelated to that branch — verified by reproducing at 7a4d01cb, the commit the branch started from, with the branch's own sawc/ checked out of the way.

SYMPTOM: a `match` whose scrutinee is a SUSPENDING call, written INSIDE A LOOP, loses its arm's payload binding. The binding is undefined by the time codegen reads it, and the compiler exits with an internal error rather than a diagnostic:

  error: internal compiler error at probe.saw:13:33 (Identifier): Undefined variable: e

MINIMAL REPRO (compiles clean if the `while` is removed):

  import std.net.{TcpStream}

  func main() {
      let (a, b) = TcpStream.pair()
      let _ = move b
      var i = 0
      while i < 4 {
          match a.write("payload") {
              case Ok(_) -> {},
              case Err(e) -> {
                  print("err {}", e)
                  break
              }
          }
          i = i + 1
      }
      let _ = move a
  }

THE MATRIX (obligation 4 — I probed the cells rather than assuming the shape I hit was the shape of the bug). Each row is a compile:

  | scrutinee      | in a loop | use of the binding | result |
  |----------------|-----------|--------------------|--------|
  | suspending     | no        | direct in arm body | OK     |
  | suspending     | no        | inside a nested if | OK     |
  | suspending     | YES       | direct in arm body | ICE    |
  | suspending     | YES       | inside a nested if | ICE    |
  | NON-suspending | YES       | inside a nested if | OK     |

So the trigger is the PAIR (suspending scrutinee, enclosing loop). Nesting inside the arm is irrelevant — I first hit it through a nested `if` and that was a red herring. A non-suspending scrutinee in the same loop is fine, and the same suspending scrutinee outside a loop is fine.

MECHANISM (named, not guessed at from the symptom): a suspending scrutinee is ANF-hoisted and the match is CFG-split by the coroutine transform, so the arm bodies become their own blocks reached from a resume state. The arm's payload binding is registered in the scope built for the straight-line path; the LOOP's back-edge re-entry rebuilds the block scope without it. This is the same family as design 218 unit 2's scope-end migration and design 247's scrutinee-temp migration — a binding whose scope is built once but whose block is entered from more than one predecessor.

SIBLINGS THE MECHANISM REACHES, worth probing before a fix is written: `for` loops as well as `while`; a `while let` whose body holds such a match; a match arm binding read after a `continue` rather than a `break`; the same shape with the suspending call one level down (a suspending helper rather than a std method); and `if let` / `guard let` payload bindings in the same loop position, which are built by the same machinery.

IMPACT: this is a plausible shape in ordinary server code — "loop, do a suspending io call, match, report the error and break" is the natural spelling of a retry or drain loop, and it is what I was writing when I hit it. The workaround is to hoist the call out of the match (`let r = a.write(...)` then `match r`), which costs nothing but is not discoverable from the error message. An internal compiler error is also the wrong failure mode regardless of the fix: whatever the outcome, this program should either compile or be refused with an anchored diagnostic (the fuzz oracle's rule).

NOT FIXED on the design-272 branch, per the no-workarounds rule: I have filed it rather than coding around it, and design 272 unit 2's test that hit it is written in the hoisted form with a comment pointing here.

CORRECTION to the description above — the original characterization was WRONG and would have sent a fixer to the wrong place. Re-probed Sep 12 after the first stated workaround (hoisting the call out of the match) failed to help, which is what exposed the error.

THE TRIGGER IS NOT "the scrutinee is a suspending call". It is:

  a match arm PAYLOAD BINDING, inside a loop, where a SUSPENSION PRECEDES the
  match in the same loop iteration.

The scrutinee itself need not suspend, and need not be a call at all. This is broader than first filed and correspondingly more likely to be met in ordinary code.

THE CORRECTED MATRIX. Each row is a compile; the suspension is `a.write("x")` on a TcpStream, the binding is a match arm payload.

  | suspension in the loop | position vs the match | scrutinee     | result |
  |------------------------|-----------------------|---------------|--------|
  | none                   | -                     | non-suspending| OK     |
  | none (match outside a loop) | -                | suspending    | OK     |
  | yes                    | BEFORE the match      | suspending    | ICE    |
  | yes                    | BEFORE the match      | NON-suspending| ICE    |
  | yes                    | AFTER the match       | non-suspending| OK     |

And the sibling I predicted does NOT fall: an `if let` payload binding in the same position (suspension before it, inside the loop) compiles clean. That is a real discriminator and the most useful fact here — whatever registers an OPTIONAL binding's scope survives the resume-state split, and whatever registers a MATCH ARM binding's scope does not. The fix should probably make the second look like the first.

REVISED MECHANISM: a suspension splits the loop body into resume states. The match's arm blocks are then entered from a RESUME entry rather than from the straight-line predecessor the scope was built against, and the arm's payload binding is not carried onto that path. A suspension AFTER the match leaves the match wholly inside one state, which is why that row passes.

MINIMAL REPRO (the scrutinee is an ordinary non-suspending call — that is the point):

  import std.net.{TcpStream}

  func attempt(n: Int) -> Result<Int, String> {
      if n > 1 { return "nope" }
      return n
  }

  func main() {
      let (a, b) = TcpStream.pair()
      let _ = move b
      var i = 0
      while i < 4 {
          let _ = a.write("x")        // the suspension, NOT the scrutinee
          match attempt(i) {
              case Ok(_) -> {},
              case Err(e) -> {
                  print("err {}", e)
                  break
              }
          }
          i = i + 1
      }
      let _ = move a
  }

THE WORKAROUND STATED EARLIER DOES NOT WORK. Hoisting the call into a local before the match changes nothing, because the suspension is still in the loop ahead of the match. What does work is moving the match into a helper function that contains no loop. The XFAIL pin `examples/errors/match_on_suspending_call_in_a_loop.saw` carries the corrected minimal repro.

STILL OPEN from the first filing, and still worth probing when this is fixed: `for` loops as well as `while`; `while let`; a binding read after `continue` rather than `break`; and nested loops where only the outer one suspends.

FIXED on the coro-soundness batch branch (worktree-agent-a99290b0bdfc9988e), together with SL-278 — they are two faces of one mechanism, as c2 said.

ROOT CAUSE. Not "a suspension precedes the match", and not the scrutinee either: a container's SPLIT decision and its FRAME-RESIDENCY census asked different questions. `_lower_stmt` split an `if`/`match`/`try`-`catch` when it SPANS a suspension OR carries a `break`/`continue` for an enclosing suspending loop (design 96 DF6's clause, computed locally as `needs_ctrl_split`), while `_collect_frame_locals` granted fields on the first clause alone. A split relocates arm bodies into their own resume states, and a binding a container's HEADER introduces — a match arm payload, a design-63 scrutinee pattern, a try/catch's `error` — exists ONLY in the dispatch, so on every clause-2 split it reached the relocated body through a field it had never been given. Hence `Undefined variable: e` on a correct program.

c1's discriminator was exactly right and led straight to it: `if let`/`guard let` never fell because ONE stamp, `_coro_split`, is both their split decision and their residency answer. Only a top-down walk knows WHICH loop owns a jump, so `_lower_stmt` could not be the authority for clause 2; it is decided in `_mark_ob_block` now and stamped on the node, and `_FrameBuilder._is_split` is the one authority the three consumers read (`_lower_stmt`, `_collect_frame_locals`, `_collect_calls`), with its entry points named in its docstring.

A plain `let` in a relocated block was never affected — it is DECLARED where it stands, whichever state that turns out to be. That is why the bug looked like it was about match specifically.

THE SWEEP (33 sync/driven twin pairs, each compiled and run, the sync half the oracle). The mechanism reaches far past the two filed faces. Failing before, passing now: `while`+break, `while`+continue, conditionless `while`+break, `for`+break, `for`+continue, `while let`+break, `while let`+continue, a suspension AFTER the match, a SUSPENDING scrutinee, an inline `sleep` vs a suspending helper, nested loops where only the outer suspends (design 127's backedge charge makes the inner one suspend too), a break targeting the outer loop past an inner one, a nested match breaking from within, a guarded arm, a catch-all pattern binding the scrutinee, a tuple pattern, a bare arm expression with a binding, two payload bindings in one arm, a generic enum's payload, and NoCopy payload drop ordering under both break and continue.

Two rows correct the issue's own matrix. "Suspension BEFORE the match" with NO early exit in the arm PASSED all along — the early exit is the discriminator, not the suspension's position. And "suspension AFTER the match" FAILS once the arm carries a break, where c1 recorded it as OK. The suspending-scrutinee row is the sharpest: the scrutinee is ANF-hoisted out of the match before the transform looks at it, so the match no longer spans anything and the census had nothing to answer — which is why the first filing's blame landed there and why hoisting it by hand did not help.

A SIBLING CONTAINER neither issue named: a `try { } catch { }` carrying a `break` lost its `error` binding the same way (`struct __Frame_driven has no field error`). Same fix, same authority.

TWO FURTHER GUARD FACES, independent of the clause, found by the same sweep:
  * a guard on ANY arm routes the match through `_check_match_general`, which stamps `matched_scrutinee_type` and leaves `matched_enum_type` unset — so `_match_binding_types` answered nothing and EVERY arm lost its payload, guarded or not, on a plain spanning match with no `break` anywhere. `_scrutinee_binding_types` resolves enum patterns now, which makes the census pair exhaustive.
  * a guard runs during DISPATCH and may read ANY name in scope, not only the arm's own bindings, and was carried through UNREWRITTEN. `case Value(n) if i == 1` died with `Undefined variable: i` — `i` being the loop counter, long since a frame field. `_rewrite_guard` rewrites it with exactly the arm's bindings masked.

ONE SHAPE REFUSED RATHER THAN FIXED, filed as SL-283: a guarded arm beside a MOVE-ONLY payload binding double-frees (the general lowering extracts a candidate arm's payload to run its guard, which on an owning payload is a transfer, so a failed guard consumes the value the next arm binds). That is the lowering not sequencing extraction against selection, not this mechanism, and the transform is handed arms already lowered. `_check_guarded_owning_payload` gives it a clean anchored diagnostic so the branch ships no miscompile; the Copy tiers are untouched and keep working. Note this shape could not COMPILE before — it was masked by the `matched_enum_type` gap above — so it is newly reachable, not newly broken.

XFAIL/LEDGERS. `examples/errors/match_on_suspending_call_in_a_loop.saw` loses its XFAIL marker and stays as this issue's regression test, name unchanged. Neither `tools/sawfuzz_known.txt` nor `tools/corodiff_known.txt` carried an entry for SL-273 or SL-278.
