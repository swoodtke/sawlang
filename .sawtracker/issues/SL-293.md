## Description

Hit while building SL-269's position matrix (Sep 14). PRE-EXISTING and unrelated to that fix — verified byte-identical against the pre-SL-269 compiler, so it is not a regression from it.

A closure literal written at a slot whose type is an OPTIONAL-wrapped function type does not take the slot's payload type. The `escaping` bit arrives (design 269's `_stamp_escaping_roles` recurses through an `Optional`), `sync` does not, and no auto-wrap into the optional happens — so a legitimate program is refused with a diagnostic naming two types that differ only in the word the author never had a chance to write.

## Repro A — a return slot

```saw
func in_optional_slot() -> (() sync -> Int)? {
    let a = 43
    { [a] in a }
}
```

```
error: function `in_optional_slot` should return `(() sync escaping -> Int)?`
       but returns `() escaping -> Int`
```

Two things went wrong at once: the payload's `sync` did not reach the literal, and the `T -> T?` auto-wrap that every other value position gets did not fire.

## Repro B — a call argument

```saw
func stash_opt(into: &var Vector<() sync -> Int>, f: (() sync -> Int)?) {
    if let g = f { try! into.push(g) }
}

// at the call site:
stash_opt(&var v, { [a] in a })
```

```
error: argument `f` expects `(() sync escaping -> Int)?` but got `() -> Int`
```

Same shape at the argument boundary. Note the argument case loses BOTH `sync` and `escaping`, which is consistent with the expected type never being peeled at all.

## Repro C — the payload binding is not callable

```saw
let o: (() sync -> Int)? = ...
let oc = o!
print(oc())          // error: undefined function `oc`
```

A closure read out of an optional payload and bound to a local cannot then be called. The same value bound directly from a non-optional source calls fine, so this is the optional layer again rather than anything about the binding.

## Mechanism (named, not inferred)

`_check_closure` takes its `expected_type` and asks `expected_type.kind == TypeKind.FUNCTION` before reading anything off it — `target_escaping` at `typechecker/expressions.py:13335-13337` is the visible instance, and the same assumption governs which parameter and return types are pushed into the literal. An `Optional` whose payload is a function answers that test False, so the literal is checked against nothing and infers a bare `() -> Int`. Every other expected-type consumer in the checker peels optional layers for the auto-wrap (design 176's "a bare value written into a two-layer slot lands intact at whatever depth the slot names"); the closure path does not.

## Why it is filed rather than fixed

Out of scope for SL-269, which is an escape-CLASSIFICATION fix in the same function — closing this one means peeling the expected type before `_check_closure` reads it, which touches the closure's parameter-type inference, its return-type inference and the auto-wrap insertion together. Worth a look at whether the same blind spot reaches a `Result`-wrapped function slot (untested).

No soundness consequence: all three faces are clean compile-time refusals. What they cost is that `Vector<(() sync -> Int)?>`, and an optional callback parameter generally, are effectively unwritable with a closure literal — the workaround is a named function or a wrapper struct.

## Also worth a ruling while someone is here

An `escaping` written inside an optional parameter — `f: (() sync escaping -> Int)?` — is refused as "redundant `escaping` — closure types outside parameter position are always escaping", because `_stamp_escaping_roles` recurses into an `Optional` with `is_param=False`. That is defensible, but it means the author of an optional callback parameter cannot write the word at all while the author of a plain one must. Whatever fixes the above should say which spelling is correct.
