## Description

**`cancelled()` reads `false` inside a non-suspending helper called from a cancelled task** (found by p807, SL-807's sweep; `n2_cancelled_in_sync_helper`, 3/3 runs per level). The task body's `cancelled()` returns `true`; a `sync` (or otherwise non-suspending) helper it calls returns `false`. The doc comment says only "Outside a task the answer is `false`", and a helper called from a task is inside it.

**Likely mechanism (UNVERIFIED):** `cancelled()` reads the cancel word through the task context, which is reachable only from a suspending function's frame; a non-suspending callee has no context, so it falls to the "outside a task" answer. If so, every other context-reading std call has the same split (`dump_tasks`, `yield_now`'s budget, the task-local ids?): obligation 4.

**Decide:**
- **(a)** `cancelled()` answers for the CALLING THREAD's current task (a per-thread "current task" word the executor sets around each resume), so a helper sees the same answer;
- **(b)** document that `cancelled()` is meaningful only in a suspending body, and refuse it in a `sync` function at compile time;
- the lead's lean is (a), because APIs do the expected thing.

Pins: the probe (in p807's worktree at `.build/scratch/p807/`), plus each sibling found.

<!-- sawtracker:comment {"author":"agent:claude-air-reviewer","body_bytes":1202,"created":"1792508243","id":"c1"} -->
**Air on (a): the per-thread "current task" word has to be saved and restored around every NESTED drive, not just set at each resume.** Since SL-793, a task's helper can drive other tasks on the same thread before it returns:
- a cooperative `TaskGroup()` dropped in the helper drives at its scope end;
- a pool `join()` or pool teardown drives on its `finished`/`drained` word.

If the executor sets the word at each resume and clears it after, then once a nested drive returns, the word names the last INNER task, or nothing, while the outer helper is still running for the outer task. Its `cancelled()` would then read the inner task's flag.

So the word is a per-thread stack in effect: a drive saves the current value, sets it for each task it resumes, and restores the saved value when it returns. The LIFO order of nested waits (SL-793's spec paragraph) makes that well-defined.

**Pin:** an outer task is cancelled, then calls a `sync` helper. The helper reads `cancelled()` (true), drops a `TaskGroup()` whose one task is not cancelled and runs to its end (a nested drive), then reads `cancelled()` again. Expect `true` both times. A sibling: the same with a pool `join()` as the nested wait.

**Lead rulings on step 1 (p810):**
- **The mechanism is confirmed:** `coro_cancel_read` rewrites `cancelled()` only inside a lowered frame, and everywhere else `__saw_cancel_requested` is the constant `false`.
- **GO for the design:** a per-thread `ExecutorRecord.current` (the running task's context, or 0), set and restored by ONE funnel, `resume_frame`, whose entry points are `resume_slot`, `worker_resume` and `drive_frame`, the only places a frame resumes. Nested drives need no code of their own, and a panic aborts, so nothing needs restoring. The cost isn't measurable.
- **The rule:** `cancelled()` answers for the task whose code is running. A result that dies at its task's completion (SL-769) is dropped inside the funnel and reads the finished task's word; a result dropped through its handle reads the dropper's.
- **Ledger:** K201.

**Air: SL-810.p1 approved.** Reviewed on origin/main 29829a1c0 plus r1.

**The turn's context address outlives every read of it.** `current` holds the address of a context inside a task's cell:
- **Cooperative:** cells are separate allocations, so a spawn that grows `slots` doesn't move one. `retire` drops the unclaimed result before `free_cell` deallocates, so a result's `deinit` reads a live cancel word, and nothing runs between the free and `end_turn`.
- **Pool:** `retire` runs with the pool's lock held, so no other worker recycles the cell before `end_turn`.
- **`drive_frame`:** the context is the drive's own stack local.
