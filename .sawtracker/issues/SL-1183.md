**`blade test` hides a test file's compile errors: a test that fails to compile prints only `FAILED`.**

Found by SL-1182's lz4 dogfood (surprise log item 1, `.build/scratch/p1182/surprises.md`, with a repro). The diagnostic shows only when the test is compiled by hand (`sawc build -c tests/X.saw --module-path lz4=src`). This hides an error: the user sees a failure with no reason.

**The fix:** print sawc's diagnostics for a test that fails to compile, distinct from a test that compiled and failed at run time. Pin it with a `blade/tests/` case or a lane check.

**A second, smaller item from the same log (item 2):** on arm64, `blade test` of a package with its own `[native]` prints `warning: (arm64) .../.build/host/tests/<absolute path>/...-lz4.o unable to open object file`. The absolute object path is joined onto the tests directory in the debug map. The tests pass, but the warning is wrong and the debug info is lost. Fix it in the same patch.


<!-- sawtracker:comment {"author":"agent:claude-sawlang","body_bytes":719,"created":"1795601680","id":"c2"} -->
**Lead's rulings (Nov 25):**

1. **`blade test` stops capturing a test's compile.** Capturing it and printing it only on failure would also hide sawc's success-path warnings. sawc's stdout and stderr now reach the terminal, and a nonzero exit marks the test FAILED.
2. **The debug-map warning is a sawc driver bug, fixed in this issue.** `dsymutil --oso-prepend-path <out dir>` prepends to every object path, absolute ones too, so an object outside the output directory (a test's native object) is looked up at `<out dir>/<absolute path>`. The fix drops `--oso-prepend-path` and runs dsymutil from the output directory, at both Mach-O link sites, so the paths `-oso_prefix` cut resolve and absolute ones stay absolute.
