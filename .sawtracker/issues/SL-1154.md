## Description

**Blade: a package opts in to `--no-hidden-alloc`.** Asked by the sawos lead (chat m1251, Nov 17): a freestanding process that must never allocate should get a compile error instead of a slow leak; the kernel builds with `--no-hidden-alloc` through sawos's own builder, but process packages build through `blade build` and cannot opt in.

**Lead's direction: a specific key, not a generic per-package sawc-flags key.** A named key is visible to a reader of the manifest, is checked by Blade (an unknown or misspelled flag string would pass through a generic key until sawc refused it, or silently change codegen), and keeps the manifest a description of the package rather than a command line.

**To settle in the detail (with evidence):**
- Where the key lives: `--no-hidden-alloc` applies to one sawc invocation, and Blade compiles an image's modules (dependencies included) in one invocation through `--module-path`, so the setting is the ROOT package's (the image's or binary's), not a dependency's: likely `[package] no-hidden-alloc = true` read only from the root manifest, or the `[sos]` table for images. Check how `blade build` invokes sawc for a hosted binary and for an image, and what a dependency declaring it should do (ignored with a note, or refused).
- It enters Blade's freshness hash (SL-1102: the flags of a build are part of its identity).
- A test: a package with the key whose code interpolates a string is refused with sawc's `--no-hidden-alloc` diagnostic; without the key it builds.
- `blade/README.md` documents the key.

Related: SL-1102 (the build identity), design 135 (`--no-hidden-alloc`).

**Lead's note with p1 (Nov 17).** Evidence: `.build/scratch/p1154/` in the lead's checkout.
- **The key:** `no-hidden-alloc = true` in `[package]` (a boolean; absent is false; another type is Blade's wrong-type manifest error naming the key and position). Blade passes `--no-hidden-alloc` to every sawc compile of a build whose ROOT package declares it: `blade build` and `blade run` (one sawc invocation in `Builder.build`), an `[sos]` image build (`build_sos_image`), each `blade test` program (`Tester.dep_flags`); queries (`--version`, `--build-id`, `tools`) get nothing. The flag covers the whole compile, so a keyed root's dependencies are compiled under it; a dependency's key does not reach a keyless root. `blade/README.md` "Refusing hidden allocations" says so.
- **Freshness:** a `no-hidden-alloc=<bool>` line in `build_hash`, and the hash marker moves `blade-hash-3;` to `blade-hash-4;` (the layout changed): every package rebuilds once after this lands.
- **Tests:** `blade/tests/manifest_no_hidden_alloc_key.saw` (true, false, absent, a string refused), red against main (no such accessor); the lane check `check_blade_no_hidden_alloc` in `tools/blade_lane.py`: a keyed package's build refused with `alloc.hidden`, its interpolating test program failing under `blade test`, the same package building with no key and with `false`, a key flip rebuilding both ways, a string refused, a dependency's key not reaching a keyless root, a keyed root making a dependency's interpolation an error. Red against main's Blade at its first row ("blade build exited 0").
- **Not exercised:** an `[sos]` image build with the key (the flag is added at that site).
- **Found, filed apart:** `blade test` discards sawc's stdout, where sawc writes its diagnostics, so a refused test compile shows only `test X ... FAILED` (the lane's row asserts the failure, not the message).
