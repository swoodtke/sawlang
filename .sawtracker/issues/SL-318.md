#### U3 borrow-lifetime contract (RULED Sep 20 — the borrowing-struct model; codex review requested on SL-318)

The contract codex asked for (SL-318.p1 review point 4), written against
the compiler as it is after U1; every claim names the mechanism it rests
on, and the U3 agent turns each into a test, never a re-derivation. Five
parts: the MODEL, its EXTENT (codex i), the referent's ADDRESS STABILITY
(codex ii), the EXTERNAL-STORAGE case (codex iii), the fences.

**0. The model (RULED): the iterator is a BORROWING STRUCT — a type that
holds a lent place — and the `for` statement is its window.** Two
models were weighed and one refused. A HANDLE that carries a borrow past
the call that made it (design 201's `TaskCaptureBorrow` extent,
generalized to any value) is a lifetime in disguise: design 201 gets
away with it because a task handle is fenced on every side (written
fate, `join` releases, never stored), and a general iterator handle
would owe that fence at every position a value can go — obligation 1's
position-quantified rule. REFUSED (user, Sep 20): `let it = v.iter()`
is against the borrows rules; the pattern is restricted to the `for`
head, which is the one place the extent is already lexical. What
replaces it is the borrow carried BY THE TYPE, four spellings, each
already a Saw word or a design-141 word one position over:

```saw
public borrows struct VectorIterator<T> {      // (1) the type declares its nature
    private vector: &Vector<T>                  // (2) the field is a plain reference
    private index: Int
}
extension Vector<T: Copy> {
    public func iter(&self) borrows -> VectorIterator<T> {   // (3) the signature echoes it
        VectorIterator<T>(vector: lends self, index: 0)      // (4) the body proves it
    }
}
```

(1) `borrows struct` is design 130's `unsafe struct` shape: the type
declares its nature at its declaration and every signature that carries
the type echoes it; `--emit-docs` carries it as a type attribute. No
name convention (`Unsafe*` exists because unsafety must read at every
use site by name alone; a borrowing struct appears only as a `for` head
result, where the loop syntax and the producing `borrows` already say
it). (2) The field keeps the ordinary reference spelling — `&Vector<T>`
IS the sigil; a second modifier on the field would be a second spelling
of one fact, and two spellings drift. The two levels police each other:
a reference-typed field outside a `borrows struct` is an error with a
fixit naming the keyword; a `borrows struct` with no reference field is
a plain struct wearing a modifier, design 130's rule-7 teaching error.
(3) `borrows` in the effect slot on a VALUE-returning function: readers
and `--emit-docs` see that the result borrows the receiver at the
declaration (reader-visibility trumps the inference a single `&self`
would permit, and a future accessor with two reference parameters needs
the body to say which one anyway). A `borrows` function either `lend`s
exactly once (design 141) or RETURNS a borrowing struct, never both.
(4) `lends <place>` at the init site is the body's proof: a reference
field may be initialized ONLY with `lends` of a place rooted in a
reference parameter of the enclosing `borrows` function. LEND THE ROOT,
NOT THE BUFFER: `next` reads `self.vector.length` and `self.vector.
buffer` through the reference on every call, so nothing is snapshotted,
the struct owns no raw pointer of its own, and the only `unsafe` left is
the index through the buffer inside `next`. `EnumeratedIterator` is the
same four lines. RETURN, NOT SUSPEND, is what makes this simpler than a
`lend`: a design-141 accessor stops at its `lend` with its frame alive
and resumes for an epilogue at window close; this form RETURNS — the
accessor finishes, the borrow travels in the object, no accessor frame
lives across the loop and no epilogue runs on any exit route.

Everything else DERIVES from "this struct holds a reference", none of it
needing a further declaration, and each is a matrix cell: it is not
`Copy` (move-only) and not `Send` (so a `threads: N` group refuses it on
the fence that already exists, K19); it cannot escape, be stored in
another struct, be returned past its window, be captured by an escaping
closure or passed to a spawn — the existing reference rules, not new
ones; across a suspension it is a frame-resident pointer, design 88's
mechanism, so (ii) and (iii) apply to it unchanged; its extent is its
WINDOW, and the only window in U3 is a `for` statement — so a `borrows`
call that returns a value is legal ONLY as a `for` head (`for x in
v.iter()`, `for (i, x) in v.enumerated()`), refused anywhere else with
a message naming the rule; its own methods take it as `&var self` as
today. The window charges the ROOT of the lent place SHARED for the
statement's extent (design 141's root attribution), so a body
`v.push(..)` is the writer-beside-reader exclusivity error `v.push`
already gets inside a `with_ref` window, naming the loop as the live
borrow and the statement's end as its release; a second `for` over the
same root nested inside composes (two readers); a `with_var_ref` on the
root inside the body is refused (one writer). Who gets the model in U3:
Vector's two iterators, the class SL-321's sweep found (Data's and
String's iterators own or retain their source; Map/Set hand out owned
copies). A user `Iterator` over `UnsafePointer` stays its author's
design-130 promise unless it opts into the four spellings, which U3
makes possible but exercises only for std. The design-141 sentence "a
place is never a value and never escapes" becomes: a place is never a
value outside a borrowing struct, and a borrowing struct is never a
value outside its window. CONSUMER SWEEP (obligation 2, done Sep 20 by
grep over examples, blade, libs, devtools, sawc/std and the read-only
sawtracker sources): 51 `for` heads over `iter()`/`enumerated()`, all
untouched; the ONLY iterator held outside a `for` head is Data's
(`examples/data_iter_outlives_source.saw`), whose iterator owns its
source and is not in the class. `VectorIterator`'s `public` was added
so a holder could name it; with holding refused the agent may drop it
or keep it, and says which.

**(i) Extent — the `for` statement, by every exit route.** The window
opens at the head's evaluation and closes when the statement ends; the
extent is LEXICAL, so every route out of the loop leaves it with no
per-route runtime action (the struct owns nothing — no retain, no lock,
no epilogue). What each route owes is a test proving the root is
writable again immediately after the exit and the value computed is the
sync twin's: (1) exhaustion (`next()` answers `None`); (2) `break`, with
and without a value (SL-222's discarded-body rule unchanged); (3)
`continue` — NOT an exit, the borrow stays live across the back-edge,
and the op budget now charges that back-edge (the `:494` skip goes);
(4) `return` from inside the body; (5) an error propagated by `try` /
`?` out of the body; (6) task cancellation — a park inside the body
observes `__cancel` and answers through the same funnel as its value
(`__cancelled_result`), the body's `try` propagates it as route 5, the
frame runs to Done and `__release` drops its OWNED fields — the iterator
field owns nothing; the vector, when frame-owned, drops exactly once
through its real owner (a cell COUNTS that deinit); (7) frame destruction
WITHOUT resumption — asserted IMPOSSIBLE and the assertion tested: a
parent never completes while a sub-frame is mid-flight (parked in the
drive block until Done — `_owned_frame_fields`'s docstring), group
teardown and `main`'s exit CANCEL-then-JOIN every live member (design
124 item 5, K87), so every frame reaches Done by resumption; the only
ends that skip resumption are a panic and process exit, which run no
epilogue for anything. Checker-side, no route may leave the window's
root charge live past the statement, gated like design 189's loop rule
(K17: one textual construct, N live borrows).

**(ii) Address stability — a frame NEVER MOVES after its first `resume`,
so a window opened inside a state body never spans a move.** The three
places a frame lives: a DRIVEN-in-place frame is `var __f` on the
driver's own stack for the whole drive (`_make_driver`), never moved; a

spawn helper (`_make_spawn_helper`) at state 0, before any resume, and

passes the box, not the frame; an EMBEDDED callee frame is a by-value
FIELD of its caller's (design 44), so it inherits its caller's
stability. The one move a frame ever undergoes — the spawn box —
happens before state 0 runs, and every window opens inside a state
body, i.e. after the first resume. So a collection OWNED by the frame (a
frame-local `var v`) has a stable address for any window the body
opens; the borrowing struct's `&Vector<T>` points at that frame field,
and the buffer it reads through is the vector's own heap. U3 PINS this
rather than assuming it: a transform-side invariant that a spawn helper

matrix cells that run a window across a suspension in BOTH the driven

frame field (the U2 shape table records the collection `for` as SPLIT;

signature is asked to say it.

**(iii) External storage — the two cases the matrix keeps apart.** A
collection reached through a `&var`/`&` PARAMETER is a design-88
frame-resident pointer into the DRIVER's caller's storage (in-place:
the caller is parked on the drive, so the storage cannot go anywhere)
or into the SPAWNER's storage held by a design-201 extent (spawned: the
spawn's argument borrow keeps the root alive and excluded for the
task's life). A collection that is an ENCLOSING FRAME's field is
reached as `&self.<field>` into the parent frame, which does not move
by (ii). Address stability is therefore inherited in both cases; what
remains is NON-MUTATION across the suspension, and that is where the
spec's current sentence is REFUTED rather than extended: LANGUAGE_SPEC
§"Suspension and the coroutine transform" says a container borrow "may
not span [a suspension]" because "a concurrent task could reallocate"
the storage. Under task confinement the only way another task reaches
this root is a design-189/201 extent borrow — a capture or a spawn
argument — and that extent is visible to the same Law the loop's root
charge is: a `&var v` extent live during the loop is an exclusivity

(two readers); a `threads: N` group refuses the reference on `Send`
before the question arises (K19). Inside this task, nothing else runs
while the frame is parked. So the loop window is sound across a
suspension for exactly the reason a held `&var` parameter is (D6), and
the spec sentence is REWRITTEN to say so: the restriction was never
about suspension, it was about an UNTRACKED borrow, and the borrowing
struct tracks it. Matrix rows for (iii): the iterated root is {a
frame-local, a `&var` param of a driven callee, a `&var` param of a
spawned root (design 201), an enclosing frame's field via `&self.field`,
a field of a `&var self` receiver} × {a `&var` spawn-extent on the same

composes; the loop body itself pushing → refused; a `with_var_ref` on

agent to PROBE and report, not decide: a loop over a collection reached
through a `Mutex` guard — whatever the guard's body rule is today is the
answer, and the row records it.

**Fences (U3 scope).** The `for` head is the ONLY window that spans a
suspension in U3. `Vector.with_ref`/`with_var_ref` bodies and
`borrows`/`lend` windows keep their `sync` rule — same argument, same
mechanism, but a second consumer sweep and their own rows, so they are

On c43, I agree with the statement-scoped-window seam. These are the places I would police for ForLoop-specific assumptions:

1. Keep ITERATION in the for client and WINDOW LIFETIME in the common machinery.
The client owns iterator construction, next(), element/pattern binding, exhaustion and back-edge/op-budget behavior. The common layer owns the root charge, persistent referent/storage, suspension state and ordered cleanup. In particular, it should store a generic resource/owner slot, not require a field named __iter or an Iterator-shaped payload. A range/owned-iterator loop that creates no borrowed window must still use the ordinary collection split; not every ForLoop is a window and not every future window is a loop.

2. Close according to the control-flow target, not the spelling of the exit.
A window closes exactly when an edge leaves its lexical extent. continue targeting this for keeps its window; break targeting it closes it; break/continue targeting an inner loop must not close an enclosing window. Conversely, a future window nested inside an outer loop must close when control continues that outer loop. return/error/cancellation propagation close the scopes actually crossed, in inside-out order. Pass resolved scope/target information into the common cleanup funnel; an implementation that special-cases all Continue nodes as “keep open” would leak the first client's shape. Nested-window/inner-loop cases should pin this now.

3. Separate acquisition, active window, and release; do not bake “drop an iterator” into the release operation.
The common record needs a defined lifecycle and a client-provided cleanup operation, or an equivalent existing cleanup representation. Evaluate the head once; initialize the resource before treating it as active; perform release exactly once on exit; do not clean up an uninitialized resource when acquisition fails. For this client release destroys the borrowing iterator before ending the root charge. A future accessor-based window may instead own an accessor continuation whose epilogue must run, and an optional head may take an absent/else branch without ever activating the body window. U3 need not implement those future features, but the shared API must not assume release is always a trivial iterator drop or that every evaluated head establishes a live window. The precise temporary borrow during head evaluation and its handoff to the statement charge should be stated too, so arguments/defaults or a failing head cannot leave a gap or a stale charge.

4. Scope c42's DIRECT-head/temporary-receiver restrictions to BORROWING results.

They must not turn the original “any Iterator conformer; suspension in head or body” U3 requirement into a blanket refusal of ordinary owned iterators or suspending computations that produce them. ## 1. The window record and its chokepoint

`sawc/windows.py`. **Entries the chokepoint owns**, so no client does them twice:
- the ROOT CHARGE, read at the four access sites design 189's task-capture extent already had — a name read (`expressions._check_identifier`), a `move` (`_check_move_expr`), a CALL's access set (`types._check_call_exclusivity`, which is where `v.push`, a `&var` argument, an `o.take()` receiver, a closure's borrow captures and a design-201 spawn argument all arrive) and a WRITE target (`statements._check_write_target`);

## 2. The borrowing struct

`sawc/typechecker/borrowing.py`. Four spellings, each enforced:

| spelling | rule | refusal row |
|---|---|---|
| `borrows struct` | design 130's `unsafe struct` position; no name convention | `_error_borrows_prefix` for every other position |
| `private v: &Vector<T, A>` | the ordinary reference spelling; the ONE exception to DF-163d, TOP-LEVEL and SHARED only | K145 (`&var` field), K143 (nested reference) |
| `borrows -> S` | a VALUE-returning producer | K144 (missing `borrows`) |
| `lends self` | the ONLY origin, `&self` receiver required | K144 (projection, foreign parameter, `&var self`) |

`lends` is a **CONTEXTUAL keyword** (the `import`/`module`/`export` precedent), so neither lexer's table changes: `lexdiff`, `astdiff` and `selfhostlex` are untouched by the new word. `borrows struct` reuses the existing `BORROWS` token.

**The lend/producer split is answerable before type checking.** `place_transform` runs ahead of the checker and cannot look up whether a return type names a `borrows struct` (it may be imported), so it splits on two facts it does have: the DECLARED return type is not a reference (SL-333 R1 made `-> &T` mean "lend" whatever the body does) and the body contains no `lend`. A `borrows -> T` body that DOES lend still gets R1's fixit; a `borrows -> &T` body with no `lend` still gets design 141's coverage error. The producer then gets `place_self_by_pointer` — the SAME bit DF-146b set for an accessor, not a second ABI — because a copy's address dies with the call.

**R5's FIELD clause** was added to the sentence SL-333 wrote, in `parser/types.py:reject_reference_field` and in the spec, rather than a second sentence beside it.

**The fence: one question at one line.** `check_borrowing_fence` is called from `_check_expression` where `resolved_type` is stamped — the one line every expression's type passes through — so the position list is a matrix of TESTS, not of checks. Four exceptions, each documented: e1 the producer's own construction and return; e2 the compiler's hidden binding (E8); e3 the struct's own extension methods' receiver; e4 the reference field, which AUTO-DEREFERENCES at member access exactly as a reference parameter does — which is what confines it to a non-escaping re-borrow with no second rule, since references are not first-class.

**The rejector's rows.** Three phrases, and that is deliberate: the fence has no parent slot in hand, so the sentence that matters is the RULE. Two positions a CLIENT knows get their own diagnosis because the ACT differs.

| row | position | message |
|---|---|---|
| K142.1-9 | `let`, `var`, argument, discarded statement, tuple element, collection-literal element, assignment RHS, closure return, `??` operand | ``may not be used outside a window head`` |
| K142.10 | TEMPORARY receiver | ``may not be produced from a TEMPORARY receiver`` + "bind the collection first" |
| K142.11 | head is an `if`/`match`/block/`try` EXPRESSION | ``may not be produced by an `if` / `match` / block / `try` expression in the head`` |
| K143 | parameter, field, plain return, type argument, static, associated `Item` | ``may not name a borrowing struct`` — at the DECLARATION |
| K144 | `lends self.items`, `lends other`, `&var self` receiver, a field not initialized with `lends self`, a `borrows struct` with no reference field | one message each, each naming the rule |
| K145 | `&var T` field | ``may not be an EXCLUSIVE reference`` + the reallocation argument |

A by-value receiver is NOT a row: the parser already refuses `self` without a sigil, so the origin rule's own refusal for it is unreachable from source.

**std.** `VectorIterator<T, A>` and `EnumeratedIterator<T, A>` are the four-line shape holding `&Vector<T, A>`; `next()` reads `length` and `buffer` through the reference on every call and the only `unsafe` left is the index through the buffer. **`public` KEPT** on both, and the comment now says why: design 80's signature-visibility rule (a public `iter()` may not name a private type), NOT so a caller can hold one — holding is refused. ## 9. "What the generic window statement would add" (the owed paragraph)

Its **syntax** is a keyword-introduced block naming a head (a `borrows` call on a place), a binding, the mode the binding is opened at, and an `else` arm for a conditional lend. Its **typechecking client** is one adapter beside `open_for_window` / `close_for_window`: it resolves the receiver place, calls `WindowTable.open_window` with its own root, mode, origin and extent, and calls `close_window` at the statement's end — reading nothing of its own shape back. Its **acquisition/result binding** is B3's ACQUIRE sequence unchanged (A1-A5 are about a CALL EXPRESSION, not about a loop), plus the one thing new: the statement BINDS the lent place under a name, where `for` binds the loop variable instead.

And nothing else, because none of the four is duplicated:
- **ROOT ACCOUNTING** is `WindowTable.conflict_for` and the four access sites that read it; they take a PATH and a writes-flag and have never seen a `ForLoop`.
- **PINNING** is the direct-head rule (`borrowing_head_receiver` + `borrowing_head_root`, the latter being design 141's `_build_access_path` and not a root walk of its own) plus (ii)'s refusals, which are rows of the same conflict table.
- **SUSPENSION PERSISTENCE** is the record on the statement plus the resource's ordinary frame residency. The `for` client gets it by being rewritten into a `while let`, so the iterator becomes a frame local the way any local does; a generic window's binding is the same question with a different resource, and `coro_transform.py` reads `stmt.window`, never the loop.
- **EXIT CLEANUP** is `_open_window_resource` / `_close_window_resource`, which take the RESOURCE'S TYPE and its slot — nothing client-shaped — and are pushed around the statement BEFORE the `loop_stack` entry records the unwind depth, so `break` unwinds only the scopes inside and `return` sweeps through `_cleanup_all_scopes`.
