## Description

Python sawc rejects an explicitly Optional-typed value `if` / `if let` when one
arm already has type String? and the other arm supplies a String that should
wrap into the annotated destination. The same expression compiles when the
String arm is first assigned to a separate String? local.

Reproduced on clean sawlang HEAD `30c5a55016aed806a2f94a64d62224c6cafc135a`,
macOS arm64, using the repository Python environment.

Minimal reproducer:

```saw
func source() -> String? { "present" }
func main() {
    let value: String? = if let item = source() {
        let absent: String? = None
        absent
    } else {
        "fallback"
    }
    if let text = value { print(text) } else { print("none") }
}
```

Expected: the declared String? destination supplies the context for both arms;
the String arm wraps, the existing String? arm stays at its current depth.
Compilation succeeds and execution prints `none`.

Actual: compilation exits 1 at line 3, column 26:
`if let` branches have incompatible types: `String?` vs `String`.

Sibling probe: replacing the conditional binding with `if true` produces the
same rejection, now naming `if` / `else`. This is not specific to binding or
ownership. A control replacing the else tail with:

```saw
let fallback: String? = "fallback"
fallback
```

compiles and prints `none` at exit 0.

Commands (from the production repository):

```
.venv/bin/python sawc/sawc.py .build/scratch/m10_if_let_optional_context.saw -o .build/scratch/m10_if_let_optional_context
.venv/bin/python sawc/sawc.py .build/scratch/m10_if_optional_context_control.saw -o .build/scratch/m10_if_optional_context_control
.venv/bin/python sawc/sawc.py .build/scratch/m10_if_let_optional_explicit_control.saw -o .build/scratch/m10_if_let_optional_explicit_control
.build/scratch/m10_if_let_optional_explicit_control
```

Likely mechanism: `sawc/typechecker/expressions.py` around lines 5370–5423 and
5602–5608 compares independently checked arm types before applying the annotated
Optional destination. The ordinary-if reconciliation handles the enclosing
Result return specially, but does not reconcile this Optional slot context.
This diagnosis is based on source inspection; no production fix was attempted.

Suggested regression scope: annotated let/assignment/call/return positions,
ordinary if and if let, both arm orders, nested value branches, and nested
Optionals distinguishing outer None from Some(None). Preserve rejection when
payloads cannot convert or when no sufficient type context exists.

Found while validating the independent Saw compiler prototype. Its Optional
frontend passes the corresponding nested contextual probe in the VM; it does
not reproduce this Python rejection. Tracker searches for `if let` and
`context` did not identify an existing report of this specific rejection.
