## Description

While any accepted TCP socket is parked in a read (io_wait) waiting for its first bytes, the runtime stops completing/accepting new connections on the listening socket. A single idle connection is sufficient. Data arriving on the parked socket wakes the reactor and everything queued (including pending accepts) drains immediately.

Impact: any browser preconnect (a socket opened speculatively that sends nothing) freezes an HTTP server for ~30s until the browser closes it. Observed as 30+ second page-load stalls in Sawtracker (ST-7); requests process in <50ms once accepted.

Reproducer against any Saw TCP server that accepts then reads (python3, server on 8787):

    import socket, time, urllib.request
    a = socket.create_connection(('127.0.0.1', 8787)); time.sleep(0.5)
    urllib.request.urlopen('http://127.0.0.1:8787/', timeout=4)   # times out
    a.sendall(b'GET / HTTP/1.1\r\nHost: x\r\n\r\n')               # wakes reactor
    a.recv(200)                                                    # parked socket served
    urllib.request.urlopen('http://127.0.0.1:8787/', timeout=4)   # now succeeds

Additional evidence:
- Scales from 1 to 20+ idle sockets; with ~20, even TCP handshakes time out (listen backlog overflow), so the accept task is not draining at all.
- A perpetual `sleep(1)` heartbeat task does NOT mitigate: with it running, handshakes complete into the kernel queue but the server still never accepts, so sleep deadlines evidently do not trigger an fd rescan.
- Everything recovers instantly when the idle socket closes or sends data, with no restart: the wakeup path works, the parked-registration path appears to lose the listen fd (or earlier-registered fds) from the poll set.

Suggested area: io_wait registration replacing rather than accumulating reactor interest, or the poll set being rebuilt only from the most recent park. Related: SL-204 (io_wait deadline) would mitigate the browser symptom but not this root cause.

Investigated from the sawlang side (2026-09-08). The runtime is exonerated at this vintage; the evidence points back at sawtracker's own accept/dispatch path.

REPRODUCED against the shipped binary: a scratch `sawtracker serve` instance (same ~/bin binary, port 8907, --no-push, seeded local repo) wedges exactly as filed — an idle preconnect stalls a following request past a 4s timeout, and data on the idle socket un-wedges everything instantly.

RUNTIME EXONERATED by five counter-probes, all built at sawlang HEAD (which is the runtime vintage this binary carries — it exports __saw_rt_tcp_listen_on, added Sep 7). Each probe is an accept-then-read HTTP server; the same reproducer passes (<60ms) against every one with an idle preconnect parked mid-read:

1. spawn-per-connection handlers, ambient scheduler
2. spawn-per-connection handlers, TaskGroup(threads: 8)
3. fixed worker pool pulling from a Channel<TcpStream>, ambient
4. handlers on the background Task.spawn engine, acceptor ambient
5. worker pool + acceptor all inside one TaskGroup(threads: 4)

So a parked read does NOT lose the listen fd's reactor registration in any of these topologies: the suggested mechanism (io_wait registration replacing reactor interest) does not reproduce in the runtime itself.

TWO NARROWING FACTS from the scratch instance:

- The wedge is not first-bytes-specific: a connection that sent a PARTIAL request ("GET / HT", then silence) wedges new connections exactly like a never-sent one. Any connection mid-read blocks all accepts until that read completes.
- data/server.log records every request at 0ms once dispatched, and a wedged request's log line appears only at the moment the blocking read elsewhere completes. The stall is entirely upstream of request handling.

That signature — strictly one read at a time gating accepts, worker count irrelevant — is what a server shows when the REQUEST IS READ BEFORE THE HANDOFF: an accept loop (or single dispatcher) that calls read_request on the new socket itself and only then hands the parsed request to a connection worker. Suggested check: the call site of read_request relative to accept and the worker handoff; the fix is moving the read (or the whole connection) into the per-connection/worker task, which the runtime demonstrably supports (probes 1-5).

Repro materials in the sawlang checkout under .build/scratch/: probe_205_server.saw, probe_205_pool.saw, probe_205_bg.saw, probe_205_mtpool.saw, probe_205_client.py, probe_205_half.py.

SL-204 (read/io_wait deadline) stands on its own as a real sawlang ask regardless — idle-connection deadlines need runtime support, and that design work is queued for a ruling.

Bisection results from the sawtracker side (2026-09-08). Your probes were right that clean servers do not wedge — and the trigger is narrower than "accept/dispatch shape": it is http.read_request itself, and the evidence now points at the coroutine frame transform rather than app structure.

All runs hermetic (file:// remotes, temp data dir, idle socket is the FIRST connection ever; wedge = a following request times out; recovery on any watched-fd traffic):

- Real binary, full startup: WEDGES.
- Real binary with open_store skipped entirely (empty store): WEDGES — startup/git/files not required.
- Real binary, full startup, but handle() reads with a naive inline loop and writes a canned response (no http.saw, no store round-trip): PASSES.
- Real read_request + real http.send, canned response (no store round-trip): WEDGES.
- Real read_request + naive write: WEDGES. => read_request is necessary and sufficient on top of the passing skeleton.
- Synthetic replicas of every other sawtracker structural element all PASS: 64 loop-spawned workers with inline channel copies, job/reply dispatcher round-trip, per-connection done channels, extra forever-parked channel tasks, SIGPIPE ignored, flock'd fd, O_APPEND log writes per request, two-part response writes, an output-capturing subprocess before listen, a regular-file read at startup, one-arg vs two-arg listen, acceptor spawned vs on the driving task.

Compiler-side clue: cloning read_request verbatim into the entry module (only change: call the local copy) does not build —

  error: cannot assign `UInt8?` to field of type `Byte?`
  --> sawc/std/compiler/frame.saw:91  (in the instantiation `Slot<Byte>.clear`)

so read_request's coroutine frame instantiates a Slot<Byte> that the frame machinery cannot even type-check in one module context; the working build presumably instantiates the same shape from src/http.saw without the error. Hypothesis: the Slot<Byte> frame path is silently miscompiled there, corrupting frame/reactor state for the task parked in stream.read, which starves the listen fd's wakeup. Casting the one explicit Byte local (val.byte_at(hi)) to Int did NOT clear the wedge, so if the frame hypothesis is right the offending slot is something the transform synthesizes, not that local.
