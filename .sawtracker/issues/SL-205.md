## Description

While any accepted TCP socket is parked in a read (io_wait) waiting for its first bytes, the runtime stops completing/accepting new connections on the listening socket. A single idle connection is sufficient. Data arriving on the parked socket wakes the reactor and everything queued (including pending accepts) drains immediately.

Impact: any browser preconnect (a socket opened speculatively that sends nothing) freezes an HTTP server for ~30s until the browser closes it. Observed as 30+ second page-load stalls in Sawtracker (ST-7); requests process in <50ms once accepted.

Reproducer against any Saw TCP server that accepts then reads (python3, server on 8787):

    import socket, time, urllib.request
    a = socket.create_connection(('127.0.0.1', 8787)); time.sleep(0.5)
    urllib.request.urlopen('http://127.0.0.1:8787/', timeout=4)   # times out
    a.sendall(b'GET / HTTP/1.1\r\nHost: x\r\n\r\n')               # wakes reactor
    a.recv(200)                                                    # parked socket served
    urllib.request.urlopen('http://127.0.0.1:8787/', timeout=4)   # now succeeds

Additional evidence:
- Scales from 1 to 20+ idle sockets; with ~20, even TCP handshakes time out (listen backlog overflow), so the accept task is not draining at all.
- A perpetual `sleep(1)` heartbeat task does NOT mitigate: with it running, handshakes complete into the kernel queue but the server still never accepts, so sleep deadlines evidently do not trigger an fd rescan.
- Everything recovers instantly when the idle socket closes or sends data, with no restart: the wakeup path works, the parked-registration path appears to lose the listen fd (or earlier-registered fds) from the poll set.

Suggested area: io_wait registration replacing rather than accumulating reactor interest, or the poll set being rebuilt only from the most recent park. Related: SL-204 (io_wait deadline) would mitigate the browser symptom but not this root cause.

TWO NARROWING FACTS from the scratch instance:

- The wedge is not first-bytes-specific: a connection that sent a PARTIAL request ("GET / HT", then silence) wedges new connections exactly like a never-sent one. Any connection mid-read blocks all accepts until that read completes.
- data/server.log records every request at 0ms once dispatched, and a wedged request's log line appears only at the moment the blocking read elsewhere completes. The stall is entirely upstream of request handling.

That signature — strictly one read at a time gating accepts, worker count irrelevant — is what a server shows when the REQUEST IS READ BEFORE THE HANDOFF: an accept loop (or single dispatcher) that calls read_request on the new socket itself and only then hands the parsed request to a connection worker. Suggested check: the call site of read_request relative to accept and the worker handoff; the fix is moving the read (or the whole connection) into the per-connection/worker task, which the runtime demonstrably supports (probes 1-5).

MECHANISM PINNED (sawlang side, 2026-09-08). This is a COMPILER bug in the coroutine transform, not a runtime reactor bug and not app structure. The reactor and both listen overloads are correct.

THE AXIS: a suspending FREE FUNCTION whose body parks on a socket read (io_wait), when it lives in an IMPORTED module rather than the entry module, registers with the reactor with a TOKEN OF ZERO. The token (design 91) is the parked frame's `__wake`-word address; `rt_reactor_poll` guards `if ud != 0 { *tok = 0 }`, so a zero token latches nothing — the parked task's wake word is never cleared and it stays parked forever. The wedge on ACCEPTS is downstream: everything funnels through one reactor, and the never-cleared park keeps the scheduler from making progress on the listen fd until unrelated traffic on the parked socket forces a rescan (which is exactly the "recovers instantly on any watched-fd traffic" behavior).

MINIMAL REPRO (no store, no http parsing, no try/catch — those were all red herrings):
- A 12-line reader: `while { let chunk = try! stream.read(); if chunk.len()==0 {return 0}; try! data.append(move chunk); if data.to_string().contains("\r\n\r\n") {return 1} }`.
- Identical body in TWO placements, spawned per-connection from the same handler:
  * in an IMPORTED module (`import src.v0; v0.read(...)`)   -> WEDGES
  * in the ENTRY module as a same-file helper or inlined    -> PASSES
- Nesting depth is NOT the trigger (a same-file helper called by the handler passes); the callee's HOME MODULE is.

DIRECT EVIDENCE (instrumented reactor register/poll, since reverted):
  wedging build:  [reg] fd=5 dir=0 tok=0            <- connection socket parks with token 0
  passing build:  [reg] fd=5 dir=0 tok=4345002096   <- real &frame.__wake address
Everything else (listen fd=3 registration, poll counts) is identical between the two.

WHERE IT IS: coro_transform.py. `__io_tok` is the root frame's `__wake`-word address, set on a frame's first `resume` (io_tok_init, ~line 5363) and propagated into an embedded sub-frame's `__io_tok` by the parent's drive block (~line 6896). The io_wait lowering registers `self.__io_tok` (~line 5918). For a cross-module suspending callee, the embedded frame runs its io_wait with `__io_tok` still 0 — either the sub-frame drive does not propagate the token across the module boundary, or the cross-module callee is materialized as a frame whose `__io_tok` field is not the one the drive block writes. This is almost certainly the SAME root cause as the Slot<Byte> clue: cross-module frame materialization diverging from the in-module path (the open DF-270b / DF-286c alias-and-materialization family). read_request's explicit `Byte` local is what surfaces the materialization divergence as a visible BUILD error when cloned into the entry module; the token=0 is the same divergence surfacing as a silent miscompile in the working (imported) build.

REPRO MATERIALS (sawlang checkout, .build/scratch/wedge/): src/v0.saw (imported, wedges) vs the same body as an entry-module helper in src/vmain.saw (passes); WEDGE_PORT-parameterized; the idle-socket oracle is .build/scratch/probe_205_client.py. Confirmed against a clean stdlib (rt rebuilt) so the finding does not depend on the instrumentation above.

WORKAROUND CAVEAT for sawtracker: relocating read_request into the spawn-root's own module is the shape that passes here, BUT read_request's `Byte` usage is exactly what trips the entry-module BUILD error (the peer already hit this), so a naive move won't compile — the two faces of the one bug collide. A source-only workaround therefore isn't clean; the fix belongs in the transform. Filing on the sawlang side and continuing on the fix.
