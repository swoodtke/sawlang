## Description

**SL-1063 unit A: `sawc` compiles a freestanding object for `xtensa-esp-unknown-elf` (the ESP32-S3).** This is the critical-path unit: sawos's Xtensa HAL (SO-75) can't compile Saw until it lands, and the lead posts the merged sha to the sawos lead at once.

**Rulings this unit implements.**
- **The triple is `xtensa-esp-unknown-elf`** (user, Nov 12): the name Espressif's clang gives its own multilib, and the only spelling it compiles with no warning.
- **The minimal set the sawos lead asked for is approved** (user, Nov 12): call0 for every image, no floating-point instruction by default, a definite set of special registers generated code may touch, word atomics inline (`s32c1i`; sawos's HAL sets ATOMCTL).
- **Only Espressif's clang serves the target:** no other clang on the machine has a working Xtensa backend (the sweep's `a3_other_clangs.txt`).

**The sweep's evidence** is in the main checkout, `.build/scratch/pxtensa/`: `REPORT.md` (also SL-1063's report comment), `sites.tsv` (every site, with riscv32's answer and Xtensa's), `abi.md`, and the spike (`e_retarget.py`, `e_spike.sh`, `e/`), which compiled sawc's riscv32 IR for four freestanding cases to Xtensa objects with only the triple and the feature string changed. Read `REPORT.md` and the `layout.saw`, `attributes.saw`, `build.py` and `checks.saw` rows of `sites.tsv` before anything else.

**Lead decisions (reversible; logged here).**
1. **The triple implies the CPU.** `xtensa-esp-unknown-elf` means an ESP32-S3 today: every function carries `"target-cpu"="esp32s3"`. The sweep showed nothing on clang's command line selects the CPU for IR input; the module's attributes are the only selector. A second Xtensa chip later needs its own selector; out of scope.
2. **The default features are `-windowed,-fp,-loop,-mac16,-bool`,** and for THIS triple they apply to every build (freestanding or `-c`), because `-windowed` is the calling convention and two objects of one image must agree on it.
   - `-windowed` is call0; `-fp` is no FPU instruction. `-loop`, `-mac16` and `-bool` turn off the zero-overhead loop, MAC16 and boolean-register options that `esp32s3` enables, so that the register set generated code can touch is a0 to a15, SAR and SCOMPARE1 BY CONSTRUCTION, not by observation (the sweep saw none of them used, but could not rule `loop` out).
   - `s32c1i` stays on: word atomics are inline.
3. **`--target-features` ADDS to the default for this triple; it does not replace it.** The emitted list is the default, then a comma, then the operand, so a later mention wins as LLVM reads it: `--target-features +fp` gives call0 with the FPU, and windowed code takes an explicit `+windowed`. On aarch64 an explicit list replaces the profile default; here that would silently flip the calling convention of one object. `target_effective_features`' comment states both rules.
