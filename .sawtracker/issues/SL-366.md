## Description

Found by codex's review of SL-357.p2 (c13) on Sep 23 as a source-level counterexample to a comment's losslessness argument. Nothing has reproduced it; the comment now states the case as unhandled.

The handler write in `rt/shim.c` drops a record when the pipe is full. A (re-)watch drains the pipe, but handlers that snapshotted an older generation before the watch can still write afterwards, at most one record per thread. Nothing bounds the thread count below the pipe's record capacity (TaskGroup accepts any positive worker count, and threads that existed before the watch count too). If the stale records fill the pipe, the current generation's write is dropped and `__saw_signal_drain` rejects every stale record, so `next()` never sees the delivery.

The practical bound is thousands of threads, each paused between snapshot and write, so this is low priority. Fix options:
- the drain re-arms or re-checks when it saw only stale records and the pipe was full;
- the handler does a non-blocking retry after draining stale records, if that stays async-signal-safe;
- the pipe is sized from the thread count;
- a documented thread-count limit enforced at watch time.
