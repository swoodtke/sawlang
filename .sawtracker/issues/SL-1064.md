## Description

**Reconcile the Stage-0-era issues against `sawc`: re-probe each, then close it with evidence or re-file what still fails.** Found by the lead's Nov 12 backlog review with the user.

**Why.** About thirty open issues were filed against the Python compiler (Stage 0, now `sawc0`, v0.18.0) or against early `sawc2`, and were never re-probed against today's `sawc`. Several carry `high`. Spot checks on Nov 12 found four whose repro no longer fails:
- SL-387 (`high`, a nested closure borrow silently losing writes): `sawc` refuses the program (`mutability.immutable`) instead of printing 0;
- SL-699 and SL-856 (MIR verifier INVARIANTs on a `match` over a NoCopy value): both repros build and run;
- SL-524 / SL-729 (`try!` not rendering its error): fixed, closed today.

So the board overstates the soundness backlog, and nobody can tell which of the rest are live.

**Unit: a read-only sweep** (no tracked edit; evidence in the main checkout's `.build/scratch/preconcile/`). For each issue below: read the issue and its comments, rebuild its repro for `sawc` (the new std's spellings; the saw-lang skill), run it at -O0 and -O2 and, for an ownership or memory claim, under `--sanitize address`, and record one row: issue, repro file, expected by the spec (quote the rule), what `sawc` does, verdict.

Verdicts:
- **FIXED:** the repro and the issue's own sweep matrix (obligation 4), where it lists one, all behave as the spec says. The lead closes it with the row.
- **LIVE:** still wrong in `sawc`. The row carries the mechanism as far as evidence shows it, labelled UNVERIFIED where it is a guess. The lead re-titles the issue for `sawc` and prioritizes it.
- **STAGE-0-ONLY:** the construct is refused or gone in `sawc` by a later ruling, so the issue has no subject. Name the ruling.
- **CAN'T TELL:** what blocks the probe (a feature `sawc` doesn't build yet: name its issue).

**The issues.**
- *Labelled `frozen`/`pinned` (Stage 0 bugs kept open for an XFAIL citation):* SL-26, SL-30, SL-34, SL-38, SL-41, SL-51, SL-80, SL-231, SL-267, SL-340. For each, also say whether an XFAIL pin still cites it (`grep -rn 'XFAIL' tests/ compiler/tests/ | grep SL-N` and the DF id), since the `citations` lane fails if a cited issue closes: the row names the pin, and what the pin does under `sawc`.
- *Stage 0 hazards and leaks:* SL-429, SL-430, SL-431, SL-455, SL-464, SL-465, SL-621, SL-695.
- *Runtime findings written against `sawc/rt/` and the Python codegen (the runtime is Saw now, under `runtime/`):* SL-35, SL-276, SL-307, SL-354, SL-355, SL-360, SL-361, SL-366, SL-375, SL-376, SL-392. For each, find today's function (the issue names the old path) and say whether the defect's code is still there; reproduce where a repro is practical, and say "source reading only" where it is not.
- *The first `sawc2` correctness review and its neighbours:* SL-387, SL-647, SL-658, SL-687, SL-689, SL-690, SL-699, SL-700, SL-705, SL-706, SL-715, SL-728, SL-732, SL-733, SL-744, SL-856, SL-881.

**Report:** one table (`reconcile.tsv`) and a summary by verdict, with the repro files. The lead applies the closures and re-files; the sweep posts nothing.
