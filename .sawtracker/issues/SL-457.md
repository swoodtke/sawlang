Follow-up from U6c2 (SL-452, chat m330): one constant evaluator for EVERY constant position (SL:architecture §3.10, 'one evaluator for every constant position').

**Today:** U6c2's MIR evaluator covers static initializers, raw values, static_assert and @align, each lowered to a MIR function, and typecheck's fold.saw agrees with it under typed arithmetic. But const-generic arguments, array lengths and repeat counts are folded by typecheck's OTHER folder, build_const in signatures.saw (literals, +, -, * and a const parameter). Their nodes are Const_* type-grammar alternatives that no body types, and typecheck records no per-node value. So there are still two folders, and one of them is outside the agreement gate.

**Do:**
1. Record typecheck's value per const-argument node (a typecheck change, with its own commit and pin).
2. Lower each const-argument node to a small MIR function, a const-grammar lowering in compiler/mir.
3. Evaluate it with the MIR evaluator, and extend the agreement gate to cover these positions.
4. Then decide whether build_const can be retired into fold.saw, or into on-demand lowering.

**Sequencing:** after SL-452.p2 (U6c2) and SL-453 (T.Item, now in typecheck) land.

Context for whoever picks this up: today's gap is a duplication hazard, not a live disagreement, and it stays that way only while `build_const` doesn't grow.

- **Why the two folders can't disagree now:**
  - `fold_chain` refuses any operand, or running value, beyond `TC_CONST_LIMIT` (2^31 − 1) as `slice.not-yet` before each operation, so every `+ − *` it accepts is exact in Int64.
  - Const parameters are `Int` only, so typed arithmetic at Int computes the same value.
  - Everything else the spec allows in these positions is refused rather than folded differently: `/ %`, `sizeof<T>()`/`alignof<T>()`, a module `static` argument, and an array length's full grammar, including shifts.
- **The hazard is growth.** Each of those additions brings a semantic choice the evaluator already makes: `/` and `%` rounding and sign, a static's typed value, and shift range under typed arithmetic. Until this issue lands, any widening of a const-argument position should go through this issue, not into `build_const`.
- **Suggested now (cheap):** one fixture per refused form above, asserting today's `slice.not-yet`. Then a change that grows `build_const` flips a fixture visibly instead of quietly forking the semantics.

**Implementation detail (lead, Nov 12): this one gets a design pass (Opus) first, then Sonnet units cut from the design. SL-511 rides on it.**

**Why it is the top sawos item.** Kernel code sizes its tables with constant expressions, and today none of these builds in a length or a repeat count: `1 << PAGE_SHIFT`, `MASK & ~ALIGN`, `8 / 2`, `BYTES / sizeof<UInt>()`, a raw-backed case, an alias constructor `Byte(4)`, and `inner<N + 1>()` over a const parameter. Six corpus programs are refused on `syntax.expr.shift` alone, including `const_bitwise_width_riscv32.saw`, which is also the only program that would show whether constants fold at the TARGET's `Int` width (SL-511).

**The state of the code (comments c1 to c8 above, re-read today).**
- Two folders. `fold.saw` (typecheck's constant fold, agreeing with the MIR evaluator under typed arithmetic) serves static initializers, raw values, `static_assert` and `@align`: those positions fold shifts, bit operators, division and `sizeof` already.
- `build_const` in `compiler/typecheck/src/signatures.saw` serves const-generic arguments, array lengths and repeat counts: literals, a const parameter, `+ - *`, bounded by `TC_CONST_LIMIT`. Their nodes are `Const_*` type-grammar alternatives no body types, and typecheck records no value per node.
- The target's word: typecheck's README says `Int`/`UInt` are the target word's width and "every fold and every `static_assert`'s layout follow it" (`TcProgram.target`, `int_width`), so SL-511 may already be fixed for `fold.saw`; nothing has proved it, because the riscv32 program is refused first.
- GRAMMAR.md §5.2: a generic argument LIST takes no bitwise operator (`Buf<(1 << BIT)>` is not grammar); a named constant there works. So bit operators belong to lengths and repeat counts only.

**The design must decide, with evidence:**
1. **One evaluator, which way?** (a) route the three positions through `fold.saw` (teach it the `Const_*` alternatives, or re-read the same tokens as expressions) and retire `build_const`; (b) the issue's original plan: record a value per const-argument node, lower each to a small MIR function and run the MIR evaluator, extending the agreement gate. State what each costs, what each does to the agreement gate between fold and evaluator, and which the SL:architecture §3.10 text ("one evaluator for every constant position") requires. Recommend one.
2. **Per-instantiation folds:** `inner<N + 1>()` inside `func outer<const N: Int>` folds only once `N` is known. Where does that fold run (mono?), what does typecheck check before then, and what is the refusal when an instantiation's value is negative or overflows.
3. **The grammar of each position**, exactly: which operators and leaves a length, a repeat count and a const argument take per GRAMMAR.md, as a matrix (position × form), with today's verdict per cell from probes and the designed verdict.
4. **`sizeof`/`alignof` in these positions:** they need the target's layout (`compiler/target`), which typecheck defers to "a layout" today (`ll_align_value` in the backend folds an `@align` the fold left). Which stage folds `[UInt8; sizeof<Header>()]`, and what happens to type identity (`[T; N]` equality) before the layout is known.
5. **Statics that hold such values:** `static WORDS: Int = BYTES / sizeof<UInt>()` passes `coro --check` and is `backend.not-yet`. Same question as 4, for a static's value.
6. **Width (SL-511):** prove or refute, with `const_bitwise_width_riscv32.saw` reduced to cells that build today (a `static_assert` on `1 << 31` at `--target riscv32-unknown-none-elf`), that every fold site takes `Int`'s width from the target. List every site that hard-codes 64.
7. **Refusals:** each fault in these positions (overflow, shift range, divide by zero, negative length) and which existing rule id reports it.

**Deliverable of the design pass** (posted on this issue as one comment; evidence in `.build/scratch/p457d/` of the main checkout; no tracked edit): the recommendation with its reasons, the position × form matrix with today's and the designed verdicts, the list of code sites to change per stage, the fixtures per cell, the corpus rows expected to move, the open questions that are the user's, and a cut into units small enough for a Sonnet agent each (with each unit's files, expected golden moves and gate).

**Then:** the lead reviews the design, takes any open question to the user, and writes each unit's implementation detail here before its dispatch. SL-511 closes with the unit that pins the riscv32 width.
