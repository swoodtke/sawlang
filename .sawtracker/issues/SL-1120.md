## Description

**Filed by the sawos lead for the sawlang lead.** Hit while writing sawos's image builder in Saw (SO-104). Run against sawlang 0.23.0, hosted, macOS arm64, by the builder's implementer.

- **Tried (reproduced).**

  ```saw
  struct Failure {
      message: String
  }

  extension Failure: Error {
      func format(&self, into: &var StringBuilder) {
          try! into.append(self.message)
      }
  }

  func main() -> Result<Void, Failure> {
      var b = StringBuilder()
      var i = 0
      while i < 100 {
          try! b.append("0123456789")
          i = i + 1
      }
      try! b.append(" END")
      return Failure(message: b.build())
  }
  ```

- **What happened.** stderr shows `error: ` and the first 508 bytes or so of the message, then `…`, and the exit status is 1. The rest of the message is gone (it looks like a buffer of about 512 bytes).
- **Expected.** The whole message.
- **Why sawos needs it.** A build tool's error is often another tool's whole output: a failed compile's diagnostics run to kilobytes, and the part that names the fault is as likely to be at the end as the start. Cutting it silently hides the error.
- **How badly.** It hides errors, so it matters; there is a workaround, which the builder uses: `main -> Int`, printing the error itself and returning 1. That puts the message on stdout.

**Triage and implementation detail (lead, Nov 14).** Reproduced on main at df036fb2f: the filed program writes 519 bytes on standard error where the whole line is 1,012 (`.build/scratch/p1120/` in the lead's checkout). **This is sawc departing from the spec, not a rule to decide.**

**The spec** ("The entry point"): "`E` is renderable ... and the `Err` path prints it the way `"{e}"` does". `"{e}"` is the interpolation spelling: it builds a `String` and has no length limit. The bounded rendering is the other spelling, a `{}` format argument ("the one bounded piece is a single user `Printable` rendering (512 bytes), which truncates with the marker"), and that sentence is about `print`, `panic` and `assert`.

**The mechanism.** `main_status` in `compiler/llvm/src/render.saw` (THE ONE PLACE a `Result` from `main` becomes the status) renders the error with `render_fixed`, the format-argument path: `Printable.format` into a fixed builder over `LL_RENDER_SCRATCH` (512) bytes of stack, cut and marked `…`. `render_fixed`'s other callers are the documented bounded ones (a `{}` argument of `print`, `panic`, `assert`; the `try!` failure message, which is a panic and is assembled without the heap on purpose: spec, "Panic messages allocate nothing"). So `main_status` is the one caller on the wrong path; the siblings are bounded by a stated rule and stay.

**The change.** On the `Err` path, `main_status` renders the error the way an interpolation does: through its `format` into a growable builder (`interpolation_into` in the same file is the model, with `builder_new_item` and `builder_build_item`), writes `error: `, the built bytes and the line break as the one line under the output lock that it writes today, and drops the `String`. Mono must resolve the two builder items for a program whose `main` returns a `Result` even when the program has no interpolation of its own: find where `builder_new_item` and `builder_build_item` are requested and add the entry's need there.
- **Where there is no heap to use, the bounded rendering stays, and the spec says so.** Under `--no-hidden-alloc` (the entry's error would be a fourth compiler-inserted allocation) and in a `--freestanding` build, `main_status` keeps `render_fixed`. The spec's entry-point section gains the sentence: the error is written whole; under `--no-hidden-alloc` and in the freestanding profile it is rendered in 512 bytes of stack and a longer one ends in `…`.
- An allocation failure while rendering is the String layer's documented panic boundary, as for any interpolation.

**Step 0:** the filed program, and the same with an erased `Result<Void, Box<any Error>>`, a `Result<Int, E>`, a suspending `main` (the entry executor's path), and `E` = `String`-holding enum: each cut at 512 today. A message of 300 bytes is whole today and stays byte-for-byte.

**Pins.** A run probe (`compiler/tests/run/probes/`): a 5,000-byte error arrives whole with its last bytes, exit status 1, for the plain and the erased `main`. The same program built with `--no-hidden-alloc` ends in `…` at the documented length. An existing probe or golden of `main`'s `Err` line must not move.

**Stops.** The builder items cannot be resolved for the entry without an interpolation in the program in a way that fits mono's existing requests; the freestanding profile has no `main_status` path to keep; any golden moves other than a pin of this unit.

**Gate.** `compiler/tests/run.py --only seed,units,golden,subset,fixture_whitespace,std,comments,mono,programs,docs`; `tools/battery.sh citations`. The freestanding suite and the corpus gate are the server's.

Workaround until it lands (sawos uses it): `main -> Int`, printing the error itself.
