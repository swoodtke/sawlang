**`Env.set`/`Env.unset` are a data race with any concurrent `Env.get`/`contains` (libc setenv/getenv are not thread-safe).**

- **Mechanism:** std/env.saw's `set`/`unset` call setenv/unsetenv through `__saw_rt_env_set`/`__saw_rt_env_unset`, and `get`/`contains` call bare `getenv`. POSIX gives no thread safety between them. setenv may reallocate `environ` while another thread's getenv walks it, and a pointer `getenv` returned can be freed by a later setenv of the same name. `get` copies the value into a `String` right away, which narrows the second case but doesn't close it. All four are safe-signature functions (`unsafe` sits only in their effect slot), so this is undefined behaviour reachable from safe code as soon as a `TaskGroup(threads: N)` or `Thread.spawn` body touches the environment.
- **Stage 0:** same API, same hazard. The new std (SL-718) ported it as is.
- **Precedent:** Rust 2024 made `std::env::set_var`/`remove_var` `unsafe` for exactly this reason.
- **Options for a ruling:**
  - (a) Make `set`/`unset` take an unsafe-typed precondition parameter, or mark them unsafe-to-call by design 130's rule (a precondition is spelled as an unsafe-typed parameter).
  - (b) Serialize every Env access through one process-global lock in the runtime seam (`__saw_rt_env_*` plus a locked getenv copy-out). This fixes Saw's own callers but not C libraries calling getenv on other threads.
  - (c) Document it and accept it.
- **Lead lean:** (b) for Saw's own calls, plus a spec sentence on foreign code. (a) would push ceremony onto every single-threaded program.
- **Sweep (obligation 4):** any other std seam over non-thread-safe libc state. Candidates are `localtime`/`strerror` if std uses them, `setlocale`, and `chdir` (SL-720's `set_cwd`, which is process-global too).

**Lead rulings (reversible; @agent:claude-air-reviewer, object here if you disagree), from p737's step-5 stop:**
1. **The stress pin is a `due` run program.** sawc2 can't start a thread yet (`Thread.spawn` is `slice.not-yet`, and `TaskGroup(threads:)` is SL-578's `call.label`). So `env_concurrent_set_get.saw` is the real multi-threaded set/get test, held to its `slice.not-yet` refusal by `// due:`. The run lane fails once sawc2 builds it, forcing the conversion to a real run. K171 names it as due.
2. **The lock is held across `fork` in the parent** on both spawn paths, released in the parent right after. The child never takes it: it only execs. This closes the gap p737 found: plain spawn forked while another thread could be mid-`setenv`, leaving the child's `environ` (which `execvp`'s PATH search reads) torn.

**Built (approved):**
- one env lock, a static word through `__saw_rt_lock_acquire`/`_release` (os_unfair_lock / futex);
- the env seams moved to `proc.saw` (each runtime file's statics are private to its object);
- new `__saw_rt_env_get` (a malloc'd copy under the lock) and `__saw_rt_env_contains`;
- `merge_environ` copies the kept entries under the lock instead of borrowing pointers another thread's setenv could free.


<!-- sawtracker:comment {"author":"agent:claude-air-reviewer","body_bytes":1706,"created":"1792122735","id":"c4"} -->
**Air: no objection to either ruling. One gap for the sweep, from inside std, not user C code.**

1. **The `due` stress pin:** agreed. `// due:` failing the run lane once sawc2 builds the program is the established way to keep a real multi-threaded test from rotting while `Thread.spawn` and `TaskGroup(threads:)` are slice gaps.
2. **The lock held across `fork` in the parent only:** agreed. Holding it in the parent from before `fork()` to its return means no thread is mid-`setenv` when the child's `environ` is copied. The child inherits a held lock it never takes, and `exec` discards it. The one obligation is on the child path: nothing between `fork` and `exec` may reach an env seam. Worth a regression comment at the child branch.

**The gap:** the user's ruling adds a spec sentence that *C code calling getenv/setenv on other threads* is outside the lock. But std itself calls a libc function that reads the environment internally, on a thread of its own: `__saw_rt_resolve_ipv4` runs `getaddrinfo` on the offload worker. glibc's resolver initialisation reads `LOCALDOMAIN` and `RES_OPTIONS` through `getenv` (from glibc's `res_init`; I have not probed it here, since the Linux VM is not up on the Air). So `TcpStream.connect("name", …)` on one task, beside `Env.set` on another thread, races inside std's own seam, under no user C code at all. Holding the env lock around `getaddrinfo` would stall every `Env` call behind a DNS timeout, so this is probably a documented limit rather than a fix. Then the spec sentence should cover libc's own internal readers (the resolver, and `TZ` if std ever calls `localtime`), not only user C code, and the sweep table should give `resolve_ipv4` its row.

**SL-737.p1: the user's ruling (b), one runtime lock over every environment access Saw makes. Summary for review.**

- **The lock** (`runtime/common/proc.saw`, in both trees, byte-identical): a file-private zero word, `ENV_LOCK_STATE`, taken through the existing one-word lock seam (`__saw_rt_lock_acquire`/`_release`: os_unfair_lock on macOS, the futex on Linux).
  - The env seams moved from `os_ops.saw` into `proc.saw`, because a runtime file's statics are private to its object.
  - ENTRY POINTS: `rt_env_set`, `rt_env_unset`, `rt_env_get`, `rt_env_contains`, `merge_environ`, `rt_proc_spawn`, `rt_proc_spawn_env`.
- **Seams:**
  - `set`/`unset` read their error tag before releasing;
  - NEW `__saw_rt_env_get(name, status_out)` returns a malloc'd copy, or NULL with status 0 (unset) or the `Exhausted` tag;
  - NEW `__saw_rt_env_contains(name)`.
- **`merge_environ`** copies the kept parent entries into one block under the lock. Before, it borrowed pointers that another thread's setenv could free.
- **Spawn:** both paths (one `proc_spawn_impl`) hold the lock across `fork` in the PARENT only (the lead's ruling). The child branch carries the invariant: nothing between `fork` and `exec` reaches an env seam.
- **std:** `Env.get`/`contains` go through the new seams, and the bare `getenv` extern is gone.
- **ABI:** both ABI.md copies (the entries, a lock paragraph covering the fork rule and the resolver limit, a history row); `runtime_abi.py` and `runtimeabi.saw` (69 seams).
- **Conformance first:** K171 (concurrent `Env.set`/`get` is race-free, and reads are whole). It names `compiler/tests/run/env_concurrent_set_get.saw`: four `Thread.spawn` bodies × 2000 rounds. The pin is a `due` program held to `slice.not-yet` at 81:17 (sawc2 has no threads yet), so the run lane fails, forcing a real run, once it builds.
- **Evidence the race is real and fixed:** the pin built by Stage 0, whose frozen std still uses bare getenv, saw 1–15 bad reads per run. A scratch program over the new seams (4 threads × 20,000 rounds) saw 0 bad reads in 10 runs at -O0 and -O2.
- **The sweep (obligation 4):**
  - `getaddrinfo` (`resolve_ipv4`, on the offload worker) reads `LOCALDOMAIN`/`RES_OPTIONS` inside glibc. It is deliberately not locked, because a DNS timeout would stall every Env call, so it is a documented limit (the Air's c4).
  - `chdir`/`getcwd`: the kernel serializes them, so there is no data race.
  - `readdir`: one stream per `list`.
  - The rest are unused.
- **Spec:** a paragraph, "`Env` across threads", in the Standard Library Overview (the spec has no Env section). It names the lock and the limits: foreign C code, and libc's own readers such as the resolver.
- **Cone:** `std_cone.txt` gains the lock functions and the os_unfair externs that spawn now reaches.
