## Description

Measured Sep 10 2026 on the sawtracker server itself (`src/main.saw` plus five
sibling modules — app/common/http/model/store — 98 KB of Saw, no
`--module-path` flags), host arm64 (M4, 16 cores), main at aa3d3e6b, warm
`.build/rt/` and warm `.build/stdcache/`. Baseline reproduced the user's
report: **1 m 51.9 s user** for one binary.

Python/native ratio).

**80% of the compile is one LLVM call.** The Python compiler is 17% of it.

## Where the back-end time goes

The emitted module is 2,015 functions / 31.7 MB of optimized IR. Twelve
compiler-SYNTHESIZED functions hold 61% of the IR lines and **94% of the
back-end time**:

    emit_object, full module                    93.5 s
    emit_object, same module with those 12
      function bodies replaced by `unreachable`  5.4 s

They are the coroutine transform's frame bodies:

    30,727 IR lines / 5,394 blocks  __Frame_mutate_patch_resume
    23,948                          __Frame_open_store_resume
    22,283                          __Frame_mutate_resume
    22,210                          __Frame_run_store_resume
    22,107                          __Frame_response_resume
    21,600                          __Frame_dispatch_resume
    20,381                          __Frame_run_resume
    19,752 / 3,509 blocks           __vtdtor$__Frame_run_store
    11,947                          __Frame_serve_resume
    10,650                          __Frame_main_resume
    10,472                          __vtdtor$__Frame_main
     7,417                          __Frame_read_request_resume

The cost is NOT per-block quadratic — the blocks are tiny (median 3
instructions; `__Frame_mutate_patch_resume` is 19,940 instructions spread over
5,394 blocks, largest block 794). It is a per-region cost paid across a
pathologically fragmented CFG. `llc -O2 -time-passes` on one isolated frame
body:

    50.0%  Machine Instruction Scheduler
    18.2%  AArch64 Instruction Selection
     4.5%  PostRA Machine Instruction Scheduler
     3.7%  Machine code sinking
     2.8%  Greedy Register Allocator

Register allocation is NOT the bottleneck: `-regalloc=fast|basic|greedy` all
time the same. The Machine Instruction Scheduler is, and it is off at codegen
opt level 0 — which is why the same module emits in 7.6 s at level 0 versus
94.3 s at level 2.

The IR optimizer is not the cause either. It nearly quadruples the block count
of these functions by inlining into them (1,498 -> 5,394 blocks on
`__Frame_mutate_patch_resume`), but emitting the UNOPTIMIZED module still costs
79.3 s. The size is inherent to the transform's output, not to O1.

    emit_object on the OPTIMIZED module:   opt=0  7.6 s | opt=1 93.1 | opt=2 94.3 | opt=3 95.4
    emit_object on the UNOPTIMIZED module: opt=0 12.4 s | opt=1 82.9 | opt=2 79.3 | opt=3 78.7

## Python hotspots (cProfile, cumulative — 422 M calls / 248 s profiled)

The Python side is only ~17% of the compile, and inside it the shape is:

* `admit_declarations` is 73% of the front half. Its two `check_module` calls
  on the entry module cost 58.8 s of the 62.0 s that ALL 14 `check_module`
  calls cost under profile — the six user modules and the entry module
  together are the other 5%. It re-checks the whole entry module, spliced
  monomorphized instances included, twice (`for attempt in range(2)`).
* One namespace walk dominates call volume: `_lookup_type_alias_deep` runs
  **19,986,260 times from 243,542 root calls** — 82 namespace visits per
  lookup — because the deep-lookup family re-walks the import graph once per
  PATH rather than once per NODE. With `imported_search_sources` (40.8 M
  calls), `imported_search_namespaces` (39.9 M), `_lookup_type` (21.5 M),
  `lookup_type_alias` (20.1 M) and `resolve_type_identity` (21.2 M) that
  cluster is ~145 M calls and 18% of profiled Python time.
* `copy_tier` / `member_copy_tier` / `is_trivially_copyable` are what call it:
  every struct field's copy tier does a fresh deep alias lookup.

## SL-124 / DF-168b verdict: NOT the cost here

The standing hypothesis is that the place-lowering re-entry re-checks std for
every program. The re-entry is real and std IS re-type-checked on it —
`_prepare_codegen` recurses with `builtins=None`, so `build_builtin_namespace`
runs again over the place-lowered std AST, which the design-168 `.build/stdcache/`
blob cannot serve because that AST has been mutated. But it costs **0.69 s of
122 s (0.6%)**. std is NOT re-lexed or re-parsed (the `parsed=` hand-off keeps
the ASTs), and it is NOT repeated per module — once per program, once more on
the re-entry. Fixing SL-124 as stated would win under 1% of this compile.

The re-entry's real cost is that it re-runs `check_module` for all six user
modules a second time (~0.6 s) and, far more, that `admit_declarations` then
re-checks the entry module twice more (12.8 s).

## What this says

Ranked by measured headroom on this workload:

1. The coroutine transform emits frame bodies that LLVM's back end cannot
   process at a sane rate. 88 of 93 back-end seconds are 12 functions. Any
   fix that makes `__Frame_*_resume` smaller or splits it — outlining per
   state, or emitting a table-driven frame destructor instead of a
   3,509-block `__vtdtor$` — attacks 80% of the compile. This is design work,
   not a patch.
2. Emitting the module in parallel would cap the compile at its largest single
   function (~7.7 s isolated) instead of the sum. Measured ceiling: back end
   ~93 s -> ~13 s, whole compile ~112 s -> ~35 s.
3. `-O0` does not currently buy a fast build: it skips the IR pipeline and then
   runs the back end at LLVM codegen level 2 anyway (`_make_target_machine`
   never passes `opt=`, and `codegen/core.py:152` records that as deliberate).
   Routing the codegen level through the `-O` funnel makes `-O0` a real debug
   build — measured 79.3 s -> 12.4 s on the emit phase — and changes no other
   level's output.
4. The deep-lookup path-vs-node walk is a small absolute win here (the whole
   front half is 17.5 s) but is paid by every compile in the test suite, where
   the front half IS the compile.

Prototypes for 3 and 4 exist with A/B numbers; filed separately for the user
to rule on. Nothing here is proposed for merge by this issue.

## Phase 2 — prototypes, measured

Two prototypes on branch `worktree-agent-a0234f2558fbb0f13`, one commit each.
NOT submitted as a patch; the user rules on what proceeds.

All numbers are median user CPU. The A/B pairs are INTERLEAVED (one run each
side per round, alternating) in one tree, so drift from another agent's suite
hits both sides equally; the absolute baselines were taken in a verified quiet
window. Clean baseline for the workload: **115.23 s** median user (113.2 /
115.2 / 116.7), which matches the user's reported 118.2 s.

### Candidate A — the codegen opt level joins the `-O` funnel (ea0515c4)

`_make_target_machine` never passed `opt=`, so every level ran LLVM's back end
at llvmlite's default codegen level 2 — including `-O0`, which had already
declined the IR pipeline. `OPTIMIZATION_LEVELS` gains a fourth field; `-O0`
maps to 0, every other level stays at 2.

| workload | `-O0` today | `-O0` with A | speedup |
|---|---|---|---|
| sawtracker | 104.49 s | 35.07 s | **2.98x** |
| irdet | 14.45 s | 6.62 s | **2.18x** |

Binary grows 2.81 -> 6.38 MB on the tracker (this is what `-O0` means).
The DEFAULT level is untouched — verified, not merely argued: objects built
with `opt=` unspecified and with `opt=2` explicit are byte-identical across 60
examples.

Correctness: full suite 2439 passed / 11 xfailed (all pre-existing and cited);
`irdet --all` byte-identical IR across 1514 examples; **105 examples compiled
and RUN at both `-O0` and the default level produced identical exit code,
stdout and stderr, 0 diverged** (60+ of them coroutine tests, the exact code
shape whose instruction selection changes).

That last check exists because nothing in the tree had it: every `-O0` lane in
the battery (`ircontract`, `test_debug_info`, `test_stable_type_id`) reads
`--emit-ir` TEXT, which this switch cannot reach, and no example carried
`// COMPILE-FLAGS: -O0`. The commit 3ed2aca5 adds
`examples/optimization_level_o0_preserves_semantics.saw` — the missing twin of
the `-O2`/`-Os`/`-Oz` trio, and the only one that runs the binary.

### Candidate B — dedup the namespace deep-lookup walk (662d0ecd)

`_lookup_struct_deep` / `_lookup_type_alias_deep` / `_lookup_enum_deep` re-walk
the import graph once per PATH rather than once per NODE. A `_seen` set over
namespace identity makes the walk linear in the graph. Skipping a namespace
already visited returns the same answer it returned the first time — the walk
only continues past a namespace that answered None — so this is
semantics-preserving by construction. (It also terminates on an import cycle,
which the recursion never guarded against.)

| workload | before | after | delta |
|---|---|---|---|
| sawtracker | 128.99 s | 121.60 s | **-7.40 s (-5.7%)** |
| irdet | 21.86 s | 21.86 s | **0.00 s (0.0%)** |

The split is the point: the win scales with import-graph DEPTH, so a
six-module app over std gets 5.7% and a shallow program gets nothing and pays
nothing. Consistent across all 3 rounds (-7.4 / -8.0 / -9.6 s).

Correctness: optimized IR byte-identical across 60 module/generic/trait-heavy
examples; full suite green; `irdet --all` clean over 1514 examples — which is
the gate that matters here, since this changes an iteration order.

### Measured but NOT proposed

* **`-enable-misched=false`** at the default level: ~25% off the back end
  (137.4 -> 105.2 s on the saved module, measured under load, so treat as a
  range). Rejected — it degrades scheduling on every shipped binary to buy a
  quarter of the compile, and `-O0` already buys 3x for the dev loop.
* **`cold` on the panic path**: killed by measurement before prototyping. Panic
  blocks are only 9.8% of blocks and 5.3% of instructions in the worst frame
  body; the fragmentation is real control flow, not check overhead.
* **Keeping the inliner out of the frame bodies**: worth only ~15% (the
  unoptimized module still costs 79.3 s), so not the lever.

### The mechanism behind the giants, now named

Of the 2,163 calls in the UNOPTIMIZED `__Frame_mutate_patch_resume` body,
**835 (39%) are deinit/drop/release** — 363 of them `Slot<String>.clear` alone.
The source function is ~200 lines with ~20 early exits over ~30 live locals,
and deterministic destruction emits a drop sequence at each exit for each live
slot. That product is what makes a 200-line function a 13,411-line IR body
before optimization, and a 5,394-block one after. A shared per-frame cleanup
epilogue keyed on the state tag — `__Frame_mutate_patch_release` already exists
and is called 29 times, so the shape is there — would attack the 39% directly,
and the back-end cost is superlinear in what it removes.

Nothing in this comment is proposed for merge.

## Correction — two claims in this issue were wrong, superseded by SL-232

Both came from measuring the whole module and ONE isolated function, before
the per-function costs were measured. Corrected here rather than left to
stand.

**1. "Emitting the module in parallel would cap the compile at its largest
single function (~7.7 s isolated) ... back end ~93 s -> ~13 s, whole compile
~112 s -> ~35 s."** WRONG on the magnitude. The function I isolated for that
estimate, `__Frame_mutate_patch_resume`, is one of the CHEAP ones. Measuring
all twelve giants individually (each = module emit with only that body
present, minus the 0.28 s all-stubbed floor):

    30.67s  __Frame_run_store_resume        3.65s  __Frame_run_resume
    22.22s  __Frame_response_resume         2.20s  __Frame_open_store_resume
    18.33s  __Frame_dispatch_resume         2.20s  __Frame_mutate_resume
     6.11s  __Frame_serve_resume            0.69s  __Frame_main_resume
     3.95s  __Frame_mutate_patch_resume     0.12s  __vtdtor$__Frame_run_store
                                            0.05s  __vtdtor$__Frame_main
                                            0.05s  __Frame_read_request_resume

The largest single function is **30.7 s**, not 7.7 s. So perfectly parallel
emission floors at ~31 s of WALL time, a 3x on the back end rather than 7x.

And the sum of the twelve nets is **90.2 s against 93.5 s for the whole
module** — the cost is ADDITIVE, not module-wide superlinear. Splitting
therefore buys wall-clock only; total CPU is unchanged. The user's report was
1 m 59.9 s wall / 1 m 58.2 s user, so this would help the wall number and not
the CPU one.

**2. "50.0% Machine Instruction Scheduler"** — that `-time-passes` run also
profiled `__Frame_mutate_patch_resume`, a cheap function. On the actually
expensive `__Frame_run_store_resume` the profile is Greedy Register Allocator
28.6%, Live Interval Analysis 18.7%, Early Machine LICM 17.0%, Machine
Instruction Scheduler 14.8%. The dominant cluster is register allocation and
live-range analysis, not scheduling.

The consequence matters: a hypothesis built on the scheduler pointed at basic
block SIZE, and that hypothesis is now tested and dead — splitting every
oversized block into <=400-instruction chunks changed the module's emit time
by -3.3%, i.e. not at all. The real predictor is the number of distinct
coroutine frame slots, roughly quadratically. SL-232 has that measurement and
the fix direction (slot coloring).

Everything else in this issue stands: the phase table, the 80% back-end
share, the 94%-in-12-functions split, the SL-124 verdict, and both
prototypes' A/B numbers.
