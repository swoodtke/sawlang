**Dogfood SL-1170's native inputs with a real C library: `libs/lz4`, then an mbedTLS TLS client example.** It follows SL-1170's design §8 ("Dogfood").

**1. `libs/lz4`** (this issue's first unit):
- **Vendored:** lz4, BSD-2: `lz4.c`, `lz4.h` and its LICENSE, pinned to one release with its SHA recorded. Since 1.9.4 it has an `LZ4_FREESTANDING` mode.
- **A safe Saw API:**
  - `compress(&Data) -> Result<Data, Lz4Error>` and `decompress(&Data, max: Int) -> Result<Data, Lz4Error>`;
  - the buffers cross as `UnsafePointer` inside small `unsafe` helpers;
  - every lz4 error code becomes a case, never hidden.
- **Tests:** `blade test` round-trips empty input, small input, incompressible input, a large buffer, and a corrupt stream (refused).
- **Freestanding:** an image build with `[native.riscv32-unknown-none-elf] defines = ["LZ4_FREESTANDING=1"]` proves the cross-compile. A freestanding case round-trip is a stretch goal.
- **The point:** the point is what the package exposes about Blade and sawc. Every surprise is recorded.

**2. The mbedTLS TLS client:** a later unit, sketched in the design.

**Lead's note with p1 (Nov 25): unit 1, `libs/lz4`.** The surprise log is at `.build/scratch/p1182/surprises.md`.

- **Vendored:** lz4 1.10.0 from `https://github.com/lz4/lz4/archive/refs/tags/v1.10.0.tar.gz`, SHA-256 `537512904744b35e232912055ccf8ec66d768639ff3abe5788d90d792ec5f48b`. `lz4.c`, `lz4.h` and the LICENSE are unmodified, and `vendor/README.md` records the per-file hashes.
- **`Saw.toml`:** `[native] c-sources` and `include-dirs`. `[native.riscv32-unknown-none-elf]` defines `LZ4_FREESTANDING=1`, `LZ4_memcpy`/`memmove`/`memset` as the `__builtin_` names (Blade refuses function-like defines, so these are object-like aliases), and `LZ4_STATIC_LINKING_ONLY_DISABLE_MEMORY_ALLOCATION`.
- **The API:**
  - `Lz4Error` has the cases `InputTooLarge(size:)`, `InvalidLimit(value:)`, `CompressFailed`, `Malformed(code:)` and `Alloc(e:)`. lz4 gives one negative code for corrupt data and for output that is too small, so those are one case.
  - The lead's fix: `decompress` reported an input past `Int32.max` as `Malformed(code: -1)`, a made-up code that could collide with lz4's own. It is now `InputTooLarge(size:)`, and the doc says so.
- **The tests:** `round_trip` and `refusals` both pass (re-run by the lead after the fix).
- **The lane:**
  - `lz4` is in `LIBRARIES`;
  - `check_lz4_image` builds `libs/lz4/image` for riscv32 and boots it under `qemu-system-riscv32`, requiring `fs check lz4_shrinks/lz4_length/lz4_bytes=1` and `fs done lz4_image ok`;
  - it skips, saying so, when the target record or QEMU is absent;
  - the whole `tools/blade_lane.py` passes.
- **Filed from the surprise log:**
  - `blade test` hides a test's compile errors;
  - `Data`'s spare-room API is package-private, which costs one copy per call;
  - there is no runtime-provider package outside `tests/freestanding/` (the image fixture reaches into that tree).

  The log's other items are by design (function-like defines, the safe-over-`unsafe` layering) or the agent's own slips.

Requested changes on patch SL-1182.p1 (revision 1) (its test run was cancelled)

**Changes requested, revision 1.** The vendored code is exactly upstream's, and the safe API is sound at every boundary I probed. There are four things to fix: `decompress` returns a shortened output for some truncated blocks with no error, the freestanding support covers riscv32 only, compression needs about 16.5 KB of stack on a freestanding thread, and the lane passes when the image build writes no ELF. My probes are in `.build/scratch/air-review/sl1182_p1/` on my machine.

**1. A truncated block can decompress to `Ok` with fewer bytes.** An LZ4 block may end after any run of literals, so a block cut at such a point is still a valid, shorter block. `decompress` never compares the output length with anything, so a caller who passes the recorded length, as the README says ("Keep the length beside the block and pass it as `max_size`"), gets a short result and no error.

I decompressed every prefix of three compressed 3,000-byte texts, with the original length as `max_size`:
- **seed 1:** a 1,912-byte block; 47 prefixes come back `Ok` and short, the first at 15 bytes;
- **seed 2:** a 1,911-byte block; 47 `Ok` and short, the first at 9 bytes;
- **seed 3:** a 2,040-byte block; 48 `Ok` and short, the first at 32 bytes.

No prefix decodes to the full length, and the rest are refused. The first half of a 2,300-byte text's block gives `Ok(31 bytes)`.

The doc says `decompress` returns "`Err(Malformed)` for a corrupt block", and `refusals.saw` says "A block cut short" is refused. That holds only at some cut points; `packed.len() - 3` happens to be one of them. Please make the length part of the contract. One way is an exact form, for example `decompress(&Data, size:)`, which returns an error of its own unless the output is exactly `size` bytes; the README's pattern already has the size. The other is to keep `max_size` as a bound and say plainly, in the doc and the README, that a damaged block can decode short, so the caller compares lengths. Either way, add a test with a prefix that decodes short.

**2. The freestanding table covers riscv32 only.** sawc has records for three bare-metal targets. I copied `image/` and built it for the other two:
- **`aarch64-unknown-none-elf`:** `lz4.c` fails to compile, with `fatal error: 'stdlib.h' file not found`.
- **`xtensa-esp-unknown-elf`:** Espressif's clang has libc headers, so it compiles, but the link fails with `ld.lld: error: undefined symbol: __assert_func`.

With the same five defines under a `[native.aarch64-unknown-none-elf]` and a `[native.xtensa-esp-unknown-elf]` section (a copy of the package):
- **arm64** builds, boots under `qemu-system-aarch64` (the freestanding suite's flags) and prints all four `fs check`/`fs done` lines;
- **the ESP32-S3** image builds; I didn't boot it.

Please give each bare-metal triple its table. If the package is meant for riscv32 alone, say so in the README.

**3. A compression needs about 16.5 KB of stack.** lz4 is built without heap mode (`LZ4_HEAPMODE 0`), so `LZ4_compress_default` keeps its 16 KB `LZ4_stream_t` on the stack. In the riscv32 object Blade built for the image, `LZ4_compress_default` reserves 0x100 + 0x4000 − 0xd0 = 16,432 bytes and calls `LZ4_compress_fast_extState`, which takes 96 more.
- **The test images** reserve 64 KiB of stack, so they pass.
- **A freestanding thread with a 16 KiB stack** would overflow, and without a guard nothing reports it.

lz4 exports the way out: allocate `LZ4_sizeofState()` bytes on 8-byte boundaries and call `LZ4_compress_fast_extState(state, src, dst, size, bound, 1)`. `compress_block` already owns one heap scratch buffer and can own the state the same way. Otherwise, the README should state the stack requirement.

**4. `check_lz4_image` passes when the build writes no ELF.** The boot is skipped on `if qemu is None or not os.path.exists(elf)`, so a missing ELF looks like a missing QEMU. I stubbed `blade_ok` to "succeed" without output and pointed `shutil.which` at a QEMU, so nothing was built or booted. The check printed `blade: no qemu-system-riscv32: the lz4 image is built and not booted` and returned (`probe_lane_missing_elf.py`). `check_blade_out_dir_and_linker_script` raises `Failure` for a missing `fsblade.elf` ("--out-dir left no …"). Please do the same here, and keep the skip for a QEMU that is absent.

**Not this patch's:** `blade test` in `libs/lz4` prints `warning: (arm64) …/libs/lz4/.build/host/tests/Users/…/libs/lz4/.build/host/native/lz4/…-lz4.o unable to open object file: No such file or directory`, twice. The object's path reaches the test link with the test directory prefixed, so the C half's debug info is lost under `blade test`. That comes from SL-1170's native support; could you file it with the other surprises?

**What holds:**
- **The vendored code.** The tarball's SHA-256 is `537512904744b35e…f48b`, as recorded. `lz4.c`, `lz4.h` and `LICENSE` are byte-identical to the tarball's `lib/` (the library's BSD-2 licence, not the top-level one), and their hashes match `vendor/README.md`.
- **The API's boundaries:**
  - each size is range-checked before its `Int32` cast, and the bound for `MAX_INPUT_SIZE` (2,122,219,150) fits `Int32`;
  - each scratch buffer is freed on every path;
  - a slice cut from the middle of a larger `Data` round-trips, so `byte_ptr` honours the window's offset;
  - an empty window compresses to one byte and decodes back to nothing;
  - limit `n - 1` is refused, and `n` and `n + 1000` both return `n` bytes;
  - limits `Int32.max + 1` and `Int.min` are `InvalidLimit`, and 64 bytes of `0xFF` are `Malformed`.
- **`blade test`** passes both tests.
- **The riscv32 image** builds (a 37,484-byte sosimg), boots under `qemu-system-riscv32`, prints the four expected lines and exits at once.
