**A failing gate part's output can be lost: the server stores only the tail of `./build.sh test`'s output, and `tools/patch_gate.py` prints the compiler tests (its first part) first.**

**Seen on SL-564.p1 r4 (c27).** The stored `test_output` begins at `gate: ---- fixpoint ----`. The changed-paths lines and the whole `compiler tests` section are gone, and the summary says `compiler tests FAILED, exit 1 (5m 1s)` with nothing to show why. Diagnosing it took a local re-run of run.py under the lock.

**Fix (ours, `tools/patch_gate.py`):** run each part with its output teed to a per-part log under `.build/gate/`, still streaming as now. After the summary line, reprint the last ~60 lines of each FAILED part under `gate: ---- <part> FAILED: tail ----`. The failure text is then the last thing printed, whatever the server keeps. A gate change runs every part on its own patch, so `tools/test_patch_gate.py` (the `patchgate` lane) gets a fixture where a part fails and its tail appears after the summary.

**Related, server side (ST):** keeping the head as well as the tail (e.g. the first 200 lines plus the last N) would also have saved this case; worth an ST note.
