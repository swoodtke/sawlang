**sawc2's `try!` panic never renders the error: it always prints the bare "try! failed".** Found by SL-716 (the Data port): `alloc_data_push_forced_panics_named.saw` moves to `wrong`, with sawc2 printing `panic at …:28: try! failed` where Stage 0 and the spec print `… try! failed: allocation of 32 bytes (align 1) failed`.

**The spec** (LANGUAGE_SPEC, the panic list): "`try!` on an `Err` panics with "try! failed: `error`", rendering the error it was handed … The error goes through the allocation-free format path, so the message survives an exhausted allocator and works freestanding; an erased `Box<any Error>` renders through its vtable, as `"{e}"` does. `E` is not bounded `Printable` at a `try!`, so an error type with no conformance keeps the bare "try! failed"."

**sawc2:** `compiler/llvm/src/prims.saw` emits the constant `"try! failed"` with no error. Lowering it means: at a `try!`, when `E` meets `Printable`, format the error through the same stack-scratch, allocation-free path `{}` format arguments use (design 137), and append it after `": "`; otherwise keep the bare text. The `Box<any Error>` case dispatches through the vtable and so waits on SL-713. Sweep the other panics with rendered operands (`opt!`'s has none; integer `as` out of range renders the value, design 170) for the same gap (obligation 4).

**Pins:** the spec's `reserve()` example as a run program, an error type with no `Printable` keeping the bare text, the corpus rows that move (starting with `alloc_data_push_forced_panics_named`), and the corpusdiff baseline.
