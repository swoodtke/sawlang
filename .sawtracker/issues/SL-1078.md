## Description

**A freestanding case for `@section` placements.** SL-934 makes a placed function or static survive code generation and the optimizer whether or not anything reaches it, and pins that on the host (the run lane's `check_placed_symbols`) and in objects. Nothing boots an image and reads a placed table from the address the linker gave its section, which is the use the attribute exists for (a driver table, an init-call list, a boot stub).

**Depends on SL-934 having merged.** Don't start before it.

**The reviewer's measurement (SL-934 review, Nov 12), which shapes this unit:** no `KEEP` is needed in a link script. The objects carry the retain flag on the placed sections (`AXR` on a placed text section, `WAR` on a placed data section, on riscv32, aarch64 and xtensa-esp), and `ld.lld --gc-sections -e _start` with no script keeps a placed function and a placed static for riscv32 and aarch64, where v0.22.0's objects lose both.

**Goal:** one case in `tests/freestanding/` on every row that places two or three statics in a named section from Saw, never names them from code, and at run time walks the section between two linker-defined symbols and prints what it finds.

**Read first:** `tests/freestanding/README.md`; `tools/freestanding_runner.py` (a case's description, the per-row link, `link_address.saw` as the model of a case that reads a linker-provided address); each row's `link.ld` under `tests/freestanding/hal/`; LANGUAGE_SPEC.md on `@section` and `@export`; how a Saw program reads a linker symbol's address (search the cases for an `extern` static or an `@export`ed symbol the script defines; if there is no way to name a linker-defined symbol from Saw without C, the walk's two bounds come from a few lines in the row's existing C or assembly, and the case says so).

**Implementation.**
1. Step 0: by hand on one row, build a program with two `@section(".saw_table")` statics nothing reaches, link it with the row's script unchanged, and read the ELF's section table and symbols. Record whether the section is present, where it landed, and whether the script needs an output-section rule to give it start and end symbols. Do the same on the xtensa row (literals precede text there; a data section should be unaffected, but record it).
2. Add the output section and its bounding symbols to each row's `link.ld` only if step 0 shows the default placement doesn't give a walkable range. No `KEEP` unless step 0 shows a row drops the section without it, in which case STOP and report: that contradicts the reviewer's measurement.
3. The case: statics of one small struct type placed in the section; `main` walks from start to end and prints each entry; EXPECT lines hold the count and the values. Unsafe-typed pointer reads are confined to one small `unsafe` helper.
4. A second assertion in the same case or its twin: a placed FUNCTION nothing calls is present in the image (the runner reads the ELF's symbols if it has a route for that; if not, leave the function half to the run lane's check and say so).

**Expected outcomes.** The suite's count rises by one case per row; nothing else moves. No compiler change: a failure here on a merged SL-934 is a finding to report, not to work around.

**Tests and gate.** `tools/test_freestanding_runner.py`, `tools/freestanding_runner.py`, `compiler/tests/run.py --only seed,fixture_whitespace,comments`, `tools/battery.sh citations`, under the suite lock.

Approved patch SL-1078.p1 (revision 1)

**Approved (rev 1).** The case boots a placed table on every row, and it would go red if the placements stopped being kept.

**Run on the patch applied to main (`bcfc0e808`), stage 2 built**
- `tools/freestanding_runner.py section_walk link_address`: both pass on riscv32, arm64 and the ESP32-S3 (6 passed, three architectures).
- The runner's self-test, `run.py --only comments,fixture_whitespace` and the grammar corpus on the new case: green.

**Does it hold the retain flag? Yes, on the two rows I tried.** In the object the four `saw_table` input sections are `WAR`. I cleared the retain bit on them in a copy and linked each with the row's own script and `--gc-sections`, as the runner does:

| row | flag kept | flag cleared |
|---|---|---|
| riscv32 (Homebrew lld) | `saw_table`, 32 bytes, both bounds defined | no `saw_table` at all, the bounds undefined (so they read null) |
| ESP32-S3 (Espressif's lld, the script's new rule) | 32 bytes | the four inputs are collected; the output section is 0 bytes and the bounds are equal |

Either way the walk counts 0 where it expects 4, so the case is red without the flag, with no `KEEP` in any script. That is the measurement of SL-934's review holding on a booted image.

**Read.** The Xtensa rule sits in flash beside the read-only data and has no `KEEP`. The two weak bounds in `support.c` read null in every other case's link. The unsafe reads are in two small helpers.

**One thing to decide, not for this patch.** The expected lines hold the entries in the order the object lists them (`FIRST`, `SECOND`, the exported one, `THIRD`), and the spec's `@section` paragraph promises no order. An init-call list is the use where order matters. If declaration order within a module is meant as a promise, the spec should say so and this case is its pin; if it is not, the lines could hold the set alone, which the two checks at the end already do.
