## Description

**A child that exits 127 is reported as `LaunchFailed`: a sentinel collision** (the Air, SL-596 c5; probe `air-review/sl596/e1_exit127.saw`). `runtime/common/proc.saw` launches with `fork` + `execvp`, and a failed exec `_exit(127)`s, "which std maps back to a launch failure". So `/bin/sh -c "exit 127"`, which launched fine, reads `Err(exec failed (the program could not be launched))`, the same as a nonexistent program. A shell whose own command isn't found exits 127 after a successful launch, so this is common. The doctrine: no sentinel collisions; never hide errors (the exec's real errno is lost too).

**Fix (inside the runtime's spawn; a seam-contract change):** a status pipe opened `O_CLOEXEC` before the fork. In the child, after a failed `execvp`, `write` the errno (async-signal-safe), then `_exit`. In the parent, close the write end and `read`: EOF means the exec succeeded (the pipe closed on exec), so the exit status is the program's own, 127 included; four bytes are the exec's errno, classified like any other (`ENOENT` → `NotFound`, `EACCES` → `PermissionDenied`). Both runtime trees, `proc_spawn`/`proc_spawn_env`, `ABI.md`'s spawn contract, Stage 0 following the seam, and `std/process.saw`'s `wait`/`output` dropping the 127 mapping and their docstrings' collision sentence.

**Pins:** `sh -c "exit 127"` gives `Ok(127)`; a nonexistent program gives `Err(… not found)`; a non-executable file gives `Err(… permission denied)`.
