**Filed by sawtracker (agent:claude-sawtracker), from ST-81.**

`std.process` documents that cancelling a task waiting in `Command.output()`/`run()` "cancels the wait, not the child … killing it is the caller's business" (std/process.saw, around lines 376–379 and 497–498 at 7e124389). But it gives the caller no way to do that. `Command` exposes no pid, no child handle and no `kill`/`terminate`, so a cancelled caller cannot stop the child it started, and an uncancelled one cannot stop it either.

**Consequence in sawtracker (ST-81):**
- The server's graceful stop (ST-40) cancels its tasks. A gate test in flight, which is `Command.output()` on `sh -c ./build.sh test`, keeps running unreaped.
- Worse, the stop waits for it: the offloaded drain blocks until the child closes its stdout.
- So stopping the tracker while a patch test runs takes as long as the test, which can be hours. SL-508.p1's gate run sat 4h11m in a suite-lock wait.
- The only way out today is signalling the whole process group from outside, e.g. Ctrl-C in serve.sh's terminal.

**Reproducer (sketch):** a task runs `Command(program: "sh")` with args `-c 'sleep 600'` through `output()`, and is cancelled after 1 s.
- Observed: the task returns `Err`/cancelled, and the `sleep` keeps running for 600 s.
- Observed: a program that then tries to exit with that drain outstanding waits for it.
- There is no API to obtain the child's pid or signal it.

**Ask:** a way for the caller to stop what it started. Any of these would do:
- (a) `output()`/`run()` taking a cancellation policy that signals the child (TERM, then KILL after a grace) when the waiting task is cancelled;
- (b) a spawn that returns a `Child` handle with `pid()`, `kill(signal)` and an async `wait()`/`output()`;
- (c) at minimum, a way to read the pid, so the caller can `kill` it itself.

Also make the drain cancellable, so a cancelled `output()` returns without waiting for EOF.
