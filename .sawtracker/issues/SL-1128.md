## Description

**A windowed Xtensa row in the freestanding suite: the programs the call0 row runs, built with `--target-features +windowed` for `xtensa-esp-unknown-elf`, booted under Espressif's QEMU.** Requested by the sawos lead (chat m920, Nov 14). The project owner has ruled, in sawos, that its kernel learns to run windowed processes on the ESP32-S3 now (Espressif's radio libraries and the ROM are windowed). sawos's own rule is that no Saw is compiled windowed for a process until this suite has the row; until then its windowed cases are C.

**What is known.**
- The triple's default features are `-windowed,-fp,-loop,-mac16,-bool` (call0), and `--target-features` ADDS to the default on this triple (SL-1067's decision), so `+windowed` is expressible today.
- One probe compiled windowed Saw at v0.23.0: `entry`, `retw.n` and `callx8` are in the output. Nothing has RUN windowed Saw.
- The suite's Xtensa row (SL-1069) boots a flash image linked with the `ld.lld` beside Espressif's clang, with the suite's own start-up code for call0.

**What a row needs that the call0 row does not (to establish by a sweep before any change; none of this is verified):**
- **Window exceptions.** Windowed code takes window overflow and underflow exceptions as calls nest and return; the image's start-up must install the vectors (and set `WINDOWSTART`, `WINDOWBASE`, `PS.WOE`) before the first windowed call. The call0 start-up has none. Where they come from (written for the suite, or the form Espressif's ROM and ESP-IDF use) is the first question.
- **The runtime and std for the feature set.** `sawc --freestanding --runtime` builds the runtime and std's weak helpers for the build's features; whether every seam body, the `shim.c` units and the C the suite links (its `support.c`) are built windowed too, and whether a windowed object may be linked with a call0 one (it may not: the two ABIs do not mix), must be shown. The row builds EVERYTHING windowed.
- **The coroutine transform and the executor.** A suspending function's frame, a task switch and `Thread`-less scheduling under register windows: which freestanding cases suspend, and what the lowering assumes about callee-saved registers. A context switch under windows has to spill the window (as `xthal_window_spill` does); whether any case switches stacks is to find.
- **`setjmp`-like or unwinding assumptions,** `@export` functions called from C, and `extern` C calling back into Saw: each case that crosses the C boundary is listed.

**Proposed shape.** A sweep first (read-only; a Sonnet `sweep` agent): build each freestanding case windowed and say what compiles, what links, what boots and what it prints, with the first failure of each; list what the start-up needs. Then the row as a unit from the sweep's matrix, with a `due` case citing an issue for each gap that is not the row's to close.

**Skip rule.** As the call0 row: the row SKIPS, naming the tool, where Espressif's clang or QEMU is known absent, and FAILS when it cannot tell.

Related: SL-1063 (the Xtensa target), SL-1067, SL-1069, sawos SO-112 and SO-113.

**The sweep is done (lead, Nov 14; a read-only Sonnet sweep; the agent's report, condensed by the lead; every figure has a file under `.build/scratch/p1128/` in the lead's checkout, named in brackets).** Tools: Espressif clang 20.1.1 with its `ld.lld`, QEMU `esp_develop_9.2.2` (`-machine esp32s3`), main's `sawc`.

**Verdict.** Windowed Saw compiles, links and runs on the ESP32-S3 row: all 34 run cases pass, and so does a Blade image, once three things hold. None holds today.

**1. sawc's frame-pointer policy is wrong for windowed Xtensa, and it miscompiles (a compiler defect, filed separately).** sawc puts `"frame-pointer"="non-leaf"` on every function of every target (`Target.frame_pointer`, `compiler/target/src/layout.saw`; applied in `compiler/llvm/src/attributes.saw`). On windowed Xtensa the frame pointer is `a7`, which is also the sixth argument word.
- Espressif's clang then overwrites an incoming `a7` before reading it: 7 cases print wrong values (`int_widths`, `call_convention`, `float_text`, `serialize_int64`, `soft_float`, `soft_float_vectors`, `soft_float_vectors_optimized`). In `check_wide`: `entry a1,208; mov.n a7,a1; ... xor a8,a5,a7`; the "high half" read back is a stack address [`win/int_widths.dis`, `allB2_nonleaf.log`]. Plain C reproduces it with `-mframe-pointer=non-leaf` [`c/fp_clash2_dis.txt`].
- It also wraps calls that pass stack arguments in `movsp`, which raises the Alloca exception (cause 5) once the stack is deep; nothing handles that. `movsp` appears 504 times in 14 of the 34 objects, and in none with the policy `none` [`movsp_nonleaf.txt`, `movsp_fpnone.txt`]. Those 14 pass today only because their stacks never got deep enough.
- With the attribute rewritten to `none` in the emitted IR: 34 of 34 pass [`allB2_none.log`]. `all` cures the clobber and not the `movsp`.

**2. A windowed start-up.** The call0 `hal/xtensa/boot.S` leaves `PS.WOE` 0 and does `callx0 fs_main`, so a windowed image dies at `fs_main`'s `entry` with IllegalInstruction [`mix/boot_hello_mixed.txt`]. What a windowed one needs, found in three stages [`start/boot_win2.S`, a scratch copy]:
- `PS.WOE` set, `callx8` into `fs_main`, the four `fs_*` hooks as windowed bodies (`entry`/`retw`): then `hello` passes, and anything deeper faults at the WindowOverflow8 vector [`allA.log`];
- the six window overflow and underflow vectors at their offsets from `VECBASE`: then the first spill reads its predecessor's stack pointer from `[sp-12]`, finds 0 and faults [`deep/result_B_vectors_nobottom.txt`];
- a valid word at `[sp-12]` below the bottom frame: everything runs.
- The vectors are the architecture's six sequences. Citable sources, nothing copied into the tree: the ESP32-S3 mask ROM's table (instruction for instruction the same [`vec/rom_window_vectors.dis`]); Espressif's toolchain `libgloss.a`, member `window-vectors.o`, section `.WindowVectors.text`, which works when placed at `VECBASE` after `--strip-debug` [`win3_deep.txt`]; the sawos repository's `hal/xtensa-esp32s3/ABI.md` section 5a. Licences of the libgloss object and the ROM ELF: not verified.

**3. Every C and assembly object built windowed.** Espressif's clang has no ABI flag (`-mabi=windowed` is refused); windowed is its DEFAULT, and the row gets call0 only by passing `-target-feature -windowed`. **A call0 object linked with windowed ones draws no diagnostic from `ld.lld`** (ELF flags are equal; there is no ABI marker) and crashes only when the call0 code is reached: `InstrAddrError epc1=0x82...` (the window-increment tag in `a0`), `LoadStoreAddrError`, `StoreProhibited` [`mix/link_mixed.txt`, `allB2_mixsupport.log`].

**What already works.**
- Every case compiles windowed; the five refusal cases give the same diagnostics; std's helpers and the runtime seams are inside the case object and are windowed [`win/summary.txt`].
- No case switches stacks: a coroutine frame is a heap object resumed by an ordinary call, so the suspending cases pass; backtraces are a table, not a frame walk. A task-switch spill (`xthal_window_spill`'s job) is the kernel's concern and no case exercises it.
- **Blade needs no change:** `target-features = "+windowed"` under `[sos.xtensa-esp-unknown-elf]` builds a windowed image that boots and passes [`blade/windowed_result.txt`].
- A scratch deep-recursion case (to 2,000 frames, and an 8-word-argument recursion) passes with the vectors, the bottom-frame word and the policy `none` [`deep/`].

**The row's shape.** A new row beside the call0 one (the start-up, the C flags and the Saw feature string all differ; a second row on one triple needs its own build directory and Blade output directory, which are keyed by triple today): `features: "+windowed"`, the no-atomics variant `-s32c1i,+windowed`, the C arguments with `+windowed` for `support.c`, `atomics.c` and the start-up, a windowed `hal/<row>/boot.S`, the same QEMU arguments, flash base and `link.ld`, the same skip rule. `link_two_objects` built windowed reports `duplicate symbol: __saw_bt_table` [`two/link.txt`]: to look at in the row's unit.

**Not verified:** silicon; the `-kernel` boot; an Alloca handler (none was written: removing the frame pointer is the cure tried); interrupts and level-1 handlers under windows; `+fp` windowed; `--lto`, `--codegen-units`, `--sanitize`; the licences above; whether sawc's own object step with the policy `none` gives the same objects as the rewritten IR did.
