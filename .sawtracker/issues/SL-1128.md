## Description

**A windowed Xtensa row in the freestanding suite: the programs the call0 row runs, built with `--target-features +windowed` for `xtensa-esp-unknown-elf`, booted under Espressif's QEMU.** Requested by the sawos lead (chat m920, Nov 14). The project owner has ruled, in sawos, that its kernel learns to run windowed processes on the ESP32-S3 now (Espressif's radio libraries and the ROM are windowed). sawos's own rule is that no Saw is compiled windowed for a process until this suite has the row; until then its windowed cases are C.

**What is known.**
- The triple's default features are `-windowed,-fp,-loop,-mac16,-bool` (call0), and `--target-features` ADDS to the default on this triple (SL-1067's decision), so `+windowed` is expressible today.
- One probe compiled windowed Saw at v0.23.0: `entry`, `retw.n` and `callx8` are in the output. Nothing has RUN windowed Saw.
- The suite's Xtensa row (SL-1069) boots a flash image linked with the `ld.lld` beside Espressif's clang, with the suite's own start-up code for call0.

**What a row needs that the call0 row does not (to establish by a sweep before any change; none of this is verified):**
- **Window exceptions.** Windowed code takes window overflow and underflow exceptions as calls nest and return; the image's start-up must install the vectors (and set `WINDOWSTART`, `WINDOWBASE`, `PS.WOE`) before the first windowed call. The call0 start-up has none. Where they come from (written for the suite, or the form Espressif's ROM and ESP-IDF use) is the first question.
- **The runtime and std for the feature set.** `sawc --freestanding --runtime` builds the runtime and std's weak helpers for the build's features; whether every seam body, the `shim.c` units and the C the suite links (its `support.c`) are built windowed too, and whether a windowed object may be linked with a call0 one (it may not: the two ABIs do not mix), must be shown. The row builds EVERYTHING windowed.
- **The coroutine transform and the executor.** A suspending function's frame, a task switch and `Thread`-less scheduling under register windows: which freestanding cases suspend, and what the lowering assumes about callee-saved registers. A context switch under windows has to spill the window (as `xthal_window_spill` does); whether any case switches stacks is to find.
- **`setjmp`-like or unwinding assumptions,** `@export` functions called from C, and `extern` C calling back into Saw: each case that crosses the C boundary is listed.

**Proposed shape.** A sweep first (read-only; a Sonnet `sweep` agent): build each freestanding case windowed and say what compiles, what links, what boots and what it prints, with the first failure of each; list what the start-up needs. Then the row as a unit from the sweep's matrix, with a `due` case citing an issue for each gap that is not the row's to close.

**Skip rule.** As the call0 row: the row SKIPS, naming the tool, where Espressif's clang or QEMU is known absent, and FAILS when it cannot tell.

Related: SL-1063 (the Xtensa target), SL-1067, SL-1069, sawos SO-112 and SO-113.

**From the sawos lead (chat m922, Nov 14), for the sweep.** sawos has no windowed start-up or vector file yet: its own is being designed (SO-112, reviewed before it is built), and its handlers will be written from the Xtensa ISA reference, in `hal/xtensa-esp32s3/kernel/boot.S` of the sawos repository once built; the sawos lead will name the commit. Until then the board's facts are in the sawos repository's `hal/xtensa-esp32s3/ABI.md` (read-only for us, `../sawos` locally): section 5a lists the six window vectors and their offsets from `VECBASE`, and 7d says what the windowed ABI adds to a trap and a switch. The order (after SL-1124 and the release) suits sawos.
