## Description

# `;` is the one-line statement separator; bare juxtaposition is refused; a brace body is one line or fully broken

RULED by the user, Sep 22 2026. Lead-authored brief; implemented by a dispatched agent after SL-318.p7 lands (the parser change touches every one-line body in the corpus, so it must not race an in-flight branch).

## 0. The finding

sawtracker's source carries shapes like

```saw
if arg == "--help" { help()
    return }
```

which the grammar accepts because Saw already parses SEVERAL STATEMENTS ON ONE LINE WITH NO SEPARATOR AT ALL: `if arg == "--help" { help() return 1 }` compiles and runs today (probed Sep 22; the two-space spelling the skill shows, `{ c in c = c + n  c }`, is a convention, not grammar). The separator is invisible, so a reader cannot tell one statement from two on a line (`let a = b (c)`, `x -1`), and the half-broken brace layout hides the body's last statement beside the closing brace. The user's ruling: what we allow now is confusing and could lead to unexpected bugs.

## 1. The rules (RULED)

**R1 — `;` separates two statements on one line.** `a; b` is two statements. Whitespace around it is free. The lexer already has the token (used in `[T; N]`), so nothing new is lexed; the type-position meaning is untouched because a `;` inside `[ ]` in a TYPE is not in statement position.

**R2 — `;` is a SEPARATOR, never a terminator.** A `;` followed by a newline, by `}`, by EOF, by another `;`, or a `;` at the start of a line is a clean error: ``a `;` joins two statements on one line; it does not end one — remove it`` (Saw has no statement terminators; that stays true). This keeps the language's "no semicolons" character: you write one only where two statements share a line.

**R3 — BARE JUXTAPOSITION IS REFUSED.** After a statement, the parser requires NEWLINE, `;`, the block's closing `}`, or EOF (and, inside a match arm's bare body, the arm's `,` — the arm grammar is unchanged). Anything else is ``two statements on one line need a `;` between them`` with a fixit naming the two statements' first tokens. The position matrix (obligation 1 — ONE chokepoint, its docstring naming the entries): function/method bodies, `if`/`else`/`while`/`for`/`match`-arm BLOCK bodies, closure bodies (`{ x in a; b }`), `try { } catch { }` blocks, `guard … else { }`, the `borrows` body, top-level module scope (two DECLARATIONS on one line are refused too — declarations are not joined by `;`, they take a newline). Every entry gets a row in the errors pin.

**R4 — `[T; N]`, the repeat literal `[v; N]` and nothing else keep their `;`.** Both are inside brackets where no statement can start.

**R5 — STYLE (the skill ruling, lenient form): a brace body is ONE LINE or FULLY BROKEN, never half-way.** Either the whole body sits on the brace's line (`if done { return }`, `{ c in c = c + n; c }`), or the opening brace ends its line, every statement has its own line, and the closing brace stands alone. `{ help()` + newline + `return }` is the shape the rule exists to catch, and it stays DISALLOWED BY STYLE even though the grammar accepts it (R3 does not refuse it — the newline is a legal separator). Prefer the broken form as soon as a body carries a `return`/`break`/`continue` beside anything else.

### The chokepoint and its entries

`Parser.expect_statement_end(previous_start=None, *, declarations=False)` in
`sawc/parser/core.py`, beside `skip_newlines`. Called once per GAP between
statements — including the gap BEFORE a list's first statement, where
`previous_start` is None, nothing precedes, and only the line-start half of R2
can fire. Entries, named in its docstring, all three:

1. `StatementsMixin.parse_block` — the ONE block-body funnel, which is why the
   rule reaches function and method bodies, `borrows` bodies, `if`/`else`/
   `while`/`for` bodies, a `match` arm's BLOCK body, both blocks of
   `try { } catch { }`, and `guard … else { }`. (Verified: `parse_block` is the
   only callee at all 13 block sites across `declarations.py`, `statements.py`
   and `expressions.py`.)
2. `ExpressionsMixin._parse_closure_body` — closure bodies.
3. `Parser.parse` — module scope, whose units are DECLARATIONS
   (`declarations=True`).

A `match` arm's BARE body ends at the arm's `,`, but that body is an expression
and not a statement list, so it never reaches the chokepoint — `parse_match`
owns that comma, unchanged.

`Parser.at_statement_end()` is the LOOKAHEAD half of the same rule, replacing
the four open-coded `NEWLINE/RBRACE/EOF` tuples at the statement forms whose
operand is optional: `return`, `break`, `lend`, and the closure body's `return`
(which also gains EOF, which it did not test before).
