## Description

`_analyze_nesting`'s suspending-recursion cycle check rejects the `__saw_drive` spelling cleanly (`examples/errors/coro_suspending_recursion.saw` pins it), but the `Task.spawn` / spawn-root spelling of the SAME cycle never reaches that check: the frame builder recurses on itself and the compiler dies with a Python traceback.

Repro (single file), verified against unmodified main (d0e38f90):

  import std.task.{yield_now}
  func recurse(n: Int) -> Int {
      yield_now()
      if n <= 0 { return 0 }
      return recurse(n - 1)
  }
  func main() {
      let t = Task.spawn(recurse(3))
      print("{t.join()}")
  }

Observed tail of the traceback:

  File ".../sawc/coro_transform.py", line 8306, in _zeroed_value
  File ".../sawc/coro_transform.py", line 485, in _zero_of
  File ".../sawc/coro_transform.py", line 211, in _int
  RecursionError: maximum recursion depth exceeded

with `_build_frame_init` repeated ~981 times above it (crash frame order: transform_program -> build_resume -> _build_sub_frame -> _build_frame_init recursing).

MECHANISM: the cycle check runs over the DRIVE roots' call graph; a spawn root is seeded on a different path and is not put through `_analyze_nesting` before its frame is built, so a cycle that check exists to refuse reaches `_build_sub_frame`, which embeds a callee frame by value -- which for a self-cycle has no fixed point. This is a fuzz-oracle violation (a traceback rather than a clean diagnostic), so it is also a `tools/sawfuzz.py` finding shape.

Found incidentally while censusing the CoroTransformError raise sites for SL-224. Not caused by and not fixed by the SL-222/223/224 batch.

FIX IN on branch agent-sl226-batch2 (commit ee32c83a after rebase). The issue's mechanism was exactly right: the graph was already SEEDED from the spawn roots (`seed_names`), so only the asking was missing. The check is a funnel now, not a clone — `_analyze_nesting` takes a graph KEY and its docstring enumerates the entry points.

THE SWEEP (obligation 4) found the bypass was wider than the filed spelling. Measured, each on unpatched main:

  Task.spawn(f())            RecursionError      -> clean diagnostic   (the filed row)
  group.spawn(f())           RecursionError      -> clean diagnostic
  mutual f -> g -> f, spawned  RecursionError    -> clean diagnostic, names the whole loop
  suspending `main`          RecursionError      -> clean diagnostic   (a root with NO spelling)
  __saw_drive(obj.m())       INTERNAL COMPILER ERROR -> clean diagnostic
  group.spawn(obj.m())       refused at the FORM ("expects a direct call to a free function") — unreachable
  Thread.spawn { f() }       refused: body is `sync`, no-executor diagnostic — unreachable

The METHOD root is why the check now takes a KEY: a method is reached by node id where a free function is a `("fn", name)` tuple, so asking about it means mapping `method_roots`' frame key across `methods_by_key`. Unasked, its cycle survived into phase 2 as the frame-key ICE ("classified this call as embeddable into `Walker_walk` ... but no such frame was built") — the invariant reporting a consequence rather than the cause. Thread.spawn is proven unreachable rather than assumed: its body is `sync`, so a suspending callee is refused before any root exists.

ONE NEAR-MISS WORTH RECORDING, because it is the part a reviewer should check. The first version asked the cycle question of the RAW GRAPH and REFUSED TO COMPILE BLADE:

  error: suspending recursion is not allowed: the suspending-call cycle `visit -> visit`
    --> blade/src/main.saw:150:1

Blade's dependency resolver recurses (`visit` descends into a dependency's dependencies) and reaches the cooperative `Command.run`, so the cycle is genuinely in the suspending-call graph and reachable from blade's suspending `main`. Blade has always compiled because NO `__Frame_visit` IS EVER BUILT — verified by emitting blade's IR on the pre-change compiler: `__Frame_main`, `__Frame_resolve`, `__Frame_Command_run` and `__Frame_Command_reap` exist, and there is no `__Frame_visit`. The closure walk follows an edge only when it can name and build a frame for the target, so the graph is WIDER than the set of frames built, and a cycle through a node it declines to reach is never embedded by value.

The check therefore asks whether every frame on the cycle will actually be BUILT (`closure` for free functions, `method_closure` plus the method roots themselves) — which is the same question `_build_sub_frame` would have answered by diverging. The `freestanding` lane is what caught this; it is the reason the per-commit gate includes it.

The contrast is pinned both ways: a cross-module callee the splice DOES take gets a frame and is refused (examples/errors/coro_cross_module_suspending_recursion.saw — it was a RecursionError before the fix too), while blade, whose callee the splice declines, must keep building, gated by the `freestanding` and `bootstrap` lanes.
