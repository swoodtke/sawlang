## Description

**Miscompile: once a generic `.copy()` instantiates a trivial enum's copy glue, assignments of that enum call the glue with the wrong signature, and the writes are lost.** Found by SL-955 unit 4b's probe; reproduced on main's source (the 4a3 compiler, Nov 4).

**Repro** (`.build/scratch/p955j/repro/`):

`pk/lib.saw` declares:
- `public enum Use: UInt8 { Unused = 0, Move = 1, Copy = 2 }`;
- `Uses { table: Vector<Use> }`, which is NoCopy;
- `func set(&var self, i: Int, u: Use) { self.table[i] = u }`;
- `unused_after_fill(n)`, which fills the table through `set` and counts the entries left `Unused`.

`main.saw` adds `func copy_all<T: ExplicitCopy>(v: &Vector<T>) -> Vector<T>`, which pushes `v[i].copy()`, and calls it on a `Vector<Use>`.

```
sawc build -O0 --module-path pk=repro/pk repro/main.saw -o repro/main && repro/main
copied 1; entries left Unused after the fill: 10 (expected 0)
```

- It is the same at -O2 -g0.
- Without `copy_all`, the control (`main_control.saw`) prints 0.
- A larger program (the probe) crashes with SIGSEGV at -O0.
- In the compiler's own typecheck code, the same shape made `set_use` drop every `expr_use` write.

**The IR** (`repro/main.ll`):
- The glue is defined returning the copy: `define internal i8 @"saw copy glue pk.Use"(ptr noalias %p1)`.
- The `.copy()` site calls it that way: `call i8 @"saw copy glue pk.Use"(ptr %t16)`.
- The assignment in `set` calls it as `call void @"saw copy glue pk.Use"(ptr %t5, ptr %l3)`.
- In the control program there is no glue, and `set` is a plain `store i8`.

**Mechanism (UNVERIFIED, the fix's first step confirms it):**
- `MonoWorklist.copy_glue_builds` (`compiler/mono/src/glue.saw`) answers true for every struct and enum, trivial ones included.
- The `.copy()` instance builds that glue in a value-returning shape.
- `operand_into` (`compiler/llvm/src/places.saw`) runs any copy glue a type has in the `(dest, src)` shape.

So one glue symbol has two call shapes, and which one a site uses depends on whether the glue happened to be instantiated elsewhere in the program.

**Presumed a class (obligation 4):** every backend site that asks whether a type has copy glue and calls it, against every glue-building shape, for trivial and non-trivial structs, enums, tuples and arrays. That covers:
- assignment;
- call arguments;
- returns;
- field and element initialisers;
- captures;
- `.copy()` itself.

The fix brief sweeps that matrix with compile-and-run evidence before fixing the mechanism: one call shape per glue, or no glue for trivial types, and the brief decides which.

**SL-961.p1: copy glue only for types not copied by their bits, and one copy-glue call shape**

**The mechanism (confirmed):**
- `build_copy_glue` makes copy glue as a function that returns the copy. `emit_function` therefore defines it as `iN (ptr)` when the type's layout is a scalar, and as `void (ptr %ret, ptr)` when it is memory.
- Three backend sites each wrote the call by hand as `call void @g(ptr dest, ptr src)`: `operand_into` (places.saw), `builtin_copy` (calls.saw) and `repeat_into` (literals.saw). That call matches only a memory-layout definition.
- A trivial type got glue because `glued` (worklist.saw) skipped the copied-by-its-bits test that the other creating paths make.
- Of the types that get copy glue, the raw-backed enum is the only one with a scalar layout.
- **A correction to the description:** the trigger isn't only a user's generic `.copy()`. std's `Vector.copy()` and `Vector.iter()` also reach it, so a plain `for x in v.iter()` over a `Vector` of a raw-backed enum is enough.

**The sweep** (`.build/scratch/p961/sweep.md`): 7 type kinds × the triggers × 23 copy sites. Every cell was compiled, run, and checked for the IR's call shape.
- **Before:** the raw-backed enum printed wrong output at 21 of the 23 rows under every trigger, and its call shape was wrong at all 23. Every other kind printed correctly with matching shapes; the trivial ones only paid for a needless out-of-line call.
- **After:** 0 wrong rows and 0 shape mismatches. No language decision was needed: the spec and `glue.saw`'s header already say a trivial value's copy is its bits.

**The fix:**
- **mono:** `glued` answers a `copy()` on a type copied by its bits with the bit-copy member helper that scalars already use, so copy glue exists only for memory layouts. `hook_of` treats both `Copy.copy` and `ExplicitCopy.copy` as the copy hook.
- **llvm:** one funnel, `copy_glue_into` (places.saw), writes every copy-glue call, and its ENTRY POINTS are those three sites. A copy glue whose layout isn't memory is refused, never called in a shape its definition doesn't have.

**Pins** (run-lane probes, -O0 and -O2, each also checking that the enum's copy glue never appears in the IR):
- `raw_enum_element_writes_beside_generic_copy` (the repro);
- `raw_enum_copies_beside_generic_copy` (every failing matrix row);
- `raw_enum_copies_beside_vector_iteration` (the std routes).

All three fail with an unfixed Stage 2 and pass with the fix. No golden and no pinned `.ll` moved. `corpusdiff.py run` over the 70 corpus programs that use raw-backed enums moved no verdict.

**Gates:**
- `run.py --only seed,units,golden,subset,fixture_whitespace,std,mono,coro,programs,sanitize,census`: rc 0;
- `battery.sh citations`: green.

**Not in this patch, both older than it:**
- `<T: Copy>` `x.copy()` at `T = Int` is refused as `mono.not-yet` ("Copy.copy() on Int, which no conformance of it meets"), while the `ExplicitCopy` bound works. Repro: `.build/scratch/p961/probe_copybound.saw`.
- The Air's suggested lane check, that every direct call's type matches its callee's definition, would be a follow-up issue.

Approved patch SL-961.p1 (revision 1)

**Air: SL-961.p1 approved.** It fixes the mechanism twice over:
- Mono no longer builds copy glue for a type copied by its bits (`glued` now asks `mono_copies_bitwise`, and `hook_of` treats both `copy()` requirements as the copy hook).
- One funnel, `copy_glue_into` (places.saw), writes every copy-glue call, with its three sites as named entry points. A glue whose layout isn't memory is refused, never miscalled.

The base is main's Stage 2 at d32b90a19, saved before applying.

**What I checked** (`.build/scratch/air-review/sl961/`):
- **The repro** (`pk/lib.saw` + `main.saw`, rebuilt from the issue): 10 entries left `Unused` under the base, **0** with the fix.
- **An independent matrix** (`matrix.saw`, ASan, -O0 and -O2), built to probe the "only the raw-backed enum has a scalar layout" premise. Beside a generic `.copy()` and a `for x in v.iter()` of a raw-backed `Use`, it copies `Use`, `Use?`, an `@synthesize`d-ExplicitCopy struct holding one `Arc<Int>`, a struct of `Use` and `Use?`, a tuple, a `[Use; 4]` repeat literal and its element write, and a closure capture, by assignment, argument, return, field and element initialiser, and generic copy.
  - The **base reads back garbage at -O0** (`iter 150 | assign 0 96 | fields 80 | tuple 16 | array … 107 | generic … 160`) and zeros at -O2. So the bug corrupts reads too, not only writes.
  - **The fix prints the right value at every site, identically at both speeds** (`iter 2 | assign 1 2 41 41 | fields 1 1 2 | tuple 1 2 array 2 1 | capture 42 | generic 1 41 2`), ASan-clean.
  - **Nothing is newly refused**, so the `Arc` holder, which needs real copy glue, still has a memory layout.
- **Call-signature census** (`.build/scratch/probe_call_signatures.py`: every direct call whose type differs from its callee's `define`):

- **The pins** (`.build/scratch/probe_stated.py`, each probe's `prints:` and `ll omits:` lines): the three new probes **match 24/24, 7/7 and 3/3 at -O0 and -O2** with the fix. Under the base they fail at both speeds (as low as 0 of 3 lines) and violate `ll omits`.
- **Gates:**
  - `run.py --only fixture_whitespace,mono,parallel_order,parser,programs,std,subset,coro,sanitize,census,golden,units`: `exit=0`. `programs` is the run lane: 514 programs stating their output, the new three included.
