## Description

Found by SL-265's obligation-4 sweep (design 271). Independent of that fix —
this is a REFUSAL, not a miscompile, and it is unchanged by design 271.

The `Set` element gate and the `Map` KEY gate do not know about the automatic
Copy tier, and say so in words that contradict the tier:

```saw
struct Rec { text: String }        // design 159: automatic Copy tier,
                                   // declares nothing, owes nothing

func main() {
    var s = Set<Rec>()             // error
    var m = Map<Rec, Int>()        // error
}
```

```
error: set element type `Rec` must be copyable (trivial, Copy, or ExplicitCopy
with retain semantics): `Rec` owns a Deinit without a copy (it is move-only,
not retainable)
```

`Rec` is neither move-only nor un-retainable: it is on the Copy tier, `let b = a`
is a free retain leaving both live, and design 219 has it satisfying both
`T: Copy` and `T: ExplicitCopy` (conformance row V32 pins exactly that).

The inconsistency that makes it a bug rather than a policy: the `Map` VALUE
position accepts the same type. `Map<String, Rec>` compiles and works (it is
one of SL-265's own probes), so one container's key gate and its value gate
disagree about one tier.

## Suspected mechanism

The gate reads a DECLARED conformance list rather than `copy_tier`, so a type
that earns its tier by derivation answers no. The wording ("owns a Deinit
without a copy") is the tell: an automatic-tier struct does own a synthesized
deinit, and the gate concludes move-only from that alone.

Worth a sweep for other predicates phrased the same way before a fix is
dispatched — design 271 found the same DECLARED-vs-DERIVED confusion in three
separate copy-emission chains, so this vocabulary has form.
