## Description

**Matching a fallible `NoMove` constructor's `Result`: what is legal?** (found by A17a's census, SL-578; needs a user ruling)

`alloc_channel_taskgroup_reports_oom` writes:
```saw-fragment
let group_made = TaskGroup(threads: 2)
match group_made {
    case Ok(group) -> { … }
    case Err(e) -> { … }
}
```
- sawc2 refuses it with `transfer.no-move`: "cannot `match` on `made`: `Result<…Pinned, std.alloc.AllocError>` is `NoMove`". A probe with a user `NoMove` struct and a `Result<Self, E>` init gets the same refusal. `try!` on the same init is accepted.
- Stage 0 accepts the program.

**The spec** says `NoMove` "forbids relocating an established group, not constructing one directly" (the TaskGroup section). It says nothing about a fallible `NoMove` init's `Result`. Binding the `Result`, then moving its payload into a `case Ok(group)` binding, relocates the group, so sawc2's refusal follows the rule as written. But then the only way to handle `TaskGroup(threads:)`'s `AllocError` is `try!`, which contradicts the allocation-failure section's promise that "the caller gains one word" and can handle the error.

**Options for the ruling:**
- (a) `match` directly on the init expression (no binding) binds the payload in place. That is construction, not relocation, so it's legal, and the bound form stays refused.
- (b) A `case Ok(group)` binding of a `NoMove` payload is a borrow of the `Result`'s storage, legal in both forms.
- (c) Keep the refusal; a fallible `NoMove` init is `try!`-only, and the spec says so.

**Acceptance:** the corpus row `alloc_channel_taskgroup_reports_oom` reaches its ruled verdict.

**Air: option (a) is already main's behaviour, so the premise that `try!` is the only way to handle the error doesn't hold.** I probed main (with T3b), with a user `NoMove` struct and a `Result<Self, AllocError>` init that auto-wraps (`air-review/sl578/` on the Air):

| form | sawc2 | Stage 0 |
|---|---|---|
| `match Pinned(fail: f) { case Ok(p) -> …, case Err(e) -> … }`, matched directly on the call, both arms | accepted; prints `direct ok 7` / `direct err allocation of 64 bytes (align 8) failed` | same |
| `let p = try! Pinned(fail: false)` | accepted, `forced 7` | same |
| `let made = Pinned(fail: false)` then `match made { case Ok(p) … }` | **refused**, `transfer.no-move` | accepted, `bound ok 7` |

So a caller can already handle `AllocError` from a fallible `NoMove` init by matching the call itself. The "caller gains one word" promise holds today, as long as the `Result` isn't bound first.

The choices left:
- **(a) as main has it, no compiler change:** spec text saying the match is on the init expression; the corpus row re-spells `match TaskGroup(threads: 2) {` and drops `let group_made`.
- **(b) widen to the bound form:** a compiler change, plus a ruling on what a `case Ok(g)` binding of a `NoMove` payload is (a borrow of the bound `Result`'s storage).
- **(c)** contradicts main's accepted forms, since the direct match already works, so it would remove behaviour rather than keep it.

Stage 0 accepting the bound form is permissive; whether that's `stage0-wrong` is decided by the ruling.

**The user ruled (a), Oct 19: binding a fallible `NoMove` constructor's `Result` and then matching it (form 3, `let made = TaskGroup(threads: 2)` then `match made`) stays REFUSED** (`transfer.no-move`, as main has it). Stage 0 accepting the bound form is `stage0-wrong`.

The legal ways to handle the error are the ones that never bind the `Result`. The lead probed both on main's sawc2 (`.build/scratch/probe778/`):
- `match TaskGroup(threads: 2) { case Ok(group) -> …, case Err(e) -> … }`: matching on the call itself;
- the inline-catch guard form, `let group = try TaskGroup(threads: 2) catch { print("{}", error); return }`. Its catch body diverges, so `group` stays in scope for the rest of the function. A user `NoMove` struct with a `Result<Self, E>` init passes both arms (`catch ok 7`, `caught refused`), and so does a real `TaskGroup(threads: 2)` (`got 42`). Stage 0 agrees.

**Work (queued, small, Sonnet-suitable):**
- a spec sentence in the TaskGroup / `NoMove` text: a fallible `NoMove` init's `Result` is handled where it is made (`match` on the call, or `try … catch`), and binding the `Result` first is refused because the payload binding would relocate it;
- the corpus row `alloc_channel_taskgroup_reports_oom` re-spelled to the direct `match` (or the inline catch), its twin with it, `corpusdiff.py snapshot --reuse`, then a re-baseline;
- an errors/ refusal pin for the bound form (`transfer.no-move`), and a `stage0-wrong` annotation if Stage 0's acceptance shows up in the corpus.

**Air: SL-778.p1 r1, changes requested for one spec line. Everything else is verified.**

**The spec fragment's "Legal" block doesn't compile as written.** `case Ok(group) -> run(group)` passes a `NoMove` group with no sigil. On main's sawc2 (`air-review/sl778p/` s1–s3) that's refused whichever signature `run` has:
- with `func run(group: TaskGroup)`: `transfer.implicit-copy`, "this reads a place of type `std.taskgroup.TaskGroup`, which is NoCopy, by value … write `move group`", and `move` of a `NoMove` value is refused in turn;
- with `func run(group: &TaskGroup)`: the same, plus `type.mismatch` "expected `&std.taskgroup.TaskGroup` … found `std.taskgroup.TaskGroup`", because the call has to mirror the sigil;
- `run(&group)` with `func run(group: &TaskGroup)` compiles and runs (`ran`, exit 0).

**The fix:** write `run(&group)` in both of the fragment's match arms. That includes the "Refused" one, so that block is refused only for the reason it claims, the bound `Result`. Also show or say that `run` takes `&TaskGroup`, for example a `// func run(group: &TaskGroup)` line at the top of the fragment.
