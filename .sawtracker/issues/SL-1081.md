## Description

**The builtin check has no ESP32-S3 row.** `compiler/tests/run/builtin_lowering.py` (SL-948) holds, for riscv32 and aarch64 freestanding objects at -O0, -O1, -O2, -Os and -Oz: std's builtin routines (`memcpy`, `memset`, `memmove`; the soft-float routines; on riscv32 the 64-bit integer helpers) are each defined weakly in a freestanding object; every function a routine reaches carries `"no-builtins"`; no routine reaches its own symbol (the hazard: LLVM turns a `memcpy` body's loop into a call to `memcpy`); and a soft-float routine reaches no soft-float routine. `ARCHES` has two rows. `xtensa-esp-unknown-elf` is a third freestanding target with no FPU by default, so it depends on exactly these routines, and nothing checks them there. SL-1076's census shows an Xtensa object references only the runtime seam, so the routines are being defined; whether they are the RIGHT set for Xtensa and whether any reaches itself there is unmeasured. The freestanding suite's row boots 41 cases, which is evidence the common paths work, not a pin.

**Goal:** an Xtensa row in `ARCHES`, with every check the other rows have.

**Read first:** all of `builtin_lowering.py` (docstring, `ARCHES`, `STD_ROUTINES`, `record_clang`, `llvm_tool`, `readobj_graph`, each `check_*`, `CROSS_MODULE_SELF_CALLS`); `compiler/llvm/src/attributes.saw` (`ll_builtin_symbol`, where `"no-builtins"` is decided and for which targets); `std/builtins/` (which routines exist and under what condition each is compiled: by word size, by target); `compiler/target/src/layout.saw` (`target_word_bytes`, `target_effective_features`); `compiler/tests/run/word32_ir.py` (how a row finds Espressif's clang record and skips with none; SL-1076).

**Implementation.**
1. **Step 0, a census, before any edit.** For `lowering/builtin_uses.saw` built `--freestanding --target xtensa-esp-unknown-elf` at each of the five levels, with Espressif's clang and the `llvm-nm` and `llvm-readobj` beside it:
   - which of `MEMORY`, `INTEGER` and `FLOAT` the object DEFINES, and with what binding (`W` expected);
   - every UNDEFINED symbol (expected: the seam alone). An undefined compiler-rt name (for example `__muldi3`, `__mulsi3`, `__divsi3`, `__udivsi3`, `__modsi3`, `__umodsi3`, `__bswapsi2`, `__clzsi2`, `__ctzsi2`, `__popcountsi2`, or a soft-float name std doesn't define such as `__extendsfdf2`, `__truncdfsf2`, `__negdf2`) means LLVM's Xtensa backend calls a routine std doesn't supply: a freestanding image using that operation would fail to link. **That is a finding: STOP and report the names, the level, and the source operation if you can tell.** Don't add the name to a list.
   - whether `llvm-readobj`'s relocation dump for an Xtensa object parses with `readobj_graph` as written (Xtensa call relocations and literal-pool loads differ from RISC-V's and AArch64's: a call is often `l32r` of a literal then `callx0`, so the relocation sits on the LITERAL, not the call site). If the graph comes out empty or misses calls you can see in a disassembly, STOP and report a sample of the dump: the check would then pass without seeing anything.
2. With a clean step 0: the `ARCHES` row (`("xtensa-esp-unknown-elf", None, <the routines step 0 found defined>)`), the skip when no Espressif clang is recorded (the whole row, saying so), and `CROSS_MODULE_SELF_CALLS` for the new row from what the run shows (pin what is measured; if `memset` reaches itself at a level where the other arches don't, report it in the summary, it is the documented cross-module limit and not a stop).
3. The two "the check sees what it is for" cases (`check_sees_a_self_call`, `check_float_operation_seen`) run on the new row too, or the report says why one cannot.
4. Docstring and `compiler/tests/run/README.md` updated to three arches.

**Expected outcomes.** riscv32's and aarch64's counts unchanged. New Xtensa counts of the same kinds. No compiler or std change; if step 0 shows one is needed, that is the stop above.

**Tests and gate.** `compiler/tests/run.py --only seed,fixture_whitespace,programs,comments` under the suite lock; `tools/battery.sh citations patchgate`.

**SL-1081, the lead's decision after step 0 (Nov 12).** The agent's census (the lead's checkout, `.build/scratch/p1081/`: `census.log`, and `nm`, `readobj` and `objdump` output per level):

- **The routines are all there.** At all five levels an Xtensa object of `lowering/builtin_uses.saw` defines the 3 memory routines, the 7 64-bit integer helpers and the 19 soft-float routines, each `W`, and its only undefined symbol is `__saw_rt_panic`. So std supplies everything LLVM's Xtensa backend calls for that program: the first stop did not occur, and the row's routine set is riscv32's (`MEMORY + INTEGER + FLOAT`).
- **The graph reader sees no Xtensa call.** `readobj_graph` returns 0 edges at every level, with 203 relocations in the -O2 object. A call on Xtensa is `l32r a8, LITERAL` then `callx0 a8`: the relocation in the function (`R_XTENSA_SLOT0_OP`) names the literal's SECTION symbol (`.literal.__adddf3`) with the literal's offset as addend, and the relocation that names the callee (`R_XTENSA_32`, to the callee's function symbol or to its `.text.NAME` section symbol) applies to the literal word, which lies in no function. The reader drops the second (no caller) and resolves the first to nothing (no function at that section and offset). A row added as written would have passed seeing nothing.

**Design: the reader follows a literal.** In `readobj_graph`:
1. Read each section's name from the Sections table (`Name: .literal.__adddf3 (N)`; strip the trailing index as the symbol names are stripped). A LITERAL SECTION is one named `.literal` or `.literal.<anything>`. Only Xtensa objects have them, so riscv32's and aarch64's graphs cannot change; that restriction is deliberate (a generic "any data word" rule would add edges through witness tables on the other arches).
2. First pass over the relocations: for each one that applies to a literal section, resolve its symbol exactly as the existing code resolves a relocation's symbol (a function symbol by index; or a section symbol plus addend to the function at that exact address) and record `literal[(section index, offset)] = that function`, when it resolves to one. A literal naming data records nothing.
3. Second pass, the existing loop: when a relocation inside a function names a section symbol and no function sits at (that section, addend), look up `literal[(that section, addend)]`; if present, add the edge caller → that function.
4. The docstring says it: on Xtensa a call loads its callee's address from a literal pool, so a relocation naming a literal names the function that literal names.
Factor the "resolve a relocation's symbol to a function" step into one inner function used by both passes; don't write it twice.

**Things to check before trusting it** (each with a line of evidence in the report):
- the addend of a `R_XTENSA_SLOT0_OP` naming a literal section IS the literal's offset when a function has several literals: find a function with at least two (`.literal.X` of 8 bytes or more) and confirm two different callees resolve from addends 0 and 4;
- a direct `call0` to a symbol, if any object has one, already resolves through the existing code (say whether one occurs);
- at -O0 and -Oz as well as -O2, sample one known call each and confirm the edge (the shapes may differ: a shared `.literal` section, or literals placed in the text section);
- after the change, the edge the census looked for exists (`__adddf3` → `saw std.builtins.float.added(...)`) and the graph's edge count per level is in the same range as riscv32's for the same program (print both).

**A guard against the next silent reader failure, on every row:** `check_std_routines` (or the function that builds the graph for `builtin_uses.saw`) fails when the object's graph has no edge at all, with a message saying the reader sees none of the object's calls. A program whose routines call helpers always has edges; zero means the reader, not the program.
