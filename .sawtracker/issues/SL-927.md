Found by p540's SL-540 sweep (`.build/scratch/p540/plan.md` §1).

**`Float` ↔ integer `as` is refused by the backend** (`backend.not-yet: this conversion is not in the backend slice yet`), and the front end accepts it. **NEEDS A USER RULING before it's built:** the spec gives no meaning for NaN, ±infinity or an out-of-range value in `f as Int` (LLVM's `fptosi` is poison there). The candidates:
- (a) `as` panics on NaN or out of range, like an integer narrowing;
- (b) `as` saturates (Rust's choice: NaN → 0, clamp to min/max);
- (c) `as` on Float→integer is refused, and `Int.from(f) -> Int?` is the partial conversion.

`integer as Float` (rounding to nearest) is less contentious. Nothing in std, the compiler or the corpus uses either direction today (per the sweep).

Never hide errors: a poison result must not be reachable whatever the ruling.

**RULED (the user, Oct 29):**
- **`f as Int`** (Float → any integer width) **PANICS** on NaN, ±infinity or a value outside the target's range, like an integer narrowing `as`. In range, it truncates toward zero.
- **`Int.from(f) -> Int?`** (every integer width) is the NO-PANIC form: `None` exactly where `as` would panic.
- **`i as Float`** (integer → Float) always succeeds: a 64-bit integer never overflows a Float (max ~1.8e19 vs ~1.8e308), so it only ROUNDS to nearest above 2^53.
- **`Float.from(i) -> Float?`** is the no-panic EXACT form: `None` when the integer isn't exactly representable, so a caller can detect precision loss.

**Work:** the spec text (numeric conversions; the partial/total table), typecheck acceptance of `Int.from(Float)` and `Float.from(Int)` at every width, and the backend (fptosi/fptoui with a range+NaN guard before them, so poison is unreachable; sitofp/uitofp, and an exactness check for `Float.from` by round-tripping). SL-540's `partial_into` is the funnel for both `from` forms. Pins at every width, including NaN, ±inf, the boundary values, -0.0, and 2^53, 2^53+1, 2^63.

**Air, before the guard is written: two boundary traps in `f as IntN`** (the IEEE-double arithmetic from `.build/scratch/probe_float_boundary.py` on the Air).

**1. The top bound for the 64-bit widths must be strict, at 2^k.** `Int64.max` (2^63 - 1) is not a double: it rounds UP to exactly 2^63 (`9.223372036854776e18`), and `UInt64.max` rounds to exactly 2^64. So a guard written `f <= (Int64.max as Float)` admits `f = 2^63`, and `fptosi double 2^63 to i64` is poison: the guard exists precisely to make that unreachable. The guard must be `f < 9223372036854775808.0` (2^63), and `f < 18446744073709551616.0` (2^64) for `UInt64`/`UInt`.

For every width up to 32 bits the maximum IS exact (127.0, 32767.0, 2147483647.0, 255.0 … 4294967295.0), so `<=` is right there. Pin `9223372036854775807.0 as Int64` and `2^63 as Int64`: both are the double 2^63, and both must PANIC.

**2. Which value is range-checked: before or after truncation?** The ruling says "in range, it truncates toward zero". If range means the TRUNCATED value (C's integral-part rule; Swift's `UInt(-0.5) == 0`, which traps only from -1.0), then:
- `-0.9 as UInt` is `0`, not a panic;
- `-2147483648.5 as Int32` is `-2147483648`.

The guard is then the OPEN interval `(min - 1, max + 1)`, i.e. `f > -1.0` for unsigned and `f > -2147483649.0` for `Int32`, combined with point 1's strict tops. If range means the value BEFORE truncation, `-0.9 as UInt` panics and the guard is `[min, max]`. These give different answers, so it's worth one line in the spec, and pins on both sides of each bound (`-0.9`, `-1.0`; `max + 0.5` at the narrow widths).

Also for the pins: `-0.0 as Int` is `0`; NaN panics; `Float.from(2^53)` is `Some` and `Float.from(2^53 + 1)` is `None`. And at -O2 the guard mustn't be folded away for a constant operand.
