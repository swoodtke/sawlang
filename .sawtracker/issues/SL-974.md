## Description

**`Vector.sort` and `Vector.sort_by` are insertion sorts, quadratic on unsorted input.** Found by SL-970 unit 4, which had to give the coroutine passes their own merge sort (`coro_sort`) to stay near-linear.

**Where:** `std/vector.saw` `sort` (for `T: Comparable`) and `sort_by` (with a comparator) each swap adjacent elements until the new one is in place: O(n²) comparisons and swaps, and O(n) only on already-sorted input. Both promise a stable sort, and the doc says nothing of its cost.

**Expected:** an O(n log n) stable sort, which is what a user reaching for `sort` expects ("APIs do the expected thing"). Options include a merge sort with an O(n) buffer, or a hybrid (insertion sort under a small threshold, merging above it).

- **Allocation:** the buffer is an allocation, so check design 234's rule. `sort` is an allocating op only if it allocates, and the in-place option, a stable in-place merge or block sort, avoids the change of signature.
- **Order:** stability and the ordering of equal elements must be unchanged, and no caller may see a different order. Every corpus and run-lane program that sorts must give identical output.
- **Pin:** a complexity check over a large reverse-sorted and a random vector, in the complexity lane or the std lane.

**Then:** replace `coro_sort` (`compiler/coro/src/`) and any other hand-written sort in the compiler with std's.

**SL-974.p1: `Vector.sort`/`sort_by` as an in-place stable merge sort**

**What changes** (`std/vector.saw`):
- `sort_by` is a bottom-up merge sort that insertion-sorts runs of 20 elements, then merges runs of doubling width in place with SymMerge. A merge whose two runs are already in order is skipped.
- It allocates nothing and moves elements only through `swap`, so a NoCopy `T` works. It asks only "is one element strictly greater than the other", which keeps it stable.
- `sort` calls `sort_by` with a `>` comparator. The signatures are unchanged, and the doc comments state the cost: O(n log n) comparisons, O(n log² n) swaps, no allocation.

**Measured** (random `Int`s, `v.sort()`):

| elements | -O0 before | -O0 after | -O2 before | -O2 after |
|---:|---:|---:|---:|---:|
| 1,000 | 12.5 ms | 1.2 ms | 0.36 ms | 0.11 ms |
| 10,000 | 1.19 s | about 20 ms | 44 ms | 1.4 ms |
| 100,000 | 120 s | about 0.4 s | 3.37 s | 0.020 s |

**Pins:**
- `compiler/tests/run/vector_sort_stable.saw` (with a Stage 0 record) sorts random, reverse-sorted, already-sorted, all-equal and many-duplicates vectors at sizes 0–2,500, including the run length ±1. It checks ordering, permutation and stability through both `sort` and `sort_by`, plus NoCopy and `String` elements. Its output is identical under Stage 0, the old std and the new one.
- `compiler/tests/run/probes/vector_sort_comparisons.saw` requires 2N elements to cost at most 2.3× the comparisons of N. That ratio was about 4 before, and is now 2.0–2.17.

**Also:** sawc's cone is re-recorded (`sort_by` and its helpers, `Ordering`). The saw-lang skill's `sort` line drops the stale `_greater_at` reason and states the cost.

**A finding for the user:** `sort`'s `T: Copy` bound is now vestigial. Nothing copies an element, and a NoCopy type sorts correctly with the bound removed. The bound is left unchanged here. Removing it would widen the API.

**Gates:**
- `run.py --only seed,units,golden,std,programs,sanitize,complexity`: ok;
- corpusdiff: 2,675 programs hold.

**Air: SL-974.p1 r2, changes requested, for one missing file. The sort itself is right, and I'd approve an r3 that only adds it.**

**1. `vector_sort_stable.saw` has a darwin Stage 0 record and no aarch64-linux twin.**
- **The check:** `probe_record_pairs.py compiler/tests/run/stage0 arm64-apple-darwin aarch64-unknown-linux-gnu`.
  - On main: 306 pairs, 0 unpaired.
  - With the patch: 306 pairs and 1 record under darwin only, this one.
- **Why it matters:** a new top-level run program recorded for darwin alone is what failed the Linux run lane on main after SL-805 (SL-820). The server's gate doesn't run that lane.
- **The fix:** `compiler/tests/run/stage0/aarch64-unknown-linux-gnu/vector_sort_stable.stage0`. Every existing pair differs only in its `triple` line. This program's output is 64-bit wrapping arithmetic over integers and strings, so the twin is the darwin record with `triple aarch64-unknown-linux-gnu`, or a `--stage0` run in the VM.

**The sort, read against its source** (Go's `sort.Stable`: insertion-sorted runs of 20, then SymMerge and a block-swap rotate):
- **Every comparison is the original's.** Each `Less(x, y)` maps to `greater_by(y, x)`: the two binary searches, the split search's `!Less(p - c, c)`, and the insertion step. The midpoint, `start`/`bound`, `stop = span - start` and both recursion guards match line for line, and so does `rotate`.
- **The extra skip is sound:** when the left run's last element is not greater than the right run's first, the two runs are already in order, and nothing moves.
- **Indices stay in range whatever `compare` answers.** That matters, because the safe `sort` reaches the unchecked `greater_by`. Every searched index lies between bounds fixed by `low`, `middle` and `high` alone, and in the split search `c` and `last - c` always fall in different runs.

**Probed with my own program** (`sort_drops.saw`: a NoCopy `Tag` owning a heap `String`, with a counting `deinit`):
- **325 sorts:**
  - 13 sizes: 0, 1, 2, 19, 20, 21, 39, 40, 41, 61, 333, 1,000 and 4,097;
  - 5 input shapes: five keys (mostly ties), a wide key range, descending, ascending, all equal;
  - 5 comparators: `sort`, an honest `sort_by`, a coin-flip comparator, always `Greater`, never `Greater`.
- **No element is dropped during a sort, and each is dropped exactly once after it.** Every element keeps its own name, so it's a permutation. The honest sorts are ordered and stable. The three lying comparators leave a permutation with the same drop count.
- **0 failures** at -O0, at -O2, under `--sanitize address`, and under Guard Malloc.

**The rest:**
- The spec and skill text match the code. The cost line agrees with what this algorithm's source documents: O(n log n) comparisons, O(n log² n) swaps.
- The bound removal is the user's ruling, and `sort` reads its comparands in place, so a NoCopy element is sound.

**Not this patch's, found while probing:** a closure with two `_` parameters, `v.sort_by({ _, _ in Ordering.Greater })`, is refused. sawc gives `name.shadowing`: `` `_` is already defined in this scope; a redefinition must derive from it ``. A single `{ _ in … }` is fine, so `_` seems to be bound as a name in a closure's parameter list. For you to file, if it isn't known already.
