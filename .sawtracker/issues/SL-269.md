## Description

## Description

Found while building SL-265's conformance rows (design 271). Not caused by that
work — every probe below has NO `.copy()` anywhere in the program, and both
faces reproduce identically against the pre-SL-265 compiler.

An escaping closure held as a `Vector` element has two independent defects.

## Face 1 — a by-value capture does not survive the frame that built the closure

```saw
func copied() -> Vector<() sync -> Int> {
    let a = 41
    let b = 42
    let c = 43
    var original = Vector<() sync -> Int>()
    try! original.push({ [a] in a })
    try! original.push({ [b] in b })
    try! original.push({ [c] in c })
    move original
}

func main() {
    let v = copied()
    let g0 = v[0]
    let g1 = v[1]
    let g2 = v[2]
    print("{g0()} {g1()} {g2()}")
}
```

Expected `41 42 43`. Actual `41 12596 4303424292` — reads out of the dead frame.
Exit 0, silent. Built entirely inside `main` (no frame boundary crossed) the same
three closures print `41 42 43`, which is what pins the frame as the variable.

## Face 2 — a `Vector`'s element env is never released

```saw
struct Res { id: Int }
extension Res: NoCopy {}

func sink(v: Vector<() sync -> Int>) -> Int { v.len() }

func main() {
    let shared = try! Arc(value: Res(id: 1))
    let held = shared.copy()
    var closures = Vector<() sync -> Int>()
    try! closures.push({ [move held] in 7 })
    print("env owns one: {shared.strong_count()}")   // 2
    let _ = sink(move closures)
    print("after the vector dies: {shared.strong_count()}")  // 2 — must be 1
}
```

The env holds the moved-in `Arc` reference, so the count is the env's own
lifetime made visible: it never drops, so the env destructor never runs and
every capture it owns leaks. Counts balance the wrong way rather than
under-running, so it is a leak, not a double free, and it exits 0.

The same oracle through a STRUCT member — `struct Watched { probe: () sync -> Int }`
as the element — reads 2 then 1, i.e. correct. So the defect is in the
element-typed-as-a-FUNCTION path, not in closure env refcounting generally.

## Why this is filed rather than fixed

SL-265's fix is a copy-EMISSION funnel; both faces above are drop/capture
lowering and reproduce with no copy in the program. Design 271 records that the
DIRECT `Vector<closure>` element is therefore unusable as a refcount oracle and
counts that arm through a struct member instead (conformance row V103's note).

## Both faces are ONE bit

This issue filed two independent defects. They are the same stack environment seen from two sides — it dies with the frame that built it, and it has no destructor — so one line fixes both, and the direct `Vector<closure>` element now behaves exactly like the struct-member route design 271 had to substitute for it (V103's note can be retired when someone revisits it).

`sawc/typechecker/expressions.py:13780`, the escape analysis:

    expr.escapes = force_escape or (
        (not as_call_argument) and (not has_reference_params))

"Is this a call argument?" answers "does the callee run it before returning?" ONLY for a callee that does not STORE it — and a container's insert stores it by definition.

**The checker already knew.** `target_escaping` — the same question asked of the PARAMETER, read off the `escaping` bit `_stamp_escaping_roles` writes on every stored position — is computed 445 lines ABOVE, for the borrow-capture gate, and the escape rule never consulted it. Instrumented on the issue's own program:

    [SL269] closure@6:24 escapes=False as_arg=True target_escaping=True
            expected=() sync escaping -> Int captures=['a']

So one closure carried two classifications at once: the borrow gate refused `[&var n]` there (correct — it is escaping) while the lowering gave it a stack env (incorrect — it is not). The fix is to OR `target_escaping` into the rule.

## The oracle is OWNERSHIP, not value — and that is load-bearing

The symptom users meet is a closure reading a dead frame (`41 42 43` coming back as `41 6159428032 4303424292`). Reading a dead frame is UNDEFINED, so that oracle is not a test: a first draft of the matrix above passed PRE-FIX at every cell because the stack happened not to be reused, and a single-closure probe reads back correctly by luck. Every cell now measures an `Arc` count while the holder is ALIVE and again after it dies — `2` then `1` is the guarantee, `1` then `1` is the bug (the capture was released at the BUILDING frame's scope exit, leaving the holder carrying an env that points at freed storage).

## Consumer sweep (obligation 2 — this is a classification flip)

std's closure parameters are all declared non-escaping — the `each` / `fold` / `each_key` / `each_value` / `lock` visitor family says so in place — so not one of them changes, and no std call site is affected. The borrow-capture gate is unaffected because it already consulted `target_escaping`; the two now agree where they used to disagree.

What DOES change is **`--no-hidden-alloc`**: a capturing closure stored by the call it is passed to now correctly reports the heap env it always allocated, so a program that compiled silently under the flag is now refused. That is the flag's entire purpose (the report and the lowering are the same bit, so they were wrong together), and it is added as `examples/errors/no_hidden_alloc_closure_pushed_into_a_vector.saw` rather than worked around.

## One corpus test changed its expectation, and it was the TEST that was wrong

`examples/closure_deinit_vector.saw` expected `deinit 2` / `deinit 1` while its own header promises "released exactly once at Vector teardown (in the container's element order)". Pre-fix NEITHER clause held: the non-escaping classification made `[move a]` a DEFERRED move, so the Vector's teardown released nothing and the two deinits were main's scope exit dropping the locals — after the Vector was already gone. Probed by sinking the Vector mid-`main`:

    pre-fix:   pushed / vector is gone / main ends / deinit 2 / deinit 1
    post-fix:  pushed / deinit 1 / deinit 2 / vector is gone / main ends

The count was right either way, which is all the old expectation checked, and reverse-declaration order happens to be the reverse of element order at two elements. The test now carries that `sink` so WHEN the envs are released is on the page, not only how many.

## Observed boundary, NOT filed (pre-existing, unrelated, clean refusals)

A closure literal at an OPTIONAL-wrapped slot does not take the slot's payload type: `func f() -> (() sync -> Int)? { { [a] in a } }` is refused with ``returns `() escaping -> Int` `` (the `escaping` bit arrives, `sync` does not, and no auto-wrap happens), and `stash_opt(&var v, { [a] in a })` at a `(() sync -> Int)?` parameter is refused the same way. Verified byte-identical against the pre-fix compiler, so it predates this work and is untouched by it. Flagging rather than filing: they are clean compile-time refusals with no soundness consequence, and the fix belongs with whoever owns expected-type propagation through an optional layer. Say the word and I will file it.

## Conformance

V115 (the guarantee — the full position matrix above, its five controls, and the ownership oracle) and V116 (the negative — a closure the callee RUNS keeps its stack env, oracled by `--no-hidden-alloc` because getting the classification wrong in THAT direction is invisible at run time and costs only an allocation nobody asked for). They are a PAIR on purpose: the fix moves a classification, and the two directions of getting it wrong fail in ways no single oracle can see at once.

struct Pair { t: (Arc<Res>, Arc<Res>) }
@synthesize
