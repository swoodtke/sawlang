## Description

**A `///` doc comment directly above a `private` struct field drops the `private`: the field becomes visible, readable and writable, from another module.** Reported by sawos (chat m1370, Nov 19, SO-144). It mattered there: `sos.system.Process.names_caller`, written `private` under a `///`, was public, so a process could set it and pass a self-only check. sawos works around it by writing those notes as `//`.

Reproduced by the lead on main (`.build/scratch/vis/`). Module `a`:

```saw
public struct Secret {
    /// The caller's identity; only this module may set it.
    private owner: Int
    private plain: Int
}
```

From another module:
- `s.owner = 99; print(s.owner)` typechecks clean;
- `s.plain = 99` is `member.unknown` ("`a.Secret` has no member `plain` this module can see"), as it should be.

sawos says `public(package)` under a `///` is not affected. Their reading (UNVERIFIED) is that the parser looks right and the marker is dropped in a later stage.

**This is a visibility soundness hole** (design 80's member visibility: a `private` member is narrowed to its module). A conformance row comes first (obligation 3).

**Sweep (obligation 4: a class until a sweep says otherwise).** Name the mechanism: where the doc comment's attachment changes what the visibility reader sees (the declaration's first token? a trivia-adjusted span?). Probe, each with and without a `///` and a `//!`-adjacent case:
- a `private` field, method, static, extension member, initializer, enum case payload accessor;
- a `private` top-level function, struct, static and type alias;
- `public(package)` and `public`;
- an attribute between the doc comment and the modifier (`/// doc` / `@align(8)` / `private x`);
- a doc comment above a field of a `public` struct in a dependency package, built through Blade.

The fix targets the mechanism, with the matrix as its pins (each red on main).

Related: SO-144, design 80, design 121 (doc comments).

**Lead's note with p1 (Nov 19).** The sweep evidence is in `.build/scratch/p1174/` in the lead's checkout (`sweep_main.txt` and `sweep_fixed.txt`, one line per probe).

- **Row B37** (Visibility and module boundaries): a `private` field is invisible outside its module whatever trivia precedes it. INDEX.md has 866 rows.
- **The mechanism:** a `///` attaches a Doc node as the field's first child (`(Field (Doc "...") private owner ...)`). `field_visibility` (`compiler/resolve/src/collect.saw`) tested "the first child is a leaf reading `private`", so with a Doc node first the test failed, and the field fell back to its struct's tier. A `private` field of a `public struct` became public.
  - `public` and `public(package)` are read by `visibility_of`, which scans every child, so they were unaffected.
  - `field_visibility` is the only reader of a field's modifier. GRAMMAR.md makes `private` a field-only modifier, and the parser refuses it elsewhere (`syntax.decl.field-visibility`), so the field is the one position.
- **The fix:** the first LEAF child decides: `private` iff it is not the name leaf and reads `private`.
- **The sweep:** about 70 probes, each with and without a `///`, over fields, payloads, functions, statics, inits, extensions, top-level declarations and bare members. Only the two field probes (a read and a write of a doc'd `private` field from another module) were wrong on main; nothing else moved.
- **Pins:** `member.unknown.doc-private-field-{write,read}/` and `call.no-match.doc-private-field-literal/`, all cross-module. Each is accepted on main and refused now. The control `typecheck/multi/doc_private_field_controls/` keeps a doc'd `public`/`public(package)` field visible and a doc'd `private` field readable in its own module.
- **Blade:** a dependency resolves through the same `collect.saw` path as a `--module-path` module, which the sweep covers. The five doc'd `private` fields in std, Blade, libs and the corpus break nothing (`std`, `programs` green).
- **Gate:**
  - run.py `seed,units,golden,subset,fixture_whitespace,std,parser,resolver,typechecker,docs,programs` green;
  - `comments` green after a comment reword (the baseline is unchanged: 521, as on main);
  - `citations` green; lint ok.
- **Not probed:** a `private` field under a `//!` comment.

Requested changes on patch SL-1174.p1 (revision 1)

**Changes requested, one point: the fix's `c != name` guard has no pin.** The mechanism and the fix are right, and every cross-module cell I tried comes out as it should. One branch of the new reader is held by nothing.

A field may be named `private` (GRAMMAR.md's contextual-word rule: `private` is the modifier only before a field name, and `field ::= field-visibility? IDENT ":" type`). For `private: Int`, the first leaf is the name, and `c != name` is what keeps that field at its struct's tier. On main the child count did that job (`n >= 3`).

I dropped the guard (`if self.text_of(self.current, c).equals("private")`) and rebuilt:
- `run.py --only resolver,typechecker` stays green under the lock;
- `public struct S { /// A field named private.  private: Int }`, read as `s.private` from another module, becomes `member.unknown`, where the patch accepts it.

No test in `compiler/tests`, `tests/corpus` or `std` has a field named `private`.

**Ask:** in `doc_private_field_controls`, a field named `private`, with and without a `///`, read from the other module. That line goes red without the guard.

**Read and held (8 cross-module cells, each typechecked with the patch and with main):**
- These are refused `member.unknown` with the patch and accepted on main, every one:
  - a doc whose text reads `public`, and one that reads `public(package) …`;

  - a field of a generic struct;
  - a doc'd `private` field after a public one;
