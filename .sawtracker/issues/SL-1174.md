## Description

**A `///` doc comment directly above a `private` struct field drops the `private`: the field becomes visible, readable and writable, from another module.** Reported by sawos (chat m1370, Nov 19, SO-144). It mattered there: `sos.system.Process.names_caller`, written `private` under a `///`, was public, so a process could set it and pass a self-only check. sawos works around it by writing those notes as `//`.

Reproduced by the lead on main (`.build/scratch/vis/`). Module `a`:

```saw
public struct Secret {
    /// The caller's identity; only this module may set it.
    private owner: Int
    private plain: Int
}
```

From another module:
- `s.owner = 99; print(s.owner)` typechecks clean;
- `s.plain = 99` is `member.unknown` ("`a.Secret` has no member `plain` this module can see"), as it should be.

sawos says `public(package)` under a `///` is not affected. Their reading (UNVERIFIED) is that the parser looks right and the marker is dropped in a later stage.

**This is a visibility soundness hole** (design 80's member visibility: a `private` member is narrowed to its module). A conformance row comes first (obligation 3).

**Sweep (obligation 4: a class until a sweep says otherwise).** Name the mechanism: where the doc comment's attachment changes what the visibility reader sees (the declaration's first token? a trivia-adjusted span?). Probe, each with and without a `///` and a `//!`-adjacent case:
- a `private` field, method, static, extension member, initializer, enum case payload accessor;
- a `private` top-level function, struct, static and type alias;
- `public(package)` and `public`;
- an attribute between the doc comment and the modifier (`/// doc` / `@align(8)` / `private x`);
- a doc comment above a field of a `public` struct in a dependency package, built through Blade.

The fix targets the mechanism, with the matrix as its pins (each red on main).

Related: SO-144, design 80, design 121 (doc comments).
