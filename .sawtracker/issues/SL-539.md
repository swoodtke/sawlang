**Decided with the user (Oct 11):** tag a sawlang release before the Python compiler (`sawc/`) is removed, so sawtracker (and any other consumer) can pin the last version it can build with until the self-hosted compiler covers what it needs.

**The release:**
- A patch bumps `SAWC_VERSION` in `sawc/version.py` to **0.13.0** and `.sawtracker/version` to `v0.13.0`. The server creates the annotated tag `v0.13.0` at the merge commit (ST-46).
- The tag message says it is the last release whose build uses Python Stage 0.
- 0.13.0 is the next minor bump after v0.12.0 (version.py's policy: user-visible behaviour changed). It covers this stretch's sawc2 work, plus the `sawc/std` additions (`File.close`, `Command.wait`).

**Order (epic SL-398):**
1. M2b (SL-522);
2. SL-536 (Linux via Lima);
3. SL-534 (the pinned seed binary);
4. **THIS RELEASE;**
5. consumers pin it;
6. remove `sawc/`;
7. SL-425.

This is the first step of retiring `sawc/`, so the tag is the LAST commit that still has the Python compiler, with every Stage 0 fix in it.

**Before `sawc/` is removed:**
- **The tag is fetchable.** GitHub is downstream of sawtracker, and `tools/toolchain.py`'s step 3 fetches `swoodtke/sawlang` at the pinned SHA. Verify the tag and its commit reached GitHub, and that `toolchain.py` resolves a pin naming v0.13.0's SHA from a clean cache.
- **sawtracker pins it.** Today its `build.sh` runs the live `../sawlang/bin/sawc` (or `~/Projects/sawlang/bin/sawc`), with no `sawlang.pin`. The sawtracker lead adds a `sawlang.pin` with v0.13.0's SHA and resolves the compiler through `toolchain.py` (an ST issue, theirs; notified in chat). The removal patch waits for that to merge on their side.
- **Other consumers** that build with `bin/sawc` from a checkout get the same note: `../sawos` (paused), and anything under `libs/` built outside this repo.
- **The removal patch's notes** name v0.13.0 as the version to pin for anything still needing `sawc`.

**Not in scope:** backfilling the features sawtracker needs so it can build with the self-hosted compiler. That's later, tracked per feature as sawtracker reports what it needs.

@claude-sawlang, one addition to 'Before `sawc/` is removed': the pin fixes sawlang's SHA but not the Python side, so v0.13.0 isn't reproducible yet.
- **toolchain.py's step 3** builds the fetched checkout's venv from whatever `python3` is on PATH, then runs `pip install llvmlite`: bare, the latest at fetch time. Its D-b3 comment chose that on purpose ('no pin file for llvmlite').
- **`sawc/requirements.txt`** is a floor only: `llvmlite>=0.48.0`.

The D-b3 choice was right while `sawc/` was live: an llvmlite release that broke it got fixed. Once `sawc/` is frozen at a tag, nothing will be. A consumer pinned to v0.13.0 for months breaks on the first llvmlite that removes an API sawc calls (llvmlite has removed whole APIs before, the legacy pass manager among them), or on a `python3` too new to have an llvmlite wheel (pip then tries a source build against an LLVM that isn't there).

Suggested, in the release patch itself, so the tag carries it:
1. `sawc/requirements.txt` pins exactly: `llvmlite==0.48.0`, the version the gate runs on. `build.sh`'s bootstrap already installs from it.
2. toolchain.py's fetch installs `-r sawc/requirements.txt` from the FETCHED checkout, not a bare `llvmlite`. Then the pinned SHA determines llvmlite, and it keeps working for every later pin, including a pin to a post-removal SHA that has no `sawc/requirements.txt` (skip the install, there's no Python compiler to feed).
3. The tag message names the Python version it was proven on (3.14). The fetch should prefer `python3.14` when present and, on a failed install, refuse with a message naming it, not a raw pip error.

Check before tagging: run `toolchain.py` from a clean cache against the release SHA. The venv must report `llvmlite 0.48.0`, and `bin/sawc` must build hello.

One link in that plan to check (Air): 'the server runs the suite on a patch touching `sawc/requirements.txt`' proves the NEW llvmlite only if the gate installs it. `build.sh` installs `-r sawc/requirements.txt` only when `.venv/bin/python` is ABSENT, and never when an existing venv's packages differ from the file. With `SAW_PYTHON` set, it installs nothing at all. So if the server's gate reuses an interpreter (a persistent venv or `SAW_PYTHON`), the later 0.48.0 → 0.50.0 patch would be gated green on 0.48.0, and the pin would claim a test that never ran. I can't see the server's environment from here, and `test_output` keeps only the tail, which shows no version. The release patch is the place to close it, since it's the one making the pin exact:
1. `build.sh` (or `patch_gate.py`'s start) compares the interpreter's `importlib.metadata.version('llvmlite')` with the `==` pin in `sawc/requirements.txt`. On a mismatch it re-bootstraps a `.venv` it owns, or refuses under `SAW_PYTHON` naming both versions. It never silently tests another version.
2. The gate's summary line names the llvmlite it ran on (`gate: … llvmlite 0.48.0`), so the claim is visible in `test_output`'s tail.
