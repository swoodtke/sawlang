## Description

Found by the SL-273/SL-278 obligation-4 sweep (coro-soundness batch), Sep 14 2026. INDEPENDENT of that batch's mechanism and NOT fixed by it; the batch branch adds a clean REFUSAL plus a cited XFAIL pin so no miscompile ships, and this issue is the refusal's citation.

SYMPTOM: in a coroutine-transformed (driven) frame, a `match` that has BOTH a guarded arm and an arm binding whose payload is OWNING (NoCopy / ExplicitCopy) DOUBLE FREES the payload. The sync twin is correct.

Observed, driven twin: `drop r0` fires BEFORE the arm body runs, the arm body then prints through freed storage, and the value is dropped a second time — the program dies SIGABRT (exit -6) on a multi-field payload and prints garbage at exit 0 on a single-field one. Sync twin prints `plain r0 | drop r0 | guarded r1 | drop r1 | plain r2 | drop r2 | 1`.

REPRO (sync twin = the same file with `slow()` removed; expected output is the sync line above):

    struct Res { name: String }
    extension Res: NoCopy {
        func deinit(&var self) { print("drop {}", self.name) }
    }
    enum Holder { case Full(r: Res), case Empty }
    extension Holder: NoCopy {}

    func make(i: Int) -> Holder {
        if i > 2 { return Holder.Empty }
        Holder.Full(r: Res(name: "r{i}"))
    }

    func slow() { sleep(Duration.ms(1)) }

    func driven() -> Int {
        var total = 0
        var i = 0
        while i < 10 {
            slow()
            match make(i) {
                case Full(r) if i == 1 -> { print("guarded {}", r.name) },
                case Full(r) -> {
                    print("plain {}", r.name)
                    if i == 2 { break }
                    total += 1
                },
                case Empty -> { break }
            }
            i += 1
        }
        total
    }

    func main() { print("{driven()}") }

MECHANISM (named, per obligation 4): a guard on ANY arm routes the whole match through the typechecker's GENERAL pattern lowering (`_check_match_general`, expressions.py) rather than the classic variant switch. The general lowering tests arms IN ORDER and EXTRACTS a candidate arm's payload in order to run that arm's guard against it. On an OWNING payload the extraction is a TRANSFER, so an arm whose guard FAILS has already consumed the value the next arm is about to bind; the coroutine transform's dispatch/state split then moves the same payload into its frame slot a second time (`_store_binding_in_slot`, which asks `Namespace.read_policy` and correctly answers 'move' for both). Neither half is wrong on its own — the extraction is not sequenced against selection.

THE MATRIX (each row a compile+run of a sync/driven twin pair; the suspension is `sleep` before the match, inside a loop):

  | arms                          | payload tier   | sync | driven |
  |-------------------------------|----------------|------|--------|
  | guard + 1 owning payload      | NoCopy         | OK   | double free, exit 0 garbage |
  | guard + 2 payloads, 1 owning  | NoCopy + Int   | OK   | double free, SIGABRT |
  | guard + 2 payloads, both Copy | String + Int   | OK   | OK |
  | guard, payload String         | Copy (retain)  | OK   | OK |
  | guard, generic enum payload   | Copy (String)  | OK   | OK |
  | NO guard + 2 payloads, owning | NoCopy + Int   | OK   | OK |
  | NO guard + 1 owning payload   | NoCopy         | OK   | OK |

So it is exactly the PAIR (a guard anywhere in the match, an owning arm binding). The Copy tiers are sound because a retained/trivial extraction consumes nothing, and an unguarded match is sound because the classic switch extracts only the arm that was selected.

WHY IT WAS INVISIBLE UNTIL NOW: a guarded match in a driven body could not COMPILE at all before the SL-273 batch. `_match_binding_types` (coro_transform.py) reads payload types off `matched_enum_type`, which the general lowering never stamps, so every arm binding of a guarded match went without a frame field and the program died `Undefined variable: <binding>`. The batch closes that census gap; with the bindings now resident, the shape reaches codegen and the extraction defect becomes visible. In other words this issue was MASKED by a different bug, not introduced by fixing it.

WHAT THE BATCH BRANCH DOES INSTEAD OF FIXING IT: `_split_match` gains `_check_guarded_owning_payload`, refusing the pair cleanly and anchored at the guard —

    error: coroutine transform: a suspension-spanning `match` in `driven` cannot
    combine a guarded arm with the move-only payload binding `r`; drop the guard
    and test inside the arm body, or match on a copyable projection of the payload

— so the shape is a diagnostic rather than a double free, and the Copy tiers keep working. Lifting the refusal is this issue's job; the fix belongs in the general lowering's extraction/selection sequencing, and the refusal in `_split_match` comes out in the same landing as its pin `examples/errors/coro_guarded_arm_owning_payload.saw`.
