Found by the Air reviewing SL-885.p1 (c-review on SL-885). `Command(program: "this_command_does_not_exist_zzq").wait()` fails with `exec failed (the program could not be launched)`, naming no program. Stage 0's `ProcessError.program_name()` carried it, and `tests/corpus/process_error_surfaced.saw` pinned that until SL-885 rewrote it to the current API. A caller running several commands can't tell which one failed (sawtracker adds the name itself). Under 'APIs do the expected thing', the std's spawn failure should name the program (and say why: not found, not executable, …). Fix: `SystemError` from `Command`'s spawn carries the program in its rendering (the shape of that detail is a std ruling; propose one), and `process_error_surfaced` pins it again.

**RULED (the user, Oct 25):**
- **Every std op with a subject names it** (A1): `SystemError` gains `subject()`, rendered `<op> "<subject>" failed (<kind>)`, covering Command, File, Directory, Env and IoError's net ops. There's no allocation on the error path and no signature change.
- **The real exec cause in the SAME unit** (B1): a close-on-exec errno pipe, so not-found and permission are distinct and a child's own 127 is `Ok(127)`.

**Lead:** `rename` names the source only; `launch` for an exec failure (`spawn` for a fork failure); a NUL renders `\0`; `listen`'s validation prose is fixed. B1 first proves whether it needs a seed bump (SL-896 showed a seam-body change doesn't).

**Step 1 (p898):** every exec failure renders the same and loses its cause (exit 127); a program's own 127 is misread as a launch failure; and NO `SystemError` op names its subject.
