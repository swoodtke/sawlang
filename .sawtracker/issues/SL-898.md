**Air, before B1 lands: no descriptor the runtime opens is close-on-exec, and that's a class finding wider than this issue.** Probes are in `.build/scratch/air-review/sl898/` on the Air, run on main 615e471dd+.

**Mechanism:** `git grep CLOEXEC -- runtime/ std/` finds nothing.
- `__saw_open_flags` (shim.c) returns bare `O_RDONLY` / `O_WRONLY|O_CREAT|…`.
- `proc_spawn_impl` (`runtime/common/proc.saw`) calls `pipe()` before `env_lock_take()`, with no `FD_CLOEXEC`.
- The child, between `fork` and `execvp`, closes only its own pipe's ends.

So every child inherits every descriptor the program has open, including other launches' capture pipes.

| probe | result |
|---|---|
| c4: a child launched after `File.open("/etc/hosts")` and `TcpListener.listen(port: 0)` | its open fds go 5 → 6 → 7, and `lsof` in the child shows `/private/etc/hosts` and `localhost:62129` (the listener) |
| c2: each child counts its own fds, while 7 pool threads keep launching | quiet baseline: at most 5; under concurrent launches: **15-16 in every run**, about 10 other launches' pipe ends |
| c3: 7 threads of quick `printf x` drains plus 1 thread launching `sleep 1` children | 3, 2 and 1 of 1,750 quick `output()` calls stall over 500 ms (about a second each): a sleeper inherited their pipe's write end, so their EOF waits for an unrelated child |

**Consequences:**
- An `output()` can hang for as long as any concurrently launched long-lived child lives (a daemon: unbounded).
- A child keeps a closed listener's port bound and holds connections half-open.
- Every child sees every file the program has open.

**For B1 specifically:** an errno pipe without close-on-exec in a sibling's child never reaches EOF, so the parent's read for "exec succeeded" blocks until that sibling's child exits. That's a launch-time hang, not just a stall.

**The platform constraint** (checked in the macOS SDK): `unistd.h` has no `pipe2`, and macOS has no `accept4`/`SOCK_CLOEXEC`. So on macOS, "create, then `fcntl(FD_CLOEXEC)`" is only safe if it happens under the same lock the fork takes (`env_lock` already spans `fork`), or launches move to `posix_spawn` with `POSIX_SPAWN_CLOEXEC_DEFAULT`. Linux has `pipe2(O_CLOEXEC)`, `O_CLOEXEC`, `SOCK_CLOEXEC` and `accept4`.

I'd file this as its own issue (obligation 4): every descriptor-creating seam (open, pipe, socket, accept, opendir) × each host, plus B1's errno pipe. On SL-898's patch I'll rerun c2/c3 and a concurrent-launch hang test of B1 under a timeout.

**Folded in (lead):**
- **SL-910 (high), close-on-exec:** the errno pipe depends on it. The guarantee is the child-side close of every fd but 0-2 and the errno pipe between `fork` and `exec` (`close_range`/`closefrom`, or a loop bounded by `getrlimit` read in the parent). Defense in depth: `O_CLOEXEC`/`SOCK_CLOEXEC`/`accept4`/`pipe2` on Linux, and `fcntl(FD_CLOEXEC)` under the env lock on macOS.
- **A runtime PATH search plus `execve`, replacing `execvp`:** `execvp`'s `/bin/sh` fallback on `ENOEXEC` breaks 'no shell, ever' (design 122) and caused the `Ok(126)` misreport.

**The child path between fork and exec** (`proc.saw` child branch, `shim.c`) allocates nothing and takes no lock. It runs:
- close/dup2;
- `__saw_close_inherited`: `close_range` twice around the errno pipe on Linux; on macOS `proc_pidinfo` into a 512-entry **stack** array, with the loop to the parent-read limit as the fallback;
- `exec_search` over candidates the parent built (and frees after the fork);
- the errno write, then `_exit`.

The macOS pipe is marked after `pipe()`, so racy on its own, but the child-side close is the guarantee, and c2/c3 show it holds.

**Launch causes and the PATH search** (`l1_launch_causes.saw`, ASan) behave like `execvp`, minus the shell:

| case | result |
|---|---|
| `/nonexistent/prog` | `launch "/nonexistent/prog" failed (not found)` |
| `/etc/hosts` (not executable), `/tmp` (a directory) | `… failed (permission denied)` |
| an executable script with no `#!` | `… failed (not an executable)`, never run by /bin/sh |
| `sh -c 'exit 127'` | `Ok(127)` |
| PATH = non-exec `tool` dir, then exec `tool` dir | runs the later one (`bin2`) |
| PATH whose only `tool` is not executable | permission denied (EACCES remembered) |
| `./tool` | not searched; not found |
| PATH unset | the default search finds `ls` |
| PATH empty | the current directory only; `ls` not found |

**The suggestion: escape the rest of the subject as well as NUL** (`l2_subject_chars.saw`):
- `open "/nonexistent/a"b" failed` has an unescaped quote, so the subject's extent is ambiguous.
- A newline in a path splits the error over two lines in a line-oriented log.
- A backslash isn't escaped, so a name with the two characters `\0` renders the same as one with a NUL.

Rendering the subject as a string literal (`\"`, `\\`, `\n`, `\0`, control characters as `\xNN`) would make it one unambiguous line. A 4,800-byte path renders whole, ending `failed (other error, errno 63)`: ENAMETOOLONG falls to the raw code, which is fine.
