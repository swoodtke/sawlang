## Description

GRAMMAR.md contradicts itself on `move self`.

**The two readings:**
- **Removed.** The removed productions `syntax.expr.refused-move-self` and `syntax.expr.move.refused-self` say `move self` is not Saw.
- **Legal.** `move-expr.place`, through `move-base.self`, derives `move self` as an ordinary move of a place.

**What the recognizer and corpus do:**
- The recognizer accepts it as `(Move.place (SelfExpr))`, since no §13 rule chooses between the two readings.
- The generated corpus pins acceptance: `syntax.expr.move-base.self/alt` is `func a() { move self }`.
- Both removed alternatives are waived in `compiler/tests/parse/waivers.tsv`. The waiver says the positive stands as the current reading until this ruling.

**Ruling needed (the user's):** is `move self` Saw?
- **No:** remove `move-base.self`, or exclude `self` from the place form. The generated positive then becomes a negative named for the removed production.
- **Yes:** retire the two removed productions and drop the waivers.

LANGUAGE_SPEC.md's consuming-method text (`consumes`, SL:borrowing) should agree with whichever way it goes.


## Comments

<!-- sawtracker:comment {"author":"agent:claude-sawlang","body_bytes":1029,"created":"1790456749","id":"c1"} -->
User ruling (relayed by the lead, Sep 26): `move self` is Saw, inside a `consumes` method only. Its meaning is the field rule taken whole. The referent is the callee's to end, so `move self` hands the whole value onward, and the end-of-body sweep then releases nothing. The type's deinit runs wherever the value finally ends. Like a field move, it is decided on every path or on none, and it cannot follow a `move self.<field>`. Outside a consuming body it is a type error, like the field form, and not a grammar refusal. The work: GRAMMAR.md keeps `move-base.self` and retires `syntax.expr.refused-move-self` and `syntax.expr.move.refused-self`, and the two parse-corpus waivers go. LANGUAGE_SPEC's 'Moving a field out' gains the whole-receiver case: consuming builders (`func with(&var self, n: Int) consumes -> Builder { …; move self }`), forwarding (`(move self).close()`) and wrapping. The frozen sawc refuses `move self` with a dedicated parse error; that becomes a §16 disagreement, since the Python compiler is frozen.

Brief obligation 3 applies here. The whole-receiver move is a safety-surface change, next to design 260's consuming rows V51–V56 in examples/conformance/INDEX.md. So the work's first step is the ledger.

**V56 needs a qualifier.**
- It currently says "the hand-written body does not run for a consumed receiver".
- Under this ruling, a consuming body that ends in `move self` is not the value's endpoint, and "the type's deinit runs wherever the value finally ends".
- So V56 holds only where the consuming body ends the value. Say so, or the two rules read as contradictory.

**New rows, each a guarantee the ruling states:**
- `move self` hands the value onward. The end-of-body sweep releases nothing, and the deinit runs exactly once, where the value finally ends.
- `move self` on some paths but not others is refused. This is V54's every-path-or-no-path rule, taken whole.
- `move self` after `move self.<field>` is refused.
- `move self` outside a consuming body is a type error, not a grammar refusal.

**Coverage.** The frozen sawc refuses `move self` at parse, so no row can be covered by a passing test today. Record the rows as owed to the self-hosted compiler, cross-referenced to the new §16 row, so the ledger still names every guarantee the language claims.
