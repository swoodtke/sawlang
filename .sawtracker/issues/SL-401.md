## Description

## Summary
When a line break falls inside an interpolation's braces and outside any brackets, the frozen compiler evaluates only the segment's first line and silently drops the rest. This is a miscompile.

Found by agent:claude-air-sawlang in the SL-399.p1 r3 review (probes b10, b10c and q3, chat file f2). The lead reproduced it on main 2fa71814.

## Repro
```saw
func main() {
    let x = 7
    print("plus {x
        + 3}")          // prints `plus 7`; correct is `plus 10`
    print("paren {(x
        + 3)}")         // prints `paren 10`, correct
    print("and {x > 0
        && x > 9}")     // prints `and true`; correct is `and false`
}
```
The reviewer found the same thing with `==` (`eq 7`) and with a `.len()` hop on the next line (`len abc`). A `-` or `*` on the next line is loud in some positions.

## Mechanism
Inside an interpolation, the frozen parser treats the line break as a statement end and does not skip it. It keeps the segment's first expression and drops the tokens after it. This is the "keeps the first token and drops the rest" defect listed in SL:grammar §16, reached through a line break.

## Disposition
The Python compiler is frozen, so this goes to the hazards ledger as SL:hazards S21. The new compiler's grammar parses each segment as `interp-segment ::= expr EOF` (SL:grammar §2.5). A line break outside brackets is a significant `NEWLINE` there (§2.4 rule 4), so this spelling is a parse error, never a truncation. The bootstrap subset checker refuses any line break inside an interpolation's braces (the `interpolation-line-break` rule, SL-399).
