**sawc2's typecheck panics on a `Map` or `Set` literal under the new std** (`--std-root std`), instead of giving a diagnostic.

```
$ .build/sawc2 typecheck --check --std-root std tests/corpus/map_literal.saw
panic at vector.saw:90: Vector.[]: index out of range: -1 (len 453)
```
This hits 25 corpus programs (coroplan's census, SL-545). `tests/corpus/map_literal.saw` reproduces it.

**Mechanism.** `compiler/typecheck/src/api.saw` resolves its known std declarations once, with `top_decl(module_named("std.map"), "Map")` and the same for `Set`. The new `std/` has neither module, so both come back as -1. The literal's typing then uses that -1 as a declaration index. Nothing checks the "known declaration absent from this std root" case.

**The class.** Every known declaration resolved in that block is reached the same way: Map, Set, and whichever others that table names that the new std does not define. Each one crashes on the first construct that needs it, instead of saying which std module is missing.

**Fix.** At each place a known declaration is used, check for its absence. Report a clean diagnostic that names the construct and the missing module, for example "a Map literal needs `std.map`, which the std root does not provide". Route it through one helper, so the next missing declaration gets the same treatment. The real `Map`/`Set` ports are separate std work.

**Pins:** `map_literal.saw` and a `Set` literal under `--std-root std` each give the diagnostic, not a panic. Add a row for any other declaration in the table that the new std lacks.

Sweep of the class (Air; obligation 4). Of `api.saw`'s known std declarations, SIX are absent under `--std-root std`: `std.serde.Serialize`/`Deserialize`, `std.map.Map`, `std.set.Set`, `std.arc.Arc` and `std.taskgroup.TaskGroup` (`Box` and `Vector` are present, and the builtins resolve). Each one's typecheck use:
- **`serialize`/`deserialize`:** `conform.saw:350`, only as `t == self.known.serialize`;
- **`arc`:** `bodies.saw:5808`, `d >= 0 && (d == self.known.box || d == self.known.arc)`;
- **`task_group`:** `bodies.saw:5802`, `d >= 0 && d == self.known.task_group`;
- **`map`:** `bodies.saw:4425`, `let md = self.known.map`, then USED as a declaration index (the literal's typing);
- **`set`:** `bodies.saw:4470`, `let sd = self.known.set`, likewise.

So the crash class is exactly the two literal sites. The other four are only ever compared against a VALID id, and `-1` never equals one, so they're safe by construction today, and the name itself is refused earlier by resolve when written. The fix's pins are the two literals (`map_literal.saw` and a `Set` literal). The helper the issue proposes is still worth it, as an accessor that returns `Optional` or refuses with the module named, rather than a raw `Int`: the next implicit use (a `TaskGroup` form, a serde derive) then can't index with -1 by accident.
