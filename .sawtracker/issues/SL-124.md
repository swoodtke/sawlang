- **DF‑168b — the place-lowering re-entry re-checks std for every program, and a
  dirty flag cannot avoid it.** DF‑164d, measured after the rest of the batch:
  the re-entry is now the single largest stage of a compile (30.3% of `hello`;
  two passes, ~0.4 s, for a driven program). The obvious saving does not apply —
  `hello.saw` is four lines with no place uses of its own and STILL forces it,
  because the program `transform_place_uses` rewrites is **std** (85 extensions),
  and it `uncheck`s every program in its list once any one changed. std is dirty
  for essentially every program. What WOULD work: std's post-lowering state is
  the same for every program, so cache the pair AFTER place lowering. The blocker
  is that `transform_place_uses` gets ONE merged namespace with no per-module
  scoping, so a user `borrows` extension on a std type could in principle change
  how std's own bodies lower — either a design-142 scoping violation to fix
  first, or a contribution the key must cover. A design question, not an
  implementation detail. Worth its own brief: it is ~30% of every compile and
  design 168's cache machinery is most of the implementation.

## Fresh reproduction (Sep 10 2026) — CONFIRMED, and its scope is now measured

Reproduced on main at aa3d3e6b, host arm64, warm `.build/rt/` and warm
`.build/stdcache/`, with `perf_counter` at the driver's phase boundaries (no
profiler). Three consecutive runs of `examples/hello.saw`, the same program
the original DF-168b measurement used:

| phase | sec | % of compile |
|---|---|---|
| **std RE-typecheck on the place re-entry** | **0.61** | **36.3%** |
| monomorphization | 0.56 | 32.9% |
| place lowering | 0.19 | 10.6% |
| builtins (stdcache restore) | 0.10 | 5.7% |
| everything else, LLVM included | 0.25 | 14.5% |
| TOTAL | 1.70 | |

Variance across the three runs: 36.2 / 36.3 / 36.3%. The original entry said
30.3%; it is 36% today, so the finding has NOT decayed — it has grown.

The mechanism is exactly as recorded. `_prepare_codegen` recurses for place
lowering with `builtins=None`, so `build_builtin_namespace` runs a second time
over the place-lowered std AST. The design-168 `.build/stdcache/` blob cannot
serve that second call because the AST it would restore has been mutated by
the transform. std is NOT re-lexed or re-parsed (the `parsed=` hand-off keeps
the ASTs) and it is NOT repeated per module — once per program, once more on
the re-entry.

## What the fresh measurement ADDS: this is a fixed cost, not a proportional one

The 0.61 s is the same 0.61 s for every program, because it is std being
checked, not the user's code. So the percentage is a statement about how small
the program is, and the finding's real value depends entirely on which workload
you point it at:

* **A minimal compile** — 36%, as above. Together with monomorphization
  (another 33%, and also nearly all std) **69% of a `hello` compile is fixed
  overhead independent of the program being compiled.**
* **The test suite** — this is where it actually costs. At ~1,500 compiles per
  suite run, the re-entry's std re-check alone is roughly **16 minutes of CPU
  per full suite**, and the compiler dev loop pays it on every run.
* **A real application** — measured on the sawtracker server itself (6 modules,
  98 KB of Saw, a 115 s compile): the same 0.69 s is **0.6% of the compile**.
  See SL-230 for that phase table; 80% of that compile is one LLVM
  `emit_object` call and nothing in the Python front half is close.

So the standing "revisit when compile speed next hurts" trigger has now fired
in one direction and not the other. Compile speed hurt on a real app, and this
was NOT the cause there. It remains the single largest item in a small compile,
which makes it a TEST-SUITE and dev-loop optimization — worth scheduling on
that basis, and worth NOT scheduling on the expectation that it speeds up
building an actual Saw program.

The design blocker recorded in the original entry is unchanged and untested by
this reproduction: `transform_place_uses` gets one merged namespace with no
per-module scoping, so caching std's post-lowering state still needs the
design-142 scoping question answered (or covered by the key) first.

Filed by the compile-performance investigation; no implementation proposed here.
