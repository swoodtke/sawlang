**`Float.min`/`max` are always the Saw body: emit `llvm.minimumnum`/`maximumnum` where the toolchain lowers them to the ruling.** A follow-up to SL-944.

**Why the Saw body today:** SL-944's capability funnel (`target_float_instruction`, `compiler/target/src/layout.saw`) marks min and max "Saw body" on every target, because sawc can't know at emission which clang will compile the module:
- The Linux VM's clang-19 (19.1.7) has no `llvm.minimumnum`/`llvm.maximumnum`. It leaves `llvm.minimumnum.f64` as an undefined external, so the link fails (SL-944's U5, `.build/scratch/p944i/u5_vm_nm.txt`).
- Apple clang 21's x86_64 lowering gives `minimumnum(±0)` = +0, against the SL-944 ruling (−0 < +0).
- Homebrew clang 23 on arm64 lowers both to `fminnm`/`fmaxnm` sequences that meet the ruling.

The Saw body is about 41–48 instructions at -O2, against a few `fminnm`s.

**What a fix owes:** either the toolchain floor rises to a clang whose lowering meets the ruling on every target (the VM pin, `build.choose_clang`'s candidates, a documented minimum), or the funnel learns the chosen clang's version. Each "instruction" cell is proved by the `float_lowering.py` lane check and by the vectors (`compiler/tests/run/float_methods.tsv`) on every host lane. Perf via measurement: schedule this when a profile shows min/max matter.

**Also:** `compiler/tests/run/float_numeric_methods.saw`'s line-1 comment still says the methods lower to libm. It wasn't edited in SL-944, because both Stage 0 records key on the file's bytes and the Linux record can't be re-recorded. Fix it by re-recording the Mac record only, or by converting the program to a stated probe.
