**Ruled by the user (Oct 11): option (b).** A pinned sawc2 seed binary replaces Python Stage 0 as the bootstrap. Recorded in SL:open-questions, "Bootstrap seed".

**Depends on SL-522:** a seed must link without Python, so sawc2 has to run clang itself and build its own runtime objects first.

**Design to settle in this unit's brief:**
- **Release:** the seed's binaries, one per host that sawlang builds on (arm64-apple-darwin today; x86_64 and aarch64 Linux when hosted Linux builds are in scope).
  - Where they're published: GitHub releases, downstream of sawtracker; ST-46 already tags releases from `.sawtracker/version`.
  - How each is checksummed: a SHA-256 in a tracked pin file.
- **Pin:** a tracked file names the seed's version and per-host SHA-256s. `tools/toolchain.py`, the design-238 resolver (SAWLANG_ROOT, then `$PATH` plus the pin, then a cached fetch), fetches and verifies the seed into `.build/seed/`. A checksum mismatch is a refusal, never a warning.
- **Build:** `compiler/tools/build.py` builds sawc2 with the seed by default. Stage 0 (`sawc/`) stays selectable, frozen, until the first seed release bootstraps a clean checkout end to end.
- **The fixpoint gate:** the `stage1` lane's chain becomes seed → Stage 1 → Stage 2, with Stage 1 equal to Stage 2 byte for byte. A seed may differ from Stage 1, since it was built from older source. It must only build the current source.
- **Bumping the seed:** each release can serve as the next seed. Say how often the pin moves, and that a pin bump is its own patch.

**Then:** the lanes run on the seed-built compiler, Stage 0 retires, and SL-425 reverts the workaround markers, S28's included.

**Numbering (decided Oct 11, after the Air's note on SL:hazards):** conventional bootstrap numbering everywhere. Stage 0 is Python `sawc/`, Stage 1 is what Stage 0 builds (`.build/sawc2`), Stage 2 is built by Stage 1, and the fixpoint is Stage 2 = Stage 3. With the seed, the seed builds Stage 1 and the chain continues the same way. U7b's lane used one lower; u7c renames it in SL-535 (M0).

From the Air's SL-522.p1 review (non-blocking for M1): sawc2 reads its runtime manifest (`sawc2-runtime.txt`) from beside `argv[0]`, so run by bare name through `PATH`, or through a symlink, it looks in the wrong directory and fails cleanly ("cannot open ./sawc2-runtime.txt"). The seed comes through `tools/toolchain.py`'s `$PATH` step and `make install`'s `bin/` shims, which are exactly those two cases. Before this unit depends on it, sawc2 resolves its real executable (`_NSGetExecutablePath` on macOS, `/proc/self/exe` on Linux, then `realpath`). The runtime-build work (SL-522 M2b) may change where the manifest lives; whichever lands, this requirement holds.
