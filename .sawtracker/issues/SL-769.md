## Description

**Retire `VoidTask`: a `Void` task is `Task<Void>` (the user's ruling, Oct 16; reasoning on SL-765 in the comment that records it).**

`group.spawn(f())` and `Task.spawn(f())` with a `Void`-returning `f` yield `Task<Void>`. `join()` returns `Void`, so it is a statement; binding its result is the visible-`Void` error. `detach` and `cancel` are unchanged. The design-242 claim that `Task<Void>` is unwritable as an annotation was a misreading: the visible-`Void` rule forbids binding a `Void` value, not naming `Void` as a type argument, and sawc2 instantiates generics at `Void` today.

**Scope (a consumer sweep, obligation 2):**
- **std:** `std/taskgroup.saw`'s `Task<T>` works at `T = Void` (a zero-sized result slot; join and double-join semantics as the spec states them for a valued task, or the spec says where `Void` differs), and `VoidTask` is deleted.
- **compiler:** the spawn typing that picks `VoidTask` (A7c's front half, A7a's lowering, A7d's must-consume minting) picks `Task<Void>`, with about 16 test files under `compiler/`.
- **docs:** the spec (7 `VoidTask` mentions, including the std module table and design 242's rationale text), the saw-lang skill and README.
- **corpus:** the 7 programs naming `VoidTask` and their `examples/` twins, rewritten and re-snapshotted. Stage 0 can't build a `Void` field, so rows that then pass become annotated `stage0-wrong`.

**Pins:** a `Task<Void>` stored in a struct field and in a `Vector`, joined, detached and cancelled, each fate once; and the binding refusal (`let x = h.join()`).

**Coordinate with SL-765:** `Thread<Void>` lands there. Whichever lands second makes the spec's handle section read as one rule for both engines.

**The user ruled (Oct 16), on p769's stop: one rule for every `T`, `Void` included.**
- **A second `join` panics** for every task, `Task<Void>` included. The spec's "`VoidTask.join` returns" exception goes, and `taskgroup_stale_handle_cancel` is re-expected.
- **A task whose handle is already gone has its result DROPPED and its slot FREED at completion,** for every `T`. A handle dropped after completion drops the result and frees the slot at the drop. So an accept loop's slots stay bounded whatever its tasks return (design 134's guarantee, now for all `T`).
- **Observable change:** a dropped valued task's result deinits at its completion (or at the handle's drop, if later), no longer at the group's teardown. The spec's text on this ("`Task`'s `Deinit` owns nothing and leaves the result in the group's cell", the slot-reclaim rule, the double-join rule) is rewritten.

**So this unit grows:**
- **`std/taskgroup.saw`'s `complete` and the handle-release path:** the result is held whenever the handle lives, at any size, which is SL-691's fix. The reclaim-on-drop rule above applies to every `T`. These are no longer limited to the `Task` declarations.
- **The compiler sites from p769's sweep (c-latest):** `typecheck/src/program.saw`, `drops/src/elaborate.saw`, `compiler/tools/std_suspension.txt`, `subset_check.py`'s `SYNC_ONLY_NAMES`, `coro/census.py`'s `PLAN_TYPES`, and the goldens and READMEs listed there.
- **Pins:**
  - a dropped-handle valued task (an owning `T` with a printing `deinit`) dropping its result at completion;
  - the same with the handle dropped after completion;
  - an accept-loop-shaped soak with a valued `T` whose peak slot count stays bounded;
  - the double-join panic on `Task<Void>`;
  - `Task<Void>` stored in a field and in a `Vector`.
- **Order:** after SL-765 T2 lands, since T2 is editing `taskgroup.saw`. The lead re-dispatches then.
