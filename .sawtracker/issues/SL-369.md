The parser's nesting budget is contract (design 259 R4: 256 levels, one named
constant, cited by the diagnostic). Every pass BEHIND the parser has a budget
too, but an accidental one: each walks the AST recursively, and its ceiling is
Python's default recursion limit divided by that pass's per-node frame cost. So
a program the parser accepts can still die downstream, and the depth at which
it dies depends on which node shape it is made of.

Measured on the SL-2 U0′ branch (parser budget 256, refusal at 257), bisecting
the deepest source that compiles end to end:

    groups        `(((…1…)))`                       256   compiles
    unary         `---…-1`                          256   compiles
    mixed         groups wrapping nested ifs        256   compiles
    calls         `identity(identity(…1…))`         245   ICE at 246
    nested ifs    `if true { if true { … } }`       196   ICE at 197
    else-if chain `if false { } else if … { }`      196   ICE at 197

The failure is a CLEAN internal compiler error (`maximum recursion depth
exceeded`, with the node kind and a source position), not a traceback or a
segfault — the downstream funnels do their job. What is wrong is the NUMBER:
the compiler refuses a program its own stated grammar limit accepts, and says
`internal compiler error` while doing it.

MECHANISM (obligation 4): one mechanism, not three symptoms — every AST-walking
pass inherits the interpreter's default recursion limit, which no pass states
or owns. The parser is the only walker with a budget of its own; it now raises
the interpreter limit for the span of the parse and restores it afterwards, so
the passes that run next are back on the default. The siblings this reaches are
every pass that recurses over the tree: the typechecker, `coro_transform`,
monomorphization, codegen and `ast_dump`. Which one trips first depends on the
node, which is why `calls` and `if` chains die at different depths.

SHAPE OF A FIX (not this unit's — U0′ owns `sawc/parser/` only): either the
compiler holds ONE recursion budget across all passes, sized from the parser's
256 the way the parser sizes its own, or the nesting limit drops to a number
every pass clears. The first keeps 256 as the single contract; the second makes
the ruled number smaller than the prototype's, which design 259 §0 freezes, so
it is a ruling rather than a fix.

PINS: `examples/nesting_limit_accepts_the_budget.saw` carries the three shapes
that do compile at 256. `examples/nesting_limit_accepts_deep_calls_and_ifs.saw`
carries the three that do not, as an XFAIL citing this issue, with the intended
behavior spelled out — so the fix flips it to XPASS.

CLOSED by design 274 U0′ (SL-2), the same landing that filed it — the mechanism
named here turned out to be the funnel's own, not a separate defect.

The depth funnel raises the interpreter's recursion limit to cover the 256-level
budget. It originally RESTORED the old limit when the outermost charged level
closed, which is why the parser accepted 256 and every later walk of that tree
then ran on the default: the typechecker at 196 for `if` chains, 245 for calls,
and `tools/dump_ast.py` — codex's parse-only oracle — at 256 for `if` and
`else if`.

The fix is that the budget belongs to the TREE, not to the parse: the funnel
raises the limit process-wide, never lowers it, and never gives it back. It
still refuses to lower a limit an embedder set higher. Re-measured after, with
the same bisection that produced the table above:

    groups        256   unary   256   mixed          256
    calls         256   ifs     256   else-if chain  256

All six compile and run at 256 and refuse at 257 at the construct's opener.

Pins: `examples/nesting_limit_accepts_the_budget.saw` carries all six shapes at
256; the six `examples/errors/nesting_limit_*.saw` carry their 257 twins. The
XFAIL pin this issue was filed with is gone — it never reached main.
