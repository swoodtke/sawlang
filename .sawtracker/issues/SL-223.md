## Description

With main 88fa56ba, a call that passes '&var <frame local>' alongside a SUSPENDING argument in the same argument list fails: 'cannot assign &var JsonValue to field of type UnsafeRef<JsonValue>' (sawtracker hit it at store.saw mutate/mutate_patch and app.saw dispatch, e.g. common.set_text(&var response, "sync", sync_project(&st, prefix))). The transform lifts the borrowed local into an UnsafeRef frame field because the call suspends mid-argument-evaluation, then re-checks the raw &var against the lifted field type - a genuine miscompile-turned-type-error, not a rule.

Reproducer: sawtracker repros/coro_ref_arg.saw + repros/coro_ref_arg_mod.saw (12 lines: mod.set_text(&var out, mod.slow()) inside a driven cross-module function). Worked around in sawtracker ST-13 by hoisting the suspending argument into a let before the call.

Claiming. Root cause is NOT the UnsafeRef re-check, it is the ANF hoist upstream of it: coro_transform._anf_is_pure marked EVERY '&var' borrow impure (design 147 unit C's coarse filter), so _anf_children lifted the borrow itself into 'let __anfN = &var out' as a side-effecting left sibling of the suspending argument. Saw has no such statement (a reference is parameter-only), and the ref-encoded frame field it produces is UnsafeRef<T>, which the raw &var cannot be stored into -- that is the reported type error. Fix: a borrow NAMES storage rather than evaluating it, so it is exempt from the lift; only a call buried in the PLACE (an index expression) is observable, and that is lifted instead, inside-out, leaving '&var v[__anfN]' in the argument. Reproduces SAME-MODULE in 21 lines too, so the module boundary is a reach, not a precondition.
