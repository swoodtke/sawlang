## Description

**A TYPE parameter is accepted as an array length where it is written: `func f<T>(a: [Int; T])` typechecks, and fails only at the backend.** Found by the Air's review of SL-1115.p1 (Nov 14); older than that patch.

- `func f<T>(a: [Int; T])`, called `f<Int>([1, 2])`: before SL-1115 it was refused only at the backend (`backend.not-yet` at the parameter); with SL-1115 the call's literal is refused first, with a sentence that shows the gap: "`[Int; Int]` holds `Int`, a length fixed only at each instantiation".
- The declaration itself is never refused: an array length that names a type parameter (not a const parameter) is accepted by resolve and typecheck.

**Expected:** a refusal at the declaration, at the length: a length is a constant expression, and a type parameter is not a value (the spec's const-generics text and GRAMMAR.md's array type decide the wording: `type.argument-kind` or the constant grammar's `static.not-constant` family; find which rule the reverse mistake, a const parameter where a type is wanted, gets today, and mirror it).

**Sweep:** a type parameter, a type alias, a struct name, a trait name and `Self` as a length, as a repeat count (`[0; T]`) and as a const generic argument (`Buf<T>` where `Buf<const N: Int>`), in a signature, a field, a local annotation and an extension; and the reverse (a const parameter where a type is wanted), for symmetry of messages.
