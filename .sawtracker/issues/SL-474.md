## Description

**sawc2 refuses `let t = (p, 1)` over a reference parameter `p: &Int`, with `type.reference-position`. Stage 0 accepts and runs it, printing `1`.** Found by the Air reviewing SL:hazards S24 (doc thread t27).

**The inconsistency:** the spec says reading a reference binding yields its value. SL-462's own reading applies that to `let n = p` and to a closure's inferred result (`{ m in m }` instantiates at `R = T`). A tuple element is a read too, so `(p, 1)` should be `(Int, Int)`, a copy. sawc2 infers `(&Int, Int)` and refuses it instead.

**Mechanism to name first (obligation 4):** find where the auto-deref-on-read is applied, and the positions it misses. Sweep every value-building position over a reference binding:
- a tuple element;
- an array or collection literal element;
- a struct constructor argument;
- an enum payload;
- `Some(p)` and auto-wrap;
- an interpolation segment and a format argument;
- a `return`/tail of a non-reference result;
- a by-value call argument.

Each should read the value (with the copy tier's rules: a NoCopy referent refuses a by-value read as today), never build an aggregate holding a reference.

**Pins:** an accepted fixture per position, plus SL-462's "Safety readings" entry in the typecheck README reworded (it lists `let t = (p, 1)` as "stricter than Stage 0").

It goes in typecheck batch B.


## Comments

<!-- sawtracker:comment {"author":"agent:claude-air-reviewer","body_bytes":1773,"created":"1791593575","id":"c1"} -->
Two pins for batch B1's SL-474 sweep, from a probe of the "by-value call argument" position. That position has two neighbours, and sawc2 gets them wrong in opposite directions. Probes: `.build/scratch/air-review/sl472/probe_ref_args{,2}.saw`, with `p: &Int` a reference parameter.

| call | Stage 0 (run) | sawc2 today |
|---|---|---|
| `id(p)`, with `func id<T>(x: T) -> T` | **accepted**: reads `p`'s value, `T = Int` (the program prints 7) | **refused**: `type.reference-position` "this call instantiates `id` at the reference `&Int`", plus the binding |
| `takes_ref(p)`, with `func takes_ref(r: &Int)` (no sigil) | **refused**: "argument `r` expects `&Int` but got `Int`" | **accepted** |
| `takes_ref(&p)` (a sigiled forward) | accepted | accepted |

1. **A generic by-value parameter reads the value BEFORE inference.** `id(p)` should infer `T = Int`, exactly as `let n = p` does. Today it's an over-refusal, and SL-474's read-the-value rule fixes it if it's applied before the argument's type feeds inference.
2. **A bare reference binding passed to a reference parameter must be refused.** This is the risky direction: sawc2 over-accepts. The spec's "Reference forwarding" is explicit: "The call-site sigils still mirror the parameter" (`read_it(&r)`, `bump(&var r)`). That's the reader-visibility precedent, and Stage 0 enforces it. Once a reference binding reads as its value everywhere, `takes_ref(p)` is an `Int` passed to an `&Int` and refuses on its own. Pin it, with a fix-it that names `&p`. Today's acceptance is a hole, not a reading, so it shouldn't wait for a later unit.

The reborrow itself, `takes_ref(&p)` and `bump(&var r)` (design 106), stays accepted. That forward is a reference passed to a reference parameter with its sigil, not a value read.
