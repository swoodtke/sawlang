## Description

In SYNC code, `try EXPR catch { … }` written as a bare STATEMENT whose value is an owning type never destroys that value. The value is discarded, so it should deinit at the statement; it does not, and nothing is reported.

Repro (no suspension anywhere, so the coroutine transform never runs; compiled with the pristine main checkout):

  struct Res { name: String }
  extension Res: NoCopy {
      func deinit(&var self) { print("drop {}", self.name) }
  }
  struct Bad { why: String }
  extension Bad: Error {
      func format(&self, into: &var StringBuilder) { try! into.append(self.why) }
  }
  func produce() -> Result<Res, Bad> { Res(name: "made") }

  func discard_it() -> Int {
      try produce() catch { Res(name: "fallback") }
      7
  }
  func bind_it() -> Int {
      let kept = try produce() catch { Res(name: "fallback") }
      8
  }
  func main() { print(discard_it())  print(bind_it()) }

Observed: '7' then 'drop made' then '8'. Wanted: 'drop made / 7 / drop made / 8'. The BOUND control (`bind_it`) is correct, which localizes it to the DISCARD of a statement-position `TryExpr` value rather than to the try lowering generally.

A leak, not a double free -- no memory is freed twice and the program exits 0. It matters because `try f() catch { fallback }` in statement position reads as a complete, handled operation, and design 151 deliberately made a discarded RESULT a compile error precisely so this shape is written rather than dropped; the value the catch supplies then quietly outlives everything.

PRE-EXISTING and SYNC-side: reproduces on unpatched origin/main with no suspension in the program. Found by SL-222's review-r5 ownership audit, where the DRIVEN twin of the same body was the one that behaved correctly (it does destroy the value) -- so the coroutine path and the sync path disagree, and here it is the sync path that is wrong. Not fixed in SL-222's branch: nothing in that batch touches the sync discard path.
