## Description

**Re-entering a `Mutex` (or `SpinLock`) through another name dies silently with signal 9 on macOS; the spec promises a panic** (found by p821, SL-821 step 1, Oct 23).

The spec (the lock re-entry ruling, Sep 24) says aliased re-entry, meaning the same lock reached through another name (two `Arc` clones, or a task that takes a lock its own thread already holds), PANICS at run time, through the owner recorded in the lock word, and must never deadlock silently. p821's probes `lock_coop_join_in_mutex_window_slow`, in which a cooperative join inside a `Mutex` window drives a task that takes the same lock, die with signal 9 and no message. That is probably `os_unfair_lock`'s own recursive-lock trap, firing before the runtime's owner check (UNVERIFIED). The `SpinLock` variant spins forever.

**"Never hide errors":** a re-entry must print a panic naming the lock and the thread, the way the spec says.

**Scope:**
- the mechanism (does the runtime check the owner before calling into `os_unfair_lock`? Linux's futex owner TID?);
- the fix (check the owner word first, then panic with the message), for `Mutex` and `SpinLock` on both hosts;
- the obligation-4 positions: a direct re-entry, re-entry via an `Arc` clone, re-entry from a task driven inside the window by a cooperative join, and (after SL-821) by a blocking pool wait;
- pins on darwin and Linux.

- **Ruled:** std records the owner itself in an atomic owner word beside each lock word, checked BEFORE acquiring, on every host. No dependence on `os_unfair_lock`'s undocumented encoding, and no runtime lock-body change.
- **The identity:** an existing per-thread facility if one exists (one patch); otherwise a single `__saw_rt_lock_owner` seam lands first with a seed bump.
- **The panic** comes from std (file:line plus dump).
