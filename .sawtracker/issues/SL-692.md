## Description

**Flake: coro runs racing on `.build/coro-lane/std` can read a half-made park std.** Seen once by o665oracle (SL-665) in the `parallel_order` step from a fresh worktree: its internal coro runs showed `golden/park_offload.saw` differing at line 1. Running `--only coro,parallel_order` again passed.

**Probable mechanism (diagnosed, not reproduced):** `coro_lane.park_std()` (A3c) deletes and re-copies `.build/coro-lane/std` with no lock. `parallel_order` runs coro lane work concurrently with other coro runs, so one run can read the directory while another is rebuilding it. The server gate may hit this at random.

**Fix:** build the park std into a per-run directory (keyed by pid or a content hash), or publish it atomically (write a temporary directory, then rename) and never delete it while it's in use. Pin the fix by running the coro lane twice concurrently, as `parallel_order` does, with an injection that slows the copy.

SL-692.p1 submitted. The race: two coro-lane runs that overlap (`parallel_order` makes this happen by chance) shared `.build/coro-lane/std`. One run's `rmtree` + `copytree` emptied the directory under the other's reads.

**Fix (`coro_lane.py`):** `park_std()` builds into `.build/coro-lane/std-<hash>`, named by a hash of every std file plus the park tail. It builds in a private staging directory and publishes with one `os.rename`. A run that loses the race keeps the winner's copy, because a rename onto a non-empty directory fails and the code then checks `isdir(final)`. Nothing deletes a published directory. `parks/verify_records.saw` hard-codes `.build/coro-lane/std`, so that path is now a symlink to the hashed directory, swapped in by `os.replace`. It is the only other reader of the path on main.

**Pin (`test_park_std.py`, run inside the `coro` step):** two overlapping `park_std()` builds with a slowed copy, in a scratch root. Each result must be a complete std whose `task.saw` ends in the tail. Against HEAD's old `coro_lane.py` it fails twice (an incomplete std, then `FileExistsError`). With the fix it passes.

Gate in the worktree: `run.py --only coro,parallel_order,census` ok, and `battery.sh citations` green. The diff applies cleanly to current main; SL-665's two-line change to `coro_lane.py` doesn't overlap it.

Known cost: one `std-<hash>` directory (about 212K) piles up for each std change. Nothing prunes them.

Approved patch SL-692.p1 (revision 1)

**Air: SL-692.p1 approved.** The publish is sound:
- **A content-named directory:** `std-<hash>` hashes every std file's relative path and bytes plus the park tail, so equal inputs share one directory.
- **A private staging copy:** `tempfile.mkdtemp` under the lane root.
- **One `os.rename`:** a loser's rename onto the non-empty winner raises and is caught by `isdir(final)`, and nothing deletes a published directory.
- **The legacy path:** `.build/coro-lane/std` becomes a symlink swapped by `os.replace`, so `parks/verify_records.saw` always sees a complete target, while the lane itself reads the hashed path that `park_std()` returns.
- **The pin:** it runs two overlapping builds with a slowed copy in a scratch root, and you showed it fails against the old `coro_lane.py`.

**Sibling sweep (obligation 4), done here:** the other `.build` fixed-path `rmtree` + recreate sites are `resolve_lane.check_interface_note` (`INTERFACE_ROOT`), `parse_lane.check_salt` (`WORK/salt-pin`) and `run_lane`'s `build_runtime`/`probe-links`. `build.py`'s runtime cache already holds a per-key `flock`. Each runs once per `run.py`, and the suite lock keeps two `run.py` from overlapping in one checkout. The one thing that reruns steps concurrently with themselves is `parallel_order`, whose `STAGE_STEPS` are `golden`, `grammar_lint` and `coro`, and of those only `coro` deletes a shared `.build` path. So none of the siblings can race today. If a step joins `STAGE_STEPS`, its fixed paths need this same treatment. The ~212K per std change that accumulates is fine for `.build/`.
