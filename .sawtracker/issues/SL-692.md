## Description

**Flake: coro runs racing on `.build/coro-lane/std` can read a half-made park std.** Seen once by o665oracle (SL-665) in the `parallel_order` step from a fresh worktree: its internal coro runs showed `golden/park_offload.saw` differing at line 1. Running `--only coro,parallel_order` again passed.

**Probable mechanism (diagnosed, not reproduced):** `coro_lane.park_std()` (A3c) deletes and re-copies `.build/coro-lane/std` with no lock. `parallel_order` runs coro lane work concurrently with other coro runs, so one run can read the directory while another is rebuilding it. The server gate may hit this at random.

**Fix:** build the park std into a per-run directory (keyed by pid or a content hash), or publish it atomically (write a temporary directory, then rename) and never delete it while it's in use. Pin the fix by running the coro lane twice concurrently, as `parallel_order` does, with an injection that slows the copy.
