## Description

Found by the lead's design 275 U3 validation (Sep 22), PRE-EXISTING on main `da84578e` and identical on the `sl318u3` branch — NOT U3's, filed beside it.

## The finding

A closure passed to a method on a reference-parameter root may reach that root INSIDE the method's window, and nothing charges it. The exclusive form is a use-after-free write:

```saw
func grow_then_write(v: &var Vector<Int>) -> Int {
    v.with_var_ref(0, { e in
        var k = 0
        while k < 64 { try! v.push(k)  k = k + 1 }   // reallocates under `e`
        e = 77                                        // lands in the FREED buffer
    })
    v[0]                                              // prints 1: the write was lost
}
```

Compiles cleanly, exit 0, prints `1`. Cells measured (worktree `.build/scratch/lead/l6_with_var_ref_hole.saw`, main and branch agree): `with_var_ref` + 64 pushes + write → `1` (write lost into freed memory); `with_ref` + push → compiles, `2`; `Vector.each` whose body pushes → compiles, `4` (the visitor walks a buffer that reallocates under it). A LOCAL root is already refused, for an unrelated reason — the closure would have to COPY the vector (`cannot copy value of type Vector<Int> which implements ExplicitCopy`) — so the hole is specific to a `&`/`&var` PARAMETER root, which a closure captures by re-borrow (design 216).

## The mechanism (obligation 4)

Design 199 joins a NESTED CALL's references to the outer call's access set, so `v.with_var_ref(0, reset(&var v))` is refused. A closure's BORROW CAPTURES are not joined against the RECEIVER of the call the closure is passed to: the receiver borrow (`&var v` for `with_var_ref`, `&v` for `each`/`with_ref`) and the closure's captured re-borrow of the same root are never compared. Design 146 called `with_ref`/`with_var_ref` "invalidation-proof"; the proof rested on the closure SCOPE, and a captured reference reaches through it.

Siblings the mechanism reaches (every `&self`/`&var self` method taking a NON-ESCAPING closure, called on a reference-param root whose closure names that root): `Vector.with_ref`/`with_var_ref`/`each`/`map`/`fold`/`each_indexed`/`sort_by`, `Map.each`/`each_key`/`each_value`, `Set.each`, `Mutex.lock`/`SpinLock.lock` (a body that re-enters the same lock through the captured root), `Arc.with_unique`. The `&var`-receiver ones are the memory-unsafe half; the `&self` ones are the iterator-invalidation half.

## The fix shape

One rule at the call-exclusivity funnel (`types._check_call_exclusivity`, which design 199 already widened): a closure argument's borrow captures — implicit reference-parameter captures included — JOIN the call's access set, so a capture overlapping the receiver's path is the ordinary exclusivity error naming both. The window record design 275 U3 introduced (`sawc/windows.py`) is the other place the same fact could live, and SL-343 (with_ref/with_var_ref windows across a suspension) is the brief that will want it settled first. Conformance row owed beside K135.

Repro cells: `.build/scratch/lead/l6_with_var_ref_hole.saw` in worktree `sl318u3` (copy into the fix's pin).

## Mechanism, confirmed in code
The `ClosureExpr` branch of `_check_call_exclusivity` joins only `capture_specs`, the written `[..]` list. An IMPLICIT capture of a reference binding is not joined. That covers a `&`/`&var` parameter, `self` in a `&self`/`&var self` method, and an enclosing window's parameter. `capture_modes` records such a capture as `plain` (or as `self`'s receiver mode), and codegen captures the pointer (design 216). The capture is therefore a live borrow that the Law never sees. The residue is one missing input to the existing funnel; there is no second funnel to build.

## The rule
A non-escaping closure argument's implicit reference captures join the call's access set, exactly as a written `[&x]`/`[&var x]` does. They then meet the pairwise overlap test, the design-189 task-borrow cross-check, and design 275 U3's open-window check, all of which run over the same entries.

Access kind of an implicit capture: **the closure captures the binding as it is** (user ruling, Sep 24).
- A `&T` binding, or `self` in a `&self` method, joins as `imm`.
- A `&var T` binding, or `self` in a `&var self` method, joins as `mut`, whatever the body does with it.
- A different capture must be spelled out. `[&v]` takes a shared re-borrow of a `&var` binding, and it is the migration for a read-only visitor.

The rule depends only on the binding's declaration. No analysis of the body is involved.

The rejected alternative was use-derived: `mut` only when the body writes through the name. The ruling's reason: the obvious meaning of an implicit capture is the variable as it stands in the enclosing scope, and a user who wants something else writes it down.

## Implementation shape (obligation 1: the existing funnel, one new input)
- The closure checker records the access kind of each implicit reference capture in ONE declared annotation on `ClosureExpr`, for example `reference_capture_access: Dict[str, str]`, declared with `annotation(...)` so the astgraft lane stays green. Fill it where `captures`/`capture_modes` are computed, from each captured binding's declared reference type (and `self_capture_mode` for `self`).
- `_check_call_exclusivity` reads that annotation beside `capture_specs`. Reading it from a closure argument that has not been checked yet is an internal-compiler-error invariant naming the call, never a silently empty set. Verify the check order at every one of the funnel's fifteen named entry points.
- EXCLUSION: the synthesized place-window closure's receiver root (`place_window_root`) must not join. `_synthesize_place_window_captures` leaves that one name plain on purpose; joining it would make every `v[i]` window conflict with itself. Say why in the code.
