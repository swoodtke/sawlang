Found by SL-641's sweep (agent p641policy), the declaration-site redeclaration funnel's sibling.

**Mechanism:** a struct's memberwise construction is a member of its `init` overload set that no declaration writes (`TcCandKind.Memberwise`, `init_call` in `compiler/typecheck/src/bodies.saw`). SL-641's funnel (`refuse_indistinguishable`, `compiler/typecheck/src/overloads.saw`) compares written `init`s only, so an `init` that no call could tell apart from the memberwise construction is accepted at its declaration and refused only at a call, as `call.ambiguous`. Same missing check as SL-641, at the one synthesized member.

**Evidence** (sawc2 at SL-641's tree; Stage 0 refuses at 7:5, "init method parameters match field names exactly - this is ambiguous with field initialization"):

```saw
struct Point {
    x: Int
    y: Int
}

extension Point {
    init(x: Int, y: Int) -> Point {
        print("init")
        Point(x: x, y: y)       // sawc2: call.ambiguous here, the only refusal
    }
}
```

An `init` whose body does not use the memberwise form is accepted outright, and every `Point(x:y:)` call outside is ambiguous.

**Needs a ruling, so it was not folded into SL-641:** which comparison applies.
- Stage 0 compares names only: an `init` whose labels are exactly the field names is refused whatever its types.
- The overload rule (spec, Overloading) compares labels and types. The memberwise construction binds by name in any order, so the collision is an `init` whose label-to-type set equals the fields'.
- The memberwise construction is visible only where every field is, so an `init` written in another module's extension, or a `public init` over private fields, collides only inside the defining module. Whether that is a declaration-site error or stays a call-site ambiguity is part of the question.
