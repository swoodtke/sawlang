Found by SL-641's sweep (agent p641policy), the declaration-site redeclaration funnel's sibling.

**Mechanism:** a struct's memberwise construction is a member of its `init` overload set that no declaration writes (`TcCandKind.Memberwise`, `init_call` in `compiler/typecheck/src/bodies.saw`). SL-641's funnel (`refuse_indistinguishable`, `compiler/typecheck/src/overloads.saw`) compares written `init`s only, so an `init` that no call could tell apart from the memberwise construction is accepted at its declaration and refused only at a call, as `call.ambiguous`. Same missing check as SL-641, at the one synthesized member.

**Evidence** (sawc2 at SL-641's tree; Stage 0 refuses at 7:5, "init method parameters match field names exactly - this is ambiguous with field initialization"):

```saw
struct Point {
    x: Int
    y: Int
}

extension Point {
    init(x: Int, y: Int) -> Point {
        print("init")
        Point(x: x, y: y)       // sawc2: call.ambiguous here, the only refusal
    }
}
```

An `init` whose body does not use the memberwise form is accepted outright, and every `Point(x:y:)` call outside is ambiguous.

**Needs a ruling, so it was not folded into SL-641:** which comparison applies.
- Stage 0 compares names only: an `init` whose labels are exactly the field names is refused whatever its types.
- The overload rule (spec, Overloading) compares labels and types. The memberwise construction binds by name in any order, so the collision is an `init` whose label-to-type set equals the fields'.
- The memberwise construction is visible only where every field is, so an `init` written in another module's extension, or a `public init` over private fields, collides only inside the defining module. Whether that is a declaration-site error or stays a call-site ambiguity is part of the question.

**The user's ruling, Oct 15**, reached over these messages:
- "should we just allow an extension to override the builtin init?"
- "if the user provides an overridden default, should we just omit the auto-generated one? then the override needs to set every field of the struct manually"
- "can we tighten that a bit - the auto-generated init is only available to the override. every other call to the default init calls the override."
- "have deserialize fail if the init returns an error seems reasonable to me. maybe we can add a DecodeError for .InitFailed or something specific?"

**The ruling:**
1. **An exact-match `init` overrides the memberwise construction.** Its labels, in any order, and its types match the struct's fields exactly. Only the type's defining module may declare one (the orphan rule's reasoning: an importer can't change what `Port(value:)` means).
2. **The raw memberwise construction is reachable only inside the override's own body,** where `Port(value: v)` builds the value from its fields. Every other construction with those labels calls the override, in any module, including the type's other `init`s. So a fallible override's `Result` reaches them too, and no construction skips the check.
3. **Any other `init`** (a subset of the fields, extra parameters, different types such as a converting `init(x: Float, y: Float)`) is an ordinary overload and leaves the memberwise construction unchanged.
4. **A synthesized `Deserialize` constructs through the override.** If the override fails, `deserialize` returns `DecodeError(offset: <where the item started>, fault: .InitFailed)`: a new `DecodeFault` case, `InitFailed = 13`, described as "the type's init refused the decoded fields". It allocates nothing, `DecodeError` stays Copy, and the init's own error is not carried. A caller who needs it hand-writes `deserialize`. This half lands with the serde port, since serde lives only in the frozen std (`sawc/std/serde.saw`) today.

**Unchanged:** a derived `copy()` duplicates an existing value field by field and calls no constructor.

**Owed:** the spec (construction and `init` sections, the serde section's `DecodeFault` list), the saw-lang skill, and SL:hazards for Stage 0, which refuses every exact-match `init` ("ambiguous with field initialization"). The self-hosted compiler's source can't use an override until after bootstrapping.

**Implementation sketch (for the unit):** typecheck's `init` candidates (`init_call`, `TcCandKind.Memberwise` in `compiler/typecheck/src/bodies.saw`) drop the memberwise candidate wherever an override exists, except inside the override's own body, where the override is dropped instead. One funnel answers "which construction does this call reach", with entry points named, and the declaration-site check (only the defining module; at most one override per type, which SL-641's `overload.indistinguishable` already gives) sits beside SL-641's redeclaration funnel. Pins: the matrix above, row by row, plus run programs: a validating override called from outside, from another `init` and from another module, with the raw construction inside it.

**Air, before dispatch: two cases the ruling's matrix should decide.** Neither reverses it; each needs a row and a pin.

1. **A test-only override.** Rule 1 limits an override to the defining module, and a test sidecar or `@test` extension is in that module. But an override changes what every `Port(value:)` means, so a test-only one would change production constructions in a test build. That's what SL:testing forbids ("Test code cannot change what production code means … production code is checked as if no test-only declaration existed"), and it's the same shape SL-630 refused for a test-only `copy()` hook (`copy.test-only-policy`). Suggestion: refuse an exact-match `init` that is test-only on a production type, with that refusal's wording. A test-only *type* may of course override its own construction.

2. **An override in a bounded extension.** A bounded extension can declare an `init` today: `extension Wrap<T: Equatable> { init(value: T, tag: Int) -> Wrap<T> { … } }` builds and runs on main (`.build/scratch/air-review/sl648_bounded_init.saw`). An exact-match `init(value: T)` there would override the memberwise construction only for the instantiations that meet the bound. Then in a generic body with an unbounded `T`, `Wrap(value: x)` reaches the override or the raw construction depending on the instantiation. That's a choice typecheck can't make once per call, and one the reader can't see. Suggestion: an override must be unconditional, so an exact-match `init` in a bounded extension is refused, naming the bound and the unbounded spelling. The alternative, a per-instantiation choice made in mono, would give one call two meanings.

Checked and not open: Saw has no struct patterns, so destructuring never constructs, and no field defaults, so the "every field, exactly" match has no defaulted fields to account for.

**Lead, a row the user pointed out (Oct 15): a module-private override hides construction.** Rule 2 plus ordinary visibility already give this. An override carries its own visibility like any `init`, and a bare one is module-private. So a bare override on a `public struct` whose fields are all public makes `Port(value:)` unreachable outside the defining module: the call resolves to the override, which isn't visible there. The fields stay readable, and writable, cross-module. A `public` override is the type's public, validating construction.

**Pins:** a bare override on a `public struct` with public fields, called from another module, is refused (the message names the module-private override), while a field read there is accepted; a `public` override called from another module runs; a write to a public field from another module is still accepted. The override guards construction, not mutation, and a `private` field remains the tool for that. The spec text says so in one sentence.

**The user's ruling, Oct 14, on the zero-init row** (i648override's question). The user chose "refuse unless constructible" from these options:
1. refuse unless constructible;
2. refuse only with an override;
3. leave it.

**The rule:** a zero-initialized `static` (no initializer) counts as a construction. It is refused when:
- the type has an init override, wherever the static is, because zero-init would skip the override's check; or
- the module declaring the static couldn't write the type's memberwise construction itself: a field it can't see (`private` in another module, at any depth of the zero-initialized value).

The refusal names the override or the hidden field. A type with no override whose fields the module can see keeps free zero-init, as today (the freestanding all-zero static).

This closes the existing private-field case too: sawc2 accepts `static P: dep.Port` with no initializer when `dep.Port` has only private fields and a validating `init`. It belongs in SL-648's matrix as its own row.
