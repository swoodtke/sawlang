## Description

**SL-1063 unit E: two follow-ups from the Air's review of the ESP32-S3 patches (chat m724, Nov 12).** Both are small; one unit.

**1. Blade's `[sos]` `mcpu` key can only make the two halves of an image differ: drop it.** (From the review of SL-1071.p1.)
- sawc takes the CPU from the triple (`target_cpu` in `compiler/target/src/layout.saw`) and has no flag for it. Blade's `mcpu` manifest key (a lead decision in SL-1071) reaches only the C half.
- The Air's evidence: with the override fixture's own `esp32s2`, the C half's atomic increment becomes a call to `__atomic_fetch_add_4` while the Saw half keeps an inline `s32c1i`.
- **Decision (lead): the key goes.** The C half's CPU is `toolchain_defaults(target).mcpu` and nothing else, so it always equals what sawc wrote. A manifest that states `mcpu` under `[sos]` or `[sos.<triple>]` is an error: "`mcpu` is not a manifest key: the CPU is the target's, `esp32s3` for `xtensa-esp-unknown-elf`, and both halves of an image are compiled for it". Follow how Blade reports any other bad `[sos]` value (`SosError`).
- Changes: `blade/src/sosimg.saw` (the reader; `SosConfig.mcpu` stays as the field the builder reads, filled from the defaults only, with its doc saying so); `blade/tests/sosimg_arch.saw` and the fixture `blade/tests/fixtures/sosxtensa_override/` (the `mcpu` override case becomes the refusal case; the `target-features` override stays); the drift pin in `tools/blade_lane.py` is unchanged.
- Sweep (obligation 4): is there any other `[sos]` key that reaches only one half? `march` and `mabi` reach the C half and `target-features` the Saw half, by design on riscv32, where the manifest's author keeps them in step. List each key, which half it reaches, and whether a mismatch is possible; report, don't change.

**2. For an `xtensa-` triple, Espressif's clang is tried FIRST.** (From the review of SL-1067.p1.)
- `clang_candidates(triple)` in `compiler/tools/build.py` appends Espressif's clangs after the usual ones, and `pick_clang` takes the first that compiles the opaque-pointer module for the target. A distribution clang that carries upstream's partial Xtensa backend and accepts the triple would be chosen instead (the sweep saw the Linux VM's clang-19 list the backend and refuse the bare triple `xtensa`; nobody has tried it with `xtensa-esp-unknown-elf`).
- Change: for an `xtensa-` triple the list is Espressif's clangs, newest first, THEN the usual ones. Every other triple's list is unchanged. Update the docstring and `check_clang_choice` in `compiler/tests/run/run_lane.py` if it pins the order.
- Evidence to record, if the Linux VM is running (`limactl list`): `clang-19 --print-targets` and the opaque-pointer probe for `xtensa-esp-unknown-elf` there, through `tools/linux.py shell`. If the VM isn't running, say so; the change stands either way.

**Expected outcomes.** `blade test` passes with the changed cases; `tools/blade_lane.py` ok; on this machine the Xtensa record (`.build/sawc-runtime-xtensa-esp-unknown-elf.txt`) names the same Espressif clang as before; no golden moves.

**Gate (agent, under the suite lock).** `tools/blade_lane.py`; `compiler/tests/run.py --only seed,fixture_whitespace,comments,programs`; `tools/battery.sh citations patchgate toolchain`.

**Files:** `blade/src/sosimg.saw`, `blade/tests/sosimg_arch.saw`, `blade/tests/fixtures/sosxtensa_override/Saw.toml`, `compiler/tools/build.py`, `compiler/tests/run/run_lane.py` only if it pins the order.

Depends on SL-1071 having merged (it edits that patch's code).
