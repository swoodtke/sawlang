## Description

**std has no bulk copy for a vector of trivially copyable elements; every copy is element by element, about 2 ns per element.** Found by SL-955 unit 4b's probe (`.build/scratch/p955j/probe2.md`, item 2).

**Evidence:**
- Copying the front end's per-layer parts, about 370 MB of elements over sawc's 15 layers, takes 73–92 ms on the build's critical path.
- Struct vectors copy at 10–17 GB/s. The per-node `Int` tables copy at 3.6–4.2 GB/s, and the `Bool` tables at 0.5–0.8 GB/s, against about 20 GB/s for `memcpy`.
- The cost is a push plus a bounds-checked read per element, not bandwidth. `Vector.copy()` does the same.

**Direction:** for a vector whose element type is copied by its bits (SL-961's rule), `Vector.copy()`, and a new suffix copy `Vector.copy(from: Int)` or an `append(contentsOf:)`, copy the elements with one `memcpy`-shaped intrinsic after one capacity reservation. Std or the compiler picks this from the element type, with no caller-side flag.

**Expected:** 4b's store copy drops from about 80 ms to about 20 ms (estimated), and every `Vector.copy()` of a trivial element type speeds up the same way. Measure first; the pins check identical contents and that no copy glue runs.

**SL-971.p1: unit 1, `Vector.copy()` and `try_copy()` copy trivially copyable elements at `memcpy` speed**

- **The funnel:** `Vector.copy_elements`, with ENTRY POINTS `copy` and `try_copy`. It reserves once and writes each slot in place (`target[i] = source[i].copy()`), with no push and no per-element bounds check, then sets the length once.
- **Trivial types:** for a type copied by its bits, mono already reduces `copy()` to a plain load (SL-961/962), so at -O2 the loop becomes a NEON bulk copy. It is not an `llvm.memcpy` call; SL-986 tracks the missing `noalias` on the allocation seam. Any other type runs its copy glue per element. No new language surface or caller flag.
- **Unchanged:** both public signatures, the all-or-nothing `AllocError`, and both error sizes.
- **Throughput** (GB/s, -O2, at 10^3 / 10^5 / 10^7 elements; libc `memcpy` measured the same way runs 52–81):

  | type | before | after |
  |---|---|---|
  | `Int` | 3.6–3.8 | 53–63 |
  | `Bool` and `UInt8` | about 0.45 | 30–80 |
  | small all-trivial struct | 6.2–7.5 | 51–54 |
  | `String` (still retains) | 2.2–2.4 | 5.9–6.1 |

- **Pins:** `probes/vector_copy_element_tiers.saw` (-O0, -O2, leak-checked). For both `copy` and `try_copy`:
  - contents are identical at 0, 1 and 1,000 elements for six element types;
  - a counting hand-written `copy()` runs exactly once per element;
  - `String`s retain;
  - writing the copy leaves the source unchanged;
  - `ll omits: saw copy glue` for the trivial types.
- **Freestanding:** riscv32 and aarch64 `-c` objects with `copy()` reference the same runtime symbols as a push-only baseline: `__saw_rt_alloc`, `dealloc` and `panic`.
- **Gate:** `run.py --only seed,units,golden,subset,fixture_whitespace,std,std_suspension,programs`: ok. `coro`: ok, and its goldens don't list `Vector.copy`. `sawc.cone` gains `Vector.copy_elements`.

**Not in this unit:** a suffix copy (`append(contentsOf:)` or a range copy) is a new public API that waits on the user's ruling. Nine compiler sites would use the whole-append form, and one a range copy.
