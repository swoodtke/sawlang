## Description

Found while writing design 270's conformance rows (SL-212, unit C of SL-209).
A SYNC-side leak, independent of the coroutine transform.

## Symptom

A `[copy x]` capture into a NON-ESCAPING closure duplicates the value and then
registers no cleanup for the duplicate: the copy's `deinit` never runs.

```saw
struct Dup { n: Int }
extension Dup: ExplicitCopy {
    func copy(&self) -> Dup { Dup(n: self.n + 1) }
    func deinit(&var self) { print("drop {}", self.n) }
}

func run_int(body: () sync -> Int) -> Int { body() }

func a(d: Dup) -> Int { run_int({ [copy d] in d.n }) }

func main() { print("= {}", a(Dup(n: 10))) }
```

```
drop 10          <-- the original
= 11             <-- the body read the copy, so the copy exists
                 <-- `drop 11` never runs
```

`copy()` bumps the value on purpose so each duplication is countable by value:
the body reads 11, so the copy was made and was live; nothing ever released it.
At a `Vector`/`Map`/`Data` capture that is the buffer; at a `File` it would be
the fd, except that tier cannot be captured this way.

## The axis, isolated (obligation 4)

Four neighbouring shapes, one program, compile-and-run:

| # | Shape | Drops observed | Verdict |
|---|---|---|---|
| A | NON-escaping closure, `[copy d]` | original only | **the leak** |
| B | ESCAPING closure, `[copy d]` | copy AND original | correct |
| C | NON-escaping closure, `[move d]` (same tier) | one | correct |
| D | NON-escaping closure, `[move o]` (`NoCopy`) | one | correct |

So it is neither the tier nor the escaping question on its own: it is the
`[copy]` capture MODE in the one lowering that keeps a stack-resident
environment. The escaping lowering builds a refcounted env whose teardown
releases every capture, and it gets this right; the non-escaping one loads each
capture into a per-call local and never registers the duplicate it just minted.

## Mechanism, and why it is a CLASS member rather than a one-off

Design 267's inventory already named this boundary as the one capture mode that
reaches NO funnel:

> The capture boundary has three modes and only one of them reaches the
> checkpoint … `[copy x]` — an inline `_is_no_copy_type` test.

`[move x]` goes to `_check_move_expr` and a plain `[x]` goes to
`_check_value_transfer`; `[copy x]` is decided by an inline type test that asks
only whether the type is copyable and records nothing. No transfer decision is
filed, so no cleanup obligation is created for the value the copy produces —
which is the same shape as SL-220 (`(try! f()).x` extracts a payload nobody
adopts and nobody registers a cleanup for). Same class: **a value produced at a
boundary that reaches no ownership funnel is adopted by nobody.**

Two siblings of that class are now known and both are cleanup-side:
SL-220 (an inline payload extraction from a fresh temporary) and this one. Both
belong with SL-213 (unit D, codegen's half of the epic), which is where SL-220
was already routed.

## Fix shape (not done here)

Route the `[copy x]` capture through `_check_value_transfer` like the other two
modes, so it files a decision with `cleanup = adopt-temporary` and the
non-escaping env teardown has an obligation to honour — or, if the checkpoint is
the wrong place for a mode whose duplication is spelled, register the cleanup at
the materialization site the way the escaping lowering already does. The
escaping path is the worked example of the correct behaviour.

## Relationship to SL-267

Distinct. SL-267 is the coroutine transform minting an EXTRA reference for a
non-escaping capture (a duplication too many, counts balanced). This is the
sync lowering minting a reference and then dropping it on the floor (a
duplication whose release is missing). They compose badly — a `[copy d]` capture
in a DRIVEN body copies twice and leaks the second, which is how this one was
found — but the mechanisms are different passes and different halves of the
ownership question.
