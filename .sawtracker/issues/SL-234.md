## Description

In a driven body, a `move` of a frame local inside the HEAD expression of a `guard let`, a `for`, or a `while` is dropped TWICE when a contained block leaves by return/break/continue: the callee consumes and destroys the value, then coroutine frame teardown destroys it again. Silent -- exit 0, no diagnostic.

Repro (deinit counter is the oracle):

  import std.task.{yield_now}
  struct Res { name: String }
  extension Res: NoCopy {
      func deinit(&var self) { print("drop") }
  }
  func note(r: &Res) -> Int { r.name.len() }
  func consume_none(r: Res) -> Int? { None }
  func cell(items: Vector<Int>) -> Int {
      yield_now()
      for i in items.iter() {
          var r = Res(name: "item")
          if note(&r) + i < 0 { return -1 }
          guard let got = consume_none(move r) else { return 1 }
      }
      1
  }
  func main() { print(__saw_drive(cell([1, 2]))) }

Observed: 'drop drop 1'. Wanted: 'drop 1'. The `for`-iterable spelling (`for j in consume_vec(move r).iter() { return 1 }`) and the `while`-condition spelling (`while consume_bool(move r) { return 1 }`) double-drop identically.

MECHANISM: `_lower_inplace` collects a statement's head-expression move-forgets and emits them AFTER the whole statement (`cap_lets + [s] + self._forgets(forgets)`). The head is evaluated FIRST and unconditionally, so the value is already gone by the time a contained block runs; a block that returns/breaks/continues leaves before the trailing clears, and the frame's drop flag is still set.

THE FIX IS ONE CALL PER ARM and already exists in the tree: SL-222's review-r3 landing added `_FrameBuilder._relinquish_before_exits(forgets, blocks)`, which prepends the clears to each contained block AFTER the block is lowered (`__saw_forget` stores a zero discriminant, so clearing twice is a no-op -- the trailing clear stays for the paths that enter no block). That landing applied it to the `TryExpr`, `IfExpr`, `IfLetExpr` and `MatchExpr` arms, which were the ones SL-222 newly made reachable. The `GuardLetStatement`, `ForLoop` and `WhileExpr` arms need the identical call and are left here deliberately, per the reviewer's scoping rule.

PRE-EXISTING, in EVERY syntactic position: measured on unpatched origin/main, where all three double-drop both as a block's tail and with a trailing statement after them. SL-222's changes neither cause nor cure them. Found by SL-222's review-r3 obligation-4 class sweep (11 cells, deinit-count oracles); pinned as an XFAIL in examples/coro_head_move_with_early_exit_drops_once.saw.

SECOND FAILURE MODE on the same cells, measured for SL-222's review r4 (which found it in the arms SL-222 owns). Beside r3's double-free of the OLD value, these arms also ERASE A REINITIALIZED claim: a block that reassigns the moved local and then falls through has its replacement's cleanup claim wiped by the unconditional trailing clear. Named-deinit oracle, one item in the vector, on the current tree:

  guard let else, reinit + continue  ->  'drop old / drop old / drop new'   (old freed TWICE, new ok)
  for  iterable, reinit + fallthrough ->  'drop old / drop old'             (old freed TWICE, new NEVER drops)
  while condition, reinit + break     ->  'drop old / drop old'             (same)
  let  initializer, reinit in a value-if arm -> 'drop old / drop old'       (same)

So three of the four leak the replacement outright, and all four double-free the original. A subsequent READ of the replacement after the statement compiles and panics 'force unwrap of None' where the claim was erased.

THE FIX SHAPE CHANGED with r4 and this note supersedes my earlier one. Prepending clears to each block (what my earlier comment described) is NOT sufficient -- it fixes the exits and still erases a reinit, because 'clearing twice is a no-op' is true of the FLAG and false of the CLAIM once a block can re-establish it. SL-222 r4 replaced that with _FrameBuilder._hoist_head_and_relinquish(head, forgets, at): bind the container's head to a temp, emit the clears immediately after it, and drop the trailing clear entirely, so the claim is given up exactly once at a point where it is provably the live one. The three CONTAINER arms here (guard let, for, while) take that helper directly. The two LEAF arms (let initializer, assignment RHS) still cannot -- their blocks are operands with no single head, and one can sit to the LEFT of the move -- so they want the refusal SL-222 r3 added in the _lower_inplace fallback, extended to those arms. The pin examples/coro_head_move_with_early_exit_drops_once.saw covers the early-exit half; the reinit half is not pinned separately.

FIX IN on branch agent-sl226-batch2 (commit 5e1bbfee). The issue's fix map held up, and the c2 supersession was right: the hoist is the shape, not the prepend.

THE THREE CONTAINER ARMS take `_hoist_head_and_relinquish` directly, as c2 said. `guard let` passes consuming=True -- checked, not assumed: it reads a PAYLOAD out of its subject exactly as `if let` does. `for` and `while` read their heads, so they take the plain name.

THE `while` PER-ITERATION HAZARD, probed before applying the helper as the dispatch asked. A hoisted while-head IS wrong in general -- it would freeze iteration one's answer -- but it is sound here, and the argument is containment: the hoist fires ONLY when the head contains a `move` of a frame local (`forgets` empty otherwise, and the helper hands the head back untouched), and such a condition cannot be evaluated twice soundly, because the second evaluation would consume a value the first gave away. So for every program in which the move is sound, the condition runs exactly once and the hoist is observationally the same loop. Ordinary per-iteration conditions never reach it.

What settled it was the sync twin, which is also a NEW FINDING: `while consume(move r) { ... }` with a body that FALLS THROUGH is an unchecked use-after-move in plain SYNC code -- one `Res` destroyed once per iteration, three drops, exit 0. So the multi-evaluation case has no correct behavior to match in either path; it is a move-checker hole, filed as SL-262 (not caused by, not fixed by, and not worked around by this change). A refusal for the moving while-head would have DIVERGED from the sync twin, which compiles and drops once for the single-evaluation case -- so the honest answer was the fix, not the refusal.

THE TWO LEAF ARMS are REFUSED, per the operand-ordering argument documented at the r3 fallback: a leaf statement's blocks are operands and one can sit to the LEFT of the move, so no placement is expressible. Rather than a third copy of that rule, the refusal is now ONE funnel -- `_refuse_buried_early_exit` -- called by the LetStatement arm, the AssignStatement arm and the fallback, with its docstring naming those three callers (obligation 1). The message names the AUTHOR'S position and never a synthesized temp:

  error: coroutine transform: `move` of a frame local in the initializer of `v` of driven `run` whose expression also `return`s, `break`s or `continue`s is not supported; bind the moving call to its own `let` first, then use the binding

  error: coroutine transform: `move` of a frame local in the right-hand side of the assignment to `acc` of driven `run` ...

The assignment arm is asked BEFORE the target rewrite, so it says `acc` and not the `self.acc` the frame rewrite would have produced.

MEASURED, sync twin beside every driven cell, named drops so a doubled `old` and a leaked `new` are distinguishable:

  EARLY EXIT (was 2 drops, 1 correct)   sync / driven after fix
    guard let else, return               drop old / drop old
    for iterable, return                 drop old / drop old
    while condition, return              drop old / drop old
  REINIT (c2's half, was old freed twice + new leaked)
    guard let else, reinit + continue    drop old, drop new / drop old, drop new
    for iterable, reinit + fallthrough   drop old, drop new / drop old, drop new
    while condition, reinit + break      drop old, drop new / drop old, drop new

The reinit half is fixed by construction rather than by a second mechanism: the hoist drops the trailing clear entirely, and the trailing clear was the thing that erased a replacement's claim.

One c2 shape turned out to be a LANGUAGE refusal, not a bug: a subsequent READ of the replacement (`while consume(move r) { r = Res(..)  break }` then `note(&r)`) is rejected by the move checker in the SYNC path too -- "value was moved at line N and can no longer be used" -- so there is nothing for the transform to get right there.
