## Description

**Faster builds: per-module IR with parallel clang, cached per-module objects, then a cached front end. One final link per image.** USER DIRECTION (Nov 2): do it in this order, and record each step's timings here so improvements can be tracked over time.

**Why this order:** the survey (`.build/scratch/p955/report.md`) and `--time-stages` show that at -O2 the build is clang, not sawc. sawc's own -O2 build is 30.9 s, of which clang is 26.1 s (84%) on one 74 MB module, single-threaded. Splitting the IR into 8 parts cut clang -O2 from 21.7 s to 1.7 s wall; with ThinLTO, 3.5 s total and a compiled sawc 18% slower; without LTO, the compiled sawc is 1.9× slower (no cross-unit inlining). For small programs the cost is std: ~180 ms of `hello`'s 362 ms is sawc re-checking all 36 std modules.

**Units, in order:**
0. **The benchmark** (`tools/bench_compile.py`): runs a fixed set with `--time-stages` (sawc's own -O2 and -O0 builds, Blade -O2, `hello` -O0, the largest corpus program -O0) N times, reports the median per step and the machine's load, and prints a table to paste here. Every later unit posts its table as a comment, so the issue is the timing history.
1. **Per-module IR, compiled in parallel.** One LLVM module per Saw module (generic instances emitted link-once where used, or in an instances unit; the whole-program pieces: the backtrace table, the entry point, vtables, in a unit of their own); clang runs them in parallel under the 75% concurrency cap; at -O2 the units are linked with ThinLTO (decision: a whole-module build stays available, e.g. for releases, if the 18% matters). Still one program object per image: sawc builds every unit and does the final link.
2. **Order-independent IR naming.** Constants, debug metadata ids and helper names stop depending on other modules (today `.bytes.N` and `!N` are numbered program-wide, so editing one module renames things in all the others).
3. **Cached per-module objects.** An unchanged module's object is reused, keyed on its IR (or its inputs), compiler and flags.
4. **A cached front end, std first.** Each module's results through drop elaboration, keyed with early cutoff (suspension and layout facts flow across modules from bodies), with a Saw-defined format.

**Baseline (Nov 2, main, M4 Max, before any unit; from `--time-stages`):** sawc -O2 30.9 s (clang 26.1 s, sawc's stages 4.7 s, of which the verifiers 1.35 s); Blade -O2 1.83 s (clang 1.40 s); `hello` -O0 0.36 s. Unit 0 re-measures this properly as the first table.

**Related, separate:** the verifiers' cost (1.35 s of sawc's 4.7 s) is a profiling question of its own. Linking several *separately compiled* sawc objects into one image stays unsupported (SL-952).

**Incremental compilation: a Saw-defined cached module format, with one final codegen and link.** USER DIRECTION (Nov 2): do this at the next free slot.

**Why:** the usual reason to support several `.o` files is build speed, reusing previously compiled modules. Linking several separately compiled sawc objects into one image doesn't work (SL-952's census): each object carries its own std, so std's process-wide state (the task registry, the panic report) and the backtrace table are duplicated per object, and they hang off one runtime word per image. A cache in sawc's own format keeps whole-program compilation: the final step sees every module, so std's statics are defined once, generic instances are made once, and there's one backtrace table and one object per image. It also gives a later route to prebuilt Saw libraries (like Rust's `.rlib` or Swift's `.swiftmodule`).

**Sketch (to be decided by the design brief, not here):** cache each module's front-end results (resolved and typechecked interface, lowered bodies), keyed on a hash of its source, its dependencies' interfaces and the compiler version; the final step loads cached modules, recompiles changed ones, then runs mono, coro, codegen and the link for the whole program. If LLVM codegen dominates compile time, the cache may also need per-module LLVM output for non-generic code.

**Unit 1, a survey (perf via measurement):** where sawc spends its time on large programs (sawc itself, Blade, the std cone, a big corpus program), stage by stage, cold and with nothing changed; which stages are per-module and which are whole-program; what a cached module must hold for each later stage; what invalidates it. Then a design brief.

**Supersedes** SL-952's question of linking several sawc objects into one image. Until this lands, an image holds one sawc object, and its Saw modules are compiled together in one invocation (`--module-path`), as sawos and Blade do.
