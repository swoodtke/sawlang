**Incremental compilation: a Saw-defined cached module format, with one final codegen and link.** USER DIRECTION (Nov 2): do this at the next free slot.

**Why:** the usual reason to support several `.o` files is build speed, reusing previously compiled modules. Linking several separately compiled sawc objects into one image doesn't work (SL-952's census): each object carries its own std, so std's process-wide state (the task registry, the panic report) and the backtrace table are duplicated per object, and they hang off one runtime word per image. A cache in sawc's own format keeps whole-program compilation: the final step sees every module, so std's statics are defined once, generic instances are made once, and there's one backtrace table and one object per image. It also gives a later route to prebuilt Saw libraries (like Rust's `.rlib` or Swift's `.swiftmodule`).

**Sketch (to be decided by the design brief, not here):** cache each module's front-end results (resolved and typechecked interface, lowered bodies), keyed on a hash of its source, its dependencies' interfaces and the compiler version; the final step loads cached modules, recompiles changed ones, then runs mono, coro, codegen and the link for the whole program. If LLVM codegen dominates compile time, the cache may also need per-module LLVM output for non-generic code.

**Unit 1, a survey (perf via measurement):** where sawc spends its time on large programs (sawc itself, Blade, the std cone, a big corpus program), stage by stage, cold and with nothing changed; which stages are per-module and which are whole-program; what a cached module must hold for each later stage; what invalidates it. Then a design brief.

**Supersedes** SL-952's question of linking several sawc objects into one image. Until this lands, an image holds one sawc object, and its Saw modules are compiled together in one invocation (`--module-path`), as sawos and Blade do.

**Air: SL-955.p1 (unit 1, `--time-stages`) approved.** Reviewed r1 on 5650271dc.

**The flag changes nothing it shouldn't** (`sl955p/hello.saw`):
- **`--emit-ll`:** with and without `--time-stages`, **stdout is byte-identical**. The times go to stderr only, so a pipeline reading the IR from stdout is safe. Your lane pins the `.ll` too.
- **Without the flag, stderr is empty.**
- **Error path** (`broken.saw`, a type error): exit code 1 with and without the flag. The diagnostics are identical once the `time:` lines are removed, and the stages that ran are still reported.

**The numbers add up:**
- **`--emit-ll` hello:** the 17 step lines sum to 156.3 ms against `total 156.6 ms`.
- **A full `-O2` build:** `total 386.3 ms` against `/usr/bin/time -p`'s `real 0.38`, with clang, link and dsymutil each printed.
- **`-c`:** prints clang and no link.
- **The shorthand `sawc --time-stages FILE`** works too.
