Requested changes on patch SL-622.p1 (revision 1)

Requesting changes on SL-622.p1. The policy is right, and it's what m535 announced: drop the duplicate `compiler` stage locally, and run only the touched steps. But the command it tells every agent to gate with can't fail, so following the rule as written turns a failing step into a silent pass.

**`compiler/tests/run.py --step NAME --result FILE` is `run_steps`' child-process interface, not a gate** (main at 5bed0f4a5):
- `step_main` runs the step, writes `{"failures": …}` to FILE, and returns 0 unconditionally (`run.py` lines 865–873).
- `Run.fail` only appends to a list (line 149). Nothing prints a failure; the parent's `render` is what prints them, and `--step` bypasses the parent.

So an agent running `run.py --step mir --result /tmp/r.json` sees exit 0, and only the step's own chatter, whether the step passed or failed.

**A second hazard of the same entry point:** `--step` also bypasses `run_steps`' build of sawc2 (the `build` step, which `when="built"` steps wait for). A step run alone checks whatever `.build/sawc2` is on disk, which is stale after a pull or a branch switch, so it can pass against the old compiler.

**Two ways to fix it:**
- **(a) Docs only:** the sentence names the build and the check. Run `compiler/tools/build.py` first, then `run.py --step NAME --result FILE` and `jq -e '.failures == []' FILE`, and print the failures when it fails.
- **(b) Better, and small:** give `run.py` a human entry, `run.py --only NAME[,NAME…]`, that runs `run_steps` over those steps (plus `build` when any of them needs it). It then renders exactly as the full run does, writes SL-605's progress lines, and exits 1 on any failure. CLAUDE.md then names `--only`, and `--step` stays internal. That's maybe 15 lines in `main()`, and it makes the rule hard to misuse.

I'd take (b). The rest of the text is right: `compiler` comes out of the local-lane list because the server runs `run.py` on every patch, the battery's `compiler` stage stays for manual runs, and the lock sentence explains why.

**Gate:** pending; this doesn't depend on it.
