**1. The report can't print after its own panic line from `std/taskgroup.saw` (the stop).**
- **What the plan and brief ask for:** Stage 0's panic line, then the dump's header and task lines, all from `std/taskgroup.saw`.
- **Why that doesn't work in sawc2:**
  - The compiler formats `panic at FILE:LINE: MSG` and hands it to the lang item `panic_sink`, whose home is `std.panic` (`compiler/resolve/src/lang.saw`).
  - `std/panic.saw`'s `panic_sink` is `__saw_rt_panic`: write, then `abort()`.
  - So nothing in `std.taskgroup` runs after a `panic(...)` line.
  - Stage 0 manages it because the compiler picks `__saw_bt_panic` (in `sawc/std/taskgroup.saw`) as the sink in programs that link the executor. That sink writes the line, then `__saw_bt_dump()`, then `__saw_rt_panic(message, 0)`.
- **The ways I see, none in my file list without a hack:**
  - **(a) A panic-path hook in `std/panic.saw`** (or a compiler-chosen sink, as Stage 0 does). This is A16b's "dump the panic path prints", brought forward. `std/panic.saw` is outside the brief's files, and `std.panic` must stay task-free (the std cone pins). Saw also can't call a raw code-pointer static, so the hook's shape is a design question.
  - **(b) The report writes a hand-formatted `panic at taskgroup.saw:N: …` line**, then the dump, then `panic_sink(p, 0)` to abort. That's a second producer of the compiler's panic-line format.
    - `#file` is refused in sawc2 (`backend.not-yet`: "a memory constant is not in the backend slice yet"), so the file name would be hard-coded.
    - The run lane's `panics` probes also require the panic line to be the *last* line.
  - **(c) The walk and Stage 0's panic text now, with the dump deferred whole to A16b (SL-577).** K67 stays `wrong` either way (below), so the corpus outcome is the same.
- **Recommendation:** (c), or (a) as a ruled scope change. CLAUDE.md's "no workarounds" rules out (b) for me without a ruling.

**2. A ruling the walk also needs: frames active on this thread's stack.**
- **Stage 0's rule:** a frame active on *some* thread's stack means "something can run", so no report.
- **Single-threaded sawc2:** `active` only ever means this thread's stack, so such a frame is blocked in a nested `join` or drive. A verbatim port turns today's interim panic into a hang.
- **Evidence:** `.build/scratch/dl/nested.saw` in this worktree. A task joins a task parked in `receive` on a channel nothing sends to.

  - port verbatim, which matches the oracle and leaves SL-578/SL-765 the wait loop they need; or
