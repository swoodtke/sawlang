## Description

**A task that drives a suspending child to completion and then panics reads a poisoned slot in the panic's task dump (ASan use-after-poison)** (found by p860, SL-860 step 1, Oct 23; repro `scratchpad/p860/panic_after_drive.saw`, at `O0asan`; with a lend: the `force_absent` cells of p860's matrix, 8 rows).

A cooperative task drives a plain suspending child to completion, then panics. The panic writes the task dump, whose backtrace walk `std.taskgroup.bt_state_record` reads the FINISHED child's frame slot after it has been poisoned (released). ASan reports `use-after-poison`; without ASan it reads freed or stale memory, so the dump can print garbage or crash.

This is a memory-safety read on the panic path. The fix must keep the dump truthful ("never hide errors") while reading only live frames.

**Mechanism (UNVERIFIED):** the dump walks a frame chain that still links a child whose slot was released at completion. Either the child's link isn't cleared when it completes, or the walk doesn't check the slot's liveness.

**Obligation 4:** a child that completes, is cancelled, or is joined, × the parent then {panics, is dumped by `dump_tasks()`, deadlock-reports}, × the engine {cooperative, pool, `Thread.spawn` drive}. Run each under ASan; each dump names only live frames.
