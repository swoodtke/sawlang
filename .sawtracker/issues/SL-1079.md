## Description

**A passing gate run prints `failed` for two steps, and nobody can see what failed.** In the server's gate log of every patch that reaches the fixpoint lane (SL-1067.p1 and SL-1018.p1 r2, both `# result: passed`, Nov 12):

```
fixpoint: run.py: failed borrowck (365 s)
fixpoint: run.py: failed programs (680 s)
fixpoint lane (default mode): ok: 1 fixpoint binaries, ... 5790 fixpoint invocations agreeing, ...
```

The same two steps pass in the same gate run a few lines earlier, when `compiler/tests/run.py` runs them itself (`compiler tests: ok`). User ruling (Nov 12): **tests shouldn't randomly report failed.**

**What is known (read from the source, nothing run).**
- `fixpoint_lane.py`'s `replay_lanes` runs run.py's sawc-driven steps a second time through `run.run_steps`, with `sawc=` a wrapper script (`.build/.../sawc-twin`, which execs `twin.py`: it runs Stage 1 and Stage 2, hands the lane Stage 1's answer and logs whether Stage 2's agrees) and `label="fixpoint: run.py"`.
- `run_steps` writes `LABEL: failed NAME` when a step's result has `failures` or `crashed` (`ended`, in `compiler/tests/run.py`).
- `replay_lanes` keeps a step's failures only when it CRASHED. A step that finished with failures is dropped without a word: the lane's docstring says "The lanes' own verdicts are run.py's to judge; here only agreement counts."
- So `borrowck` and `programs` each finish with at least one failure under the twin, every run, and the text of those failures is discarded.

**What is not known, and is this issue's first job:** what those failures are. They pass under Stage 2 directly, and every compared invocation agrees, so the likely kinds are (UNVERIFIED, each to be confirmed or ruled out by reading the failure text):
- a check that reads something BESIDE the binary (the runtime manifest, `--version`, a file path derived from `build.SAWC`), which a wrapper script in another directory doesn't have;
- a check on timing or a timeout, since each call runs two compilers;
- a check that builds and RUNS a program, or reads a file sawc wrote, where the twin's rewrite of output paths gives another answer;
- a real Stage 1 / Stage 2 difference the comparison doesn't cover.
The last would be a compiler finding, and is why the text must be read before anything is changed.

**Goal.** A step that fails under the twin is either fixed so that it passes, or fails the fixpoint lane with its text. After this issue a gate log has no `failed` line in a passing run, and a new failure under the twin is seen the day it appears.

**Implementation.**
1. **Step 0, evidence, before any edit.** Under the suite lock, run the fixpoint lane once in default mode with a small change that only PRINTS (or writes to your evidence directory) each step's `failures` list as `replay_lanes` receives it. Record for `borrowck` and `programs`: the count and every failure's full text. Check no other step has failures. This run is about fifteen minutes.
   - If any failure names a difference between Stage 1's and Stage 2's output, exit status, or a file either wrote: STOP and report it with the text. Don't classify it yourself.
2. **Classify each failure** by reading the check that produced it (the message names its lane and usually its probe): which of the kinds above, or another. Write the table: failure, the check, why it fails under the twin, and the proposed remedy, one of:
   - **(a) make the twin faithful:** the wrapper lacks something the real binary has (a file beside it, an environment variable, a path), and supplying it is the smaller, more honest change;
   - **(b) the check doesn't apply under a twin:** it tests the binary's installation, not its answers. The step skips that check when run under the twin (one named predicate, set from the environment `replay_lanes` already passes, `FIXPOINT_REF`), and says in its counts that it skipped it. Never a silent skip.
   - **(c) raise a bound** only if the check is a deadline and the evidence shows it is the twin's doubled work, with the measured times.
   STOP after the table and report it to the lead before implementing if any failure fits none of the three, or if (b) would skip more than a check or two: the lead decides.
3. **Implement the remedies.**
4. **Make the lane loud:** `replay_lanes` appends every step's failures, crashed or not, as `fixpoint: under the twin, <step>: <failure>`. Update the docstring sentence that says only agreement counts: agreement is what the lane judges, and a lane that cannot finish cleanly under the twin is reported, because its invocations may be missing or its failure may hide a difference.
5. **A pin.** `compiler/tests/fixpoint/` has tests of the lane's own parts (read what exists: the twin's rewrite cases, `check_twin_stderr`). Add one that feeds `replay_lanes`' result handling a finished step with a failure and requires the lane to fail with its text. If the handling isn't separable enough to test without running the lanes, split out the few lines that turn results into failures and test that function.

**Expected outcomes.**
- The fixpoint lane's log: `finished` for every step, the same invocation counts as before (5790 compared in default mode on today's main; a count that falls means a step now does less under the twin, which must be explained in the report).
- `compiler/tests/run.py` itself unchanged in behaviour and counts when not under the twin.
- No compiler source change.

**Tests and gate.** Under the suite lock: `compiler/tests/fixpoint/fixpoint_lane.py` (default mode), `compiler/tests/run.py --only seed,borrowck,programs,fixture_whitespace,comments`, `tools/battery.sh citations patchgate`. The server runs the fixpoint lane on this patch too, since it touches `compiler/`.

**Docs.** CLAUDE.md's Testing section describes the fixpoint lane in one clause; add nothing unless the rule "a step that fails under the twin fails the lane" changes what a reader would do (it doesn't).
