## Description

**On windowed Xtensa, sawc's frame-pointer policy miscompiles: a function with six or more argument words reads a clobbered argument, and a call with stack arguments can raise an unhandled Alloca exception.** Found by SL-1128's sweep (Nov 14). It affects only `xtensa-esp-unknown-elf` built with `--target-features +windowed`, which nothing has shipped with; it blocks the windowed row of the freestanding suite and so the sawos project's windowed processes.

**The mechanism.** `Target.frame_pointer` (`compiler/target/src/layout.saw`) answers `NonLeaf` for every target, and `ll_function_attribute_group` (`compiler/llvm/src/attributes.saw`) puts `"frame-pointer"="non-leaf"` on every function. On windowed Xtensa the frame pointer is `a7`, which is also the sixth argument word (`a2` to `a7` carry arguments).
- **The clobber.** Espressif's clang 20.1.1 sets up the frame pointer (`mov.n a7,a1`) before reading the incoming `a7`. `check_wide` in the suite's `int_widths` case: `entry a1,208; mov.n a7,a1; ... xor a8,a5,a7`: the value read is a stack address. Seven suite cases print wrong values (`int_widths`, `call_convention`, `float_text`, `serialize_int64`, `soft_float`, `soft_float_vectors`, `soft_float_vectors_optimized`). Plain C reproduces it with `-mframe-pointer=non-leaf` (`all` saves `a7` first), so the root is in the backend; sawc is what asks for the policy.
- **The Alloca exception.** With a frame pointer, a call that passes stack arguments is wrapped in `movsp`, which raises exception cause 5 when the caller's window has been spilled (a deep stack). `movsp` appears 504 times across 14 of the suite's 34 objects with `non-leaf`, and nowhere with `none`. Nothing in a freestanding image handles cause 5.
- Evidence: `.build/scratch/p1128/` in the lead's checkout (`win/int_widths.dis`, `allB2_nonleaf.log`, `allB2_none.log`, `c/fp_clash2_dis.txt`, `ir/fp_attr_result.txt`, `movsp_nonleaf.txt`, `movsp_fpnone.txt`, `deep/`).

**The fix (lead's decision; it is the only policy of the three that the sweep shows right).** `Target.frame_pointer` answers `Omitted` for an Xtensa target whose effective features have the windowed ABI on, and `NonLeaf` everywhere else, call0 Xtensa included (its objects must not change). The function is the one funnel; its docstring says why windowed Xtensa is the exception (the frame pointer is an argument register there, and a frame pointer brings `movsp`). With the policy `none` in the emitted IR, all 34 cases pass.
- To settle in the unit: `frame_pointer(&self)` has no feature string today; how the target learns its effective features (`target_effective_features`) decides the signature. Every caller is listed.
- **What omitting the frame pointer costs:** nothing in sawc reads a frame chain (backtraces are a table). A KERNEL that walks frames on windowed Xtensa would walk the window save areas, not a frame-pointer chain; say so in the spec's or the target notes' sentence on frame pointers if there is one.

**Pins.** An IR pin per policy: a windowed Xtensa build carries `"frame-pointer"="none"`, a call0 one and every other target `"non-leaf"` (where the lanes pin function attributes today: find it; `compiler/tests/mono/` backend goldens or the run lane's `ll` checks). An object pin: a windowed build of a function with eight argument words has no `movsp` and does not write `a7` before reading it (disassembly with the `objdump` beside Espressif's clang; skipped, naming the tool, where it is absent). The seven cases become the windowed row's when it exists (SL-1128).

**Gate.** `compiler/tests/run.py --only seed,units,golden,subset,fixture_whitespace,std,comments,mono,programs`; `tools/battery.sh citations freestanding` (the call0 row must not move). The corpus gate is the server's; no hosted object may change.

Related: SL-1128 (the windowed row), SL-1063, SL-1067.

**Implementation detail (lead, Nov 14; it settles what the description left to the unit).**

**1. The signature.** `Target.frame_pointer` takes the effective feature list: `frame_pointer(&self, features: String) -> TargetFramePointer`. Its one caller, `ll_function_attribute_group` (`compiler/llvm/src/attributes.saw`), already has `features`, which the driver computes with `target_effective_features` before it reaches the backend. The answer:
- `Omitted` when `self.triple` starts with `xtensa` and `target_feature_state(features, "windowed")` is not `Off`. (Espressif's clang is windowed unless the feature is turned off, so a list that does not name it is windowed too; sawc's effective list for the triple always names it.)
- `NonLeaf` otherwise: call0 Xtensa and every other target, whose IR must not change by a byte.
- The function's comment says why: on windowed Xtensa the frame pointer is `a7`, an argument register, and a frame pointer makes the backend wrap calls that pass stack arguments in `movsp`. Present tense, no history, one trailing reference at most.

**2. Sweep first (obligation 4): who else reads the policy or assumes a frame pointer.** A table in the report: every use of `frame_pointer`, `TargetFramePointer`, the text `frame-pointer` and `FRAME_POINTER` under `compiler/`, `runtime/`, `std/`, `tools/` and `tests/freestanding/`, each classed "follows the funnel", "pins the text" or "assumes a frame chain exists". Approved patch SL-1133.p1 (revision 1)

**Approved (reviewer, Nov 14), revision 1.** With the patch, windowed Xtensa code reads its sixth argument and wraps no call in `movsp`, at every optimization level and argument shape I tried, and no other target's IR moves. Two observations at the end are about code the patch does not touch.

Before is v0.24.1's compiler: nothing but tracker files separates the tag from fetched main, which is what the tree is on (base `82fc2a5d1` was not in my mirror).

**The defect and the fix, in the object** (the patch's probe, `-O1`, `+windowed`):

```
before:  entry a1, 32 ; mov.n a7, a1 ; movi.n a8, 3 ; mulsh a9, a7, a8     the sixth argument is the stack pointer
after:   entry a1, 32 ; movi.n a8, 3 ; mulsh a9, a7, a8
```

**IR, before against after** (chat f128, `probe_fp.py`; three freestanding programs and one hosted):
- The same bytes on Xtensa with no feature list, `-windowed`, `+windowed,-windowed` and `+fp`; on riscv32 with its default list and with `+windowed`; on `aarch64-unknown-none-elf`; and hosted on the host, both Linux triples and with `--sanitize address`.
- `non-leaf` becomes `none` on `+windowed`, `-windowed,+windowed`, `+windowed,+fp` and `+windowed --runtime`. The two attribute groups are the only lines that differ (compared line by line on one program).

**Objects, before against after**, at `-O0`, `-O1`, `-O2` and `-Os`, with `+windowed` and `+windowed,+fp`: the patch's two functions, six of mine (six, seven and nine words; one that reads its sixth after a call passing stack arguments; one calling in a loop; one with a 64-byte local) and two with larger frames. In every cell `movsp` goes from 2 to 0 in the first two programs, and each function taking six or more words goes from writing a7 first to reading it first, by the lane's own `a7_first_use`.

**The comment's two claims, with Espressif's clang 20.1.1 on the IR by hand** (chat f129, `probe_clang.py`; the feature list and the frame-pointer attribute rewritten in the probe's `.ll`):

| feature list | `non-leaf` | `none` |
|---|---|---|
| as sawc writes it for `+windowed` | windowed, `movsp` 2, a7 written first | windowed, `movsp` 0, a7 read first |
| empty | windowed, 2, written | windowed, 0, read |
| `+fp` alone | windowed, 2, written | windowed, 0, read |
| sawc's default | call0, 0, read | call0, 0, read |
| `+windowed,-windowed` after the default | call0, 0, read | call0, 0, read |

So the defect is there exactly when the code is windowed and the frame pointer is kept, and a list that never names the feature is windowed, as the comment says.

**Can a frame pointer come back another way?** The backend keeps one whatever the attribute says for a function with a stack allocation outside its entry block or sized by a value. In sawc's IR for 271 programs (228 of `tests/corpus` for the host, and 43 of the run lane's probes and mine for windowed Xtensa; about 36,000 functions and 420,000 allocas) there is none. The scan finds both shapes in a file made for it.

**Pins.**
- The unit program: seven mutants of the policy and of the list reader are red (always `NonLeaf`; only when named on; any triple; any triple named on; Xtensa whatever the list; `All` for `Omitted`; the first mention winning).
- The lane's check: green on the patch with the object half run (`run xtensa windowed objects: 1`); red on v0.24.1's compiler at the IR half. Two mutants of the caller, each built into a compiler (the caller passing an empty list; `none` written for `NonLeaf`), are red on its call0 row.
- Under the fixpoint twin the check's three invocations agree between Stage 1 and Stage 2 (the lane's own twin and judge: 0 failures).
- The source rules and the grammar corpus pass on the four `.saw` files.

**Consumers.** sawos main passes no `+windowed` to sawc (its lists are riscv's or none), so what it builds is the unchanged call0 IR. The SO-112 prototype's runner hands sawc no `+windowed` either.

**Not run by me:** windowed Saw code on a machine or in an emulator; `run.py` and the freestanding suite, which the server runs.

**Observations, not this patch's.**
1. **A feature named with no sign.** `--target-features windowed` is accepted, sawc reads it as on (`target_feature_state`: "a bare `name` turns it on") and now writes `"frame-pointer"="none"`, and the list reaches the IR as `-windowed,-fp,-loop,-mac16,-bool,windowed`, which Espressif's clang compiles as call0. So that build is call0 code with no frame pointer. `fp` with no sign is accepted the same way; I did not probe what the other answers read from the list do with it. Refusing an unsigned name in the driver would close it.
2. **A frame `entry` cannot state.** A function with a 40,000-byte local keeps one `movsp` in its prologue (`entry a1, 32 ; l32r ; sub ; movsp a1, a8`), before and after. It is the windowed ABI's own shape for a frame over 32,760 bytes, not the frame pointer's, but the lane's message calls `movsp` an exception nothing handles, and SL-1128's row and SO-112's handler set will meet it.
3. **The lane's a7 reader** takes `ssl a7`, `ssr a7`, `wsr a7, sar` and `loop a7, …` for writes, since those mnemonics are not in its no-write list. None is in the probe's function today; if one became its first use of a7 the check would go red on correct code. It cannot go green on wrong code by this.
