## Description

**On windowed Xtensa, sawc's frame-pointer policy miscompiles: a function with six or more argument words reads a clobbered argument, and a call with stack arguments can raise an unhandled Alloca exception.** Found by SL-1128's sweep (Nov 14). It affects only `xtensa-esp-unknown-elf` built with `--target-features +windowed`, which nothing has shipped with; it blocks the windowed row of the freestanding suite and so the sawos project's windowed processes.

**The mechanism.** `Target.frame_pointer` (`compiler/target/src/layout.saw`) answers `NonLeaf` for every target, and `ll_function_attribute_group` (`compiler/llvm/src/attributes.saw`) puts `"frame-pointer"="non-leaf"` on every function. On windowed Xtensa the frame pointer is `a7`, which is also the sixth argument word (`a2` to `a7` carry arguments).
- **The clobber.** Espressif's clang 20.1.1 sets up the frame pointer (`mov.n a7,a1`) before reading the incoming `a7`. `check_wide` in the suite's `int_widths` case: `entry a1,208; mov.n a7,a1; ... xor a8,a5,a7`: the value read is a stack address. Seven suite cases print wrong values (`int_widths`, `call_convention`, `float_text`, `serialize_int64`, `soft_float`, `soft_float_vectors`, `soft_float_vectors_optimized`). Plain C reproduces it with `-mframe-pointer=non-leaf` (`all` saves `a7` first), so the root is in the backend; sawc is what asks for the policy.
- **The Alloca exception.** With a frame pointer, a call that passes stack arguments is wrapped in `movsp`, which raises exception cause 5 when the caller's window has been spilled (a deep stack). `movsp` appears 504 times across 14 of the suite's 34 objects with `non-leaf`, and nowhere with `none`. Nothing in a freestanding image handles cause 5.
- Evidence: `.build/scratch/p1128/` in the lead's checkout (`win/int_widths.dis`, `allB2_nonleaf.log`, `allB2_none.log`, `c/fp_clash2_dis.txt`, `ir/fp_attr_result.txt`, `movsp_nonleaf.txt`, `movsp_fpnone.txt`, `deep/`).

**The fix (lead's decision; it is the only policy of the three that the sweep shows right).** `Target.frame_pointer` answers `Omitted` for an Xtensa target whose effective features have the windowed ABI on, and `NonLeaf` everywhere else, call0 Xtensa included (its objects must not change). The function is the one funnel; its docstring says why windowed Xtensa is the exception (the frame pointer is an argument register there, and a frame pointer brings `movsp`). With the policy `none` in the emitted IR, all 34 cases pass.
- To settle in the unit: `frame_pointer(&self)` has no feature string today; how the target learns its effective features (`target_effective_features`) decides the signature. Every caller is listed.
- **What omitting the frame pointer costs:** nothing in sawc reads a frame chain (backtraces are a table). A KERNEL that walks frames on windowed Xtensa would walk the window save areas, not a frame-pointer chain; say so in the spec's or the target notes' sentence on frame pointers if there is one.

**Pins.** An IR pin per policy: a windowed Xtensa build carries `"frame-pointer"="none"`, a call0 one and every other target `"non-leaf"` (where the lanes pin function attributes today: find it; `compiler/tests/mono/` backend goldens or the run lane's `ll` checks). An object pin: a windowed build of a function with eight argument words has no `movsp` and does not write `a7` before reading it (disassembly with the `objdump` beside Espressif's clang; skipped, naming the tool, where it is absent). The seven cases become the windowed row's when it exists (SL-1128).

**Gate.** `compiler/tests/run.py --only seed,units,golden,subset,fixture_whitespace,std,comments,mono,programs`; `tools/battery.sh citations freestanding` (the call0 row must not move). The corpus gate is the server's; no hosted object may change.

Related: SL-1128 (the windowed row), SL-1063, SL-1067.

**Implementation detail (lead, Nov 14; it settles what the description left to the unit).**

**1. The signature.** `Target.frame_pointer` takes the effective feature list: `frame_pointer(&self, features: String) -> TargetFramePointer`. Its one caller, `ll_function_attribute_group` (`compiler/llvm/src/attributes.saw`), already has `features`, which the driver computes with `target_effective_features` before it reaches the backend. The answer:
- `Omitted` when `self.triple` starts with `xtensa` and `target_feature_state(features, "windowed")` is not `Off`. (Espressif's clang is windowed unless the feature is turned off, so a list that does not name it is windowed too; sawc's effective list for the triple always names it.)
- `NonLeaf` otherwise: call0 Xtensa and every other target, whose IR must not change by a byte.
- The function's comment says why: on windowed Xtensa the frame pointer is `a7`, an argument register, and a frame pointer makes the backend wrap calls that pass stack arguments in `movsp`. Present tense, no history, one trailing reference at most.

**2. Sweep first (obligation 4): who else reads the policy or assumes a frame pointer.** A table in the report: every use of `frame_pointer`, `TargetFramePointer`, the text `frame-pointer` and `FRAME_POINTER` under `compiler/`, `runtime/`, `std/`, `tools/` and `tests/freestanding/`, each classed "follows the funnel", "pins the text" or "assumes a frame chain exists". Anything of the third class is a STOP. Known pins of the text: the run lane's `FRAME_POINTER` and its attribute rows (`compiler/tests/run/run_lane.py`), `compiler/tests/run/hello.ll`, `runtime_dirent.ll`.

**3. Pins.**
- A unit program in `compiler/target/tests/` (beside `float_instructions.saw`, or in it): the policy for the Xtensa triple with the default list (`NonLeaf`), with `+windowed` (`Omitted`), with `-windowed` after `+windowed` (`NonLeaf`); for the riscv32, both arm64 and both Linux triples with their defaults (`NonLeaf`); for the arm64 freestanding triple with a list that happens to name `+windowed` (`NonLeaf`: the triple decides first).
- The run lane, beside `check_xtensa_object`: `--emit-ll` for the Xtensa target with `--target-features +windowed` holds `"frame-pointer"="none"` and no `"frame-pointer"="non-leaf"`; without the flag it holds `non-leaf` as today. `--emit-ll` needs no clang, so this part never skips.
- The object, in the same check, where Espressif's clang is present (the check's existing skip rule and message otherwise): a probe with a function of eight `Int` parameters that returns a value computed from the sixth, and a caller of it, built `-O1 --freestanding --target-features +windowed -c`; its disassembly (the `llvm-objdump` beside Espressif's clang) holds no `movsp`, and in the eight-parameter function no instruction writes `a7` before the first one that reads it. Show the same probe built from main's compiler failing both.
- The seven suite cases are SL-1128's, when the windowed row exists; nothing in `tests/freestanding/` changes here.

**4. What must not move.** Every hosted target's IR and the call0 Xtensa row's: `tools/battery.sh freestanding` passes with the same counts as on main, and the run lane's existing attribute rows are untouched. The corpus gate's verdicts must not move (the server's).

**Files:** `compiler/target/src/layout.saw`, `compiler/llvm/src/attributes.saw`, a `compiler/target/tests/` program, `compiler/tests/run/run_lane.py` with one probe under `compiler/tests/run/probes/` and the lane's README. Anything else is a stop. (`compiler/tools/front_parts.py --check` after the edit, since a public signature in `compiler/target` changes.)
