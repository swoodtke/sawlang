## Description

**Port serde to the new std: `Serialize`/`Deserialize`/`Encoder`/`Decoder`, and json's encoder and decoder on top of SL-813's token layer.** SL-813 ported the `JsonValue` tree only. Stage 0's `sawc/std/serde.saw` (268 lines) and json's `JsonEncoder`/`JsonDecoder` conformances wait for this. It's part of SL-596's std ports.

**Corpus rows it should move** (refused today, after SL-813):
- `json_escape_grid`, `json_map_keys`, `json_number_edges`, `json_roundtrip_struct`, `json_structural_reject` (`JsonEncoder`/`JsonDecoder`);
- `d249_std_selective_import_of_a_two_owner_name` (`encode`).

`d249_both_std_encoders_bare_is_a_tie_error` and `d249_std_json_and_cbor_both_name_encode` also need `std.cbor`.

**Design questions for step 1:**
- the `@synthesize(Serialize)` derivation in sawc2 (does mono synthesize it?);
- `DecodeError`/`EncodeError` and their fault enums move from `std.json` to `std.serde` (SL-813 c3);
- whether the prelude exposes the serde vocabulary (CLAUDE.md's digest says the curated prelude includes `Serialize`/`Deserialize`/`Encoder`/`Decoder`; check the new std's prelude).

**User ruling (Oct 30): the module is `std.serialize`, not `std.serde`.**

`Serialize`, `Deserialize`, `Encoder`, `Decoder`, `EncodeError`/`DecodeError` and their fault enums live in `std.serialize`. It is the format-neutral layer `std.json` and `std.cbor` (SL-938) both implement. "serde" was an abbreviation the no-abbreviations rule argues against, and it didn't explain itself to readers.

The port renames every mention of `std.serde`:
- `std/json.saw`'s doc comments
- LANGUAGE_SPEC.md's Serialization section
- the saw-lang skill
- `std/CBOR.md`/`std/JSON.md`
- any corpus program or resolver reservation that names it

The p833 survey lists the exact sites. Still open in this issue: whether the prelude exposes all four traits or only `Serialize`/`Deserialize`.

**Survey done (p833; full report `.build/scratch/p833/report.md`).** sawc does NOT derive `@synthesize` Serialize/Deserialize: typecheck accepts it, mono refuses it as `mono.not-yet`, and no serde glue exists. That is the port's only compiler work. Everything else probes green: hand-written conformances over `any Encoder`/`any Decoder`, Decoder's default bodies, `T.deserialize` on a type parameter, and json's JsonEncoder/JsonDecoder on SL-813's token layer, which passes 3 of the 6 rows std-only (4 with `json_map_keys` re-spelled, since `Map.each` isn't sync-callable). The error types move to std.serialize, with `InitFailed = 14` because `Alloc` already holds 13. A user type named `Encoder` does NOT shadow a prelude one: it's a hard `name.reserved` error. Recommendation: a slim prelude (only Serialize/Deserialize bare), pending the user. Units: 1, the std.serialize module (Sonnet); 2, the library's conformances for the integers, Bool, String, Optional and Vector (Sonnet); 3, json's seam (Sonnet); 4, the derivation, an eager typecheck check plus a MIR lowering of one uniform body (Opus). Probable bug, same class as the missing eager check: a reached `==` on a @synthesize Equatable with a non-Equatable member is refused as `mono.not-yet`, not as a user error (`u/derive_eq_bad.saw`).
