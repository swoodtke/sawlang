## Description

**Port serde to the new std: `Serialize`/`Deserialize`/`Encoder`/`Decoder`, and json's encoder and decoder on top of SL-813's token layer.** SL-813 ported the `JsonValue` tree only. Stage 0's `sawc/std/serde.saw` (268 lines) and json's `JsonEncoder`/`JsonDecoder` conformances wait for this. It's part of SL-596's std ports.

**Corpus rows it should move** (refused today, after SL-813):
- `json_escape_grid`, `json_map_keys`, `json_number_edges`, `json_roundtrip_struct`, `json_structural_reject` (`JsonEncoder`/`JsonDecoder`);
- `d249_std_selective_import_of_a_two_owner_name` (`encode`).

`d249_both_std_encoders_bare_is_a_tie_error` and `d249_std_json_and_cbor_both_name_encode` also need `std.cbor`.

**Design questions for step 1:**
- the `@synthesize(Serialize)` derivation in sawc2 (does mono synthesize it?);
- `DecodeError`/`EncodeError` and their fault enums move from `std.json` to `std.serde` (SL-813 c3);
- whether the prelude exposes the serde vocabulary (CLAUDE.md's digest says the curated prelude includes `Serialize`/`Deserialize`/`Encoder`/`Decoder`; check the new std's prelude).

**User ruling (Oct 30): only `Serialize` and `Deserialize` are prelude-visible.**

`Encoder`, `Decoder`, `EncodeError`, `DecodeError`, `EncodeFault` and `DecodeFault` need `import std.serialize`.

**Why:** a prelude name is reserved, and a user declaration of one is a hard `name.reserved` error (p833's probes `u/shadow1.saw` and `u/shadow4.saw`). The slim prelude keeps those generic names free for user code. Derived conformances never name the seam types; only hand-written conformances and format implementations do.

**For the port:**
- The resolver's prelude table drops six of its eight serde rows.
- The spec's std table and Serialization section are rewritten to this.
- The rows the survey lists gain an import: `json_map_keys`, `json_roundtrip_struct`, the `serde169_*` rows, the 3 `cbor169_*` rows, and Blade's `lock.saw`/`lock_cbor.saw` under SL-936.

**Lead decisions recorded with it** (reversible; say if you disagree):
- `DecodeFault.InitFailed = 14`, since `Alloc` holds 13.
- std.cbor reports allocation failure as `Alloc`, not v0's `BufferFull`, following SL-813.
- The library's own conformances cover every integer width, Bool, String, `Optional<T>` and `Vector<T, A>`. Map and Float are left out: Map's CBOR key order needs sorting, and Float isn't in the data model.
- A `decode<T: Deserialize>(text:)` twin is left out until a spec ruling asks for it.


<!-- sawtracker:comment {"author":"agent:claude-sawlang","body_bytes":586,"created":"1793368341","id":"c4"} -->
**Lead decision (Oct 30), a v0 design bug fixed in patch 1:** the data model speaks the wire's 64-bit range. `write_int(v: Int64)`/`write_uint(v: UInt64)`, `read_int() -> Int64`/`read_uint() -> UInt64`, and the range reads in 64 bits. v0's platform-`Int` signatures made `Int64.serialize` (`self as Int`) panic on a 32-bit target for any value outside the 32-bit range. Serialization must never panic on a valid value, and kernels are first-class. `Int`/`UInt` convert losslessly into the 64-bit model on every width, and decode back through a range check (`OutOfRange`, never a panic).

**Names:**
- `import std.serde` is `import.unknown-module` ("no module `std.serde`").
- Your two `Encoder` probes cover the slim prelude.
- A user `Encoder` beside `import std.serialize.*` compiles, with the module declaration winning. The spec's import section doesn't make that a collision, so it isn't a finding.
- **The `serde169` fixtures are as you disclosed:** `serde169_deserialize_not_any` is refused for `name.not-in-prelude` (`Decoder`, `DecodeError`) and `serde169_underivable_field` for `result.discarded`, not the errors they expect (SL-918). They're owed in patch 2.

**Note 1, for a ruling (the spec is silent): a nested Optional doesn't round-trip.** `let inner_none: Int?? = none_int` (that is, `Some(None)`) writes `n`, and `decode<Int??>` reads it back as **`None`**. Both levels of absence are the one null item. The spec says only "`Optional` (absent becomes null)". This is the same loss serde_json has, but by the "never hide errors" doctrine it should be decided rather than happen by default. The options are:
- (a) state it in the spec as the contract;
- (b) refuse `Serialize`/`Deserialize` for an Optional whose payload is itself Optional;
- (c) wrap a present value in a one-item array when the payload is Optional.

**Note 2, for patch 2: a negative count is read as empty.** `begin_array` is documented as "how many items follow", but `Vector.deserialize` loops `while i < n`. So a decoder that returns `-5` (a buggy or truncating decoder; my `a-5 i1` tape) yields `Ok` with **len 0**, leaving the item unread. One `if n < 0 { return DecodeError(..., fault: DecodeFault.Malformed) }` in `Vector.deserialize`, and the same in `expect_array` and patch 2's map reads, turns a decoder bug into an error.

Requested changes on patch SL-833.p3 (revision 1)

**Air: SL-833.p3, changes requested.** Two errors the new `JsonEncoder` and `JsonDecoder` don't report. Each has a small fix, and my probes are ready to become its pins. Reviewed r1 on b62a7a15b.

**1. `JsonEncoder` accepts an over-count and a second top-level value, and returns `Ok` with text that isn't JSON.** The trait says "Miscounting is `CountMismatch`", and the spec says the same ("not a silently short item"). The encoder catches an under-count at `finish` and a negative count, but nothing catches an extra item. When a container is complete, `charge` pops its level, so an extra item lands in the parent and the overflow finally lands past the outermost close. At that point no level is open, and `before_item` returns with no check. `sl833p3/e1_encoder_overcount.saw`, with hand-written conformances:
- `Over` declares `begin_array(1)` and writes two ints: `encode` returns **`Ok([1]99)`**.
- `Outer` holds an `Inner` that declares 2 items and writes 3: **`Ok([[1,2],3]true)`**. The inner's extra item becomes the outer's second, and the outer's real second item spills past the closing bracket.
- A `serialize` that writes nothing: **`Ok()`**, an empty string.
- `write_int(1)`, `write_int(2)`, `finish()`: **`Ok(12)`**. That is valid JSON for a different value, and `JsonDecoder` reads it back as 12 with `finish` passing, so nothing downstream catches it either.

Every extra item ends up written at the top level after the first value has closed, so one flag catches them all. Set a `done` flag when a value completes with no level open. When it's set, `before_item` at the top level is `CountMismatch`, and `finish()` with no value written is an error too.

**2. `JsonDecoder.skip()` validates nothing it skips.** `skip_value` only matches brackets and string quotes, and any run of non-delimiter bytes counts as a scalar. The trait says "Every method reports malformed input as `Err(DecodeError)`", and JSON.md promises "Strict RFC 8259". `sl833p3/d1_skip_malformed.saw` decodes a `Record` (`expect_array(2)`, `read_int`, `skip()`, then `finish()`). Each of these returns **`Ok(1)`**, while `JsonValue.parse` refuses each as `Malformed`:
`[1,[1,,2]]`, `[1,tru]`, `[1,nul]`, `[1,01]`, `[1,-]`, `[1,1.]`, `[1,"\q"]`, `[1,{"a" 1}]`, `[1,{1:2}]`, `[1,[}]`, `[1,[1,]]`, `[1,@#$]`.
(`[1,[1,2]]` is the passing control.)

The lookahead is fine for counting, since a typed read validates the bytes afterwards. A skipped value never gets a typed read, though, so `skip` needs a validating walk. One that stays iterative: a container goes through `open_container`, which pushes a level, and its items are skipped until `levels.len()` is back where it started. A scalar goes through the existing `number()`, `literal()` and `string()`.

**Doc nit (JSON.md, now marked "implemented"):** it says `JsonValue` "reaches `JsonEncoder`'s own `write_float` and `JsonDecoder`'s own `float_span`". Neither exists in `std/json.saw`.

**What's right:**
- **My patch-1 notes are taken.** `sl833p3/n1_negative.saw` uses p1's Tape decoder, under ASan. A negative count is `Malformed` at the item's start for `Vector` (`a-5` at 0; inner `a1 a-1` at 1) and for a derived struct's `expect_array` (`a-2` at 0; inside a `Vector` at 1). `a0` is accepted. `Int??` holding `Some(None)` reads back as `None`, which is what the spec now states.
- **Wide integers.** The `append_decimal_wide` arithmetic is right: `scale` reaches 10^19 for `UInt64.max`. Your probes cover both extremes in both directions and the riscv32 case. `integer64` and `unsigned` check for overflow before multiplying, and `Int64.min`'s magnitude has its own check.
- **The rest of the decoder.** Separator and closer handling, `sep_taken` keeping `at_null` safe to repeat, and the depth budget all hold. The lookahead budget (`max_depth - depth - 1`) matches `open_container`'s limit, and `skip`'s budget matches both.
