Approving SL-527.p1. `astdiff` is green again, `Data.spare()`'s fence is the right pairing, the new structural check refuses every misplacement I tried, and `File.read`'s doc matches its body. On your "please weigh": Python 3.14 turns the C-stack risk into a clean `RecursionError`, so the 20000 limit is safe as written.

**What I checked**
- **The gate passed on the applied commit:** tested_commit == applied_commit == c14c5d2e, with the python suite and freestanding run and passed. The tested tree, e30424ec, is the tree I get when I apply the diff to 7fc36dec.
- **`astdiff` on the applied tree:** 4810 tracked `.saw` files swept (390 rejected by the parser, as expected), "OK -- every file dumps completely and identically twice", rc 0, with no crash, fallback or skip line in the log.
- **`run.py`:** rc 0, including the std lane's 5 MIR pins (the new `data_spare.mir` among them), 16 std modules and 57 run programs matching Stage 0.
- **The fence pairs correctly.** `deinit` decrements with `__saw_atomic_sub_i64_release`, and the last owner fences acquire. `spare()`'s new acquire fence, after its relaxed `== 1` load, completes the same release/acquire pair for the path where another thread's copy was released, so that thread's reads of the bytes happen-before ours.
- **The structural check, by mutation** (`sl527/probe_uniqueness.py`). I ran `uniqueness_order_problem` on sawc2's MIR of `Data.spare` against four copies of `std/`:

  | variant | verdict |
  |---|---|
  | as patched | accepted |
  | fence removed | refused |
  | fence moved before the relaxed load | refused |
  | fence on the panic arm only | refused |

  All three refusals are "reaches its return on the sole-owner path with no acquire fence". The moved-before-the-load case is the one a plain "contains a fence" check would have passed.
- **The backend emits it:** Stage 2 builds a program reaching `spare()` through `String.to_data()` (`sl527/spare_build.saw`), its IR carries `fence acquire`, and it round-trips `fenced bytes`.
- **`File.read`'s doc against the body:**
  - It reads `end - here` bytes from `lseek(SEEK_CUR)`/`lseek(SEEK_END)`, so growth past `end` is left for the next `read`.
  - A pipe or FIFO fails the first `lseek` with ESPIPE.
  - **The edge the doc doesn't name:** a position PAST the end, reachable with no seek API (read to the end, let another process truncate the file, read again). It gives a negative `end - here`, then `Data.reserved` returns a blockless `Data`, `spare_count()` is 0, and the result is the empty `Ok` the doc promises. It's correct, so the doc needs nothing.
- **`sawc/ast_dump.py`'s `TupleLiteral` case** is used only by `--emit-ast` and the dump lanes, so no compile output moves. That fits the freeze's lane-tooling allowance.

**On the recursion limit (your "please weigh").** On the venv's Python 3.14.8 (`sl527/probe_recursion.py`):
- **Python-to-Python recursion, the parser's shape,** runs 300000 levels at a limit of 1e6 with no crash, because it uses no C stack.
- **Recursion through C calls** stops with `RecursionError: Stack overflow (used 16354 kB)`, a clean exception and not a segfault. 3.14 measures the real stack.

So the 20000 limit can't turn a deep input into a crash on 3.14. The worst case is a loud `RecursionError`, which `astdiff` reports as a crash. The `threading.stack_size` fallback isn't needed, and the venv is pinned to 3.14 (the SL-539 line).

**On the parked gate policy:** agreed. A per-file `astdiff` over the patch's changed `.saw` files, beside the grammar corpus's `CHANGED_SAW` step, closes the fixture-only gap that let main go red, and it costs seconds.
