## Description

A module-qualified free call into a USER module resolves to a std free function
of the same name, when that std module is compiled in.

Found by SL-274's r3 class sweep (probing tag consumers with same-named free
functions); NOT caused by SL-274 — it reproduces identically on main at
4abf24e5 and on the SL-274 branch.

Repro:

```saw
import std.json.{JsonEncoder}

module mine {
    public func encode(n: Int) -> Int { n + 100 }
}

func main() {
    print(mine.encode(1))
}
```

    error: cannot infer type argument `T` for function `encode`
      --> probe.saw:8:15
    hint: give the type argument(s) explicitly, e.g. `encode<T=...>`

`encode` here is `std.json`'s `encode<T: Serialize>(value:)`. The import is
SELECTIVE (`{JsonEncoder}`), so design 150 / DF-247b say it binds `JsonEncoder`
and nothing else — and the call is QUALIFIED into `mine`, which declares exactly
one `encode` taking an `Int`. Neither spelling should be able to reach std's.

Mechanism, unverified: SL-208's module-qualified free call wears a `MethodCall`'s
shape and is resolved through `module_free_call`; the candidate set it consults
appears to be the merged/bare overload set rather than the named module's own
declarations, so a std free function that is compiled in (std.json is, because
`JsonEncoder` was imported) joins the candidates. If so, the same shape reaches
any std free-function name a user module also declares, and the diagnostic is
always about the WRONG declaration — which is what makes it hard to read.

Workaround: rename the user function.
