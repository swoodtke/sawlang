**F2. The fixpoint twin reaches every descendant that runs sawc2** (SL-606, bucket F). Finding: Tooling 1, confirmed by gateperf on SL-605 (Oct 13).

- **Mechanism:**
  - The recognizer's worker Pythons (and those of `cases.py`, `negative.py` and the parse lane's `load_records`) import `build` fresh. Their `build.SAWC2` comes from `SAWC2_STAGE` (default Stage 2), not the twin the fixpoint lane put into the parent's `build.SAWC2`.
  - gateperf's probe (`.build/scratch/probe_twin_workers.py` in the gateperf worktree) logged 0 worker calls against 2 in-process.
  - So the fixpoint compares almost none of the recognizer's token dumps. In the SL-604 run, the parser-corpus step logged 63 calls and the parse lane 9.
- **A second hazard, from the same cause:** with stale stage binaries, two workers each started their own `build_sawc2()` and crashed racing on `.build/sawc2-runtime.txt.tmp`. The parent's `ensure_sawc2` checked the wrapper, which was fresh, instead of what the workers use.
- **Fix:**
  - pass the chosen binary to every descendant through the environment: `run_steps` sets e.g. `SAWC2_BINARY` in each step's environment;
  - `compiler/tools/build.py` resolves `SAWC2` from it before `SAWC2_STAGE`;
  - a worker that sees a fresh binary never tries to rebuild.
- **Then correct `recognize.py`'s comment and the reason it gives for the fixed 24-worker split,** which become true once the workers' calls are counted.
- **Expect** the fixpoint invocation count and replay time to rise, since the worker calls are compared for the first time. Report both, and keep the lane within SL-604's budget.
- **Pins:** a check like the probe, as a `run.py` step or in `parallel_order.py`: under a logging twin, a worker-based caller's calls are logged; and a stale-binary case where no worker rebuilds.
- **Done when:** the fixpoint compares the workers' calls, the pins pass, and the comment is true.

On c2's dedup decision (Air): sound if the key covers every input the command READS, not just the paths in its argv. For `sawc2 lex FILE`, which is almost all of the 38,000 new calls, the output is a function of FILE's bytes and the binary, so keying on (argv, FILE's content) is exact. From `resolve` on, though, a call also reads files its argv doesn't list:
- the `--std-root` tree;
- every `--module-path NAME=DIR` tree;
- an `@LIST` file and the files it names;
- the imports a program resolves.

Steps that generate fixtures under `.build/` and rewrite them between calls (module trees, the std lane's alternate roots) would then get a recorded verdict for inputs that have since changed. That's a stale comparison, and it can pass. Two safe shapes: (a) dedupe only the commands whose output depends on the named file alone (`lex`, `parse --dump` with no `@LIST`), which takes nearly all the gain; or (b) key every other command on the content of everything it can read (the std root, module-path trees, list files and their entries). (a) is simpler and loses little. Either way, a pin that rewrites a module-path file between two identical-argv `resolve --dump` calls under the twin, and requires the second to be compared afresh, keeps the key honest.
