Requested changes on patch SL-565.p1 (revision 1) (its test run was cancelled)

**Air: SL-565.p1 changes requested. A `join` releases spawn loans the joined local no longer holds, so a use-after-free compiles.** Probes are in `air-review/sl565p/probes/` on the Air, built on origin/main 2f6da4e09 + r1.

**The repro** (`r1b_reassigned_uaf.saw`):
```saw
var buf: Vector<Int> = []
var group = TaskGroup()
var h = group.spawn(fill(&var buf, 200))   // fill pushes with a yield_now per element
h = group.spawn(quick())                   // the first handle is discarded: its loan must last to the group's death
print("quick {}", h.join())
let taken = consume(move buf)              // must be loan.move-while-borrowed
```
It compiles at -O0 and -O2. It prints `quick 7` / `taken 1`, then dies at the group's teardown, which drives `fill` into the freed buffer: SIGTRAP natively, SIGSEGV under Guard Malloc. The spec says a discarded handle "holds its borrow until the group's death".

**The sibling** (`r1c_moved_then_rebound.saw`): `let g = move h; h = group.spawn(quick()); h.join(); consume(move buf)` compiles too, though the borrowing handle is in `g` and not yet joined. SIGSEGV under Guard Malloc. `r1_reassigned_handle.saw` is the `Int` form, a write to `a` after the rebound join, also accepted.

**The mechanism:** `spawn_releases` releases loan `n` at every `join` whose receiver local satisfies `facts.carries(n, h)`. The carrier set is built over the whole function: the spawn's destination plus every local it's ever assigned into. So the question asked is "did this local ever hold the handle", not "does it hold it here". Any redefinition between the spawn and the join (a rebind, or a move-out then a rebind, through `h` or any carrier like `var k = move h; k = …`) makes the join release a loan its handle no longer carries.

**Fix direction:** release loan `n` at a `join` of `L` only when the value reaching `L` there is `n`'s handle on every path. The simple sound form: every local on the chain from the spawn's destination to `L` has exactly one definition, which makes `r1`/`r1b`/`r1c` refusals and keeps `let g = move h; g.join()` releasing. Pin the three probes, plus a conditional rebind (`if c { h = group.spawn(quick()) }` before the join), as refusal fixtures.

**Stage 0 has the same hole:** `r1b` compiles under `sawc/` and faults the same way. Since the oracle can't catch this, it wants an SL:hazards entry; that's the lead's to write.

**Checked and fine:**
- **The other release path:** a group's `Drop` releases its loans. Sound, because `TaskGroup` is `NoMove` (`r7_moved_group.saw` is refused at `transfer.no-move` on both compilers), so a dropped group place is where the tasks live.
- **Refusals with Stage 0's wording, at the right statement:** two handles joined one at a time (`r2`), a handle handed to a function that drops it (`r3`), `cancel()` without a join (`r4`), a handle moved but not joined (`r5`), and a write under a shared spawn borrow (`r6`).
- `a1_accepts.saw` (a join releases, two shared borrows beside a read, a join inside a loop body) runs identically to Stage 0.
- **The two reversible decisions match the spec.** The `loan.handle-escape` refusal is the spec's LIFO hazard through a `&TaskGroup` parameter: a discarded handle holds its borrow "until the group's death", which is after the callee's locals. A chained `.join()` is a join.

**Air: a correction to my c5 fix direction. "Every local on the chain has exactly one definition" doesn't cover the loop instance S36 r97 adds.** A `let h = group.spawn(look(&buf))` in a loop body has one definition in the text but runs once per iteration, and every iteration's task carries the same static loan. So one join can't tell iteration 1's handle from iteration 0's.

**Evidence** (Stage 0; I haven't rebuilt r1 for it), `air-review/sl565p/probes/r9b_shared_loop_uaf.saw`:
```saw
while i < 2 {
    let h = group.spawn(look(&buf, if i == 0 { 5000 } else { 1 }))   // look yields n times, then reads v[0] + v[2]
    i = i + 1
    if i == 1 {
        continue                     // iteration 0's handle dropped unjoined: its &buf lasts to the group's death
    }
    print("joined {}", h.join())     // iteration 1's join
}
let taken = consume(move buf)        // accepted
```
It compiles. Natively it prints `taken 3`, then `look reads 3`: iteration 0's task reads the freed buffer after the move (the true sum is 4). Under Guard Malloc it dies with SIGSEGV. The branch-join shape (`r8_shared_loop.saw`, join under `if i == 1`) is refused by Stage 0 ("nothing joins its handle"). The `continue` shape is not, because every path to the loop's exit passes the join.

**Two sound fixes:**
- **(1) The spec's loop-body rule, read as written:** "A borrow still live when a loop body ends is refused outright". As written, that covers a shared spawn borrow too, not only the exclusive one its reason names. Iteration 0's `continue` path leaves the loan live at the body's end, so `r9`/`r9b` are refused. This is the smaller change.
- **(2) Keep shared loop spawns legal:** a join releases loan `n` only if `n` wasn't already live where its spawn re-made it. A loan that reaches its own spawn site live is held by two tasks, so no single join releases it, and it lasts to the group's drop.

Either way, my c5 single-definition rule still holds for the straight-line instances (`r1`, `r1b`, `r1c`, the conditional rebind), and `r9b` joins the refusal fixtures. Which reading of the loop-body sentence is the user's or the lead's call: (1) refuses the shape, (2) accepts it with a longer loan.
