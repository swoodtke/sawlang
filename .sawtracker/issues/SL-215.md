A suspending call inside the catch block of the INLINE try form (`try EXPR catch { ... }`, a TryExpr with a catch_block — parser/expressions.py:1382) is refused by the coroutine transform:

  coroutine transform: suspending call to `respond` in `caller` appears in a nested/expression position

Repro (same-module; cross-module behaves identically after SL-208):

  func respond() { yield_now(); print("x") }
  func fallible() -> Result<Int, Failure> { yield_now(); 5 }
  func caller() -> Result<Int, Failure> {
      let n = try fallible() catch { respond()  return 0 }   // REFUSED
      n
  }

MECHANISM: design 196 unit 3 CFG-splits the BLOCK form `try { } catch { }` (a TryCatchExpr) when it spans a suspension, so a suspending call in that catch embeds fine. The INLINE form parses to a TryExpr with a catch_block, which _collect_calls never routes to the split path (its try/catch arm matches TryCatchExpr only), so the catch's suspending call falls to _reject_buried_suspend_call. Pre-existing, same-module too — NOT the SL-208 module-boundary divergence (SL-208 fixed that; before it, the CROSS-module spelling was silently token-0 miscompiled here, now it reports the same clean refusal as same-module).

WORKAROUNDS that embed correctly today (both verified under SL-208): the match-arm form (`match fallible() { case Ok(v) -> v, case Err(_) -> respond() }`) and the block form (`try { let _ = try fallible() } catch { respond() }`).

FIX DIRECTION: either route the inline TryExpr-with-catch through the design-196 TryCatchExpr split (it is semantically `match EXPR { Ok(v) -> v, Err(error) -> catch_block }`), or normalize it to that match before the split walk. Watch the error-binding name, the try!/try/try? variants, the route_path `try (x as ...)` clause, and the multi-error union refusal (DF-196b).
