**A named function used as an ordinary function value is refused by sawc's backend.** `let f: (Int) sync -> Int = doubled`, with `doubled` a named `sync` function, typechecks and then fails in the backend with "a memory constant is not in the backend slice yet". Found by SL-940's census (`.build/scratch/p940/census.md`); the agent will attach a minimal repro to its report.

This is a closure-typed value, not a `FuncPointer`: SL-940 covers `FuncPointer` and leaves this path as it is. The spec lets a named function stand where a function type is expected (check the section on function types and closures, and say if it doesn't).

**What a fix owes:** a census of the positions a named function can appear as a value (a `let`, an argument, a field, a return, a collection element, a generic argument), each compiled and run, and the lowering: a thin closure value with no environment, whose call goes through the same path as any closure's.


<!-- sawtracker:comment {"author":"agent:claude-sawlang","body_bytes":715,"created":"1793632715","id":"c2"} -->
USER RULING (Nov 2): it should work, with no FuncPointer involved. A function type like `(Int) sync -> Int` is a closure value (code plus an optional environment); a named function is the zero-capture case and fits wherever such a closure fits (`sort(by: compare)`, a callback field, a `let`). `FuncPointer<F>` stays the bare C-ABI address, built by expected type (`let f: FuncPointer<F> = doubled`), with no constructor call. The spec's "Functions are not first-class values in Saw" (the FuncPointer section) contradicts its own "a named function's value" (Sendable function types) and "a blocking function cannot be taken as a function value"; SL-940's patch 1 rewrites that sentence, since it edits that section.

<!-- sawtracker:comment {"author":"agent:claude-sawlang","body_bytes":901,"created":"1793633528","id":"c3"} -->
USER RULING (Nov 2), part 2: a named function that may suspend cannot be taken as a function value, until Saw supports heap-allocated frames (the design the spec already names for dispatch and suspending recursion). A call through a function value has no frame to park a suspension in, the same reason a closure body may not suspend and a FuncPointer must be sync. So: a sync named function converts to its function type with or without `sync` (and to FuncPointer); a suspending one converts to neither, and taking it as a value is a clean compile error at the use, naming the function, the suspension source it reaches, and the reason (in the style of the blocking-function refusal). The fix owes: the refusal funnel with its entry points (every position a named function can be a value), the spec text beside 'A blocking function cannot be taken as a function value', and fixtures for each position.
