## Description

A closure literal NESTED inside another one, both naming a frame-resident local
of a driven body, is an INTERNAL COMPILER ERROR — on a program whose sync twin
compiles and runs.

    internal compiler error at f.saw:11:27 (Identifier): Undefined variable: __cap0_t

Found by the SL-213 r2 obligation-4 sweep (the nested-literal cell). Reproduces
on origin/main (5755f60b) with NO capture spec written anywhere, so it is
independent of SL-267/SL-268; the branch reaches it too, because per-literal
materialization newly routes an authored `[copy x]` through the same rename.
FIXED IN THE SL-213 r3 LANDING (see below for why it was not separable).

MECHANISM (named, per obligation 4). `_materialize_closure_captures`
(sawc/coro_transform.py) materializes a captured frame local as a `let` ahead of
the closure and RENAMES the closure onto that fresh local — two closures in one
block cannot both declare a `let n` (DF-196e). The rename is
`_rename_in_closure`, which does two things:

    map_nodes(cexpr.body, rule)      # identifier reads, a `move`, a call head
    ...rename cexpr.capture_specs / cexpr.captures / cexpr.capture_modes

The first reaches a NESTED literal's body — those are ordinary AST nodes under
`cexpr.body`, and `map_nodes` walks them. The second did not: a nested literal
carries its OWN three capture lists, which hold plain strings that no identifier
rewrite can see. So the inner closure went on declaring a capture of `t` while
its body read `__cap0_t`, and codegen built an environment with a field for `t`
and no binding named `__cap0_t` — hence the undefined-variable ICE at the inner
read.

REPRO (no capture specs at all):

    struct Tick { n: Int }
    extension Tick: Copy { func copy(&self) -> Tick { Tick(n: self.n) } }

    func run_tick(body: () sync -> Int) -> Int { body() }

    func both_implicit_sync(t: Tick) -> Int { run_tick({ run_tick({ t.n }) }) }
    func both_implicit_driven(t: Tick) -> Int {
        __saw_suspend()
        run_tick({ run_tick({ t.n }) })
    }

    func main() {
        print("-- both implicit sync")
        print("= {}", both_implicit_sync(Tick(n: 30)))
        print("-- both implicit driven")
        print("= {}", __saw_drive(both_implicit_driven(Tick(n: 30))))
        print("end")
    }

On origin/main the sync line compiles and the driven one is the ICE above; the
whole program therefore does not build.

FIX. `_rename_in_closure`'s rule now renames the bookkeeping of every nested
`ClosureExpr` it walks, through one `_rename_closure_bookkeeping` helper that
the outer literal also goes through — one rename, every literal in the subtree.
Safe as a flat rename for the same reason the identifier half is:
`_uniquify_bindings` has already made every binding in the tree unique by name,
so no binding inside the closure can be spelled the old name and shadow it.

WHY IT LANDED WITH SL-213 rather than on its own: that branch makes an authored
`[copy x]` take the rename path (each `[copy]` capture needs its own local, so
the frame local's name can no longer be reused), which puts `{ [copy t] in ...
{ t.n } ... }` on exactly this ICE. Leaving the helper incomplete would have
meant the branch INTRODUCING the failure for a shape that worked; the two are
one mechanism and the fix is the same three lines either way.

PINNED BY: `examples/nested_closure_captures_frame_local.saw` — the all-implicit
pair (this repro), an authored outer over an implicit inner, and an authored
`[copy]` pair, sync and driven.
