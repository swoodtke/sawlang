## Description

**`T()` through a type parameter is refused by mono when `T` is an allocator with fields or an `init`.** Found by SL-964's sweep while it was looking for an owned trigger for a refusal reached inside std.

**What happens:** `check_empty_construction` (`compiler/mono/src/worklist.saw`) refuses a `T()` construction through a type parameter unless `T` is an empty type. A generic std routine that builds its allocator this way is refused at mono when it's instantiated with an allocator that has fields or an `init`, for example `Vector<Int, A>` with such an `A`. Typecheck accepts the program.

**Expected:** decide whether `T()` through a type parameter is part of the language for non-empty types:
- **If it is**, mono constructs it: the default `init`, or a memberwise one with defaults.
- **If not**, typecheck refuses it at the bound, with a reason the reader can act on.

Either way, mono shouldn't refuse late what typecheck accepted.

**First step, per obligation 4:** census every position where a type parameter is constructed (`T()`, `T(...)`, a static on `T`) against the allocator and non-allocator types that reach it, with compile-and-run evidence.

SL-964 points its std-position refusal fixture at this gap as its owner until it closes.

# SL-966 census: `T()` through a type parameter (sweep agent, Nov 6; raw results in results.json, cells/, extras/)

**The headline:** typecheck accepts a zero-argument `T()` through a type parameter, checking no bound. Mono then refuses every instance that isn't a fieldless struct with no `init` (`mono.not-yet`, `compiler/mono/src/worklist.saw:2022–2054`). Edge shapes:
- `struct S { e: E }` with zero-sized E, and `enum S {}`: refused by mono, so an uninhabited value is never fabricated.
- Fieldless NoCopy with a `deinit`: OK.
- A generic with `T()` that is never instantiated at a non-empty type: OK. The refusal is instantiation-driven, against spec 12734–12738's "a generic body is type-checked once, abstractly, against its bounds".

## Spec and designs
- Nothing states whether `T()` on a type parameter is allowed. The spec's only `A()` is the allocator idiom:
  - 15935–15937: `GlobalAllocator` is a zero-field unit struct;
  - 15944–15956: "a custom allocator is written as a zero-field unit struct conforming to `Allocator`", and `A().alloc` is a direct static call.
- Design 19 (designs/19-freestanding-profile.md:82–114) decided on zero-sized, static-backed allocators and rejected stored allocator values. Design 37:32–34 calls `A()` a "zero-sized construction".
- Static requirements on a type parameter work: spec 2699–2727 and 8379–8385, and `std/serialize.saw:431,460`. SKILL.md:2198–2200 says they don't (DF-169e), which is stale.

## The mono check

**Ruled (user, Nov 6): option C, init requirements in traits.** A trait may declare an `init` requirement, and `T(args)` through a type parameter is legal exactly when `T`'s bounds declare an init that matches the call. `T()` is the zero-argument case of the same rule. A generic body is checked against its bounds, so `T()` with no such bound is refused at typecheck. Mono's late refusal goes away. **For allocators, `A()` is a no-op:** an `Allocator` conformance is a zero-field unit struct, whose zero-argument construction materializes nothing (design 19's zero-sized, static-backed allocators).

**Design draft.** The lead's recommendation for each open point; points 1–4 are for the user to confirm:
1. **A memberwise init satisfies a requirement** when its labels and types match the requirement's exactly. An override `init` satisfies it too, since an override is called by every construction, a generic body's included (spec, B31).
2. **Fallibility is matched exactly.** A requirement `init(...) -> Result<Self, E>` or `-> Self?` makes `T(...)` produce that type. A conformer's init must have the same return form. Whether an infallible init may satisfy a fallible requirement is deferred until a use case.
3. **`Allocator` declares `init() -> Self`.** Its conformance must be a zero-field struct with no hand-written `init`, checked at the conformance with a reason naming the allocator model. Its memberwise `A()` is a no-op that LLVM emits nothing for, as today.
4. **No default body for an init requirement.** An init requirement can't be called through `any Trait`, because an existential has no `Self` to build, but a trait that has one can still be erased.

Points 5–7 follow from the ruling and need no decision:

5. **Enums can't satisfy an init requirement**, since enums have no `init`. That refusal happens at the conformance. Builtins are already orphan-blocked.
6. **`Self(args)` in a trait's default body** follows the same rule (SL-987 refuses it in the meantime).
7. **Existing users:** the 3 non-allocator `T()` programs (`default_type_param.saw`, `generic_instance_constructs_type_param.saw`, typecheck golden `lowlevel.saw`) add `init()` to their bound traits. std's 9 `A().alloc`/`dealloc` sites are unchanged.

**Design (user-confirmed, Nov 6): init requirements in traits, and `init`s on enums and primitives.**

**The rules:**
1. **Init requirements.** A trait may declare `init(labels...) -> Self`, or `-> Result<Self, E>` or `-> Self?`. `T(args)` through a type parameter is legal exactly when `T`'s bounds declare an init requirement matching the call's labels and types. `T()` is its zero-argument case. A generic body is checked against its bounds, so a `T(...)` with no matching requirement is refused at typecheck, with a fix-it naming the requirement to add. No late mono refusal.
2. **Satisfying one:**
   - A conformer's `init` with the same labels, types and return form satisfies the requirement.
   - So does a struct's memberwise construction, when the fields match exactly.
   - An override `init` satisfies it too, since an override is called by every construction.
   - Fallibility matches exactly. Whether an infallible init may satisfy a fallible requirement is deferred until a use case.
3. **Restrictions:** no default body for an init requirement. An init requirement can't be called through `any Trait`, since there is no `Self` to build, but a trait that has one can still be erased for its other members.
4. **Enums may declare `init`s.** The spec's refusal ("an enum's cases are its constructors") is lifted. An enum `init` returns one of its cases, or a `Result`/`Optional` of one. Case construction stays qualified (`Color.Red`), so `Color(...)` collides with nothing. Raw-backed `E.from(raw:)` is unchanged.
5. **Primitives may declare `init`s** in an extension, like any extension init: `extension Int { init(...) -> Int }`. No primitive gets an implicit `init()`, and no zero default is inferred. A trait that wants one declares it, and its conformance supplies it.
6. **Where an `init` may live is unchanged.** An ordinary `init` may be declared in any module and is import-scoped, like a method. Only an `init` that overrides a struct's memberwise construction is confined to the struct's module (`init.override-outside-module`). Enums and primitives have no memberwise construction, so nothing of theirs is an override. A generic's `T(...)` resolves only through its bounds, so the satisfying init is the conformance's, which the orphan rule places in the type's or the trait's module. An import-scoped `init` elsewhere never changes what a generic does.
7. **Allocators:** `Allocator` declares `init() -> Self`. An `Allocator` conformance must be a zero-field struct with no hand-written `init`, checked at the conformance with a reason naming the zero-sized allocator model (design 19). Its memberwise `A()` is a no-op that emits nothing. std's 9 `A().alloc` and `A().dealloc` sites are unchanged.
8. **`Self(args)` in a trait default body** follows rule 1 over the trait's own init requirements. SL-987 refuses it in the meantime.

**Units:**
- **U1, spec and grammar first (obligation 3):** GRAMMAR.md's `requirement` gains an `init` form, and the enum-init refusal is removed from the grammar and spec. LANGUAGE_SPEC's Traits, Methods on enums, Extensions and Allocators sections are rewritten to the rules above. Conformance rows (`tests/corpus/conformance/INDEX.md`) cover a requirement satisfied and missed, a fallibility mismatch, an enum init, a primitive init, the allocator unit rule, and `T()` with no bound refused at typecheck.
- **U2, parser, resolve and typecheck:**
  - the init requirement, and conformance matching including memberwise and override;
  - `T(args)` through a bound, and the typecheck refusal with its fix-it;
  - enum and primitive inits, with `Int(...)` resolving to an extension init;
  - the `Allocator` unit rule at the conformance.
- **U3, mono:** dispatch `T(args)` to the conformer's init. `check_empty_construction` becomes an invariant. The erased-box allocator glue follows rule 7.
- **U4, the existing users and docs:** the 3 non-allocator `T()` programs (`default_type_param.saw`, `generic_instance_constructs_type_param.saw`, typecheck golden `lowlevel.saw`) add `init()` to their bound traits. The saw-lang skill and README get the feature, and corpusdiff records the moves.

**Air: SL-966 design pre-review. Three points before U1 writes the spec.**

**1. `-> Self?` contradicts a standing rule, and nothing says so.** Rule 1 lets an init requirement return `-> Self?`, and rule 4 lets an enum init return "a `Result`/`Optional` of one" of its cases. LANGUAGE_SPEC refuses an optional `init` today, with its own pinned error (DF-245a):
> `init` may not return an optional — an optional creation encodes as `Result<Config, E>`, because a `None` names no cause

That's the never-hide-errors rule applied to constructors. So the design either drops `Self?` from rules 1 and 4, or reverses DF-245a for requirements and enums, which is the user's call and should say so. If it's dropped, the fallibility-matching sentence in rule 2 simplifies to infallible against `Result` only.

**2. A memberwise construction satisfying a requirement can bypass `private`.**
- Rule 2 lets a struct's memberwise construction satisfy `init(...) -> Self` when the fields match exactly.
- The orphan rule lets the TRAIT's module declare that conformance. If any field is `private`, that module can't write the memberwise literal itself: the spec's member-visibility rule needs every field visible.
- But through the conformance, any generic anywhere could then build the value with `T(a:, b:)`, private fields set to arbitrary values.
- **Suggested rule:** memberwise construction satisfies a requirement only where it's legal at the conformance's declaration. In the type's own module that's always true; elsewhere every field must be visible. An `init` the type's author wrote is unaffected.

**3. `Int(...)` today: no clash, but a message to replace.** On main, `Int(5)` and `UInt8(7)` are `slice.not-yet` ("constructing the builtin type `Int` is not in the bootstrap slice yet"). They fall into the builtin-construction catch-all in `bodies.saw`, which exists for `Atomic` and `UnsafeMemory`. `Byte(65)` already works, as alias construction. So rule 5 collides with nothing. But once primitives may declare inits, `Int(5)` with no matching extension init should be a real refusal naming rule 5 (no implicit `init()`, no inferred zero), not a "not yet". U2's fixture list could carry that row.

**Design amendments, after the Air's pre-review (lead, Nov 6).** These are folded into `.build/scratch/p966/design.md`.

1. **No optional inits.** DF-245a stands: an `init` may not return an optional, because a `None` names no cause, and a fallible creation is `Result<Self, E>`. In rules 1 and 4, "`-> Self?`" and "an `Optional` of one" are struck. A requirement and an enum `init` return `Self` or `Result<Self, E>`. Rule 2's fallibility matching is now "a conformer returns exactly the requirement's form, `Self` or `Result<Self, E>`". Reversing DF-245a would be a separate user ruling. The lead's draft carried `Self?` by mistake.
2. **A memberwise construction satisfies a requirement only where it is legal at the conformance's declaration.** In the type's own module that is always true. Elsewhere, for example a conformance in the trait's module, every field must be visible, so a private field can never be set through `T(...)` from outside. An `init` the type's author wrote is unaffected. It's a ledger row in U1 and a fixture in U2.
3. **`Int(5)` with no matching extension init** gets a real refusal naming rule 5: no implicit `init`, no inferred zero. It replaces today's builtin-construction `slice.not-yet` catch-all for primitives (`Atomic` and `UnsafeMemory` keep theirs). It's a fixture in U2. `Byte(65)`'s alias construction is unchanged.
