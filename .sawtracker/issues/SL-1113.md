## Description

**The Linux run lane fails on main: 8 checks on aarch64, 10 on x86_64, none of them a run program.** Measured by the lead on Nov 14 in the `sawlang-linux` VM, on main at 3fc4db5b3 (both architectures) and on SL-1109's commit (the same failures), with `tools/linux.py lane` and, for x86_64's baseline, `run_lane.py --target x86_64-unknown-linux-gnu` in the VM's clone. Logs under `.build/scratch/p1109f/` in the lead's checkout: `linux_lane_main.log` (aarch64, and x86_64 cut short by a full disk), `linux_lane_main_x86.log`, `linux_lane.log`. So the battery's `linux` lane cannot pass today, and a real regression on Linux would be one more line among these.

**1. `run front shared writers`, eight rounds, both architectures.** Each round: "after round N the packages' layers are ['computed', 'computed']", followed by the build's `--time-stages` lines. The check expects something other than two `computed` layers after concurrent writers share a front cache (read the check for what: by its name, one writer's layers should be read by the other). It passes on macOS. UNVERIFIED cause: a difference in file locking or rename visibility on the VM's filesystem, or timing.

**2. `run codegen units`, x86_64 only:** "the split -c object does not link: … ld: …/codegen-units/object.o: relocation R_X86_64_32 against `.bytes.2.llvm.…` can not be used when making a PIE object; recompile with -f…". A `-c` object built with split codegen units for `x86_64-unknown-linux-gnu` is not position-independent where the cross linker makes a PIE. Either sawc's `-c` objects for that target want the PIC relocation model, or the check's link line wants `-no-pie`; which is right is the question (what does `sawc build` without `-c` do for that target, and why does it link?).

**3. `run object cache`, x86_64 only:** "a sanitized split build exits 1 and uses no a cache" (the message has a typo, "no a cache"). The VM's cross toolchain has no x86_64 address-sanitizer runtime (`libclang_rt.asan.a` for `x86_64-unknown-linux-gnu` is absent; seen directly while investigating SL-1109). The check should skip, naming the missing runtime, where the target has none, as the freestanding suite skips an architecture whose tool is known absent; or the VM image should carry the runtime (`tools/lima/sawlang-linux.yaml`).

**4. The lane meets a full disk as a traceback.** With the VM's 20 GB disk full (stale clones under `~/sawlang/` and scratch under `/tmp`), `run_lane.py` ended in `OSError: [Errno 28] No space left on device` from `check_executable_path`'s `os.makedirs`, and `tools/linux.py lane` reported exit 2 with no sentence of its own. `tools/linux.py` should check free space in the VM before a sync or a lane (and say how to free it), and `status` should show it. Clones are removed by hand today (CLAUDE.md's landing steps do not mention the VM's clone; the lead's notes do).

**Also printed on both, not counted as a failure:** "builtin lowering: xtensa-esp-unknown-elf not compiled: no clang qualifies …" (the VM has no Espressif clang). Expected there; listed so nobody reads it as one of the failures.

**Not in question:** every run program and probe passes on both architectures, SL-1109's seven and the process probes among them.


## Comments

**The mechanisms (Sonnet investigation p1113, Nov 14; read-only; evidence under `.build/scratch/p1113/` in the lead's checkout, file names in brackets), and the lead's ruling on each.** All three failures reproduce alone in the VM's clone [step0_*.txt].

**1. `run front shared writers`: the CHECK's defect. The cache is shared on Linux; the check compares two commands that use different triples there.**
- The check runs `sawc resolve --check` on a cold cache, then `sawc build --time-stages --emit-ll` on the same cache, and wants the build's `geometry` and `shapes` layers `loaded`. On Linux the build recomputes everything, std's image included (3 cache files become 7) [hand1_resolve_then_build.txt].
- **Why:** the check stages (`resolve` … `coro`) take their triple from `driver_check_triple()`, which returns the constant `"arm64-apple-darwin"` (`compiler/driver/src/main.saw`); `build` takes the host's from the runtime manifest (`aarch64-unknown-linux-gnu` in the VM). `driver_front_key` hashes the triple, so the two never share an image. On arm64 macOS the two coincide, which is why the check passes there.
- **Shown by varying one thing** [hand3_vm_typecheck_target.txt, probe_aligned_vm.txt]: `typecheck --check --target aarch64-unknown-linux-gnu` then `build` loads (3 files become 4); the check's eight rounds replayed with the first command's `--target` set to the host's pass 8 of 8 on Linux; and on macOS, `typecheck --check --target aarch64-unknown-linux-gnu` then `build` reproduces the Linux failure [hand4_host_mirror.txt]. Filesystem, locking and rename are ruled out by the aligned pass. The lane's "x86_64" run of this check is the same experiment (the check ignores the target, and the VM's sawc is aarch64).
- **Ruling:** fix the check: its first command names the triple the warm build uses. And sweep its siblings (the other checks that mix a check-stage command with a build and assert a layer or cache state).
- **A question this raises, the user's, filed separately:** on Linux `sawc typecheck FILE` (and `resolve`, `mir`, `eval`, `borrowck`, `drops`, `mono`, `coro`) checks for `arm64-apple-darwin` by default, not for the host. Deliberate (a fixed triple keeps the lanes' goldens the same on every host) or not?

**2. `run codegen units`, x86_64: the DRIVER's defect. A split `-c` object built with the default thin LTO is not position-independent on x86_64 Linux.**
- `sawc build --target x86_64-unknown-linux-gnu -c --codegen-units=module` compiles each unit `clang -c … -flto=thin` and joins them with `clang … -r -nostdlib -flto=thin -fuse-ld=lld` (`driver_split_link`'s object branch) [cg_clang_lines.txt]. `ld.lld -r` runs the LTO backend with the static relocation model, since nothing tells it otherwise.
- `readelf -rW` [cg_reloc.txt]: that object has 598 `R_X86_64_32` and 291 `R_X86_64_32S`; a whole-module `-c` object and a split one with `--lto=none` have none. The check's link line is the ordinary one (clang defaults to PIE there), and it links the other two. A whole-program `sawc build` is a PIE. On aarch64 the same object happens to carry no absolute 32-bit relocation, so the same path is non-PIC there and harmless.
- Tried on the `-r` link [cg_fix_probe.txt, cg_fix_probe2.txt]: `-fPIC`/`-fPIE` on the link or on the units change nothing; `-Wl,-mllvm,-relocation-model=pic` gives 0 such relocations and the object links. Only clang-19 and thin LTO were tried.
- **Ruling:** fix the driver: a hosted ELF target's split `-c` object is position-independent, as its whole-module and non-LTO objects are. Freestanding objects stay non-PIC (`driver_freestanding_arguments`). The implementer confirms the spelling for `--lto=full` and for each clang the project accepts before choosing it.

**3. `run object cache`, x86_64: the VM lacks the runtime, and the check words a link failure as a cache failure.**
- The VM's clang-19 resource directory holds address-sanitizer runtimes for aarch64 only; `sawc build --target x86_64-unknown-linux-gnu --sanitize address` ends "ld: cannot find …/libclang_rt.asan.a", `clang exited 1` [san.txt]. The check discards that and says "a sanitized split build exits 1 and uses no a cache".
- **Ruling:** the check skips, naming the target and the missing runtime, where a link of an empty C `main` with `-fsanitize=address` for the target fails (the lane's existing skip-with-a-count form); on any other failure its message carries the build's output; the typo goes. Whether the VM image gains the runtime (`libclang-rt-19-dev:amd64` by the agent's reading of `apt-cache`; UNVERIFIED that it lands where clang looks, and that a sanitized x86_64 binary runs under Rosetta) is left open: say if you want it.

**4. A full VM disk** (nothing new found): `tools/linux.py` gains a free-space check before a sync or a lane, a line in `status`, and a command to remove a clone by name, so landing can clean up through the tool.
