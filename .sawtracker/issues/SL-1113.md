## Description

**The Linux run lane fails on main: 8 checks on aarch64, 10 on x86_64, none of them a run program.** Measured by the lead on Nov 14 in the `sawlang-linux` VM, on main at 3fc4db5b3 (both architectures) and on SL-1109's commit (the same failures), with `tools/linux.py lane` and, for x86_64's baseline, `run_lane.py --target x86_64-unknown-linux-gnu` in the VM's clone. Logs under `.build/scratch/p1109f/` in the lead's checkout: `linux_lane_main.log` (aarch64, and x86_64 cut short by a full disk), `linux_lane_main_x86.log`, `linux_lane.log`. So the battery's `linux` lane cannot pass today, and a real regression on Linux would be one more line among these.

**1. `run front shared writers`, eight rounds, both architectures.** Each round: "after round N the packages' layers are ['computed', 'computed']", followed by the build's `--time-stages` lines. The check expects something other than two `computed` layers after concurrent writers share a front cache (read the check for what: by its name, one writer's layers should be read by the other). It passes on macOS. UNVERIFIED cause: a difference in file locking or rename visibility on the VM's filesystem, or timing.

**2. `run codegen units`, x86_64 only:** "the split -c object does not link: … ld: …/codegen-units/object.o: relocation R_X86_64_32 against `.bytes.2.llvm.…` can not be used when making a PIE object; recompile with -f…". A `-c` object built with split codegen units for `x86_64-unknown-linux-gnu` is not position-independent where the cross linker makes a PIE. Either sawc's `-c` objects for that target want the PIC relocation model, or the check's link line wants `-no-pie`; which is right is the question (what does `sawc build` without `-c` do for that target, and why does it link?).

**3. `run object cache`, x86_64 only:** "a sanitized split build exits 1 and uses no a cache" (the message has a typo, "no a cache"). The VM's cross toolchain has no x86_64 address-sanitizer runtime (`libclang_rt.asan.a` for `x86_64-unknown-linux-gnu` is absent; seen directly while investigating SL-1109). The check should skip, naming the missing runtime, where the target has none, as the freestanding suite skips an architecture whose tool is known absent; or the VM image should carry the runtime (`tools/lima/sawlang-linux.yaml`).

**4. The lane meets a full disk as a traceback.** With the VM's 20 GB disk full (stale clones under `~/sawlang/` and scratch under `/tmp`), `run_lane.py` ended in `OSError: [Errno 28] No space left on device` from `check_executable_path`'s `os.makedirs`, and `tools/linux.py lane` reported exit 2 with no sentence of its own. `tools/linux.py` should check free space in the VM before a sync or a lane (and say how to free it), and `status` should show it. Clones are removed by hand today (CLAUDE.md's landing steps do not mention the VM's clone; the lead's notes do).

**Also printed on both, not counted as a failure:** "builtin lowering: xtensa-esp-unknown-elf not compiled: no clang qualifies …" (the VM has no Espressif clang). Expected there; listed so nobody reads it as one of the failures.

**Not in question:** every run program and probe passes on both architectures, SL-1109's seven and the process probes among them.
