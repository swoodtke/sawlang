Found by the SL-1011 spec review (F10 and F11).

LANGUAGE_SPEC "Type Definitions" makes `type UserId = Int` a DISTINCT type:
- `let order: OrderId = user` is an error;
- `42 as UserId` is an error;
- a sibling-alias cast is rejected;
- `let m: Byte = 45` is not legal;
- an annotated `let` takes an underlying-typed initializer only for the four primitive kinds.

It also refuses an alias whose underlying type is an enum, whether written directly, through an alias chain, raw-backed or module-qualified. That includes `type Outcome = Result<Int, ParseErr>`.

sawc accepts all of these. `/Users/shawn/Projects/sawlang/.build/scratch/p1000e/F29_alias_distinct.saw` builds and runs. `/Users/shawn/Projects/sawlang/.build/scratch/p1000e/F28_alias_refusals.saw` reports none of m1–m5 or m11. `/Users/shawn/Projects/sawlang/.build/scratch/p1000e/F30_alias_enum.saw` is accepted.

sawc does refuse wrong construction arity, a wrong construction type and `Byte(300)`.

Related: SL-48 (literal adoption) and SL-744 (alias construction). The fix brief owes a position matrix: every transfer position, casts, statics and constructions.

**Implementation detail (lead, Nov 12): a design pass (Opus) first; alias identity touches every transfer position. SL-876 is this issue's first two cells and closes with it.**

**The ruling (user, Nov 9, c2):** the spec is kept. `type A = B` is a DISTINCT type, and an alias of an enum or of a `Result` is refused.

**What sawc does today (c1's probes, `.build/scratch/p1000e/F28`, `F29`, `F30`):** an alias is transparent. `let order: OrderId = user`, `42 as UserId`, a sibling-alias cast and `let m: Byte = 45` are all accepted, and an alias of an enum (direct, through a chain, raw-backed, module-qualified, `type Outcome = Result<Int, ParseErr>`) is accepted. Construction arity, a wrong construction type and `Byte(300)` are refused already.

**Related issues the design reads first, so one mechanism serves them:** SL-48 (literal adoption for distinct aliases across slots, needs a ruling: check its comments for one), SL-744 (`A(x)` for a distinct alias over a struct resolves as the struct's construction), SL-823 (alias invariance: `Vector<TokenKind>` accepted at a `Vector<UInt8>`; conformance-signature checks), SL-1050 (an alias as a static-call receiver or construction callee), SL-928 (representation-identity casts on non-scalar aliases), and the Oct 10 ruling on SL-457 c3 (an alias constructor over a constant is a constant expression).

**The design must settle:**
1. **Representation.** How typecheck's type interner tells `UserId` from `Int` (a nominal wrapper kind keyed by the alias declaration, versus today's resolution to the target), and what every `types.ty(t).kind` consumer sees for an alias: field access through the alias, method lookup (does an alias of a struct have the struct's methods? the spec says), conformances (does `UserId` meet `Equatable` because `Int` does?), layout (identical to the underlying), mono and the backend (erased to the underlying, or carried).
2. **Every position, as a matrix against the spec's "Type Definitions" section** (quote each rule): annotated `let`/`var` from an underlying-typed value (legal "only for the four primitive kinds": which four, and what counts); from a literal; assignment; argument; return; field initializer; collection element; `as` in each direction and between siblings; construction `A(x)`; comparison and arithmetic between an alias and its underlying, and between two aliases; generic arguments (invariance, SL-823); a `match` on an alias; statics; constants (the alias constructor fold); a public API naming an alias.
3. **The refusals:** an alias of an enum or a `Result` (every spelling in c1), with its rule id and message naming what to write instead (a struct wrapper).
4. **The blast radius.** A census of every `type X = Y` in `std/`, `runtime/`, `compiler/`, `blade/`, `libs/` and `tests/corpus/` and of every use that today relies on transparency (the compiler has many `type` aliases over `Int` and `UInt8`; `TokenKind` is one). This is the unit's real cost: how many sites change, and whether the change lands in one patch or needs a migration (accept both for one release with a warning, as the `borrow` prefix did, then refuse).
5. **The seed.** The compiler's own source must build with the seed (the previous release's `sawc`) and with itself: if distinctness changes what the compiler's source must write, in which order do the std and compiler edits and the seed bump land (compiler/README.md "The seed").

**Deliverable** (one comment on this issue, evidence in `.build/scratch/p1012d/` of the main checkout, no tracked edit): the representation choice with reasons, the position matrix with the spec's verdict, today's verdict and OPEN cells, the census counts by directory, the migration and seed order, the questions that are the user's, and the cut into Sonnet-sized units with files, fixtures, expected corpus moves and gates.

**Note for scheduling:** if the census shows the blast radius is large (hundreds of sites in the compiler), this is more than one week's unit and the lead takes the migration question to the user before any implementation is dispatched.
