## Description

**sawc panics on a 32-bit target compiling the literal `-9223372036854775808`.** Found by SL-1129's design pass (Nov 15); reproduced by the lead on main (`.build/scratch/pneg/neg.saw` in the lead's checkout):

```saw
func main() {
    let x = -9223372036854775808
    print(x)
}
```

- `sawc build --target riscv32-unknown-none-elf --freestanding -c neg.saw`: `panic at arith.saw:508: integer overflow` (the compiler itself aborts; no diagnostic).
- On the host (64-bit `Int`) it builds.
- The same happens in a const generic argument with no expected type (SL-1129's matrix).

**The mechanism** (`tc_arith_negative_literal`, `compiler/typecheck/src/arith.saw`): the literal's magnitude `m` arrives as `Int.min` (2^63 does not fit the compiler's own `Int`, and the magnitude wrapped). On a 64-bit target `m == low` returns `Int.min`. On a 32-bit target `low` is -2^31, so the function takes the refusal branch, `m < 0`, and computes the fault's bits as `0 - m`: `0 - Int.min` overflows in the compiler's own checked arithmetic, and the compiler panics where it should refuse the literal for not fitting `Int`.

**The fix's shape:** the refusal must not negate a magnitude that is `Int.min` (record the bits without overflowing, or refuse on `m < 0` before any negation), and the literal is then refused with the ordinary "does not fit `Int`" diagnostic and its suffix suggestion, as `-2147483649` is on the same target. **Obligation 4:** every `0 - x` / unary minus in `compiler/typecheck/src/arith.saw` and the fold (`compiler/typecheck/src/` const evaluation, `compiler/eval/`) on a value that can be `Int.min`; a probe per site on riscv32, arm64 freestanding and the host, at the literal, in a const generic argument, in a static's initialiser and in a fold (`-(N)` with `N` at `Int.min`).

**Pins:** a refusal fixture for the literal on riscv32 (the lane's `COMPILE-FLAGS` for a target), and the sweep's other sites as rows.

Related: SL-1129 (its design keeps `ConstInt` at [-2^63, 2^64) and touches this file).

**Lead's note with p1 (Nov 15): the compiler no longer panics on a literal whose magnitude is 2^63 for a 32-bit target; it refuses it.** One Sonnet unit from the issue. Evidence: `.build/scratch/p1139/` in the lead's checkout. The lead read the change, ran the comment lint (ok), and checked the patch applies to main.

**The change** (`tc_arith_negative_literal`, `compiler/typecheck/src/arith.saw`, the refusal branch): the fault's bits for a magnitude that arrived as `Int.min` are `Int.min` itself (its two's-complement negation), instead of `0 - m`, which overflowed the compiler's own checked `Int`. One site: the fold's two callers and the evaluator's reach it through this function.

**The sweep** (`sweep_before.txt`, `sweep_after.txt`; riscv32, `aarch64-unknown-none-elf` and the host): every negation in `arith.saw`, the fold and the evaluator, at a literal, a const generic argument, a static's initialiser and in a fold (`-M`, `M * -1`, `M / -1`, `M % -1`, `-(M + 0)`, `-(U as Int)` with `U = 2^63`, and the 32-bit `Int.min`). **Only three cells panicked, all through this branch:** the literal, `Wide<-9223372036854775808>` and a static's initialiser, on riscv32. Approved patch SL-1139.p1 (revision 1)

**Approved. The panic is gone at every position I could put the literal, and it was wider than the note says: the base compiler panics on the host too.**

**What I ran.** 85 programs, each judged by the base compiler and this patch's on the host and for riscv32 (`mono --check`, and the host build run): the literal with no expected type, at each fixed width, at the unsigned types and with a suffix; magnitudes past 2^63; the literal as a static, a const argument, a const default, a generic default value, a repeat literal's count and its element, an argument, a return, a field, an element, a tuple element, an optional slot, an `if` arm, a compound assignment, a mixed operand, a comparison, a match pattern and a range pattern, an enum's raw value, under a cast, and in a format argument; every negation the fold makes of a value at its type's minimum; and the same at the 32-bit and 8-bit minimums.

- **63 of the 170 rows differ, and every one is `panic at arith.saw:508: integer overflow` turned into the ordinary `type.mismatch`**, "integer literal -9223372036854775808 does not fit in `T` (range …)", at the literal. No row still panics in the compiler, nothing that built stops building, and no message of another literal moved (`-2147483649`, `-129`, `-9223372036854775809`, `-18446744073709551615` read as before on both targets).
- **19 of the 63 are host rows.** The refusal branch is reached whenever the slot is narrower than 64 bits or unsigned, on any target, so at main the host compiler panics on `let x: Int8 = -9223372036854775808`, and the same at `Int16`, `Int32`, `UInt8`, `UInt` and `UInt64`, in a static, an `unsafe static var`, an `if` arm, an optional slot, a tuple element, a compound assignment, a mixed operand, an `Int8` enum's raw value, a generic default value at `Int32`, and a match pattern or range pattern on `Int32` or `UInt8`. The note's "only three cells panicked, all on riscv32" is the sweep's slots, not the mechanism's reach. This patch fixes all of them, since they are the one line; a host fixture would pin nothing the three do not, so I leave it to you whether the record wants one.
- **The three fixtures hold the line:** the base compiler panics on each, this patch refuses each at the position and with the message its header states (run directly, with the fixture's own flags).
- **The value the branch records is read by nothing.** A compiler that records 0 there in place of `m` judges all 170 rows and the three fixtures as the patch does: the message is the literal's own text (`settle_literal`, `check_pattern_range`), and the fold's fault for a literal returns early. The comment's sentence is true (the 64-bit pattern of -2^63 is `Int.min`), and there is nothing to pin it with.
- **The sweep's other sites** hold in my rows as in yours: `-M`, `0 - M`, `M * -1`, `M / -1`, `M % -1`, `-(M + 0)`, a length `-M` and a const parameter's `0 - K` are `constant.overflow` at 64 bits, and `-M` at 32 and 8 bits too.

One thing I met and leave alone, since this patch does not move it: for riscv32 a const argument or a const default of an `Int64` parameter written as a bare `-9223372036854775808` is refused as an `Int` literal (the `…i64` spelling is taken), and so is `-2147483649` there, on both compilers. I did not find the spec's sentence that says which it should be.
