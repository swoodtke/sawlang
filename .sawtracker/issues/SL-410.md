## Description

The reference recognizer names a refusal only for some rules. Everything else is recorded `parse-error`, so the parse corpus never tests those diagnostic ids.

**Findings, from SL-406.p4's review:**
- About 50 hand-written negative cases are recorded `parse-error` where a §13 or §2.7 rule squarely refuses the input. The productions or the lexer encode the rule, and the recognizer names nothing. Examples: statement-separator, juxtaposition, declaration-separator, assignment-target, test-form, interpolation-whole, effect-slot order, try-extent's `catch`, move-place, and the lexical unclosed-bracket, unterminated-string, float-point, escape, directive, int-range, shift-adjacent and ascii-identifier.
- Six rules are named in some cases and not in others: attribute-position, borrow-form, effect-slot, range-open-end, cast-target-question and contextual-words.
- `syntax.lex.ascii-identifier` never fires, because sawc2 refuses a non-ASCII letter as "Unexpected character" first. It is waived in `waivers.tsv`.

**Why it matters:** under the c35 contract (SL-406), a parser only has to reproduce a name the corpus records. U4's parser units will not be held to these rules' ids until the recognizer names them.

**Fix:**
- For each rule GRAMMAR.md states, make the recognizer name it wherever it is the reason for the refusal.
- Re-derive the affected expectations.
- Make `parsecoverage` require the refusing side of each rule's decision as a named negative case. Today it checks only one golden case per rule.

This is not needed before U4 starts. It should land before the parser units that own these rules.

**Scope:** this issue's description plus c1. c2's doc-run case already landed in SL-440.

**The goal.** Wherever a GRAMMAR.md §13 or §2.7 rule is the reason a text is refused, the reference recognizer names that rule, and the case records the name rather than `parse-error`. The parse lane then holds sawc2 to the name, per the c35 contract.

1. **Inventory first.** List every hand-written negative case, and every generated negative worth checking, that records `parse-error` while a §13 or §2.7 rule squarely refuses the text. The description's list is the seed:
   - statement-separator, juxtaposition, declaration-separator, assignment-target, test-form, interpolation-whole, effect-slot order, try-extent's `catch`, move-place;

   - a removed production, as SL-440 did for infinite-loop;

   Where naming a rule would make a text "between two rules" under README Refusals, leave it unrecorded and say so. Don't invent a precedence.
3. **Re-derive the affected expectations** with `cases.py --write` and `negative.py --write`. Report every expectation that changes, from `parse-error` to its name.
4. **sawc2 follows.** Where the recognizer now names a rule that sawc2 reports as a plain `parse-error`, make sawc2 name it at the same position, so the parse lane stays at 0 failures. That may touch `compiler/parse/`.
5. **`parsecoverage`** requires the refusing side of each rule's decision as a named negative case, not only one golden per rule. Report rules whose refusing side can't be recorded, and why.
6. **Waivers:** remove each waiver in `compiler/tests/parse/waivers.tsv` that this makes obsolete, including borrow-form's refusal waiver and the ascii-identifier waiver, if it can now fire.

One decision to make before item 6's ascii-identifier waiver. It needs a ruling.

§2.7 words the rule as "a **letter** outside ASCII cannot start or continue [an identifier]". Today sawc2's lexer, which the recognizer shares through its token dump, refuses all of these alike, as "Unexpected character" (parse-error):
- `let é = 1` (2:9);
- `let naïve = 1` (2:11);
- `let x = 1 → 2` (2:15).

To name ascii-identifier for `é` and `ï` but not for `→`, the lexer needs a Unicode letter test. In the subset, that means a table. The cheaper reading is to word the rule as "a character outside ASCII, outside a string literal or a comment". Every such character is refused either way, so only the name changes. That's a reversible reading under the brief's rules.

Worth deciding up front, so the agent doesn't sink time into a letter table the ruling might not want. Otherwise the waiver stays, with that as its reason.

SL-410.p1 is up: the recognizer names every rule that refuses a text (brief c3, with c4/c6 and D11). It is 2 commits over 54 files, +2376/−1017; about 1,500 of those lines are regenerated `.expect` files and `grammar.saw`.

**The mechanism: stops.** Filters only refuse trees the chart already holds, and a removed production names itself rather than the rule. So `STOPS`/`Stops` in `recognize.py` read 18 rules from the chart's state at the token where a restricted chart stops.
- **What the restricted chart applies as it runs:** the two rules that look ahead.
  - range-open-end: an open range completes only before a token that lets it end;
  - borrow-form: a place form never completes before a binding's `=`.
- **Why a stop is decided on the spot:** its name depends on nothing after its token, so `Checked.decided` skips the settle check. That gives c1's "whatever follows".
- **Two names at once:** a stop and a filter naming different rules make the text lie between two rules, so it is a Problem. Head-restriction still outranks everything.

**The inventory before:** 61 hand-written negatives named for a rule recorded `parse-error`, out of 126 `parse-error` hand-written cases in all.
- test-form 6;
- borrow-form, declaration-separator, effect-slot and statement-separator 5 each;
- assignment-target, attribute-position, interpolation-whole, juxtaposition and range-open-end 3 each;
- and others.

**Per rule.** Every expectation change is from `parse-error` to a name; no name changes and no name is lost.
- **Statements and declarations:**
  - statement-separator (5);
  - juxtaposition (3 layout cases, plus 20 cells and 68 mutations);
  - declaration-separator (5);
  - assignment-target (3 postfix cases, plus 82 cells);
  - try-extent (1).
- **move-place:** moved into an argument, `g(move x.f())`, because at statement level it sits between two rules. Two cases are added.
- **Declaration heads and attributes:** test-form (6), effect-slot (8), static-head (3) and attribute-position (5).
- **borrow-form:**
  - a line break after `borrow` or `borrow var`;
  - a binding with no value (`borrow var e =`);
  - bindings with no `{` outside condition heads. That is 41 cells.
- **Expressions and types:** arm-body, brace, range-open-end (`a.. == c`, whatever follows), prefix-type-suffix (`[T]`) and interpolation-whole.
- **Lexical:** shift-adjacent and float-point (`7.`).
- **unclosed-bracket:** `cases.py` records it at the opener for every text that leaves a bracket unclosed, generated mutations included (531).

  - the waiver is gone.
- **Recognizer fixtures:** 18 new `// stops:` fixtures, one per stop rule. Each proves that switching the rule off stops it being named.

**sawc2 follows** (`parser.saw`):
- **Generated tables:** `begins_statement`, `begins_expression`, `begins_range_bound`, the per-list item starts, and `holds_capture`.

- **Expressions and types:** range-open-end, shift-adjacent, arm-body, move-place, brace, interpolation-whole and prefix-type-suffix.
- **The closure head scan:** a `[...]` group is a capture list only when it holds capture tokens.

Approving SL-410.p1. I found one naming class the new stops get wrong, below, which should be a follow-up. I built sawc2 at the base, 947c00ed, and with the patch, and compared the two builds (`.build/scratch/air-review/sl410/`). Names come from the lane's own `cases.Expectations().refusal()`.

**What I checked**
- **Nothing accepted changes, and no verdict does.** I ran both binaries over two sets of inputs:
  - every tracked `.saw` file (6,582);
  - 821 probe cases from my SL-424/440/442/410 reviews.

  Every accepted text dumps identically (`--dump --alternatives`), and no text changes verdict. Among the refusals:
  - **Renamed from `parse-error`, first error only:** 31 now juxtaposition, 13 statement-separator, 7 each declaration-separator, attribute-position and ascii-identifier, and 23 across 13 other rules.
  - **Positions:** only 2 first positions move, both `attr_on_method_error.saw` (examples/ and tests/corpus): 8:5 becomes 8:6, still `parse-error`, and now at the reference's position.
- **The parser paths that changed beyond naming.** I ran 20 texts at the closure head scan (`{ [1, 2].len() }`, `{ [a, b] }`, capture lists with and without `in`) and at `return`/`break` operands (`.none`, `-1`, `(1)`, `}`, `;`, `not`, `try`, a closure, an array, a string). All are identical before and after, and all match the lane.
- **D11.** `é`, `naïve` and `→` are each named ascii-identifier by both parsers, at the same position, and the hint names the character.
- **My earlier name probes, under the new naming:** the D10 set, the doubly-broken class, match/loop twins, doc runs, gap texts, attribute texts, and the U4d–U4g sets. All have 0 mismatches except the class below.
- **The gate** passed on the applied commit: tested_commit == applied_commit == 82e299bf. The tested tree, e2a6a1e9, is the tree I get when I apply the diff to 947c00ed.

**Non-blocking, but worth a follow-up**
1. **Statement stops fire at the start of a match's arm list, where no statement stands.** In `match x {`, then `1 => 2`, then `}`, the lane now records `syntax.rule.assignment-target` at the `=` (3:11). sawc2 says "expected `case` to begin an arm" at 3:9, and that is the grammar's reason: an arm starts with `case`.
   - **The same happens for four more stops at that spot,** with a name or a literal as the head alike:
     - `a b`: juxtaposition, 3:11;
     - `a.. == c`: range-open-end, 3:13;
     - `borrow var e =`: borrow-form, 3:23;
     - `1 = 2`: assignment-target.
   - **Heads don't matter:** it also fires after `match 1 {`, `match (x) {`, a call head, a member head and a value `match`.
   - **The mechanism:**
     - `Stops._ended` checks only that the statement ending at the stop has a tree of its own.
     - Here that statement sits in a `block-body` that the chart can read only as a trailing closure on the head. The trailing-closure and head-restriction filters refuse that reading, but nothing in the stops checks it.
     - Struct, enum, trait, extension, import and parameter lists don't misfire, since no closure reading reaches them: 12 texts checked.
   - **Why it matters:** `1 => 2` is the natural Rust-style mistake. A negative case for it would record assignment-target and hold sawc2 to it.
   - **Fix direction:** have `_ended` (and `_assignment_target`'s held list) require that the holder's own reading survives the filters.
   - **Probes:** `cases_arms/`, `cases_arms2/` and `cases_stops*/`.
2. **Cosmetic.** Every ascii-identifier hint ends "an interpolation's expression is source", even for a character that isn't in a segment. That clause could appear only when the character is in one.
