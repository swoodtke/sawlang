## Description

**`sawc` can't build a freestanding object yet: sawos's command line (`-c --freestanding --no-hidden-alloc --target … --target-features …`) is Stage-0-only** (the Air, SL-667 c12, Oct 23).

sawos's `tools/sos_runner.py` compiles the kernel with Stage 0's flags: `--freestanding --no-hidden-alloc --target <triple> --module-path kcore=… hal=…` to an object (`-c`). The self-hosted `sawc build` has no `-c`, no `--no-hidden-alloc` and no `--target-features`, and `sawc build --freestanding` checks the profile but doesn't build. So the self-hosted compiler can't build the kernel, whatever the resolver does. "Kernels and embedded are first-class targets" (design doctrine), and sawos resumes only once `sawc` is ready (the user, Oct 9).

The corpus records the same gap: `refused driver.usage: sawc build takes no --no-hidden-alloc` (the fixedbuf rows and others).

**Scope** (an epic-sized ask; step 1 is a plan):
- object output (`-c`);
- `--freestanding` building, not just checking (the runtime-provider path, no hosted runtime linked);
- `--no-hidden-alloc` (design 135's three refusals);
- `--target` with `--target-features`;
- the `--runtime-build` and `--runtime-provider` modes Stage 0 has;
- port the freestanding suite (`tests/freestanding/`, frozen by SL-667) onto `sawc` as its gate.

Until this lands, sawos builds through a pin at or before v0.18.0 (SL-667's landing note says so).

Approved patch SL-865.p3 (revision 1)

**Air: SL-865.p3 (U3) approved**, with one finding for U4/U9 to own. Reviewed r1 on 2a5880e32. Probes are in `.build/scratch/air-review/sl865p3/`; each built with `--freestanding -O2 --target aarch64-unknown-none-elf` and read with Homebrew LLVM 23's tools.

**The profile holds:**
- **Hosted imports:** `import std.file/process/net/time/signal/env/directory` gives seven `import.hosted-only` refusals, one at each import (`f_imports`).
- **No FP/SIMD:** under the `-neon,-fp-armv8` default, no instruction has an FP/SIMD register operand (`llvm-objdump -d --no-show-raw-insn`) in any of the three objects. `Float` arithmetic lowers to soft-float libcalls, with `__adddf3` and `__muldf3` undefined (`f_float`).
- **No PIC:** relocations are `R_AARCH64_ABS64`, `CALL26`, `ADR_PREL_PG_HI21`, `ADD_ABS_LO12_NC` and `PREL32`/`ABS32`, with **no GOT** relocation. Functions get per-function sections (`.text.scale`, `.text.count`).
- **Q7:** a `main()` beside the exports isn't emitted as a symbol; only `T scale`, `T count`.
- **`print` and interpolation:** these compile and leave the provider's seams undefined (`__saw_rt_alloc`/`_dealloc`/`_panic`/`_write_line`/`_last_raw_code`), plus `memcpy`, which a kernel supplies as it would for C (`f_print`).
- **`Thread.spawn`:** refused (`member.unknown`).

**The finding, for U4/U9: a freestanding `TaskGroup` object needs libc's pthreads.** A `TaskGroup` is allowed under the profile (the spec, and the frozen suite's `export_with_coroutine.saw`, mirroring the sawos kernel's spawning entry). `f_group.saw`'s object leaves undefined:
- the expected seams (`__saw_rt_thread_*`, `_reactor_*`, `_offload_done`, `_sleep_ns`, `_output_lock`, …);
- AND `pthread_mutex_lock`/`_trylock`/`_unlock`/`_destroy` and `pthread_cond_wait`/`_broadcast`/`_destroy`.

Those come from `std/taskgroup.saw` and `std/channel.saw`, which call pthread directly through `extern "C"`, not through a `__saw_rt_*` seam. A kernel can't supply pthreads, so the restart's first spawning entry won't link. Options: route those locks through seams the provider exports (the SpinLock family), or keep a cooperative group's code from reaching the threaded paths. Either way it wants a row in U9's suite.
