## Description

Found while migrating `prototypes/minivm` onto design 268's lexer API (SL-238.p1 review round). NOT caused by that patch — the defect is in copy lowering, which design 268 does not touch; the prototype simply became the first caller to copy a `Vector` of an automatic-Copy-tier struct, and it corrupted memory immediately.

## The defect

`Vector<T>.copy()` (and by inspection `try_copy`) accepts an element type on the AUTOMATIC Copy tier — a struct whose members are all trivial/Copy, declaring nothing (design 159/219) — and duplicates each element BITWISE, never retaining its refcounted fields. The copy's `String` fields alias the original's storage, so once the original vector drops, every element's text is freed memory: reads return empty/garbage and the second release aborts with `panic: over-release of a String reference (refcount underflow)`.

`sawc/std/vector.saw:493-509` is CORRECT — it spells `result.push(buf[i].copy())`. The miscompile is in what that per-element `.copy()` lowers to when `T` is monomorphized to such a struct.

## The inconsistency that pins it

The SAME type is REFUSED `.copy()` at a direct call site:

```
error: type `Rec` is not Copy; `.copy()` requires a trivially-copyable, Copy, or ExplicitCopy type
```

So two judgments about the automatic Copy tier disagree: the generic BOUND `Vector<T: ExplicitCopy>` admits `Rec`, while member resolution says `Rec` has no `copy()` at all. In the generic body the call then degrades to a bitwise duplicate instead of erroring or retaining.

## Repro (single module, no lexer, 30 lines)

```saw
struct Rec {
    text: String
    tag: String?
}

func heap_string(seed: String) -> String {
    var sb = StringBuilder()
    try! sb.append(seed)
    try! sb.append("-built")
    sb.build()
}

func copy_then_drop() -> Vector<Rec> {
    var original = Vector<Rec>()
    try! original.push(Rec(text: heap_string("alpha"), tag: None))
    try! original.push(Rec(text: heap_string("beta"), tag: heap_string("tag")))
    let duplicate = original.copy()
    move duplicate          // `original` drops at the end of this function
}

func main() {
    let v = copy_then_drop()
    print(v.len())
    print("[{v[0].text}]")
    print("[{v[1].text}]")
    if let t = v[1].tag { print("[{t}]") }
    print("done")
}
```

Expected: `2`, `[alpha-built]`, `[beta-built]`, `[tag-built]`, `done`.
Actual: `2`, `[]`, `[]`, `[]`, then `panic: over-release of a String reference (refcount underflow)`, SIGABRT (exit 134).

GOTCHA for anyone re-probing: the fields must hold HEAP strings. A string LITERAL is immortal (rc == -1), so a literal-filled struct hides the missing retain completely — three earlier probes of mine passed for exactly that reason.

## Boundary probes (all same-module, heap strings)

| probe | shape | result |
|---|---|---|
| P1 | `Vector<Rec>.copy()`, `Rec` = automatic-Copy-tier struct | BROKEN — no retain, over-release abort |
| P2 | `Vector<String>.copy()` (element IS the refcounted primitive) | correct |
| P3 | implicit struct copy, `let duplicate = original` | correct — retains |
| P4 | explicit `original.copy()` on that struct | REFUSED at compile time (message above) |
| P5 | same as P1 but the struct is defined in ANOTHER module | BROKEN identically (first seen through the selfhost lexer's `Token`) |

So the retain works everywhere the compiler handles the value directly, and is lost exactly on the generic `ExplicitCopy`-bounded element path.

## Suspected class (not verified — worth a sweep before a fix is dispatched)

Every `T: ExplicitCopy`-bounded std API that spells a per-element `.copy()` is a candidate, not just Vector: `Vector.try_copy` (`vector.saw:518-532`), and design 251's conditional `Map`/`Set` conformances, whose copies duplicate keys and values the same way. A `Map<String, Rec>` or a `Set<Rec>` copy would corrupt on the same mechanism if it shares the lowering. The automatic tier is the common ingredient: a DECLARED `@synthesize extension Rec: ExplicitCopy {}` presumably synthesizes a real `copy()` and is unaffected (unprobed).

## Impact

Silent memory corruption on a safe-code path with no `unsafe` anywhere, at exit 0 until the allocator or the over-release detector happens to notice. The automatic Copy tier is the tier a struct lands on by writing NOTHING, so this is reachable without the author ever naming a copy policy.

## Workaround in use

`prototypes/minivm/src/frontend.saw` clones the token stream element by element through its own `clone_token` (field reads + memberwise construction), which retains correctly. The comment there cites this issue.
