## Description

**`Channel.recv()` returns `Result<T, ChannelError>`** (the user, Oct 17, on the Air's SL-765 c51 question).

T3b (SL-765.p4) landed `recv() -> T`, which panics on a closed, drained channel. A thread then can't write the usual drain-until-closed consumer loop. The ruling makes `recv` uniform with the cooperative `receive() -> Result<T, ChannelError>`:
- a closed, drained channel → `Err(ChannelError.Closed)`;
- recv's other panics (the gate's allocation, and mutex or condition-variable init) become `Err` through `ChannelError`'s existing allocation and system cases, never a panic (never hide errors).

**Scope:**
- `std/channel.saw` `recv`, and its docstring.
- The spec: the Channels section's `recv() -> T` lines and the `Thread.spawn` example that calls it.
- README and the saw-lang skill where they show `recv`.
- **Consumer sweep (obligation 2):** every `recv()` call in `compiler/tests/`, `tests/corpus/` and `examples/` (twins together, with `corpusdiff.py snapshot --reuse`). Stage 0's `recv` is infallible, so a rewritten row that passes is `stage0-wrong`, annotated with this ruling.

**Pins:** a thread drains a channel until its producer closes it (`while` over `recv()` ending at `Closed`), and the closed-and-drained case reports `Closed`.

**Lead's call (reversible), on a gap in the description:** the description routes recv's mutex and condition-variable init failures through "ChannelError's existing allocation and system cases", but `ChannelError` has no system case (`Closed`, `Cancelled`, `Alloc(e: AllocError)`). Doctrine: never hide errors, and never fold an OS refusal into `Alloc`. So the unit adds **`case System(e: SystemError)`**, built with `SystemError.of("pthread_mutex_init" / "pthread_cond_init", …)` from the seam's status, as `std/task.saw` does, with a `describe()` line and a `format` arm matching `Alloc`'s. An exhaustive `match` on `ChannelError` with no `_` arm breaks, so the consumer sweep covers those too.

Also in the unit: `open_gate` holds the queue lock, so every early return unlocks first and frees the raw block, leaving `gate` at 0 so a later `recv` can retry.

Those are `thread_recv_drains_until_closed`, `thread_recv_woken_by_close`, `thread_recv_gate_allocation_refused`, `thread_channel_pipeline` and `thread_spawn_spec_examples`.

**The `System` case, which has no pin, forced here:** I wrote a DYLD interposer that fails a chosen `pthread_mutex_init` or `pthread_cond_init` call (`air-review/sl777p/failinit.c`, `recv_system.saw`, `run_injected.py`). The probe: a first `recv` on an empty channel, then `send(7)`/`recv`, then a close from a thread. Results at -O0 and -O2:
- **The cond init refused:** "refused: the operating system refused the channel's lock: pthread_cond_init failed (…)". The half-made gate's mutex is destroyed exactly once. The queue lock is released, since the `try_receive`/`send`/`recv` after it run. The retry builds a new gate (the second mutex and cond init), and the close wakes it with `channel is closed`.
- **The mutex init refused:** the same outcome, with no destroy on the failure path and the gate's mutex destroyed once at the channel's teardown.
- **The kind follows the errno:** 12 renders "resources exhausted", 22 "invalid argument", 1 "permission denied", 999 "other error".

**A follow-up, not blocking this patch: `EAGAIN` from these two inits renders as "would block".** POSIX's `EAGAIN` from `pthread_mutex_init`/`pthread_cond_init` means "the system lacked the necessary resources (other than memory)". `pthread_status` (`runtime/common/pthread.saw`) classifies it through the shared classifier, so the user sees `pthread_cond_init failed (would block)`. That's the same misreport the lead's SL-768 c7 rule fixed for the spawn family ("a seam classifies its errno in ITS OWN context"). Before this patch it was hidden inside a panic that printed the raw errno. `recv`'s `Err(System(e))` is the first place it reaches a caller. The fix is body-only, in both runtime trees: the init seams map `EAGAIN` to `Exhausted`, with the raw code still stamped. My interposer, run with `SAW_FAIL_ERRNO=35`, is a ready repro. `recv` is the only std caller that reports these seams' kind: `TaskGroup(threads:)` panics with the raw errno.

**Read and agreed:** `recv`'s `try` through `wait_ready`/`open_gate`; the waiter counts itself only after `open_gate` succeeds, so a writer never broadcasts on a gate that doesn't exist; every early return unlocks; `0 - status` matches the seams' `0`/`-tag` (ABI.md) and `std/task.saw`'s use of `SystemError.of`. The rewritten `recv()` call sites, the spec (the Channels bullet, NAMING, the `Thread.spawn` example, the enum listing), README and the skill all match. No `recv` site was missed (a `git grep` over std, compiler/tests, tests/corpus, examples, blade, libs and runtime), and no tracked text keeps the old panic.

**Nit:** in `thread_recv_gate_allocation_refused`, if the closer's 50 ms nap ever ran out before `main` reached the final `recv`, that `recv` would see the channel closed and return `Closed` without making a gate. The line would still print, so the "retry made its gate" claim would go unchecked rather than fail. It's harmless as a flake, but the claim isn't strictly pinned.
