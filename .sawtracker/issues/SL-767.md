## Description

**The Linux run lane's x86_64 arch fails `float_hook_hash.saw` at -O0:** `line 5: sawc2 'nan 8058138970211093139', Stage 0 'nan 1165233065239906963'`. x86_64 is held to the aarch64 Stage 0 record. The program (from SL-722) hashes a NaN, and its hash depends on the NaN's bit pattern.

UNVERIFIED: x86_64's default NaN (`0xFFF8…`, sign bit set, from SSE arithmetic) differs from aarch64's (`0x7FF8…`). Confirm by printing the NaN's bits on both arches. Then decide:
- if the spec says a NaN's hash is canonical (one hash for every NaN), sawc2 is wrong on x86_64;
- if it isn't, the pin must not print a NaN's hash.

This belongs with SL-722 (the Float work, PAUSED). Found by SL-569's agent, c8.

**Air: confirmed. sawc2 is right on both arches, and the test line is platform-dependent.**

- **The spec** (hash/== contract): "NaN bit patterns are not normalized (`NaN != NaN`, so nothing is required)". So a NaN's digest is a function of its bits.
- **The bits:** `0.0 / 0.0` makes the default NaN, which is 0x7FF8000000000000 (sign clear) on aarch64 and 0xFFF8000000000000 (sign set, x86's "indefinite") on x86_64.
- **Probe on the Air** (aarch64 darwin, main's sawc2, `air-review/sl767/nan_sign.saw`): `digest(nan)` prints 1165233065239906963, the recorded line. `digest(-nan)`, the same NaN with its sign flipped by `fneg`, prints **8058138970211093139**, exactly what the x86_64 lane printed. Nothing differs but the sign bit.

**Fix direction:** the program, not the compiler. `float_hook_hash.saw`'s `nan {}` line should print something every arch shares: for example `flag(digest(nan) == digest(nan))`. `set nans 2 0` already pins the two-NaNs-are-two-elements behaviour without printing a digest. Then re-record both records. Stage 0 run on x86_64 would print the x86 number too, so no hazards entry is owed.

**Sibling sweep** (`compiler/tests/run/`): six programs make a NaN by division. The other five print only comparisons of it (`nan != nan`, `compare(...)`), and `float_operators` prints bits for non-NaN values only, by its own stated rule ("never a NaN's"). So this is the one line whose output depends on the NaN's sign, which matches the lane passing them all on x86_64.
