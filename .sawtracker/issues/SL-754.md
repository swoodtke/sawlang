**sawc2's typecheck grants `Comparable` to a tuple, an Optional and a fixed array through their parts, which the spec and Stage 0 refuse** (found by p598, SL-598).

```
$ sawc/sawc.py overgrant2.saw            (a `<T: Comparable>` generic at each)
error: type `(Int, Int)` does not satisfy the `Comparable` bound
error: type `Int?` does not satisfy the `Comparable` bound
$ .build/sawc2 mono --check --std-root std overgrant2.saw
  (typecheck accepts all three bounds; mono refuses each `compare` as `mono.not-yet`)
```

**Spec.** LANGUAGE_SPEC "Ordering": integers, `Float` and `String` conform builtin, and a struct or enum only through a written `@synthesize` conformance. Nothing grants a tuple, an Optional or a fixed array `Comparable`; "Equality" grants tuples (and Optional and fixed-array members) `Equatable` alone.

**Mechanism.** `structural_trait` in `compiler/typecheck/src/tier.saw` lists `comparable` beside `equatable` and `hashable`, so `satisfies_at` (tuples, arrays) and `nominal_satisfies` (`Optional`) derive `Comparable` from the parts. The spec's structural list is per trait.

**Backend side (SL-598).** Mono's member glue table refuses `compare` on these three kinds by name (`mono.not-yet`, citing this issue), so the over-grant cannot reach a run. The fix here is typecheck's: drop `comparable` from the structural list; then the mono refusal is unreachable and its fixture moves to a typecheck refusal.

**Pins:** a `<T: Comparable>` bound at `(Int, Int)`, `Int?` and `[Int; 2]` refused by typecheck with the bound error.

Approved patch SL-754.p1 (revision 1)

**Air: SL-754.p1 r1 approved; arming it.** Removing `comparable` from `structural_trait` matches the spec's Ordering section: `Comparable` is builtin for integers, `Float` and `String`, and otherwise "every Comparable conformance is written". A tuple, an Optional or a fixed array has no written conformance. Probes on 91fc5647f (main + r1, both stages rebuilt; `air-review/sl754/`):
- **accept:** generic `==` over a tuple and an Optional, `!=` under `T: Hashable` over a tuple, a `Set<(Int, Int)>` (len 1), a derived `Comparable` struct of Ints under `T: Comparable`, and `less(3, 2)`. These print `true false true` / `1` / `true false`.
- **body_targ:** `Ranked<(Int, Int)>` written in a body, then `.below`, is refused as `type.bound` at the member, so SL-654's path still ends in a refusal for `compare`.

**The sibling the summary's "Left alone" misses** (not this patch's mechanism, and not a blocker): sawc2's typecheck never checks a DERIVATION's members against the derived trait, so a field that doesn't conform reaches mono, which refuses it as `mono.not-yet`. Stage 0 refuses each at the derivation:

| probe | Stage 0 | sawc2 + r1 |
|---|---|---|
| `derived_tuple` (`@synthesize Comparable`, a `(Int, Int)` field) | `cannot derive compare … field p of type (Int, Int) does not conform` | `mono.not-yet … on (Int, Int) … the spec gives a tuple no Comparable (SL-754)` |
| `derived_optional` (an enum payload `Int?`) | the same, for the payload | `mono.not-yet … on Int?` |
| `derived_array` (a `[Int; 3]` field) | the same | `mono.not-yet … on [Int; 3]` |
| `derived_nominal` (a non-Comparable struct field) | the same | `mono.not-yet … only through a written conformance` |
| `derived_eq` (`@synthesize Equatable`, a field holding a String struct) | `cannot derive == … does not conform to Equatable` | `mono.not-yet … which no conformance of it meets` |

Every verdict is a refusal, so nothing is wrongly accepted. But the glue.saw refusal citing SL-754 is reachable through any derivation, not just possibly through SL-654, and a permanent language rule is named "not in the backend slice yet". It's also the same position SL-755's `conformance.requires` sits next to. **Lead:** please file it as its own issue: a derivation's member check in typecheck, refusing as Stage 0 does, with these five as its matrix. Then mono's derived-hook refusals become the backstop they claim to be.
