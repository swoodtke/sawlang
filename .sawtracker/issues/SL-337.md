## Description

## Summary

With the `insertvalue` abort cleared (see the sibling SL issue filed from sawtracker ST-37), `sawc` at `-O1` and above aborts in LLVM's machine scheduler on sawtracker's `src/main.saw`. `-O0` compiles clean and sawtracker's whole suite passes, so sawtracker's `build.sh` now pins `-O0` (SAW_NOTES ST-SAW-17). That pin is a workaround for this abort, not a choice about optimization level, and should be removed when this is fixed.

```
Assertion failed: (Delta.CriticalMax.getUnitInc() >= 0 && Delta.CurrentMax.getUnitInc() >= 0 && "cannot decrease max pressure"), function getMaxDownwardPressureDelta, file RegisterPressure.cpp, line 1350
Abort trap: 6
```

## Reproducer

sawtracker main after ST-37.p1 merged (`a19e2fb`):

```
cd sawtracker && SAWOPT=-O2 ./build.sh      # or: sawc -O1 src/main.saw
```

## What is known

Not minimized; the abort prints no function name. Bisection by stubbing:

- stubbing `mutate_patch`'s body (`return common.fail("stub")`) compiles at the default level;
- stubbing only `rebase_patch_branch` (a 21 KB frame reduction) still aborts;
- the ST-SAW-16 call-site reductions (a 55% frame reduction across the whole dispatch chain, `__Frame_mutate_patch` 203,728 → 76,032 bytes) did not clear it.

That pattern points at the SIZE OF ONE RESUME FUNCTION rather than at frame layout: `__Frame_mutate_patch$m$src_store_resume` is ~76,000 lines of IR, and the sibling `__Frame_dispatch` / `__Frame_response` / `__Frame_run_store` resumes and `__vtdtor$__Frame_run_store` are the same order. Splitting the module to name the function was not attempted. The LLVM assertion itself is a known class of scheduler bug on very large basic blocks / very high register pressure; splitting resume functions or breaking up very long basic blocks in the emitted resume would likely avoid it.

## Impact

sawtracker ships unoptimized until this is fixed. Anything else with a resume function of this size will hit the same abort at the default optimization level.
