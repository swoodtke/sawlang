## Description

Found while building SL-306's matrix (pre-existing, and NOT SL-306's mechanism — reproduced identically on main `607ab218` and on the pre-SL-280 compiler `f982f54c`, so it predates both).

A `[&var x]` BORROW CAPTURE into a closure passed directly to a non-escaping parameter writes through to the caller's local in a plain `sync` function and writes NOTHING when the enclosing body is a coroutine frame (a spawned task; a driven root behaves the same way). Silent: the program compiles, runs, exits 0 and prints the wrong number.

## Repro

```saw
import std.task.*
import std.channel.{Channel}

func sync_sum() -> Int {
    let v: Vector<Int> = [1, 2, 3]
    var total = 0
    v.each({ [&var total] n in total = total + n })
    total
}

func task_sum(out: Channel<Int>) {
    let v: Vector<Int> = [1, 2, 3]
    var total = 0
    v.each({ [&var total] n in total = total + n })
    yield_now()
    let _ = out.send(total)
}

func main() {
    print("sync {sync_sum()}")
    let out = try! Channel<Int>()
    var group = TaskGroup()
    let h = group.spawn(task_sum(out.copy()))
    print("task {try! out.receive()}")
    h.join()
}
```

Observed, on all three compilers:

```
sync 6
task 0
```

Expected `task 6`. The two bodies are the same six tokens; the only difference is that `task_sum`'s `total` is frame-resident.

## Suspected mechanism (not probed further)

Design 88 holds a frame-resident local in a frame FIELD, and the closure's environment is built from a pointer to the local's storage. In a frame, that storage is the frame field, and the environment is plausibly given the address of a stack copy of the field (or of the pre-suspension materialization) rather than of the field itself — the closure then increments a copy that nothing reads back. That is a guess from the symptom; the shape to instrument is `_FrameBuilder`'s closure-capture materialization (`_cap_lets`, design 77 item 4) against a borrow capture rather than a by-value one.

Adjacent, and the reason this is worth a row rather than a note: SL-267 is already open on a driven body's NON-ESCAPING closure capture DUPLICATING (`V96_driven_capture_duplicates_once`), which is the by-value face of the same materialization. This is its borrow face, and it loses writes instead of duplicating values.

## Why it matters

`[&var acc]` is the spelling the compiler's own diagnostic recommends when a closure writes to a capture ("capture it by borrow — `{ [&var n] ... }`, legal in a closure passed directly to a non-escaping parameter"), so the accumulate-with-a-visitor idiom is unwritable inside a task and says nothing about it. Every std visitor lends its element (design 264), so the ONLY way a `Vector.each` body can accumulate is a borrow capture or an `Arc<Mutex<T>>`.

Workaround: index with a `while` loop instead of a visitor, or accumulate through an `Arc<Mutex<T>>`.
