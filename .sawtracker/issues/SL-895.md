Found by the Air from sawtracker's port notes (ST-97; chat m598). `std/env.saw` `cwd` panics with 'Env.cwd: the path is not valid UTF-8 (byte …)' instead of returning `Err`, so a caller's `try?` can't catch it, against never-hide-errors. **Obligation 4 sweep:** every std function that builds a `Path` or `String` from OS bytes (Directory listing, `Env.get`, the program's arguments, `Command` output, `readlink`-shaped calls, `getaddrinfo` names), probed with a non-UTF-8 input; each must return its `Err`. The error's shape (a `SystemErrorKind` for an unrepresentable path, or something else) is a user ruling; propose one.

<!-- sawtracker:comment {"author":"agent:claude-sawlang","body_bytes":649,"created":"1792870333","id":"c2"} -->
**RULED (the user, Oct 25):**
- **The error:** a new `SystemErrorKind.InvalidUtf8` (no offset; raised by std, no seam).
- **The environment readers:** `Env.get`/`Env.argument` → `Result<String?, SystemError>`, and `Env.args` → `Result<Vector<String>, SystemError>`.
- **The five SystemError sites** (`Env.cwd`, `Env.executable_path`, `Path.canonical`, `Directory.list`, `Command.output`) return `Err(InvalidUtf8)`.
- **New `Command.output_bytes()`,** for a binary child.

**Step 1 (p895)** found 7 panicking sites (four of them already `Result`-typed), and `Command.output` dropping the code and bytes. A non-UTF-8 `Path` is filed as **SL-902**.

**Air: SL-895.p1 approved.** Reviewed r1 on 71d5b6636. This is the user's ruling on my ST-97 finding.

**Real non-UTF-8 OS bytes, from outside the process.** `b1_os_bytes.saw` is run by a launcher that execs it with bytes `caf\xe9-\xff` in argv[1] or in an environment value. It builds under ASan.

| input | result |
|---|---|
| clean | `argument(1)` Ok(None), `argument(0)` Ok, `args` Ok(1), `get(SAW_PROBE)` Ok(None), `get(HOME)` Ok, cwd Ok; rc 0 |
| bad argv[1] | `argument(1)` and `args`: `Err(args failed (not valid UTF-8))`; `argument(0)` still Ok; the env readers are untouched; rc 0 |
| bad env value | `get(SAW_PROBE)`: `Err(getenv failed (not valid UTF-8))`; `get(HOME)` Ok; `contains(SAW_PROBE)` true; rc 0 |
| child prints `caf\351-\377` | `output()`: `Err(output failed (not valid UTF-8))`; `output_bytes()`: Ok(6 bytes, exit 0) |

On this host's APFS a non-UTF-8 directory name can't be made: mkdir fails with EPERM. So the cwd, canonical, list and executable_path cells rest on `system_paths_not_utf8.saw` in the lead's aarch64 Linux run, where it creates `x\xff`, enters it and runs a hard-linked child. I read the pin: on macOS each `InvalidUtf8 true` line holds through its `not nameable` branch, and on Linux through the site's own Err.

**The funnel is complete.** On the patched tree, every `string_from_bytes` caller in std/ and runtime/ was checked:
- `system_text` itself;
- `Data.decoded`, which validates, and is how `Command.output` reports `InvalidUtf8`;
- String and StringBuilder building from their own UTF-8 buffers.

The six OS sources (readdir, executable_path, args, getenv, getcwd, realpath) each call `system_text`. Every public function in std.env, std.process and std.directory that returns OS text is covered.
