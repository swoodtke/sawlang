## Description

**The largest type sawc accepts is the target's `Int.max` bytes, and a value of that size makes clang allocate without bound.** Found by SL-1116's sweep (Nov 18; it crashed the machine twice): `func make() -> [UInt8; 9223372036854775807] { panic("never") }` is accepted and emitted as `alloca [9223372036854775807 x i8]` plus a `memcpy` of that length; clang at `-O0` passed 100 GB. LLVM's own layout arithmetic (`DataLayout::getTypeSizeInBits`, `NumElements * 8 * allocSize` in `uint64_t`) wraps at 2^61 bytes on every target, 32-bit included (read from the headers, not run).

**Question for the owner:** what is the largest object size Saw accepts per target? Options: (a) the target's `Int.max` (today; clang's behaviour past some size is its own); (b) the target's address-space bound, as Rust does (`2^47` bytes on 64-bit targets, `2^31 - 1` on 32-bit); (c) LLVM's layout bound (`2^61 - 1` bytes) on 64-bit. Lead's default: (b), so a type no machine can hold is refused at sawc, never handed to clang.

**Before the ruling, a safe measurement:** clang's peak memory and time against the object size, at small sizes only (2^16 to 2^28 bytes, one at a time, under a time limit and with `/usr/bin/time -l`), for a stack value, a global and a `memcpy` of it, to see whether clang's cost grows with the size (which would make any large bound a crash risk) or is constant (which would point at one pathological path). Never run clang above the measured safe size.

Related: SL-1116.
