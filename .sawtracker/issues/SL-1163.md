## Description

**The largest type sawc accepts is the target's `Int.max` bytes, and a value of that size makes clang allocate without bound.** Found by SL-1116's sweep (Nov 18; it crashed the machine twice): `func make() -> [UInt8; 9223372036854775807] { panic("never") }` is accepted and emitted as `alloca [9223372036854775807 x i8]` plus a `memcpy` of that length; clang at `-O0` passed 100 GB. LLVM's own layout arithmetic (`DataLayout::getTypeSizeInBits`, `NumElements * 8 * allocSize` in `uint64_t`) wraps at 2^61 bytes on every target, 32-bit included (read from the headers, not run).

**Question for the owner:** what is the largest object size Saw accepts per target? Options: (a) the target's `Int.max` (today; clang's behaviour past some size is its own); (b) the target's address-space bound, as Rust does (`2^47` bytes on 64-bit targets, `2^31 - 1` on 32-bit); (c) LLVM's layout bound (`2^61 - 1` bytes) on 64-bit. Lead's default: (b), so a type no machine can hold is refused at sawc, never handed to clang.

**Before the ruling, a safe measurement:** clang's peak memory and time against the object size, at small sizes only (2^16 to 2^28 bytes, one at a time, under a time limit and with `/usr/bin/time -l`), for a stack value, a global and a `memcpy` of it, to see whether clang's cost grows with the size (which would make any large bound a crash risk) or is constant (which would point at one pathological path). Never run clang above the measured safe size.

Related: SL-1116.

**Owner's ruling (Nov 25): one cap for every target. A type larger than 2^31−1 bytes (2 GiB) is refused.**
- **What it covers:** every type whose size the compiler fixes (an array `[T; N]`, a struct, an enum, a tuple, a static, a frame's value), wherever the type is written or reached, the same cap on 64-bit and 32-bit targets.
- **What it does not cover:** run-time heap allocations (`Vector`, `Data`, a `Box` payload's growth) are not types of that size and are not capped.
- **The layout funnel's arithmetic** (size times count, record and enum sums, `align_up`) is checked, so no overflow panics and no wrong size at riscv32. A size past the cap is an error naming the type and its size, never handed to clang.
- **Before fixing the boundary,** measure clang at the cap safely: one run at a time, stepping up from small sizes, under a time limit and a memory ceiling, stopping at the first superlinear growth.

**Lead's note with p1 (Nov 25), per the owner's ruling.** Evidence is in `.build/scratch/p1163/`.

- **The measurement** (`measure.tsv`): one clang at a time, `-O0 -c`, three shapes (a returned array, a static, a copied struct). Each shape was run at 2^16, 2^20, 2^24, 2^26, 2^28, 2^29, 2^30 and 2^31−1 bytes. All 24 runs exited 0, with a flat peak of 63–103 MB and 0.13–0.39 s. At the cap, clang only warns `-Wframe-larger-than`.
- **The funnel:** `layout()` computes each type once.
  - `wide_sum`, `wide_product` and `wide_aligned` check against the compiler's 64-bit `Int`; `compute`, `record`, `tagged`, `flagged` and `laid_cases` use them.
  - A size past `target_size_cap()` (2147483647) becomes an Unsupported layout with `overflow=true`, keeping its exact size so an enclosing type sums correctly. Past 2^63, the message says "more than 2^63 bytes".
  - `size_sum`, `size_product` and `size_aligned` check against the cap, for the coroutine frame arithmetic.
- **The rule:** `type.too-large` replaces `constant.overflow` for size refusals (const-generic arithmetic stays `constant.overflow`). Its consumers are updated: mono's `refuse_oversize`, llvm's `lay_at`, the asserts layout checks, the coro frame refusal and mono's api.
- **The position matrix:** 22 fixtures `compiler/tests/mono/refuse/type.too-large.cap-*`, 11 positions at the host (2^32 bytes) and at riscv32 (2^33).
  - On main, every host case was ACCEPTED, and every riscv32 case was refused with the wrong rule (`constant.overflow`).
  - Now all 22 are `type.too-large` with the exact size.
- **Controls:** the golden `size_cap_edge` accepts `[UInt8; 2147483647]` and a struct of exactly 2^31−1 bytes, at the host and riscv32. `size_edge.saw` now runs on all four triples.
- **Renames:** 26 size fixtures renamed to `type.too-large.*`, and 3 moved from typecheck to mono refusals (asserts refuses them).
- **Spec:** the `sizeof` entry states the cap (lead).
- **Gate:**
  - `run.py --only seed,units,golden,subset,fixture_whitespace,std,comments,typechecker,mono,programs,coro` green;
  - the corpus gate: all 2703 hold;
  - citations ok; the lint ok.
  - The lead rebased and rebuilt.
- **A finding outside the ruling:** a frame may hold several 2 GiB values (clang warns past a 4 GB frame). That is separate from the type cap.

Approved patch SL-1163.p1 (revision 1)

**Approved, revision 1.** The cap holds wherever a type's layout is needed, at the host and at riscv32. I probed positions beyond the 22 fixtures with `typecheck --check`, `mono --check` and `build --emit-ll` (which runs no clang), each under a time limit and never built. The probes are in `.build/scratch/air-review/sl1163_p1/p/cases/` on my machine.

**Refused as `type.too-large` with the exact size, at both targets:**

| Probe | Size |
|---|---|
| `Box<[[UInt8; 60000]; 50000]>` | 3000000000 |
| that type's `Optional` (a local, a result) | 3000000001 |
| a `Vector` element of it | 3000000000 |
| `sizeof` of it | 3000000000 |
| indexing through `UnsafePointer` to it (`p[1][0][0]`) | 3000000000 |
| `drop_in_place(at:)` instantiated at it | 3000000000 |
| two 1.5 GB fields, each under the cap | 3000000000 |
| `{ a: UInt8, b: [UInt64; 268435455] }`, over by one byte of padding | 2147483648 |
| `[UInt8; 2^31-1]` plus a `UInt8` field | 2147483648 |
| an enum whose `[UInt8; 2^31-1]` payload plus its tag passes the cap | 2147483652 |
| `[Row; 10^9]` with `Row = [UInt64; 10^9]` | 8000000000000000000 |

The control `[UInt64; 268435455]` alone (2147483640 bytes) is accepted at both targets, and its IR carries the array.

**Accepted, as the spec's text says:** an unused alias of the big type, an unused struct holding it, and an `UnsafePointer` to it that is only cast and compared. None of these needs the type's layout. The `sizeof` entry places the error "wherever its layout is first needed", and pointer indexing and `drop_in_place`, which do need it, are refused.

The fixtures' headers match their refusals, and the riscv32 twins use 2^33-byte shapes that fit riscv32's 32-bit `Int`.
