**Found by:** u7skel and u7b (U7a, SL-505, merged as 7e04eaa0). **Area:** mono's glue and the LLVM backend's closure lowering.

**Today:** a closure whose environment holds an owning capture is refused as `backend.not-yet`, since freeing the environment isn't built. Escaping closures are refcounted `Copy` (SL:open-questions, Oct 9), so the environment needs a release that drops each owned capture once.

**Not on the bootstrap path:** `compiler/` takes no closure captures (SL:architecture §4). Pin it with run-lane programs: a String capture, a NoCopy capture moved in, and a copied escaping closure released twice.

**Lead ruling (reversible): the driven twin's drop order.** Five rows (V106, V107, V108, `nested_closure_captures_frame_local`, `two_copy_captures`) print the same lines as before, but in the driven twin of a non-escaping `[copy d]` closure, sawc2 drops the duplicate before its source (`drop 71`, then `drop 70`). Stage 0 drops the source first.

sawc2 is right. The closure's environment is declared after `d`, so reverse declaration order (spec, "parts it holds die in reverse declaration order") releases it first. That is also the order both compilers print for the sync twin. SL-209's guarantee is that the sync and suspending versions behave the same, and sawc2's driven twin now matches its sync twin exactly. Stage 0's driven order comes from its own frame teardown (V106's comment calls it that), not from a rule.

**Mechanism, following the precedent of K32 and the SL-513 rows:** each row's EXPECT-OUTPUT states the ruled order, in both twins where an `examples/` twin exists. The comment paragraph that explained Stage 0's order is rewritten to state the rule. Each row gets an `annotations.tsv` `stage0-wrong` row: "SL-525 ruling: a non-escaping closure's environment is declared at the closure, so it dies before the bindings declared earlier, in a driven body exactly as in its sync twin; Stage 0's frame teardown releases the materialized source first. This file's EXPECT-OUTPUT states the ruled order".
