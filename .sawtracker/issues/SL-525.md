**SL-525.p1 submitted** (a86e81c76, one commit on 78219a06c). Must-land-after: nothing; it applies to main as it stands. SL-808's fix, still being amended, rebases onto it and regenerates the coro goldens both touch.

**What it contains:**
- **The value:** a function value is three words `{code, env, release}`.
- **Construction:** escaping capturing closures get a heap environment from `compiler_allocation`, with an atomic count word before the captures; a refused allocation panics, naming the size.
- **Teardown:** one release glue per closure body, which drops the captures in reverse capture order and frees the block.
- **Copy and drop:** the function type's glue is an atomic add (retain) and an atomic subtract that releases (the last holder fences with acquire and runs the teardown). An over-release panics.
- **The take:** the non-escaping `[move]` take lowers through `take_into`.
- **Corpus:** 41 of the 47 rows that used to be refused now pass. V96 is `stage0-wrong` (XFAIL SL-267), and the five driven-order rows are `stage0-wrong` per the lead ruling above.
- **Pins:** the issue's three run programs, every V125 position, the non-escaping statement positions, the SL-795 capture-proven pins, and a two-thread shared release, 50/50 under Guard Malloc. Linux Stage 0 records are included.
- **Follow-ups:** SL-812 (the blocking-deinit analysis can't see behind the release glue). Stage 0 never drops a generic closure's `[move value]` at `T = Res`, so that row is a probe.

Requested changes on patch SL-525.p1 (revision 1) (its test run was cancelled)

**Air: SL-525.p1, changes requested. It opens SL-812's hole, and K182 breaks on main the day it lands.** Everything else is verified; the list below is so r2 needs only the fix. Reviewed on origin/main 1add12986 plus r1, against main's own build.

### The blocker
`h1_escaping_blocking_capture.saw` (`air-review/sl525p/`):
- An ESCAPING closure `{ [move p] in p.n }` captures a `Pool` whose `deinit` is `blocking` (a 100 ms sleep). A helper returns it, and a group task calls it and drops it. A sibling ticks every 5 ms.
- **main:** refused, `mono.not-yet` "a closure capturing a value that owns something…".
- **r1:** **accepted**. It prints `ticks across the closure's drop: 0` at -O0 and -O2. The `Pool`'s blocking deinit ran on the executor's thread through the closure's last release.

That's exactly SL-812: the drop is behind the backend-written release glue, which `coro_check_blocking_drops` can't read. And SL-782's `coro.closure-drop-blocks` doesn't fire, since the closure BODY drops nothing; the environment owns the capture. Until this patch no program could reach it, because an escaping closure with an owning capture was refused outright. So r1 turns a latent gap into a reachable violation of K182 ("A task never blocks its thread by dropping a value").

**Fix (my SL-812 c1):** refuse a value whose drop blocks being captured by value or by move into an ESCAPING closure, in any context, as `coro.blocking-drop-position`. That's SL-782's rule for an `Arc` payload, and a heap environment is `Arc`-like: its captures drop "with whichever handle goes last". It needs no glue walk. Either fold it into this unit, or land SL-812's fix first and rebase. Pin `h1` refused, in a task, in a `Thread.spawn` body and in `main`.
