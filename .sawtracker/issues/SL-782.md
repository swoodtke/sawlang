## Description

**One `Channel.receive()`, lowered by context; `recv` is removed** (the user, Oct 19: "yes, file that and queue it in the next agent slot").

**Why.** After SL-777 the two methods have the same signature (`(&self) -> Result<T, ChannelError>`), and only their spelling tells them apart. `recv` blocks the OS thread, so calling it from a cooperative task stalls the executor's thread and every sibling task on it, the sender included, and nothing in the type system prevents it (the spec's NAMING note; `recv`'s docstring). `recv` is also an abbreviation, which the API doctrine forbids. A rename would only label the hazard; unifying removes it.

**The model: the one `blocking` externs already have** (spec, "What the offload does"). Mono keys a thread-context copy of everything a `Thread.spawn` body reaches (`MONO_KEY_THREAD`, SL-765 T3b), so every specialization knows statically which context it is in.

| context | `receive()` |
|---|---|
| a cooperative body (task, `Task.spawn`, a suspending `main`) | parks on the channel and suspends, as today; `Cancelled` applies |
| a `Thread.spawn` body (the thread copy) | blocks the thread on the gate's condition variable, as `recv` does today; `Alloc`/`System` from the gate apply, and `Cancelled` never occurs |
| a plain `sync` function | REFUSED, exactly like a `blocking` extern (it could be called from a task and stall the executor) |
| through `&any Trait` or a function value inside a thread body | refused, as a `blocking` extern is today (SL-776's g3/g7 rows) |

**The mechanism (design, at the brief):** std needs one method with two context-dependent bodies. Today only externs get that, from the compiler. **The lead's default: a std-internal intrinsic** (`public(package)`, the `__saw_` family) that mono folds to a constant per specialization: true in a thread copy, false otherwise. The thread copy then keeps only the condition-variable branch, the cooperative copy only the park, and the dead branch's suspension never reaches the thread copy. **Open for the user:** whether user code may branch on the context too (a public `in_thread_context()`-style surface). The default is NO, std only, because it's reversible. Alternatives the brief weighs: the compiler treats `receive` as a known intrinsic call (no std branch), or std declares the thread body as an extern-like `blocking` twin the compiler substitutes.

**Depends on SL-776:** its thread-context key funnel keys a thread copy from the resolved instance's causes. That's the same decision this folds on, so this unit lands after SL-776's patch.

**Scope:**
- `std/channel.saw`: one `receive()`, with `recv` deleted, and the docstring rewritten for both contexts.
- The compiler: the intrinsic's typecheck, its fold in mono's thread keying, and the `sync` refusal through the same rule as `blocking` externs (one funnel; obligation 1: name its entry points).
- The spec (Channels, the NAMING note, the `Thread.spawn` example, the effect rules where `blocking` is listed), README and the skill.
- **Consumer sweep (obligation 2):** every `recv()` (SL-777's six sites, and `git grep` again), now `receive()`. Stage 0's frozen std has no thread-context `receive`, so its rows become `stage0-wrong`, annotated.
- The Air's SL-777 nit: `thread_recv_gate_allocation_refused`'s 50 ms closer can race the final receive, leaving "the retry made its gate" unchecked. Pin the retry deterministically.

**Pins:**
- one helper function calling `receive()`, called from a `Thread.spawn` body (blocks; drains until `Closed`) and from a task (suspends; a sibling task keeps running while it waits);
- `receive()` in a plain `sync` function is refused;
- `receive()` through `&any` in a thread body is refused;
- the gate refusals (`Alloc`) on the thread path.

**Widened (the user, Oct 19): "we should make this a generic mechanism because i think we might have other functions which behave differently in task vs thread context."** SL-782 becomes the MECHANISM, and `receive` is its first user.

**The family** (std today; each row to verify at its unit):
| operation | task | thread body |
|---|---|---|
| `Channel.receive` / `recv` | `receive` suspends | `recv` blocks: two names for one operation |
| `sleep(duration:)` | parks a timer | needs a blocking sleep (today a suspension; a thread body presumably refuses it, UNVERIFIED) |
| `yield_now()` | re-queues the task | an OS yield, or nothing |
| `Thread.join()` | blocks the executor thread (the `recv` hazard) | blocks, correctly |
| file/net reads, `Command.wait` | park on the reactor | should block plainly (UNVERIFIED per API) |

**The lead's proposed shape:** one declaration, one signature, two context bodies, with the body picked when mono builds that context's copy (SL-776's thread-context key funnel):
```saw-fragment
public func receive(&self) -> Result<T, ChannelError> {
    in task { … }
    in thread { … }
}
```
- Each body is effect-checked in its own context: the task body may suspend and not block; the thread body may call `blocking` externs and not suspend.
- The function's summary per copy is the selected body's. In a plain `sync` copy the body must be sync-callable, else the call is refused, which is the `blocking`-extern rule.
- It generalizes the compiler's hardwired `blocking`-extern offload (a split whose task body is "offload").
- Freestanding never selects the thread body.
- The hazard: the two bodies must keep ONE contract (the same results and errors). Pins call every split function from both contexts; a lint may follow.
- An `if` on a context intrinsic (the earlier draft) is rejected: effect checking would depend on branch folding.

**Rulings needed from the user before the brief:**
1. **The spelling.** Lead lean: two arms in one declaration. Two `@context(…)` declarations of one name read like overloading by effect, which the spec rules out.
2. **Who may write one.** Lead lean: std only first (the std profile), opened to user code once std's uses have tested the rules (reversible in that order).

**Units:** (1) the mechanism (GRAMMAR, the spec, typecheck's per-body checking and summary, mono's selection through SL-776's funnel), with `receive` as its first user, `recv` removed, its sweep, and the Air's SL-777 nit on `thread_recv_gate_allocation_refused`; (2…) one small unit per remaining row of the family table. Depends on SL-776.
