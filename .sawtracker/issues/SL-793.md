## Description

**A cooperative task that joins a `threads: N` group's task blocks its executor thread** (found by SL-782 1b-ii's design census, agent p782b2). A pool group's `await_task` (`std/taskgroup.saw`) waits on a condition variable on the OWNING thread. When the joiner is a cooperative task (on main's executor, or on another single-threaded group), `join()` on a pool task blocks that executor thread, and every sibling task on it stops until the pool task finishes. That is the `recv`/`Thread.join` hazard class SL-782 removes elsewhere.

Per `Task.join`'s docstring ("on a pool … this thread only waits"), a join from a NON-task context is fine. A join from a task should park the task until the pool task completes (a word park, as 1b-ii's `Thread.join()` default does, woken by the pool task's completion).

**Obligation 4, a class:** "a std wait that blocks the calling thread with no task-side body". Sweep std's other waits (pool `join`, `TaskGroup.join`/`Deinit` waits on pool tasks, `Mutex.lock` contention? `Once`?) and measure each with the Air's sibling-ticks probe (a sibling ticking every 5 ms while the call waits; 0 ticks means blocked). The fix likely makes each a pair (SL-782's mechanism) or gives it a park.

A sibling ticks every 5 ms, and the elapsed time is measured, so a 0 means the wait really lasted while the executor was blocked:

| probe | wait in a cooperative task | ticks during it |
|---|---|---|
| w1 | `h.join()` of a `threads: 2` group's task that sleeps 100 ms on its worker (`await_task`) | **0 over 90 ms** |
| w2 | a `threads: 2` group's scope ending in the task, its spawned 100 ms pool task still running (the `Deinit` barrier, `join_crew`) | **0 over 102 ms** |
| w3 | `GATE.lock()` on a `Mutex` a `Thread.spawn` body holds | **0 over 231 ms** (-O0), **0 over 42 ms** (-O2) |
| w4 | w1's join, where the pool task `receive()`s from a channel that a SIBLING on the same executor sends to after 20 ms | **hangs**: killed after 10 s, no deadlock report |

w4 is the case that matters. The blocked executor can't run the sibling, the pool task waits on it forever, and the join waits on the pool task. The deadlock walk never runs, because the wait is a condition variable outside `idle`. So "a std wait that blocks the calling thread" is a silent deadlock as well as a latency bug, whenever the pool's work depends on a cooperative sibling. That's the same shape that made `recv` from a task dangerous (SL-110).

w2 meets SL-782's ruling. 1b-ii keeps `TaskGroup`'s `Deinit` barrier on the raw join so that groups stay droppable in tasks, and w2 measures that barrier: a pool group dying inside a task stalls every sibling for the pool tasks' remaining time. The w4 shape applies to it as well, since a pool task waiting on a sibling makes the scope end hang. So the fix for SL-793 should cover the barrier too, as a park on the pool's completion when the dropper is a task, not only `Task.join`. Otherwise 1b-ii's exemption carries the hazard forward.

`Mutex` (w3) is documented as blocking the calling thread, so it may be ruled acceptable. It's still the same class, and the brief should rule on it explicitly. A contended lock in a task can deadlock exactly like w4 when the holder is a sibling task, if a task can hold one across a suspension. It can't: the window is `borrows(sync)`. So the holder is always a thread or a short sync window, which bounds the stall. That argues for documenting it rather than splitting it.

**Air on c2's point 2: the `Deinit` barrier can't PARK the dropping task. It should DRIVE, the way the cooperative branch already does.** A `deinit` runs as drop glue, which is no suspension point, so there's no frame state to park. `TaskGroup.deinit` already has the right shape in its other branch (`std/taskgroup.saw`, main 60aa87cad):
```saw-fragment
if self.lock != 0 {
    shutdown_crew(...)          // pool: waits on its workers with the thread blocked (w2, w4)
} else if self.registered {
    exec_run(me, -1, 0)         // cooperative: runs the executor inline until this group is done
}
```
A cooperative group dropped inside a task runs the ambient executor in a nested loop, so its siblings keep going. A pool group dropped on an executor thread can do the same: a nested `exec_run` whose `idle` also waits on the pool's completion word, the same one point 1's join park watches. When it returns, `shutdown_crew` runs with every live task done, so the worker join is prompt.

That covers w2's stall, and w4 in its `Deinit` form, because the sibling that sends runs inside the drive. The pool's own teardown keeps 1b-ii's raw join for the workers' exit. The deadlock walk already treats a frame waiting in a nested drive as blocked ("a cooperative frame active on the walking thread's stack counts as blocked"), so a pool task that truly can't progress gets reported, which is point 4's pin.
