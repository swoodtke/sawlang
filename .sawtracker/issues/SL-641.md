## Description

Found by SL-630's sweep (agent c630hook), checking that MIR's `deinit_member` (`compiler/mir/src/build.saw`, the first `deinit` an extension writes) can find only one.

**Mechanism:** typecheck has no declaration-site check that two members of one type, written in different extensions, have indistinguishable signatures. Stage 0 refuses the second at its declaration ("method `deinit` is already defined for struct `Noisy` with an indistinguishable signature"). sawc2 accepts both. An ordinary method is caught later, at a call, as `call.ambiguous`; but the members no source call names, a hand-written `deinit` and a policy `copy()`, are never called by name, so nothing refuses them. `deinit_member` then takes the first in declaration order and the other body is dead.

**Evidence** (`sawc2 build --std-root std` at SL-630's tree, then run): prints `made 7` and `first deinit 7`; Stage 0 refuses at 16:5.

```saw
struct Noisy {
    id: Int
}

extension Noisy: NoCopy {
    func deinit(&var self) {
        print("first deinit {}", self.id)
    }
}

extension Noisy: ExplicitCopy {
    func copy(&self) -> Noisy {
        Noisy(id: self.id)
    }

    func deinit(&var self) {
        print("second deinit {}", self.id)
    }
}

func main() {
    let n = Noisy(id: 7)
    print("made {}", n.id)
}
```

**Fix, proposed:** refuse an indistinguishable redeclaration of a member across a type's extensions at its declaration, as Stage 0 does, so `deinit_member` and `policy_copy` each have one answer by construction.

**Related, needs a ruling:** this program also declares two copy policies on one type, `NoCopy` and `ExplicitCopy`. Both compilers accept two (the tier table lets `NoCopy` win), with or without the duplicate `deinit`. The spec says every type has exactly one tier ("Wrappers carry the tier of what they wrap"), which suggests a second policy conformance should be refused, but nothing states it.

**More of the same mechanism, from SL-615's sweep (r3lit):** the missing declaration-site check reaches free functions too, not only members across extensions. sawc2 accepts both of these. Stage 0 refuses each at the second declaration, with "function `h` is already defined with an indistinguishable signature".

```saw
func h(x: Int8) -> Int { 1 }
func h(x: Int8) -> Int { 2 }      // an exact duplicate
```

```saw
type Small = Int8
func h(x: Int8) -> Int { 1 }
func h(x: Small) -> Int { 2 }     // the same signature after aliases (spec, Overloading)
```

In sawc2 each one surfaces only at a call, as `call.ambiguous` naming `h(x: Int8)` twice. With no call, nothing refuses it. The fix should be the one declaration-site rule the spec states, applied to every overload set: free functions, and members across extensions. The spec's comparison is post-alias, with bare type parameters folded and labels included.

**The user's ruling, Oct 15** ("ok. i agree with the full ruling as stated."), reached over these messages:
- on `Copy` + `ExplicitCopy`: "it should also not be allowed - to me it reads as ambiguous: will the type be automatically be copied or does .copy() need to be called?"
- on `NoCopy` + either: "i would lean towards having NoCopy + ExplicitCopy/Copy be an error"
- on a stray `copy()`: "duplicating a .copy() function in a Copy type should be an error - just as having duplicate deinit function. though i think defining a .copy() func in a NoCopy type should be valid"

**The ruling:**
1. **One copy policy per type.** `Copy`, `ExplicitCopy` and `NoCopy` exclude each other. No pair is allowed, bounded or not: a type that declares one may declare no conformance to another. This reverses design 219's acceptance of `Copy` + `ExplicitCopy`, so `examples/copy_traits_both_declared_legal.saw` (and its `tests/corpus/` copy) becomes a refusal.
2. **A `Copy` or `ExplicitCopy` type's `copy()` lives only in its conformance.** One written anywhere else is refused at the declaration, like a duplicate `deinit`. That includes a derived-Copy type with no declaration and a `copy()` in a plain extension: it writes its own copy as `extension T: Copy { func copy(&self) -> T { … } }`, the retain hook, which every silent, spelled and generic copy runs.
3. **A `NoCopy` type may define a `copy()` method.** It is an ordinary method: silent copies are still refused, a spelled `.copy()` calls it, and it doesn't satisfy an `ExplicitCopy` bound (Stage 0 already refuses `dup<T: ExplicitCopy>(&h)` for such a type).

**Also in scope here, needing no ruling:** the declaration-site check for indistinguishable redeclarations, of members across extensions (the duplicate `deinit` in this issue's example) and of free functions (r3lit, c1), as Stage 0 and the spec's overloading rule have it.

**Evidence** (Stage 0; `.build/scratch/copy_own.saw` and `nocopy_own.saw` in the main root). A derived-Copy type with a plain-extension `copy()` copies bitwise when silent (3) but runs the method when spelled or generic (103): two answers for one value, which rule 2 removes. A conformance's `copy()` answers all three alike.

**Owed at landing:** the spec's Copy Trait Family section (one policy per type; where `copy()` may be written), the saw-lang skill, and SL:hazards for Stage 0, which accepts every pair and every stray `copy()`. No tracked source declares any pair (the frozen std's `UnsafeRef`, `NoCopy` + `ExplicitCopy`, is outside sawc2's std), and every `copy()` in `std/` is already inside its conformance.
