**The new std's `Vector.copy` and `Map.copy` request different allocation sizes from Stage 0's std, so an allocation-failure panic names another byte count.** Found by p711scalar (SL-711): both programs were refused by mono before SL-711 (`ExplicitCopy.copy()` / `Equatable.equals` on `Int`) and now run, moving to `wrong / stdout differs`.

```
alloc_vector_copy_panics.saw: sawc2 "panic at <std>: Vector.copy: allocation of 16 bytes (align 8) failed"
                              Stage 0 "panic at <std>: Vector.copy: allocation of 32 bytes (align 8) failed"
alloc_set_copy_panics.saw:    sawc2 "panic at <std>: Map.copy: allocation of 192 bytes (align 8) failed"
                              Stage 0 "panic at <std>: Map.copy: allocation of 128 bytes (align 8) failed"
```

**Mechanism.**
- `Vector.copy`: Stage 0's (`sawc/std/vector.saw`) builds the copy with `Vector(capacity: self.capacity)`; the new std's (`std/vector.saw`) reserves `self.length`. A 2-element vector of capacity 4 asks for 32 bytes in one, 16 in the other.
- `Map.copy` (reached through `Set.copy`): 192 against 128 bytes for one table, so the new std's slot is larger or its table count differs (UNVERIFIED which: compare `std/map.saw`'s slot layout and the copy's capacity with `sawc/std/map.saw`'s).

Not a backend question: the bytes are what each std asks its allocator for. Either the new std matches Stage 0's sizing (the corpus's oracle), or the programs' EXPECT lines stop naming a size and the difference is recorded as intended. The panic line's location is already normalized by corpusdiff; the byte count is not.

**Pins:** both corpus programs `pass` in corpusdiff.
