## Description

Found by SL-630's sweep (agent c630hook). Wrong code from a test-only declaration, by a mechanism of its own.

**Mechanism:** typecheck's `written_member` (`compiler/typecheck/src/conform.saw`) finds the member that meets a conformance's requirement by scanning every extension of the type, test-only ones included. So a requirement of a production conformance can be met by a method a `@test extension` writes, and production code calling through the conformance runs test code. SL:testing ("Test code cannot change what production code means") requires production code to be checked as if no test-only declaration existed. SL-626 filtered the member tables and SL-629 is the test-only conformance itself; here the conformance is production and only the member is test-only. SL-630 refuses the one copy-family instance (a test-only `copy()` on a production type), so a copy hook can no longer come this way; every other trait still can.

**Evidence** (`sawc2 build --std-root std` at SL-630's tree, then run): prints `test-only name` and `99`. Expected: a refusal, since without the test-only body the production conformance is missing `name`.

```saw
struct Money {
    cents: Int
}

trait Named {
    func name(&self) -> Int
}

extension Money: Named {}

@test
extension Money {
    func name(&self) -> Int {
        print("test-only name")
        99
    }
}

func get<T: Named>(x: &T) -> Int {
    x.name()
}

func main() {
    let a = Money(cents: 1)
    print("{}", get(&a))
}
```

**Fix, proposed:** `written_member` skips a test-only extension's members when the conformance's own extension is production, so the production conformance is refused as missing the requirement (`conformance.missing` or the trait's equivalent). A test-only conformance may still be met by test-only members.

**Readings 2 and 3 are one shape, and I'd rather it be refused at the declaration** (the user's ruling; the patch's readings are sound either way: no wrong code reaches production). The shape: a test-only member whose signature meets a requirement a production conformance of its type already meets. What happens now depends on *how* production meets it:

| production meets the requirement by | the test-only member | test code's direct call | through the trait |
|---|---|---|---|
| a written member (p3) | `overload.indistinguishable` at its declaration, on both builds | n/a | n/a |
| the trait's default (p4, p4b) | nothing reported | `call.ambiguous` | the default runs, silently |
| `@synthesize` (p10, p10b) | nothing reported (main: production's `@synthesize` turned `synthesize.inert`) | `call.ambiguous` | test code's `==` runs the derivation, silently |

In the last two rows, a test author's stub never runs through the trait, nothing says so, and the only call that could reach it is refused. A declaration-site refusal naming the requirement and the production conformance would make all three rows the same, and refuses nothing a test could use: the member is uncallable either way. **The user's ruling, Oct 14:** "ok. refusing at the declaration make sense then..." (in reply to the Air's suggestion, after first asking whether an explicit `@override` in a `@test` declaration would be useful).

**The rule:** a test-only member whose call shape meets a requirement that a production conformance of its type already meets is refused at its declaration. It doesn't matter how production meets the requirement: by a written member (already `overload.indistinguishable`), by the trait's default, or by `@synthesize`. The diagnostic names the requirement and the production conformance, and points to the supported seam for a fake: a test-only type passed to a production generic.

**`@override` is not adopted.** Replacing what production code runs would break "test code cannot change what production code means". Overriding only test code's own direct calls would just be shadowing, which adds nothing a differently named helper can't do. If real mocking is ever wanted, it gets its own design.

This replaces readings 2 and 3 of SL-640.p1. t640rev takes it in the revision, and SL:testing gains a clause at landing.
