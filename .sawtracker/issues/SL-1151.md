## Description

**A non-escaping function value leaves through a non-escaping closure's result, and safe code reads a returned frame.** Found by the reviewer of SL-1137.p1 (Nov 16, chat f296), on main today:

```saw
func apply<R>(g: () -> R) -> R { g() }

func leak(f: () -> Int) -> () -> Int {
    apply({ f })
}

func make() -> () -> Int {
    let s = "abc{1}"
    leak({ [&s] in s.len() })
}

func main() {
    let g = make()
    print(g())
}
```

Accepted; prints `0` at `-O0` (the string is four bytes), traps at `-O2`, `stack-use-after-return` under `--sanitize address`.

**Mechanism (the reviewer's reading):** `add_capture` refuses capturing a non-escaping function value only when the capturing closure escapes ("a non-escaping closure may capture a non-escaping function value, which keeps its kind in the body"), and nothing holds the value to its kind at the body's RESULT when the result type is inferred: `check_tail` with `want < 0` consumes the tail with no escape check, and `return f` in such a body is accepted too. A closure passed to a non-escaping generic parameter (`R` inferred as the function type) is one road; SL-1137.p1's in-place literal (`{ f }()`) is another, which is why SL-1137.p1 carries the fix: one result check, a funnel over every way a non-escaping closure's body produces its value (tail, `return`, a `match`/`if` arm's value, `try`), closes both.

**Safety:** a conformance row (refusal) per road, written first. Lands with SL-1137.p1.
