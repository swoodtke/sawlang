## Description

Found by the SL-340 implementer (Sep 24) in a driven body. The lead narrowed the scope: it is NOT specific to the driven lowering. Reproduces on main (e62b3164).

Member access on a value whose type is a distinct ALIAS over a struct is silently typed `Void`. The sync program below reports `undefined variable n`, because the `let` initializer is Void-typed and binds nothing:

```saw
struct Noisy { name: String }
extension Noisy: NoCopy {}
type Tag = Noisy

func work() {
    let t = Tag(Noisy(name: "four"))
    print("{}", t.name)
    let n = t.name.len()     // typed Void: `n` is then "undefined"
    print("{}", n)
}

func main() { work() }
```

As a function tail (`func work() -> Int { … t.name.len() }`) the refusal is "should return `Int` but body has no value", in both the sync and the driven lowering. The implementer's driven variant showed the window typed `(&Tag) -> Void` and then "`Tag` is not Printable".

This is almost certainly the same mechanism as SL-383, where an enum payload of an alias type is Void in a match arm. Name the mechanism (obligation 4) and fix it once. Expected behaviour is one of two:
- member access through a distinct alias resolves the underlying struct's members, which is what "an alias IS its underlying" (design 63) suggests;
- or it is a clean diagnostic that names the alias.
It is never a silent `Void`, which violates "never hide errors".

Sweep the positions:
- field read, method call and field write;
- optional chaining through an alias;
- payload binding (SL-383), `if let` and tuple destructuring;
- the driven twin of each.
