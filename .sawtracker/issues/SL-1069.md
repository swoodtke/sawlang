## Description

**SL-1063 unit B: the freestanding suite gains an ESP32-S3 row, booted under Espressif's QEMU.** It follows unit A (SL-1067, the triple) and is developed on top of A's commit; its patch is submitted after A merges.

**Why:** unit A proves `sawc` writes an Xtensa object. Only a booted case proves the object RUNS: the calling convention against C, 64-bit arithmetic through std's helpers, the inline atomics, soft-float, panics. The user ruled (Nov 12) that the row gates patches wherever Espressif's clang and QEMU are present, and skips that one architecture where they are absent.

**What sawos gave us (SO-73, chat m703 to m705; in the lead's checkout, `.build/scratch/so73/`).** Treat these as reference material from another repository: read them, copy what the suite needs into `tests/freestanding/hal/xtensa/` as our own files, and never run a script from inside that directory.
- `esp32s3-ABI.md`: the board facts, each with its probe.
- `stub/stub/`: `boot.S`, `stub.c`, `stub.ld`, `frame.h`, `run.py`: a call0 stub that boots from flash under Espressif's QEMU, takes a `syscall` and three timer ticks, and exits with a status. The sawos lead re-ran it; it passes.

**The facts the row is built on (from m703; each is in `esp32s3-ABI.md`).**
- **Boot is from a flash image, not `-kernel`.** `qemu-system-xtensa -machine esp32s3 -nographic -semihosting -drive file=IMG,if=mtd,format=raw`. IMG is 4 MiB of `0xFF` with each `PT_LOAD` segment copied to `LMA - 0x4200_0000` (`run.py`'s `build()` shows the twenty lines). The flash words at 0x400 and 0x404 are both `0xAEDB041D`; the first instruction is at flash offset 0x408 (address 0x4200_0408); byte 0 must not be `0xE9`.
- **Layout:** code executes in place from flash at 0x4200_0000; vectors in IRAM (the stub uses 0x4037_8400); data and bss in DRAM (0x3FC8_C000). In every output section `*(.literal .literal.*)` comes BEFORE `*(.text .text.*)`: `l32r` reaches only backwards, and the linker reports `R_XTENSA_SLOT0_OP out of range` otherwise.
- **The ROM enters windowed** (`callx8`, PS.WOE = 1, WINDOWBASE = 5). The start stub resets WINDOWSTART and WINDOWBASE, clears WOE and installs its own VECBASE before any call0 code runs; writing WINDOWBASE renames every address register, so anything needed across it is parked in a special register. Take `boot.S`'s sequence as it is.
- **Console:** one byte store to 0x6000_0000 prints.
- **Exit:** `simcall` with a2 = 1 (SYS_exit) and a3 = the status ends QEMU when it runs with `-semihosting`. The runner also reads the transcript and kills on its deadline, as it does for the other rows.
- **Atomics:** the ROM leaves ATOMCTL = 0x15 and `s32c1i` works on DRAM and IRAM, so inline word atomics run.
- **Toolchain:** `.S` files need `-fintegrated-as`; `-fp` is what removes FPU use; `char` is unsigned; link with the `ld.lld` beside Espressif's clang (Homebrew's refuses Xtensa objects, `unsupported e_machine value: 94`).

**Read first:** `tests/freestanding/README.md`; `tools/freestanding_runner.py` whole (`ARCHES`, `find_tool`, `find_clang`, `probe_tools`, the C compile's flag list, the two link lines, how QEMU is started and how a status and a transcript become a verdict, `due`/`due_on`); `tools/test_freestanding_runner.py` whole; `tests/freestanding/hal/riscv32/` and `hal/arm64/` (what `boot.S` owes a case: the entry symbol, the `fs_*` hooks, the exit path); `tests/freestanding/hal/support.c`; the sweep's `sites.tsv` rows for the runner (`.build/scratch/pxtensa/`).

**Design.**
1. **Tools are found per architecture.** Each `ARCHES` row says how its clang, linker and emulator are found:
   - clang: `build.choose_clang(triple)`, as today (unit A makes that Espressif's for the Xtensa triple).
   - linker: for the Xtensa row, the `ld.lld` beside that clang (`clang -print-prog-name=ld.lld`); the other rows keep PATH's.
   - emulator: for the Xtensa row, the newest `ROOT/tools/qemu-xtensa/*/qemu/bin/qemu-system-xtensa` for ROOT in `$IDF_TOOLS_PATH` when set and `~/.espressif`, and it must list `esp32s3` under `-machine help`. Never PATH's `qemu-system-xtensa`: Homebrew's has no such machine.
2. **The skip-or-fail rule is per architecture.** Today one known-absent tool skips the whole suite. New rule: an architecture whose tools are known absent is skipped, with one line naming the architecture and the missing tool, and the others run. A tool whose presence can't be determined still FAILS the suite. The summary line counts each architecture as ran or skipped. `tools/test_freestanding_runner.py` pins the old rule against stub tools; extend it: Xtensa's tools absent and the others present (the others run, Xtensa is skipped by name); every architecture's tools absent (today's whole-suite skip); a tool that can't be probed (fail); and its one-clang-for-every-arch assumption (the sweep's finding) replaced by a clang per arch.
3. **A row may boot from an image.** The row carries how it boots: `-kernel ELF` (the existing rows) or the flash image above, built by the runner from the linked ELF's `PT_LOAD` segments (a small function; no esptool). A segment outside the flash window is a build failure naming the segment.
4. **The row.**
   ```
   name: xtensa
   triple: xtensa-esp-unknown-elf
   qemu_args: -machine esp32s3 -semihosting, plus the -drive the runner adds
   cc_args: -mcpu=esp32s3 and the five features sawc's default states, each as
            -Xclang -target-feature -Xclang <feature>  (-windowed, -fp, -loop, -mac16, -bool);
            -fintegrated-as for the .S file
   features: None (sawc's default for the triple)
   no_atomics: features "-s32c1i" on the Saw half (sawc adds it to the default) and the C half,
               with hal/xtensa/atomics.c supplying __atomic_compare_exchange_4 and what
               hal/riscv32/atomics.c supplies, the same single-core way
   word_bytes: 4
   load_base: 0x4200_0000
   ```
   The C half and the Saw half must be compiled for the same convention and feature set; if clang rejects a `-Xclang -target-feature` for C that sawc's IR accepts, STOP and report it.
5. **`tests/freestanding/hal/xtensa/`:** `boot.S` (the magic words, the reset entry, the window and VECBASE setup from the stub, a stack, bss clear and data copy, a minimal exception vector that reports a fault and exits non-zero, the call into the case, and the `fs_*` hooks the other HALs provide: the console byte through the UART, the exit through `simcall`), `link.ld` (the stub's memory map and the literals-before-text rule, with `.fsmark` at `FSMARK_OFFSET` from the load base as the other scripts place it, and `KEEP` for the sections the cases place), and `atomics.c`. Comments follow CLAUDE.md "Code comments"; no reference to sawos's issue ids inside them.
6. **Every existing case runs on the new row.** No case is marked `due_on` by the agent's own decision.

**Steps.**
1. Confirm unit A's object first: from the worktree, the hello case compiles for the triple (unit A's step 3). If it doesn't, STOP: this unit can't start.
2. Reproduce sawos's stub once, by copying its five files to your evidence directory and following `run.py`'s commands by hand (don't execute `run.py`): it must print `STUB: halt pass`. This proves the toolchain and emulator work from your shell. If the sandbox refuses the emulator, STOP and report the refusal.
3. The runner changes of design items 1 to 3 with NO Xtensa row yet; `tools/test_freestanding_runner.py` extended and passing; the existing rows' results unchanged (run the suite for them).
4. The HAL and the row; boot `hello` first. Then the whole suite on the row.
5. **Triage (STOP point).** Record every case's verdict on the Xtensa row in a table: pass, or the failure with its transcript tail. For each failure say which side it looks to be on, with evidence: the HAL (a hook, the link script), the case (an assumption about riscv32 or arm64 written into it), `sawc` (a wrong object: give the disassembly), or the emulator. Then STOP and report the table, unless every case passes: the lead decides which failures are fixed in this unit, which become `due_on` with a filed issue, and which go to sawos. Don't mark anything `due_on` yourself, and don't change a case.
6. After the lead's decision: the agreed fixes, the docs (`tests/freestanding/README.md`: the row, where its tools come from, the per-arch skip rule; CLAUDE.md's freestanding paragraph in "Testing" gains the per-arch rule and the Espressif tools), the gate, the commit.

**Expected outcomes.**
- The riscv32 and arm64 rows: every case's verdict unchanged.
- With `IDF_TOOLS_PATH` pointing at an empty directory and no `~/.espressif` (simulate as unit A's step 6 does), the suite runs the other two rows and prints one line that Xtensa is skipped for an absent clang.
- `tools/patch_gate.py`'s freestanding inputs (`SUITE_INPUTS`) already include `tests/freestanding/` and the runner; if the Xtensa HAL adds an input the gate should watch, add it and run the `patchgate` lane.

**Gate (agent, under the suite lock).** `tools/test_freestanding_runner.py`, `tools/freestanding_runner.py` (the whole suite, all rows), `compiler/tests/run.py --only seed,fixture_whitespace,comments,programs`, `tools/battery.sh citations patchgate childgroups` (the runner starts QEMU: its process-group handling is what `childgroups` pins; a new launch path must go through `tools/child_groups.py`).

**Files:** `tools/freestanding_runner.py`, `tools/test_freestanding_runner.py`, `tests/freestanding/hal/xtensa/` (new), `tests/freestanding/README.md`, `CLAUDE.md`, `tools/patch_gate.py` only for an input.

**Corrections to the board facts (the sawos lead, chat m712, Nov 12; from the Air's review of SO-73.p1; a revised `esp32s3-ABI.md` follows).** The implementing agent applies these over the description above and over the copy in `.build/scratch/so73/`:
1. **ATOMCTL:** the emulator reads bits [1:0] only. 0x01, 0x15, 0x2A and 0x3F work; 0x00, 0x04, 0x10, 0x28 and 0x3C make `s32c1i` fault with EXCCAUSE 3.
2. **Under `-kernel` (no ROM) QEMU resets ATOMCTL to 0x28, a faulting value.** Our row boots from flash and inherits the ROM's 0x15, but `hal/xtensa/boot.S` sets ATOMCTL to 0x15 itself before the first call into the case anyway, so the HAL doesn't depend on which way it was booted; say why in its comment.
3. The ROM's RAM ends at 0x3FCE_FFFF, not 0x3FCF_FFFF: check `link.ld`'s DRAM region and stack top against it.
4. EXCCAUSE 15 is LoadStoreAddrError; StoreProhibited is 29 (for the fault vector's report).
5. The ROM banner's first line carries the strap word, so it isn't fixed text: the runner's transcript match must begin at the case's own first line, never at the banner.

A further correction from the sawos lead (chat m714): section 7e of `esp32s3-ABI-r3.md` is wrong on struct RESULTS. At call0, Espressif's clang returns a struct of up to FOUR words in a2 to a5 (field order); the hidden result pointer in a2 starts at five words, with the first argument then in a3. This doesn't touch what sawc emits today: sawc refuses every aggregate at an `extern` or `@export` boundary (`c_class` in `compiler/target/src/layout.saw`), on this target as on the others. It matters only to a HAL C helper that returns a struct, and to whoever later lifts the aggregate refusal, who must read clang's output (the sweep's `.build/scratch/pxtensa/abi.md` and its `c2_*` probes), not that table.

**Triage decided (lead, Nov 12).** The first full run on the ESP32-S3 row: 36 of 40 cases pass; the four failures are all on the case side, none in sawc, the HAL or the emulator. Decisions sent to the agent:
1. `cooperative_channel_park` and `cooperative_drive` assert that a stack address reads negative on a 32-bit target, which is riscv32's memory map (RAM above 2^31), not a compiler fact. The check becomes a reported value the runner asserts per row.
2. `link_address` masks the address with `0x0FFF_FFFF`, which holds for 0x8000_0000 and 0x4000_0000 bases but not 0x4200_0000; the mask becomes `0x00FF_FFFF` (load bases are multiples of 16 MiB).
3. `bladepkg` is `due_on` the xtensa row, citing SL-1073 (its manifest has no section for the triple; Blade's support is SL-1071).
4. `spinlock_without_atomics` stays riscv32-only; the Xtensa wording is pinned by unit A's typecheck fixture.
The agent's six `arches` extensions (32-bit-word and helper cases, all passing on Xtensa) are confirmed. Then: rebase onto main (unit A merged as c2262aa8a), the gate, one commit.
