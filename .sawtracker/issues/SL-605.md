**`compiler/tests/run.py` reports each step live on stderr** (requested by the sawtracker lead for ST-90, chat m512).

- **Why:** since SL-604, `run.py` keeps each step's stdout and prints it all in the serial order. So a gate's log, live (ST-90) or local, shows nothing during a step and then a burst. One stderr line as each step starts and finishes shows progress without changing stdout.
- **Shape:** `run.py: started STEP` and `run.py: finished STEP (N s)`, written at once (flushed) to stderr in the order events happen, which is nondeterministic under the pool. A failed step says `failed` instead of `finished`. The fixpoint lane's replay gets the same lines, prefixed with the stage.
- **The parity pins:**
  - SL-604's serial-vs-parallel identity is about stdout, so `compiler/tests/parallel_order.py` and any check of "empty stderr" compare stdout only, or drop the progress lines first;
  - a pin requires that every step yields one started line and one finished line;
  - stdout stays byte-identical to SL-604's.
- **Depends on:** SL-604 (merged first). SL-603 also edits `run.py`, so whichever of the two lands second rebases.
- **Done when:** a gate's log shows each step starting and finishing as it runs, and stdout is unchanged.

The Air (chat m514): emit the lines from the scheduler (`run_steps`, in the parent process), never from inside a step process. `parallel_order.py`'s `stage_output` compares each step's captured stdout and stderr plus the merged render, so a line printed inside a step would enter the compared bytes in timing-dependent order. The parent's own stderr isn't captured there. If a line ever has to be in a step's output, the pin filters it by a fixed prefix. This is binding for the unit.

**Read:**
- **The lines come from the scheduler only,** as c2 asked. `say` runs in the parent's `run_steps`, never inside a step process, so a step's captured stdout and stderr, which `parallel_order.py` compares, stay the same at every worker count.
- **Locking:** `say` takes `cond`, which its callers (`finish`, `do_build`, the launch loop) already hold. That's safe because `cond` is a default `threading.Condition()`, whose lock is an `RLock`. Each line is written and flushed under the lock, so lines never interleave, and `started[name]` is set before the step launches.
- **`failed` for a crash agrees with the pin:** `ended` says `failed` for failures or a crash, and `_crashed` always records one failure, so the pin's `bool(r["failures"])` gives the same answer.
- **Live in the gate:** `tools/patch_gate.py` runs `compiler/tests/run.py` with stdout and stderr inherited (`subprocess.run(... ).returncode`, no capture), so the lines reach the gate's log as they happen, which is what ST-90's streaming needs. In `main`, the steps' own stderr is still written afterwards through `sys.stderr.buffer`. The progress lines are flushed before that, so the order holds.

**Landed:** `compiler/tests/run.py` reports each step live on stderr. The scheduler (`run_steps`, in the parent process) writes:
- `run.py: started STEP` when a step starts;
- `run.py: finished STEP (N s)`, or `failed`, when it ends;
- `run.py: skipped STEP` for a step skipped after a failed build.

The build gets the same pair of lines, and the fixpoint replay writes them prefixed `fixpoint: `. Only the scheduler writes them, never a step process, so each step's captured output and run.py's stdout are unchanged at every worker count. The gate's log shows them as they happen, which is what sawtracker's ST-90 streams.

**Pin:** `compiler/tests/parallel_order.py` requires, in serial and parallel modes alike, exactly one started line then one ending line per step, `failed` exactly when the step's result has failures, and nothing else.

Landed in SL-605.p1, merged as 8950a9b3c (r2, the merge queue's replay onto main). The Air approved it. The sawtracker lead asked for it, for ST-90.
