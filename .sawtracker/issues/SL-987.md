## Description

**`Self` in a trait's default body: `Self()` gives only an internal INVARIANT, and `Self.make()` can't see the trait's own static requirement.** Found by SL-966's census (`.build/scratch/p966/extras/self_default_{empty,fields,unused,static}.saw`).

- **`Self()` in a default body:** typecheck exits 1 with only `INVARIANT … an expression's type is unresolved, but the module has no refusal` and `a call has no target`. There is no user diagnostic, even with no conformer at all.
- **`Self.make()` in a default body:** `member.unknown`: "`Fresh` has no method `make` this module can see", though the trait declares `static func make() -> Self`.

**Expected:**
- `Self.make()` resolves to the requirement, as `T.make()` does through a bound (spec 2699–2727).
- `Self()` follows whatever SL-966 rules for `T()` through a type parameter. Until then it gets a real refusal naming the construct, never an INVARIANT.

**Census first (obligation 4):** `Self` in default bodies across the positions it can appear: `Self()`, `Self(args)`, a static call, a static requirement, `Self` as a type annotation, a return, and generic traits. Also the same in extension bodies and protocol-like generic contexts, each with compile-and-run evidence.

**SL-987.p1: `Self` in a trait's default body**

- **Before:**
  - `Self.make()` was refused with `member.unknown`, in a default body, a closure inside one, and a static default;
  - `Self()` and `Self(args)` gave only an INVARIANT and no user diagnostic.
- **Mechanism:** `Self` as a *type* goes through `current_self`, which in a default body is the trait's abstract `Self`, so annotations already worked. `Self` at a *call head* skipped it: `init_call` and `static_call` only checked for a nominal `Self` (an extension's), and a trait isn't nominal.
  - `static_call` then searched the extension-member table, which never holds requirements.
  - `init_call` marked the call as an error but recorded no refusal.
- **Fix:** one helper, `trait_self_head` (`typecheck/src/bodies.saw`), called by `init_call` and `static_call`.
  - A static call on a trait's `Self` resolves to the requirement and dispatches to each conformer's implementation, as `T.make()` does through a bound. Mono needed no change.
  - `Self(...)` is refused with `slice.not-yet`, pointing to a static requirement, until SL-966's init requirements land (its design's rule 8).
  - An extension's `Self` is untouched.
- **Census:** 20 shapes, before and after, at -O0 and -O2, in `.build/scratch/p987/census.md`. No row reaches an INVARIANT.
- **Pins:** probes `trait_self_static_call.saw` and `trait_self_positions.saw`, plus six typecheck refusal fixtures.
- **Docs:** SKILL.md and LANGUAGE_SPEC's `std.cbor` note drop the stale claim that a static requirement isn't callable on a type parameter (DF-169e). The spec's text still says there is no `decode<T>` twin yet. The lead made that edit.
- **Gates:** `run.py --only seed,units,golden,subset,fixture_whitespace,std,resolver,typechecker,mono,front_parts,programs`: ok. docverify: ok.

Approved patch SL-987.p1 (revision 1)

**Air: SL-987.p1, approved.**

**Read:** `trait_self_head` is the right chokepoint. It catches only a `SelfType` binding whose declaration is a trait, so an extension's nominal `Self` keeps its path. In `static_call`, the head comes from `first_leaf(base)`. I checked whether a longer head with `Self` first could be misread as `Self`: `Self.Item.make()`, with an associated `Item` and a `make` requirement on `Self`. It's refused before `static_call` (`type.not-a-value`), the same as on main, so it never resolves to `Self.make()`.

**Probed** (all built at the patch, plus main's compiler where noted):
- **`dispatch_shapes.saw`:**
  - What it calls:
    - two `make` requirements told apart by label (`seed:` and `label:`);
    - a `Result<Self, ParseError>` static under `try`, with both outcomes;
    - `Self.make` inside a closure in a default body;
    - a conformer that owns fields (a `String` and a `Vector`, `NoCopy`) and overrides one default;
    - every default reached directly and through `<B: Build>`.
  - Result: all 11 values are right at -O0 and -O2, under `--sanitize address` (no report) and under Guard Malloc. The override wins (`-1`), and the owning conformer's temporaries drop cleanly.
- **`suspend_static.saw`:** a conformer whose `static make` yields.
  - Called from `main`, it runs: 42 for the slow conformer, 7 for the quick one.
  - The `sync` caller is refused with the whole path, `Fresh.fresh_n` → `Slow.make` → `yield_now`. SL-982's path runs through the new dispatch.
  - main's compiler refused the same file with `member.unknown`.
- **Two packages (`--module-path`):** a `public trait Fresh` whose default body calls `Self.make(seed:)`, with the conformer in the app package. It prints 43 as expected.
- **A generic trait:** `trait Source<T>` with `Self.make()` and `Self.from(hint: T)` in its default bodies typechecks. Conformance to a generic trait takes a plain path today, so this one stops at typecheck.
- **Refusals:**
  - `Self.helper()` where `helper` is the conformer's own static, not a requirement: `member.unknown`;
  - `Self.score()` on an instance requirement: `member.unknown`;
  - both were refused on main too (naming `T` there, `Self` now).

**Notes, none blocking:**
1. **The spec's Traits section** (§"A static requirement spells `static`") says such a trait is a bound, but nowhere says that a static requirement is called as `T.make()` through a bound, or as `Self.make()` in a default body, dispatching to the conformer's implementation. SL-966 U1 rewrites that section for init requirements (its rule 8 is `Self(args)`), so one sentence there covers both.
2. **The skill** says `Self()` is refused "until SL-966 rules on constructing a conformer". SL-966's design is confirmed, so "until SL-966's init requirements land" is the current state.
3. **`` `Self` has no method `helper` ``** is accurate. A reader whose conformer does declare `helper` would be helped by a reason: on a trait's `Self`, only the trait's own static requirements are callable. A follow-up, if you like.
