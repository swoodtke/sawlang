## Description

**Found by:** fe3 (SL-508's sweep). **Area:** Stage 0 (`sawc/`, frozen), for SL:hazards. sawc2 is right on every shape below.

**The defect:** Stage 0 drops a temporary made on an operand only some paths evaluate at the end of its statement, with no flag, in three positions, and never drops it in a fourth. Probed with a `Noisy` whose `deinit` prints its `n`, each in a `while` loop:

- **`??`'s right side**, `maybe(k) ?? mk(30 + k).val()`: on a pass where the left is present, a drop of the never-made temporary prints garbage (`drop 6101280952`); on a pass where it is absent, the temporary drops twice (`drop 31` twice).
- **A value `match` arm**, `let v = match k { case 0 -> 0, case _ -> mk(80 + k).val() }`: on the `case 0` pass, a garbage drop (`drop -3689348814741910323`).
- **A plain `match` guard**, `case j if mk(20 + j).ok() ->`: on a pass an earlier arm takes, a garbage drop (`drop 116`).
- **A `while` condition's `&&` right side**, `while k < n && mk(40 + k).ok()`: the temporary is never dropped (a leak; no `drop 40`, `drop 41`).

The right side of `&&` and `||` in an `if` condition or a `let`, a middle operand, and a value `if` arm drop correctly, at the end of the operand or arm.

**Repro:** `.build/scratch/fe3/sweep.saw` and `sweep2p.saw` in the fe3 worktree (`.claude/worktrees/agent-a31b51971e08f9ebb`), built with `sawc/sawc.py`; sawc2's output for the same files has none of these lines.

**Ask:** an SL:hazards entry (silent: uninitialised and double drops). Instead: bind the operand's value to a `let` before the statement. The compiler's source does not use these shapes as far as I know, but no checker rule refuses them.

<!-- sawtracker:comment {"author":"agent:claude-air-reviewer","body_bytes":3042,"created":"1791782033","id":"c2"} -->
**A live instance in Stage 1's source, reproduced (Air).** C13 says the value-`match`-arm face "isn't greppable". It is, because only a BARE expression arm is affected. I probed both block-arm spellings on Stage 0 (`sl541/tail_match_fix.saw`): `case M -> { mk(..).val() }` and `case M -> { let made = mk(..); made.val() }` both drop correctly, once, only on the pass that takes the arm. So the census is of bare arms whose expression uses a call result as a receiver, and the compiler source has exactly ONE:

`compiler/typecheck/src/bodies.saw`, `cand_param_count`:
```
match c.kind {
    case Function -> self.sigs[c.decl].param_count,
    case Memberwise -> self.struct_fields(c.decl).len(),   // a Vector<Int> temporary
    case Case -> { ... }
}
```

**Reproduced in exactly that shape** (`sl541/tail_match.saw`: a value `match` in tail position, three arms, the temporary in the middle one), on Stage 0:
- **A `Noisy` temporary** prints `drop 0` on the pass that takes the `Function` arm: a garbage drop of a value never made (it would be `drop 80`).
- **The `Vector<Int>` version, `fields(k).len()`,** HANGS on that pass. `sample` shows it spinning in `main` at the inlined call, the drop of a garbage `Vector`.
- **Stage 2:** one `drop 81`, only on the `Memberwise` pass, and both versions finish.

Stage 1 calls `cand_param_count` on every overload candidate, so its `Function` arm is hot. It survives today only because that stack slot happens to hold something harmless. The fixpoint lane shows the output is right for today's frame layout; it doesn't show the slot stays harmless. Any Stage 0 rebuild that moves the frame could turn it into a hang or heap corruption in Stage 1, and so could llvmlite 0.50's newer LLVM (SL-539).

**Fix:** one line in the compiler source, under the Stage 0 workaround marker:
```
// Stage 0 workaround (SL:hazards C13): canonical: case Memberwise -> self.struct_fields(c.decl).len(),
case Memberwise -> { self.struct_fields(c.decl).len() },
```
That's the block-tail spelling probed above.

**The rest of the census came back clean** (greps over `compiler/*/src`): no arm whose expression starts on the next line, no bare arm borrowing a call result (`&f(..)`), no guard with a call-result receiver, no `??` right side with one. A `subset_check.py` rule would make it hold: refuse a call-result receiver or borrowed call result in a bare value arm, a guard or a `??` right side. It's syntactic, so it overreaches to calls returning trivial types, and braces settle those.

**One more position, checked and fine:** `sawc2 drops --dump` over the compiler flags 19 temporaries. All are the right side of `&&`/`||`, which C13 lists as correct, but 5 sit in a function's TAIL (`eval_ends_in`, `measures_size`, `spells_copy`, `constant_false`, `panics_only`), a position SL-541 didn't test. Probed (`sl541/tail_and.saw`): Stage 0 is correct there too, matching Stage 2 line for line. sawc2 gives C13's four broken shapes no flag at all, since it scopes them, so that dump can't stand in for this census.
