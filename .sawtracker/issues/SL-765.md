## Description

**sawc2 has no `Thread.spawn` engine, and no unit of the SL-545 plan owns one.** A18 (SL-580) takes only `Thread.spawn`'s typecheck rules: the body's sync rule and the retired `spawn { }`. SL-580 c5 leaves the thread engine itself "outside the plan". This issue owns it: the OS-thread engine behind `Thread.spawn { }` (`Thread<T>`/`VoidThread`, `join`/`detach`/`cancel`, a `sync` body that may call blocking externs), lowered by sawc2 over the runtime's `__saw_rt_thread_spawn` seam.

**Why now:** under the coroutine push's deferral rule (the user, Oct 16), a unit that can't pass a corpus row because a later feature is missing registers that row on the feature's issue rather than building the feature. `Thread.spawn` is the largest refusal key outside the plan: about 26 corpus programs are refused on it (`.build/scratch/probe_coro_corpus.py ROOT` reproduces the tally).

**Related runtime findings to sweep with it:** SL-276 (`__saw_rt_thread_spawn` discards `pthread_create`'s failure), SL-360 and SL-35 (the thread control block's layout and size).

Needs a plan section (scope, the spawn's capture-list-as-parameters rule, join and drop fates, the Send gate it shares with A17b) before dispatch.

**Air: three things for the plan section, one of them a ruling.**

1. **What `Thread.spawn` does when the OS refuses a thread is unruled.** SL-276 is still live in the runtime sawc2 links: `runtime/shim.c`'s `__saw_rt_thread_spawn` ignores `pthread_create`'s return and hands back an uninitialised `pthread_t`. The spec types the form `Thread.spawn { ... } -> Thread<T>` (spec ~8422). Its list of six panics, "Where a refusal still panics", covers "a spawned task's control block" (an allocation), but no OS refusal such as `EAGAIN`. sawc2 is about to become a second producer of this seam, so the plan should put the question to the user before dispatch:
   - **(a) a panic naming the OS error,** a seventh entry in that list;
   - **(b) `Thread.spawn` returns `Result<Thread<T>, …>`,** the way `TaskGroup(threads: N)` is written `try!` in the spec's own example. The corpus's `Thread.spawn` sites and the spec's examples gain a `try!`.

   I lean (b): that list admits a panic only where "the report has nowhere to go", and a spawn expression can carry a `try`. SL-578's pool workers start at a group's first spawn (spec ~9191), so the same question reaches them.
2. **Settle SL-360/SL-35's layout before the new std's `Thread` is written.** The new `std/` has no `Thread`, `VoidThread` or join seam at all: `compiler/resolve/src/walk.saw` refuses the form at resolve. So this unit ports them. SL-360's defect is Stage 0's std freeing the control block with a hand-computed `24 + sizeof<T>()` against codegen's padded size. Port it as-is and both compilers carry it. The detach seam already carries the size in the state word; `join` should read it from there, or from one compiler-provided layout, as SL-360's fix direction says. The comment above `__saw_rt_thread_detach` in `shim.c` names Stage 0's `_generate_spawn_trampoline` as "the other end"; it should name sawc2's lowering once this lands.
3. **The tally:** main's `corpus_diff.tsv` keys 28 rows on "the `Thread.spawn` form is not in the bootstrap slice yet", and 41 corpus files mention `Thread.spawn` (the rest stop earlier). The plan's sweep should take the 28 as its row list.
