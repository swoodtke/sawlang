## Description

**sawc2 has no `Thread.spawn` engine, and no unit of the SL-545 plan owns one.** A18 (SL-580) takes only `Thread.spawn`'s typecheck rules: the body's sync rule and the retired `spawn { }`. SL-580 c5 leaves the thread engine itself "outside the plan". This issue owns it: the OS-thread engine behind `Thread.spawn { }` (`Thread<T>`/`VoidThread`, `join`/`detach`/`cancel`, a `sync` body that may call blocking externs), lowered by sawc2 over the runtime's `__saw_rt_thread_spawn` seam.

**Why now:** under the coroutine push's deferral rule (the user, Oct 16), a unit that can't pass a corpus row because a later feature is missing registers that row on the feature's issue rather than building the feature. `Thread.spawn` is the largest refusal key outside the plan: about 26 corpus programs are refused on it (`.build/scratch/probe_coro_corpus.py ROOT` reproduces the tally).

**Related runtime findings to sweep with it:** SL-276 (`__saw_rt_thread_spawn` discards `pthread_create`'s failure), SL-360 and SL-35 (the thread control block's layout and size).

Needs a plan section (scope, the spawn's capture-list-as-parameters rule, join and drop fates, the Send gate it shares with A17b) before dispatch.

That was harmless while no other thread could write the word. Once T2/T3 let a `Thread.spawn` body send to a cooperative receiver (K56, `channel_pipeline`), the receiver's thread wakes 1000 times a second until the send. The spec says (design 230) "Treat a 0%-CPU channel wait as working now and SUSPECT in older builds". **The user ruled (Oct 16): retire `VoidThread` and `VoidTask`.** A `Void` body yields `Thread<Void>` / `Task<Void>`, and `join()` returns `Void` (a statement; `let x = h.join()` is the visible-`Void` binding error, as it should be).

**Why the old types existed:** design 242 read the visible-`Void` rule (122/132, DF-225h) as making `Task<Void>` "unwritable as an annotation". That rule forbids BINDING a visible `Void` value, not naming `Void` as a type argument: the spec writes `Result<Void, E>` everywhere, and its instantiation-uniformity rule requires generic code to work at `Void`. sawc2 confirms it: a generic struct at `Void` (`Holder<Void>`) builds as an annotation and as a parameter type, and runs (`.build/scratch/probe_void_arg.saw`). Stage 0 can't store a `Void` field (an internal compiler error: "void type only allowed for function results"); that limit, not a language rule, is the real origin of the two types.

- **`Thread<Void>`:** SL-765, built that way from the start. T1 types a `Void` body as `Result<Thread<Void>, SystemError>`, and T2's `Thread<T>` must work at `T = Void` (a zero-sized result slot).
