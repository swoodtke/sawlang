**A sync window around an SOS driving wrapper is accepted, and a task run inside it re-enters the window's Mutex at run time.**

sawos's typed wrappers (`Waiter.wait`, `Thread.join`, `PipeInlet.send` and others in the `sos` package) now drive the calling thread's background tasks while they wait: each calls `__saw_background_drive()` through `sos.floor`'s `extern "C"` declaration, then makes its syscall through the non-seam `sos_syscall*` stubs. The window fence is expected to count such a wrapper as running tasks, and so to refuse it inside a `sync` window, as it refuses `sleep`.

**Repro** (sawlang v0.24.6, a sawos `main` program; the file is attached as `probe-window-task.saw`):
```saw
let r = borrow var g = m.value().lock() {
    g = 10
    let _ = waiter.wait()        // a driving wrapper
    g
}
```
- **What happens:** it compiles. At run time a task spawned on the same thread runs inside the window and takes the same `Mutex`, and std panics: `Mutex.lock: this thread already holds the lock — … reached again through another name or by a task run inside its window`.
- **Control:** `sleep(Duration.ms(1))` in the same window is refused at compile time (`borrows.sync-window`: "this call may suspend while a borrow from `Mutex.lock` is open").
- **Expected:** the same refusal for the wrapper, since it reaches `__saw_background_drive` through `extern "C"`. The question is whether `coro_extern_edges`, or whatever maps an extern to the sweep, sees a drive reached through a package's wrapper, and what an extern-using package must declare for the fence to see it.

Found in sawos review (the drive in the typed wrappers); sawos states it as a run-time hazard until the fence catches it.

**Lead's reading (Nov 28): this works as specified. Nothing is refused, and the outcome is the documented panic.**

- **The window-drive fence covers static roots only.** `coro.window-drives` refuses a drive only inside a *static root's* exclusive window (LANGUAGE_SPEC, "Cooperative tasks", the teardown bullet: "Inside a static root's exclusive window no other task may run"). A lock's `borrows(sync)` window is named there as one where the teardown "keeps the nested sweep, … whose rules govern what runs there".
- **A lock window may drive.** "Synchronized Access" says re-entry through another name panics, and "Every wait that runs other tasks reaches that last name". Its list is a thread-context `Task.join()`, a pool's `join()` or `Deinit`, a thread-context `Thread.join()` and `Channel.receive()`. These run the thread's tasks inside the window, and a task that takes the held lock panics at its `lock()`. `SpinLock` has the same rule ("re-entry never spins forever").
- **sawos's wrapper is that case.** It calls `__saw_background_drive` through `extern "C"`. The panic it gets is the re-entry check working.
- **`sleep` is refused for a different reason.** It suspends, and a `borrows(sync)` window admits no suspension (`borrows.sync-window`). Driving the thread's tasks doesn't suspend the caller.

**The static-root fence does see this route.** I probed it on main (v0.24.6) with `.build/scratch/probe_root_window_drive.saw`, at `--freestanding -c`, riscv32. Inside `count_slot()`'s window (`unsafe sync borrows(sync, COUNT)`), both a direct `__saw_background_drive()` and a call through a plain wrapper function are refused with `coro.window-drives`:

> `wait_wrapper` → `__saw_background_drive` (an `extern` with no body in the program, which may run anything) → `sweep`

The entry isn't in the seam table that `coro_extern_edges` exempts, so the edge reaches the sweep. A package needs no declaration for the fence to see it.

**To get the refusal at compile time,** keep the state in a static root (`borrows(sync, ROOT)`), not behind a `Mutex` or `SpinLock`. The root window is the one the compiler fences.

**Open for the owner (a language question):** whether a lock's `borrows(sync)` window should refuse a drive too, turning today's run-time re-entry panic into a compile error. The cost is that hosted code inside a `Mutex` window could no longer make a thread-context `Task.join()`, `Thread.join()` or `Channel.receive()`, all of which the spec allows today. The lead's recommendation is to keep the rule as written. The static root already gives kernels the compile-time fence, and a lock window's re-entry is always caught, never silent. If the owner keeps it, this issue closes as by design.
