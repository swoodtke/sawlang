**A sync window around an SOS driving wrapper is accepted, and a task run inside it re-enters the window's Mutex at run time.**

sawos's typed wrappers (`Waiter.wait`, `Thread.join`, `PipeInlet.send` and others in the `sos` package) now drive the calling thread's background tasks while they wait: each calls `__saw_background_drive()` through `sos.floor`'s `extern "C"` declaration, then makes its syscall through the non-seam `sos_syscall*` stubs. The window fence is expected to count such a wrapper as running tasks, and so to refuse it inside a `sync` window, as it refuses `sleep`.

**Repro** (sawlang v0.24.6, a sawos `main` program; the file is attached as `probe-window-task.saw`):
```saw
let r = borrow var g = m.value().lock() {
    g = 10
    let _ = waiter.wait()        // a driving wrapper
    g
}
```
- **What happens:** it compiles. At run time a task spawned on the same thread runs inside the window and takes the same `Mutex`, and std panics: `Mutex.lock: this thread already holds the lock — … reached again through another name or by a task run inside its window`.
- **Control:** `sleep(Duration.ms(1))` in the same window is refused at compile time (`borrows.sync-window`: "this call may suspend while a borrow from `Mutex.lock` is open").
- **Expected:** the same refusal for the wrapper, since it reaches `__saw_background_drive` through `extern "C"`. The question is whether `coro_extern_edges`, or whatever maps an extern to the sweep, sees a drive reached through a package's wrapper, and what an extern-using package must declare for the fence to see it.

Found in sawos review (the drive in the typed wrappers); sawos states it as a run-time hazard until the fence catches it.
