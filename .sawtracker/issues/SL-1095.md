## Description

**Filed by the sawos lead for the sawlang lead.** The user asked that sawos's build tools be written in Saw, not Python, and that the gaps be filed here. Each was hit while designing sawos's image builder (SO-95, tracker doc `SO:images-and-packaging`, section 11). Run against sawlang 0.23.0 (`sawc-stage2` and its `blade`), hosted on macOS arm64, by the design's author; "reproduced" means it was run, "read" that only the source was read.

- **Tried.** In the kernel (freestanding riscv32, `-Oz`), reproduced:

  ```saw
  @export("sos_slot_geometry")
  static SLOT_GEOMETRY: [UInt32; 2] = [sizeof<ProcessBody>() as UInt32,
                                       alignof<ProcessBody>() as UInt32]
  ```

  and separately

  ```saw
  static_assert(sizeof<ProcessBody>() == 804, "stale")
  ```

  `ProcessBody` is `kcore.pslot`'s; it holds raw-backed enums.
- **What happened.**
  ```
  ERROR static.not-constant `sizeof<ProcessBody>()` is not a constant, and
    a static's initializer is a constant expression:
    `kcore.pslot.ProcessBody` is laid out only by code generation, so
    `sizeof` and `alignof` measure it only in a `static_assert`; elsewhere
    they measure an integer, `Bool`, `Float`, `String` or a raw pointer
  ERROR slice.not-yet a layout this `static_assert` measures is not in the
    bootstrap slice yet: a raw-backed case whose value was not evaluated
  ```
- **Expected.** `sizeof<T>()` and `alignof<T>()` of any sized struct as a
  constant: in a static's initializer, and in a `static_assert`.
- **Why sawos needs it.** The per-board kernel exports each slab's slot
  size, so the builder can size the kernel's reserve and refuse an image
  that does not fit (SO-95 design section 6). The kernel already computes these at run
  time (`Slab.slot_bytes`).
- **How badly.** Has a workaround, which I ran: literal numbers per board
  in the exported table, compared with `slot_bytes()` at boot. That is a
  hand-kept table per board, made red by the gate's first boot when stale.

**Update from the sawos lead:** downgraded to nice to have. sawos can read each slab's size from the kernel ELF's symbol table, so no hand-kept number is needed. The entry as the design's revision 3 has it:

- **Tried (reproduced).** `sizeof<ProcessBody>()` in a static initializer,
  and in a `static_assert`.
- **What happened.**
  - `static.not-constant`: "... laid out only by code generation, so
    `sizeof` and `alignof` measure it only in a `static_assert`".
  - `slice.not-yet`: "a layout this `static_assert` measures is not in the
    bootstrap slice yet: a raw-backed case whose value was not evaluated".
- **Expected.** `sizeof` and `alignof` of any sized struct as a constant.
- **Why.** The kernel would export its slot sizes directly.
- **How badly.** Now has a workaround that keeps nothing by hand: the
  builder reads the slab statics' symbol sizes (rule 6.3). That workaround
  depends on the compiler's symbol spelling and `Slab`'s layout. Nice to
  have.

Lead (Nov 14): this issue owns making `sizeof`/`alignof` of a struct, enum, tuple or array a constant outside a `static_assert`. It is not an open question: SL:architecture §3.10 "`sizeof` of a struct in a constant position (Ruled, Sep 25)" makes it legal and names the spec text it overrides. SL-457's design (its Q4) keeps those positions refused by name until this lands, and gives primitives and pointers a value first (SL-457 U1). What this needs, from that design: layout callable from typecheck (`compiler/target` imports typecheck today) and a cycle rule for `struct A { x: [Int; sizeof<A>()] }`. It gets its own design pass when scheduled.
