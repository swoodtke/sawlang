**The seed leaves git: `compiler/seed/` keeps a manifest of SHA-256s, and the `.ll.xz` files are fetched from https://blobs.sawlang.com/ by hash.** This is SL-693's option 1, binary hosting. It also ends the 8 MiB patch problem, because a bump becomes a few-line manifest diff.

**The host (set up Oct 15, nothing to build there).** Caddy serves `/srv/blobs` read-only at `https://blobs.sawlang.com/<sha256>`, immutable cache, no listing. The upload path is ssh to user `blobs` with `.claude/blobs_upload_key` (git-ignored, on the lead's Mac only), whose `authorized_keys` entry forces `rrsync -wo -no-del -no-overwrite -munge /srv/blobs`. So an upload can only ADD a blob. An overwrite of an existing name is ignored and still exits 0, and macOS openrsync has no `--chmod`. The client therefore does `chmod 644 F; rsync -p -e 'ssh -i .claude/blobs_upload_key -o IdentitiesOnly=yes -o UserKnownHostsFile=.claude/linode_known_hosts' F blobs@blobs.sawlang.com:/` and then verifies by fetching the blob back over HTTPS and hashing it. A blob is never deleted: one orphaned by an abandoned bump is harmless.

**The change:**
1. **Manifest.** `compiler/seed/TRIPLE/` holds no `.ll.xz`. One tracked manifest (per target, or one file for all of them) lists each seed file's relative name, SHA-256 and size, in `build.seed_files` order. `compiler/seed/pin` is unchanged. Delete the committed `.ll.xz` files from the tree in the same patch. History keeps the old ones; rewriting it is out of scope.
2. **Fetch.** `build.py` resolves a seed file through ONE funnel. It looks in a content-addressed cache under `.build/` keyed by SHA-256 first, then fetches over HTTPS, verifies the hash and size, and publishes by rename. A hash mismatch or a fetch failure is an error naming the file, the URL and the expected hash, never a silent fallback. `seed_key` hashes the manifest's digests, so a warm cache needs no network. `build_seed`, `seed_files` and `seed.py check` all read through it.
3. **Upload.** `seed.py write` writes the files into `.build/`, uploads each one, verifies each by fetch-and-hash, then writes the manifest and the pin. A machine without the upload key gets a refusal that names the key. `tools/linux.py seed` brings the VM-written Linux files back to this checkout and uploads them from here, because the VM has no key.
4. **Consumer sweep (obligation 2: the seed goes from in-tree to fetched).** Check, at least: `compiler/tools/build.py` (`seed_files`, `seed_key`, `build_seed`), `compiler/tools/seed.py` (check/write and `check_path_free`, which reads the files), `tools/linux.py` (`seed`; the VM's `sync` clone must be able to fetch), `tools/patch_gate.py` (`compiler/seed/` as a gate input), `compiler/tests/fixpoint/fixpoint_lane.py`, `compiler/README.md` "The seed" (the bump procedure), `TESTING.md`, and CLAUDE.md's repo map. The server's gate must reach blobs.sawlang.com over HTTPS; confirm it can.

**Ordering.** The patch that deletes the in-tree seed must upload the CURRENT seed's blobs first and pin them in the manifest, so that `seed.py check` reproduces exactly as it does today. Land it after SL-662.p2 (the pending bump) so the files moved are the newest ones.

**Acceptance.** A cold `.build/` builds the seed from the fetched blobs, and `seed.py check` passes on all three targets. A corrupted cache entry is detected and refetched. A wrong manifest hash fails with a clear error. A bump patch's diff touches only the manifest and the pin.

**Open:** whether sawtracker (or any machine besides the lead's) gets its own upload key, added as another restricted line. Not needed for this unit.

**Air, pre-review of SL-694.** The shape is sound. The tracked manifest is the trust root, the blob host is untrusted storage, and an add-only upload key keeps old commits buildable. Five points for the unit:

1. **Keep `seed.py check` as the reviewer's control, reading fetched blobs.** On each bump I run `seed.py check`: it builds the pinned commit's IR and compares it with the seed. After this change, the seed is what the manifest's hashes fetch. A manifest and blob pair that isn't the pinned commit's output must fail that comparison. So `check` should resolve files through the same fetch funnel, against a cache it verifies on read. It must never read a `.build/` populated by `seed.py write` on the author's machine without re-hashing it.

2. **One base URL constant, with an environment override** (`SAWLANG_BLOB_URL` or similar, one funnel). The acceptance cases are a corrupted cache, a wrong manifest hash, and a failed fetch. Those can then run hermetically against a local directory or a throwaway HTTP server, instead of production or the network. A mirror also becomes a configuration change.

3. **Don't let an xz upgrade churn the manifest.** Blobs are keyed by the compressed bytes, but `seed.py check` compares decompressed IR. A different liblzma (this Mac's CLI is XZ Utils 5.8.4; seed.py's Python `lzma` links its own) can recompress unchanged IR into new bytes. Every file would then get a new hash and a new upload on the next bump. Suggestion: `seed.py write` keeps a file's existing manifest line when its decompressed IR is byte-identical to the current blob's, so a bump diff names only the files that really changed.

4. **Every builder needs HTTPS egress from now on:** the server's gate, the Lima VM's `sync` clone, any CI dispatch, and fresh developer clones. From this Mac, `https://blobs.sawlang.com/<absent-hash>` answers 404 in 0.17 s, so the host is up and reachable. One for the sawtracker lead: its production `.sawlang` root pins v0.13.0, which has the in-tree seed, so nothing changes there until a pin moves past SL-694's merge. That bump will need egress from production too.

5. **The gate inputs move with the files.** `tools/patch_gate.py` names `compiler/seed/` as a `fixpoint` and `grammarcorpus` input. After this, a bump touches only the manifest and pin under that directory, so the rule still fires. Please confirm the dry run says so (`./build.sh test --dry-run --diff` on a manifest-only diff).

**On the patch I'll check:**
- a cold `.build/` builds from fetched blobs on this Mac;
- `seed.py check` passes, 43/43;
- each injection fails with the file, URL and expected hash named;
- the manifest's hashes equal the current in-tree files' SHA-256s, so the move changes no byte;
- the diff deletes exactly the `.ll.xz` files it lists.
