Noticed by SL-897's agent (p897a). On MAIN TODAY, a plain read through a `borrows` accessor whose only declaration takes `&var self` lowers to `ref(shared, …)` in MIR. §3 says the root is charged EXCLUSIVELY for every use of a `&var self` accessor, reads included, because a shared narrowing is unsound when the prologue or epilogue writes `self` (two paused frames would each hold `&var self`). **Obligation 4 sweep before any fix:** probe whether borrowck still charges the root exclusively despite the shared MIR ref (a second shared read of the root inside the window must be refused), whether two such windows can be open at once, and whether an epilogue that writes `self` can then race. That is, is it only a MIR spelling, or a soundness hole? Positions: a statement read, an argument, a field read, a condition, a `for` head, a borrowing struct.

**Air, the obligation-4 sweep for SL-903, on main (24ef8d9a3):** every cell I could build is sound. The `ref(shared, …)` appears to be a MIR spelling that neither borrowck nor codegen reads. Probes are in `.build/scratch/air-review/sl903/` on the Air.

Each probe uses `H { v: Vector<Int> }` with one `func [](&var self, i: Int) borrows -> &var Int` whose PROLOGUE pushes 64 elements onto `self.v` (a reallocation), then `lend self.v[i]`. A shared charge would let the second prologue free the buffer an open window points into, and ASan would catch it.

| cell | position | main |
|---|---|---|
| s1 | `borrow let x = h.peek(0) { let y = h[0] }` (a plain read inside a shared window) | refused, `loan.window-root` 28:17: "`h` is borrowed exclusively here while the window of `peek` … holds `h` shared" |
| s3 | `borrow let a = h[0] { borrow let b = h[1] { … } }` (two windows of the accessor) | refused at 26:9: "the window of `[]` opened at 25:5 holds `h` **exclusively**" |
| s4b | `pair(borrow h[0], borrow h[1])`, both `&Int` (two windows spanning a call) | refused at 27:39: holds `h` exclusively |
| s5b | `mixed(borrow h[0], h[1])` (an open window, then a plain read) | refused at 26:40: holds `h` exclusively |
| s2 | `let y = h[0]` alone | runs: `y 7 len 2` at -O0 and -O2 (the prologue's push is visible after) |

**Where the `shared` spelling stops:**
- In s2's MIR, `main` declares `window w0: s2_plain_read_alone.H.[](i: Int) shared` and passes `_9 = ref(shared, _1)` to the prologue.
- The LLVM call is to `@"saw prologue …H.[](i: Int) receiver exclusive"(ptr noalias %p1, …)`. So codegen picks the exclusive instance from the declaration, and `noalias` is correct for it.
- Borrowck's messages say "exclusively" for the same window. Its charge must also come from the declaration, not from the MIR window kind.

**Not covered here:**
- the borrowing-struct and `for`-head positions;
- any MIR pass that reads the ref kind, such as the coroutine frame analysis or a MIR-level optimization.

If the fix makes MIR spell `exclusive`, MIR goldens move, and both of those are worth a grep for consumers of `RefKind.shared`. Otherwise a priority below "high" looks right, since no cell builds unsound.
