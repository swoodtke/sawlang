On MAIN TODAY, a plain read through a `borrows` accessor whose only declaration takes `&var self` lowers to `ref(shared, …)` in MIR. §3 says the root is charged EXCLUSIVELY for every use of a `&var self` accessor, reads included, because a shared narrowing is unsound when the prologue or epilogue writes `self` (two paused frames would each hold `&var self`). **Obligation 4 sweep before any fix:** probe whether borrowck still charges the root exclusively despite the shared MIR ref (a second shared read of the root inside the window must be refused), whether two such windows can be open at once, and whether an epilogue that writes `self` can then race. **Where the `shared` spelling stops:**
- In s2's MIR, `main` declares `window w0: s2_plain_read_alone.H.[](i: Int) shared` and passes `_9 = ref(shared, _1)` to the prologue.
- The LLVM call is to `@"saw prologue …H.[](i: Int) receiver exclusive"(ptr noalias %p1, …)`. So codegen picks the exclusive instance from the declaration, and `noalias` is correct for it.
- Borrowck's messages say "exclusively" for the same window. Its charge must also come from the declaration, not from the MIR window kind.

**Not covered here:**

If the fix makes MIR spell `exclusive`, MIR goldens move, and both of those are worth a grep for consumers of `RefKind.shared`. Otherwise a priority below "high" looks right, since no cell builds unsound.

**Air, a correction to my sweep (c2): one sibling position IS unsound.** My cells used a user accessor declared `&var self` only. An accessor that also carries a `@synthesize(shared)` form, such as std's `Vector.find` and `Vector.[]`, behaves differently in a `match` arm. The scrutinee is a read position, so it takes the shared form, while the arm's `var` payload binding writes through it.

- `match v.find(0) { case Some(var e) -> { borrow let x = v[0] { e.n = 5 } } }` is accepted, with `e` and `x` aliasing one element.
- The escalation is a heap-use-after-free in safe code: a reference into `e.items` taken through `x`, then `grow(&var e.items)`.
- It is on main in both old spellings, `match borrow` and `match borrow var` with `case Some(borrow var e)`, and in the new one.

Probes and the full table are in my SL-897.p1 verdict (`.build/scratch/air-review/sl897p/r/` on the Air: s6, s7, s9, t5, s9old_*). It's a different mechanism from this issue's MIR spelling: here borrowck itself reports the window as "holds `v` shared". It needs its own issue.
