## Description

**The executor's park words encode an address by negating it, which breaks on a 32-bit target whose memory lies above 2^31.**

**Found by** SL-933's `cooperative_deadlock` case on riscv32 (QEMU virt, RAM at 0x8000_0000). It panics with:

```
panic at taskgroup.saw:2263: executor: a task recorded park word 2146893788, which names no park
```

**Mechanism:**
- `Channel.park_word` is `0 - address of the ready word`. The park-word vocabulary reads a NEGATIVE word as "parked on this address" and a positive one above `PARK_TIMER` as no park (`Unknown`).
- On riscv32, `Int` is 32 bits, so every address at or above 0x8000_0000 is already negative, and negating it gives a positive word. Here 2^32 − 2146893788 = 0x8009_0024, an address in fsrt's arena.
- Hosted 64-bit targets are unaffected, since user-space addresses are below 2^63.

**Siblings (obligation 4; read from the code, UNVERIFIED until probed):**
- `__saw_exec_join_park` (`0 - word - 1`)
- `__saw_exec_offload_park` (`0 - job - 2`)
- `drive_until_set` (`0 - word`)

Each uses the same negated-address encoding. So on such a target every channel, join and offload park would mis-decode. That includes the sawos riscv32 and any 32-bit board with high RAM.

**Fix direction (for the brief):** an encoding that doesn't assume addresses fit in w−1 bits. For example, tag the low bits of a word-aligned address, or keep the reason and the address in separate fields. It goes through one encode/decode funnel with its ENTRY POINTS named.

**Pins:**
- SL-933's `cooperative_deadlock` riscv32 row, `due` on this issue until it lands.
- A riscv32 join-park case and a channel-park case in the freestanding suite.
- The hosted run lane's executor probes unchanged.
