**Local suite-lock runs yield to the server's gate: `suite_lock.sh acquire --yield-to-gate`** (proposed by the Air, chat m551; lead-approved).

- **Why:** the merge path waits on local runs. From today's merged gates (suite-lock wait / tests): SL-607 26m17s / 19m10s; SL-613 9m31s / 29m24s; SL-608 29m47s / 17m54s. A server gate that needs the lock queues behind an agent's local pin or step run. This is the merge path's single biggest cost now.
- **The rule:** `acquire --yield-to-gate` waits while the server's SL gate either holds the lock OR has a run queued. `sawtracker gate --project SL --json` reports both. It takes the lock only between gate runs, and re-checks right after taking it: if a gate run appeared, it releases and waits again. The gate's own acquire (`build.sh`) is unchanged.
- **Never starve the local run forever:** report the wait as the existing heartbeat does. If `sawtracker gate` can't be reached, fall back to the plain acquire, saying so.
- **Docs:** CLAUDE.md's suite-lock paragraph says local agent runs use `--yield-to-gate`. Its edit is one sentence; SL-622's patch also edits CLAUDE.md's per-commit paragraph, so expect a hunk merge. The lead's brief templates follow.
- **Pins:** `tools/test_suite_lock.py` gains cases with a stubbed `sawtracker gate`:
  - a queued gate run makes a yielding acquire wait;
  - an idle gate lets it take the lock;
  - a gate run that appears between the check and the take makes it give the lock back;
  - an unreachable tracker falls back, with the message.
- **Files:** `tools/suite_lock.sh`, `tools/test_suite_lock.py`, CLAUDE.md's suite-lock sentence, and TESTING.md if it describes the lock.

Requested changes on patch SL-632.p1 (revision 1)

Requesting changes on SL-632.p1 for one counting bug. The mechanism is right otherwise.
- The tracker is asked only when the lock is free, through one tool, `gate_status.py`: 0 idle, 1 busy, 2 unknown, so it falls back loudly.
- The holder re-checks after taking the lock and gives it back if a gate run became due.
- The gate's own acquire doesn't yield.

**`busy_runs` counts entries that will never run.** Since ST-91, `gate_view` puts a runner's held and superseded entries in the same `queued` array as the runnable ones, marked instead of omitted (sawtracker `src/store.saw`, in the gate runner view):
- **held:** `"held": "changes requested"`, with `position` and `eta` null. It stays held until a revision or an approval releases it, or it's dropped when it reaches the front;
- **superseded:** `"superseded": <reason>`, with `position` null, which `gate_next` drops at its next pick.

`busy_runs` appends every entry whose `project` matches, so a single held SL patch anywhere in the queue makes every `--yield-to-gate` acquire report 'busy' until that patch is revised. Under the user's review process (m539) I request changes on sight, so held entries will be common, and local runs would yield to runs that aren't coming. The live gate has none queued at this moment (`totals.held` 0), which is why it doesn't bite yet.

**Fix:** count a queued entry only when it's runnable, that is when neither `held` nor `superseded` is set (equivalently, it has a `position`). Name the held ones in the message if you like (`… 1 held: SL-612.p1`) without counting them as busy. Add a `test_suite_lock.py` case whose `SAW_GATE_STATUS_CMD` reports one held and one superseded entry and nothing running: the acquire must take the lock at once.

**A note, not a request:** a runner that's down with runnable entries queued would make local runs wait indefinitely. The five-minute heartbeat names the queued runs, so it's visible rather than silent, which is enough for now.

**Gate:** not waited for, under the user's review process (Oct 13); this doesn't depend on it.
