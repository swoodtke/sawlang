## Description

A `&var arr[i]` argument, where `arr` is a `[T; N]` LOCAL of a body that suspends, mutates a copy: the callee's write is discarded and the element reads back unchanged. Silent -- exit 0, no diagnostic. The SYNC twin of the same code is correct, and a frame-resident STRUCT FIELD (`&var h.doc`) is correct too, so the defect is specific to the fixed-array element read in the coroutine path.

Repro (single file, no modules), compiled with main 88fa56ba / d0e38f90:

  import std.task.{yield_now}
  struct Doc { n: Int }
  func slow() -> Int { yield_now()  7 }
  func set_one(d: &var Doc, k: Int) { d.n = d.n + k }
  func driven() -> Int {
      var arr: [Doc; 3] = [Doc(n: 0); 3]
      let k = slow()
      set_one(&var arr[1], k)
      arr[1].n
  }
  func sync_control() -> Int {
      var arr: [Doc; 3] = [Doc(n: 0); 3]
      set_one(&var arr[1], 7)
      arr[1].n
  }
  func main() { print(__saw_drive(driven()))  print(sync_control()) }

Observed: 0 then 7. Wanted: 7 then 7.

Note the suspending call is HOISTED into its own `let` here, so no ANF lift is involved -- the shape is plain 'frame-resident fixed array, borrow one element, call through it'.

MECHANISM (hypothesis, not yet confirmed against the IR): `arr` is frame-resident and lands on design 218's legacy 'fixed-array' deferred family rather than a `Slot<T>`, and `_address_taken` records it. The suspicion is that the frame READ for that family produces a VALUE (a copy of the array) where `&var arr[1]` needs the field's storage, so the address handed to the callee points into the copy. A struct field's read does not go that way, which is why `&var h.doc` is correct in the same body.

Found while sweeping SL-223's sibling shapes (obligation 4). It is INDEPENDENT of SL-223: it reproduces on unmodified main with no ANF lift in the picture, and SL-223's fix neither causes nor cures it. SL-223's branch therefore pins only the ORDER of the impure-index cell, not its value, and cites this issue.
