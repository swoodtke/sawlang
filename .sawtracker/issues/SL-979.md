## Description

**`match` lowering's decision tree grows steeply with mixed arms; a 350-arm `match` exhausts memory.** Found by the Air after SL-970 unit 3 (SL-970 comment, chat m667, repro f35 `m0089_250.saw`). Main's compiler grew past 20 GB on generated programs before it was stopped.

**Evidence** (unit 3's compiler, `mir --check`, the first K arms of one generated `match` over an `Int` plus its catch-all; arms mix literals, ranges, guarded wildcards like `case _ if x % 3 == 0`, and duplicate literals):

| arms | ranges | guarded | peak memory | `pick`'s MIR blocks |
|---:|---:|---:|---:|---:|
| 150 | 20 | 64 | 0.05 GiB | 25,063 |
| 200 | 25 | 90 | 0.25 GiB | 61,363 |
| 250 | 30 | 120 | 0.83 GiB | 246,368 |
| 300 | 37 | 155 | 2.07 GiB | — |
| 350 | 46 | 187 | over 4 GiB, killed | — |

At 250 arms the one function is 1.39 million lines of MIR. Typecheck peaks at 0.05 GiB throughout.

**Mechanism (the Air's reading, UNVERIFIED):** a row with no cell at the tested place goes down both edges of every test. That covers a guarded wildcard, since `_` simplifies away, and a range, which compares with no literal. A tree built from such rows copies each of them into every subtree of every earlier test, and each guard's false branch compiles the rows after it again. The tree's size then multiplies with the mix.

**Direction:** bound the code size of `match` lowering, keeping the arm semantics and diagnostics. Options:
- share identical subtrees: a DAG, memoised on (remaining rows, tested places);
- compile rows that take both edges by backtracking, falling through to the next row instead of duplicating it;
- a hybrid: a decision tree over literal columns and backtracking past guards and ranges.

Measure code size and compile time against arm count for each, and pin it with a complexity-lane shape (a mixed-arm `match`).

**Identity:** program behaviour must stay the same, but the MIR shape and IR will change. Golden MIR or IR dumps of `match` move once, reviewed.

**SL-979 unit B: `match` lowering stays linear with guarded ranges and guarded literals**

- **The rule** (`compile_rows` in `compiler/mir/src/lower.saw`): the decision tree keeps testing decided rows. It cuts at a guarded row or a row with an undecided cell (a range), and the code after the cut falls through to the remaining rows instead of copying them. A guard's false edge continues in the same loop instead of recursing, so neither a cut nor a guard copies the rows after it.
- **Measured** (unit A, on SL-979): K guarded ranges doubled the tree per arm, and 350 mixed arms passed 4 GiB. Now 6,400 mixed arms lower in 0.6 s. The new lane row is `match_mixed 1600 2.20 0.10`; main's compiler passes 4 GiB on it at N=100.
- **Behaviour:** 1,007 programs (300 random, 300 printing every guard call and payload drop, and the 407 corpus programs holding a `match`) are identical to main in exit status, compiler stderr and stdout.
  - The Air's `guard_trace` probe is committed as `probes/match_guard_order.saw`: guard order and count, a NoCopy payload dropped once behind failing guards, and a suspending guard in a task. It is byte-identical at -O0, at -O2 and under ASan.
- **Golden MIR:** exactly 4 functions move, reviewed one by one.
  - `matches.pairs` really changes: one shared copy of its guarded tail, and each place tested once per path.
  - `matches.area`, `leftovers.guarded` and `short_circuits.guarded` only reorder, because a guard's true edge is now emitted first.
  - No std function moves. All-literal matches are byte-identical.
- **Gate:** `run.py --only seed,units,golden,subset,fixture_whitespace,std,mir,programs,complexity` passed apart from the probe's missing `// stage 0:` line. The lead added that line and leaves the rerun to the server.

**Theory (UNVERIFIED):**
- `cut_at` cuts only at a guarded row or one with an undecided cell.
- An unguarded `(_, v)` row has no cell at `p.0`, so it goes down both edges of every `p.0` test, and lands in each literal's true edge in `split_literal_chain`.
- Each `(v, w)` row then compiles a `p.1` chain over all those copies, and so does each guarded `(v, _)` row on its false edge: O(rows × rows).

**Two experiments would confirm it:**
1. Cut at every undecided row for tuple places, as in backtracking, and see `wild` go linear.
2. Drop the `(_, v)` rows from `wild`, and see the hybrid's block count go linear.

The fix then picks a rule that bounds this without repeating tests on paths where the answer is known. Its candidate is a middle rule: cut an unguarded wildcard row when rows before it carry further cells or a guard. It adds `wild` as a complexity-lane shape.

Approved patch SL-979.p1 (revision 1)

**Air: SL-979.p1 (unit B), approved.** The memory blow-up I found is gone, and nothing I can see moved in behaviour.

**Read:**
- **The cut:** rows before a guarded or undecidable row compile as a sub-match whose falls all go to one shared fail block, and the rest compile once from there, in order. So first-match order holds, and no row is copied per edge.
- **Nested cuts** save and restore `state.fail`. A cut whose sub-match never falls returns, rightly leaving the later rows unreachable.
- **A guarded leaf** continues on its false edge in the same loop, over the same rows the old recursion took (`simple[start+1..]`).
- **Bindings:** guards still read their bindings through references, and only the taken arm decides what's left over.

**Measured, one process at a time:**
- **Memory:** the generated programs that passed 4 GiB in `mir` on main (m0089 cut at 150, 250, 350 and 399 arms, and two full 400-arm programs at `--emit-ll`) now peak at 0.05 GiB in 0.2 s each.
- **My guard-trace baseline** (`sl979/guard_trace.saw`, which is your `match_guard_order.saw`) is byte-identical to main's output at -O0, at -O2 and under `--sanitize address`:
  - guard order and count;
  - a NoCopy payload dropped once behind failing guards;
  - a suspending guard in a task.
- **600 random `match` programs** (3–60 arms; `Int`, tuple, `String` and `Int?` scrutinees; literal, range, guarded and duplicate arms), against main. 81 emit identical IR. 519 emit different IR, and each was built and run on both compilers with the same output and exit status. 0 differ in behaviour.
