## Description

**A type whose size in bytes does not fit `Int` panics sawc on the host, and at riscv32 is accepted with a wrong size.** Found by SL-457's U4 detail pass (Nov 14; `.build/scratch/p457u4/extra.tsv` rows h01 to h03, `one/h03b.riscv.txt`, in the lead's checkout). Plain programs, no generics.

- `struct S { d: [UInt64; 2305843009213693952] }`, or `[0u64; 2305843009213693952]`: sawc panics at `compiler/target/src/layout.saw` (`l.size = el.size * lt.a`): the layout funnel multiplies in the compiler's own `Int` unchecked. `record`, `laid_cases` and `target_align_up` add sizes unchecked the same way (by reading).
- At riscv32, `[UInt32; 1073741824]` (4 GiB, past a 32-bit `Int`) is not refused: `sawc mono --check` passes, and `static_assert(sizeof<S>() == 0)` FAILS where the type should have been refused (the size it measured is UNVERIFIED).

**What SL-457's U4a does about it:** a guard in the layout funnel turns the panic into an error with the "not in the slice yet" family's wording (a backstop, so a symbolic length that comes out huge cannot crash the compiler). That wording promises a fix that is not coming; this issue is for the real rule.

**The rule to design (the U4 detail's Q-S, default taken by the lead):** `constant.overflow` ("a size counts bytes in an `Int`"), reported at the array type's length where typecheck can measure the element (a target-fixed element type), and at the instance in mono otherwise; every size computation in the layout funnel checked against the TARGET's `Int`, not the host's. Sweep: arrays of arrays, a struct of large arrays whose sum overflows, an enum's payload, a tuple, alignment padding that tips a size over, `sizeof` of each as a constant, and the same at riscv32 and the two 32-bit freestanding targets.
