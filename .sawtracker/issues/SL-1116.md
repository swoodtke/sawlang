## Description

**A type whose size in bytes does not fit `Int` panics sawc on the host, and at riscv32 is accepted with a wrong size.** Found by SL-457's U4 detail pass (Nov 14; `.build/scratch/p457u4/extra.tsv` rows h01 to h03, `one/h03b.riscv.txt`, in the lead's checkout). Plain programs, no generics.

- `struct S { d: [UInt64; 2305843009213693952] }`, or `[0u64; 2305843009213693952]`: sawc panics at `compiler/target/src/layout.saw` (`l.size = el.size * lt.a`): the layout funnel multiplies in the compiler's own `Int` unchecked. `record`, `laid_cases` and `target_align_up` add sizes unchecked the same way (by reading).
- At riscv32, `[UInt32; 1073741824]` (4 GiB, past a 32-bit `Int`) is not refused: `sawc mono --check` passes, and `static_assert(sizeof<S>() == 0)` FAILS where the type should have been refused (the size it measured is UNVERIFIED).

**What SL-457's U4a does about it:** a guard in the layout funnel turns the panic into an error with the "not in the slice yet" family's wording (a backstop, so a symbolic length that comes out huge cannot crash the compiler). That wording promises a fix that is not coming; this issue is for the real rule.

**The rule to design (the U4 detail's Q-S, default taken by the lead):** `constant.overflow` ("a size counts bytes in an `Int`"), reported at the array type's length where typecheck can measure the element (a target-fixed element type), and at the instance in mono otherwise; every size computation in the layout funnel checked against the TARGET's `Int`, not the host's. Sweep: arrays of arrays, a struct of large arrays whose sum overflows, an enum's payload, a tuple, alignment padding that tips a size over, `sizeof` of each as a constant, and the same at riscv32 and the two 32-bit freestanding targets.

**Finding during the sweep (Nov 18): a type at the edge of `Int` crashed the machine twice.** `func make() -> [UInt8; 9223372036854775807] { panic("never") }` (a `[UInt8; Int.max]`, whose size fits a 64-bit `Int` exactly) is accepted by sawc on the host, and its IR sends clang at `-O0` past 100 GB (the owner watched it), out of memory; both crashes today were the sweep reaching this cell (`.build/scratch/p1116/p/arr_edge.lay.w64.saw`; its emitted IR `out2/arr_edge.lay.w64.host.bin.ll`). So "fits in `Int`" is not the bound that matters: an object the target cannot address or lay out (a stack frame, a global) is the real limit, and the rule must refuse it at sawc, never hand it to clang. The design question for this issue grows: the size limit is the target's addressable object size (e.g. what LLVM accepts for an alloca or a global on that target), not `Int.max`; say which bound, per target, with evidence from `--emit-ll` (never from running clang on such IR).

**Sweep safety rules from here (every agent on this issue):** never run clang (no `build`, no `-c`) on a type whose size is within reach of the limit; probe with `typecheck --check`, `mono --check`, `mono --layouts` and `--emit-ll` only, one at a time, each under a time limit; read the IR as text. A sawc process that starts clang must not be left running unattended.

**The sweep is done (Nov 18; `.build/scratch/p1116/sweep.md` in the lead's checkout; 316 programs on four targets, no clang run, peak 101 MB):** the description's premise is stale. SL-457's U4a guard already checks every size operation in `compiler/target/src/layout.saw` against the target's word (`size_limit()`, `holds_bytes`): nothing panics and nothing is mis-sized; the riscv32 4 GiB cell is refused. What is wrong: (1) the RULE: `typecheck --check` and `mono --check` accept every oversize type, `build`/`--emit-ll` refuse it as `backend.not-yet` (`lay_at`, `compiler/llvm/src/prims.saw`) and a `static_assert` measuring it as `slice.not-yet` (`asserts_verdict`); `constant.overflow` is never reported; (2) the EDGE: `holds_bytes` requires `n <= limit - align`, so a struct, tuple, enum, `Optional` or `Buf<Int.max>` whose size fits is refused; (3) `compiler/asserts/src/layout.saw` silently skips a memory view of a type whose layout is unsupported. And the crash: a type sized exactly `Int.max` (`[UInt8; Int.max]`) is accepted and emitted (`alloca [9223372036854775807 x i8]` plus a `memcpy` of that length), and clang then passed 100 GB.

**Lead's ruling (Nov 18):**
1. **Phase B goes ahead** on the rule, the place and the edge: one checked-size funnel taking the target word (ENTRY POINTS: the array case, `record`, `laid_cases`, `flagged`, `tagged`), replacing `holds_bytes`, accepting the exact edge for records, tuples, enums and `Optional`, and returning a distinguishable overflow kind; `lay_at` and `asserts_verdict` report `constant.overflow` from it.
2. **Where:** at the mono instance, for every shape (no new typecheck-to-target dependency; `compiler/target` imports typecheck). A length literal past the target's `Int` is already refused at the literal.
3. **The message** names the type and says its size does not fit the target's `Int` (e.g. "the type `S` is larger than `Int` counts on this target"), in `constant.overflow`'s family.
4. **The silent skip** in `compiler/asserts/src/layout.saw` is the same mechanism (a layout the funnel refuses, read as "nothing to check"): in scope; it refuses through the funnel.
5. **The bound** (whether the limit should sit below `Int.max`, since a size-`Int.max` stack object breaks clang) is a question for the owner, filed apart with a measurement (SL-1163): this patch keeps the target's `Int` as the bound.

Requested changes on patch SL-1116.p1 (revision 1) (its test run was cancelled)

**Changes requested: the coroutine frame is a second layout the funnel does not reach, and it shows both of the issue's symptoms; the alignment check has no fixture. The funnel itself, the rule at mono and the exact edge hold.** Every probe here is `coro --layouts`, `mono --check` or `--emit-ll`, one at a time under a time limit; nothing was built (f393, which must never be built either).

**1. The coroutine frame overflows outside the funnel.** `coro_lay_out_frame` lays out each value through the funnel, but sums the frame itself in its own unchecked arithmetic (`v.offset + v.size`, `coro_assign`'s placement and sort key, `coro_held_bytes`, `coro_align_up`). So a frame of values that each fit can overflow:
- **The host compiler panics.** A suspending function with one local of 2^62 bytes, live across a `yield_now()`, ends `coro --layouts` and `--emit-ll` with `panic at layout.saw:205: integer overflow`: `coro_assign`'s sort key `(biggest - values[k].size) * n + k`. So `build` dies there, before clang. v0.24.3 does the same; `coro --check` passes because it never lays a frame out.
- **riscv32 accepts a wrong size.** Two locals of 2^30 bytes each, live together across the suspension, fit riscv32's `Int` one by one; the frame does not. `--emit-ll` emits it: the task's frame descriptor records the size as `i32 2147483656`, and the second local sits at `getelementptr ... i32 2147483652`, both past `Int32.max`.

That is the issue's own description (a panic on the host, a wrong size accepted at riscv32), in a layout this patch does not route through `size_sum` and `size_aligned`. The frame wants the same checked arithmetic against the target's `Int`, and `constant.overflow` naming the function, with a fixture for each half.

**2. `size_aligned`'s overflow check has no fixture.** With it unchecked (`n + align - rem`), all 18 mono refusals, the 3 typecheck refusals and the four exact-size edges still pass (f394). Your padding fixture's overflow falls in the sum, after the padding. My two cells overflow only by a struct's trailing padding: `{ w: UInt64, b: [UInt8; 2^63 - 11] }` on the host and `{ w: UInt32, b: [UInt8; 2^31 - 7] }` at riscv32. The patch refuses both `constant.overflow`; with the mutant, the host compile panics at `layout.saw:547` and riscv32 accepts.

**3. Smaller: a static's type passes `mono --check`.** `unsafe static var BIG: [UInt64; 2^61]`, read in a function, is accepted by `mono --check` and refused only by `lay_at` at `--emit-ll`. The ruling puts the rule at mono for every shape, so either catch a static's type there or say that a static is the backstop's.

**What holds.**
- **Mutants** (f394, 11, each rebuilt): 9 red: both edges at `>=`, the sum and the product unchecked, the target's limit replaced by the host's, the overflow flag unset, mono's refusal off, the depth rule keeping size refusals, and the memory view skipping. Besides point 2's, `elements_bound_gone` passes and is equivalent: a length past the target's `Int` is refused at the literal (`[(); 4_294_967_296]` at riscv32 is `type.mismatch`), so the bound has nothing to catch.
- **Positions:** a generic body's `sizeof<T>()` instantiated with an oversize type, and an oversize element reached only behind a pointer and indexed, are each refused at mono at their call.
- **The fixtures** match their headers, and the four exact-size edges are accepted on their triples.
