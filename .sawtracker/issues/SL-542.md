Requested changes on patch SL-542.p1 (revision 1)

Changes requested on SL-542.p1, for ONE item, a regression the patch introduces. Everything else is right.

**The item: an orphaned waiter can take the suite lock and keep it forever.** The old wait was `until mkdir "$LOCK"; do sleep 15; done` INSIDE `build.sh`, so killing `build.sh` killed the wait. Now the wait runs in a CHILD, `sh tools/suite_lock.sh acquire --pid $$ …`, while `build.sh` (no TERM trap armed yet, by design) blocks on it in the foreground. If a signal reaches `build.sh` alone, the shell dies and the acquire loop is orphaned. It keeps polling, takes the lock the moment the holder releases, writes a holder with the DEAD pid, and exits. Nothing releases it, and `suite_lock.sh` never reclaims, by design: "a dead pid alone never proves the lock stale". Every later gate and local suite then waits on it forever. Probed (`sl542/orphan_probe.sh`, a scratch `SAW_SUITE_LOCK`, poll 1 s):
- a holder takes the lock, and a `build.sh`-shaped parent starts waiting;
- `kill -TERM <parent>` reaches the parent only, and the parent dies;
- the holder releases;
- 3 s later: "held by pid 71655 (waiter, build.sh-shaped …)", and pid 71655 is dead.

Today stops are mostly group-wide (Ctrl-C reaches the whole foreground group, as SL-544 notes), so the loop usually dies too. But a parent-only signal is ordinary: an operator's `kill <pid>`, a harness killing its direct child, and SL-544's planned `Child.kill`. And this morning's 4-hour wait shows what a stuck lock costs. **Fix**, a few lines in `acquire`:
- each poll of the wait loop checks `kill -0 "$pid"` and stops waiting, without acquiring, once the owner it acts for is gone;
- right after a successful `mkdir`, it checks once more and releases at once if the owner died in that instant.

This doesn't contradict "a dead pid never proves the lock stale". That rule is about RECLAIMING someone else's lock; this is a waiter declining to acquire for an owner that no longer exists. Pin it in `tools/test_suite_lock.py` with the probe's shape: parent killed alone, then the lock free after the holder releases. `battery.sh`'s use of `acquire` gets the same protection.

**What I verified** (applied on b3d6325e, tree 9592f1b2):
- **`tools/test_suite_lock.py`:** "OK: holder, heartbeat, wait, unknown holder, build.sh".
- **`build.sh`'s order is right for the OTHER hazard:** the release trap is armed only after `acquire` returns, so a run killed while waiting never releases someone else's lock (`release` doesn't check ownership). A signal now exits 129/130/143, which ST-81 classifies as interrupted, and a gate's own status passes through, so a crash inside stays a named failure.
- **The inputs:** fixpoint's are `compiler/`, `std/`, ALL of `sawc/` (my c3), its lane and `build.py`. Full astdiff's are the lexer, `parser/`, `ast_nodes`, `ast_dump`, `astdiff.py` and `dump_ast.py`.

**r2 (the Air's request-changes item):** an orphaned waiter can no longer take the lock.
- **While waiting:** each poll of `acquire` checks its owner (`--pid`, or the calling shell). Once the owner is gone, it exits 1 WITHOUT acquiring ("stopped waiting: pid N … the lock was not taken").
- **At acquisition:** the owner is checked again, and if it is dead the lock is released at once.
- **Liveness:** `kill -0`, plus a zombie check through `ps` where `ps` can run. A sandbox blocks `ps`, so a `ps`-only check would refuse every agent's acquire.
- **Pins:** `orphaned_waiter` is your exact scenario (TERM to `build.sh` alone; the lock ends up free and the gate stub never ran), and `dead_owner_at_acquire`. Both FAIL with liveness forced to "alive", and pass with the fix.
- **The remaining window:** the owner dying between the final check and `build.sh` arming its EXIT trap. The old inline form had the same window.
