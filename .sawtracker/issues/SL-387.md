## Description

Found by the SL-345 implementer (Sep 24); present before SL-345. Silent wrong behavior in synchronous code: the outer closure captures total BY VALUE (a copy), and the inner [&var total] borrows that copy, so the increment never reaches the enclosing binding. The program exits 0 printing 0. Mechanism: a design-132 hole in the closure checker. A written &var capture inside a nested closure resolves to the enclosing closure's value capture rather than being refused or forcing the outer capture to be a reference. Sweep: nesting depth 2 and 3; [&var x] vs [&x] (reads are fine but stale?); outer escaping vs non-escaping; the driven twin (SL-315 is the driven cousin). Fix direction: an inner by-reference capture of a name the outer closure captures by value is either an error naming the outer capture, or makes the outer capture by-reference. That's a language rule, so it needs a ruling.

Closed by the SL-1064 reconcile sweep (agent preconcile, Sonnet; Nov 12), re-probed against `sawc` at main eb43124e8.

**Verdict: FIXED.**

- **The rule:** LANGUAGE_SPEC.md:9825-9831 "Captures are `let`. A plain, `move` or `copy` capture is an immutable binding inside the closure's body ... The only way a closure changes state outside its body is a borrow capture, `[&var x]`, which only a closure passed directly to a non-escaping parameter may take. Every write shape is refused on a by-value capture: `x = v` ... and `&var x`."
- **What `sawc` does:** SL-387.saw (`run({ run({ [&var total] in total = total + 1 }) })`, -O0 and -O2): "ERROR mutability.immutable SL-387.saw:9:33 this assignment writes `total`, and `total` is captured by value, which makes it a `let` in the closure's body: to write the caller's binding, capture it with `[&var total]` ..." and a second error at 9:18 "this exclusive borrow of `&var total` would let it be written". The program no longer builds, so nothing prints 0. SL-387_c.saw: depth 3 (15:39), an ESCAPING outer (22:37, "an escaping closure keeps no state that changes across calls ... share the state as an `Arc<Mutex<T>>`") and the driven twin (31:33) are each refused with `mutability.immutable`. SL-387_b.saw (the legitimate spelling, the outer also `[&var total]`): depth 2 -> "depth2 total 1", depth 3 -> "depth3 total 2" at -O0 and -O2 (writes land through the chain). SL-387_d.saw (`[&total]` shared inner borrow of the outer's by-value capture, a read): "shared read 5" at -O0 and -O2.
- **Note:** Every cell of the issue's sweep matrix ran: depth 2 and 3, [&var] vs [&x], outer escaping vs non-escaping, the driven twin. The issue said the fix "needs a ruling" (error vs make the outer capture a reference); the spec text above already is the ruling and sawc refuses, so the outcome is the first option.
