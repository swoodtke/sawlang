## Description

**`std.channel` used only between OS threads still links the task executor.** SL-965's sibling: its census measured 129 `std.taskgroup` functions in a program whose channel is used only between threads, even with SL-965's thread prototype applied (`.build/scratch/p965/design.md`, the `channel_threads` probe).

**Mechanism (from the census):** a thread-context receive goes through `__saw_exec_await_word`, and a send or close wakes through `__saw_exec_chan_wake`. Both are the executor's.

**Direction:** the same as SL-965's. The channel's thread path uses the thread primitive, and the executor adds its task-side waiting through an observer, so a program with no executor pays nothing for it. Pinned by a cone fixture, `channel_between_threads.saw`, that refuses the executor's seams.

**Depends on** SL-965 unit 3, which provides the thread module and the observer pattern.

**Scope note (lead, from the user's question): channels stay one primitive for both engines.** Nothing here takes channels away from tasks.

How `std.channel` waits today:
- **In a task,** `receive` parks the task on the channel's readiness word, through the executor (`__saw_exec_channel_park`, `__saw_park_channel`).
- **In thread context** (a `Thread.spawn` body or a `blocking` function), `receive` waits on a pthread mutex and condition variable, and keeps running that thread's own tasks while it waits (the pairing rule, spec "Blocking functions"). That is why it goes through `__saw_exec_await_word`.
- **`send` and `close`** wake both kinds of waiter through `__saw_exec_chan_wake`.

**The change:** the task-side parts become a hook the executor installs:
- parking a task;
- running a thread's own tasks while it waits;
- waking a parked task.

A program that uses a channel only between threads with no tasks then waits and wakes with the mutex and condition variable alone, and links no executor. A program with tasks behaves exactly as today. The pins:
- the cone fixture `channel_between_threads.saw`, with no executor seams;
- the existing task and mixed channel probes, unchanged.

**SL-967.p1: a channel used only between OS threads links none of the task executor**

- **The seam** (SL-965's observer pattern): a channel's thread-context wait and its send/close wake go through `std.thread`'s observer, which only the executor installs, in `this_executor`.
  - `ThreadEvent` gains `AwaitWord` and `WordSet`. The observer answers a `Bool`: whether the executor waited the word out by running the thread's tasks.
  - `notify_observer` is the one funnel.
  - `std/channel.saw` has one funnel per direction (`wait_ready`, `wake_receivers`), keeping the old order: observer first, then the gate broadcast.
  - `__saw_exec_chan_wake` is deleted, and `__saw_exec_await_word` is module-private.
- **Why skipping is sound:** a thread's executor record is set only in `this_executor`, which installs the observer right after, on that same thread. A thread that sees no observer has no record. A sender that sees none wrote its word before the install, and every executor waiter reads the word after it. The full argument is in `.build/scratch/p967/design.md`.
