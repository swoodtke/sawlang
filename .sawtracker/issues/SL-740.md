- `Vector<String>.join(separator:)`, which SL-717 batch 2 could not port: the seed's Stage 1 build refused std/string.saw at the extension head.
- 5 Blade/libs files call `.join(`.
- Corpus: 2 rows refuse on the specialized extension itself and 1 on the missing `join` (`alloc_string_no_degradation`, `string_split_join`, `extension_specialized`).

**Scope (Opus):**
- A specialized extension's members resolve only on the matching instantiation; the matrix covers a concrete arg, a nested generic arg, and a member call on a non-matching instantiation, which must refuse cleanly.
- Mono instantiates them like any other member.
- Conformances in a specialized extension follow the spec, or are refused with a clear message if the spec leaves them planned.
- One funnel for the "does this extension apply to this receiver type" question, which names its entry points.
- Then port Stage 0's `join` into std/string.saw (Sonnet, SL-717 tail).

**SL-740.p1: the compiler half of specialized extensions. Summary for review.** No std edits: `Vector<String>.join` follows as a seed bump plus std in one patch, once this lands.

- **The rule** (spec vs Stage 0; the agent's table is in its report):
  - a concrete head (`Vector<String>`, defaults filled) is supported;
  - a nested argument in the head is a parse error (the grammar allows a name only);
  - a partially concrete head (`Pair<Int, T>`) is spec-planned, and refused with its own rule, `extension.partial-specialization` (Stage 0 misreads it as a parameter named `Int`);
  - a conformance in a specialized extension is spec-silent, so planned, and refused as `extension.specialized-conformance`;
  - a call through a generic `T` instantiated to the matching type doesn't resolve (a generic body is checked against its bounds), giving `member.unknown`.
- **The funnels** (`signatures.saw`), each naming its ENTRY POINTS:
  - `extension_applies`: members_for, member_place, construction_candidates, extensions_disjoint, and mono's glue_member and member_with;
  - `ext_self_type`: `Self` is the concrete type.

  A non-matching instantiation is a clean `member.unknown` (an `init` there is `call.label`, from the memberwise candidate). Mono needed no change.
- **A bug found and fixed:** an extension written BEFORE its type read the type's parameter entries as its own (`ensure_generic_list`). That dropped a bounded extension's bounds, so the seed wrongly refuses `extension Cell<T: Equatable>` placed before `struct Cell`. Pinned by `type.bound.extension-before-type`.
- **Pins:**
  - the run program `specialized_extensions` (with a Stage 0 record, at -O0 and -O2): methods, `&var self`, `Wrap<Int>`/`Wrap<Point>`, a nested receiver, a generic member beside specialized ones, two specializations sharing a name, a generic method inside one;
  - the probe `specialized_extension_statics` (statics both spellings, `init`, `Self`, an enum head);
  - fixtures for every refusal; the `slice.not-yet` fixture deleted; the README rows updated.
- **Corpus:** `extension_of_imported_type_with_spawn` → pass; `errors/specialized_method_wrong_type` stops later at `join`; `extension_specialized`/`string_split_join`/`alloc_string_no_degradation` stop at `join`'s absence (expected until the std half). None to `wrong`.

Approved patch SL-740.p1 (revision 1)

**Air: SL-740.p1 r1 approved; arming it.** Specialized extensions work through the two named funnels (`extension_applies`, `ext_self_type`), and the planned forms are refused by their own rules.

**Probes** (on 828a95965 = main + r1, both stages rebuilt; -O0 and -O2 identical):
- `air-review/sl740/owning_spec.saw`: an `extension Wrap<Res>` over a NoCopy payload with a printing `deinit`. `peek` reads 1; `bump` (a `&var self`) gives 11; `swap_in` drops the old payload at its assignment (`drop 11`) and returns 11; `peek` reads 2; and the new payload drops once at the end (`drop 2`).
- `two_specs.saw`: two specializations each declaring `static func seven()` and `func label()`. `Wrap<Int>.seven().label()` gives `int` and `Wrap<String>.seven().label()` gives `string`. A bare `Wrap.seven()` is `call.ambiguous`, which is right, since the bare head names neither.

**Checks:** `run.py --only typechecker,golden,resolver,mono,std,programs,subset` ok. `corpusdiff.py gate --no-build`: all 2661 hold. The `ensure_generic_list` fix (an extension written before its type) is pinned by `type.bound.extension-before-type`.

**Two notes for a follow-up, not blocking:**
1. **The declared slot doesn't pick a specialization.** `let s: Wrap<String> = Wrap.seven()` is also `call.ambiguous`, although the slot names exactly one specialization. Under SL-657's ruling, the declared slot tells a bare generic head which instantiation it is (`let g: G<Int> = G.empty()` runs), and a reader would expect the same here: the slot says `Wrap<String>`, so the call is `Wrap<String>.seven()`. Refusing is conservative, and lifting it is additive. Probably a question for SL-751's ruling on how far the slot reaches.
2. **The ambiguity names its candidates indistinguishably:** `Wrap.seven() [two_specs]; Wrap.seven() [two_specs]`. With specializations in play, the candidate text should carry the head (`Wrap<Int>.seven()`, `Wrap<String>.seven()`). Otherwise the fix the message asks for ("write … type arguments that pick one") has nothing to point at.
