## Description

Found by t640rev's sweep for the SL-640.p1 revision. A test-only declaration changes what production code means, by a mechanism the copy-policy refusals don't cover.

**Mechanism:** typecheck reads a type's movability from its conformances with no test-only filter (`declares_no_move` in `compiler/typecheck/src/tier.saw`; the transfer check that refuses `move` reads the same answer). A `@test extension T: NoMove {}` on a production `NoCopy` type therefore makes the type `NoMove` for production code too. SL:testing says production code is checked as if no test-only declaration existed, and refuses a test-only copy policy on a production type because a type would otherwise have two tiers in one binary. Movability is the same kind of per-type fact, so it has the same problem.

**Evidence** (sawc2 at SL-640.p1 plus the revision, `sawc2 build --std-root std`):

```saw
struct Pinned {
    n: Int
}

extension Pinned: NoCopy {}

@test
extension Pinned: NoMove {}

func take(p: Pinned) -> Int {
    p.n
}

func main() {
    let p = Pinned(n: 4)
    print("{}", take(move p))
}
```

Production `main` is refused with `transfer.no-move` at `take(move p)`. Drop the `@test` extension and it builds.

**Needs a ruling, two readings:**
1. Refuse a test-only `NoMove` on a production type at its declaration, as `copy.test-only-policy` does for the copy family. A type then has one movability in a binary.
2. Filter it like any other test-only conformance. Production code then sees a movable type and test code sees a `NoMove` one, which is the two-answers shape t15 refused for the copy tier.

Reading 1 matches the copy-family precedent.

**Air: a second face, in a different check, and it favours reading 1.** The containment cascade also reads the unfiltered `NoMove`, so a test-only `NoMove` breaks a production *declaration*, not just a `move`. sawc2 at main plus SL-639 (`typecheck --check`):

    p: Pinned

This gives ``nomove.undeclared: `Holder` contains NoMove member `p` of type `Pinned` but does not declare `NoMove` …`` at 13:8. Without the `@test` extension it checks clean.

Refusing it at its declaration closes both faces at once. **The user's ruling, Oct 14:** "I think we should treat a test section as a separate source file - so it can only do what is allowed in such a file." The lead offered (a), a file rule for policy conformances, and (b), a narrow test-only refusal. The user answered "I approve (a)".

**The rule (a):**
- A type's **policy conformances** may be declared only in the **file that defines the type**: `Copy`, `ExplicitCopy`, `NoCopy`, `NoMove` and `ZeroInit`. A hand-written `deinit` already lives inside a copy-policy conformance, so it follows.
- **An `@test { … }` section and an `@test` declaration count as a separate file,** and so does a test sidecar (`parser.test.saw`). None of them may declare a policy conformance for a type defined elsewhere, its own module's production types included.
- **A test-only type** declared in a test section or sidecar may declare its own policies there, since that is its defining file.
- **Production code is restricted too:** another file of the same module can no longer declare these for the type. A type's policies sit next to it.

This subsumes SL-659 (a test-only `NoMove` on a production type), SL-630's `copy.test-only-policy` and the copy-family test-only refusal under one rule. Those diagnostics may be folded into it, or kept as its special cases; the unit decides, and the funnel names its entry points.

**Owed by the unit:**
- **A consumer sweep first, with compile evidence:** every policy conformance in the tree declared outside its type's file, in production code and in tests. It covers `std/`, `compiler/`, `libs/`, `blade/`, `examples/`, `tests/corpus/` and the compiler test fixtures. Report the count before building, so the cost is visible.
- One funnel, with the position matrix pinned row by row.
- The spec (the orphan-rule section and the copy-policy, `NoMove` and `ZeroInit` sections), SL:testing's sidecar text ("can only do what is allowed in such a file", for policies), and the saw-lang skill.
- An SL:hazards entry if Stage 0 accepts what sawc2 now refuses.

**Open for the Air:** do `Send`/`Sync` and `UnsafeSend`/`UnsafeSync` belong in the policy set? They are type-level properties too, but the user's ruling names neither. Raise it before dispatch rather than include them silently.

**Air, on the open question: `UnsafeSend`/`UnsafeSync` belong in the policy set. `Send`/`Sync` should need nothing, but sawc2 has a hole there: it accepts a declared `Send`.**

- **`UnsafeSend`/`UnsafeSync`: include them.** They're the declared half of a type's thread behaviour, and their obligations (heap-only memory, nothing thread-affine, `deinit` sound from any thread; for Sync, the whole `&self` surface race-free) are facts about the type's implementation, which only its defining file can vouch for, just as a copy policy is. Today a test section can assert one for a production type, and test code relies on it. SL-640 hides it from production (`.build/scratch/air-review/sl659/send_probe.saw` on the Air, sawc2 at main):
  - `@test extension Buf: UnsafeSend {}` on a production `struct Buf { raw: UnsafePointer<Int> }`;
  - a `@test func` passing `&b` to `need<T: Send>` is accepted;
  - the same call in production code is refused `type.bound`, correctly.

  Under rule (a) the test section is a separate file, so the assertion itself is refused there.

- **`Send`/`Sync`: nothing to add, since they're derived and never declared. But sawc2 doesn't refuse the declaration, and that's a soundness hole.** At main:
  - `extension Buf: Send {}` on the raw-pointer holder above typechecks clean, and production code then passes it to `need<T: Send>` (`send_forged.saw`). The same holds for `extension Buf: Sync {}` with a `T: Sync` bound (`sync_forged.saw`).
  - That is a safe-code assertion of thread-safety, past every check `UnsafeSend` makes (a blocking field must be unsafe-typed, and asserting where the derivation already succeeds is refused).
  - Stage 0 refuses both: "cannot explicitly implement `Send`: it is a marker trait derived structurally by the compiler" (and the same for `Sync`), as the spec says (`Send`/`Sync` stay derivation-only).

  It's a missing refusal, independent of the file rule, so please file it as its own soundness issue. Presume it's a class (obligation 4): the other derivation-only traits (whatever else the spec lists as derived structurally) likely take the same unguarded path.

**p659file: rule (a) is built (worktree, not submitted; on top of SL-673). One reading I chose that the ruling leaves open, flagged for the lead and the Air.**

The ruling says "an `@test { … }` section and an `@test` declaration count as a separate file", and "a test-only type ... may declare its own policies there". Read strictly, each top-level `@test` declaration is its own file, so `@test struct Fake { … }` followed by `@test extension Fake: NoCopy {}` would be refused: the extension is a different "file" from the struct, and a bare `@test struct` could then never have a policy at all.

I built the other reading: **every `@test` declaration and group of a module counts as one test file.** Production types gain the full refusal either way (no test code may declare their policies), so the readings differ only for a test-only type whose policy sits in a different test declaration or group than the type. The tree has two such sites, both in golden `test_only_copy_policy.saw` (`Ticket: Copy`, `Buffer: ExplicitCopy`, SL-630's own accepted controls), and nothing else changes. The choice is one line in `in_defining_file` (`compiler/typecheck/src/conform.saw`), and golden `policy_placement.saw` pins it. If the strict reading is wanted, it needs a group identity per test declaration from resolve, and those two goldens move into groups.

**Air, on p659file's reading: I agree with the one you built.** One test file per production file, made of all its `@test` sections and declarations together with its sidecar, is what the user's words describe: "treat a test section as a separate source file - so it can only do what is allowed in such a file". - Production types get the full refusal under both readings.
- It would forbid any policy on a bare `@test struct`, the commonest way to write a fake.

**One thing to pin down: what unit the test file is keyed by.** The production rule's unit is "the file that defines the type". The test half should be keyed by that same file, plus its sidecar, not by the module.
