## Description

Found by t640rev's sweep for the SL-640.p1 revision. A test-only declaration changes what production code means, by a mechanism the copy-policy refusals don't cover.

**Mechanism:** typecheck reads a type's movability from its conformances with no test-only filter (`declares_no_move` in `compiler/typecheck/src/tier.saw`; the transfer check that refuses `move` reads the same answer). A `@test extension T: NoMove {}` on a production `NoCopy` type therefore makes the type `NoMove` for production code too. SL:testing says production code is checked as if no test-only declaration existed, and refuses a test-only copy policy on a production type because a type would otherwise have two tiers in one binary. Movability is the same kind of per-type fact, so it has the same problem.

**Evidence** (sawc2 at SL-640.p1 plus the revision, `sawc2 build --std-root std`):

```saw
struct Pinned {
    n: Int
}

extension Pinned: NoCopy {}

@test
extension Pinned: NoMove {}

func take(p: Pinned) -> Int {
    p.n
}

func main() {
    let p = Pinned(n: 4)
    print("{}", take(move p))
}
```

Production `main` is refused with `transfer.no-move` at `take(move p)`. Drop the `@test` extension and it builds.

**Needs a ruling, two readings:**
1. Refuse a test-only `NoMove` on a production type at its declaration, as `copy.test-only-policy` does for the copy family. A type then has one movability in a binary.
2. Filter it like any other test-only conformance. Production code then sees a movable type and test code sees a `NoMove` one, which is the two-answers shape t15 refused for the copy tier.

Reading 1 matches the copy-family precedent.

**Air: a second face, in a different check, and it favours reading 1.** The containment cascade also reads the unfiltered `NoMove`, so a test-only `NoMove` breaks a production *declaration*, not just a `move`. sawc2 at main plus SL-639 (`typecheck --check`):

```saw
struct Pinned {
    n: Int
}

extension Pinned: NoCopy {}

@test
extension Pinned: NoMove {}

struct Holder {
    p: Pinned
}

extension Holder: NoCopy {}

func main() {
    let h = Holder(p: Pinned(n: 4))
    print("{}", h.p.n)
}
```

This gives ``nomove.undeclared: `Holder` contains NoMove member `p` of type `Pinned` but does not declare `NoMove` …`` at 13:8. Without the `@test` extension it checks clean.

**I'd take reading 1.** A test-only `NoMove` on a production type asserts an address-stability property that production code, the code actually moving the value, doesn't honour, so it protects nothing. Refusing it at its declaration closes both faces at once. Reading 2 would have to filter the transfer check and the cascade (`nomove.undeclared`) separately, and would leave production and test code each holding one type's movability differently. That's t15's two-tier shape, here on the `NoMove` axis.

**On the patch, I'll check:**
- both programs are refused only at the test-only conformance;
- `Holder` raises no `nomove.undeclared` beside that refusal;
- a test-only `NoMove` on a test-only type is still accepted, with its own containment cascade intact.

**The user's ruling, Oct 14:** "I think we should treat a test section as a separate source file - so it can only do what is allowed in such a file." The lead offered (a), a file rule for policy conformances, and (b), a narrow test-only refusal. The user answered "I approve (a)".

**The rule (a):**
- A type's **policy conformances** may be declared only in the **file that defines the type**: `Copy`, `ExplicitCopy`, `NoCopy`, `NoMove` and `ZeroInit`. A hand-written `deinit` already lives inside a copy-policy conformance, so it follows.
- **An `@test { … }` section and an `@test` declaration count as a separate file,** and so does a test sidecar (`parser.test.saw`). None of them may declare a policy conformance for a type defined elsewhere, its own module's production types included.
- **A test-only type** declared in a test section or sidecar may declare its own policies there, since that is its defining file.
- **Production code is restricted too:** another file of the same module can no longer declare these for the type. A type's policies sit next to it.

This subsumes SL-659 (a test-only `NoMove` on a production type), SL-630's `copy.test-only-policy` and the copy-family test-only refusal under one rule. Those diagnostics may be folded into it, or kept as its special cases; the unit decides, and the funnel names its entry points.

**Owed by the unit:**
- **A consumer sweep first, with compile evidence:** every policy conformance in the tree declared outside its type's file, in production code and in tests. It covers `std/`, `compiler/`, `libs/`, `blade/`, `examples/`, `tests/corpus/` and the compiler test fixtures. Report the count before building, so the cost is visible.
- One funnel, with the position matrix pinned row by row.
- The spec (the orphan-rule section and the copy-policy, `NoMove` and `ZeroInit` sections), SL:testing's sidecar text ("can only do what is allowed in such a file", for policies), and the saw-lang skill.
- An SL:hazards entry if Stage 0 accepts what sawc2 now refuses.
