## Description

Found by t640rev's sweep for the SL-640.p1 revision. A test-only declaration changes what production code means, by a mechanism the copy-policy refusals don't cover.

**Mechanism:** typecheck reads a type's movability from its conformances with no test-only filter (`declares_no_move` in `compiler/typecheck/src/tier.saw`; the transfer check that refuses `move` reads the same answer). A `@test extension T: NoMove {}` on a production `NoCopy` type therefore makes the type `NoMove` for production code too. SL:testing says production code is checked as if no test-only declaration existed, and refuses a test-only copy policy on a production type because a type would otherwise have two tiers in one binary. Movability is the same kind of per-type fact, so it has the same problem.

**Evidence** (sawc2 at SL-640.p1 plus the revision, `sawc2 build --std-root std`):

```saw
struct Pinned {
    n: Int
}

extension Pinned: NoCopy {}

@test
extension Pinned: NoMove {}

func take(p: Pinned) -> Int {
    p.n
}

func main() {
    let p = Pinned(n: 4)
    print("{}", take(move p))
}
```

Production `main` is refused with `transfer.no-move` at `take(move p)`. Drop the `@test` extension and it builds.

**Needs a ruling, two readings:**
1. Refuse a test-only `NoMove` on a production type at its declaration, as `copy.test-only-policy` does for the copy family. A type then has one movability in a binary.
2. Filter it like any other test-only conformance. Production code then sees a movable type and test code sees a `NoMove` one, which is the two-answers shape t15 refused for the copy tier.

Reading 1 matches the copy-family precedent.
