## Description

U4d measured this (SL-424.p4 report). `SourceFile.offset_of(line, col)` in `compiler/parse/src/source.saw` walks forward from the line's start, one scalar at a time, for every token the parser converts. So a parse costs time quadratic in line length: 20,000 call arguments on one line take 2.1 s, while 20,000 pairs one per line take 0.013 s.

This is not urgent. Real sources have short lines, and tests/corpus parses in 0.09 s. But a generated or minified input is a plausible input for a compiler, and nothing refuses a long line.

**Fix: carry the byte offset on the token.** The lexer already knows it, so the parser never recomputes one.
- If the lexer's token layout makes that awkward, a (line, col, offset) memo of the last conversion would make sequential calls O(1).
- Either way, pin it with a cell: a 20,000-argument single-line call parses in linear time. The depth cells show how.
- Report the change's cost on tests/corpus.

SL-434.p1 is up. `offset_of` is no longer on the parser's token path, so a long line parses in linear time. It is one commit touching 8 files, +272/−36.

**Approach.** The lexer records each token's byte offset, but beside the token rather than on it.
- **Why not a field on the token:** `prototypes/minivm/src/frontend.saw` builds `Token` values at four sites. Saw fields have no defaults, so a new `Token` field would break the minivm build.
- **Instead:**
  - `LexResult` gains `offsets: Vector<Int>`, one entry per token. `tokenize` records the pass's start, and each branch emits at most one token.
  - `StringSegment` gains `offset`, the `{` of an expression segment.
  - `parser_tokens` reads both, and no longer calls `offset_of`.
- **`offset_of` stays for:** lex errors, once per file, and doc comments. A doc comment starts its line, so that walk costs its indentation, not the line's length.
- **The minivm lane** is green, with 446 cases.

**Measurements, before → after** (best of 3, one `sawc2 parse --check` process each):

| input | before | after |
|---|---|---|
| 20k call arguments on one line | 2.068 s | 0.007 s |
| the same, one per line | 0.008 s | 0.008 s |
| a 20k set literal on one line | 1.904 s | 0.007 s |
| a 20k tuple pattern on one line | 1.934 s | 0.006 s |
| tests/corpus `--check` / `--dump` | 0.099 / 0.120 s | 0.088 / 0.110 s |
| the lane's single process | 0.246 s | 0.231 s |

**Dumps.** The old and new binaries were run over 7,299 files: tests/corpus, every parse-lane case, and the long lines. Their `--dump --alternatives` output (15.3 MB) and `--check` output are byte-identical.

**The pin: `compiler/tests/line_length.py`,** run from `run.py`'s parser section.
- **What it measures:** three one-line texts (20k call arguments, a set and a tuple pattern), each against the one-per-line call. There is no wall-clock threshold.
- **How:** 10 parses per process, the best of up to 3 runs, and a failure above 5× the one-per-line time.
- **Evidence it catches the bug:** after the fix the texts run at 0.7–0.9×. Against the old binary they ran at 317–329×, and all three failed.

**The unit test,** `compiler/lex/tests/offsets.saw`, checks every token and segment offset against a line:col reference. It covers every kind, multibyte text, nested and blank interpolations, and CRLF. Two deliberate lexer breaks were each caught.

**Unchanged:** the token fixture format. `format_token` and the golden files are untouched.

Approving SL-434.p1. I built sawc2 at the base, 895b7d72, and again with the patch, and compared the two binaries (`.build/scratch/air-review/sl434/`).

**What I checked**
- **Byte-identical output.** I ran both binaries over two sets of inputs:
  - every tracked `.saw` file (6,561);
  - the 669 probe cases from my SL-424/440/442 reviews, many of them refused.

  Their `--dump --alternatives` output (49 MB) and their `--check` output (1,981 ERROR lines, each with its position) are byte-identical. Dumps carry no positions, so the ERROR lines are what shows the offsets unchanged.
- **The positions an offset bug would move.** Eight more texts give the same ERROR lines from both binaries:
  - an error inside an interpolation segment after multibyte text;
  - a nested segment;
  - a second segment;
  - a multibyte line before a later error;
  - a CRLF file, with its segment and its bracket errors;
  - a tab-indented line;
  - an error at column 19,897 of a 3,000-argument line.
- **Linear time.** Best of 3, one process each, base against new:
  - 20k call arguments on one line: 1.869 s against 0.007 s;
  - a 20k `+` chain: 2.090 s against 0.007 s;
  - 20k multibyte string arguments: 2.550 s against 0.007 s;
  - 5k interpolations in one string: 0.066 s against 0.004 s;
  - the per-line control: 0.009 s against 0.008 s.
- **The pin.** `line_length.py` passes at 0.8×, 0.8× and 0.7×. Its 5× ratio leaves wide headroom both ways: the bug measured in the hundreds.
- **What still calls `offset_of`:** doc comments (a doc comment starts its line, so the walk covers only its indentation), a lex error in a file, and a lex error in a segment. Each is one-off, and none is on the per-token path.
- **The minivm prototype** constructs neither `LexResult` nor `StringSegment`, so the new fields can't break it.

**Gate:** passed on the applied commit: tested_commit == applied_commit == 7ba8ad21. The tested tree, 9aa836e4, is the tree I get when I apply the diff to 895b7d72.
