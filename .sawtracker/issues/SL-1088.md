## Description

**Five small things two reviews left behind (SL-1085.p1 and SL-1079.p1, the Air, Nov 12 and 13). None blocks anything; each is a few lines.**

1. **An up-to-date image doesn't notice a changed tool.** After a Blade build of an `[sos]` package, the same package with `SOS_CLANG` naming no program prints `Finished ... (up to date)`. The image's stamp never held the C compiler or the linker. It should hold what was used (the variable's value or the recorded path), so a changed tool rebuilds. `blade/src/builder.saw`, where the stamp is computed; a test in `blade/tests/`.
2. **`check_blade_finds_tools` (`tools/blade_lane.py`) fails on a machine that has a riscv32 record but no `ld.lld` beside that clang or on `PATH`.** It skips only for a missing record. Skip, saying so, when no linker can be found by the route Blade itself uses.
3. **`sawc tools --target T` and `sawc build --freestanding --target T` disagree for a Linux triple with no record:** `tools` refuses ("no runtime for it is configured"), while the freestanding build compiles with the host's clang. Both follow the records as written. Decide which is right (a freestanding object needs no runtime, so `tools` should probably answer with the clang the build would use) and make the two agree through one function.
4. **`hand_on.check`'s second case loops forever if `write_all`'s `if not took: raise` is removed** (`compiler/tests/hand_on.py`): `view[None:]` is the whole view again. Give `_Sipping(0)` a limit on writes so the check fails in place of hanging.
5. **When `check_split_object` (or `check_sawc_tools`) fails before the part it leaves out under a twin, `check_twin_table` adds a second line** ("N checks were left ... names M") beside the real failure. Either say so in that message ("or a check failed before its left-out part"), or have such a check count its row on entry.

**Gate.** `tools/blade_lane.py`, `compiler/tests/run.py --only seed,programs,fixture_whitespace,comments` and its `parallel` step, `tools/battery.sh citations patchgate`.

**Implementation detail (lead, Nov 14): a batch of this issue's test-tooling items. Each makes a lane say what happened where today it says something else. One patch; this issue stays open.** Each item names the comment above that recorded it.

**A. A compiler that dies mid-batch is reported as that.** `compiler/tests/typecheck/typecheck_lane.py`'s `check_refusals` runs every refusal fixture in one `sawc typecheck --check` call, ignores the exit status, and reads the records printed; when sawc panics on one fixture, each fixture after it is "expected RULE, nothing refused" and the panic's text is nowhere (SL-457 U3: a dozen unrelated fixtures named for one panic).
- The lane's `sawc()` helper captures standard error too. A call whose exit status is neither 0 nor 1 (a signal, an abort, a panic's 134) is ONE failure: "`sawc typecheck` died (exit N) after FILE: LAST LINE OF STANDARD ERROR", FILE being the last `FILE` record printed (the one being checked, or the one before it: say which the compiler's output order makes true), and the fixtures with no record are not reported one by one.
- Find the status sawc uses for "refused" and for "usage" before fixing the set of normal exits (read the driver; do not guess).
- The same check wherever a lane batches: the golden groups and warnings in the same file, and each other lane under `compiler/tests/` that feeds many files to one sawc call and reads records (`resolve`, `mir`, `borrowck`, `drops`, `mono`, `coro`, `eval`: grep for the `FILE\t` record reader). One shared helper if the lanes already share a module; otherwise the same few lines in each, named the same. List every call site you changed and every one you found that needs no change, with why.
- Test: each changed lane has a way to be tested against a stand-in compiler (read how `tools/test_*.py` or the lanes' own self-tests stub one; `SAWC_BINARY` hands a chosen binary down). A stub that prints two records and then exits 134 with a line on standard error must produce exactly the one failure line. If no lane has a self-test harness, add one small test file for the shared helper and say so.

**B. A refusal fixture may state how many errors it prints.** The typecheck lane checks a fixture's FIRST error only, so "exactly one error" and "one error per case" are held by nothing (SL-1107's review: with the two quiet-on-cycle lines removed, `static.cycle.raw-case-used` prints three errors and passes).
- A header line `// errors: N` (after `// refuses:` and `// flags:`, before `// message:`; read `header_of`, `_FLAGS`, `_MESSAGE` and the lane's docstring for the header grammar and keep its order rules), checked when present: the fixture's record must hold exactly N `ERROR` lines, else "RULE at L:C: N errors stated, M printed", listing the extra ones' rule and position.
- `--fill` does not write it. The lane's docstring and `compiler/tests/typecheck/README` (if it describes headers) gain the line.
- Apply it to SL-1107's six fixtures (`static.cycle.raw-case-self` 1, `-siblings` 2, `-ring` 3, `-flag` 1, `-used` 1, `static.not-constant.raw-case-two-enums` 2) after printing each alone to confirm the count, and to no others in this patch.
- Self-check: temporarily state a wrong count in one fixture, show the failure line, restore.

**C. A stated probe that exits with the wrong status shows standard error.** `compiler/tests/run/run_lane.py`, the stated branch of `check_probe` ("exit %s (expected %d); output: ..."): when the exit status differs, append standard error's last lines (at most five, each cut at 200 characters), so a panic's text is in the lane's log. The x86_64 failure of `process_output_cancel_reaps_child` read `exit -6 (expected 0); output: line 1: printed '', expected '...'` and nothing else. Do the same at the other checks in that file that compare a program's exit status and print no standard error (list them). Show before and after with a scratch probe that panics.

**D. The two cancel probes know a wrong `WNOWAIT`.** `process_output_cancel_ends_its_drain.saw` and `process_output_cancel_closes_the_pipe.saw`: `has_children` reads any failure of `waitid` as "no child", so a wrong flag for the host (`EINVAL`) would end the sweep at once and bring back the race silently.
- A self-test at the start of `main`, after `choose_wait_flag`: with one child certainly alive (a child that blocks until its standard input closes, spawned so the program holds its handle; read how the probes' own children wait on a gate), `has_children()` must be true; if it is false the probe panics "waitid refuses WNOWAIT=0x... on HOST". Then release and reap that child the ordinary way, and go on. No errno is needed.
- `SIGINFO_BYTES` in the first probe is read by nothing: use it as the buffer's length in both probes or drop it.
- The probes' stated output must not change. Run each 200 times at `-O0` and `-O2` on the host (they are short), comparing the whole output.

**E. `tools/linux.py shell CMD < FILE` carries FILE.** A redirected file arrives empty (`.build/scratch/p1109/stdin_check.log` in the lead's checkout). By reading, `command_shell`'s two preliminary `limactl shell` calls (`vm_home`'s `printenv HOME`, the `test -d`) inherit standard input and the first consumes it. Give every call the tool makes for its own purposes `stdin=subprocess.DEVNULL` (find them all: `run_in_vm(..., capture=True)` and `limactl list`), leaving the user's command its standard input. `tools/test_linux.py` gains a case with its stub `limactl` (read how the stub is built): the stub records whether each invocation saw standard input at end of file, and the user's command's invocation must receive the bytes. If the VM is running (`tools/linux.py status`), also show the real thing: a 500-byte file's checksum through `shell bash -c 'sha256sum'`; if it is not, say so and do not start it.
