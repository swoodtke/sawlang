## Description

**The spec says an `@export` survives a collecting link; sawc keeps it only as far as the object. And an export that is also placed with `@section` is dropped where an unexported placement is kept.** Reported by the Air (chat m743, found reviewing SO-50.p2); reproduced by the lead on main at v0.22.0 plus SL-934.

**The spec** (LANGUAGE_SPEC.md, Attributes): `@export` is "kept alive through DCE (via `@llvm.used` ...)", and "An export is a keep-root at all three points where unreached code is discarded: the `-O1` pipeline above, code generation ..., and the link (`-dead_strip` on mach-O, `--gc-sections` on ELF). So an exported function that nothing in the program calls is still in the object and still in the executable."

**sawc** (probe `.build/scratch/q_export_placed.saw` in the lead's checkout: four functions nothing calls, built `--freestanding --target riscv32-unknown-none-elf -O2 -c`, then `ld.lld --gc-sections -e _start`):

| function | section flags in the object | in the linked file |
|---|---|---|
| `@section(".placed_only")` | `AXR` (retained) | yes |
| `@export("plain_export")` | `AX` | **no** |
| `@export("vector_table") @section(".vectors")` | `AX` | **no** |
| `@export("_start")` (the entry) | `AX` | yes |

An export is an external `define` and is in no `@llvm.used` list (the Air read the `.ll`: the list holds the backtrace table alone), so the optimizer and code generation keep it and the object carries no retain flag for it.

## Part 1, a defect, no decision needed: an exported placement is not retained

`@export` beside `@section` is the vector-table shape the spec names, and it is the one combination that is dropped: SL-934's keep-list skips an exported item (it is external, so the optimizer keeps it anyway), and with that it loses the retain flag an unexported placement gets. The spec's `@section` paragraph ("A placed function or static is emitted and kept ... At the link it is kept where the object format carries a retain flag") is false for it. Both rules, either reading of Part 2, say it stays.

- **Mechanism:** `note_placed_define`'s caller in `emit_function` (`compiler/llvm/src/bodies.saw`) skips an exported item; the static half has the same test where placed statics are collected (`compiler/llvm/src/program.saw`).
- **The class:** exported placed FUNCTIONS and exported placed STATICS; whole-module and `--codegen-units=module`; a suspending exported placed function if the language allows one (an export may be refused from suspending: check, and say).
- **Fix:** a placed definition joins `@llvm.used` whether or not it is exported. Pins: `check_placed_symbols` gains an exported placed function and an exported placed static (symbol and section, -O2, both unit modes); and a link-level pin, which the lane lacks today: build the probe above for riscv32 (when its clang and an `ld.lld` are recorded), link with `--gc-sections -e _start`, and require the placed symbols in the linked file. If the run lane has no route to an `ld.lld`, the pin goes in the freestanding suite as a case (SL-1078 is that case's issue; coordinate, don't duplicate).
- This part can be dispatched now.

## Part 2, a decision for the user: does a plain `@export` survive the link?

Today it doesn't, the spec says it does, and **sawos relies on today's behaviour**: its 54 `sos_*` floor stubs are exports in every object, and only the called ones reach a process image (the Air; a sawos comment still describes the spec's behaviour as the cost of a stub).

- **(A) sawc follows the spec:** every export joins `@llvm.used` and is retained at the link. A `_start` or a table nothing references can never vanish silently. Every unreferenced export is then in every image: sawos's images grow by the unused stubs unless sawos changes how it supplies them, and there is no way left to write "external and callable from C, but collectable".
- **(B) the spec follows sawc, with Part 1 fixed:** an export is kept through the optimizer and code generation into the OBJECT, as a C external function is; at the link it is kept when something references it, when it is the entry, or when it is also placed with `@section` (retained) or kept by a linker script. The spec's third keep-root point and its "still in the executable" sentence are rewritten. The vector-table shape is spelled `@export @section(...)`, which is how one is placed anyway.

**Lead's recommendation: (B).** It is what C and a linker already mean by an external symbol, it keeps "exported" and "retained" as two things a program can say separately (`@section` now carries the second), and sawos's use is a real one for the first without the second. Its cost is the silent case: an unreferenced, unplaced export that someone expected in the image is absent with no diagnostic. (A)'s cost is paid by every image that links a library of exports.

Not measured: the hosted mach-O link (`-dead_strip`), which the spec's sentence also names. Measure it before either side's text is written.

**Until the user rules:** the spec text stays as it is (a spec rule is never reworded toward sawc on the lead's own reading), nothing changes for plain exports, and sawos's images are unaffected. Part 1 changes nothing for sawos: it uses no `@section` from Saw.
