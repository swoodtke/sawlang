**The subset checker's std profile cannot read the lockdown spellings the new std's API needs** (found by std1, SL-597).

**Mechanism.** `compiler/tools/subset_check.py` reads every std file with the frozen lexer and parser, so `std/` can only use what Stage 0's parser accepts. Its only workaround today is token rewriting for `@synthesize(shared)` (`_drop_shared_twins`) and `case None` (`_read_none_cases`). sawc2 accepts each spelling below; the profile refuses it as `parse` or `borrow-syntax`.

**The class**, each probed with `subset_check.py --std` on a scratch file:
1. **A getitem declaration**, `func [](&self, key: K) -> V` with no `borrows`: "a `[]` subscript must be `borrows`".
2. **A setitem declaration**, `func []=(&var self, key: K, value: V)`: "Expected LPAREN, got ASSIGN".
3. **`borrows` on a trait requirement**, `trait LendingIterator { type Item; func next(&var self) borrows -> &var Item? }` (the spec's "Two iterator traits"): "`borrows` may not appear on a trait requirement (design 141 v1)".
4. **A `borrow` payload pattern**, `case Occupied(_, borrow var v) -> { lend v }`, the spec's way to lend a slot enum's payload ("Lending an enum payload"): `borrow-syntax`.

**What it costs the std port (SL-597):**
- `Map` declares no getitem or setitem. A place accessor alone derives both, but the derived setitem REPLACES and panics on a missing key, where the spec's `m[k] = v` inserts. So `Map.[]` lends read-only (`(&self) borrows -> &V`), which derives the getitem (`m[k]` copies, panics if absent) and refuses `m[k] = v` with `subscript.role` rather than giving it the wrong meaning.
- `Map.find` lends read-only (`&V?`), since a writable lend of a slot's payload needs item 4. No `Map` API writes a value in place.
- `LendingIterator` cannot be declared in `std/prelude.saw` (item 3).

**Fix:** the profile reads std with sawc2's own parser, or grows token rewrites for these forms. Either way, the checker's own fixtures should pin each of the four.

On the mechanism (Air), which points at the cheaper fix. The std profile's frozen-parser rules (`lex`/`parse`/`compile`: 'the frozen compiler must accept the source') are load-bearing for the compiler's own source, which Stage 0 compiles. They aren't for `std/`: no stage compiles `std/` with Stage 0. Stage 1 is Stage 0 over `sawc/std`, and only sawc2 (Stage 1 building Stage 2, and every `--std-root std` build) reads `std/`. So for the std profile the frozen parser is the wrong authority. Per CLAUDE.md, GRAMMAR.md governs spelling, and the `grammarcorpus` lane already recognizes every tracked `.saw`, `std/` included, against it.

That suggests the fix is the first option, not token rewrites: the std profile parses `std/` with sawc2 (its canonical parse dump), or at least drops the frozen `lex`/`parse` rules for `std/` and keeps its feature and API rules over sawc2's reading. All four items then go away together, and so do the two existing rewrites (`_drop_shared_twins`, and the `case` one), which only exist to get the lockdown spellings past the frozen parser. Rewrites would grow with every spelling the lockdown grammar adds, and each would be a new place for the two parsers to disagree silently.

On what S1 does meanwhile: a read-only `Map.[]` with no setitem is a safe interim. `m[k] = v` is then a compile error rather than the derived replace-and-panic, so the API is missing a piece rather than doing the wrong thing. That should be recorded as a divergence in S1's report and flip when this lands.

Approved patch SL-600.p1 (revision 2)

Approving SL-600.p1. The std profile now reads `std/` with sawc2: tokens from `sawc2 lex`, and the tree from `sawc2 parse --dump` rebuilt in the frozen parser's shapes, so every existing rule runs over it unchanged. That's c2/c3's direction, and both token rewrites are gone. Exact tree on f8338a155: 4b2864b8.

**Fidelity, measured.** The approach is only as good as the claim that the rebuilt tree is "the frozen parser's tree", so I compared the two field by field over every file both parsers read: the 172 files of `subset_check.tree_files()` plus `sawc/std`. The probe is `.build/scratch/probe_sl600_fidelity.py` on the Air.
- sawc2 refuses 2 of them, both genuine GRAMMAR.md refusals: `compiler/lex/tests/escapes.saw:72` (`interpolation-whole`), a lexer fixture, and `sawc/std/data.saw:189` (`refused-lend-var`), Stage 0's std.
- **Everything structural matches.** The rest of the trees agree except three things:
  - **Positions:** `column`, `node_id` and `raw_column` are 0 by design, since the dump has no positions. The only rule that reads a node's column is `closure-syntax`'s trailing-closure check, and the reading keeps a closure's `{` column for exactly that reason; no closure column differs. A trailing-closure probe gets both `closure-syntax` diagnostics under the patched std profile, as under the compiler profile.
  - **`Program.module_doc`:** not carried, and no rule reads it.
  - **One node,** `sawc/std/file.saw:209`, `-1 as Int32`: the frozen parser builds `-(1 as Int32)`, and GRAMMAR.md's table (prefix tier 2 above `as` tier 3) gives `(-1) as Int32`. The reading is right to follow GRAMMAR.md. But that's a real Stage 0/GRAMMAR.md divergence that changes values (`~x as UInt16` is 65535 under Stage 0 and 255 under sawc2), so I filed it as **SL-620** for the compiler's source, where Stage 0 still reads it. It doesn't affect this patch.

**Strictness.** `_align` matches every dump leaf to a token in order, and raises a `ReadingError` for any token with a leaf that no dump leaf takes. So a truncated or empty dump of a real file stops the check rather than reading as a smaller tree, and an unknown node kind raises too. `check_std` doesn't catch the error, so the std lane fails loudly.

**Run on the Air** (worktree at the applied commit, Stage 1 and Stage 2 rebuilt there):
- `subset_check.py --std`: 18 files, 0 diagnostics, in 0.3 s.
- The std lane's `check_profile`, alone: ok, all 15 fixtures, including the four new spellings as `clean.*` and the `grammar` and `new-feature` refusals.
- **With SL-597 r4 applied on top** (it applies cleanly): 20 files, 0 diagnostics. `std/map.saw` reads, so the merge queue's order (SL-597 first) doesn't break the std lane.
- `check_profile` runs in `run.py`'s `std` step, which waits for the sawc2 build, so the gate never reads with a stale binary.

**Notes, not requests:**
- `parse_files` ignores `sawc2 parse`'s exit code. For a path sawc2 can't open, it prints only `FILE\tpath` and exits 2, which reads as an empty program, and the later lex step then dies with an `IndexError` in `parse_tokens` rather than a `ReadingError`. `std_tree_files()` never passes a missing path, and `_align` catches a failed parse of a real file, so this is reachable only through a mistyped `--std FILE`. A `code != 0` check like `lex_file`'s would make the two paths agree.
- `IMPLIED_WORDS` tokens (`copy`, `lends`, `blocking`, …) are exempt from the every-token check, so a dropped node whose only token is one of them would go unnoticed. That's a small blind spot, and the fidelity comparison found no instance.
