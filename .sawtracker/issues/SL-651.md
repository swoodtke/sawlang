**The user's ruling, Oct 15** ("sure let's use your recommendations for the factory function / init issue"): a function that only builds a value is the type's `init`, and new code follows that from now on. The existing factories are converted later, as one mechanical unit (filed separately).

**The rule** (for `compiler/README.md` and the saw-lang skill):
- A function whose body only builds a value of a type is that type's `init`, called `Type(label: …)`. Write `TcValue(fault: f)`, not `tc_fault(f)`.
- A named alternative with no argument to label is a `static func` on the type, such as `ResBinding.unbound()`.
- A constructor whose parameters are exactly the struct's fields is the memberwise construction itself, so it is not written.
- A function that computes something and returns it as a struct stays a function named for what it computes: `coro_edges(coro)`, `parse_source(...)`.
- **Compiler-source limits:** no `init` in an extension with type parameters (`generic-extension-init`, SL:hazards S1). No `init` whose labels and types are exactly the fields' (an override under SL-648), because Stage 0 refuses one, until the compiler builds itself.

This issue is the doc patch. The conversion is its sibling issue.

Approving SL-651.p1: the constructors-are-`init`s rule from the user's Oct 15 ruling, as a "Constructors" section in `compiler/README.md` and four comment lines in the saw-lang skill's core-syntax block, right after the `init` and `static func` examples they refer to. Exact tree on 6782d703a: 897da9cb.

The README section states the ruling as filed on SL-651: build-only functions become `init`s, a no-argument alternative becomes a `static func`, compute-then-build functions and stage entry points stay functions. It states both compiler-source limits: no `init` in an extension with type parameters (S1), and no exact-match `init`, an SL-648 override that Stage 0 refuses. The skill lines are comments inside an existing `saw-fragment`, so `docverify`'s result can't change.

**One nit, take it or leave it:** "A constructor whose parameters are exactly the struct's fields is the memberwise construction itself, so it is not written" holds where every field is visible to the callers. Per the spec, that's any `public struct` with bare fields. A struct with a `private` field has no memberwise construction outside its module, and in this source no exact-match `init` either, so such a constructor stays a function until the compiler builds itself. A clause saying so would keep SL-652's grid honest (see my SL-652 c3).
