**Refinement from the Air (SL-561 c3), adopted for A7d's mechanism:**
- **The origin is recorded at the site.** The spawn-site terminator records its form (singleton or group) on the local it defines. The obligation is that local's origin fact, with no role and no type involved.
- **The per-path check uses drop elaboration's existing machinery.** `drop.must-consume` fires when a singleton-origin value reaches an implicit drop on some path. A move into `join`/`detach`/`cancel` consumes it, a move into another local carries the origin along, and a group-origin value never refuses (K80).
- **Escapes need no interprocedural analysis.** A handle moved into a field, a collection or a return leaves the local, and the language's run-time, provenance-keyed drop panic is the check for that escape (the handle carries its form). So the static half stays intraprocedural, as Stage 0's `_mint_spawn_obligation` effectively is. A7d confirms that the run-time panic exists in the new std's handle (A7b's `Task<T>`). If it doesn't, A7d names that as a dependency on A7b and doesn't invent one.

(The lead's decision is SL-561 c4; A7d's body says c3, which is the Air's comment, and this is the mechanism it describes.)

Right, and that corrects my SL-561 c3 wording ('a move into `join`/`detach`/`cancel` consumes it'). Those methods borrow, so the obligation can't be read off move-tracking alone. What the check becomes (Air):
- **The fact:** a forward per-path fact on each singleton-origin value, 'its fate has been written', set by a call of `join`, `detach` or `cancel` with the value as receiver. It joins as AND over predecessors, so 'fate written' must hold on every path. `drop.must-consume` fires at a drop the value reaches with the fact false on some path.
- **Moves still carry the origin AND the fact.** A handle cancelled and then moved into another local arrives consumed. One moved and then joined through the new local is consumed there. So the fact belongs to the value's ownership, which drop elaboration already follows, not to the local's name.
- **Calls through a place the analysis doesn't follow** (`s.handle.join()` on a handle stored in a field) are the escape rows the run-time panic covers, as the matrix says.

Pins worth adding to the list:
- `let t = Task.spawn(f()); if c { t.join() }`: refused, because the fact is false on the else path;
- `let t = Task.spawn(f()); t.cancel()`: accepted, because `cancel` alone writes a fate;
- `let t = Task.spawn(f()); let u = move t; u.detach()`: accepted, because the move carries the origin.

Approving SL-595.p1 (SL-545 A7d): `Task.spawn(f(x))` lowers to a `Spawn` call in MIR, and the must-consume obligation is minted by the spawn FORM through one funnel (`mir_mint_obligation`), then checked path by path (`check_fates`). Exact tree on 00d5bf195: 0458e052. I built Stage 2 with the patch.

**Beyond the escape matrix** (`sl595/fates_extra.saw` and `fates_missing.saw`, `drops --check --std-root std`):
- **accepted:** a fate on each arm of a three-arm `match` (`join`, `detach`, `cancel`); a handle spawned and joined on every iteration of a `while`; a `guard` whose exit cancels before it returns;
- **refused at the spawn site, `drop.must-consume`:** the same `match` with one arm missing its fate, and a `guard` that returns without one.

So the per-path rule reaches `match` and loops and early exits, not only the `if` the matrix lists.

**The design:**
- The obligation follows the form, not the type, so `group.spawn`'s `Task<T>` may be dropped.
- `check_fates` follows the handle's value forward to a fixpoint, before elaboration.
- A move carries the obligation, and a move into storage whose owner declares a `deinit` discharges it, with the run-time panic SL-562 added as the backstop.
- Every other way out is refused once, at the site.
- The matrix is probed against Stage 0 row by row. The two divergences (a handle moved to another local and then given a fate; a fate on each arm of an `if`) both follow the spec's per-path rule, where Stage 0 keys on the first binding's name or undoes a nested consume.

**One request, not blocking:** the report's 'left, not filed: under Stage 0's std root, mono hits an INVARIANT for `Task.deinit`'. Please file it with its reproducer. An INVARIANT is a compiler defect wherever it's reachable, and the default std root is what a user without `--std-root` gets. For the record, my probe under the default root gives clean `mono.not-yet` refusals for `join`/`detach`/`cancel`, so the INVARIANT needs a shape I didn't hit, probably a handle discharged into `deinit`-owning storage, which makes mono lower `Task.deinit` from Stage 0's std.
