## Design first
Post a design comment on this unit's issue (SL-505), then implement without waiting. The Air reviews the design along with the patch. Settle these points:
1. **Mono (§3.8).**
   - Its input is drop-elaborated MIR.
   - Item identity is (function, canonical concrete arguments), with defaults filled.
   - The worklist runs from `main`, `@export` functions and the runtime seams it reaches, in a deterministic order.
   - Substitution produces concrete MIR, and trait calls become direct calls.
   - Glue (drop, copy, retain) is made once per concrete type through the one glue function, and the copy tier is read from typecheck.
   - Polymorphic recursion: the ruled refusal (§3.8) belongs before mono. If it isn't built, stop on it and file it; don't silently loop.
   - Mono needs a dump (`sawc2 mono --dump`) and a golden lane, like the other stages.
2. **Target description (§3.10).** One module answers size, alignment, field offsets, the enum tag, and payload layout for every concrete type. That covers primitives, references, raw pointers, structs, tuples, enums (`Optional` and `Result` included) and function pointers. It also owns the C calling convention for `extern` calls.
   - The host is the first target: arm64-apple-darwin, and x86_64 Linux if it's cheap.
   - Every backend queries it, so no layout fact lives in the backend.
   - Pin each layout in a golden. Wherever Stage 0 has a layout for the same type, compare against it, because the two compilers share the runtime ABI.
3. **Backend (§3.10).**
   - Textual `.ll`, one LLVM function per concrete MIR function, and each MIR local an `alloca`.
   - Places become GEPs, and the terminators map 1:1.
   - Checked arithmetic uses the overflow intrinsics, branching to the panic seam with `FILE:LINE` (design 122).
   - `print` and `panic` go through the runtime seams (`__saw_rt_write`, `__saw_rt_panic`).
   - String literals and statics are globals, and the atomic intrinsics are LLVM atomics.
   - Emission must be deterministic, with no hash-order iteration (§4's fixpoint depends on it).
   - The backend makes no language decisions (§3.10's invariants).
4. **Runtime linkage (§3.11).** Link the Saw runtime objects Stage 0 builds and caches under `.build/rt/`, and say how `build` finds them. The decision: sawc2 links Stage 0's prebuilt runtime first, and porting the runtime build is later work. clang does the compiling and linking. Say how `build` finds clang and passes the optimisation level (the `speed_level` funnel, design 265; `-O0` is fine for now).
5. **Entry and the program shape.**
   - How `main` and process arguments reach the runtime.
   - The exit code.
   - Whole-program only: one `.ll` for the whole build. Separate compilation is §3.12's later work.

## Milestones (commit at each, run.py green)

2. Layout goldens for the types those programs reach.
3. `sawc2 build hello.saw -o hello --std-root std`. The binary prints `hello, world` and exits 0.
4. **The differential lane:** about 15 to 30 small programs under `compiler/tests/run/`, each built by sawc2 and by Stage 0. The lane runs both binaries and compares stdout and the exit code. Cover:
   - integer arithmetic, including one overflow panic;
   - `if` / `while` / `match`;
   - structs and enums, `Optional` and `Result`;
   - a generic function and a generic struct;

   - a drop with a printing `deinit`, to check the order;
   - a non-escaping closure;
   - one bounds-check panic.

   A program sawc2 can't build yet is recorded as due, with its reason; it doesn't fail the lane. Register the lane with `run.py`.
