## Description

**Borrowck's block dataflows sweep in index order, and `borrowck_trace` stops at 64 steps** (SL-606; found by SL-610's sweep).

- **Mechanism, part 1 (block order):** three fixpoints in `compiler/borrowck/src/loans.saw` re-walk every block per round in index order until nothing changes:
  - `loan_liveness` (backward, last block first);
  - the forward loan and window dataflow (`created_in`/`open_in`, `while changed` near the `reached` sweep);
  - the window-exclusivity loop (`window_exclusive` propagated to the enclosing window).

  The lowering numbers a join below its arms, so each sequential `if` costs one more full round. That's O(joins × blocks × width). The answers are right, since none of the loops is capped, but the time is quadratic. SL-610 fixed the same mechanism in `split.saw` liveness, `initialisation.saw` `init_analysis`, the MIR verifier's `window_entries`/`verify_payloads` and the drops verifier's `refined_entries`: a worklist swept in reverse postorder (`MirProgram.init_block_order`), or in postorder for a backward analysis. Each fix was shown byte-identical on mir/borrowck/drops dumps over about 3,000 files. Do the same here and pin the result as unchanged.
  - Evidence: on SL-610's 1100-`if` accessor probe (`compiler/tests/run/run_lane.py` `long_accessor_source`), `sawc2 borrowck --check` takes 1.7 s. That's after the MIR fixes, with bitsets keeping the width small, so this is time, not a wrong answer.
- **Mechanism, part 2 (M1 cap family, bucket B):** `borrowck_trace` loops `while rounds < 64` and, at the cap, returns the path it has reached so far, an intermediate reference local, not the place it borrows. A chain of more than 64 single-assignment reference locals would then be charged to the wrong root. That's the permissive answer past the cap, the same shape as `satisfies`/`is_no_move`. Not probed: no source form building such a chain was tried. The fix is an identity walk to the end, with a visited set as the only guard.
- **Holder:** `loans.saw` is held by a1cap (SL-607), so this waits for it.

**A sibling of `borrowck_trace`'s cap, from SL-627's sweep, filed here at the lead's direction:** `compiler/borrowck/src/conflicts.saw` `from_receiver(f, l, facts, depth)` returns false once `depth > 32`.
- **What it does:** it follows a prologue local's single definition back through `ref`s (via `borrowck_trace`), and through call arguments, asking whether the value was read out of the receiver. `lendable_root` calls it for a pointer's deref or index.
- **The harm:** a false past the cap makes a lend through a pointer read out of the receiver count as not rooted in it. That is a false refusal of a legal accessor, never an acceptance.
- **Why it terminates without the cap:** the chain follows definitions of locals defined once (`def_count == 1`). A visited set keyed by local id makes the walk terminate on a cycle and stay linear. Two call arguments that share a defining chain are what make the unmemoized walk exponential.
- **The fix belongs with `borrowck_trace`'s:** one identity walk over the def chain, with no depth count. Not probed with a deep chain: an accessor with more than 32 single-definition hops is needed to show it.
