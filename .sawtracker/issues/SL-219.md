## Description

SOUNDNESS. A `try` whose SUBJECT is a binding or a field forwards that storage
unjudged, so the Ok payload is extracted out of a value the source still owns
with no ownership check. TRIPLE FREE at exit 0 on NoCopy. Found Sep 9 by SL-210
(design 267 unit A) while inventorying the ownership boundaries; NOT introduced
by that unit and deliberately not fixed there (SL-210 is behavior-preserving).

## The mechanism (obligation 4 — the SIBLING of the `self` finding filed beside
## this one; ONE mechanism, two sub-classes)

`_is_aliasing_expr` (`sawc/typechecker/types.py:3440`) answers the producer
question as a NODE-TYPE TEST over four classes — `Identifier`, `MemberAccess`,
`ArrayIndex`, `TupleIndex` — plus two hand-added TRANSPARENCIES for nodes that
FORWARD a read rather than being one (`ForceUnwrap`, design 131; a forwarding
`CastExpr`, DF-299a). The two sub-classes of the same defect are:

  (a) a node that IS a read and is not in the set — the `self` receiver;
  (b) a node that FORWARDS a read and is not transparent — this one.

`TryExpr` is in `_VALUE_BRANCH_TYPES`, but `_value_branch_arm_results`
(`types.py:4345`) deliberately returns the CATCH handler only —

    # Only the CATCH handler: the `try`'s own value comes out of the
    # subject expression, which is that expression's question ...

— and nothing ever asks that question. With no catch block it answers None
outright. Control then reaches `_is_aliasing_expr(TryExpr)`, which is False,
so the extraction is judged a fresh temporary at every tier. The comment is
right that the subject is the subject expression's question; what is missing is
that a `try` over an ALIASING subject forwards that subject's storage, exactly
as `o!` and a forwarding cast do.

## Measured evidence

Compiles clean, exit 0. One value, THREE `drop` lines (the binding's own drop
plus one per extraction):

    struct Res { w: Int }
    extension Res: NoCopy { func deinit(&var self) { print("drop {self.w}") } }
    enum Bad { case Nope }
    extension Bad: NoCopy {}
    func make() -> Result<Res, Bad> { Res(w: 5) }

    func use_it() -> Result<Int, Bad> {
        let r = make()
        let a = try r
        let b = try r
        a.w + b.w
    }
    func main() { print(try! use_it()) }
    // prints: drop 5 / drop 5 / drop 5 / 10   — exit 0

FOUR SPELLINGS, each measured, each triple-freeing in one program
(`drop 1`, `drop 2`, `drop 3`, `drop 4` three times apiece):

  1. `try r`               — the propagating form (above)
  2. `try! r`              — the panicking form
  3. `try? r`              — the optional form
  4. `try r catch { ... }` — the inline-catch form; the catch ARM is judged
                             (DF-299b's recursion) and the SUBJECT is not
  5. `try! h.r`            — a FIELD subject, so the hole is not
                             binding-specific

A `try` over a CALL RESULT (`try make()`) is correct and must stay correct: the
value is a fresh temporary the reader already owns. That is the line the fix
has to draw, and it is the same line DF-299a drew between a forwarding cast and
a building one.

## Pin

`examples/conformance/V87_try_subject_read_is_a_transfer.saw`, XFAIL citing
this issue, with EXPECT directives stating the intended refusal. Conformance
INDEX row V87.

## Fix shape (NOT this issue's scope)

Make `_is_aliasing_expr` transparent through a `try` to its SUBJECT, on the
terms `ForceUnwrap` already has — `try r` aliases iff `r` does — and keep the
building case (`try f()`) answering False. Tier-blind, per V62/V65: the Copy
tier's missing retain is the worse half, not the NoCopy refusal. Natural home
is SL-211 (unit B, the forwarding taxonomy), swept and fixed together with the
`self`-receiver sibling since the mechanism is one.

FIXED on branch `worktree-agent-af5361be8244c3ca4` (SL-211, unit B). Not submitted — the lead squashes and submits. Full write-up is SL-211's comment; brief is `designs/269-forwarding-taxonomy.md`.

Fixed on the terms this issue proposed — `try r` aliases iff `r` does, `try f()` stays a fresh temporary — and as the MECHANISM rather than as a second hand-added transparency. `TryExpr` joins `PRODUCER_PROJECTS` in `sawc/typechecker/producers.py`, one row of a classification that is now total and gated.

`try` turned out to be the one node that belongs in TWO buckets, and saying so is what fixed it properly: it PROJECTS its Ok value out of the subject's storage and BRANCHES into its catch handler — two result sources, two rules. That is exactly the bug restated: DF-299b's recursion judged the catch arm, returned `delegated`, and never reached the subject. The checkpoint now judges the arm, keeps its decision in the `try`'s own `delegates`, and falls through to the producer path for the Ok projection. The gate knows about that single dual membership by name and rejects any other.

All five measured spellings refused (`try`, `try!`, `try?`, `try … catch`, and a FIELD subject), and the CONTROL row stays legal — `try f()` over a call result, plus the inline `(try! make(n)).w`.

THE FIXIT NAMES THE SUBJECT. The value refused is the PAYLOAD but the storage that still owns it is the SUBJECT, so a bare "use `move`" named nothing an author could act on. It now spells `try move r` / `try! move r` — probed on the unfixed tree before the wording was written: it compiles and releases the payload exactly once. A FIELD subject gets the other half of that sentence instead, because `move h.r` is the no-partial-moves refusal and pointing at it would be sending the author at a wall.

TIER BLINDNESS, per this issue's own note: `try` was the position MISSING a retain at the `Copy` tier rather than at risk of a second one — an unretained second owner is a refcount underflow. Conformance row V89 counts it, and it now duplicates exactly once.

CORPUS COST: zero. No `try`-over-a-binding at an owning tier in std, blade, libs, devtools or the corpus.

V87 lost its XFAIL marker in the fixing commit.
