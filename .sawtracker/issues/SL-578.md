**Air: two single-threaded assumptions A13a (SL-571, merged bc7bbf3f6) leaves for this unit.**

1. **The readiness word's read.** `park_wakes` reads a channel's `ready` word with a plain load (`word[0] != 0`). `publish_ready` writes it with the channel's lock held, but the executor reads it without that lock. Once a pool worker sends while another worker sweeps, that plain load races the store: a data race, and a load the compiler is free to keep stale across the sweep. It needs an atomic load. The queue itself is safe, because the woken receiver's `take` re-reads `count` under the lock, so a relaxed load is enough for the wake decision.
2. **`idle`'s deadlock panic.** `idle` panics when only channel parks are left and no timer is pending, on the premise that only code this thread runs can set a readiness word. With N workers, a channel park on one worker can be woken by a task running on another, so `idle` has to wait rather than panic while any worker is busy. SL-765 has the `Thread.spawn` side of this (my c2 there).

**p578 (A17a), stopped before writing code: the plan leaves out how std starts a worker thread.**

**What's missing.** A17a's scope is "the live worker pool" in `std/taskgroup.saw` alone. The pool needs N OS threads. sawc2's std has no way to start one:

1. **Stage 0's pool starts its workers with `Thread.spawn { [addr] in __saw_exec_worker(addr) }`** (`sawc/std/taskgroup.saw`, `__start_crew`). sawc2 refuses that form at resolve: "the `Thread.spawn` form is not in the bootstrap slice yet" (`compiler/resolve/src/walk.saw`, `is_thread_spawn`). **The user ruled (Oct 17): an OS-refused pool worker PANICS at the group's first spawn.** The pool keeps the spec's lazy start ("a group that never spawns starts no thread"), so the refusal surfaces inside `group.spawn`, which has no `Result`. That is the same boundary as spawn's compiler-inserted frame allocation, and it matches Stage 0's `__start_crew`. The panic names the errno and `TaskGroup(threads:)`. No spec or API change, and the constructor's `Result<TaskGroup, AllocError>` covers only allocation.

This corrects SL-765 c5's last line, which assumed a refused worker would be the constructor's `Err`. It can't be with a lazy start.
