## Description

A driven body's `[move x]` capture of an `ExplicitCopy` frame local runs the
user's `copy()` hook that its sync twin never runs, so the closure reads a
DIFFERENT VALUE. Found by the SL-213 r2 obligation-4 sweep (the mixed-mode cell);
broken on origin/main and unchanged by that branch — byte-identical output from
both compilers — so it is filed, not fixed there.

MECHANISM (named, per obligation 4). `_materialize_closure_captures`
(sawc/coro_transform.py) materializes a captured frame local as a `let` ahead of
the closure, and asks `_frame_read_policy` HOW to produce an independent owner.
That funnel is selected on the TIER alone, before the capture MODE is consulted:

    if policy == 'nocopy' and self._frame_slot_has_explicit_copy(name):
        read = <frame field>.copy()          # ceremony tier
    elif policy == 'nocopy':
        read = <move read of the frame field> + __saw_forget   # NoCopy tier

A `move` capture duplicates NOTHING — that is what the mode means — so at the
NoCopy tier the second branch is right (the frame hands its own reference over
and forgets it). At the ExplicitCopy tier the first branch fires instead and
mints a duplicate through the author's `copy()`, which is the `copy` mode's
answer applied to a `move` capture. SL-267 is the same mechanism one mode over
(the materialization being a duplication the author did not write); its fix does
not reach here, because it addressed the SECOND duplication rather than the
choice of read.

The `copy()` hook is where it becomes visible rather than merely wasteful: a
non-idempotent hook makes the driven body compute a different answer.

REPRO (both twins in one program):

    struct Dup { n: Int }
    extension Dup: ExplicitCopy {
        func copy(&self) -> Dup { print("copy {} -> {}", self.n, self.n + 1)  Dup(n: self.n + 1) }
        func deinit(&var self) { print("drop {}", self.n) }
    }

    struct Res { w: Int }
    extension Res: NoCopy { func deinit(&var self) { print("drop res {}", self.w) } }

    func run_int(body: () sync -> Int) -> Int { body() }

    func mv_sync(d: Dup) -> Int { run_int({ [move d] in d.n }) }
    func mv_driven(d: Dup) -> Int { __saw_suspend()  run_int({ [move d] in d.n }) }

    func res_sync(o: Res) -> Int { run_int({ [move o] in o.w }) }
    func res_driven(o: Res) -> Int { __saw_suspend()  run_int({ [move o] in o.w }) }

    func main() {
        print("-- lone move, ExplicitCopy, sync")
        print("= {}", mv_sync(Dup(n: 20)))
        print("-- lone move, ExplicitCopy, driven")
        print("= {}", __saw_drive(mv_driven(Dup(n: 20))))
        print("-- lone move, NoCopy, sync")
        print("= {}", res_sync(Res(w: 70)))
        print("-- lone move, NoCopy, driven")
        print("= {}", __saw_drive(res_driven(Res(w: 70))))
        print("end")
    }

MEASURED, identically on origin/main (5755f60b) and on the SL-213 branch:

    -- lone move, ExplicitCopy, sync
    drop 20
    = 20
    -- lone move, ExplicitCopy, driven
    copy 20 -> 21          <- the hook the sync twin never runs
    drop 21
    drop 20
    = 21                   <- a DIFFERENT ANSWER from the sync twin's 20
    -- lone move, NoCopy, sync
    drop res 70
    = 70
    -- lone move, NoCopy, driven
    drop res 70
    = 70                   <- the NoCopy tier is correct: no duplication

Memory-safe throughout — the drops balance — so the failure is the ANSWER and
the extra observable side effect, which is SL-267's own signature.

SWEEP. The mechanism is the read-policy funnel, so its other reachable positions
are the remaining capture modes over a frame-resident local:
  * `[copy x]` — CORRECT since SL-213 (the materialization IS the author's
    duplication, and codegen skips the second one).
  * `[move x]` at NoCopy — CORRECT (move_read + `__saw_forget`, above).
  * `[move x]` at ExplicitCopy — THIS FINDING.
  * `[move x]` at the silent Copy tier — the `retain`/`trivial` branch takes an
    owning read, which retains rather than calling a user hook, so nothing
    visible diverges; a retain is still one more than a move owes, and it is the
    same shape one tier down.
  * a PLAIN `[x]` / implicit capture at ExplicitCopy — refused at both tiers
    (V96's row), so the funnel is unreachable there.
  * `[&x]` / `[&var x]` — store a pointer, no materialization.

WHY IT IS NOT A ONE-LINE FLIP. Selecting the NoCopy branch for an ExplicitCopy
`move` capture means handing the FRAME's own value over and forgetting the
field, which is exactly what the sync twin does — but the frame may be resumed,
and whether an emptied field is sound depends on the same "materialize a
non-owning local" capability SL-267's implicit half is blocked on (V96's XFAIL).
That is the design question this issue holds.

PINNED BY: nothing yet. `examples/conformance/V105_copy_capture_releases_its_duplicate.saw`
row C2 covers the sync twin of this shape; no row states the driven one.
