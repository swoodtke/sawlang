Found by the SL-1049 spec review (F17). A type alias can't be the receiver of a static call or the callee of a construction. All three refuse in one probe (`.build/scratch/p1000o/p19_alias_static.saw`, sawc at main):

- `type J = Job` then `J.make_one()` (a static of a plain struct): `member.unknown`: "`p19_alias_static.J` has no method `make_one` this module can see".
- `type JobBox = Box<Job>` then `JobBox.make(Job(n: 5))`: `member.unknown`, the same.
- `type IntVec = Vector<Int>` then `IntVec()`: `infer.failed`: "cannot infer type argument `T` of `Vector`", although the alias writes it.

The spec's slab section offers `type JobBox = Box<Job, JobSlab>` as "the kernel idiom", in place of the spelled `Box<Job, JobSlab>.make(...)`, which builds and runs (`p19_slab2.saw`). A transparent alias names its target in every type position, and a static receiver and a construction callee are type positions.

**Expected:** an alias resolves to its target, with its type arguments, wherever a type is named. Sweep first, because this is a position-quantified rule: a static receiver, a construction, a generic alias (`type Pair<T> = …`), an alias in a pattern (`case JobBox…`), an alias used as an extension target, and the distinct-alias interaction (SL-1012).
