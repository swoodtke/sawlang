## Description

**A Saw program can link C object files, static archives and named libraries, and a Blade package can declare and compile its C sources.** This is the owner's request (Nov 18). A user program should be able to use a C library, for example mbedTLS for TLS over `std.net`'s `TcpStream`, without the library being in std.

The language side already works:
- `extern "C"` declarations;
- `FuncPointer<F>` C callbacks;
- `UnsafePointer` buffers;
- suspending `TcpStream` I/O (a sans-IO library's callbacks copy to and from Saw buffers and return want-read/want-write).

The gap is linking. `sawc build` links the program's objects plus the target's own libraries (`driver_link_tail`, `driver_link_libraries`), and has no flag for anything else. Blade has no manifest key for it. Hand-linking after `-c` means reproducing sawc's link line and runtime: undocumented and fragile.

**Owner rulings (Nov 18):**
1. **Link and compile.** Blade also compiles a package's C sources, per target, with the clang `sawc tools --target T` records, so a wrapper's helper `.c` or a vendored library cross-compiles for riscv32 and Xtensa. Prebuilt objects and libraries are supported too.
2. **Structured inputs only.** No raw linker-argument passthrough: everything sawc passes is something it understands and can check (an object, a static archive, a named library, a library path, and on Mach-O a framework). More forms are added when a real need shows up.

**Draft design (lead; the design pass verifies it against the code and fills the OPEN points):**
- **sawc flags** (no abbreviations): `--link-object FILE` (a `.o` or a static `.a`), `--link-library NAME` (`-lNAME`), `--library-path DIR` (`-L`), `--link-framework NAME` (Mach-O targets only; refused elsewhere). Each is repeatable.
  - Order on the link line: the program's objects, then the link objects in the order given, then the library paths and libraries in the order given, then the target's own libraries (`-lm`).
  - A missing file or directory is refused before anything is compiled, naming it.
  - With `-c` (no link) or on a bare-metal target (`sawc build` does not link those), each flag is a clean error, never dropped silently.
  - A framework on a non-Mach-O triple is an error.
- **Blade manifest** (sketch; the spelling is OPEN for the design):
  ```toml
  [native]
  c-sources = ["c/helper.c", "vendor/mbedtls/library/*.c"]
  include-dirs = ["vendor/mbedtls/include"]
  defines = ["MBEDTLS_CONFIG_FILE=\"saw_config.h\""]
  objects = ["prebuilt/x.o"]
  libraries = ["z"]
  library-paths = ["vendor/lib"]
  frameworks = ["Security"]

  [native.target.xtensa-esp-unknown-elf]   # per-target additions or overrides
  defines = ["..."]
  ```
  - Paths are relative to the declaring package's root.
  - C sources are compiled with the target's recorded clang, `--target`, the build's optimization level, and the package's include dirs and defines. Objects are cached by their inputs.
  - A dependency's native inputs reach the root's link, in dependency order and deduplicated, each path resolved against its own package.
  - Blade's freshness covers the C sources, the headers they include (OPEN: a depfile from clang's `-MD`?), and each prebuilt input's content.
  - Freestanding: Blade's own image link (`build_sos_image`, ld.lld with the linker script) takes the same inputs.
- **OPEN for the design:**
  - Whether `pkg-config` is consulted (lead's default: no; explicit paths only).
  - Whether a library is linked statically or dynamically, and how a hosted binary finds a dynamic one at run time (rpath?).
  - Whether a package's native inputs are visible to its tests and examples.
  - How an object built for the wrong target is reported (the linker's error alone, or a check first).
  - Whether `sawc --build-id` or the object cache must see link inputs. They don't change compiled code, but the link must rerun when an input changes.
  - Windowed vs call0 C code on Xtensa: the C compile must get the same `--target-features` as the Saw code.
- **Units (after the design pass):**
  1. sawc's flags, with fixtures: a C object compiled in the test, a static archive, a system library (e.g. `-lz` on the host), each refusal, and the run lane linking and running a program that calls C.
  2. Blade's `[native]` prebuilt inputs, with propagation through dependencies and freshness.
  3. Blade compiling C sources per target.
  4. The freestanding image link with native inputs, as a riscv32 case.
  5. Docs: the spec's build section, the README, and Blade's README.
  6. Dogfood, as a separate issue: a `libs/` package wrapping a small C library end to end, and later an mbedTLS TLS-client example over `TcpStream`.

Related: the TLS question (Nov 18), SL-1154 (Blade `[package]` keys), `sawc tools`.

**Accepted, as the design's defaults:**
1. **sawc's flags:**
   - `--link-object FILE`, `--link-archive FILE`, `--link-library NAME`, `--link-library-path DIR`, `--link-framework NAME` (Mach-O only), each repeatable.
   - Link order: the module, the runtime objects, objects and archives in the order given, `-L`, `-l`, `-framework`, `-lm`, `-o`. All of it goes through `driver_link_tail`, which every link path calls.
   - Refusals (exit 2, before anything compiles):
     - any link flag with `-c`, `--emit-ll`, `--freestanding` or a bare-metal target;
     - a framework on a non-Mach-O target;
     - a missing path, or a file and a directory swapped;
     - a wrong-target object, a shared library or LLVM bitcode, found by reading the object header (Mach-O cputype or ELF machine). Archives are checked by magic only.
   - Link inputs are seen by Blade's freshness only: not by `--build-id`, the object cache or the ThinLTO cache.
   - `sawc tools` gains a `triple` line.
2. **Blade's `[native]` table:**
   - Keys: `c-sources`, `include-dirs`, `defines`, `objects`, `archives`, `libraries`, `library-paths`, and `frameworks` in Mach-O tables only. An unknown key is an error.
   - `[native.<triple>]` tables append to the base table.
   - Paths are relative to the declaring package. A `*` is allowed in the last path segment only, and a pattern matching nothing is an error.
   - Every resolved package's inputs reach the root's link, each package before its dependencies. Archives and libraries keep their last occurrence; objects and paths keep their first.
   - `blade test` links the same inputs.
3. **Compiling C sources:**
   - Hosted builds use the clang `sawc tools` names, with `-target <triple line> -O2 -g`. Image builds use `native_compile_arguments`, which carries the Xtensa windowed or call0 features.
   - `-I` and `-D` (a C identifier or `NAME=VALUE`), plus `-MD -MF`.
   - An object cache keyed by clang's path and version, the arguments, the source and every header in the depfile.
   - A `TaskGroup` of compile jobs, capped at 75% of cores.
4. **Freestanding:** `build_sos_image` passes the same inputs. The freestanding suite gains a C function with eight `Int32` arguments, tested on all four rows.
5. **Static vs dynamic:** file inputs are static only, a named library links however the system ships it, there is no `pkg-config`, and there is no rpath.
6. **Non-Saw C code:**
   - (a) Vendoring now.
   - (b) `[native.fetch]` is NOT in SL-1170; it follows SL-1099, because Blade does not honour a locked git rev today.
   - Submodules are fetched (`--recurse-submodules --shallow-submodules`).
7. **No raw `c-flags`, and no exported include dirs, until a need shows up.** `[sos.<triple>] native` stays. Blade's freshness does not see a named system library's contents.
8. **Linux:** `zlib1g-dev` and `zlib1g-dev:amd64` are pinned in `tools/lima/sawlang-linux.yaml`. The owner reprovisions the VM when unit 1 lands.

**Bugs the design found, owned by the units named:**
- `-x none` in `driver_link_module` is emitted only when runtime objects follow, so a `--runtime` provider's link objects would be read as IR (unit 1).
- Blade's `read_file` returns `""` for non-UTF-8 files, so `build_hash` misses a `.o`/`.a` change (unit 2).
- Blade's tester compiles through a `system()` shell string (unit 2).
- Blade never honours a git dependency's locked `rev`. This is recorded on SL-1099.
- aarch64 images: the C half gets no `-neon,-fp-armv8` default (UNVERIFIED; unit 4 checks it).

**Lead's note with p1 (Nov 24): unit 1, sawc's link flags**, as the owner accepted (`briefs/q1170_rulings.md`).

**Flags.** `--link-object`, `--link-archive`, `--link-library`, `--link-library-path` and `--link-framework` each take a word and can repeat. They are carried as `DriverLinkInputs` into every link path.

**Order.** Every link path goes through `driver_link_tail`:
1. the module;
2. the runtime objects;
3. objects and archives, in the order given;
4. `-L`;
5. `-l`;
6. `-framework`;
7. `-lm` on Linux;
8. `-o`.

A path starting with `-` is emitted as `./PATH`.

**The `-x none` fix.** `driver_link_module` emits `-x none` whenever runtime objects or link files follow, so a `--runtime` provider's link object is no longer read as IR. A provider linked with an object runs.

**Refusals.** These exit 2 before anything compiles and write nothing:
- a link flag with `-c`, `--emit-ll`, `--freestanding` or a bare-metal target;
- a framework on a non-Mach-O triple;
- a missing path, or a file and a directory swapped;
- by a 32-byte header read (Mach-O cputype and file type; ELF class, `e_type` and `e_machine`; `target_object_machine`): an object for another machine or format, a shared library, bitcode, text, or an archive given as an object (archives by magic; thin archives accepted);
- a `--link-library` name that is a path, a filename, or `lib`-prefixed;
- a missing operand.

**`sawc tools`** gains a `triple` line, which equals `build.clang_triple`.

**Approved, revision 2.**

**Probes on this patch's sawc** (macOS host, `build -O0`):
- **Freshness:** a C object relinked after its source changed at the same path. Builds print `value 5`, then `value 6`, then `6` again, so no link result is reused across a changed object.
- **A path starting with `-`:** `--link-object -dash.o`, given relative, links and runs (`value 7`). It reaches clang as `./-dash.o`.
- **Option-looking values:** none reaches the linker as an option.
  - `--link-library -Wl,-x` is refused by sawc, exit 2 ("no leading `-`").
  - `--link-library-path -fuse-ld=bogus` and `-Wl,-x` are refused, exit 2 ("no such directory").
  - `--link-library z,-x` and `'z -x'` arrive as one `-l` argument; the linker refuses them by name ("library 'z,-x' not found").
  - `--link-framework -lz` and `Core,-x` arrive as `-framework`'s operand ("framework '-lz' not found").

**`run.py`** `fixture_whitespace, subset, comments, parser, resolver, std, docs, programs, census, parallel_order`: green on this tree.

**One small inconsistency, not a hold:** `--link-library` refuses a leading `-`, and `--link-framework` doesn't. The framework name stays one argument, so the linker only reports a missing framework, but the same refusal there would read the same.
