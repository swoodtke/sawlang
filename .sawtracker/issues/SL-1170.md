## Description

**A Saw program can link C object files, static archives and named libraries, and a Blade package can declare and compile its C sources.** This is the owner's request (Nov 18). A user program should be able to use a C library, for example mbedTLS for TLS over `std.net`'s `TcpStream`, without the library being in std.

The language side already works:
- `extern "C"` declarations;
- `FuncPointer<F>` C callbacks;
- `UnsafePointer` buffers;
- suspending `TcpStream` I/O (a sans-IO library's callbacks copy to and from Saw buffers and return want-read/want-write).

The gap is linking. `sawc build` links the program's objects plus the target's own libraries (`driver_link_tail`, `driver_link_libraries`), and has no flag for anything else. Blade has no manifest key for it. Hand-linking after `-c` means reproducing sawc's link line and runtime: undocumented and fragile.

**Owner rulings (Nov 18):**
1. **Link and compile.** Blade also compiles a package's C sources, per target, with the clang `sawc tools --target T` records, so a wrapper's helper `.c` or a vendored library cross-compiles for riscv32 and Xtensa. Prebuilt objects and libraries are supported too.
2. **Structured inputs only.** No raw linker-argument passthrough: everything sawc passes is something it understands and can check (an object, a static archive, a named library, a library path, and on Mach-O a framework). More forms are added when a real need shows up.

**Draft design (lead; the design pass verifies it against the code and fills the OPEN points):**
- **sawc flags** (no abbreviations): `--link-object FILE` (a `.o` or a static `.a`), `--link-library NAME` (`-lNAME`), `--library-path DIR` (`-L`), `--link-framework NAME` (Mach-O targets only; refused elsewhere). Each is repeatable.
  - Order on the link line: the program's objects, then the link objects in the order given, then the library paths and libraries in the order given, then the target's own libraries (`-lm`).
  - A missing file or directory is refused before anything is compiled, naming it.
  - With `-c` (no link) or on a bare-metal target (`sawc build` does not link those), each flag is a clean error, never dropped silently.
  - A framework on a non-Mach-O triple is an error.
- **Blade manifest** (sketch; the spelling is OPEN for the design):
  ```toml
  [native]
  c-sources = ["c/helper.c", "vendor/mbedtls/library/*.c"]
  include-dirs = ["vendor/mbedtls/include"]
  defines = ["MBEDTLS_CONFIG_FILE=\"saw_config.h\""]
  objects = ["prebuilt/x.o"]
  libraries = ["z"]
  library-paths = ["vendor/lib"]
  frameworks = ["Security"]

  [native.target.xtensa-esp-unknown-elf]   # per-target additions or overrides
  defines = ["..."]
  ```
  - Paths are relative to the declaring package's root.
  - C sources are compiled with the target's recorded clang, `--target`, the build's optimization level, and the package's include dirs and defines. Objects are cached by their inputs.
  - A dependency's native inputs reach the root's link, in dependency order and deduplicated, each path resolved against its own package.
  - Blade's freshness covers the C sources, the headers they include (OPEN: a depfile from clang's `-MD`?), and each prebuilt input's content.
  - Freestanding: Blade's own image link (`build_sos_image`, ld.lld with the linker script) takes the same inputs.
- **OPEN for the design:**
  - Whether `pkg-config` is consulted (lead's default: no; explicit paths only).
  - Whether a library is linked statically or dynamically, and how a hosted binary finds a dynamic one at run time (rpath?).
  - Whether a package's native inputs are visible to its tests and examples.
  - How an object built for the wrong target is reported (the linker's error alone, or a check first).
  - Whether `sawc --build-id` or the object cache must see link inputs. They don't change compiled code, but the link must rerun when an input changes.
  - Windowed vs call0 C code on Xtensa: the C compile must get the same `--target-features` as the Saw code.
- **Units (after the design pass):**
  1. sawc's flags, with fixtures: a C object compiled in the test, a static archive, a system library (e.g. `-lz` on the host), each refusal, and the run lane linking and running a program that calls C.
  2. Blade's `[native]` prebuilt inputs, with propagation through dependencies and freshness.
  3. Blade compiling C sources per target.
  4. The freestanding image link with native inputs, as a riscv32 case.
  5. Docs: the spec's build section, the README, and Blade's README.
  6. Dogfood, as a separate issue: a `libs/` package wrapping a small C library end to end, and later an mbedTLS TLS-client example over `TcpStream`.

Related: the TLS question (Nov 18), SL-1154 (Blade `[package]` keys), `sawc tools`.

1. the module;
2. the runtime objects;
3. objects and archives, in the order given;
4. `-L`;
5. `-l`;
6. `-framework`;
7. `-lm` on Linux;
8. `-o`.

**Correction to my review's parenthetical "(sawos takes FP on first use)", which was wrong about sawos. The request stands, and sawos makes it stronger.**

sawos's arm64 HAL sets `CPACR_EL1.FPEN` to 0b01: EL1 may use FP/SIMD, and only EL0 traps on first use, which `fp_trap` handles lazily (`hal/arm64/kernel/ABI.md`). So a kernel struct copy in NEON would not trap there. The HAL's invariant is the stricter one: "A trap therefore never disturbs V0-V31, `FPCR` or `FPSR`". A syscall, fault or interrupt saves no FP state, so no EL1 code outside `sos_fp_save` and `sos_fp_load` may touch those registers.

That is why sawos builds its own kernel C (`sink.c`, `rt/common_c/support.c`) with `-mgeneral-regs-only`, and why its runner disassembles every arm64 kernel image and fails on an FP/SIMD instruction anywhere else. A Blade `[native]` object compiled as unit 4 compiles it, with no `-neon,-fp-armv8`, is exactly what that rule forbids. In a kernel image it would clobber the interrupted thread's V registers, or be refused by that runner. So the ask is unchanged: the arm64 C half gets the Saw half's `-neon,-fp-armv8` (or `-mgeneral-regs-only`), with a pin that doesn't depend on the suite's FP-on boot.
