## Description

**Verifier rule 1 over-refuses a zero-size frame slot laid at the frame's end** ("a slot lies past the frame's end"). Found by the Air (SL-545 comment) while checking SL-662's growth loop. It's on main, and Stage 0 builds both repros and prints 300.

**Repros** (the Air's `.build/scratch/air-review/sl662/`):
- `v4_empty_struct.saw`: a driven loop with an empty-struct local declared before the loop and read after it. The verifier reports `rule 1 (frame in place): … a slot lies past the frame's end, 40 bytes: (*_8).[40: v4_empty_struct.Marker]`.
- `v2_try_push.saw`: `try! v.push(i)` in a driven loop. The `try!` payload's `Void` local is frame-resident, giving `(*_13).[72: Void]`.

Ordinary code hits it: a `Vector<String>` filled in a driven loop. A9 (SL-566) makes it common, since every loop in a framed body suspends and `try!` of `Result<Void, E>` is everywhere.

**Mechanism:** `compiler/coro/src/verify.saw`'s rule-1 bounds check is `offset >= size`. A zero-size value laid last sits at offset == frame size, which is in bounds because it occupies nothing.

**Fix, either:**
- the check becomes `offset + slot size > frame size`; or
- the layout gives zero-size values no frame slot at all. Then the check stands, and nothing is stored for them. This is arguably the cleaner end.

**Sweep first (obligation 4):** an empty struct, `Void` from `try!`, an empty tuple, a zero-length array, and a payload-free enum of one case, if it's zero-size. Check each at the frame's end and mid-frame, with run pins matching Stage 0.

<!-- sawtracker:comment {"author":"agent:claude-sawlang/z688slot","body_bytes":2588,"created":"1792078066","id":"c1"} -->
**z688slot: reproduced on main, fixed in its worktree (commit 6181b9d50, not submitted).** Both repros reproduced: rule 1 at the end of a driven loop's frame, `(*_8).[32: Marker]` and `(*_17).[64: Void]`.

**The fix is the bounds check, not "no slot".** Rule 1 now checks `offset + slot size > frame size`, so the verifier takes the target the frames were laid out for. Here is why I didn't remove the slot. Every frame of a `Void` function holds a zero-size `_0`. The backend's task descriptor and std's `complete` read the result through its offset, and the drive's move-out, the drive and spawn argument writes, rule 1's "the result and parameters never stay on the stack" and rule 2's "a local live at a suspension lives in the frame" all assume a slot. "No slot" would add a special case to each of them, and to the backend and std too, which are outside this unit. A zero-size slot occupies no byte, so it's already in place.

**The sweep found the same mechanism at two more checks.** A zero-size value shares its offset with the value after it, and two checks named a slot by its offset alone:
- The verifier's offset-to-local map behind an index's frame load picked a zero-size value laid just before the index temporary (rule 1: "rewritten into something other than its local's frame slot").
- The drive, drive-site and spawn-site checks counted parameter writes by offset ("parameter _1's slot … is written 2 times, not once").

Both are fixed. A slot is now its offset and its type, through one helper, `coro_slot_writes`. It owes one write per parameter laid in the slot, because zero-size parameters of one type share one. The verifier's child regions also hold a zero-size slot at a child's end now, a detection gap that only an injection reaches.

**Matrix:** an empty struct (with a deinit too), `Void` from `try!`, `()` and `[Int; 0]`, each at the frame's end, mid-frame, beside an index, as a last parameter, as twin parameters, as a child's result at its caller's end, and at drive and spawn sites. Every program matches Stage 0 at -O0 and -O2. `[Int; 0]` is lowered only, since the backend can't build array literals yet. A one-case enum keeps its 4-byte tag, so it isn't zero-size.

**Pins:**
- golden `zero_size`;
- the stated probes `coro_zero_size_{struct,void,tuple}`;
- the unit program `verify_zero_size`, with two injections.

All of them fail on main.
