## Description

**Two literal-shaping gaps that Stage 0's closed issues fixed and sawc2 still has** (SL:hazards L1 and L4; the SL-425 sweep, c7; main and seed alike).

1. **L1, DF-276c (SL-70, closed for Stage 0): a literal-valued `if`/`match` doesn't adopt its operand's width.** `wide + (if up { 1 } else { 0 })` with `wide: UInt64` is `type.mismatch`. The same literal alone adopts `UInt64`, and the other L1 faces (SL-75, SL-56, SL-13, SL-84, a `UInt` parameter) adopt. The expected type must flow into each arm of a value `if` and `match` (and a block's tail) as it does into a bare literal.
2. **L4, DF-250a (SL-28, closed for Stage 0): a collection literal doesn't shape through a `Result`'s Ok payload.** A collection literal as the tail or the `return` of `-> Result<Vector<Int>, String>` is refused: ``expected `Result<Vector<Int>, String>` ... found `[Int; 3]` ``. Auto-wrap must apply the payload's expected type to the literal before wrapping. SL-291, SL-292, SL-42 and SL-46 are fine.

**Obligation 4:** one funnel, the expected type's propagation into a literal, with its entry points named. The positions:
- value `if`/`match` arms;
- block tails;
- `return`;
- the auto-wrap of `Optional` and `Result`;
- `??`'s right side;
- a collection literal's elements;
- a struct field initializer;
- an argument.

Each × an integer literal, a float literal and a collection literal.

**Retires:** the L1 overload faces of `integer-overload` (batch B2), and the SL-28 part of `optional-shaping`.
