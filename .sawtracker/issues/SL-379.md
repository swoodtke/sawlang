## Description

Found by the SL-340 implementer (Sep 24) while taking the census of intercepted constructions. The cell is `c6`, in `.claude/worktrees/sl340/.build/scratch/`.

`UnsafeMemory.write(v)` with an owning `T` is legal. `c6` writes a `String` into a `Normal` view, and it compiles and runs. SL-340 routes `write`'s argument through the value-transfer funnel, so ownership moves into the memory, exactly as with `ptr[i] = v`.

The `read()` side hands back an UNRETAINED bitwise alias of whatever is stored. That is:
- for a refcounted `T`, a missing retain, so the next drop over-releases;
- for a NoCopy or ExplicitCopy `T`, an implicit copy that the value-transfer rules would refuse anywhere else.

Question for a brief:
- Should `read()` follow the payload's copy tier? That means retaining a Copy-tier read, and demanding an explicit form for ExplicitCopy/NoCopy, just as place reads do (design 131/141).
- Or should `UnsafeMemory<T>` views be restricted to trivial `T`, which is what MMIO registers are?

The second is a language rule and needs a user ruling. The first is consistency with existing place reads. Sweep `read` and any other accessor that returns a `T` by value out of a view.
