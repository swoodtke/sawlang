## Description

Found by the design-272 obligation-4 sweep of rt/shim.c (Sep 12 2026), prompted by the SL-228 r1 review. PRE-EXISTING, a different class from the two races that review found, and deliberately NOT fixed inside the r2 delta.

`__saw_rt_thread_spawn` (sawc/rt/shim.c) ignores `pthread_create`'s return value:

    long __saw_rt_thread_spawn(void *(*entry)(void *), void *env) {
        pthread_t t;
        pthread_create(&t, NULL, entry, env);
        return (long)t;
    }

On failure — `EAGAIN` under thread or memory exhaustion is the realistic one — `pthread_create` does not write `t`, so the function returns an UNINITIALIZED stack word as a thread handle. Every consumer then treats that garbage as a live thread:

  * `rt/common/offload.saw`'s `rt_offload_start` stores it in `p[0].thread` and `rt_offload_take` later calls `__saw_rt_thread_join` on it;
  * `Thread.spawn` codegen stores it in the control block and `Thread.join` / `Thread.detach` use it the same way.

So a thread that was never created is joined as though it existed, and the body that was supposed to run never runs — with no error anywhere. That is a never-hide-errors violation at the seam layer: the failure is not merely unreported, it is converted into undefined behaviour.

WHY IT IS NOT THE SAME BUG as SL-228 r1's two findings, which is what the sweep was looking for: those were unsynchronized transactions over shared state. This is a single call whose status is discarded. The sweep cleared every other shim transaction for the SYNCHRONIZATION shape (offload's thunk is quiesced by `pthread_join` before its pipe is closed; `__saw_environ_get`/`_set` never form a shared transaction because the get is a parent-side read and the set runs in the forked child's private address space; the futex lock uses real atomics; the rest are pure functions of their arguments). This one turned up alongside and is recorded rather than dropped.

SHAPE OF A FIX (not a ruling): the seam would need to report failure, which means a sentinel the callers can branch on — `0` is not usable as one because `pthread_t` is opaque and a valid handle may be any bit pattern, so the honest shape is probably an out-parameter for the handle plus a status return, matching the design-117 status-carrying convention the rest of the ABI already uses. That is an ABI.md signature change and therefore a real unit of work rather than a patch.

WORTH CHECKING WITH IT: `__saw_rt_thread_detach` and the `Thread.spawn` control-block handshake assume a valid handle throughout; whatever sentinel is chosen has to be recognised there too.
