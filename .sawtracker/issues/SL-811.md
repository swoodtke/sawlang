## Description

**A `group.spawn` into a cooperative group from a thread other than its owner is not refused** (found by p808fix, SL-808 step 1, from reading; UNVERIFIED by a probe). For example, a pool task that captured or holds a `TaskGroup()` and resumes on another worker, or a group torn down (`unregister`) from another thread (SL-808's S5 path). `check_home_thread` (SL-806) guards handle operations only (`join`, `cancel`, `cancel_addr`, `detach`, drop). `place` and `unregister` called from a non-owner thread write the owner's run queue. Under SL-808's fix they take the owner's latch, so they WAIT instead of racing; but a cooperative group's tasks run only on its driving thread (K189), so a foreign spawn either never runs or runs on the wrong thread.

**Note:** SL-788's ruling 4 (TaskGroup/Task handles are not `Send`) should make the safe-code routes compile errors once the uniform Send check lands. This issue covers what still reaches it: unsafe code, and any route the Send check misses.

**Scope:**
- probe each route (safe and unsafe), after SL-788 lands, for the safe-code verdict;
- refuse the operation from a non-owner thread, through the same check as SL-806's `check_home_thread` (one funnel, its entry points extended to `group.spawn`/`place` and `unregister`);
- pin it.
