The same 14 lines appear on the SL-934 branch at 45110f91b, so they are standing failures, not that patch's. No patch runs this lane (it is the battery's opt-in `linux` stage), so nothing said when it went red. ## Finding 1 (6 failures): a provider link warns under clang-19, and the check requires silence

```
run compiler/tests/run/probes/runtime_provider.saw --runtime -O0: sawc exits 0: clang-19: warning: '-x none' after last input file has no effect [-Wunused-command-line-argument]
```
Six lines: `runtime_provider.saw` with `--runtime` and `--runtime-provider`, and `cooperative_group_provider.saw` with `--runtime`, each at -O0 and -O2.

**Mechanism (read from the source; the clang line itself was not echoed).** `driver_link` (`compiler/driver/src/main.saw`) builds `CLANG -target T SPEED -x ir LL -x none OBJECTS... LIBRARIES... -o OUT`. For a provider, `driver_build` calls it with no objects ("A provider is its own runtime: none of sawc's objects join its link"), and `driver_link_libraries` gives only `-lm` on the two Linux triples. So `-x none` is followed by no input file, and clang-19 says so on stderr. `check_runtime_provider` (`run_lane.py`) requires exit 0 and empty output. macOS doesn't show it: either Apple's clang doesn't warn or the lane's macOS link has something after it; which one is not established.

**The class (obligation 4).** Every clang command line the driver builds with `-x ir ... -x none`: `driver_link`, and the other sites that push `"-x"` in `main.saw` (the split link and the `-c` object paths), plus `build.py`'s own (`head + ["-x", "ir", ll, "-x", "none"] + tail`, which builds the stages). For each: can the list after `-x none` be empty of input files? Probe each on Linux with clang-19 by echoing the command and running it.

**Fix.** `-x none` is pushed only when an input file follows it. One helper builds the `-x ir LL [-x none OBJECTS...]` part for every site that needs it, so the rule lives in one place. Pin: the existing six lines going green in the VM, and a host-side check that the provider link's command line has no `-x none` (the lane has a way to see sawc's clang command if `--time-stages` or a verbose flag prints it; if nothing does, the Linux lane is the pin and the report says so).

## Finding 2 (8 failures): on Linux a warm build recomputes the front layers a cold `resolve --check` just stored

```
run front shared writers: after round N the packages' layers are ['computed', 'computed']: time: std front end 253.4 ms ...
```
Rounds 0 to 7, every round. `check_front_shared_writers` (`run_lane.py`): each round runs `resolve --check` over two entries on a fresh cold cache, then a warm `build --time-stages --emit-ll -g0` on that cache, and requires the warm build's `geometry` and `shapes` layers to read `loaded`. On Linux both read `computed`. On macOS the check passes.

**Mechanism: not known.** Candidates, each UNVERIFIED and each checkable in the VM clone by running the check's two commands by hand and listing `front/g*` in the cache between them:
- the cold `resolve --check` stores no layer parts on Linux (a store that fails quietly: look for a `front cache` warning in its stderr, which the check's 300-character cut may hide);
- it stores them under a key the warm `build` doesn't compute on Linux (a key ingredient that differs between the two commands there: a path, the target record, a clang identity);
- the two concurrent writers of a round leave no complete part (a rename or lock that behaves differently on Linux's filesystem; the check is named for its shared writers).
The other front-cache and front-layer checks pass on Linux in the same run, so the single-writer store and load work there; that points at what is particular to this check (two entries, or `resolve --check` as the writer and `build` as the reader). Say which once the listing shows it.

**This one is an investigation first.** Step 0: reproduce one round by hand in the VM clone (`tools/linux.py shell ...`), with the full stderr of both commands and the cache listing after each. Report that before choosing a fix; if it is a compiler defect in the cache's keying or its store, the fix is in `compiler/driver/` and gets its own pin on the host if the mechanism can be shown there.
