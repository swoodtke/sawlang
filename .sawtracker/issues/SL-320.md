## Description

A user module named `std` breaks the compilation of std's own files.

Found by SL-274's r3 class sweep (probing whether a user module path can reach
the `("<std>", leaf)` half of the module-tag domain); NOT caused by SL-274 — it
reproduces identically on main at 4abf24e5 and on the SL-274 branch.

Repro:

```saw
import std.once.*

module std {
    public module once {
        struct State { n: Int }
        extension State {
            func value(&self) -> Int { self.n + 7 }
        }
        public func peek() -> Int { State(n: 1).value() }
    }
}

static SLOT: Once<Int>

func main() {
    SLOT.set(5)
    print(SLOT.get())
    print(std.once.peek())
}
```

    error: internal compiler error at sawc/std/once.saw:99:44 (Identifier):
           Undefined variable: State

The diagnostic points INTO std's own source at a line the author did not write,
and the failure is an ICE rather than a refusal. `std` is the standard library's
reserved import root (`import std.X` never reaches a user module — DF-225e), so
either an inline `module std` should be refused where it is declared, or it
should be an ordinary user module whose declarations cannot displace std's.

Not a tag collision: since SL-274's r3 the module tag keeps the two apart
(`("<std>", "once")` renders `std_once`, a user `("std", "once")` renders
`_173_td_once`). What collides is earlier — the module-keyed name view std's own
file resolves its private `State` through.
