## Description

Found by design 275 U4's disagreement sweep (obligation 4), probed on main at
46d6db9c and unchanged by U4, which is behaviour-preserving.

Design 260's two fences on a SUSPENDING consuming body
(`typechecker/consumes.py::_check_consumes_suspending_fences`, ~:196) gate on the
BROAD bit — `node.suspends`, "might". Their reason is a FRAME: a suspending
method's receiver is hoisted into the CALLER's coroutine frame, whose per-slot
release can neither skip a field nor take a hand-written `deinit`'s place. A body
that "suspends" only by the conservative closure-call cause is never hoisted
anywhere — no frame is built for it at all (SL-306) — so neither fence applies.

REPRO (main, 46d6db9c — `.build/scratch/probe_consumes_conservative.saw` in the
sl318u4 worktree):

    func apply(f: (Int) -> Int) -> Int { f(1) }

    struct Holder { r: Res, n: Int }
    extension Holder: NoCopy { func deinit(&var self) { print("holder gone") } }
    extension Holder {
        func finish(&var self) consumes -> Int { apply({ v in v + self.n }) }
    }

    error: `finish` is `consumes` on `Holder`, which has a hand-written `deinit`,
    and it SUSPENDS — design 260 v1 does not support that combination
    hint: ... Make the consuming method `sync`, or drop the hand-written `deinit`

Nothing in `finish` parks. The hint's first out is the tell: writing `sync` on
the method is refused too (the same conservative cause violates a `sync`
declaration, correctly — it is not provably suspension-free), so the author is
told to do a thing the compiler will not accept, and the only way out is to stop
calling a closure-taking helper. The field-move fence (the same function's other
arm) reads the same bit and refuses the same way.

MECHANISM (obligation 4): the same one as the parameter-default refusal filed
beside this — a consumer that must decide "is a FRAME owed here?" reading the
derivation that answers "is this provably suspension-free?". Design 275 U4 makes
both askable by name (`frame_boundary` vs `might_suspend`) and preserves every
consumer's current reading.

FIX DIRECTION: both fences ask `frame_boundary`. Strictly widening (a program
refused today would compile), and the receiver-in-the-caller's-frame argument
they rest on is exactly what `frame_boundary` decides, so the fix is one word per
fence once the ledger owns the reading — SL-318 U1/U2.
