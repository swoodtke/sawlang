**The entry-point rule, by case:**

| `main` | verdict |
|---|---|
| `-> UInt8` (invalid IR on main) | `entry.result` |
| `-> Int32` | `entry.result` |
| `-> Never` | `entry.result` |
| `-> String` | `entry.result` |
| `-> Code` (`type Code = Int`) | `entry.result` |
| `-> Result<UInt8, E>` | `entry.result` |
| `main(n: Int)` | `entry.parameters` |
| none at all | `entry.missing` |
| `func main()` beside `func main() -> Int` | `overload.indistinguishable`, the existing overload rule, which fires first; `entry.duplicate` has its own two fixtures |

**One observation for a ruling, not a blocker** (it predates this patch and isn't its scope). The spec's table says `-> Int` and `Result<Int, E>`'s `Ok` set the exit status to "the value". The OS keeps only its low 8 bits:
- `Ok(256)` exits **0**, a success;
- `Ok(300)` exits 44;
- `Ok(-1)` exits 255.

A program returning a failure code of 256 reports success, the collision "never hide errors" rules out. Either the spec states the low-8-bit rule, or the entry point refuses or clamps an out-of-range value at run time. That's worth filing for the user to decide.
