## Description

**The ESP32-S3 target has one IR pin and no word check.** `check_xtensa_object` (the run lane) holds that sawc writes an ELF32 Xtensa object with the triple and the one attribute group. The riscv32 target has more, in `compiler/tests/run/riscv32_ir.py`: every probe's `.ll` at the target is read for an `i64` the 32-bit word doesn't allow, each probe's undefined symbols at -O0 are held to a known set (the runtime seam, the `__atomic_*` routines the target's width allows, compiler-rt's helpers), and a wide probe is checked to render `Int64` through the 64-bit renderers. Xtensa is a second 32-bit target with a different answer on two of those: word atomics are inline (`s32c1i`), and there is no FPU by default, so `Float` arithmetic is soft-float libcalls. Nothing holds either today; the freestanding suite's row would catch a wrong word only where a case happens to run it.

**Goal:** the word check runs for both 32-bit targets from one table-driven module, and the Xtensa row's undefined-symbol set is pinned.

**Read first:** all of `compiler/tests/run/riscv32_ir.py` (its docstring's rule, `ALLOWLIST`, `atomic_routines`, `i64_problems`, `symbol_problems`, `sawc_object_problems`, `wide_problems`, `check`); in `compiler/tests/run/run_lane.py`: where `riscv32_ir.check` is called, `check_xtensa_object`, `XTENSA_TARGET`; `compiler/target/src/layout.saw` (`target_word_bytes`, `target_native_atomics`, `target_effective_features`, `target_cpu`); `compiler/tools/build.py` (`runtime_manifest`, `choose_clang`, `clang_candidates`); LANGUAGE_SPEC.md's paragraph on `xtensa-esp-unknown-elf` (search "is the ESP32-S3").

**Implementation.**
1. Step 0, a census, before any edit: for each probe `riscv32_ir.check` reads, emit the `.ll` at `xtensa-esp-unknown-elf` with the same flags and run `i64_problems` and the undefined-symbol read on it with Espressif's clang (the one the stage build recorded for the triple). Record a table: probe, i64 problems (expected none: the word rule is the same), undefined symbols not in riscv32's allowed set. The interesting column is the last: soft-float helpers (`__adddf3`, `__muldf3`, `__floatsidf`, ...), 64-bit division helpers, `__atomic_*_8` for 64-bit atomics, and whether any `__atomic_*_4` appears (it must not: word atomics are inline with `s32c1i`).
   - If any probe has an i64 problem on Xtensa that it doesn't have on riscv32, STOP: that is a compiler finding.
   - If an `__atomic_*_4` or narrower routine is referenced, STOP: likewise.
2. Make the module table-driven: a row per target (triple, the clang's lookup, the atomic routines its width and features allow, the compiler-rt helper set). Rename the module to what it now is (`word32_ir.py`), keeping `riscv32`'s behaviour byte for byte: its counts, its messages, its skip rule when no clang is recorded. Update the run lane's import, call and docstring line.
3. The Xtensa row: the same probes; the allowed undefined set from step 0, written as explicit names grouped by reason (seam, 64-bit atomics, soft-float, 64-bit integer helpers). When the stage build recorded no clang for the triple, the row skips and says so, as `check_xtensa_object` does.

**Out of scope.** A hard-float row (`--target-features +fp`): the no-FPU default is the approved minimal set, and a second feature set waits for a user of it.

**Expected outcomes.** riscv32's counts in the run lane's summary are unchanged. A new count for Xtensa of the same probes. No compiler source changes; if one seems needed, STOP and report.

**Tests and gate.** `compiler/tests/run.py --only seed,fixture_whitespace,programs,comments` under the suite lock; `tools/battery.sh citations patchgate`. `SUITE_INPUTS` in `tools/patch_gate.py` names files a part reads: if it names `riscv32_ir.py`, follow the rename there and run `patchgate`.

**Docs.** None: the spec already states the target's defaults.
