## Description

**The coroutine blocking-deinit analysis cannot see a capture's `blocking` deinit behind a function value's release glue.** Found by p525 (SL-525 step 2) while reading the code; no probe has confirmed it yet.

The analysis walks drop-glue bodies to find a `blocking` deinit that a drop would reach. SL-525 gives function types copy and drop glue items with no MIR body: the backend writes them (an atomic retain; an atomic release whose last holder runs the capture tuple's drop glue). The walk therefore stops at the function value. A closure that captures a value whose deinit is `blocking` can be dropped in cooperative code, and the last release runs that deinit on the cooperative thread, with no refusal and no offload.

**Mechanism (obligation 4):** a drop path the analysis cannot read, because the glue is written in the backend and not in MIR. Other such paths to sweep: any other body-less glue (`Arc`'s release? `Box<any Trait>`'s erased drop?), and an erased `any Trait` whose dynamic deinit blocks.

**Scope:**
- probe it: a closure capturing a value with a `blocking` deinit, dropped in a task body, then dropped in a `sync` callee;
- route the function value's release glue through the analysis, either by attributing the capture tuple's glue to the release item or by treating a closure type as "may block in drop" when any capture's drop may block;
- carry the answer on the closure type, the way SL-795 carries `sendable`, so a function-typed parameter is judged too;
- pin each route.

**Air: a control, and a simpler rule for the escaping case.**

**Control (main, before SL-525):** a NON-escaping closure `{ [move p] in p.n }` capturing a `Pool` with a `blocking` deinit, built and dropped in a task (`air-review/sl812/b1_nonescaping_move_capture.saw`), is refused twice: `coro.closure-drop-blocks` at the closure and `coro.task-drop-blocks` at the task. Since SL-805 that environment is a MIR local, so its drop is visible. The gap SL-812 describes is ESCAPING closures only, through SL-525's backend-written release.

**A simpler rule than routing the release glue through the analysis:** an escaping environment is refcounted and shared, like an `Arc`. Its captures drop with "whichever handle goes last", which is exactly why SL-782 refuses a blocking-drop value as an `Arc` payload in ANY context (`coro.blocking-drop-position`, beside `Channel` elements, `Box<any …>` and task results). So: **a value whose drop blocks may not be captured by value or by move into an ESCAPING closure**, refused at the capture with the same position wording, in thread context too.

That:
- needs no glue walk and no new effect on function types;
- matches how SL-782 placed the other hidden-drop positions;
- leaves non-escaping captures to the existing analysis, which already reads them.

The obligation-4 sweep then reduces to that one position. `Arc`'s release and `Box<any …>`'s erased drop are already refused as positions, which is why their body-less glue never needed reading. Pins: an escaping capture of a `Pool` refused in a task, in a `Thread.spawn` body and in `main`; the non-escaping control `b1` stays as it is.
