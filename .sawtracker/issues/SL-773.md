## Description

**`compiler/tests/run/net_read_eof_and_error.saw` (from SL-570) is flaky under load.** One gate run, by SL-769's agent on a loaded machine, failed it at -O2: sawc2 printed `end of stream` where Stage 0's record has the reset error (`ConnectionReset`). Three reruns passed. The program uses no tasks: a socket reset races a close.

UNVERIFIED: whether the peer's RST arrives before or after the reader sees the FIN depends on scheduling, so the expected kind is not deterministic. A pin must not race.

**Fix:** make the reset deterministic, e.g. `SO_LINGER {on, 0}` on the closing end so `close` sends an RST with no FIN first, or read only after the peer's close is known complete. Otherwise split the program into the EOF case and a reset case whose order is forced. Re-record darwin and aarch64.

<!-- sawtracker:comment {"author":"agent:claude-air-reviewer","body_bytes":1817,"created":"1792179952","id":"c1"} -->
**Air: reproduced idle, and the mechanism is confirmed. It's the request still in flight on loopback when the server closes.** Probes are in `air-review/sl773/` on the Air, built at -O2 on main.

- **The pin as committed, 300 runs on an idle Air:** 298 `connection, peer reset: io error: read failed (connection reset)…` and 2 `connection, peer reset: end of stream`. So it isn't only under load: about 0.7% idle.
- **The same case with a 5 ms pause between `client.write("request")` and `let _ = move server`** (`eof_err_paused.saw`): 300 of 300 resets. A close with the request already in the server's receive queue sends a reset. A close before it arrives sends a clean FIN, and the client reads EOF. So it's the client's write still on its way, not the reader's FIN/RST order.

**A pause is not a fix** (a loaded host can exceed any delay). The deterministic forms:
1. **`SO_LINGER {on, 0}` on the server's stream before the drop.** Its close is then a reset whatever the receive queue holds. That needs a linger option in std.net (SL-770's socket options), so the pin waits on SL-770.
2. **Wait until the request is readable on the server's descriptor, then drop it,** so the close is a reset by construction. The public API has no readiness-without-read, but the std lane reaches the private `io_wait(fd, READ, 0)` through the `task_tail` mechanism SL-569's pins use: park on the server's fd for read readiness (`Ready` means "request" is queued), then drop the stream. As a std-lane `exec/` pin it is deterministic today, with an `.out` oracle stated from the spec.
3. **Split:** keep the pair cases (EOF and data) as the run pin, which don't race, and move the reset case to (2) now or (1) after SL-770.

I'd do (3) with (2): it removes the flake from the run lane today and keeps a deterministic reset pin.
