DESIGN CARRIER (user ruling, Sep 18, on design 275 §3 ruling 2): the two call shapes the by-value frame embedding of design 44 cannot serve get ONE design, landing together — a HEAP-ALLOCATED frame with an indirect resume.

1. Existential dispatch of a suspending conformance body (`any Trait` receiver; K37, DF-223b). A frame is a compile-time identity and dynamic dispatch has none, so the callee's frame cannot be embedded in the caller's; a vtable slot must allocate and resume it.
2. Suspending self/mutual recursion (SL-287's refusal, SL-304's option 2 — left unruled by design 275 §4, revived here). A cycle has no finite embedded frame; the recursive edge must allocate its callee frame on the heap.

Both need heap allocation, both need a resume through a pointer, both are the same runtime shape, so neither lands alone. Until this design lands, design 275 U2's shape table records both as REFUSE PENDING THIS ISSUE, with the refusal message naming it (the message for a cycle names the recursive function — the anchor SL-280's landing asked for); K37 stays an XFAIL row citing it.

Questions the brief must settle (lead's list, not rulings): (a) the allocation is compiler-inserted, so `--no-hidden-alloc` (design 135) must reject it and the SURFACE must be explicit — a spelling at the call or the declaration that says "this frame is heap-allocated", reader-visible per the doctrine; (b) allocation failure surfaces as `Result<_, AllocError>` per design 234's one policy or is added to the five documented panic boundaries — decide, never swallow; (c) the allocator is a type parameter the way spawn's is, so freestanding targets (first-class) choose it; (d) deinit of a heap frame on cancellation rides the synthesized `__release` (design 124); (e) Send: a heap frame crossing a thread boundary follows design 88's confinement rule for any held reference.

Related: K37 row, SL-287, SL-304 (option 2), design 44, design 223 C2/C3, design 275 U2.
