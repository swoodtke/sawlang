## Description

Found by SL-333's sibling sweep (agent:claude-sl333, Sep 21), PRE-EXISTING and reproduced on the design-141 spelling before SL-333 changed anything. FIXED in the SL-333 branch, in the same walk, because it is one clause of the mechanism that brief was already repairing — filed so the defect is on the record rather than absorbed.

## The defect

Design 188 unit 2 charges a place borrow to its ROOT, so two by-reference accesses of one root in one call — at least one of them a place — are an exclusivity error on every copy tier. `typechecker/types.py::_build_access_path` is the walk that builds those access entries. It stepped through a `?.` hop (`BindOptional` / `OptionalEvalExpr`) and NOT through a `!` (`ForceUnwrap`), so a `!`-headed place fell out of the walk to `return None` and **never joined the call's access set at all**.

A conditional lend's place is normally reached through exactly that `!`: `m[k]!`, `v.get(i)!`, `doc.section(name)!`.

## Repro (compiles on `main`, both writes land)

```saw
struct Cell { n: Int }
struct Bag { rows: [Cell; 2] }

extension Bag {
    public func opt(&self, i: Int) borrows -> Cell? {
        if i < 0 || i >= 2 { return None }
        lend self.rows[i]
    }
}

func setboth(a: &var Cell, b: &var Cell) { a.n = 1  b.n = 2 }
func setroot(a: &var Cell, r: &var Bag) { a.n = 1  r.rows[0].n = 9 }

func main() {
    var b = Bag(rows: [Cell(n: 5), Cell(n: 6)])
    setboth(&var b.opt(0)!, &var b.opt(1)!)   // X16's shape — accepted
    setroot(&var b.opt(0)!, &var b)           // X31's shape — accepted
    print("{b.rows[0].n}")
}
```

Both lines are shapes the conformance suite already pins for the `m[k]` spelling (X16 "two exclusive place windows on one Vector in one call", X31 "a window on a trivial struct beside a `&var` of the same root). Written with a `!` head they compiled.

## Mechanism

One missing clause in ONE walk, not a scattered rule: `_build_access_path` enumerates the hops an access path is made of, and `ForceUnwrap` was the hop it did not know. `!` is the panicking spelling of a conditional lend's presence, so it adds no path component for the same reason `?.` adds none — the root and its field/index projections are what decide overlap.

Siblings probed with compile evidence before the fix (all cells in the SL-333 branch's sweep): the same pair through `m[k]`/`v.get(i)` (already refused — this is what made the `!` divergence visible), a window beside a plain `&root` and beside `&var root`, both orders of a mixed pair, and the same four with the window reached through a forwarded lend. `ForceUnwrap` was the only hop missing; `_render_lvalue_path` had the matching gap and rendered `<expr>` for the same nodes.

## Fix (in the SL-333 branch)

`ForceUnwrap` joins the `BindOptional`/`OptionalEvalExpr` clause in `_build_access_path`, and `_render_lvalue_path` renders `x!`. Pin: `examples/errors/place_window_through_a_forced_lend_charges_its_root.saw`, conformance row X41. Zero other corpus outcomes changed — the widened access set cost nothing.

The lead may close this at the SL-333 landing, or split the clause out if it should land on its own.
