## Description

**User decision: should a lone raw-backed enum case fold into an integer THROUGH a `Result` or an Optional?** Left open on purpose by SL-1087 (Nov 13), which fixed the case where a layer of the slot takes the case's own enum.

**What happens today, after SL-1087** (measured by the agent's census and by the Air's matrix):
```saw
enum Why: UInt8 { case Bad = 11 }
enum IoKind: UInt8 { case Closed = 3 }

func f() -> Result<UInt, IoKind> {
    return Why.Bad          // builds; the caller gets Ok(11)
}
let m: UInt? = Why.Bad      // Some(11)
```
A function returning `Result<UInt, IoKind>` that names ANOTHER raw-backed enum's case builds and answers `Ok`. That is the failure sawos hit (SL-1087) with a different mistake in front of it: the wrong enum's case, or a case of an enum that was the error type before a refactor.

**What the spec says** (Flag enums; a user ruling, amended Aug 21 and Aug 31 2026): "Where a declared integer type is in force — an annotated `let`, a field, an argument, a `return`, a `static`, an arm — the combination folds ... A LONE case folds there too". The words are "a declared integer type". The implementation peels the slot: an Optional's payload, and a Result's unique payload that is an integer, count as the integer slot.

**Options.**
- **(A) The fold needs the slot's own type to be an integer.** `let n: UInt = Why.Bad` and `return Why.Bad` from a function returning `UInt` stay. Through a wrapper it is a `type.mismatch` naming the enum and suggesting `as`: `Result<UInt, IoKind>` ← `Why.Bad`, `UInt?` ← `Why.Bad`. Closes the hole completely. Cost: a flag constant passed where a `UInt32?` is expected needs `as UInt32` (or the combination form, if combinations keep folding there: decide both together).
- **(B) Through an Optional yes, through a `Result` no.** An Optional has one payload and no second reading; a `Result`'s integer payload is where an error enum's case is most likely to be written by mistake. `UInt?` ← `Why.Bad` stays `Some(11)`; `Result<UInt, Other>` ← `Why.Bad` is a `type.mismatch`.
- **(C) As it is.** The fold goes through both wrappers whenever no layer takes the enum.

**The same question for a COMBINATION** (`Perm.Read | Perm.Write` into `Result<UInt8, E>` or `UInt8?`): it is the backing integer by rule, never the enum, so there is no "wrong enum" reading of it; (A) or (B) could still leave combinations folding through wrappers. Say which.

**Lead's recommendation: (A) for a lone case, combinations unchanged.** It is what the spec's sentence says, it leaves the flag idiom the ruling was written for intact (a lone flag into an integer slot), and a `Result`-returning function that names an enum case and builds should mean that enum, every time.

**If (A) or (B):** one condition in `expect` (`compiler/typecheck/src/bodies.saw`, beside `slot_takes_case_enum`): the integer peel may not pass through the wrapper kinds the ruling excludes. A census of std, the compiler, Blade and the corpus for code relying on the fold through a wrapper first (the Air's text sweep for SL-1087 found none returning a raw-backed case by name into a `Result`; arguments and Optionals were not swept). sawos should be asked to sweep too before it lands.
