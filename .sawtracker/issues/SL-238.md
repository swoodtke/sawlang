## Description

Confirmed on production sawlang checkout 30c5a55016aed806a2f94a64d62224c6cafc135a, macOS arm64, using its Python sawc compiler.

The lexer encodes an escaped brace as byte 0x01 followed by the brace. A legitimate Unicode escape for U+0001 followed by a Unicode escape for a brace produces the same token bytes. The parser unconditionally removes the marker, silently deleting real String content.

Reproducer:

```saw
func main() {
    let escaped = "\{"
    let literal = "\u{1}\u{7b}"
    print(escaped.len())
    print(literal.len())
    print(literal.byte_at(0) as Int)
}
```

Expected stdout: `1`, `2`, `1`. Actual stdout: `1`, `1`, `123`, exit 0. The intended two-byte String (U+0001 and `{`) is changed to a one-byte `{` String. This example does not use interpolation. The same marker mechanism is used for closing braces.

Relevant implementation: sawc/lexer.py:381-383 inserts `\x01{` / `\x01}` for escaped braces; sawc/parser/expressions.py:731 removes either sequence by replacement, without provenance. The existing selfhost/lexer/src/lib.saw read_string follows the same marker protocol, so its StringLit token representation is also ambiguous. Preserve whether a brace came from an escape independently of real content (or use an unambiguous encoding), and test literal marker bytes beside both braces as well as ordinary escaped braces/interpolation.

Local standalone source: /Users/swoodtke/Projects/sawlang/.build/scratch/string_brace_provenance.saw. Compiled with `/Users/swoodtke/Projects/sawlang/.venv/bin/python sawc/sawc.py .build/scratch/string_brace_provenance.saw -o .build/scratch/string_brace_provenance`, then executed directly. No production files changed. Found while implementing isolated owned-String support in the compiler prototype; that prototype will preserve literal provenance rather than reproduce this behavior.

Review of SL-238.p1 revision 1 (base 4f488e5a; server-tested 6d5ef843): request changes.

P1 — Migrate the minivm frontend with the selfhost lexer API change.

At selfhost/lexer/src/lib.saw:1322, lex() now returns Result<LexResult, LexError> instead of Result<Vector<Token>, LexError>; Token also gains required seg_start/seg_count fields. The existing consumer in prototypes/minivm/src/frontend.saw was omitted from the migration. As a result, the prototype already on main no longer builds.

Reproduction from the patched checkout:

    /Users/swoodtke/Projects/sawlang/.venv/bin/python sawc/sawc.py prototypes/minivm/src/main.saw --module-path sawlex=selfhost/lexer -o .build/scratch/minivm

This produces five errors: four missing-field Token initializers at frontend.saw:7, :2935, :3209 and :3453, plus `field tokens expects type Vector<Token> but got LexResult` at :3526. The identical command succeeds on the exact unpatched base 4f488e5a. This is an introduced build regression, independent of implementing interpolation in the prototype. The design's exclusion of prototype string-handling work does not remove the need to keep this existing API consumer building.

Please migrate the frontend's lex result extraction and all token construction/copy sites together with this change, retaining valid segment provenance wherever it is used, then build and run the minivm regression harness. The prototype may continue rejecting interpolation as before; no feature expansion is required.

Validation: all eight focused string/interpolation/position tests passed, including the original U+0001 reproducer and the pattern/raw-control-byte coverage. git diff --check passed. The tracker reports its full compiler/freestanding gate passed for 6d5ef843, but that gate did not catch the prototype build regression. The typed-segment approach addresses the original ambiguous encoding; the missing consumer migration blocks approval.
