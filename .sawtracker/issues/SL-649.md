Found while building SL-641 (agent p641policy); not reduced yet.

**Symptom:** in `refuse_second_policy` (`compiler/typecheck/src/conform.saw`, SL-641's patch), the lines

```saw
let e = self.conformances[earlier]
let start = self.res.nodes[e.node].start
```

made Stage 0 report "undefined variable `start`" when building Stage 1. Renaming the two locals made the error go away. A small scratch file with the same shape didn't reproduce it, so the trigger depends on something in the surrounding function or file.

**Why it matters:** this is a Stage 0 defect in code the self-hosted compiler is written in. The renamed site is a workaround with no `// Stage 0 workaround (SL:hazards <id>)` marker, because no hazard id exists for it yet.

**Wanted:**
1. Reduce it from SL-641's tree: restore the original names in `refuse_second_policy` and shrink until the cause is named (a shadowing check misfiring on `start` against the field read, a `let` name colliding with a field or method `start`, or something else).
2. Write the SL:hazards entry, with an "Instead" and whether a checker rule is needed.
3. Mark the renamed site with the Stage 0 workaround marker and its canonical spelling.

**The minimal Stage 0 repro (r649reduce), three files per side; the trigger needs a module boundary.** Build with `./.venv/bin/python sawc/sawc.py main.saw -o out` in each directory. The trigger fails `undefined variable \`s\``; the twin compiles. Published as SL:hazards L33 (r92).

`trigger/inner.saw`:
```saw
public struct Node {
    start: Int
}

public struct Inner {
    node: Node
}
```

`trigger/outer.saw`:
```saw
import inner.{Inner}

public struct Outer {
    res: Inner
}
```

`trigger/main.saw`:
```saw
import outer.{Outer}

func show(x: Int) -> Int {
    x
}

func f(o: &Outer) -> Int {
    let s = o.res.node.start
    show(s)
}

func main() {
}
```

`twin/inner.saw`:
