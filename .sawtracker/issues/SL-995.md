## Description

**Observed (the Air, Nov 8, on current main):** `sawc build ... --target-features +strict-allign` builds and exits 0, and writes the object. LLVM prints "'+strict-allign' is not a recognized feature for this target (ignoring feature)" twice, and nothing else follows from it. So a misspelled feature silently drops the property it was meant to set. For sawos's `+strict-align,-fp-armv8`, that would be an unaligned-access or FP-register hazard in kernel code, with no failing build. This is a follow-up from SL-865 unit 1 that was never filed.

**Mechanism:** `driver_features_ok` (`compiler/driver/src/main.saw`) checks only the list's characters and the `forced-atomics` rule. Each name then goes to clang/LLVM, whose unknown-feature report is a warning written by the backend: it doesn't change the exit code, and sawc doesn't read it.

**Wanted:** a misspelled or unknown feature for the selected target is a usage error naming the entry and the target. This follows "never hide errors"; a warning isn't enough. It's open how sawc learns the target's feature set: ask the selected clang (it varies by clang version and target), keep a table per supported target, or treat LLVM's "not a recognized feature" text as fatal. Settle that in the brief.

**Sweep (obligation 4):** check every place the feature list reaches LLVM (`sawc build -c`, a linked build, `--emit-ll`'s attribute group, `sawc runtime --target`), and each supported target (aarch64/x86_64 hosts, riscv32, freestanding aarch64), so no path keeps the silent ignore.

**SL-995.p1: a `--target-features` entry the target's clang doesn't recognize is a usage error** (the Air's SL-865 follow-up, Nov 8)

- **The mechanism:** LLVM drops an unknown feature name with its own "is not a recognized feature for this target (ignoring feature)" line. That isn't a clang diagnostic, so `-Werror` can't catch it, and the exit is 0.
- **The check:** `driver_check_feature_names` asks the very clang the build runs. It compiles a one-function probe module carrying the list for the build's clang triple, through the driver's `driver_captured` funnel (the driver runs nothing that suspends), and refuses each name the output reports, once each, with exit 2. The message names the entries, the target and the clang. A real feature of another target is caught the same way (`+sse2` on arm64, `-fp-armv8` on riscv32).
- **Scope:** it runs where `sawc build` runs clang (a link, `-c`, split units), and only when `--target-features` is written; the freestanding profile's default list isn't re-checked. `--emit-ll` compiles nothing and writes the list as given, as the run lane's attribute-group rows need. The checking subcommands run no clang.
- **Pin:** the run lane's `check_attribute_groups` builds the attribute probe with `-c` for the host three times, each checked for exit code and object:
  - an unknown name, refused with exit 2, naming it, no object;
  - the other architecture's name, refused the same way;
  - the host's own name (`+neon`/`+sse2`), which builds.

  The run README follows.
- **By hand (arm64-apple-darwin):**
  - `+strict-allign` gives exit 2 and no object;
  - `+neon` builds;
  - `+neon,+sawc-x,+sse2` names `+sawc-x` and `+sse2`;
  - `--emit-ll +foo,-bar` is unchanged;
  - sawos's `--freestanding --target aarch64-unknown-none-elf --target-features +strict-align,-fp-armv8` builds.
- **Gates:**
  - `run.py --only seed,units,golden,subset,fixture_whitespace,std,programs`: ok, with 12 attribute rows pinned and the std cone unchanged;
  - `battery.sh citations`: green.
