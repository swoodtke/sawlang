## Description

**The coro lane's Stage 0 records (`compiler/tests/coro/stage0/`, `refusals.tsv`) have drifted from what Stage 0 produces today, and nothing noticed.** Found by SL-768 c1 (agent p768err, Oct 19). A full `snapshot.py --write --jobs 8` on its branch changed 94 records plus `index.tsv` and `refusals.tsv`. Only 8 of those were c1's intended stream move; the other 86 differ for reasons unrelated to it:

| records | what changed | example |
|---|---|---|
| 55 | the build line and everything after it | `net_loopback_echo`: `build ok` became `build refused`, ``` `try` requires a Result type, got `Int` ``` |
| 15 | the refusal log only | `refusals/errors/spawn_capture_not_send`: a 22-line diagnostic became `Parse error at 13:31: two statements on one line need a ';'` |
| 8 | the `twin` line only | `two_copy_arc`: `twin same` became `differs` (confirmed with `cmp`) |
| 8 | other combinations (`btframe`, `meets_expect`, `expect`) | K32, `signal_concurrency_pins`, `taskgroup_stale_handle_cancel` |

In `refusals.tsv`, D11, K112 and K114 flipped from `yes` to `no: no error contains …`.

**The evidence that it predates c1:** main's unmodified Stage 0 (73584cbee) refuses `examples/errors/spawn_capture_not_send.saw` with the same parse error, and `two_copy_arc`'s old `twin same` line was already false. Likely cause, UNVERIFIED: corpus or `examples/` twins edited since the snapshot was written (several by SL-768's `Result`-API rewrites and SL-765), with no lane re-checking these records against a live Stage 0 run.

**Asked (obligation 4, a class until swept):**
1. Which lanes read these records, and why none fails when a record no longer matches. If a record that silently goes stale can't fail anything, either the lane needs a freshness check or the records are dead weight.
2. Do the corpusdiff `stage0/` records and the run lane's have the same exposure?
3. Then a clean re-snapshot on main, with each verdict change explained. D11, K112 and K114 in particular: is each flip a stale record, or a real change in what the refusal says?

Small to medium; a sweep agent (read-only) first.

**Air on questions 1 and 2, by reading the three checkers on main 73584cbee: the coro snapshot is the only one of the three Stage 0 record sets with no freshness check.**

| record set | its checker | what notices a source edit after the record was written |
|---|---|---|
| corpusdiff `stage0/` | `corpusdiff.py`'s snapshot check | each `index.tsv` row carries `twin_sha` (sha256 of the `examples/` twin). A changed twin fails with "examples/X has changed since its record was written", and a changed twin relation fails with "the twin is X now, Y in its record" |
| run lane `stage0/HOST/` | `run_lane.py` | its docstring: "a program without one, or whose bytes changed since it was made, fails until it is rerecorded" |
| coro `compiler/tests/coro/stage0/` | `snapshot.py check()` | **nothing.** `INDEX_COLUMNS` has `twin` but no source hash, and `check()` compares each row with its record, requires every record to have a row, and requires each refusal test's log to exist. The `twin` column is copied from the record, never recomputed from the files |

**This accounts for every kind of drift in the description:**
- An edited program can't fail the check. That covers the 55 build-line records and the 15 refusal logs.
- `twin same` → `differs` isn't recomputed. That covers the 8 `two_copy_arc`-style rows.
- The `refusals.tsv` flips aren't re-checked against a live run.

**The fix by precedent is corpusdiff's:** a `twin_sha` column (or a source hash) per row. A mismatch fails, naming the `snapshot.py --write` to run. The `twin` column is recomputed from the files, as corpusdiff's check does with `oracle.twin_of`. That turns question 3's clean re-snapshot into something the lane enforces from then on, instead of a one-time cleanup.
