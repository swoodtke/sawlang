## Description

**Lending a static from a `borrows` function.** Ruled by the project owner (Nov 17, in the lead's session, on SL-1155): design it. sawos's SO-124 design wants `func held() unsafe borrows -> &Res { lend HELD }` over an `unsafe static var`.

**Today:** a `lend` must be rooted in the receiver (LANGUAGE_SPEC.md: "An accessor lends storage its receiver already owns"; borrowck's `lendable_root`, `lend.root`); lending a static is refused even from a method; a receiver-less `borrows` function crashed MIR (SL-1155 fixes the crash, refusing those lends cleanly). The SL-1155 sweep (`.build/scratch/p1155/sweep.md`) maps the lowering's receiver assumptions: `prepare_lend`, `window_open` (always passes the receiver; about ten callers), the split halves, borrowck's `MirLocalKind.Receiver` root.

**To design (Opus, with a prototype):**
- Which statics may be lent and from what: a plain `static` (immutable: a shared lend is free) versus an `unsafe static var` (in an `unsafe` function only?); a field or element of one; shared versus `&var` lends.
- The exclusivity story: a static is reachable from every task and thread. What the window guarantees, what the compiler checks (a second lend of the same static inside the window; a lend held across a suspension, when another task can run), and what stays the `unsafe` author's obligation, stated in the spec.
- Receiver-less functions and `static func`: whether a `borrows` function needs a receiver at all once a static can be its root, and a parameter's place (still refused?).
- The lowering: a receiver-less window through mir, borrowck, drops, mono, coro; the position matrix (sync, suspending body, closure, generic, conditional lend, across a call and a suspension) with each cell's verdict.
- The spec's Places section, the conformance rows (a safety guarantee changes: rows first), and the units.

Lands after SL-1155. Related: SL-1155, SO-124 (sawos), design 141 (places).

**The owner's framing (Nov 17, in the lead's session): what is held shared or exclusively by a function with no receiver?** For a method, the window is charged to the receiver, which the caller sees written at the call (`v.first()` holds `v`; `v.push` inside the window is `loan.window-root`), and the use site picks shared or exclusive out of the one `&self` declaration. A free function lending a static needs the same concept: the static is the window's root. This is the design's central question, not a detail. Two consequences it must answer:
1. **The caller cannot see the root.** `held()` names nothing; borrowck is per function, so the caller needs the lent root from something it can read: the signature naming it (e.g. `borrows HELD`, which the doctrine "reader-visibility trumps inference" favours) or an inferred per-function summary. Recommend one, with what each costs.
2. **The root is global.** Conflicting uses can come from any function the caller calls during the window and from other tasks and threads, none visible in the caller's body. Say what the compiler checks (a lexically visible second lend or write of the same static), what it restricts to stay checkable (shared lends only of a mutable static? no suspension inside the window?), and what stays the `unsafe` author's obligation, stated in the spec.

**The owner's preferred spelling (Nov 17, in the lead's session): the function declares its root, `borrows(HELD)`,** so `HELD` is the thing that is borrowed, as the receiver is for a method: `func held() unsafe borrows(HELD) -> &Res { lend HELD }`. The design builds on it (the lead's reading, to confirm with the prototype):
- **Caller side:** `held()` charges a loan on the declared root for the window (shared or exclusive picked at the use site, as for `&self`); a lexically visible conflicting use of `HELD` in the caller during the window (a direct read or write, another `borrows(HELD)` call, `&var HELD` as an argument) is refused as `loan.window-root` refuses `v.push` today.
- **Callee side:** `lend.root` checks the lent place is rooted in the declared root (`HELD`, a field or element of it) instead of the receiver.
- **Borrowck:** a static becomes a loan root (a new root kind keyed by the declaration, conflicts by root plus projection path); the receiver-less window through mir, drops, mono, coro.
- **Still open (questions for the owner, each with a default):** a function the caller calls during the window that touches the root, and other tasks and threads (an `unsafe` obligation the spec states; or restrictions that keep it checkable: shared lends only of a mutable static, no suspension inside the window); an immutable `static` (shared lends always sound); several roots (`borrows(A, B)`); a parameter as a declared root; the grammar (the effect slot beside `unsafe`, `sync`).

**The owner (Nov 17, in the lead's session): a lent static must be private, so its only references are in the module that defines the `borrows(HELD)` function.** The lead's reading of what that buys, for the design to confirm:
- Every direct use of `HELD` is in one module, so the set of that module's functions that reach it (directly or through other functions of the module) is finite and computable; the compiler records "touches `HELD`" on each, as the root is recorded on `borrows(HELD)`.
- A call, inside a window on `HELD`, to a function that touches `HELD` is then refused like a direct use, in any caller in any module (a caller elsewhere never names `HELD` but sees the recorded fact on what it calls). The guarantee widens from "visible in the caller's body" to "every touch of `HELD` in the program", with no user-written effect system.
- Still open: other tasks and threads (a suspension inside the window lets another task run; another thread can run at any time): no suspension inside a window on a static, and for a mutable static reachable from several threads a sync guard or an `unsafe` obligation. And whether "touches `HELD`" is written in each touching function's signature (reader-visibility) or inferred and recorded (all within one module): a question for the owner with a default. The refusal for a non-private lent static: a rule and message at the `borrows(HELD)` declaration.

**The owner (Nov 17, in the lead's session): once any function declares `borrows(HELD)`, naming `HELD` anywhere else is a compile error** (with `HELD` module-private: every access to it goes through a `borrows(HELD)` function's window). The lead's reading, for the design to confirm:
- Every access path to `HELD` is a window, so a conflict on `HELD` is exactly two overlapping windows on it, which borrowck already reasons about for a receiver; every function that touches `HELD` directly DECLARES `borrows(HELD)` (reader-visible); the rule itself is a declaration-level check in one module ("`HELD` is named only inside a function declaring `borrows(HELD)`"; the static's own declaration and initializer excepted: say how).
- **Still to design:** a function `f` that calls `held()` internally opens a window on `HELD` without declaring it; a caller holding an EXCLUSIVE window on `HELD` that calls `f` overlaps invisibly. So "opens a window on `HELD`" must flow up the call graph, across modules (`held()` may be public), as the compiler already infers suspension transitively: a compiler-recorded fact per function, and inside an exclusive window on `HELD` a call to anything carrying it is refused (two shared windows may overlap). The design weighs inferring it against writing it, with a default.
- Tasks and threads as before: a window on a static never spans a suspension (checkable through the inferred suspension); a mutable static reachable from several threads needs a sync guard or stays an `unsafe` obligation.

**sawos's use case (chat m1268, Nov 17; SO-124's design `SO:sosmain-startup` §2-§4), at the owner's request, for the design pass:**
- **What is held:** one `Boot` value built in `_start`'s frame (the process's `System`, its `Process`, its `BootSet`, its console client `Uart<PipeTransport>`), each with a `deinit`; written once before `__saw_main`; read by `main` and every later thread for the life of the process through accessors (`sosmain.system()`, `process()`, `boot_set()`). Today SO-124 parks the frame value's address in a static and lends through the pointer (rooted in a frame, not a static). **What fits SO-124 best: a static that holds the value itself** (`private unsafe static var BOOT: Boot?` with `deinit`-bearing fields, never dropped or dropped at process end), lent by `borrows(BOOT)` accessors. If statics must stay trivially destructible, SL-1156 covers only three parked handle words and the frame lend stays an `unsafe` pointer step.
- **The parked words** (System, Process, console-inlet handle words, `UInt`s, written once at start-up) are read from other modules (`rt/common`, `kernel/sysapi`'s floor) as `unsafe` word reads; they need no lend. The kernel touches neither.
- **One module** for the `Boot` lends (`sosmain`): yes.
- **Shared** lends of System and Process (their ops take `&self`); **exclusive** of the BootSet (`take(&var self, tag:)`) and of the console client if its `write` keeps state.
- **Windows across blocking calls:** yes, routinely (`main` holds `&Process`/`&System` across `Waiter.wait` and pipe calls); across suspensions later (a suspending `main` with SL-1150), shared. **Threads:** several threads read System and Process concurrently (shared windows); the BootSet's exclusive window is start-up's and `main`'s, accepted as an `unsafe` obligation or a sync guard.

**What this asks of the design (the lead's reading):** (1) a static holding a value whose type has a `deinit` (written once, never dropped or dropped at process end), which is new beyond lending; (2) the tasks-and-threads rule refined: SHARED windows on a static may span blocking calls, suspensions and threads (they read), while an EXCLUSIVE window is the restricted one (no other window on the static while it is open: checkable within the module, an `unsafe` obligation or a sync guard across threads); so "no suspension inside a window on a static" applies to exclusive windows only. Both are questions for the owner, with defaults, in the design.
