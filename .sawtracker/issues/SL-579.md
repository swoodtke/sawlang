**SL-579.p1 submitted: A17b, the Send-on-frames gate** (agent p579send, Opus; one commit, 378163cb0).

- **New `compiler/coro/src/send.saw`** (`coro.spawn-not-send`), called once after `coro_find_frames` (`compiler/coro/src/api.saw`). For a group spawn it traces the group operand back through the spawner's MIR to `TaskGroup.init(threads:)`. It then checks, in Stage 0's order, the root's parameters, its resident locals, each embedded child's parameters and locals, and the root's result, and refuses the first value that can't cross, once per root.
- **What crosses** (the agent's reversible calls): `Send` and no borrowing struct (K146). A root's reference parameter is refused outright (spec, K19). Any other reference follows typecheck's rule (`&T` is `Send` iff `T: Sync`). `Void`/`Never` always cross. Any `threads:` label gates, `threads: 1` included, as Stage 0 does. That is stricter than the spec's "`threads: 1` remains the single-threaded engine"; no corpus row depends on it, and the lead takes it to the user with the issue below.
- **Acceptance:**
  - the six `wrong` rows (K02, K19, K31, `spawn_capture_mt_send`, `taskgroup_threads_nonsend_reject`, `window_in_a_threaded_group`) go `wrong` → `pass`, refused on Stage 0's line. K02 and K31 meet their first directive (ruling (a), c3);
  - `discard_send_leftover` is restored to the run lane, refused at `step` on darwin and aarch64.
- **Pins:** five `compiler/tests/coro/refuse/` fixtures (a reference parameter, a resident local, a child's local, the result, a borrowing iterator), plus a README rules row.
- **Gate (agent):** `run.py --only coro,mono,typechecker,programs,std,census,units,golden,seed,std_cone,subset,sanitize,parallel_order`, `corpusdiff.py gate` (2662 hold; exactly the six moves), `citations`, `gmgate` (86 programs, 0 failing), and the aarch64 run lane.

**A gap the spec documents** ("`threads:` is tracked on the group's binding, not yet through an opaque helper it is passed to"): a multi-threaded group passed to a helper as a parameter is NOT gated, so a non-`Send` frame can be spawned onto a worker through it. That is a soundness hole; it's filed separately, and its fix needs a user ruling.

**Read and agreed:**
- the trace from the spawn's group operand through a reference, a use, a cast and the `Result` payload to `TaskGroup.init(threads:)`;
- the order Stage 0 checks in: parameters, resident locals, each embedded child's, then the result;
- `coro_unsent`: `Send` and no borrowing struct, a root's reference parameter refused outright, any other `&T` crossing iff `T: Sync`, `Void`/`Never` crossing;
- the check running after `coro_find_frames`, on real resident sets.

**The gap this leaves is SL-788, not a regression.** Before this patch nothing was gated, and every direct spawn into a pool group is gated now (my `sl579p/g3` control: refused). A group reached through a helper parameter (g1) or a struct field (g2) still builds and runs a non-`Send` frame on a worker, as the spec's parenthesis says. I posted the probes and a fourth option, a per-root runtime bit checked on the pool path, on SL-788 (c1). I also posted that std's `init(threads:)` returns `TaskGroup()` for `threads <= 1` (c2). That makes this gate's refusal of `threads: 1` stricter than both the spec and the runtime, and a constant `<= 1` could be folded to "not threaded".

**Nit, not blocking:** `discard_send_leftover` sits in the run lane under `// due:`. The README defines `due` as "one sawc2 cannot build yet", and it says the lines come off when the slice reaches it. This refusal is permanent and correct, so the `due` lines would never come off. Its point is the SL-513 discard held across the arm's suspension, which belongs beside the other five as a `coro/refuse/coro.spawn-not-send.discard` fixture.
