**Make the per-patch gate use the machine's cores** (the user asked for this on Oct 13: "queue the test perf improvements").

**Measurement** (SL-594.p1's server run, typical for a compiler patch): 26m 58s holding the suite lock.
- **Compiler tests** (`compiler/tests/run.py`): 14m 25s.
  - Unit programs, the run lane and the census each use 8 threads.
  - The stage lanes (lex, parse, resolve, typecheck, mir, eval, borrowck, drops, mono, coro, std) each run their sawc2 calls one at a time, and run one after another.
- **Fixpoint** (`compiler/tests/fixpoint/fixpoint_lane.py`): 12m 31s, fully serial. That's about 915 independent Stage 1 against Stage 2 invocations.
- The machine has 16 cores.

Every merge re-tests every other approved patch, and agents' local gates queue behind the server on one lock, so gate time multiplies.

**Fix:**
1. **The fixpoint lane** runs its invocations on a worker pool.
2. **Each stage lane** runs its sawc2 calls on a pool, and/or `run.py` runs independent lanes concurrently.

Each lane's printed result must stay identical between a serial and a parallel run: same lines, same order, same counts, same failures. Results are collected and then printed in a fixed order, never in completion order. Keep one knob for the worker count (for example, `SAW_GATE_JOBS`, defaulting to the core count, with a cap), shared by every runner. Don't spread a constant across files.

**Done when:**
- Per-part wall times are measured before and after, under the suite lock with nothing else running: `run.py`'s lanes each, and the fixpoint lane.
- Serial and parallel output are identical for every lane (diff the two), pinned by a test or a lane check that runs a lane both ways on a small input.
- An injected failure, in one fixpoint invocation and in one stage-lane case, is still reported, with the same text and in the same position, in parallel.
- Nothing changes about WHAT is tested.

Perf by measurement: don't parallelize a lane whose time is negligible. Report each lane's share first.

**User ruling (Oct 13):** "keep the concurrency to at most 75% of the cores on a machine so we don't overload it". The gate's total concurrency is `max(1, floor(0.75 × cpu_count))` (12 on the 16-core Studio), counted across everything the gate runs at once. Concurrently scheduled lanes share one budget, never one pool each, and an explicit worker-count setting is clamped to the ceiling.

Approved patch SL-604.p1 (revision 1)

Approving SL-604.p1. The user's 75%-of-cores ceiling holds by construction, the output is the same serial or parallel, and I confirmed both on a second machine with a different core count: the Air has 10 cores, so the ceiling is 7, where the Studio's is 12. Patch applied to 43caeb9fd, exact tree 001ba311.

**The budget (`tools/gate_jobs.py`), read:**
- The ceiling is `max(1, cpus * 3 // 4)`, and `SAW_GATE_JOBS` is clamped to it. A non-count is an error, never a silent default.
- The outermost runner makes `jobs() - 1` token files, and its own thread is the implicit first token. Every child process inherits the directory. A token is an exclusive `flock`, which the kernel drops if its holder dies.
- `map_ordered`'s thread 0 runs on its caller's token, and every other thread takes a token for each item. So every busy worker holds a token: concurrent lanes share one budget and never multiply it. Thread 0 always progresses, and the others stop waiting once every item is taken, so a pool can't deadlock waiting on tokens held elsewhere.
- Fixed-width work is bounded too. The census, the one pool that takes no tokens, runs as a `run.py` step with `width=2`. That step holds two tokens and hands its process `SAW_GATE_JOBS=2`, so the census pool's `jobs()` is 2. The twin runs Stage 1 and Stage 2 at once only on a second token it holds, and never for a command that writes files.
- `test_runner.py`'s default worker count is now `jobs()`, and the per-patch gate runs its parts one after another, so the suite never overlaps `run.py`.

**Order is fixed:** each `run.py` part is a step in a process of its own, and output is merged in `STEPS` order, never completion order. The fixpoint twin writes one record file per call, and the lane sorts them.

**On the Air:**
- **The pin**, `compiler/tests/parallel_order.py`: ok, 2 serial/parallel comparisons (with failures injected into a coro case and into a Stage 2 call, each reported in the same place both ways) and 11 knob cases, in about 20 s.
- **All of `run.py`, both ways, diffed:**

| | wall time | result |
|---|---|---|
| parallel, ceiling 7 | 550 s | ok |
| serial, `SAW_GATE_JOBS=1` | 2047 s | ok |

Every line is identical, timing lines aside, except one count in the summary: 'recognizer records computed', 5387 parallel against 0 serial. That is the parse lane's cache (`parse_lane.py`: 'Each case's recognizer record is computed once and cached under a hash'). The parallel run went first and cold, and the serial run reused its records. So it reflects run order, not parallelism; reversing the order flips it. It predates this patch, but note that it makes a byte-for-byte comparison of two gate outputs depend on cache state.

The Air's 3.7× (2047 s to 550 s) is in line with the Studio's 887 s to 265 s for `run.py` at a ceiling of 12.

**Gate:** passed on the applied commit (tested_commit == applied_commit == 45da54121). Its tested_tree 001ba311 is exactly the patch applied to 43caeb9fd, the tree I built and ran both ways. Every part ran, since the patch touches `test_runner.py` and `tools/`: compiler tests passed in 4m 50s (today's other SL gates took 13m 22s to 15m 9s), fixpoint in 4m 1s (against 11m 58s to 13m 15s), and the Python suite, freestanding, the grammar corpus and astdiff all passed.
