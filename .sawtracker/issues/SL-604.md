**Make the per-patch gate use the machine's cores** (the user asked for this on Oct 13: "queue the test perf improvements").

**Measurement** (SL-594.p1's server run, typical for a compiler patch): 26m 58s holding the suite lock.
- **Compiler tests** (`compiler/tests/run.py`): 14m 25s.
  - Unit programs, the run lane and the census each use 8 threads.
  - The stage lanes (lex, parse, resolve, typecheck, mir, eval, borrowck, drops, mono, coro, std) each run their sawc2 calls one at a time, and run one after another.
- **Fixpoint** (`compiler/tests/fixpoint/fixpoint_lane.py`): 12m 31s, fully serial. That's about 915 independent Stage 1 against Stage 2 invocations.
- The machine has 16 cores.

Every merge re-tests every other approved patch, and agents' local gates queue behind the server on one lock, so gate time multiplies.

**Fix:**
1. **The fixpoint lane** runs its invocations on a worker pool.
2. **Each stage lane** runs its sawc2 calls on a pool, and/or `run.py` runs independent lanes concurrently.

Each lane's printed result must stay identical between a serial and a parallel run: same lines, same order, same counts, same failures. Results are collected and then printed in a fixed order, never in completion order. Keep one knob for the worker count (for example, `SAW_GATE_JOBS`, defaulting to the core count, with a cap), shared by every runner. Don't spread a constant across files.

**Done when:**
- Per-part wall times are measured before and after, under the suite lock with nothing else running: `run.py`'s lanes each, and the fixpoint lane.
- Serial and parallel output are identical for every lane (diff the two), pinned by a test or a lane check that runs a lane both ways on a small input.
- An injected failure, in one fixpoint invocation and in one stage-lane case, is still reported, with the same text and in the same position, in parallel.
- Nothing changes about WHAT is tested.

Perf by measurement: don't parallelize a lane whose time is negligible. Report each lane's share first.

**User ruling (Oct 13):** "keep the concurrency to at most 75% of the cores on a machine so we don't overload it". The gate's total concurrency is `max(1, floor(0.75 × cpu_count))` (12 on the 16-core Studio), counted across everything the gate runs at once. Concurrently scheduled lanes share one budget, never one pool each, and an explicit worker-count setting is clamped to the ceiling.
