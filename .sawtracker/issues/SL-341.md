## Description

The read-only build of `/Users/shawn/Projects/sawtracker/src/main.saw` dies in the LLVM BACKEND under the default pipeline, identically before and after design 275 U3:

    Assertion failed: (Delta.CriticalMax.getUnitInc() >= 0 &&
                       Delta.CurrentMax.getUnitInc() >= 0 &&
                       "cannot decrease max pressure"),
    function getMaxDownwardPressureDelta, file RegisterPressure.cpp, line 1350.

`sawc src/main.saw -O0 -c` COMPILES CLEAN on both, which is what locates it: the whole front end is satisfied — typecheck, place lowering, the coroutine transform (SL-215's inline catches and SL-317's collection `for`s included) — and the failure is in the machine scheduler's register-pressure tracking, reached only once the optimization pipeline runs.

Measured (Sep 22): branch `sl318u3` at `04ec6faf`+, main at `da84578e`. Same assertion, same function, both at the default `-O1`-style pipeline, neither at `-O0`.

This is the last thing between design 275's epic acceptance criterion — "a read-only build of `/Users/shawn/Projects/sawtracker/src/main.saw` that compiles, and whose IR shows no out-of-frame park in any driven path" — and its first half. The second half is checkable today at `-O0`.

WHAT TO LOOK AT FIRST: the assertion is llvmlite's bundled LLVM refusing a negative pressure delta while scheduling, which is usually reached through malformed-but-verifying IR rather than a plain LLVM bug — an enormous basic block, a very wide live range, or a `phi` shape the scheduler cannot account for. sawtracker's driven bodies are the biggest state machines in any tree we build, so the first bisect is which FUNCTION: compile with `-O0` (clean) and re-enable the pipeline per module, or narrow by deleting driven bodies until it stops. Filed as a finding rather than a fix because it is neither U3's nor the front end's.

LEAD ASSESSMENT + FIX OPTIONS (Sep 22) — for the user's ruling.

The sweep separates two facts. (1) The ABORT is LLVM's: an assertions build of LLVM 22.1.0 inside llvmlite 0.48.0, in the AArch64 pre-RA machine scheduler, on a shape a newer LLVM handles and a release build passes silently (the user's clang -O2 binary passes sawtracker's suite). (2) The SHAPE is sawc's: the coroutine transform's frame initialisation builds the whole embedded frame tree as ONE SSA aggregate value — thousands of `insertvalue` plus `Slot.empty()` calls in one straight-line block — and that block grows with the transitive embedded frame tree of a suspending call graph. That same emission is what SL-336 overflows (`visitInsertValue`'s 65535-value limit) and what design 263's census found sawc paying for elsewhere (whole-struct `load` + `extractvalue` per field read, 261-U2's memcpy conversion's missing enum sibling in DF-300a). Two bugs in LLVM, one emission in sawc.

Three paths, not exclusive:
A. **MITIGATION in sawc (small, immediate):** set `-enable-misched=false` on the AArch64 host target machine (via llvmlite `set_option` before the machine is created) — the whole sawtracker build then passes at the default level and the binary runs. Cost: pre-RA machine scheduling off for EVERY hosted AArch64 build, i.e. some codegen quality on all programs to fix four functions in one; and `set_option` is process-global and silently ignores unknown flags, so it needs a lane pinning that the flag still takes effect (the sweep's slice is that pin). Not a fix. If sawtracker already has `SAWLINK=clang` (ST-41), this may not be worth its cost — the user's call.
B. **THE FIX in sawc (the real one, a design brief):** emit coroutine frame initialisation as STORES into the frame allocation (zero-fill + per-slot stores through GEPs, or a `Slot.empty()` written in place), never as an `insertvalue` chain over a whole-frame SSA aggregate — the same move design 261 U2 made for aggregate copies. Closes the mechanism behind SL-341 AND SL-336 at once, shrinks the giant blocks that also cost compile time (a 76,000-line resume), and is the front-end's own emission, so it needs no LLVM change. Obligation 2 sweep: every consumer of the frame aggregate value (the spawn helpers, `__release`, the bt-table, `--emit-frame-layout`) and the IR-determinism/reemit lanes. Test: sawtracker's post-build `.ll` at the default level compiles; SL-336's overflow repro compiles; the corpus IR compare (design 220) classifies every change.
C. **llvmlite upgrade or rebuild (external):** a wheel on LLVM 23.x, or one built without assertions. Unknown availability; not under sawlang's control; would leave sawc's emission as it is (and SL-336's limit is a hard one regardless of assertions).

Lead recommendation: B as the brief (queued after SL-347's landing, sized as one unit + a mech sweep of the emission's consumers), with A only if the user wants `sawc -O2` on sawtracker before B lands — sawtracker's `SAWLINK=clang` already covers that need. SL-336 becomes B's second acceptance test rather than its own fix. The sweep's `slice_743_nodbg.ll` is the regression pin for the LLVM-side symptom; the corpus-wide "biggest frame-init block" census (sweep §5) is the metric B reports before/after.
