## Description

The read-only build of `/Users/shawn/Projects/sawtracker/src/main.saw` dies in the LLVM BACKEND under the default pipeline, identically before and after design 275 U3:

    Assertion failed: (Delta.CriticalMax.getUnitInc() >= 0 &&
                       Delta.CurrentMax.getUnitInc() >= 0 &&
                       "cannot decrease max pressure"),
    function getMaxDownwardPressureDelta, file RegisterPressure.cpp, line 1350.

`sawc src/main.saw -O0 -c` COMPILES CLEAN on both, which is what locates it: the whole front end is satisfied — typecheck, place lowering, the coroutine transform (SL-215's inline catches and SL-317's collection `for`s included) — and the failure is in the machine scheduler's register-pressure tracking, reached only once the optimization pipeline runs.

Measured (Sep 22): branch `sl318u3` at `04ec6faf`+, main at `da84578e`. Same assertion, same function, both at the default `-O1`-style pipeline, neither at `-O0`.

This is the last thing between design 275's epic acceptance criterion — "a read-only build of `/Users/shawn/Projects/sawtracker/src/main.saw` that compiles, and whose IR shows no out-of-frame park in any driven path" — and its first half. The second half is checkable today at `-O0`.

WHAT TO LOOK AT FIRST: the assertion is llvmlite's bundled LLVM refusing a negative pressure delta while scheduling, which is usually reached through malformed-but-verifying IR rather than a plain LLVM bug — an enormous basic block, a very wide live range, or a `phi` shape the scheduler cannot account for. sawtracker's driven bodies are the biggest state machines in any tree we build, so the first bisect is which FUNCTION: compile with `-O0` (clean) and re-enable the pipeline per module, or narrow by deleting driven bodies until it stops. Filed as a finding rather than a fix because it is neither U3's nor the front end's.
