## Description

**An enum case named `None` in a compiler module makes an unrelated `StringBuilder.append` call ambiguous.** Reported, unfiled, by a8bspawn (A8b, SL-564).

While building A8b, naming an enum case `None` in borrowck made an unrelated `StringBuilder.append` call in `compiler/borrowck/src/dump.saw` ambiguous during the Stage 2 build. Renaming the cases cleared it. A user enum case named `None` should not change overload resolution of an unrelated call. That suggests the case name leaks into a lookup it shouldn't reach, perhaps confused with `Optional.None` during candidate selection or literal typing.

**Owed:** reduce it to a minimal program, name the mechanism (obligation 4: which lookup sees a user case named like a prelude case), sweep the other prelude case names (`Some`, `Ok`, `Err`) for the same leak, and fix it or refuse such names with a clear diagnostic, per the spec.

Stage 0 refuses it at parse ("Expected variant name"). A reference `Mode.None` is a parse error before that (`n1.saw`). So either A8b's enum sat in a position where `name.none-case` doesn't fire, which is the mechanism to find (a nested or generic enum, another module, a `@test` enum?), or the ambiguity was reported beside that refusal and was its downstream. Only the original enum and the `dump.saw` call settle which; a8bspawn's discarded edit or a diff of it would do. If the refusal does fire at that position, this narrows to the cascade, a second diagnostic after a refused declaration.
