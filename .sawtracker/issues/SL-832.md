## Description

**A `consumes` method declared outside its receiver type's defining module is accepted, and silently skips the type's `deinit`** (found by p831, SL-831, Oct 23; reproduced on the seed). This is a soundness hole: any module can bypass any type's teardown.

**The spec** ("Consuming method receivers" → "The callee is the release point") says a consuming method "is declarable ONLY in the module that DEFINES the receiver type", since it overrides the type's teardown. Nothing in `compiler/typecheck/src/` enforces it, and no `consumes.*` refusal fixture covers it.

**Probe:** `lib.saw` declares `public struct Conn { fd: Int }` with a NoCopy `deinit` that prints `closing {fd}`. `main.saw` declares `extension Conn { func into_fd(&var self) consumes -> Int { self.fd } }` and prints `(move c).into_fd()`. It builds and prints `7` and exit 0, and `closing 7` never prints. The same works on `std.task.Thread` (`extension Thread<T> { func steal(&var self) consumes … }`), which only the fate check refuses.

**The fix:** a typecheck refusal at the declaration (`consumes.foreign-type` or the spec's id), naming the receiver type and its defining module. Obligation 4: every way a method can be declared on a type outside its module:
- a plain extension;
- an extension with a conformance;
- a generic extension;
- an extension on an alias of the type;
- an extension inside an inline module (if built);
- a trait default body that is `consumes` (is that a declaration on the conformer?).

Each cell pinned. Also check that std declares no foreign `consumes` method itself (if it does, list it: the rule would break std).

Implemented in SL-831 patch 1, which needs this guarantee for its fate rule.
