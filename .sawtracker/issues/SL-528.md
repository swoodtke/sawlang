**Found by:** the lead's first performance comparison, Oct 11: sawc2 at -O2 against Stage 0. The benchmark is `.build/scratch/bench/compute2.saw` (main checkout), four kernels inside sawc2's current slice. **Area:** the LLVM backend's check and panic lowering (`compiler/llvm`), and the accessor prologue's shape.

**Measurement** (best of 5 after a warm-up, Apple Silicon, the same checksums from every binary):

| kernel | Stage 0 | sawc2 -O2 |
|---|---|---|
| empty `main` (startup) | 0.0017s | 0.0018s |
| sieve to 2M (`Vector<Bool>` set and read) | 0.0067s | 0.0103s |
| insertion sort, 20k `Int` | 0.0277s | **0.2848s** |
| Collatz lengths to 300k (pure arithmetic) | 0.0398s | 0.0398s |
| push 1M, then fold | 0.0059s | 0.0057s |
| all four in one program | 0.0738s | 0.3363s |

Compile time: Stage 0 2.25s; sawc2 0.20s (-O2, clang included) and 0.31s (-O0). sawc2's -O0 binary runs in 1.44s.

**Mechanism:** after `clang -O2`, `saw prologue std.vector.Vector.[]` and `Vector.set` stay out-of-line calls in the sort's inner loop (`while k >= 0 && v[k] > key { v.set(k + 1, v[k]) … }`), and each access carries 24-byte `memcpy`s of the Vector header. The prologue isn't inlined because of its size, not because of any attribute (no `noinline` or `optnone` appears). Each bounds check's failure path is emitted INLINE, with two `alloca [512 x i8]` message buffers and the `__saw_append*` formatting. So every checked function carries its panic formatting on the hot side of the branch, in the same frame.

**Fix (perf by measurement; this is the measurement):**
- outline each check's failure path into a cold, `noinline` per-site or shared helper, with the message buffer in that helper's frame, so the checked function keeps a compare and branch;
- mark the failing branch cold (`!prof` weights or a `cold` callee);
- find out why the receiver's header is `memcpy`'d per access and remove it if it's a by-value copy.

**Done when:** the sort kernel is within 1.5× of Stage 0, with the sieve and the others unchanged or better, and a size note (the `.ll` and object for `compiler/` should shrink). Add the benchmark as a `devtools/bench` program, or as a run-lane timing report that gates nothing, so this is measured again later.

**Not on the self-hosting critical path** (correctness first), but sawc2 compiling itself will be the next big consumer: `compiler/` is index-heavy. Do it after U7b's M1, in `compiler/llvm`, which u7b2 owns until then.

**Review note (lead).**

**The mechanism.** Every check failure's formatting moves out of the checked function into shared `noinline noreturn` helpers, emitted once per program by `ll_fail_helpers`:
- `__saw_fail_head`;
- the per-kind helpers for overflow, divide, shift, unwrap and try;
- `__saw_fail`, `__saw_fail_signed` and `__saw_fail_unsigned`;
- `__saw_fail_parts` for formatted messages.

Each message buffer lives in its helper's frame. The funnel is in `prims.saw`, and its docstring lists the entry points `fail_check`, `fail_message`, `fail_value` and `fail_parts`; `call_panic_sink` is gone. Panic text is byte-identical.

**Measured, by design doctrine:** `cold` and `!prof` were tried, gave no speed gain, and made clang split every failing block into a `.cold.N` function (a 5.09 MB binary). So neither is used; `noreturn` already ranks the failing block unlikely.

**Results** (best of 5, the same checksums; the tables are in the commit body):
- **Kernels:** sort 0.2887s → 0.0324s (10.3× → 1.15× Stage 0); sieve 0.0106s → 0.0054s, now faster than Stage 0; Collatz, push-and-fold and startup unchanged.
- **Self-compile (Stage 2):** `typecheck --check` 0.53s → 0.36s (equal to Stage 1); `build --emit-ll -O2` 6.84–7.10s → 5.54–5.85s.
- **Sizes:** the binary −4.3%, the `.ll` −3.8%, the object −3.7%. `__text` +9% (the accessors inline), `__const` −52%.

**The "header memcpy" was not a receiver copy.** It was the inlined `__saw_append` copying the message head on the failure path, and it is gone with the inline formatting.

**Goldens:** `hello.ll` and `runtime_dirent.ll` gain only the appended helper block, with no existing line changed.

**Benchmark:** `compiler/tests/run/bench/*.saw`, and `run_lane.py --bench`, a timing report that gates nothing (README and TESTING.md).

**Lead's checks:**
- I reproduced the sort kernel: 0.29s → 0.03s, the same checksum.
- An out-of-range `v[3]` prints `panic at vector.saw:68: Vector.[]: index out of range: 3 (len 1)`, byte-identical before and after (rc 134).
- The agent's gate (`run.py`, plus `battery.sh compiler citations fixpoint`) is green: 63 run programs match Stage 0, and 914/914 fixpoint invocations agree.

**Left for later:** a format argument rendered through `Printable.format` still uses 512 bytes of caller-frame scratch.

Approved patch SL-528.p1 (revision 1)

Approving SL-528.p1. The claim that matters for correctness, that panic text is byte-identical, holds across every failure kind I could reach, not just the index case. The IR is shaped the way the speedup needs.

**Byte-identical panics, by differential** (`sl528/faults.saw`): one program, eleven failure cases chosen by argument count, built by Stage 2 of the base (cf75ca1e) and of this patch, each run's stderr and exit status compared exactly. **11 of 11 identical, all rc 134:**

| case | panic text (both builds) |
|---|---|
| signed `+` overflow | `integer overflow` |
| signed `-` overflow | `integer overflow` |
| unsigned `+` overflow (`UInt64.max + c`) | `integer overflow` |
| `/` by a run-time zero | `division by zero` |
| `%` by a run-time zero | `division by zero` |
| shift count out of range | `shift out of range` |
| `boxed(c)!` on `None` | `force unwrap of None` |
| `try!` on an `Err` with a negative payload | `try! failed` |
| `v[7]` on a 1-element vector | `panic at vector.saw:68: Vector.[]: index out of range: 7 (len 1)` |
| formatted `panic` with a negative `Int`, `UInt64.max` and an `Int` | `custom -92 and 18446744073709551615 and 8` |
| formatted `assert` | `assertion failed: assert with -91 inside` |

The `__saw_fail_signed`/`__saw_fail_unsigned` split renders both signs and the full unsigned range right.

**The IR** (`new.ll` from that program):
- **Each helper is defined exactly once,** as `internal … noinline noreturn`: `__saw_fail`, `_overflow`, `_divide`, `_shift`, `_unwrap`, `_try`, `_signed`, `_unsigned`, `_parts`. `__saw_fail_head` is the plain internal builder they share. The base build has none of them.
- **Every check site is one compact call** carrying file and line, e.g. `call void @__saw_fail_overflow(ptr @.bytes.0, i64 10, i64 21)`, and every check-site call is followed by `unreachable` (67 of 67). The remaining helper calls are the helpers' own internal formatting calls.
- **Deterministic:** two `--emit-ll` builds of the program are byte-identical.

**The measurements** are the lead's and the agent's (sort 10.3× → 1.15× Stage 0, the self-compile faster, the binary −4.3%), and I didn't re-time them. Leaving out `cold` and `!prof` on the measured evidence (a 5.09 MB binary of `.cold.N` splits for no gain) is the "perf via measurement" doctrine applied as written.

**Gate:** passed on the applied commit (tested_commit == applied_commit == abe862bc); its tested_tree ee353597 is exactly the patch applied to cf75ca1e, the tree I reviewed and probed.
