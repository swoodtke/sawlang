## Description

**`Vector.sort()` stopped being sync-callable with SL-974, so a `sync` function or a `Thread.spawn` body that sorts no longer compiles.** Found by SL-955 4b's rebase: the seed refuses Stage 1 with `effect.thread-body` along the path `driver_store_parts` → … → `driver_cache_generations` → `Vector.sort` → `sort_by` → `insertion_sort` → `greater_by`: "a call through a non-`sync` function value".

**Repros** (in `.claude/worktrees/p955j/.build/scratch/`):
- `repro_sync_sort.saw`: a `sync` function calls `v.sort()` on a `Vector<Int>`, giving `effect.sync`: "`sorted_first` is declared `sync`, and it calls `Vector.sort`, which is not sync-callable";
- `repro_thread_sort.saw`: a `Thread.spawn { … }` whose callee sorts, giving `effect.thread-body`.

Both built before SL-974 (std at `5725e52d0`): the first is refused by `effect.sync` and the second printed `123`.

**Mechanism:** SL-974's `sort` calls `sort_by` with a closure. The spec says a call through an unmarked function value conservatively suspends, so every caller of `sort` lost sync-callability. The old `sort` compared with `>` directly.

**Direction:** keep one algorithm, generic over an order type rather than a function value. A private trait such as `SortOrder<T>` has a method that answers "is a greater than b". `sort` instantiates it with an order type built on `Comparable`, and `sort_by` with one that wraps the closure. Effect inference runs per instantiation (LANGUAGE_SPEC, "Effect polymorphism"), so `sort` is sync-callable whenever `T`'s comparison is, while `sort_by` keeps its signature and effect. Duplicating the algorithm is the fallback, and only with a stated reason.

**Census (obligation 4):** find every std function that calls an internal closure or function value it wasn't handed by its caller. Give each one compile evidence of whether a `sync` caller, and a `Thread.spawn` body, can call it on a typical instantiation. Compare with std before SL-974 where the function existed.

**Pins:** `sort` from a `sync` function and from a `Thread.spawn` body, both on `Vector<Int>` and a user `Comparable` struct. Keep SL-974's stability, comparison-count and move-only pins.

**SL-981: `Vector.sort` is sync-callable again**

- **Fix:** the in-place merge sort (`merge_sort`, `insertion_sort`, `sym_merge`, `greater_at`) is generic over a file-private `SortOrder` trait. `compare` travels beside the order as a non-escaping parameter, since a field can't hold one.
  - `sort` passes `NaturalOrder<T>`, which asks `>` and never calls `compare`, so its instantiation makes no call through a function value. Per-instantiation effect inference then keeps it sync-callable.
  - `sort_by` passes `ClosureOrder<T>` and its own closure.
  - Unchanged: `sort_by`'s public signature, stability, no allocation, no `Copy` bound.
- **Census (obligation 4):** `Vector.sort` is the only std routine that lost sync-callability this way. The others that call through function values use `sync` `FuncPointer`s (the Channel gate, the pool engine, the offload check, the thread observer) or are `unsafe sync` (frame descriptors), and are unchanged.
- **Pins:** the new `probes/vector_sort_sync_callable.saw` sorts `Vector<Int>` and a user `Comparable` struct from a `sync` function and from a `Thread.spawn` body, at -O0 and -O2. SL-974's three pins pass unchanged.
- **Cost:** the unused closure is copied at each comparison site, but 200,000 random `Int`s sort within noise of main: 37.9–41.7 ms against 39.0–43.5 ms.
- **Generated and docs:** `sawc.cone`'s `std.vector` entries follow the new functions. The saw-lang skill's `sort` note says `sort` asks `>` directly.
- **Gate:** `run.py --only seed,units,golden,subset,fixture_whitespace,std,programs`: ok.

**Unblocks** SL-955.p9 (4b and v0.20.0): its store thread sorts generation numbers.

Approved patch SL-981.p1 (revision 1)

**Air: SL-981.p1, approved. It fixes the regression it was filed for. A second SL-974 regression is still open, and I'm reporting it below for you to file.**

**Read:** the merge sort moved from `Vector` methods into file-private generic functions over `SortOrder`, line for line. Only the comparison goes through `order.greater`.
- `sort` passes `NaturalOrder<T>` (`left > right`) and a closure it never calls. Effects are inferred per instantiation, so `sort`'s path makes no call through a function value.
- `sort_by` keeps calling its closure, as before.

**Probed:** `sort` from a `sync` function and from a `Thread.spawn` body (`sync_sort.saw`) across three std versions.

| case | before SL-974 | main | this patch |
|---|---|---|---|
| `sort` on `Vector<Int>`, from a `sync` function and a thread body | runs | refused (`effect.sync`) | runs, the same output as before SL-974 |
| `sort_any<T: Comparable>(v: &var Vector<T>) sync`, at `Int` and a `@synthesize`d struct | refused (the old `T: Copy` bound) | refused | runs and sorts both |
| a `Comparable` whose `compare` suspends, sorted from a `sync` function | refused | refused | refused, "may suspend", the right answer |

- **`sort_drops.saw`,** my SL-974 stress probe (325 sorts, NoCopy owning elements, lying comparators): 0 failures at -O0, -O2 and under ASan.

**A second regression from SL-974, which this patch doesn't fix** (chat m670, `sort_slow_task.saw`). A `Comparable` whose `compare` calls `yield_now()`, sorted inside a task:
- **Before SL-974:** it runs and prints `slow in a task: 123`.
- **Main:** refused with `effect.closure-suspends`, since `sort`'s closure would call a suspending `compare`.
- **This patch:** refused with `coro.suspending-cycle`: "suspending recursion is not allowed: the suspending-call cycle `sym_merge -> sym_merge`…". SymMerge recurses, and with a suspending comparison that recursion becomes a suspending cycle.

**Two ways out,** a choice for you or the user:
- make `sym_merge` iterative (an explicit stack of ranges, or a bottom-up merge with no recursion), so a suspending comparison sorts in a task again;
- or rule that `sort`'s comparison must not suspend, and give the refusal a sentence that names `sort` rather than `sym_merge`.

The second message also bears on SL-982: the path names an internal helper, not the user's `compare`.
