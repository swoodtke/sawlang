**Decided with the user (Oct 11).** Linux builds and runs come from a pinned aarch64 Debian Lima VM on the Mac, which the Air already has Lima for. Not a bare-macOS sysroot: building inside the VM was preferred over a checksummed `.deb`-extraction script.

**When:** after Stage 2 is self-contained (SL-522 M1 and M2: sawc2 writes its output, runs clang and builds its own runtime), and BEFORE the Python Stage 0 compiler (`sawc/`) is retired. The seed work (SL-534) needs per-host Linux seed binaries, and Stage 0 must still be available as the cross-check while the Linux path is brought up.

## Where things stand (lead probe, Oct 11)
- Stage 0 cross-compiles `examples/hello.saw` to correct ELF objects for `x86_64-unknown-linux-gnu` and `aarch64-unknown-linux-gnu` (`file`: "ELF 64-bit LSB relocatable, x86-64 / ARM aarch64, (GNU/Linux)").
- The hosted link fails at the runtime's `shim.c`: `#include <stdio.h>` not found. Apple's clang has no Linux sysroot.
- sawc2 refuses a non-host `--target` by design (U7a). Its target layouts already describe other triples (`sawc2 mono --layouts --target …`).
- The runtime's Saw half has a Linux port in `sawc/rt/host_linux/` (epoll, the errno map, the Linux-only futex lock in `shim.c`).
- This Mac has `ld.lld` (Homebrew). QEMU's user-mode emulation is Linux-only, and Docker isn't installed.

## The environment: one tracked Lima config
- **VM:** Debian 12 (bookworm), aarch64, with `vmType: vz` (native speed on Apple Silicon).
- **Rosetta:** `rosetta: {enabled: true, binfmt: true}`, so x86_64 Linux binaries run near native speed inside the VM.
- **Fallback for hosts without Rosetta:** `qemu-user-static` and `binfmt-support` (emulation, perhaps 5–20× slower for compute).
- **Packages, pinned in the config's provisioning script:**
  - `clang` and `lld` (Debian's LLVM has every backend);
  - `libc6-dev` (native aarch64);
  - the x86_64 cross sysroot: `gcc-x86-64-linux-gnu` and `libc6-dev-amd64-cross`, which install `/usr/x86_64-linux-gnu`, with `crtbegin.o` and libgcc from the cross gcc. Alternatively multiarch (`dpkg --add-architecture amd64`, `libc6-dev:amd64`); pick one and say why;
  - Python 3.14 plus llvmlite only if Stage 0 must run inside the VM. Prefer building on the Mac side and running in the VM, or sawc2 alone in the VM.
- **Checkout access:** Lima mounts the home directory, so the VM sees the checkout without copying.
- **Pinning:** the config lives in the repository (for example `tools/lima/sawlang-linux.yaml`), with the image digest and package versions pinned. The Air and this Mac then get the same environment.
- **Bring-up:** a `tools/linux.py` (or `make linux-*` targets) to create, start and run commands in the VM.

## What it enables
1. **Native aarch64 Linux:** sawc2 (Stage 2) builds and runs hosted programs inside the VM, linking the `host_linux` runtime.
2. **x86_64 Linux cross-builds** inside the VM: clang with `--target=x86_64-linux-gnu --sysroot=/usr/x86_64-linux-gnu -fuse-ld=lld`, plus the runtime built for x86_64.
3. **Running the x86_64 results** under Rosetta, with QEMU as the fallback.
4. **Lanes:**
   - a `linux` battery lane: the run lane's programs built and run on aarch64 and on x86_64, held to the same expected output as macOS;
   - the fixpoint lane on Linux aarch64 (Stage 2 = Stage 3 there too);
   - `host_linux`'s epoll runtime exercised on both arches. This lane runs on whichever machine has the VM; on the Mac's patch gate it is opt-in until the server can host it.
5. **SL-534's per-host seeds:** a release builds the macOS seed natively and both Linux seeds inside the VM, each with its fixpoint checked.

## Changes outside the VM
- sawc2's `--target` refusal relaxes to "refuse unless a sysroot/linker for the target is configured", never silently building for the host.
- `compiler/driver` passes `--sysroot` and the target to clang.
- The runtime build (SL-522 M2) builds `host_linux` plus `shim.c` for the target.

## Open in the brief
- Does the Mac build Linux objects and the VM only link and run them, or does everything Linux happen in the VM? The lead leans to everything in the VM: one toolchain, no Mac sysroot.
- How CI and the sawtracker server reach a Linux runner later (out of scope here; note it).

**VM bring-up, Oct 11 (lead).** The `sawlang-linux` VM was created from `.build/scratch/lima/sawlang-linux.yaml` and verified with `.build/scratch/lima/check.sh`:
- **Versions:** Debian 12 aarch64 (kernel 6.1), clang/lld 14.0.6, x86_64-linux-gnu-gcc 12.2, uv 0.13. The checkout is mounted read-only at `/mnt/sawlang`. 17 GiB free in the VM.
- **Native aarch64:** `clang` builds a PIE that runs.
- **x86_64 cross:** `clang --target=x86_64-linux-gnu -fuse-ld=lld` links. **Do NOT pass `--sysroot=/usr/x86_64-linux-gnu`:** Debian's cross `libc.so` is a linker script with absolute paths, which a sysroot prefixes twice, so the link fails. Debian's clang finds the cross installation from `--target` alone.
- **Running x86_64 under Rosetta:** needs the amd64 RUNTIME loader at `/lib64/ld-linux-x86-64.so.2`, which the cross packages don't install. `dpkg --add-architecture amd64` plus `libc6:amd64` (now in the config's provisioning) fixes it, and the binary then runs under Rosetta.
- **Host access:** `limactl shell sawlang-linux …` works from the Claude Code session once the VM is running. STARTING the VM from inside the session fails with VZErrorDomain "Internal Virtualization error" at the Rosetta share, even with the command sandbox disabled. That looks like the session's seatbelt blocking the Virtualization XPC service. For now the user starts it, so an unattended Linux lane needs that permission (or a `vmType: qemu` fallback).
- **Python in the VM** is 3.11; the frozen compiler's venv wants 3.14, which uv provides.
