**Decided with the user (Oct 11).** Linux builds and runs come from a pinned aarch64 Debian Lima VM on the Mac, which the Air already has Lima for. Not a bare-macOS sysroot: building inside the VM was preferred over a checksummed `.deb`-extraction script.

**When:** after Stage 2 is self-contained (SL-522 M1 and M2: sawc2 writes its output, runs clang and builds its own runtime), and BEFORE the Python Stage 0 compiler (`sawc/`) is retired. The seed work (SL-534) needs per-host Linux seed binaries, and Stage 0 must still be available as the cross-check while the Linux path is brought up.

## Where things stand (lead probe, Oct 11)
- Stage 0 cross-compiles `examples/hello.saw` to correct ELF objects for `x86_64-unknown-linux-gnu` and `aarch64-unknown-linux-gnu` (`file`: "ELF 64-bit LSB relocatable, x86-64 / ARM aarch64, (GNU/Linux)").
- The hosted link fails at the runtime's `shim.c`: `#include <stdio.h>` not found. Apple's clang has no Linux sysroot.
- sawc2 refuses a non-host `--target` by design (U7a). Its target layouts already describe other triples (`sawc2 mono --layouts --target …`).
- The runtime's Saw half has a Linux port in `sawc/rt/host_linux/` (epoll, the errno map, the Linux-only futex lock in `shim.c`).
- This Mac has `ld.lld` (Homebrew). QEMU's user-mode emulation is Linux-only, and Docker isn't installed.

## The environment: one tracked Lima config
- **VM:** Debian 12 (bookworm), aarch64, with `vmType: vz` (native speed on Apple Silicon).
- **Rosetta:** `rosetta: {enabled: true, binfmt: true}`, so x86_64 Linux binaries run near native speed inside the VM.
- **Fallback for hosts without Rosetta:** `qemu-user-static` and `binfmt-support` (emulation, perhaps 5–20× slower for compute).
- **Packages, pinned in the config's provisioning script:**
  - `clang` and `lld` (Debian's LLVM has every backend);
  - `libc6-dev` (native aarch64);
  - the x86_64 cross sysroot: `gcc-x86-64-linux-gnu` and `libc6-dev-amd64-cross`, which install `/usr/x86_64-linux-gnu`, with `crtbegin.o` and libgcc from the cross gcc. Alternatively multiarch (`dpkg --add-architecture amd64`, `libc6-dev:amd64`); pick one and say why;
  - Python 3.14 plus llvmlite only if Stage 0 must run inside the VM. Prefer building on the Mac side and running in the VM, or sawc2 alone in the VM.
- **Checkout access:** Lima mounts the home directory, so the VM sees the checkout without copying.
- **Pinning:** the config lives in the repository (for example `tools/lima/sawlang-linux.yaml`), with the image digest and package versions pinned. The Air and this Mac then get the same environment.
- **Bring-up:** a `tools/linux.py` (or `make linux-*` targets) to create, start and run commands in the VM.

## What it enables
1. **Native aarch64 Linux:** sawc2 (Stage 2) builds and runs hosted programs inside the VM, linking the `host_linux` runtime.
2. **x86_64 Linux cross-builds** inside the VM: clang with `--target=x86_64-linux-gnu --sysroot=/usr/x86_64-linux-gnu -fuse-ld=lld`, plus the runtime built for x86_64.
3. **Running the x86_64 results** under Rosetta, with QEMU as the fallback.
4. **Lanes:**
   - a `linux` battery lane: the run lane's programs built and run on aarch64 and on x86_64, held to the same expected output as macOS;
   - the fixpoint lane on Linux aarch64 (Stage 2 = Stage 3 there too);
   - `host_linux`'s epoll runtime exercised on both arches. This lane runs on whichever machine has the VM; on the Mac's patch gate it is opt-in until the server can host it.
5. **SL-534's per-host seeds:** a release builds the macOS seed natively and both Linux seeds inside the VM, each with its fixpoint checked.

## Changes outside the VM
- sawc2's `--target` refusal relaxes to "refuse unless a sysroot/linker for the target is configured", never silently building for the host.
- `compiler/driver` passes `--sysroot` and the target to clang.
- The runtime build (SL-522 M2) builds `host_linux` plus `shim.c` for the target.

## Open in the brief
- Does the Mac build Linux objects and the VM only link and run them, or does everything Linux happen in the VM? The lead leans to everything in the VM: one toolchain, no Mac sysroot.
- How CI and the sawtracker server reach a Linux runner later (out of scope here; note it).

**Refined (the Air, Oct 11): test the CAPABILITY, not the version number.** Apple clang numbers its own versions: Xcode 14.3's Apple clang 14.0.3 is LLVM 15 and accepts opaque pointers, but a `major >= 15` parse of `clang --version` would refuse it. So sawc2's link step (or `build.py`, which writes the runtime manifest) compiles a two-line opaque-pointer module, `define ptr @f(ptr %p) { ret ptr %p }`, with the chosen clang, records the result beside the clang path, and refuses with a clear message naming the clang and the requirement when it fails. No version mapping to drift with Xcode.

<!-- sawtracker:comment {"author":"agent:claude-air-reviewer","body_bytes":1358,"created":"1791812900","id":"c7"} -->
On the proposed `__saw_rt_executable_path` seam (Air). The seam is the right shape: std can't branch by OS, every other OS-specific symbol already lives in `sawc/rt/host_*`, and `fs_dirent_name` is the precedent. One point for the ABI entry, since it decides what sawos's runtime owes. ABI.md lists four hosts (host_macos, host_linux, sos-hosted, kernel/none), and its only "optional" convention (`__saw_rt_alloc_deny_after`) holds because "nothing in std calls it, so a freestanding runtime may omit the symbol". `Env.executable_path` IS called by std, so this seam can't be optional that way. A provider that omitted it would fail to link any program reaching `Env`, and `sawc2 runtime`'s exactly-once check would refuse the runtime. Suggest the entry say every host defines it: host_macos (`_NSGetExecutablePath` + `realpath`) and host_linux (`realpath("/proc/self/exe")`) really, and a host with no notion of an executable path (sos-hosted, kernel/none) as a one-line stub returning NULL. std already reports NULL as `Err(Unknown)` (D43 as amended: no errno read). That keeps the seam total, the runtime-build check uniform across hosts, and std free of a profile split. For the D43 record: on Linux, a binary deleted while running makes `/proc/self/exe` read `… (deleted)`, `realpath` fails, and that's the same `Err(Unknown)` D43 describes for macOS.

One defect in SL-536.p1, found while probing it (Air); the rest of my review is in progress, and the probes so far pass.

**`tools/linux.py` reports an unreadable Lima state as 'no VM', so the `linux` lane SKIPS and passes for a reason that isn't true.** `instance()` runs `limactl list --json sawlang-linux`, ignores its exit status and stderr, and finds no record, so it raises the "there is no VM" error with `EXIT_NOT_RUNNING` (3). On the Air, in this sandboxed session:
```
$ limactl list
level=fatal msg="cannot evaluate symlinks in `/Users/swoodtke/.lima`: lstat /Users/swoodtke/.lima: operation not permitted"
$ tools/linux.py status
linux: there is no `sawlang-linux` VM; create it once with `limactl start --name=sawlang-linux tools/lima/sawlang-linux.yaml`, then run this again (this tool never creates or starts it)
rc=3
```
`limactl` is installed here, and whether a VM exists is exactly what this session can't know. The battery's `run_linux` turns rc 3 into "linux: SKIPPED, not failed", so from any session that can't read `~/.lima` the lane never runs and never fails. The advice it prints, to create the VM, may also be wrong. Under 'never hide errors' the fix is small: when `limactl list` exits non-zero, raise a `VmError` carrying limactl's stderr with status 1, so the lane fails and names the cause. Keep 3 for the two states it's right about: no such VM, and a VM that isn't running.

Two smaller points, take or leave:
- **uv's pin:** the yaml says the image, the apt packages and uv are pinned, but uv arrives by `curl … /uv/0.13.0/install.sh | sh`, which pins a version and checks no digest (the image is pinned by sha512, and apt checks its own signatures). A sha256 check on the uv release tarball would make the claim hold.
- **The cross-build refusal's wording:** it says `build.py --runtime T` 'builds one once a clang passes its check for that target'. The check compiles only the opaque-pointer module, so it says nothing about T's C headers. On macOS, `build.py --runtime x86_64-unknown-linux-gnu` passes the clang check, then fails on shim.c's `stdio.h`. It fails cleanly, writes no manifest, and names the missing header, so only the sentence overstates.
