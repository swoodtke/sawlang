**Air, on SL-900: it can deadlock, not only stall.** I approved `File.read(size:)` in SL-847 without checking this.

`s1_read_stall.saw` (on the Air, `.build/scratch/air-review/sl900/`) runs three tasks in one cooperative `TaskGroup()`:
- a reader doing `File.read(size: 4)` on a pipe's read end, opened as `/dev/fd/N`;
- a sibling ticker;
- a third task that sleeps 300 ms and then writes the pipe.

On main it never finishes: killed by a 10 s timeout. The reader's read(2) holds the group's only thread, so the writer that would satisfy it never runs. With the writer in another process it would be the stall the issue describes; with the writer in the same group it's a hang.

So the pin set should include that cell: the reader and its writer in one cooperative group, which must finish in roughly the 300 ms the writer waits. A ticker beside the reader proves the siblings run meanwhile. The same cell applies to `Command.wait()` with a child that waits on something only a sibling task provides.

**Implementation detail (lead, Nov 12): a design pass (Opus) first; the fix is a rule per operation, and each rule is a concurrency contract.**

**The defect (c1, c2).** `Command.wait()` and `File.read(size:)` on a pipe, FIFO or terminal block the OS thread without being declared `blocking`. In a cooperative `TaskGroup()` that stalls every sibling, and when the event that would end the wait can only come from a sibling it is a hang: the Air's `s1_read_stall.saw` (a reader, a ticker, and a writer that sleeps 300 ms then writes the pipe, all in one group) never finishes.

**The rules that already exist and bind the design.**
- SL-782's rule: an operation that blocks the OS thread and can't be offloaded is `blocking` (refused at a task root, with a pair for the cooperative path), or it offloads, or it parks on the reactor.
- The user's standing ruling (Oct 23): suspension is allowed by default; every ban names its safety reason.
- CLAUDE.md doctrine: APIs do the expected thing, not the easy-to-implement thing; never hide errors.
- `Command.output()` already parks on the child's exit descriptor through the reactor (`io_wait(__saw_rt_proc_wait_fd(job), 0)`) and drains stdout by an offload; `process_reaped` (which `wait()` uses) polls `__saw_rt_proc_try_wait` on a doubling SLEEP OF THE CALLING THREAD (`std/process.saw`).

**The design must decide, per operation, with a probe for each claim:**
1. **`Command.wait()`:** park on the exit descriptor as `output()` does (cooperative, cancellable), or stay thread-blocking and be declared `blocking`? What does a `Thread.spawn` body (which is `sync`) get: does one function serve both contexts (a pair), and what does cancellation of a parked `wait()` do to the child (the spec's "the child keeps running" and SL-799's orphan list apply)?
2. **`File.read(size:)` and its siblings on a descriptor that may block:** the census below finds which std file operations can block indefinitely (a pipe, FIFO, terminal, socket opened as a file) versus ones bounded by the disk (regular files, which design 182 documents as naked blocking calls, DF-181b / SL-109). Options: readiness-park for non-regular descriptors (needs `fstat` at open or at first read, and O_NONBLOCK handling), offload every read, or declare `blocking`. What does each cost a regular-file read, which is the common case?
3. **What is refused, and where:** if an operation becomes `blocking`, which existing programs (corpus, Blade, the compiler's own driver, which "never calls a suspending std function") stop building, and what they write instead.
4. **Linux and macOS both:** the exit descriptor is a pidfd or a kqueue EVFILT_PROC (SL-108 notes pidfd waiting is unverified at run time); the reactor seams available per host (`runtime/host_linux`, `runtime/host_macos`, `runtime/ABI.md`).
5. **Freestanding:** none of this may reach a freestanding build (`import.hosted-only` already gates `std.process` and `std.file`; confirm).

**Census the design pass runs first** (evidence in `.build/scratch/p900d/` of the main checkout; scratch programs only, no tracked edit): every `std/file.saw`, `std/process.saw` and `std/directory.saw` operation that reaches a blocking libc call or seam, as a table: operation, seam or call, can it block without bound, declared `blocking` today, what a task calling it does to a sibling ticker (measured: a ticker task counting ticks while the operation waits 300 ms), and whether cancellation reaches it. Include the Air's cell (the reader and its writer in one group) for `File.read` and its `Command.wait()` twin.

**Deliverable** (one comment on this issue): the rule per operation with its reason, the seam or std changes each needs, the pins (each cell above must finish in about the 300 ms its writer waits, with the ticker's count proving siblings ran; no pin may depend on machine speed, per SL-977's direction), what becomes refused, the questions that are the user's, and the cut into Sonnet-sized units with files, expected golden moves (coroutine goldens move when `std/taskgroup.saw`-reached items change; `runtime/ABI.md` and the `abidoc` lane if a seam is added) and gates.

# SL-900 design: `Command.wait()`, `File.read(size:)` and the other std waits that hold a task's thread

Agent p900d, Nov 14, main at ee01ba8b6, Stage 2 rebuilt from it. Evidence is in
`.build/scratch/p900d/` (file names in brackets). Everything was run on macOS
arm64. Linux is UNVERIFIED unless the code settles it (§7).

## 1. The rule per operation

| operation | rule | why |
|---|---|---|
| `Command.wait()`, `Child.wait()` | **A pair.** The default parks on the child's exit descriptor, like `output()`'s wait loop. The `blocking` twin is today's body. A cancel ends the wait with `Interrupted`, the child keeps running and goes on the orphan list, and the handle is settled (Q2). | The seams already exist (`__saw_rt_proc_wait_fd`, `try_wait`), so this needs no runtime change. With the scratch pair, all three wait cells finish in about 310 ms with about 50 sibling ticks, and a cancel lands at 52 ms [census_wait_pair.txt]. A lone `blocking` would refuse Blade (12 errors) and 7 run probes [blade_std_wait_lone.txt, sweep_wait.txt]. |
| `File.read(size:)` | **A pair.** The default classifies the descriptor once, at open: a descriptor with a position reads plainly, as today; a stream the reactor can wait on parks on read readiness and then reads (no `O_NONBLOCK`); a stream the reactor refuses has its read offloaded. Cancel-first, so a cancelled read takes nothing. The twin is today's body. | It fixes the c2 hang: 306 ms, 49 ticks [census_read_pair.txt]. It costs a regular-file read nothing per read and about 180 ns per open [cost.txt, trial_cost.txt]. Offloading every read would cost 40 to 72 µs per read, 60 to 100 times a plain read [cost.txt]. |
| `File.write` | **A pair, same classification.** On a stream the reactor can wait on, the default waits for write readiness before each chunk of at most 512 bytes. On a refused stream it offloads. On a positioned file it writes plainly. | A write into a full FIFO holds the thread for 315 ms [census_run3.txt]. macOS reports a full pipe writable only once 512 bytes are free (PIPE_BUF) [pipe_lowat.txt], so a write of 512 bytes or less after readiness cannot block. |
| `File.read()` (whole file) | **Unchanged (sync).** | It never waits on a stream: lseek refuses a pipe and a terminal at once (ESPIPE, after 0 ms) [census_run3.txt tty_whole; probe `file_read_size_chunks`]. |
| `File.open` / `create` / `open_append` on a FIFO | **Unchanged in this issue, documented (Q4).** A follow-up is filed. | The open waits for a peer: 314 ms and 315 ms, 0 ticks [census_run1.txt, census_run3.txt]. The spec already states it (LANGUAGE_SPEC "File and directory IO is prompt by policy"). |
| `seek_*`, `position`, `close`/deinit, `exists`, `remove`, `rename`, every `Directory` op, `Command.spawn` | **Unchanged: bounded by the disk, by policy (SL-109).** | Measured between 0 and 93 µs on /tmp, and 542 to 582 µs for `spawn` (the exec handshake) [census_run3.txt prompt]. |

A pair keeps a `Thread.spawn` body, a `blocking` function and `func main() blocking` on today's thread-blocking body [twin_contexts.txt]. Freestanding is untouched: `std.file` and `std.process` are already `import.hosted-only` [free_file.txt].

## 3. Findings, with evidence

**F1. The pair for `wait` works, and needs no seam.** In a scratch std (`std_wait_pair/process.saw`), the default `Child.wait` is `output()`'s park loop: `cancelled()` first, `io_wait(__saw_rt_proc_wait_fd(job))`, a `sleep()` poll fallback, the op-budget yield, and `process_abandon` on a cancel. The twin is today's body. Results:
- `command_wait`: 308 ms, 51 ticks; `child_wait`: 310 ms, 50 ticks;
- the c2 twin (`wait_sibling`): **314 ms, 51 ticks**, where today's std hangs;
- a cancel at 52 ms gives `Err(wait "/bin/sleep" failed (interrupted))` [census_wait_pair.txt];
- a `Thread.spawn` body calling `wait()` and `read(size:)` compiles as sync and runs [twin_contexts.txt].

**F2. A lone `blocking` `wait` breaks Blade and seven run probes; the pair breaks nothing in the tree outside the driver.**
- **Lone, Blade:** Blade's `main` suspends (it calls `output()`), so it is a task root. Against a `blocking` `wait` it gets one `effect.task-blocks` (`main` → `Builder.build` → … → `clone_tag` → `Command.wait`) and 11 `effect.blocking-undeclared` on its public functions [blade_std_wait_lone.txt].
- **Lone, run probes:** 7 of the 43 files using `std.process` are refused with `effect.task-blocks`. Each one's `main` suspends for another reason [sweep_wait.txt].
- **Pair:** Blade builds, and 0 of those 43 files and 0 of the 112 using `std.file` change verdict under `coro --check` [blade_std_both.txt, sweep_process_both.txt, sweep_file_both.txt]. Four of the programs, built against both pairs and run, print their stated output [runs_std_both.txt].

**F3. The compiler's driver is the one consumer the pairs reach. Three `blocking` markers fix it, and they can land first.**
- The typecheck lane holds every function in `compiler/` to sync-only (`compiler/tests/typecheck/typecheck_lane.py`, `check_acceptance`: "may suspend …, and the subset is sync-only").
- Against the wait pair, 18 driver functions become `suspends`, `main` among them [driver_tc_std_wait_pair.txt]. Against the read pair, 16 do, again with `main`, through `driver_cache_token`, which reads `/dev/urandom` with `read(size:)` [driver_tc_read_pair.txt].
- Declaring `driver_tool`, `driver_run_jobs` and `driver_cache_token` `blocking` makes them thread context, so the twins are selected. The driver then summarizes with nothing suspending against both pairs [driver_tc_both_blocking.txt], and against today's std too, `main` `never-suspends` [driver_tc_blocking_realstd.txt]. The driver already uses the marker (`func deinit(&var self) blocking`, main.saw:2148).
- The unit programs (`compiler/*/tests/*.saw`) are unaffected.

**F4. The pairs flip a written contract, and the flip is visible.**
- **Today:** spec §9 says "`wait()` … never suspends, so a `sync` function may call it", and the skill repeats it.
- **Under the pairs:** a declared-`sync` function calling either operation is refused, `effect.sync` "it calls `Command.wait`, which may suspend (`Command.wait` → `Child.wait` → `io_wait` (parks the task))", and the same for `File.read` [wait_sync_fn.txt]. A closure body is refused the same way (`effect.closure-suspends`, shown with `Channel.receive` [pair_contexts.txt]), and so are a non-`blocking` `deinit` and a trait implementation (spec "Where `blocking` is written").
- **Plain `main`:** a plain `main` that reaches one suspends and links the executor: 100,064 → 140,424 bytes. `func main() blocking` keeps 100,112 [plain_wait_sizes.txt; frames in pair_contexts.txt via `coro --layouts`].

**F5. Classify by position, not by `fstat`.** `lseek(fd, 0, SEEK_CUR)` failing with ESPIPE matches the descriptors that can wait without bound, on this host [fdkinds.txt]:
- ESPIPE: a pipe, a FIFO, a pty slave and master, a unix socket, and `/dev/tty`;
- a position: a regular file, `/dev/urandom`, `/dev/null` and `/dev/zero`.

It needs no new seam, since `__saw_rt_fs_lseek` exists, and it is the line `read()` already draws. `fstat`'s `st_mode` sits at a different offset per host, so using it would need a seam.

**F6. A stream the reactor refuses exists on macOS, and a naive park panics on it.**
- kqueue refuses `EVFILT_READ` with EINVAL on `/dev/tty`, the controlling-terminal alias [devtty_script.txt], and on `/dev/urandom`, `/dev/null` and `/dev/zero` [fdkinds.txt]. Those three have a position, so they never reach the park.
- It accepts pipes, FIFOs, pty ends, sockets and regular files.
- The arm funnel panics on a refused registration (`std/taskgroup.saw` `__saw_exec_io_register`: "A failed arm panics"). Under a lseek-then-`io_wait` default, a task reading `/dev/tty` dies with `panic at taskgroup.saw:3432: reactor: arming fd 3 for read readiness failed (errno 22)`, where today's std reads [devtty_task.txt].
- `/dev/tty` is what the sawtracker port reads for its token prompt (SL-847's description). So the classification must also ask whether the reactor accepts the descriptor. A trial registration on a throwaway kqueue costs about 630 ns for a pipe, and 180 ns for a regular file, which needs only the lseek [trial_cost.txt].

**F7. Never set `O_NONBLOCK` on a `File`.** On macOS, `open("/dev/fd/N")` shares N's open file description: `O_NONBLOCK` set on the new descriptor shows on N, for a pipe and for a pty [fdkinds.txt]. A program that opens `/dev/stdin` or `/dev/fd/0` would make its parent shell's terminal nonblocking. Readiness followed by a blocking read is safe.
- **The residual:** another reader of the same pipe can drain it between the readiness and the read, and the read then blocks the thread, as today. The default treats `WouldBlock` (a descriptor someone else made nonblocking) as "park again".
- **Process pipes differ:** a pipe std makes itself, as `take_stdout` does, has a private description and may be nonblocking (SL-896's drain).

**F8. Costs for the common case, a regular file, -O2, three runs** [cost.txt]:
- a seek plus a 4 KiB `read(size:)`: 618 to 985 ns;
- one lseek: 172 to 180 ns;
- an offloaded 4 KiB pread: 39.8 to 72.3 µs.

So "offload every read" is ruled out by measurement. The pair adds one lseek per open, and per read a branch on the cached kind and a `cancelled()` read.

## 5. Questions for the user

**Q1. May `Command.wait()`/`Child.wait()` change effect: never-suspends becomes a pair whose task body parks?**
- (a) Pair (default). It breaks nothing measured but the driver (F2, F3).
- (b) Lone `blocking`. It refuses Blade and 7 run probes (F2), and a task could never wait for a child.
- (c) Keep it sync and add a cooperative spelling.

What breaks under (a): any `sync`-declared function, closure, non-`blocking` `deinit` or trait implementation that calls `wait()` (F4; none in the tree). A plain `main` that waits starts linking the executor (+40 KB), and `func main() blocking` opts out. Going back later from (a) to (b) would break Blade.

**Q2. What does a cancel do to a parked `wait()`?**
- (a) Ends the wait with `Interrupted`; the child keeps running, goes on the orphan list, and a later spawn reaps it; the `Child` handle is settled, so its drop is quiet and a second `wait` panics (default). This is `output()`'s contract, the spec's "cancellation ends the WAIT, not the child", and SL-799's list.
- (b) Ends the wait but leaves the handle unsettled. This is unusable in practice: the next `wait` in a cancelled task returns `Interrupted` at once, and dropping the handle panics.
- (c) No cancellation point, as with `Thread.join`.

SL-1093's kill and deadline wait stay additive under (a): `wait(timeout:)` returns the handle unsettled, the way `TcpStream.read(timeout:)` returns `Timed`, so kill-then-wait works, and kill-on-cancel can be an opt-in. Moving between (a) and (c) later changes runtime behaviour, not compilation.

**Q3. May `File.read(size:)` (and `File.write`) change effect, from sync to a pair?**
- (a) Pair (default). Tasks reading pipes and terminals stop stalling, and regular files cost about 180 ns per open. Every `sync`-position caller is refused, even for a regular file, because the effect is static; there are none in the tree but the driver.
- (b) Keep `File` sync, and add a separate stream type or method (`File.open_stream`, a `Pipe`), which is a new name.
- (c) Lone `blocking`. A task could no longer read a regular file in chunks.

Reversing (a) later breaks callers either way.

**Q4. `File.open`/`create` on a FIFO wait for a peer.**
- (a) Stay documented, prompt by policy, as the spec already says (default; file a follow-up).
- (b) Offload the open when the path names a FIFO: a stat first, racy but harmless.
- (c) Open nonblocking and park. Its semantics differ per host (a nonblocking FIFO read sees end of file before any writer), UNVERIFIED.

**Q5. A twin in thread context blocks plainly.** Unlike the `Channel.receive` and `Thread.join` twins, it does not run the thread's own tasks while it waits. So a `func main() blocking` that reads a pipe one of its not-yet-joined tasks writes still hangs; the spec states that hazard generally (11329).
- (a) Document it (default; adding it later breaks nothing).
- (b) Build it now, which needs a readiness wait inside the thread observer.

**Q6. A stream the reactor refuses (macOS `/dev/tty`), read in a task.**
- (a) Offload the read (default). Siblings run, it is not cancellable, and it costs about 40 to 70 µs per read.
- (b) Block the thread as today.
- (c) `Err(Unsupported)`.

(c) would refuse the sawtracker port's prompt; (b) keeps the stall.
