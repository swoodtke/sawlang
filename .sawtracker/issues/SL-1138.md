## Description

**Two small follow-ups from the review of SL-1128.p1 (Nov 15), in the freestanding suite only.** Neither changes a verdict of the suite today.

**1. The mixed-ABI check is fooled by a literal pool.** `abi_problem` (`tools/freestanding_runner.py`) disassembles an object and counts `entry` lines over the whole listing. A `.literal` section's pool disassembles as instructions, and `0x36` is the first byte of `entry`, so a call0 object whose pool holds a word with low byte `0x36` passes as windowed. The reviewer's reproduction: a C file compiled with the row's own call0 flags (`xtensa_cc_args(False)`) shows three `entry` lines, all in `.literal` (chat f139 `call0_literal.c`, f140 `abi_literal.py`). An image that slips through still fails its case when the call is reached, so no verdict is wrong; what is lost is the message naming the object.
- **Fix:** count only executable code sections, skipping `.literal` as the run lane's `xtensa_instructions` does (one funnel if both need it: say whether they can share it); a row in `tools/test_freestanding_runner.py` with the reviewer's file, refused by name.

**2. Both start-ups write `WINDOWSTART` and then `WINDOWBASE` through a9 while the ROM's `PS.WOE` is still set.** Between the two writes a reference to a9 is checked against the new `WINDOWSTART`, so the sequence relies on the ROM's `WINDOWBASE` at entry not being 14 or 15. It holds for this ROM (the row passes), but a0 to a3 are never window-checked: using one of them removes the dependence. In `tests/freestanding/hal/xtensa/boot.S` and `hal/xtensa-windowed/boot.S`, the same lines. The sawos lead should hear of it: its own start-up may have the same sequence.

**Gate:** `tools/battery.sh freestanding` (the Xtensa rows' counts unchanged), the comment lint.

Related: SL-1128, SL-1133.
