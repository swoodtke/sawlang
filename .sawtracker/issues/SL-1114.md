## Description

**User decision: which target do the check commands assume when none is named?** Found by SL-1113's investigation (Nov 14).

**Today:** `sawc resolve`, `typecheck`, `mir`, `eval`, `borrowck`, `drops`, `mono` and `coro` take their triple from `driver_check_triple()` (`compiler/driver/src/main.saw`), which returns the constant `"arm64-apple-darwin"` (its comment: an LP64 host's). `sawc build` takes the HOST's triple from the runtime manifest beside the binary. So on Linux, `sawc typecheck FILE` checks FILE for arm64 macOS, and `sawc build FILE` builds it for Linux. `resolve` accepts no `--target` at all; the others do.

**What follows from it today:**
- The front cache is keyed by the triple, so on Linux a `sawc typecheck` and a `sawc build` of the same program share nothing (measured: the build recomputes std's image).
- Anything the front end decides by target is decided for macOS: `Int`'s width is the same on every LP64 host, so most programs cannot tell; a program or a std module whose checking depends on the OS could (UNVERIFIED that one exists today; none was looked for).
- The lanes' goldens (`typecheck`, `mir`, `coro`, …) are recorded with no `--target`, so they are the same on every host. That may be the reason for the constant.

**Options:**
- **(A) The host, as `build` does** (the triple from the runtime manifest; the constant only where there is no manifest). A check command then answers for the machine it runs on, and shares its cache with the build. The lanes pass `--target` where a golden must not vary by host (a sweep: every lane's sawc call), and `resolve` learns `--target`.
- **(B) Keep the fixed triple, and say so:** `--help` and the spec state that the check commands assume `arm64-apple-darwin` unless told; `resolve` learns `--target`.
- Lead's recommendation: (A). "APIs do the expected thing": a reader of `sawc typecheck` on Linux expects the host, and the cache they paid to fill should serve the build.
