## Description

**A shared/exclusive accessor pair fails at clang: both halves of both accessors get one LLVM symbol** (found by a6flow on SL-559, A6).

A `&self` accessor and a `&var self` accessor of one name (SL:borrowing §4's pair, which typecheck accepts) build to a `.ll` that defines each half twice:

```saw
struct Grid { a: Int, b: Int }
extension Grid {
    public func [](&self, i: Int) borrows -> &Int { if i == 0 { lend self.a } else { lend self.b } }
    public func [](&var self, i: Int) borrows -> &var Int { if i == 0 { lend self.a } else { lend self.b } }
}
func main() {
    var g = Grid(a: 1, b: 2)
    g[0] += 5
    print(g[0] + g[1])
}
```

`sawc2 build --std-root std` (no coroutine involved):

```
define internal ptr @"saw prologue w0.Grid.[](i: Int)"(ptr noalias %p1, ptr noalias %p2, i64 %p3) #0 {
define internal void @"saw epilogue w0.Grid.[](i: Int)"(ptr noalias %p1) #0 {
define internal ptr @"saw prologue w0.Grid.[](i: Int)"(ptr noalias %p1, ptr noalias %p2, i64 %p3) #0 {
define internal void @"saw epilogue w0.Grid.[](i: Int)"(ptr noalias %p1) #0 {
w0.ll:258:21: error: invalid redefinition of function 'saw prologue w0.Grid.[](i: Int)'
```

**Mechanism:** `ll_symbol` (`compiler/llvm/src/module.saw`) spells an item's symbol from `mono.item_name`, and mono's item name for a method names its owner, path and parameters but not its receiver's mode. Typecheck's `overload.indistinguishable` refuses every other pair of methods that differ only in their receiver ("the result, effects, receiver and staticness never tell two apart"), so the accessor pair is the one overload set whose items share a name; both its halves, and its whole accessor item if one is emitted, collide.

**What it blocks:** `tests/corpus/lend_var_coro_and_forwarding` (A6's pin for a window across a suspension, SL-559) and any program using such a pair, through any std or user type.

**Fix:** the item name (or the symbol alone) tells the pair apart, for example by the receiver's mode for an accessor; `--dump` names and goldens follow if the name changes. Pin: the program above in the run lane, against Stage 0's spelling of the pair.

SL-671.p1 submitted. **The bug:** mono's item name left out what tells two declarations apart when the MIR dump spells them alike. A shared/exclusive accessor pair (one `borrows` declaration used through `&self` and `&var self`) got both halves under one name, so clang refused the module for a symbol defined twice.

**The fix:** `MonoProgram.item_name` is the one naming funnel. The dump, every later stage's records and every LLVM symbol spell an item through it; its docstring names the backend entry points (`ll_symbol`, `ll_resume_symbol`, `ll_descriptor_symbol`, `ll_resume_value_symbol`, `ll_result_drop_symbol`). `append_qualifiers` adds only what the dump's spelling leaves out:
- a lending member's receiver (`receiver shared` / `receiver exclusive`);
- `extends T` for an extension member of another module's type, so two extended types of one name differ;
- `in module M` for a top-level function whose module is named like a vocabulary declaration.

A closure is named for its enclosing function's declaration.

**Pins:** mono golden `names` (with its `// stage 0:` line, which the mono lane now honours by skipping the program's Stage 0 layout probe); run program `Range.saw` with its Stage 0 record; probes `accessor_pair` and `extension_same_name`.

**Golden churn:** 17 coro goldens, 40 lines each way. With ` receiver …` stripped and item numbers normalised, the added and removed lines pair off exactly, so every change is a name change. No `INVARIANT` line.

Gate in the worktree: `run.py --only mono,coro,programs` ok and `battery.sh citations` green. The diff applies cleanly to current main.

**Air: SL-671.p1 approved; arming it.**

- **The bug, reproduced on main's build and gone on the patch's:** `accessor_pair`, `extension_same_name` and `Range` each fail on main with clang's `invalid redefinition of function` (`saw prologue accessor_pair.Grid.[](i: Int)`, `saw extension_same_name.Path.weight()`, `saw Range.next()`); on the patch they build at `-O0` and `-O2` and print what they state (`8 1 8 1 8 6102`, `105`, `8`).
- **The funnel is whole:** the five item-symbol spellers the docstring lists (`ll_symbol`, `ll_resume_symbol`, `ll_descriptor_symbol`, `ll_resume_value_symbol`, `ll_result_drop_symbol`) are the only ones in `compiler/llvm/src`, every one goes through `item_name`, and the backend reads `func_name` nowhere; `ll_export_symbol` (an `@export`'s C name) and `ll_fail_symbol` (a stub by kind) are not item names.
- **The mechanism's reach, probed:** a module named like a generic vocabulary type (`Optional.saw` with `is_some()`, `Atomic.saw` with `load()`) builds on both main and the patch, since the dump's ` args …` suffix already tells a generic instance apart; the non-generic case (`Range.next()`) is the one that collided, and the `in module M` rule covers both uniformly.
- **The golden churn is renaming only:** with ` receiver …`, ` extends …`, ` in module …` and item numbers normalised, the removed and added lines of all 17 coro goldens pair off exactly (`probe_golden_pairing.py`); the only unpaired file is the new `names` golden; no `INVARIANT` line is added.
- `run.py --only mono,programs` ok on the patched tree (14 mono golden records incl. `names` with its Stage 0 skip; 130 run programs matching Stage 0, `Range` among them; the probes' `ll defines` checked). The diff applies cleanly on main with SL-652 merged.
