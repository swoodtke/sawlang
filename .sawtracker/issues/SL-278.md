## Description

In a coroutine-transformed (driven) frame, a `break` inside a match arm unbinds that arm's payload binding, producing an internal compiler error at a USE of the binding BEFORE the break on the same line:

    error: internal compiler error at repros/coro_match_break.saw:22:20 (Identifier): Undefined variable: n

The identical loop in a sync function compiles and runs. `return` in an arm is fine; only `break` triggers it. Found adopting SL-204: the natural read-loop shape is `case Value(bytes) -> { if bytes.len() == 0 { break } ... }`.

Self-contained reproducer (sawtracker repros/coro_match_break.saw carries the same file; sync twin passes, driven twin ICEs — expected output `1 1`):

    enum Step { case Value(value: Int), case Done }

    func next(i: Int) -> Step {
        if i > 3 { return Step.Done }
        Step.Value(value: i)
    }

    func sync_loop() -> Int {
        var total = 0
        var i = 0
        while {
            match next(i) {
                case Value(n) -> {
                    if n == 2 { break }
                    total += n
                },
                case Done -> { return total }
            }
            i += 1
        }
        total
    }

    func driven_loop() -> Int {
        var total = 0
        var i = 0
        while {
            sleep(Duration.ms(1))          // makes this frame suspending
            match next(i) {
                case Value(n) -> {
                    if n == 2 { break }
                    total += n
                },
                case Done -> { return total }
            }
            i += 1
        }
        total
    }

    func main() {
        print("{sync_loop()} {driven_loop()}")
    }

Workaround used in sawtracker (src/http.saw read loops, src/main.saw accept loop): set a flag in the arm and break after the match. Reproduced against sawlang main 5755f60b. Filed from sawtracker adoption of design 272 (ST-25); sawtracker-side analysis in SAW_NOTES ST-SAW-13.

FIXED on the coro-soundness batch branch (worktree-agent-a99290b0bdfc9988e). It is SL-273's mechanism from the other side, exactly as SL-273 c2 predicted — the full write-up is on SL-273; this is the short version plus what is specific to the `break` face.

WHY `break` AND NOT `return`. The coroutine transform CFG-splits a `match` for either of two reasons: it spans a suspension, or — design 96 DF6 — it carries a `break`/`continue` for an ENCLOSING suspension-spanning loop, which has to be routed to that loop's exit STATE instead of lowering in place as a raw jump. A `return` needs no such routing, so it never triggered the split and never met the bug. `continue` does, and falls exactly as `break` did (probed: `while`, `for` and `while let` all fail with `continue` before the fix).

The split relocates the arm bodies into their own resume states. `_collect_frame_locals` granted arm payloads a frame field on the SPANNING reason alone, so on a `break`-driven split the binding reached the relocated body only through a field it had never been given — `Undefined variable: n`, reported at the use BEFORE the break because that is simply the first read in the relocated block. `_FrameBuilder._is_split` is the one authority both the lowering and the residency census read now, and design 96's clause is decided in `_mark_ob_block` (the walk that knows which loop owns the jump) and stamped on the node.

The workaround sawtracker adopted — set a flag in the arm and break after the match — is no longer needed: the arm may `break` directly. `src/http.saw`'s read loops and `src/main.saw`'s accept loop can go back to the natural shape `case Value(bytes) -> { if bytes.len() == 0 { break } ... }` whenever the fix lands.

YOUR REPRO IS THE REGRESSION TEST, verbatim, at `examples/coro_match_arm_binding_early_exit.saw`, asserting `1 1` with the sync twin as the oracle.
