## Description

**For `riscv32-unknown-none-elf` with no `--target-features`, sawc states no feature list, so the object's instruction set is whatever the clang defaults to, and the front end assumes something else.** Found by SL-1077's fact-checking (Nov 12); confirmed by the lead.

**Measured** (`compiler/tests/run/riscv32/word_atomics.saw`, `sawc build --freestanding --target riscv32-unknown-none-elf`, no `--target-features`):
- the `.ll`'s attribute groups carry no `"target-features"` and no `"target-cpu"` (`attributes #0 = { "frame-pointer"="non-leaf" }`);
- the object (Homebrew LLVM's clang) holds `amoadd`, `lr.w` and `sc.w` instructions and references no `__atomic_*` routine: the clang's default for the triple includes the `A` extension (and, by the same default, `M` and `C`);
- `target_native_atomics("riscv32-unknown-none-elf", "")` (`compiler/target/src/layout.saw`) answers FALSE: with `a` unnamed it reads the triple's ISA string, and `riscv32` names no extension.

So three things disagree for the no-flag build: what the front end believes (no native atomics), what the spec says ("riscv32 without `+a`" calls the `__atomic_*_4` routines), and what is emitted (inline atomic instructions). And what is emitted is not sawc's decision at all: another clang with another default would emit other instructions from the same `.ll`. The other two bare-metal targets state their defaults: aarch64 `-fp-armv8`, Xtensa `-windowed,-fp,-loop,-mac16,-bool` with `esp32s3`.

**Who is affected today.** Nobody known: sawos and Blade always pass a list (Blade's default for a `riscv32` triple is `+m,+a,+c`), and every riscv32 test passes one. A user who types the bare command gets code for rv32imac, which traps on a core without those extensions, with nothing in the build saying which ISA was chosen.

**The class (obligation 4).** Every target record: does sawc state the feature list and CPU it reasons about, or leave part to the clang's default? Enumerate `target_triples()` and for each compare `target_effective_features` with the attribute group emitted and with what the front end's questions (`target_native_atomics`, the float-unit answer behind `ll_builtin_symbol`, `target_word_bytes`) assume. Hosted triples are expected to follow the host's baseline; say so explicitly for each.

**Decision (lead's, reversible; the Air may object in review).** riscv32 gets a stated default, as the other two do, and it is the triple's own meaning: `riscv32` names the base ISA and no extension, so the default is `-m,-a,-c,-f,-d` written out, the front end's present answer becomes true, and a build that wants extensions names them, as every existing user already does. The alternative, defaulting to `+m,+a,+c` (what Homebrew's clang happens to pick, and Blade's default), makes the bare command produce faster code and makes the triple's name mean less; it is the choice to make if the first breaks something step 0 finds.

**Implementation.**
1. Step 0: the census above, per target, as a table; and for riscv32 with the proposed default, build `lowering/builtin_uses.saw` and the six `riscv32/` probes with NO `--target-features` and record every undefined symbol. With `-m` a 32-bit multiply or divide becomes a call (`__mulsi3`, `__divsi3`, `__udivsi3`, `__modsi3`, `__umodsi3`, and 64-bit `__muldi3`); std's builtins (`std/builtins/`) may not define those. **If any such name is undefined, STOP and report the list: the default then needs either std routines or `+m`, and that is the lead's choice.**
2. With a clean step 0: `target_effective_features` returns the default for a `riscv32` triple with the operand appended (the Xtensa rule: `--target-features` adds to the default; a later `+a` wins over the default's `-a`); the attribute group carries it. Check `target_feature_state` reads the LAST mention of a feature, so `-a,...,+a` is On.
3. Blade's `toolchain_defaults` and every test that passes a full list are unaffected; confirm by the goldens that move: only no-flag riscv32 `.ll` files (list each).
4. Spec, Profiles: the riscv32 sentence states the default as the Xtensa paragraph does. saw-docs skill first.
5. A row in `word32_ir.py`'s riscv32 feature sets for the no-flag build (the atomics probe references the five routines there, as with `-a`).

**Tests and gate.** `compiler/tests/run.py --only seed,units,golden,subset,fixture_whitespace,std,programs,docs,comments`; `tools/freestanding_runner.py` (its riscv32 row passes lists everywhere; expected unchanged); `tools/blade_lane.py`; `tools/battery.sh citations`.

**Lead decision after step 0 (Nov 13): the riscv32 default is `+m,+a,+c`, given when no `--target-features` is passed; an operand replaces it.** This supersedes the description's "Decision" and its steps 2 and 5. Reversible; the Air may object in review, and the user may overrule.

**What step 0 found** (agent p1084; logs in the lead's checkout, `.build/scratch/p1084/census_minus_m.log`, `census_plus_mac.log`, `census.md`). With `-m,-a,-c,-f,-d`, 70 objects (the eight `lowering/` programs and the six `riscv32/` probes at five optimization levels) reference `__mulsi3` (8 objects), `__divsi3` (20), `__udivsi3` (46), `__modsi3` (20), `__umodsi3` (18) and `__muldi3` (65). `std/builtins/` defines none of them (it has the 64-bit divide, remainder and shift routines, the memory routines and soft float). So a base-ISA default would make the bare command produce objects that do not link. With `+m,+a,+c` none of the six is referenced.

**Why `+m,+a,+c`, and why "replaces".**
- It is what the bare command has been emitting (the clang's default for the triple) and what Blade passes, so no object anyone builds today changes; the change is that sawc states it and the front end's answers (`target_native_atomics`, the float unit) are asked about the same list the code is compiled for.
- An explicit list keeps the meaning it has today. A function's `"target-features"` attribute replaces the target machine's list in LLVM, so today `--target-features=+m,-a,+c` means the base ISA plus M and C, and `+m` alone means rv32im. If the operand were added to a `+m,+a,+c` default (the Xtensa rule), `+m` alone would silently become rv32imac. Xtensa's rule exists because `-windowed` is the calling convention and two objects must agree on it; riscv32 has no such feature in the list. The aarch64 rule already in the funnel is the precedent: a default for a build with no operand, and an operand replaces it outright.
- The default applies to every riscv32 build, freestanding or not: the triple is bare-metal either way.

**Implementation (replaces steps 2 and 5; steps 3 and 4 hold with the new text).**
1. `target_effective_features` (`compiler/target/src/layout.saw`): for a `riscv32` triple, `explicit` when it is not empty, else `+m,+a,+c`. The funnel's comment states the three rules. `compiler/target/tests/float_instructions.saw` asserts `""` for the no-flag riscv32 case today; it moves to the default, and gains the cases "an operand replaces it" (`+m` gives `+m`; `+m,-a,+c` unchanged).
2. **The mechanism check (obligation 4).** Every caller of `target_native_atomics`, `target_float_unit`, `target_front_end` and the feature questions behind `ll_builtin_symbol` must pass the EFFECTIVE list, never the raw operand. List each caller and what it passes. One that passes the operand is the mechanism of this bug and is fixed in this unit (it would also be wrong on Xtensa and freestanding aarch64: say whether it is, with a build that shows it).
3. Check everything that keys on the feature list (the front cache's key, the object cache's key) uses the effective list too, so a no-flag build and a `+m,+a,+c` build may share entries and nothing keyed on `""` goes stale. Report what each keys on.
4. `word32_ir.py`: a third riscv32 feature set, the no-flag build (no `--target-features` argument at all), expecting what the `+m,+a,+c` set expects (inline atomics, no `__atomic_*` reference).
5. Spec, Profiles: the riscv32 sentence states the default and that an operand replaces it, beside the aarch64 and Xtensa statements. The saw-lang skill and README only where they state the riscv32 default today. saw-docs skill first.

**Pins the report shows.**
- No-flag build of `riscv32/word_atomics.saw`: the attribute group reads `"target-features"="+m,+a,+c"`; the object is byte-for-byte the object main's compiler writes for the same command with the same clang (or the difference, explained).
- `--target-features=+m,+a,+c`: `.ll` and object identical to main's.
- `--target-features=+m,-a,+c`: `.ll` identical to main's; the object references the `__atomic_*_4` routines.
- `--target-features=+m`: the attribute group reads `+m` and nothing else.
- Goldens that move: only no-flag riscv32 `.ll` files, each listed. Any other golden moving is a mismatch.

**Gate:** as the description's.

**Not in this unit, filed separately:** std has no `__mulsi3`-class routines, so any riscv32 build without `+m` fails at link on its first multiply or divide. That was true before this issue and stays true after it.

**Lead's note with the patch (Nov 13): one correction to my decision comment, the mechanism the unit found, and one thing left.**

**Correction.** My decision comment said that with `+m,+a,+c` as the default "no object anyone builds today changes". That is true of every build that passes a list, and false of the bare command. Measured on `riscv32/word_atomics.saw` (`build --freestanding -g0 -c --target riscv32-unknown-none-elf`, Homebrew LLVM's clang; files in the lead's checkout under `.build/scratch/p1084/pins/` and `.build/scratch/p1084/lead/`):
- main's compiler, no flag: 148,424 bytes; the patch's compiler, no flag: 85,628 bytes, byte-for-byte the object both compilers write for `--target-features +m,+a,+c`.
- the patch's compiler with `--target-features +m,+a,+c,+relax`: disassembly and relocations identical to main's no-flag object (`llvm-objdump -d -r`, no differing line); the two files differ only in the string table's length (6 bytes).

So the clang's default for the triple is rv32imac WITH linker relaxation, and a function's `"target-features"` attribute replaces that list, relaxation included. The instruction set of the bare command's object is unchanged by this patch; what changes is that it no longer carries relaxation relocations, exactly like every Blade and sawos build today. The decision stands: the default is the list Blade passes, so the bare command and a Blade build write the same object. Whether riscv32 builds should ask for `+relax` is a size question for a measurement, not part of this unit.

**The mechanism (obligation 4).** The checking subcommands (`sawc typecheck`, `resolve`, `mono`, `coro`, through `driver_check_target`) asked the target record about the RAW operand, while `sawc build` asked about the effective list. With the new default that made `sawc typecheck --check --freestanding --target riscv32-unknown-none-elf` refuse a `SpinLock` static (`atomics.target`) that `sawc build` accepts. Fixed in the patch: `driver_check_target` takes `freestanding` and asks about `target_effective_features`. The front cache keys on the record's answers and the object cache on the IR text, so neither key changed.

**Left, not in this patch.** `sawc mono` and `sawc coro` take no `--freestanding` flag and pass `false`, so for `aarch64-unknown-none-elf` they are asked about a list without the freestanding default (`-neon,-fp-armv8`), where `build --freestanding` has it. Not shown by a build; riscv32 and Xtensa are unaffected (their defaults apply to every build). Added to SL-1088's list.

**Process.** The agent used `sed -i` once (an import line in `compiler/target/tests/float_instructions.saw`), against the brief; the line is in the diff and reads correctly.
