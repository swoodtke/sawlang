## Description

**For `riscv32-unknown-none-elf` with no `--target-features`, sawc states no feature list, so the object's instruction set is whatever the clang defaults to, and the front end assumes something else.** Found by SL-1077's fact-checking (Nov 12); confirmed by the lead.

**Measured** (`compiler/tests/run/riscv32/word_atomics.saw`, `sawc build --freestanding --target riscv32-unknown-none-elf`, no `--target-features`):
- the `.ll`'s attribute groups carry no `"target-features"` and no `"target-cpu"` (`attributes #0 = { "frame-pointer"="non-leaf" }`);
- the object (Homebrew LLVM's clang) holds `amoadd`, `lr.w` and `sc.w` instructions and references no `__atomic_*` routine: the clang's default for the triple includes the `A` extension (and, by the same default, `M` and `C`);
- `target_native_atomics("riscv32-unknown-none-elf", "")` (`compiler/target/src/layout.saw`) answers FALSE: with `a` unnamed it reads the triple's ISA string, and `riscv32` names no extension.

So three things disagree for the no-flag build: what the front end believes (no native atomics), what the spec says ("riscv32 without `+a`" calls the `__atomic_*_4` routines), and what is emitted (inline atomic instructions). And what is emitted is not sawc's decision at all: another clang with another default would emit other instructions from the same `.ll`. The other two bare-metal targets state their defaults: aarch64 `-fp-armv8`, Xtensa `-windowed,-fp,-loop,-mac16,-bool` with `esp32s3`.

**Who is affected today.** Nobody known: sawos and Blade always pass a list (Blade's default for a `riscv32` triple is `+m,+a,+c`), and every riscv32 test passes one. A user who types the bare command gets code for rv32imac, which traps on a core without those extensions, with nothing in the build saying which ISA was chosen.

**The class (obligation 4).** Every target record: does sawc state the feature list and CPU it reasons about, or leave part to the clang's default? Enumerate `target_triples()` and for each compare `target_effective_features` with the attribute group emitted and with what the front end's questions (`target_native_atomics`, the float-unit answer behind `ll_builtin_symbol`, `target_word_bytes`) assume. Hosted triples are expected to follow the host's baseline; say so explicitly for each.

**Decision (lead's, reversible; the Air may object in review).** riscv32 gets a stated default, as the other two do, and it is the triple's own meaning: `riscv32` names the base ISA and no extension, so the default is `-m,-a,-c,-f,-d` written out, the front end's present answer becomes true, and a build that wants extensions names them, as every existing user already does. The alternative, defaulting to `+m,+a,+c` (what Homebrew's clang happens to pick, and Blade's default), makes the bare command produce faster code and makes the triple's name mean less; it is the choice to make if the first breaks something step 0 finds.

**Implementation.**
1. Step 0: the census above, per target, as a table; and for riscv32 with the proposed default, build `lowering/builtin_uses.saw` and the six `riscv32/` probes with NO `--target-features` and record every undefined symbol. With `-m` a 32-bit multiply or divide becomes a call (`__mulsi3`, `__divsi3`, `__udivsi3`, `__modsi3`, `__umodsi3`, and 64-bit `__muldi3`); std's builtins (`std/builtins/`) may not define those. **If any such name is undefined, STOP and report the list: the default then needs either std routines or `+m`, and that is the lead's choice.**
2. With a clean step 0: `target_effective_features` returns the default for a `riscv32` triple with the operand appended (the Xtensa rule: `--target-features` adds to the default; a later `+a` wins over the default's `-a`); the attribute group carries it. Check `target_feature_state` reads the LAST mention of a feature, so `-a,...,+a` is On.
3. Blade's `toolchain_defaults` and every test that passes a full list are unaffected; confirm by the goldens that move: only no-flag riscv32 `.ll` files (list each).
4. Spec, Profiles: the riscv32 sentence states the default as the Xtensa paragraph does. saw-docs skill first.
5. A row in `word32_ir.py`'s riscv32 feature sets for the no-flag build (the atomics probe references the five routines there, as with `-a`).

**Tests and gate.** `compiler/tests/run.py --only seed,units,golden,subset,fixture_whitespace,std,programs,docs,comments`; `tools/freestanding_runner.py` (its riscv32 row passes lists everywhere; expected unchanged); `tools/blade_lane.py`; `tools/battery.sh citations`.
