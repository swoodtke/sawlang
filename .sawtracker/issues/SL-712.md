**Air, on the hold: SL:borrowing already contains the distinction option 1 needs, so the exception can be stated as a rule rather than a carve-out.**

- **The getitem precedent (§5.1, §5.2, Ruled):** `m[k]` is "a shared lend plus a copy" and is written with no `borrow`; "plain subscripts are values and `borrow` subscripts are places; the spelling at the call site picks the role." §2.2 then says `borrow` "is written only where a `borrows` accessor is called" — but a derived getitem calls one and is still bare, because what the *reader* gets is a value, not a place. §5.2's "field reads of a derived getitem" goes further and lets `v[i].f` lower as a shared borrow plus a copy of `f` with no spelling, when the copy runs no code.
- **Forwarding is the same shape.** `b.peek()` opens a shared lend of the payload, calls a `&self` method on it, and closes the lend inside the expression; the caller holds nothing afterwards. The reader gets a value. A forwarded `borrows` method is different: its result *is* a place, and it is already spelled — the spec's own example (`borrow var c = arc.lock() { … }`, LANGUAGE_SPEC ~8395) and the corpus (`arc_forward.saw`: `ac.peek()` bare, `borrow var c = shared.lock()` spelled; `capture_write_allowed_forms.saw`, `alloc_channel_taskgroup_reports_oom.saw` likewise).
- **So the rule for §2.7 or a new §2.8:** *through a `Box` or an `Arc`, a `&self` method of the payload is called bare, like a getitem, because its lend opens and closes inside the call and its result is a value; a `borrows` method of the payload yields a place and is written under `borrow`, like any other `borrows` call. A `&var self` payload method does not forward (refused, `forward.exclusive-receiver`). The pointer's own members win the lookup.* The user's reason ("just reading the code") is kept: `borrow` still marks every expression whose result is a held place, and never marks one whose result is a copy — the same line the getitem ruling drew.
- **Options 2 and 3 cost real spellings:** option 2 makes every `ac.peek()` into `borrow ac.value().peek()` and every `shared.lock()` into `borrow var c = borrow shared.value().lock()` (a `borrow` inside a `borrow` head, which §2.2's chain rule allows but nobody wants to read), and option 3 keeps `Arc` and `Box` from being the same shape, which the spec says they are ("like `Arc`").
- **Sound either way:** the forwarded lend is a shared hold on the pointer for the call, so `b.peek()` while a `borrow var p = b.value()` window is open is the ordinary exclusivity error, and K-row coverage for that cell (bare forward inside an exclusive window → refused) is what the patch owes beyond its fixtures.

Recommendation: option 1 with the paragraph above as the Ruled text.
