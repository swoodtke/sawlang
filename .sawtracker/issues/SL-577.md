**p577dump: A16b stopped at Step 0, before any code.** The dump's format can be produced exactly. But three parts of the scope need files outside the list (`std/taskgroup.saw`, `std/task.saw`, `tools/lldb_saw.py`, `tools/test_bt_table.py`, the run lane's `held_probe`). Base 14c86c546. The only edit is the `// (SL-577: in progress)` line at the top of `std/taskgroup.saw`, uncommitted.

**Step 0, the format** (Stage 0's corpusdiff records, darwin):
- **Header:**
  - `saw tasks: N live (unsynchronized snapshot)` from `dump_tasks()`, on stdout. Single- and multi-threaded groups print the same header; `task_backtrace_mt` prints this one.
  - `saw tasks: N live (as-of panic, unsynchronized)` on the panic path, on stderr after the panic line.
  - `saw tasks: none live` when nothing is live. A panic with nothing live prints its line alone.
- **Task line:** `  task group G slot S gen N STATUS`. G is the group's 1-based position in the walk, newest-registered first. STATUS is `running` (active), `io-parked`, `channel-parked`, `ready` or `sleeping`.
- **Frame lines:** `    at FILE:LINE in NAME`, innermost first. A state record always prints its line, so a root that was never resumed prints `:0` (K86: `ready`, `at K86_…:0 in work`, two groups). An index outside the table prints `    at <unknown frame>`.
- **The pins:**
  - nest: slot 0 gen 1 `sleeping`, at 24 leaf, 29 middle, 34 worker; slot 1 gen 1 `running`, at 41 watcher.
  - mt: the same shape, `channel-parked`, at 50/55/60, then `running` at 78.
  - K67: the panic line, `saw tasks: 1 live (as-of panic, unsynchronized)`, `task group 1 slot 0 gen 1 channel-parked`, `at K67_…:30 in consume`.
  - `coro_panic_value_position`: gen 4 `running`, at 48 in boom.

**How the new std reaches a task:**
- **The walk:** `EXEC_RECORDS`, then each record's `groups` list through `TaskGroup.next`, then each group's `slots`, taking the slots that are not `done`. This is the registry `quiescent_now` walks (c5). Groups are numbered across records in walk order.
- **The frame:** the slot's `frame`. A pool worker doesn't take it out while it resumes.
- **The table index:** `cell.descriptor[0].backtrace`. A16a fills it in every task-root descriptor and in `main`'s.
- **The status:** from `slot.active` and `cell.park`:
  - `PARK_READY` is `ready`;
  - `PARK_TIMER` is `sleeping`;
  - `PARK_FD` is `io-parked`;
  - an even word below -1 is `channel-parked`.
- **The frame lines:** the table walk is Stage 0's `__bt_*` as it stands. A16a's fold already records a std park as a leaf on the caller's line.

**The stop: three crossings.**

1. **std can't read the table.** sawc2 has no `__saw_bt_table()` intrinsic, and a Saw `extern` names a function, not data.
   - Probe `.build/scratch/p577/table_probe.saw`: clang says `redefinition of function '@__saw_bt_table'`.
   - **Proposal:** the backend defines `ptr @__saw_bt_table_address()` beside the table global. std declares it `extern "C"`, the pattern of `__saw_rt_get_argc` and `__saw_frame_resume`.
   - **Files:** `compiler/llvm/src/program.saw`, or `module.saw` beside `bt_table_global`.
   - No seed bump is needed, as long as the compiler binary never reaches the walker (see 2).

2. **The panic path can't reach `std.taskgroup`.** Every panic ends in the lang item `panic_sink` (`std/panic.saw`), which calls `__saw_rt_panic`. Stage 0 has the compiler pick `__saw_bt_panic` when the executor links. SL-572 c3 ruled out a `std/panic.saw` hook for A13b.
   - **(a) A hook in `std/panic.saw`.**
     - The state: `static PANIC_REPORT: Atomic<Int>` holds the address of a never-freed record carrying a `(UnsafePointer<Int8>, Int) unsafe sync -> Void` closure.
     - The install: taskgroup's `claim_record`, when it makes the process's first executor record, before any task exists.
     - The call: when the hook is set and not re-entered, `panic_sink` takes the output lock, writes the message through `__saw_rt_write_error`, and calls the hook (the walker, writing to stderr). Then it calls `__saw_rt_panic(message, 0)`, as Stage 0's `__saw_bt_panic` does. Otherwise it takes the seam as today.
     - **The cone:** `std.panic` stays task-free statically, with no import. The cone gains a static load and an indirect call. The compiler binary reaches `panic_sink` and never the walker.
     - **The probe:** `.build/scratch/p577/hook_probe.saw` builds and runs under `sawc2-stage2`: a closure in a heap record, reached through an `Int` static, called through it. A named function as the value is refused (`backend.not-yet`: a memory constant), so the hook is a closure literal.
   - **(b) A compiler-chosen sink, Stage 0's way.** That needs a second lang item rooted when the executor is reached, across `resolve/src/lang.saw`, typecheck, mono and llvm, which crosses A18's track.
   - **Recommendation:** (a). **Files:** `std/panic.saw`.

3. **The exec descriptor is the compiler's bytes.** `exec_off` points inside the blob that `compiler/coro/src/bttable.saw` builds, and that file holds `CORO_BT_VERSION`. The offsets are std types' layouts, which mono knows.
   - **The proposed v2 descriptor**, all u32:
     - the head symbol, `EXEC_RECORDS`' LLVM name, as a string-table offset;
     - `ExecutorRecord.{groups, next}`;
     - `TaskGroup` size and `.{slots, next, lock}`;
     - a `Vector`'s element-pointer and length offsets;
     - `TaskSlot` size and `.{frame (present, pointer), cell (present, pointer), generation, done, active}`;
     - `TaskCell.{descriptor, park}`;
     - `FrameDescriptor.backtrace`.
   - **The version:** 2, and `coro_bt_render` prints `exec=OFFSET`.
   - **lldb:** `lldb_saw.py` imports Stage 0's decoder, which refuses any version but 1, and `sawc/` is frozen. So the script carries its own v2 decoder and keeps v1 for Stage 0's binaries.
   - **`test_bt_table.py`** compiles with Stage 0 throughout (`sawc.py --emit-bt-table`), so its fixture check reads Stage 0's v1 table. I'd leave it, or move it to `sawc2 coro --bt-table`.
   - **Files:** `bttable.saw`. **Goldens that move:** the coro lane's `.bttable` records, and every `.ll` golden that carries the table's version byte, `hello.ll` included.
   - **The alternative:** split the exec descriptor into its own unit with lldb and `test_bt_table.py`. The in-process walker doesn't read it.

**Decisions needed (each reversible):**

**Air: SL-577.p1 (A16b) approved.** Reviewed on origin/main bd9cb0c75 plus r1; probes in `air-review/sl577p/`.

**The risk I watched for: the panic dump walks other threads' live frames with no lock** (`q1_panic_beside_busy_thread.saw`). A `Thread.spawn` body drives three tasks that `yield_now()` in a tight loop, so their state words change constantly, while `main`'s task panics.
- **600 runs (300 per level): every one exit −6.** Each prints the panic line, the `saw tasks: 4 live (as-of panic, unsynchronized)` header and four well-formed slot and frame pairs. No SIGSEGV or SIGBUS, and no malformed line.
- The busy tasks' statuses vary run to run (`ready`, `running`, `unrecorded`; occasionally two `running` in one single-threaded group). That's the documented unsynchronized snapshot. **Every frame line is right whatever the status** (`at …:12 in spinner`, the `yield_now`), so a mid-resume state never indexes the table wrongly.
- The re-entry guard (`PANIC_REPORTING`'s compare-and-swap) and the plain-seam fallback read right for a panic inside the report and for a second thread's panic.

**`dump_tasks()` over mixed states** (`q2_dump_states.saw`, both levels): `sleeping` at the `sleep`, `channel-parked` at the `receive`, `joining` at 1b-ii's `Thread.join` park, and `running` for the dumping task. Then the program continues: `results 1 5 200`, exit 0.

**Cost to a task-free program:** `hello.ll` gains two statics (`PANIC_REPORT`, `PANIC_REPORTING`) and five small atomic helpers, with no walker, as the hook's design intends.

**Gates:** `run.py --only subset,std_cone` passes.

**Notes, not blocking:**
1. **A `running` task's frame line is its LAST SUSPENSION, not where it is now.** `dumper` prints `at …:31` (its `sleep`) while it is executing `dump_tasks()` on line 32. In `q1`, `doomed` prints `:27` (its `sleep`) beside the panic line's `:28`. That's what the frame records, and the panic line gives the current site. But no corpus row pins a running task's line against Stage 0 (`task_backtrace_panic` pins only the parked ones), so the dump's docs should say "a running task: the line it last resumed from".
2. **The aarch64 run lane didn't run** (the Linux VM's disk is full, per the submission), and the server's gate has no Linux lane. The aarch64 Stage 0 record of `channel_deadlock_cycle_dump` is in the patch but unexercised against an aarch64 build until the VM is cleared.
