## Description

**On x86_64 Linux the run probe `process_output_cancel_reaps_child` dies intermittently in ways a correct program cannot: a `Vector` with a length and no buffer at `-O2`, a segfault at `-O0`.** Found by the lead's Linux run after SL-1105 landed (Nov 14, main e5279661f, the `sawlang-linux` VM, x86_64 cross-built and run under Rosetta). The probe is unchanged by SL-1105 and passes on macOS and on aarch64 Linux.

**Evidence** (logs under `.build/scratch/linux/` in the lead's checkout; binaries built in the VM by its Stage 2 with `sawc build -O? --target x86_64-unknown-linux-gnu`, then run in a loop keeping standard error):

| binary | runs | bad | how it dies |
|---|---|---|---|
| reaps_child, x86_64, `-O2` | 150 | 4 | exit 134, `panic at vector.saw:92: Vector.[]: buffer is empty` |
| the same binary again | 150 | 10 | the same panic, every time |
| reaps_child, x86_64, `-O0` | 150 | 5 | exit 139 (segfault), nothing on standard error |
| reaps_child, aarch64, `-O2` | 300 | 0 | |
| `process_output_cancel_ends_its_drain`, x86_64, `-O2` | 150 | 0 | |
| `process_output_cancel_closes_the_pipe`, x86_64, `-O2` | 150 | 0 | |

In the lane itself it was 1 failure in 4 runs of the probe (`run_1105_x86_64.log`: `-O2: exit -6`). Every bad run printed nothing on standard output, so it dies before the probe's two final prints.

**Why this is not a test's flake.** `std/vector.saw`'s `[]` panics "buffer is empty" only after its range check passed: the index is in `0..<length`, so the length is above zero, and the buffer is absent. No sequence of pushes makes that state. The probe indexes one vector, `pids` (`existing`: `kill(pids[i], 0)`), which it only ever pushes to (`look`), through a `&var Vector<Int32>` handed down from `main` across suspensions (`await_started` and `await_exits` sleep between looks; `sweep_until_reaped` holds `&pids` across a sleep). Whether the panicking vector is `pids` or one inside std (the task group's, the reactor's) is not known: the panic has no backtrace.

**Not known.**
- Which vector, and what wrote over it or which reference went stale.
- Whether it happens on real x86_64 hardware or only under Rosetta. Rosetta changes timing and memory ordering; a real data race would show there first. The VM's cross toolchain has no x86_64 address-sanitizer runtime (`libclang_rt.asan.a` for `x86_64-unknown-linux-gnu` is absent), so `--sanitize address` does not link there.
- Why this probe and not its two siblings. What it has that they lack: `dup2` of standard error around each launch, `poll(2)` on a pipe through a `PollFd` struct, twenty rounds each with its own `TaskGroup()`, and a reference to a vector in `main`'s frame used inside callees that suspend.
- Whether macOS x86_64 (Rosetta on the host) shows it.

**For the investigation** (obligation 4: name the mechanism before a fix): reduce the probe while keeping the failure rate (drop the process work first: does a `&var Vector` pushed in a callee that sleeps, twenty groups in a row, fail alone?); print the vector's address, length and buffer at each look; build with `-g` and take a core in the VM; try `--codegen-units=1`, `-O1`, and a `TaskGroup(threads: 1)`; try the x86_64 macOS target on the host under Rosetta; compare the coroutine frame layout of `await_started` and `sweep_until_reaped` between the two architectures (`sawc coro --layouts`).

**Also** (recorded on SL-1088): the run lane's message for a stated probe that exits with the wrong status shows the output difference and not standard error, so this panic's text was invisible in the lane's log.

**The mechanism (Opus investigation p1109, Nov 14; lead reproduced the reduction on macOS with main's compiler, 3 of 3). It is a use-after-free in std's executor, reachable from safe code on every target. It is not the probe, not code generation, and not Rosetta's memory model.** Evidence is under `.build/scratch/p1109/` in the lead's checkout (file names in brackets).

**The fault.** `std/taskgroup.saw`, `sweep_passes`: the scheduler's walk holds a group pointer and a slot index (`g`/`cur`/`i`) across a resume of a task that does NOT belong to that group. The sleep-order hand-off (`walk_turn` / `cooperative_sleeper`: "A turn given to another sleeper keeps the walk here") can give the turn to the group's OWNER (`main`, or any suspending function it calls), which joins the task, drops the group, and parks. The walk then goes on reading the dead group: `g[0].runnable(i)` indexes its `slots` vector. The `ahead`-of-waiter loop inside `sweep_finished`, also called mid-walk, resumes other tasks the same way. The hand-off arrived with SL-977.p3 (8bf777058, Nov 6), so it is in v0.21.0, v0.22.0 and v0.23.0.

**Twenty lines, no processes, no unsafe** (`src/r1.saw`): twenty rounds of `var group = TaskGroup()`, `let t = group.spawn(napper())` where `napper` sleeps 1 ms, `sleep(1 ms)` in `main`, `t.join()`; then a sleeping call.

| program | what | result |
|---|---|---|
| `r1.saw` | as above | fails 100 of 100 on x86_64 and aarch64 Linux at `-O0`, `-O1`, `-O2`, `--codegen-units=1`, and on macOS arm64: `Vector.[]: buffer is empty` (or a segfault at `-O0`) [matrix_r1_r2.log, r1_mac_O2.log] |
| `r2.saw` | one round, the group in a called function's frame | segfault 100 of 100 everywhere |
| `s1.saw` | round 1's group has two slots, round 2's one, built at the same address | `Vector.[]: index out of range: 1 (len 1)`, 300 of 300 on macOS, 100 of 100 in the VM [s1_host.log, s1_vm.log] |
| `c1.saw`, `c2.saw` (controls) | without `main`'s sleep before the join; with `main` sleeping 5 ms so the task's timer is first | 0 of 300 each [controls_mac.log] |

What is needed: a group's owner sleeping AHEAD of one of the group's sleeping tasks in the sleep order, then tearing the group down.

**The silent form is the common one.** When the next round builds a new group at the same address, the walk carries on over a DIFFERENT group with a stale index and nothing crashes: 274 of 300 x86_64 runs of the original probe did that [ring5b_x86_O2.log]. Only when another frame overwrites the storage (the last round) does it crash.

**Which vector, in the original probe:** not `pids` (one address, buffer present, length growing to 20 in failing runs) but the slot list of round 20's group: element size 64 (`TaskSlot`), at `main`'s frame + 8 where `group` lives, holding what `await_exits`'s frame puts there [i1_x86_O2.log, layouts_x86.txt]. An event ring printed at the panic gives the order every time: the walk stands on round 20's group, slot 0; `main`'s timer is first, so the walk hands `main` the turn; `main` joins, drops the group (the list's epoch moves 19 to 20), enters `await_exits` and parks; the walk resumes on the same pointer and `runnable(0)` panics [ring2_fail49.log, ring4_tails.log].

**Why only x86_64 showed it in the lane.** Under Rosetta `pidfd_open` fails (ENOSYS); natively on aarch64 it returns a descriptor [pidfd.log]. With no descriptor, `Command.output` waits for the child by a doubling sleep from 1 ms, the same tick as the probe's own wait, so the cancelled task is a timer sleeper and the hand-off can happen. Forcing the no-descriptor path in a scratch std makes the unmodified probe fail 10 of 300 on native aarch64 Linux and 1 of 300 on macOS [nofd_a64.log, nofd_mac.log]. Code generation is ruled out: `sawc coro --layouts` and the IR of the functions involved are identical across the two architectures [layouts_*.txt, irdiff_x86_a64.txt].

**A candidate, tested in a scratch std** (`std_f`, `edits/tg_fix.spec`): when `record.regroups` (the group list's epoch) changed across `resume_queued` plus `sweep_finished`, restart the pass instead of continuing. `r1`, `r2`, `s1`: 0 of 300 in every cell; the original probe on x86_64: 0 of 300 at `-O2`, 0 of 600 at `-O0`; the no-descriptor aarch64 build: 0 of 300 [fix_matrix_and_base_O0.log, fix_mac.log, fix_orig_x86.log]. It confirms the mechanism. It is NOT yet the fix: see the lead's note below.

**Closed off:** a group inside a spawned task is refused at compile time (`coro.spawn-not-send`), so the owner is always `main`'s chain or a drive point.

**Not determined:** real x86_64 hardware (expected: `pidfd_open` works, so the original probe passes, while `r1`/`s1` fail everywhere); whether `sweep_finished`'s waiter path alone can destroy the walked group; which of the 112 tracked `.saw` files holding both `TaskGroup()` and `sleep(` meet the shape (grep candidates only).

**Lead's note on the fix.** Restarting a pass whenever the group list changed is safe for memory and open for fairness: a task at the head of the list that makes or drops a group on every turn restarts the walk every turn, and a runnable task in a later group may never be reached. The fix needs a design pass over the whole executor first: every place that holds a group pointer or a slot index across a resume (the cooperative walk, `sweep_finished`'s loop, the queue build that already checks the epoch, the pool, the background `Task.spawn` singleton, the thread-context waits that run a thread's tasks), one rule for all of them, and a fairness pin beside the three reductions. That pass is dispatched next.
