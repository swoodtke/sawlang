## Description

**On x86_64 Linux the run probe `process_output_cancel_reaps_child` dies intermittently in ways a correct program cannot: a `Vector` with a length and no buffer at `-O2`, a segfault at `-O0`.** Found by the lead's Linux run after SL-1105 landed (Nov 14, main e5279661f, the `sawlang-linux` VM, x86_64 cross-built and run under Rosetta). The probe is unchanged by SL-1105 and passes on macOS and on aarch64 Linux.

**Evidence** (logs under `.build/scratch/linux/` in the lead's checkout; binaries built in the VM by its Stage 2 with `sawc build -O? --target x86_64-unknown-linux-gnu`, then run in a loop keeping standard error):

| binary | runs | bad | how it dies |
|---|---|---|---|
| reaps_child, x86_64, `-O2` | 150 | 4 | exit 134, `panic at vector.saw:92: Vector.[]: buffer is empty` |
| the same binary again | 150 | 10 | the same panic, every time |
| reaps_child, x86_64, `-O0` | 150 | 5 | exit 139 (segfault), nothing on standard error |
| reaps_child, aarch64, `-O2` | 300 | 0 | |
| `process_output_cancel_ends_its_drain`, x86_64, `-O2` | 150 | 0 | |
| `process_output_cancel_closes_the_pipe`, x86_64, `-O2` | 150 | 0 | |

In the lane itself it was 1 failure in 4 runs of the probe (`run_1105_x86_64.log`: `-O2: exit -6`). Every bad run printed nothing on standard output, so it dies before the probe's two final prints.

**Why this is not a test's flake.** `std/vector.saw`'s `[]` panics "buffer is empty" only after its range check passed: the index is in `0..<length`, so the length is above zero, and the buffer is absent. No sequence of pushes makes that state. The probe indexes one vector, `pids` (`existing`: `kill(pids[i], 0)`), which it only ever pushes to (`look`), through a `&var Vector<Int32>` handed down from `main` across suspensions (`await_started` and `await_exits` sleep between looks; `sweep_until_reaped` holds `&pids` across a sleep). Whether the panicking vector is `pids` or one inside std (the task group's, the reactor's) is not known: the panic has no backtrace.

**Not known.**
- Which vector, and what wrote over it or which reference went stale.
- Whether it happens on real x86_64 hardware or only under Rosetta. Rosetta changes timing and memory ordering; a real data race would show there first. The VM's cross toolchain has no x86_64 address-sanitizer runtime (`libclang_rt.asan.a` for `x86_64-unknown-linux-gnu` is absent), so `--sanitize address` does not link there.
- Why this probe and not its two siblings. What it has that they lack: `dup2` of standard error around each launch, `poll(2)` on a pipe through a `PollFd` struct, twenty rounds each with its own `TaskGroup()`, and a reference to a vector in `main`'s frame used inside callees that suspend.
- Whether macOS x86_64 (Rosetta on the host) shows it.

**For the investigation** (obligation 4: name the mechanism before a fix): reduce the probe while keeping the failure rate (drop the process work first: does a `&var Vector` pushed in a callee that sleeps, twenty groups in a row, fail alone?); print the vector's address, length and buffer at each look; build with `-g` and take a core in the VM; try `--codegen-units=1`, `-O1`, and a `TaskGroup(threads: 1)`; try the x86_64 macOS target on the host under Rosetta; compare the coroutine frame layout of `await_started` and `sweep_until_reaped` between the two architectures (`sawc coro --layouts`).

**Also** (recorded on SL-1088): the run lane's message for a stated probe that exits with the wrong status shows the output difference and not standard error, so this panic's text was invisible in the lane's log.

**The mechanism (Opus investigation p1109, Nov 14; lead reproduced the reduction on macOS with main's compiler, 3 of 3). It is a use-after-free in std's executor, reachable from safe code on every target. It is not the probe, not code generation, and not Rosetta's memory model.** Evidence is under `.build/scratch/p1109/` in the lead's checkout (file names in brackets).

**The fault.** `std/taskgroup.saw`, `sweep_passes`: the scheduler's walk holds a group pointer and a slot index (`g`/`cur`/`i`) across a resume of a task that does NOT belong to that group. The sleep-order hand-off (`walk_turn` / `cooperative_sleeper`: "A turn given to another sleeper keeps the walk here") can give the turn to the group's OWNER (`main`, or any suspending function it calls), which joins the task, drops the group, and parks. The walk then goes on reading the dead group: `g[0].runnable(i)` indexes its `slots` vector. The `ahead`-of-waiter loop inside `sweep_finished`, also called mid-walk, resumes other tasks the same way. The hand-off arrived with SL-977.p3 (8bf777058, Nov 6), so it is in v0.21.0, v0.22.0 and v0.23.0.

**Twenty lines, no processes, no unsafe** (`src/r1.saw`): twenty rounds of `var group = TaskGroup()`, `let t = group.spawn(napper())` where `napper` sleeps 1 ms, `sleep(1 ms)` in `main`, `t.join()`; then a sleeping call.

| program | what | result |
|---|---|---|
| `r1.saw` | as above | fails 100 of 100 on x86_64 and aarch64 Linux at `-O0`, `-O1`, `-O2`, `--codegen-units=1`, and on macOS arm64: `Vector.[]: buffer is empty` (or a segfault at `-O0`) [matrix_r1_r2.log, r1_mac_O2.log] |
| `r2.saw` | one round, the group in a called function's frame | segfault 100 of 100 everywhere |
| `s1.saw` | round 1's group has two slots, round 2's one, built at the same address | `Vector.[]: index out of range: 1 (len 1)`, 300 of 300 on macOS, 100 of 100 in the VM [s1_host.log, s1_vm.log] |
| `c1.saw`, `c2.saw` (controls) | without `main`'s sleep before the join; with `main` sleeping 5 ms so the task's timer is first | 0 of 300 each [controls_mac.log] |

What is needed: a group's owner sleeping AHEAD of one of the group's sleeping tasks in the sleep order, then tearing the group down.

**The silent form is the common one.** When the next round builds a new group at the same address, the walk carries on over a DIFFERENT group with a stale index and nothing crashes: 274 of 300 x86_64 runs of the original probe did that [ring5b_x86_O2.log]. Only when another frame overwrites the storage (the last round) does it crash.

**Which vector, in the original probe:** not `pids` (one address, buffer present, length growing to 20 in failing runs) but the slot list of round 20's group: element size 64 (`TaskSlot`), at `main`'s frame + 8 where `group` lives, holding what `await_exits`'s frame puts there [i1_x86_O2.log, layouts_x86.txt]. An event ring printed at the panic gives the order every time: the walk stands on round 20's group, slot 0; `main`'s timer is first, so the walk hands `main` the turn; `main` joins, drops the group (the list's epoch moves 19 to 20), enters `await_exits` and parks; the walk resumes on the same pointer and `runnable(0)` panics [ring2_fail49.log, ring4_tails.log].

**Why only x86_64 showed it in the lane.** Under Rosetta `pidfd_open` fails (ENOSYS); natively on aarch64 it returns a descriptor [pidfd.log]. With no descriptor, `Command.output` waits for the child by a doubling sleep from 1 ms, the same tick as the probe's own wait, so the cancelled task is a timer sleeper and the hand-off can happen. Forcing the no-descriptor path in a scratch std makes the unmodified probe fail 10 of 300 on native aarch64 Linux and 1 of 300 on macOS [nofd_a64.log, nofd_mac.log]. Code generation is ruled out: `sawc coro --layouts` and the IR of the functions involved are identical across the two architectures [layouts_*.txt, irdiff_x86_a64.txt].

**A candidate, tested in a scratch std** (`std_f`, `edits/tg_fix.spec`): when `record.regroups` (the group list's epoch) changed across `resume_queued` plus `sweep_finished`, restart the pass instead of continuing. `r1`, `r2`, `s1`: 0 of 300 in every cell; the original probe on x86_64: 0 of 300 at `-O2`, 0 of 600 at `-O0`; the no-descriptor aarch64 build: 0 of 300 [fix_matrix_and_base_O0.log, fix_mac.log, fix_orig_x86.log]. It confirms the mechanism. It is NOT yet the fix: see the lead's note below.

**Closed off:** a group inside a spawned task is refused at compile time (`coro.spawn-not-send`), so the owner is always `main`'s chain or a drive point.

**Not determined:** real x86_64 hardware (expected: `pidfd_open` works, so the original probe passes, while `r1`/`s1` fail everywhere); whether `sweep_finished`'s waiter path alone can destroy the walked group; which of the 112 tracked `.saw` files holding both `TaskGroup()` and `sleep(` meet the shape (grep candidates only).

**Lead's note on the fix.** Restarting a pass whenever the group list changed is safe for memory and open for fairness: a task at the head of the list that makes or drops a group on every turn restarts the walk every turn, and a runnable task in a later group may never be reached. The fix needs a design pass over the whole executor first: every place that holds a group pointer or a slot index across a resume (the cooperative walk, `sweep_finished`'s loop, the queue build that already checks the epoch, the pool, the background `Task.spawn` singleton, the thread-context waits that run a thread's tasks), one rule for all of them, and a fairness pin beside the three reductions. That pass is dispatched next.

# SL-1109: the executor walk's use-after-free — design

Design pass p1109d, Nov 14. Every file named below without a directory is under
`.build/scratch/p1109d/`. Host: macOS arm64, `.build/sawc-stage2` (sawc 0.23.0)
at main 4b748c4fe (std and runtime identical to the brief's base). VM:
`sawlang-linux`, the clone's sawc at e5279661 (same std and runtime; its compiler
lacks SL-1107 and SL-900, typecheck only). Nothing tracked was changed.

## 0. Summary

- **The fault is a class of two holders, not one.** Every place in the executor
  that keeps a group, slot, cell or frame across code that can run user code
  was censused (section 3). Two are unguarded:
  1. `sweep_passes` keeps the group it walks (`cur`/`g`) and a slot index (`i`)
     in locals across a turn. Three routes reach the owner while the walk
     stands on the group: the sleep-order hand-off to the owner (the finding's
     `r1`, `r2`, `s1`), the hand-off to a THIRD task whose own join resumes the
     owner (new probe RB), and an unclaimed result's `deinit` that drives
     (new probe RF).
  2. `resume_queued` reads the resumed slot's group (`timer_parked(g, slot)`)
     after `resume_slot` has dropped a finished task's unclaimed result, and that
     drop can run a nested sweep that tears the group down (probe RF). The
     finding's candidate does not cover this one: RF fails 100 of 100 under it.
- **The rule (THE TURN RULE):** across any call that can run user code, the
  executor keeps no group address, slot index, cell or frame pointer in a local
  unless the thing is pinned for the whole call (an active slot of this thread,
  which the teardown refuses to free; a frame on this thread's stack; a handle's
  group, which the borrow rules keep alive), or it is kept where the one unlink
  funnel (`TaskGroup.unregister`) or a stamp check rewrites or invalidates it.
- **The mechanism (chosen, (e) below): walk cursors moved by the unlink.** Each
  open sweep keeps its walk position in a `WalkCursor` on its own stack, linked
  from the thread's `ExecutorRecord.walks`. `TaskGroup.unregister`, under the
  latch it already takes, moves every cursor standing on the group it unlinks to
  that group's successor. After a turn the walk reads its cursor: unmoved, it
  goes on with its locals; moved, it goes on where the cursor stands. Plus a
  one-line change: `resume_slot` answers whether the frame parked on a timer,
  and `resume_queued` reads the group only on that answer (a timer park retires
  nothing, so no user code ran after the outcome section).
- **Why it wins:** it is the only candidate that is memory-safe on every route,
  keeps today's walk order exactly wherever today's order is defined (so it is
  fair by the same property the executor has today), costs one store and one
  load per turn, adds nothing to `TaskGroup` (a word to each thread's record),
  allocates nothing (freestanding-safe), and is small (section 5).
- **Evidence:** the three reductions, RB and RF fail on main 100 of 100 (host)
  and 20 of 20 (aarch64 and x86_64 Linux), and pass under the design 100 of 100
  everywhere, at -O0 and -O2, and under Guard Malloc; the original probe's
  no-descriptor form fails 17/300 (host) and 8 to 15/300 (aarch64) on main and
  0/300 under the design; the fairness probe passes on main and the design and
  fails (starves until the give-up bound) under the candidate; 42 existing
  concurrency programs print their stated output under the design; turns per
  second are unchanged within noise (section 7).
- **Units:** two (section 9). Unit 1: the fairness row and pin, which pass on
  main today. Unit 2: the fix with its two rows and six pins, the 29 `.coro`
  golden re-records, and a gmgate category.
- **Owner questions:** two (section 10): whether the spec states the fairness
  property; and whether a group may be torn down while its finished task's
  result is still being dropped (default yes, which is what the design does).

## 1. Terms

- **Executor record** (`ExecutorRecord`): one per thread that drives tasks. It
  holds the thread's list of registered groups (`groups`, newest first, linked
  through each group's `next`), the sleep queue, and `regroups`, a count of
  unlinks (the list's epoch).
- **Group** (`TaskGroup`): a scope of tasks. A cooperative group registers in
  its thread's list at its first spawn; its teardown (`deinit`) drives its tasks
  to the end, then unlinks it (`unregister`) and frees its slots. Its storage is
  wherever its owner declared it, usually a coroutine frame.
- **Owner:** the frame that declared the group and will drop it. For a group
  that can be dropped while a sweep is open, it is `main` (a suspending `main`
  is itself a task, slot 0 of the entry group), a callee embedded in `main`'s
  frame, a drive point's frame, or a sync helper on some task's stack.
- **Slot:** a run-queue entry of a group (`slots[i]`), with a generation, a cell
  (result and cancel word, which outlives the frame) and a frame.
- **Turn:** one resume of a slot's frame (`resume_slot`), plus the bookkeeping
  after it, including dropping an unclaimed result when the task finished. A
  turn runs user code, and user code can run a **nested sweep** (any join, a
  group's teardown, a drive point, a thread-context wait), which resumes any
  task of this thread that is not active.
- **Sweep / pass / walk:** a sweep (`sweep`) runs passes until its stop
  condition; each pass walks the group list from the head and gives each
  runnable slot a turn (`sweep_passes`).
- **Hand-off:** SL-977.p3's sleep order. When the walk reaches an expired
  sleeper, it gives the turn to the expired sleeper with the earliest deadline
  (`walk_turn` / `cooperative_sleeper`), possibly in another group, and stays
  where it is. `sweep_finished`'s **ahead loop** does the same for sleepers
  ahead of a drive point's own expired sleep.
- **Active:** a slot whose frame is being resumed, on this thread's stack. The
  teardown panics if any of its slots is active (`group_on_this_stack`).

## 3. The census

Method: `std/taskgroup.saw` read whole; `std/task.saw`, `std/thread.saw`'s exit
path and both reactors' arm flags read. A holder is something the code keeps
(in a local, a parameter, or a structure) across a call that can run user code:
a resume, a result's drop, a deinit, a nested sweep, a thread's exit. "Who can
invalidate" lists the events of the brief: owner drop, rebuild at the same
address, `slots` growth, slot reuse, frame release, another thread.

### 3.1 Facts the census rests on (each with evidence)

- **F1. A spawned task never owns a group across a suspension**: refused,
  `coro.spawn-not-send` ("local `g` of type `std.taskgroup.TaskGroup` is held
  across a suspension but is not `Send`") [`logs/refusals.log`,
  `src/refuse_group_in_task.saw`]. So the only suspended frames the walk can
  resume that own a registered group are `main` (and callees embedded in its
  frame). A task may still own a group inside one turn, through a sync helper
  (the fairness probe does exactly this), while it is active.
- **F2. A cooperative group never reaches another thread in safe code**:
  `Thread.spawn { [move g] ... }` is refused three ways, `transfer.no-move`
  twice and `spawn.send` [`logs/refusals.log`]. So only the owner's thread
  unlinks a cooperative group, and the walk's unlatched reads of its own groups
  race with nothing.
- **F3. A task's group outlives the task's own turn while the slot is active**:
  the teardown panics first when one of its slots is active on this thread's
  stack (`TaskGroup.deinit` → `group_on_this_stack`, K200). The gap: the slot
  goes inactive BEFORE `retire` drops an unclaimed result (in `resume_slot`),
  so the result's drop runs with no pin on the group. That is probe RF.
- **F4. The ahead loop always ends the sweep**: it runs only when the drive
  point's own park is an expired timer (`expired_sleep`), and an expired timer
  makes `should_stop` true (`park_wakes`), so `sweep_finished` returns true and
  every caller returns at once. Probe RA reaches the case (an ahead-loop turn
  unlinks a group in 10 of 10 instrumented runs
  [`logs/ra_ahead_loop_instrumented.log`]) and passes on main 100 of 100, under
  Guard Malloc 10 of 10 [`logs/host_matrix.log`, `logs/guard_malloc.log`].
- **F5. Reactor registrations are one-shot** (`EV_ADD|EV_ONESHOT` on macOS,
  `EPOLLONESHOT` on Linux; `runtime/host_*/reactor.saw`), and a descriptor park
  that ends without its event unregisters before its task can end (`io_wait`).
- **F6. A handle borrows its group** (SL-683, `loan.handle-outlives-group`) and
  the teardown panics while a `group.spawn` handle is outstanding
  (`check_no_outstanding`).

## 4. The rule

**THE TURN RULE.** A turn may run any code, and that code may resume any frame
of this thread that is not active, so it may tear down any group no active
frame or stack frame of this thread belongs to. Therefore, across any call that
can run user code (a resume; a result's drop; any join, teardown, drive or
thread-context wait), the executor keeps no group address, slot index, cell
pointer or frame pointer in a local, unless:

1. **it is pinned for the whole call**: the slot is `active` on this thread
   (the teardown refuses, K200), the thing lives in a frame on this thread's
   stack, or it is the group of a handle the caller holds (the borrow rules and
   the outstanding check); or
2. **it is kept where invalidation reaches it**: in a walk cursor, which the
   unlink funnel (`TaskGroup.unregister` → `move_walks_past`) moves; or in a
   sleep-queue entry, read only after the `regroups`/`seen` rebuild check and
   through `SleepEntry.live`.

A reader checks a new line against it by asking: does this read follow a call
that can run user code, and if so, which of (1) or (2) covers the name?

## 5. The candidates

## 6. The chosen design

`design.diff` is the whole change (`diff -u std/taskgroup.saw
.build/scratch/p1109d/std/taskgroup.saw`). In prose:

1. `ExecutorRecord` gains `walks: Int` (after `regroups`), the address of the
   innermost open sweep's `WalkCursor`, 0 with none; `claim_record` builds it 0.
2. New `struct WalkCursor { group: Int, slot: Int, outer: Int }` and
   `static WALK_ENTER: Int = -2`, beside `sweep_passes`.
3. `sweep` builds a `WalkCursor(group: 0, slot: WALK_ENTER, outer:
   record[0].walks)` in its own frame, stores its address in `record[0].walks`,
   passes it to `sweep_passes`, and restores `record[0].walks = cursor.outer`
   after. (A panic aborts, so no unwinding path needs the restore.)
4. `sweep_passes` takes `cursor: UnsafePointer<WalkCursor>`. At each pass it
   sets `cursor[0].group` to the list head and `slot` to `WALK_ENTER`, and loops
   while `cursor[0].group != 0`: `g` from the cursor, `i` from `next_live(0)`
   (cooperative) or -1 (pool), `moved = false`, and the slot loop runs
   `while i >= 0 && not moved`. Before `resume_queued` it stores
   `cursor[0].slot = i`. After `sweep_finished`: if `cursor[0].slot != i` the
   unlink moved it, so `moved = true` and `g` is never read again; else if the
   turn was `(g, i)` itself, `i = g[0].next_live(i + 1)`; else (a hand-off) the
   walk stays. After the slot loop, if not moved, the cursor steps to `g[0].next`
   with slot `WALK_ENTER`.
5. `TaskGroup.unregister` computes `me` after `self.registered = false` (the
   borrow checker refuses it before: `loan.write-while-shared`, seen while
   building), unlinks, bumps `regroups`, then calls
   `move_walks_past(record, me, self.next)`, all under the latch.
6. New `move_walks_past(record, me, after_me)`: for every cursor on
   `record[0].walks`'s chain whose `group == me`, set `group = after_me`,
   `slot = WALK_ENTER`. Its comment is the funnel (THE WALK RULE, ENTRY POINTS:
   `TaskGroup.unregister`).
7. `resume_slot` returns `Bool`: true exactly when the frame reported `Pending`
   with a timer park (set beside `take_sleep_order`), false on its early return
   and otherwise. `resume_queued` calls `timer_parked(g, slot)` and notes the
   entry only when it answered true. Sound because a `Pending` outcome retires
   nothing (`retired` stays `retired_none()`), so between the outcome section's
   unlock and the read only `retire(none)` and `end_turn` run.

The iterations (section 7.5) chose two details: the walk keeps `g`/`i` in
locals between turns and touches the cursor only around a turn (v1 read the
cursor at every step); and `resume_slot` answers a `Bool` rather than the
`SleepEntry?` it builds under the latch (v1, v2), which cost about 5% on the
sleeper benchmark.

## 10. Questions for the project owner

1. **Does the language state the fairness property?** Today the spec says the
   scheduler wakes expired sleepers earliest deadline first and that the op
   budget makes every task cede; it says nothing about whether a pass reaches
   every group. The design keeps today's behaviour, which does.
   - (a) **default**: state it in the spec's scheduler bullet (text in unit 1)
     and hold it as conformance row K223;
   - (b) leave it unstated: the probe stays as a regression pin of the
     implementation, with no ledger row.
2. **May a group be torn down while its finished task's unclaimed result is
   still being dropped?** Probe RF: the drop's `deinit` joins a task of its own,
   `main` runs meanwhile and drops the group. Today that is a use-after-free.
   - (a) **default**: yes, the teardown proceeds. The task's root has returned,
     its slot was released and its cell unlinked before the drop, so the drop
     needs nothing of the group. This is what the design does
     (`pins/executor_walk_result_deinit_resumes_the_owner.saw` prints
     `waited 1`).
   - (b) no: the teardown panics, as K200's teardown does when one of its tasks
     is further up the stack, treating the drop as part of the task. That needs
     the slot to stay marked until `retire` finishes (a third latch section in
     `resume_slot`) and the pin to become a `panics` probe.

Implementation-only decisions made here (not questions): keeping the hand-off;
the cursor over (a)-(d); a `Bool` from `resume_slot`; the cursor on the sweep's
stack rather than in the record.
