## Description

Found while writing design 270's conformance rows (SL-212, unit C of SL-209).
The epic's acceptance for unit C is "sync and suspending versions have
equivalent ownership behavior"; this is the one row of that where they diverge.

## Symptom

A NON-ESCAPING closure that implicitly captures a `Copy`-tier local pays TWO
duplications in a driven body and ONE in its sync twin. Measured with a printing
`copy()` hook, which is called at exactly the transfer sites no source construct
names (design 219):

```saw
struct Counted { n: Int }
extension Counted: Copy {
    func copy(&self) -> Counted { print("copy {}", self.n)  Counted(n: self.n) }
}

func run_int(body: () sync -> Int) -> Int { body() }

func cap_sync(seed: Counted) -> Int {
    let held = seed
    run_int({ held.n })
}

func cap_driven(seed: Counted) -> Int {
    let held = seed
    __saw_suspend()
    run_int({ held.n })
}

func main() {
    print("-- sync")
    print("= {}", cap_sync(Counted(n: 1)))
    print("-- driven")
    print("= {}", __saw_drive(cap_driven(Counted(n: 1))))
}
```

```
-- sync
copy 1
= 1
-- driven
copy 1
copy 1          <-- the extra one
= 1
```

Counts BALANCE — the closure environment releases its reference at frame death
— so this is not a leak and not a double free. It is an extra implicit
duplication a driven body performs and its sync twin does not, which at a
hand-written hook is an unbounded cost the author never wrote, and at an `Arc`
payload is a refcount that reads one higher inside a driven body than outside
one.

## Mechanism (obligation 4)

`_materialize_closure_captures` (`sawc/coro_transform.py:7790-7891`) rewrites
every implicit capture of a frame-resident local into an EXPLICIT
`[move __capN_<name>]` capture, and materializes `__capN_<name>` with an
`owning_read` frame read — a fresh reference, per its own comment: "The
materialized local must be an INDEPENDENT OWNER — the `move` capture below
transfers it into the env, and the env releases it once at frame death."

That is the ESCAPING closure's discipline, applied unconditionally. The sync
lowering of a NON-escaping closure does not mint a reference at all: the
environment is stack-resident and the capture reads the local where it sits.
So the transform pays the escaping cost for a closure that does not escape.

## Sibling sweep — every neighbouring shape probed, compile-and-run

| Shape | sync | driven | Verdict |
|---|---|---|---|
| non-escaping closure, `Copy`-tier capture | 1 copy | **2 copies** | **the bug** |
| non-escaping closure, capture read TWICE in the body | 1 copy | **2 copies** | same bug, count unchanged by uses |
| ESCAPING closure (`let f = { held.n }`), `Copy` tier | 2 copies | 2 copies | parity — the sync env already retains |
| plain capture of an `ExplicitCopy` local | refused | refused | parity, identical diagnostic and position |
| `[move o]` capture of a `NoCopy` local | 1 drop | 1 drop | parity |
| trivial tier | no hook | no hook | unobservable by construction |

So the mechanism reaches exactly one cell: the escaping/non-escaping
distinction is the thing the materialization does not make, and every other
axis (tier, use count, capture mode) is already right.

## Fix shape (not done here — it changes behaviour)

The materialization should ask whether the closure ESCAPES, as the sync
lowering does, and for a non-escaping one read the frame field without minting
a reference (the field stays the frame's; the closure runs and returns inside
the frame's own lifetime, so nothing can outlive it). The `owning_read` arm
stays for the escaping case. `_frame_read_policy` is already the funnel the
branch asks; the missing input is the escape answer, which `noescape.py` /
the non-escaping parameter slot already carries at the call site.

Design 218 stage 1's `Slot` migration is the other end of this: a `Slot`-encoded
field's `value()`/`take()` is an ordinary method call the post-transform
re-check judges by the ordinary rules, so the capture materialization over a
migrated field would ask the language rather than answer for itself.

## Why unit C files it rather than fixing it

Design 270 is behaviour-preserving by construction — it records and verifies
decisions, it does not change any. This one changes an observable (a user's
`copy()` hook stops running twice), so it is a filed bug with a cited
conformance pin, per the epic's conduct rule. The pin is
`examples/conformance/V96_driven_capture_duplicates_once.saw`, XFAIL, asserting
the intended parity so the XPASS flip validates the fix.

```saw
func sync_cap(d: Dup) -> Int   { run_int({ [copy d] in d.n }) }
func driven_cap(d: Dup) -> Int { __saw_suspend()  run_int({ [copy d] in d.n }) }
```

```
-- sync
copy 70 -> 71
body saw 71
-- driven
copy 70 -> 71
copy 71 -> 72
body saw 72          <-- a DIFFERENT ANSWER from the sync twin
```

The materialization's `.copy()` (the `policy == 'nocopy' and
_frame_slot_has_explicit_copy` arm, `coro_transform.py:7852-7860`) runs, and then
the capture spec's OWN `[copy]` runs on the materialized local — two
duplications where the author wrote one. At the silently-copyable tier that is
only an extra retain (the original report); at the ceremony tier the user's hook
runs twice, so a non-idempotent `copy()` makes the driven body compute a value
its sync twin does not.

So the mechanism is not "an extra reference" but "the materialization
duplicates, and then the capture mode duplicates again" — the materialized local
should BE the capture (it already carries the transfer), not a fresh source for
the capture spec to duplicate a second time. That widens the fix note above: the
spec the materialization appends is `mode="move"`, which is right for the local
it just made; what is wrong is that for a `[copy]` capture the ORIGINAL mode's
duplication is performed too.

(The leak visible beside this — `drop 72` never runs — is SL-268, a separate
sync-side mechanism.)

## Fixed here — the WRITTEN `[copy x]` capture (this issue's comment c1)

The materialization already produces an independent owner, and the author's own
`[copy x]` spec was left riding that local and duplicated it a SECOND time. The
spec the materialization appends for an IMPLICIT capture is `mode="move"`, which
is right for a local it just minted; c1's finding is that for an EXPLICIT
`[copy]` the ORIGINAL mode's duplication was performed too. So the fix is c1's
own sentence — the materialized local IS the capture — spelled as: when the
author wrote `copy` over a frame-resident local, rewrite that spec to `move`
(both `capture_specs` and `capture_modes`, as `_rename_in_closure` already does
for the pair).

Measured, sync and driven now byte-identical:

    -- sync                      -- driven
    copy 70 -> 71                copy 70 -> 71
    drop 71                      drop 71
    drop 70                      drop 70
    body saw 71                  body saw 71

The `drop 71` on both sides is SL-268 closing in the same landing — this issue's
c1 noted `drop 72` never running and attributed it there correctly.

Pinned by conformance row **V106**, at the ceremony tier (where the divergence is
a different COMPUTED VALUE) and the silent tier (where it is an extra retain).

## NOT fixed here — the IMPLICIT capture, which is what V96 pins

`{ held.n }` over a frame-resident `Copy`-tier local still pays ONE duplication
in a driven body and NONE in its sync twin. Counts balance, so it is a
duplication too many rather than a leak.

WHY IT DID NOT MOVE, stated as the blocker rather than as a preference. The
issue's own fix note says to ask whether the closure ESCAPES and, for a
non-escaping one, read the frame field without minting a reference. The escape
answer IS available at the materialization — verified by tracing
`cexpr.escapes` there, which reads `False` for the non-escaping row and `True`
for V96's escaping control, correctly. The blocker is the OTHER half: what to
materialize instead.

A non-retaining read needs a local that nothing releases, and every spelling
available today releases it somewhere:

* `mode="move"` into a NON-escaping env takes DF-218h's DEFERRED arm — the body
  TAKES the value and drops it at the body's end — so a non-retaining read plus
  `move` double-frees against the frame field.
* `mode="plain"` leaves the materialized `let` cleanup-registered like any
  owning local, which is the same double free one statement earlier, and is
  exactly what the `move` was introduced to prevent ("a persistent
  function-local holding an owning value would be dropped on EVERY resume
  re-entry").
* `move_read` + `__saw_forget` (the frame hands its own reference over) is
  correct only if the frame never reads the field again, which is not knowable
  at the materialization.
* codegen's `borrowed_variables` is the "this name is borrowed, do not clean it
  up" marker, but it is CLOSURE-BODY scoped (saved/reset around closure
  generation) and the `let` cleanup path does not consult it.

So closing this needs the transform to be able to materialize a NON-OWNING
local — a borrow of a frame field that codegen will not cleanup-register — or,
architecturally cleaner, to skip materialization for a non-escaping closure
entirely and let the body read the frame through a captured receiver, which is
what the sync lowering does and what design 216 permits for exactly the
non-escaping case. Either is a brief-sized change to the capture seam with
corpus-wide reach (every driven `Mutex.lock` body, place window, `with_ref`
body and `Vector.each`), not a sub-item of unit D. Design 218 stage 1's `Slot`
migration is the standing plan the issue already names.

V96 keeps its XFAIL and its citation; V106 records in its own header that the
implicit half remains pinned there, so the two rows do not read as covering the
same thing.
