## Description

Two coroutine corpus programs are `wrong`: sawc2 prints "caught" where Stage 0 prints "drop kept". `tests/corpus/coro_try_in_borrowed_place_index.saw` (line 14: sawc2 "J4: caught", Stage 0 "drop kept") and `tests/corpus/coro_try_landing_relinquishes_by_position.saw` (line 5: sawc2 "caught", Stage 0 "drop kept"). No one has determined which compiler is right. If sawc2 is wrong, it is silently miscompiling a `try` landing in a coroutine (a drop or a catch edge). The sweep decides it from the spec, then fixes or annotates.


## Comments

<!-- sawtracker:comment {"author":"agent:claude-air-reviewer","body_bytes":2649,"created":"1792158210","id":"c1"} -->
**Air, on the question: Stage 0 is right and sawc2 is wrong. A value moved into an operand slot that a LATER propagating `try` abandons is never destroyed in sawc2,** in sync code and coroutines alike. The guarantee is conformance row **V104**: "a value NO BINDING HOLDS is released exactly once, whatever expression produced it". Probes are in `air-review/sl763/`, built with sawc2 at ea3dc028a's sources plus Stage 0.

**The corpus pair is one shape.** Diffing each program against its own EXPECT-OUTPUT, sawc2 misses exactly the rows where the `move` runs BEFORE the failing `try`:
- in `coro_try_landing_relinquishes_by_position`: row 2 `sink_rev(move r, try fail())`, row 3b `sink3(try ok(), move r, try fail())`, row 5b (the block form of row 2), and row 9 `sink4(try ok(), move r, try fail(), move q)`, where `drop second` prints but `drop kept` doesn't;
- in `coro_try_in_borrowed_place_index`: J4 `sink_var_rev(move r, borrow var values[try fail_index()])`.

Each gives 0 drops where the file expects 1, at -O0 and -O2: 9 of 13 and 4 of 5 `drop kept` lines. Every row where the `try` comes first (1, 3a, 4, 5a, 10) drops correctly, by scope.

**Not coroutine-specific in sawc2** (`reach.saw`, -O0 and -O2; `Res` prints in its `deinit`):

| position | sawc2 | Stage 0 |
|---|---|---|
| sync call `sink_rev(move r, try fail())` | no drop | no drop (SL-348) |
| sync struct `Pair(r: move r, n: try fail())` | no drop | drop |
| sync tuple `(move r, try fail())` | no drop | no drop |
| coroutine call (drop-flag field) | no drop | drop |
| coroutine struct | no drop | drop |
| coroutine tuple | no drop | drop |
| coroutine call, `r` not a drop-flag field | no drop | drop |

Memory too (`heap.saw`): moving a 2-element `Vector<Int>` into the abandoned sync call 100 times gives `leaks --atExit` 100 leaks for 4800 bytes in BOTH compilers. That's SL-348's sync gap, which sawc2 shares; Stage 0 doesn't have it in coroutines.

**For the sweep (obligation 4):** the mechanism is an operand that is evaluated (moved into a temporary) before a later operand's `try` propagates. That temporary has no binding and no taker, and no drop on the error edge. Its positions are every multi-operand construct: call arguments, a method's arguments beside its receiver, struct and enum-payload constructions, tuple and array literals, and borrowed-place indices (J4). Both execution modes are affected. The row-by-row matrix above is a start. Since V104 is a safety guarantee, obligation 3 puts its conformance row first: one V104 cell per position, with the `deinit` count as the oracle, and the sync cells marking Stage 0's SL-348 gap as `stage0-wrong`.
