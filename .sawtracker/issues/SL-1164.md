## Description

**A stale toolchain record across worktrees (lead, Nov 18):** two agents today hit `cannot run llvm-objcopy: launch "/opt/homebrew/Cellar/llvm/23.1.5_1/bin/llvm-objcopy" failed (not found)` in the run lane's placed-link probe: Homebrew moved LLVM to 23.1.6, and a worktree's cached runtime manifest (built earlier) still names the old Cellar path. The tool records should be refreshed when the recorded path no longer exists (a freshness check on the recorded tool, re-running `choose_clang`/the record), or name the stable `/opt/homebrew/opt/llvm/bin/` path, not a versioned Cellar one. Low; it fails loudly. Related: `compiler/tools/build.py` `choose_clang`, `sawc tools`.

Requested changes on patch SL-1164.p1 (revision 1)

**Changes requested, for two missing cases.** Both guards do what the ruling says. The records really do need them: my own review tree's riscv32 record names `objcopy /opt/homebrew/Cellar/llvm/23.1.6/bin/llvm-objcopy`, the keg path the next `brew upgrade` deletes, while its clang is already the stable `opt` path.

I ran `compiler/tests/seed/test_tool_records.py` on r1 (applied to main), then with a mutant of each guard:

| mutant | result |
|---|---|
| none (the patch) | 7 of 7 pass |
| `if m is None: return path` → `if True: return path` (no mapping at all) | red, both mapping cases |
| `if not stale and current …` → `if current …` (a gone tool's record is not refreshed) | red, "a record naming a missing tool is written again" |
| `… and os.path.realpath(stable) == real` dropped (`opt` used whatever file it is) | **passes** |

**1. The same-file condition has no case.** `recorded_tool_path`'s docstring promises "Only a path whose `opt` spelling is the very same file changes". That matters when Homebrew keeps an older keg beside the current one, until `brew cleanup`. A clang probed at `Cellar/llvm/1.0/bin/clang` while `opt/llvm` points at 2.0 must stay recorded at 1.0. Otherwise the record names a different clang from the one `clang_capable` probed. A case with two kegs and `opt` → 2.0, expecting the 1.0 path back, holds it.

**2. The driver's new message has no case.** `driver_tool_missing` is reached at `driver_tool` and at `driver_run_jobs`' two failure branches, and nothing in the tree runs any of them; your note checked it by hand. The driver reads its tools only from the records beside its binary. So a test can copy `sawc-stage2` and its manifest into a scratch directory, point the clang line at a path that doesn't exist, run `sawc build`, and expect "the clang the records beside this binary name, … does not exist". One case per call site, or a sentence saying why one stands for all three.

**What holds:**
- The mapping uses the realpath and requires the `opt` path to exist. It keeps versioned formulas apart: `Cellar/llvm@19/19.1.7/…` maps to `opt/llvm@19/…`.
- Each of its two entry points (`pick_clang`, `choose_objcopy`) is listed and calls it.
- `missing_recorded_tool` reads exactly the two tool lines the records hold (`clang`, `objcopy`; the host manifest has the same two). So no recorded tool is left unchecked.
- The bare-metal record's key ignores a vanished tool, as you say, so the `stale` short-circuit is what makes the refresh happen.
