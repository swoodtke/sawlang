**On riscv32, a freestanding object can reference 64-bit shift helpers that the spec's freestanding contract doesn't name.** Found by SL-944's survey (`.build/scratch/p944/q1_census.txt`, `q5_fs_nm.txt`).

**What it found:**
- `float_census.saw` at `-Oz` references `__ashldi3` and `__lshrdi3`; at `-Os`/`-Oz` it also references `__udivdi3` and `__umoddi3`.
- The SL-944 Saw prototypes at `-Oz` reference `__ashrdi3` and `__lshrdi3`.
- These are libgcc/compiler-rt integer helpers, which LLVM emits for 64-bit shifts and divisions on a 32-bit target when it optimises for size.

**The contract:** LANGUAGE_SPEC.md's Profiles section lists the soft-float routines exactly, and the runner's `SOFT_FLOAT_ROUTINES` holds them. The spec names `__udivdi3`/`__umoddi3` only for Float printing. No list names the shift helpers, so an environment built to the spec can fail to link a size-optimised riscv32 object.

**What the fix owes:**
- A census of every integer helper reachable on riscv32 at every optimisation level. That covers `UInt64`/`Int64` shifts, multiplications, divisions and remainders, and `clz`/`ctz` and `popcount` if std uses them.
- A ruling: either the spec lists them as routines the environment supplies (and the freestanding suite's HAL vendors them, as SL-929 did for soft-float), or sawc avoids them.
- The runner's symbol check covering the list, with a case at `-Oz`.

**Air, a census for SL-947: two helpers the issue doesn't list, reachable at every optimisation level.** Probe: `.build/scratch/air-review/sl947/i64_ops.saw` on the Air. It has one `@export` function per 64-bit integer operation (`Int64`/`UInt64` `*`, `&*`, `/`, `%`, `<<`, `>>`, `+`, `-`, negate), built by sawc on 917b983a0+SL-945 as `--freestanding --target riscv32-unknown-none-elf --target-features +m,+a,+c -c` (the runner's flags). `llvm-nm -u`:

| level | undefined |
|---|---|
| -O0, -O1, -O2, -Os | `__divdi3` `__moddi3` `__udivdi3` `__umoddi3` (+ `__saw_rt_panic`, `memcpy`) |
| -Oz | the same, plus `__ashldi3` `__ashrdi3` `__lshrdi3` |

- **Signed 64-bit `/` and `%` (`__divdi3`, `__moddi3`) are reached at every level,** not only under size optimisation. The issue's list doesn't name them, and neither does the runner's `HAL_LIBCALLS` (only `__udivdi3`, `__umoddi3`). So a freestanding riscv32 case that divides two `Int64`s fails the runner's stray-symbol check today, at the suite's `-O1` too.
- **The shift helpers appear only at `-Oz`,** matching the survey.
- **Multiplication needs no helper.** Overflow-checked `*` on `Int64` and `UInt64`, and wrapping `&*`, compile inline: no `__muldi3` and no `__mulodi4` at any level. `__mulodi4` is the one to watch, since libgcc doesn't ship it. This holds with `+m`; a base-rv32i build would differ, and the runner never uses one.

For the fix's list and its `-Oz` case: the set is `__divdi3 __moddi3 __udivdi3 __umoddi3 __ashldi3 __ashrdi3 __lshrdi3`. Whatever the ruling, the runner's case should divide signed values, not just shift.
