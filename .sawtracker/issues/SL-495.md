## Description

**Found by:** batch B2b (tcb2b), SL-490's sweep of the `lend` form. **Area:** borrowck, `loan_forward` / `loan_collect` over an accessor's epilogue.

**The defect:** an accessor's epilogue may touch its root while a window its prologue forwarded with `lend` is still open. The loan analysis marks the carried windows open at the epilogue's entry (`loan_forward`), but makes no loan for them there: `loan_collect` creates a window's loan only at its `window_open`, which sits in the prologue's function. So nothing conflicts with the carried window in the epilogue.

```saw
struct P { n: Int }
struct Grid { rows: Vector<P> }
extension Grid: NoCopy {}
extension Grid {
    func cell(&var self, i: Int) borrows -> &var P {
        lend self.rows[i]
        try! self.rows.push(P(n: 2))    // accepted: the window on `self.rows` is still open here
    }
}
func main() {
    var g = Grid(rows: Vector<P>())
    try! g.rows.push(P(n: 1))
    borrow var g.cell(0).n += 1
}
```

`.build/sawc2 borrowck --check` accepts it, with and without `--std-root std`. In the dump, the epilogue's `window_close w0` comes after the push, and the epilogue lists no window loan.

**Why it matters:** the inner accessor (`Vector.[]` here) is paused at its own `lend` until that close, holding its `&var` receiver. A user accessor whose epilogue uses a pointer it took in its prologue would see the storage reallocated under it. README "Liveness" says "An accessor's epilogue starts with the windows its prologue left open across the `lend`". The open set does that, but the loans don't.

**Mechanism to fix:** give each carried window a loan in the epilogue, on its receiver's path as the epilogue's locals name it. The receiver is restored from the state record (`_2 = move (*_1).0`), so the path has to be mapped from the prologue's locals to the epilogue's.

**Lead note before this is scheduled: two halves, and the first may be placement rather than loans.**

1. **A bare `lend self.rows[i]` statement.** §2.7 says the forwarded borrow "opens for as long as the outer lend is open… and closes in reverse order". The outer lend's window closes when the consumer finishes, which is the start of the epilogue. So the inner window should close as the epilogue begins, as the `lend` statement completes. In the repro, the epilogue's `window_close w0` comes after the `push`, so the close is placed too late, and `push` would then be legal. Check which reading MIR intends. If the close belongs at the end of the `lend` statement, the fix is where the close is placed, and this repro is accepted for the right reason.
2. **A `lend` inside a `borrow` block,** such as Map's `find`: `borrow var slot = self.slots[b] { match slot { case Occupied(_, borrow var v) -> { lend v } } … }`. Here the block's own window legitimately stays open in the epilogue until the block ends. Code after the `lend` in that block must conflict with it, which is where a carried window needs a loan in the epilogue. That is the mechanism described above.

Pin both shapes. The fix may need both halves.
