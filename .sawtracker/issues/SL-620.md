**Stage 0 and sawc2 disagree on a prefix operator's operand of `as`, so the same compiler source means different things to the compiler that builds Stage 1 and the one that builds Stage 2.** I found it while reviewing SL-600 (Air).

**The mechanism.** GRAMMAR.md's precedence table puts the prefix tier (`-` `not` `~` …, tier 2) above `as` (tier 3), so `-x as T` is `(-x) as T`. The frozen parser casts first and builds `UnaryOp(-, CastExpr(x as T))`. The sawc2 reading of SL-600 shows the tree difference at `sawc/std/file.saw:209` (`self.fd = -1 as Int32`), the only such node across the 172 files both parsers read: the compiler's source plus `sawc/std`.

**Evidence.** Probes are in `.build/scratch/air-review/sl600/` on the Air: Stage 0 is `sawc/sawc.py`, and sawc2 is Stage 2 built at f8338a155 with `--std-root std`.

| source | Stage 0 | sawc2 |
|---|---|---|
| `~x as UInt16` with `x: UInt8 = 0` (`prefix_cast.saw`) | 65535 | 255 |
| `-x as Int` with `x: Int32 = Int32.min` (`neg_cast_widen.saw`) | 2147483648 | panic: integer overflow |
| `let m = -128 as Int8` (`neg_cast.saw`) | refused: "`128` is not representable as `Int8`" | -128 |
| `not t as Bool` | false | false (no difference for Bool) |

**Why it matters.** Stage 0 compiles the compiler's source to build Stage 1, and sawc2 compiles the same source to build Stage 2. A `~mask as UInt32` or `-delta as Int` written in `compiler/` would compute one value in Stage 1 and another in Stage 2. The fixpoint compares outputs, not intermediate values, so it can only catch this when the difference reaches emitted code. Today no such shape exists in `compiler/`; the one hit in `sawc/std` is a literal, where both readings give the same value.

**Mitigation:** `sawc/` is frozen, so the fix goes in the ledger and the checker.
1. Add an SL:hazards entry: "a prefix operator's operand of `as`: Stage 0 casts first, GRAMMAR.md applies the prefix first".
2. Add a subset rule refusing an unparenthesized prefix expression as the operand of `as` (or a cast inside a prefix operand) in the compiler's source. The fix-it is to write `(-x) as T`, the GRAMMAR.md meaning, which both parsers read alike. Pin it with a fixture per prefix operator that has a numeric reading (`-` and `~`; `not` agrees for `Bool`).
3. The std profile doesn't need the rule after SL-600, since only sawc2 reads `std/`.

Obligation 4 sweep: the probes cover the three prefix operators with a value-level reading. `*` applies only to raw pointers in both parsers, and `&`, `&var`, `move` and `try` don't produce a castable integer in practice. A census of `compiler/` for the shape found none (the SL-600 fidelity comparison).

A constant face of the same divergence (Air, at the user's question): `let a: UInt16 = ~(0 as UInt8) as UInt16`. The spec's Appendix B and GRAMMAR.md (prefix above `as`) give `(~0u8) as UInt16` = **255**, which is what sawc2 prints, as Rust and Swift would. Stage 0 reads `~((0 as UInt8) as UInt16)` and, folding in its signed domain, refuses it: 'constant expression -1 does not fit in `UInt16`'. With a runtime operand (`~x as UInt16`) Stage 0 gives 65535 silently, as in the table above. Probe: `.build/scratch/air-review/sl600/user_cast.saw` (all three parenthesizations; sawc2 prints 255, 255, 65535).
