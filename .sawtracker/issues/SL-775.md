## Description

**`print` writes its line and its newline separately, so output from two threads interleaves** (found by SL-765 T3b's agent: K82 printed `storedworked` followed by two newlines; UNVERIFIED beyond that run).

With `Thread.spawn` landing (SL-765 T3b), two OS threads can `print` at once. sawc2's `print` lowering (`compiler/llvm/src/prims.saw`) appears to emit the text and the `\n` as two `__saw_rt_write` calls, so another thread's write can land between them. A line printed by one call should appear whole: never split by another thread's output, and never split from its own newline.

**Fix:**
- emit ONE `__saw_rt_write` per `print` call, with the newline appended in the stack scratch or buffer that formatting already uses;
- check the format-argument path (`print("{}", x)`, design 137's stack scratch) and the interpolation path both end in a single write;
- confirm Stage 0's behaviour for parity.

**Coordinate:** SL-768 part (c) makes `print` PANIC on a failed write (the user's ruling) and touches the same lowering. Doing both together is natural.

**Pin:** two threads each printing N distinct lines; every output line is whole (no mixed lines, no lone newlines). Run it many times.

**Air: the guarantee needs stating, because one `write` per line is atomic only up to `PIPE_BUF`.**

POSIX makes a `write(2)` to a pipe atomic only up to `PIPE_BUF` bytes, which is 512 on macOS and 4096 on Linux. A longer write to a pipe can interleave with another thread's. Terminals and regular files give no stronger promise. The spec says nothing on `print` atomicity today. So the unit should pick one and write it in:
- **(a) One write per `print`, best effort:** a line is whole whenever the OS keeps a single write whole, which a pipe does up to `PIPE_BUF`. That's the fix as filed.
- **(b) Never split:** `__saw_rt_write` takes a process-wide lock around the write, as SL-737's env lock does. A line of any length is then whole against other `print`s, though not against a raw `write` from C.

The pin as filed ("every output line is whole", run many times) passes under (a) only while its lines stay under 512 bytes on macOS, since the run lane captures output through a pipe. A pin under (b) should add a line longer than 4096 bytes. SL-768 (c), `print`'s panic on a failed write, touches the same seam, so the lock (if (b)) and the status check land together.

**The user ruled (Oct 16): a `print` line is NEVER split by another `print`, at any length.**
- **Mechanism:** the runtime writes all of a line's parts and its newline under one process-wide output lock. There is no allocation and no length limit; it doesn't guard against raw C writes.
- **The spec states the guarantee.**
- **Folded into SL-768 part (c),** which changes the same write seam to report a status (the user's earlier ruling: `print` panics on a failed write). One ABI cut. The `print_call` lowering in `compiler/llvm/src/calls.saw` hands all parts to one seam call (or the locked sequence).
- **Pin:** a two-thread stress test with lines longer than 4096 bytes (the Air's c1), registered on SL-765 and done in that unit once `Thread.spawn` is on main.

This issue closes with SL-768 (c).
