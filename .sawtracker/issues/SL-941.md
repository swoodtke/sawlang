## Description

**A reached `==` on a `@synthesize` Equatable whose member isn't Equatable is refused as `mono.not-yet`, not as a clean user error at the comparison site.**

The spec (Equality, "Optional and fixed-array members") says: "A genuinely non-Equatable member remains a clean error at the comparison site." So the error is LAZY. Deriving Equatable over a `Vector` field is legal until `==` is reached. Five existing pins rely on that: `lent_optional_*` and `borrows.optional-place-read*`, each comparing a `Bag?` only against `None`.

**Today:** reaching the comparison gives:

```
mono.not-yet … a call of Equatable.equals(other: &Self) on derive_eq_bad.Opaque, which no conformance of it meets, is not in the backend slice yet
```

That reads as a compiler gap, not a user error, and it isn't placed at the comparison. Repro: `.build/scratch/p833/u/derive_eq_bad.saw`. The corpus row `equatable_field_not_equatable_error` shows it too.

**Fix direction:** a user-facing refusal at the comparison site that names the member and its type ("`Holder`'s field `x` of type `Opaque` does not conform to `Equatable`"). It covers the Equatable, Comparable and Hashable faces alike (obligation 4: list every derived requirement mono can reach unmet). Where it is raised, typecheck at the reached use or mono with a user code, is for the brief.

**Not this:** an eager check at the derivation. That contradicts the spec's lazy rule. SL-833 unit 4 tried it and broke the five pins.
