## Description

**`drop.must-consume` refuses moving a `Thread` handle into storage reached through an `UnsafePointer`, but accepts the same move through `&var`.** (side finding from SL-578 A17a, agent p578pool)

In `std/taskgroup.saw`, `g[0].crew.push(move worker)`, with `g: UnsafePointer<TaskGroup>`, is refused as an unconsumed handle. The same push through a `&var TaskGroup` parameter is accepted, so `start_crew` takes `&var TaskGroup`.

The must-consume funnel (A7d's minting funnel and its consumers) apparently doesn't count a move into a place rooted at a raw-pointer subscript as consuming. That cause is UNVERIFIED. Per obligation 4, sweep the other place roots too (a `Box` payload, an `UnsafeRef`, a field through an `UnsafeMutablePointer`).

**Acceptance:** a minimal repro (a handle moved into a field through `UnsafePointer`) builds, and a moved-away handle is still never double-fated.

**Air: SL-779's cause is confirmed, and the same mechanism errs the other way too. A handle pushed into a plain local `Vector` or `Map` compiles, then panics at run time.** The probes are in `air-review/sl779/` on the Air, built with sawc2 from main 20b3eca38.

**The mechanism.** `owner_declares_deinit` (`compiler/drops/src/elaborate.saw`) decides by the type of the place's ROOT local, with references stripped. It never looks at the storage the handle moves into. In the MIR:
- **p2:** the pointer form's receiver is `ref(exclusive, _2[_7].workers)` with `_2: UnsafePointer<Pool>`. Nothing strips `UnsafePointer`, and it declares no deinit, so the move is refused even though `Pool` declares one.
- **p5:** a plain `var v = Vector<Thread<Void>>()` has the root `_1: Vector<…>`. `Vector` declares a hand-written deinit (`std/vector.saw`), so `v.push(move t)` discharges the obligation. That deinit only drops its elements.

**p5 and p10 need a ruling.** The spec (No implicit fates) asks only that "the owning type DECLARE a hand-written `deinit`".
- Read against the root, `Vector` and `Map` qualify. By the letter p5 compiles, and the run-time panic is the backstop.
- The cost: the most natural way to collect handles, a local vector you forget to join, gets no compile-time error, and catching that is the obligation's purpose.
- It also covers a `&var Vector<Thread<…>>` parameter. A fix that only strips `UnsafePointer` the way references are stripped would let `UnsafePointer<Vector<Thread<Void>>>` discharge as well.
- sawc2 isn't consistently root-based either. p6's root is a `Vector<Bag>`, yet it's refused, because the accessor window re-roots the place at a `&var Bag` local.

**A rule that settles both directions:**
1. Walk the place from its root outward, stripping references and raw pointers.
2. A type on that path counts only when it declares a deinit AND names the handle's type in its own fields, rather than holding it as a type parameter.
   - `Pool` names `Thread<Void>`, so it counts.
   - `Vector<T>`, `Map<K, V>` and `Box<T>` hold a `T`, so their deinits can only drop it, and they don't count.

Under that rule p2 is accepted, p5 and p10 are refused, and every other row keeps its result. Whatever the ruling, p5 should become a pin.

**The refusal's wording is wrong at every method-receiver store.** p2, p6, p7 and p8 all report "`Thread.spawn` hands back a `std.task.Thread<Void>` whose `Ok` handle must be consumed, and this one is discarded. Bind the handle, as `try! Thread.spawn { ... }` does…".
- The handle IS bound (`var t = try! …`), and it isn't discarded.
- The cause: the method call first moves `t` into an argument temporary (`_6 = move _2` in p7's MIR). `refuse_fate` receives that temporary, which isn't a user local, so it falls back to the discard text.
- The discard text also leaves out the one hint this user needs: "Moving it into storage writes its fate only when the storing type declares a `deinit` of its own".
- A plain-call argument keeps the name. p12 reads "`t` moves into an argument of `keep`, which writes no fate".
- The fix should carry the user's binding through argument temporaries, with p7's message as its pin.

**Side note:** the assignment form through a pointer, `g[0].slot = move t` (p3), stops earlier at `slice.not-yet` ("a write to an owning part of a raw pointer's pointee is not lowered to MIR in the bootstrap slice yet"). So this issue's repro has to use the push form. The same assignment through `&var` works (p4: accepted, joins).
