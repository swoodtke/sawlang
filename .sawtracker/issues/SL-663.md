## Description

**Unit 2 of SL-661: the bootstrap seed.** `compiler/tools/build.py` builds Stage 1 by running `sawc/sawc.py` (`FROZEN_SAWC`). This unit makes it build from a pinned seed instead, so deleting `sawc/` leaves sawc2 buildable.

**Facts:**
- sawc2 already compiles itself: the fixpoint lane builds Stage 2 with Stage 1.
- Once SL-425 re-canonicalizes the workaround markers, `compiler/` leaves Stage 0's subset, so the v0 compiler can't be the long-term seed.

**Decide (with the user, before dispatch):** where the seed comes from. Options:
- a sawc2 binary per target, built from a tagged sawlang and published as a release artifact that `tools/toolchain.py` fetches and caches by version, the way it fetches a pinned checkout today;
- building the seed from a pinned sawlang commit by bootstrapping that commit (which needs Stage 0 at least once, through the tag);
- both: the artifact, with the bootstrap as the fallback that proves the artifact reproducible.

Whichever is chosen, the seed is bumped deliberately (a pin file) when `compiler/` needs a newer feature than the seed accepts.

**Owed:**
- `build.py`'s stage chain: seed, then Stage 1, then Stage 2. The fixpoint compares Stage 1 against Stage 2, as it does now.
- The pin and how to bump it, documented in `compiler/README.md`.
- The fixpoint lane passing from the seed.
- The `toolchain` battery lane covering the seed's resolution.
- Every user of the build chain checked against the new chain (obligation 2): `build.py`'s callers, `patch_gate.py`, the fixpoint lane and `tools/linux.py`.

**Depends on:** nothing. It can land while `sawc/` still exists, as long as the tag's build environment is untouched.

**Air, pre-dispatch on option C (the checked-in LLVM IR seed): one gap and two checks.**

1. **The seed also needs a runtime, and today only Stage 0 can supply the first one.** `compiler/tools/build.py`'s docstring: "Stage 1 links against Stage 0's runtime, since Stage 0 links it; every link after that takes the runtime Stage 1 builds with `sawc2 runtime`". A seed binary compiled from the driver's `.ll` alone has nothing to link against once `sawc/` is gone: `sawc2 runtime` needs a sawc2 binary, and the seed is that binary. So commit the runtime's IR beside the driver's, per target (`sawc2 runtime … --emit-ll` exists), and compile the C shim from source with `choose_clang`'s clang. That ties this unit to SL-664 (where the runtime's sources move): say which lands first, or have the seed take its shim from wherever SL-664 puts it.
2. **The IR is path-free today; keep it that way with a check.** This session's `.build/sawc2-stage2.ll` (34 MB, arm64-apple-darwin) contains no `/Users/` path. Its only target-specific line is `target triple = "arm64-apple-macosx11.0.0"`, so a bump made on any machine for a target is byte-identical. A lane (or the bump's own check) that refuses an absolute path in the committed IR keeps that true.
3. **Reproducibility, which c1 asks to choose: I'd take a self-reproduction fixpoint.** The pin records the source commit the seed was emitted from. The check builds the seed binary from the committed IR, has it emit the IR of that pinned commit (`git worktree` at the pin), and requires byte equality with the committed IR. That proves the IR is what the source says, not only that it builds today's Stage 1. Each target's IR is its own artifact, since the runtime half differs per host, so a bump regenerates all three, the two Linux ones in the Lima VM through `tools/linux.py`. I'd check that equality when reviewing each bump.

**SL-663.p1 (b663seed), SL-661 unit 2: the bootstrap seed is checked-in LLVM IR.** It is a binary diff, 7.32 MB, under the 8 MiB request cap.

**What it does:**
- **`compiler/seed/<target>/`** holds, for each of arm64-apple-darwin, aarch64-unknown-linux-gnu and x86_64-unknown-linux-gnu, the driver's IR (`sawc2 build -O2 --emit-ll`) and each runtime module's IR, xz-compressed. That is 1.81 MB per target for the driver, about 60 KB of runtime, 5.62 MB in total. **`compiler/seed/pin`** names the source commit: 9fbc756c9, SL-664's merge.
- **`build.py`'s `build_seed()`** decompresses the host's IR, compiles it and `runtime/shim.c` (from the tree) with `choose_clang`'s clang, links, and caches the result by key. `bootstrap_stage1()` builds Stage 1 from the seed, linked against the seed's own runtime. Stage 1 then builds `runtime/` and Stage 2 as before, and Stage 1 is now cached by key.
- **No Stage 0:** a clean build under a Python with no llvmlite succeeds. A cold build takes 58 s, against 2 min 30 s with Stage 0.

**Your three pre-dispatch points:**
1. The runtime IR is committed and the shim is compiled from source.
2. The path-free check refuses any absolute path in a committed `.ll`, with five detector cases.
3. The self-reproduction check: the seed built from the committed IR re-emits all 43 files from the pinned commit's tree (`git archive`), byte for byte.

`seed.py check` runs inside the fixpoint lane (12 s) and by hand. The Mac seed reproduces all three targets, and the aarch64 seed and the x86_64 seed (under Rosetta) pass in the VM. An injected absolute path and an injected instruction change were both refused, beside a clean control.

**The bump procedure** is in `compiler/README.md` "The seed" (`seed.py write`, `tools/linux.py seed`, `seed.py check`). The shim is compiled from the current tree, so a shim change that alters a seam the pinned runtime IR calls owes a bump; this is documented.

**Sweep:**
- `std_cone` stays, re-described as the one Stage 0 build of the driver; SL-667 deletes it.
- `build_program` still uses Stage 0 for unit programs and oracles (SL-665/666).
- `sawc/` stays a fixpoint input.
- The hazard prose in `compiler/README.md` that assumes Stage 0 builds Stage 1 is left for SL-425.

Gate (agent): a clean build from the seed; `run.py --only units,subset,runtime_table,programs`; `citations toolchain`; the fixpoint lane; `tools/test_linux.py`; and `tools/linux.py run-lane hello` on both arches with the Linux seed. The final pin was rechecked under the lock.

**The size headroom is under 1 MB.** A future bump may need a lighter recipe (e.g. dropping -O2 from the seed IR, or per-target patches), or the deferred binary hosting.
