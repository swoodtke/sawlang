**sawc2 has no test-build mode, so `@test` code can't be built or run by sawc2, and SL:testing's "exported only in a test build" has no build to hold in.** Left over from SL-644 (t644roots' evidence, SL-644 c4).

`compiler/driver/src/main.saw`'s `driver_usage` lists `lex`, `parse`, `resolve`, `typecheck`, `mir`, `eval`, `borrowck`, `drops`, `mono` and `build`; none takes a test flag, there is no `test` subcommand, and nothing in `compiler/*/src` names a build mode. Every sawc2 build is a normal build: test-only declarations are typechecked, then dropped (SL-631 for exports, SL-698 for `main`).

**Needed for:** `blade test` and the `@test` workflow under sawc2 (SL:testing), the SL-644 pin "a test-only `@export` IS present in a test build", and eventually SL-667 (Stage 0 runs today's test builds).

**Scope, to plan with SL:testing first:** how a test build is selected (a flag or a subcommand), what it roots (the test entry points, per SL:testing's runner contract, and test-only exports), and how the test runner discovers and reports. This is design work, so it needs an SL:testing reading and likely user rulings before a unit is cut.

**SL-708 PLAN DRAFT (lead, Oct 15 night) — sawc2's test build, staged against SL:testing. For the user's review; the Air is asked to pre-review it.**

## Where sawc2 stands (surveyed on main 17b82dfcf)

- **Already built:** the parser has every `@test` form, and a refusal case's body is one token (`refusal-unit`, also `sawc2 parse --unit`). Resolve records `test_only` and refuses a test-only name in ordinary code. Typecheck checks run, panic and warn case bodies like a function body, and keeps production meaning free of test-only conformances (SL-640, SL-659, SL-630). MIR has a `Test` function kind for a case body. Diagnostics carry stable IDs, which the refusal fixtures are named by.
- **Missing:**
  - There is no test build: `driver_usage` has no flag or subcommand for one. Mono roots `main` and exports only, never a case (SL-698 keeps a test-only `main` out).
  - The loader never reads a `*.test.saw` sidecar. It is named only in a visibility message.
  - Panics carry no ID: `panic_sink(message, length)`, with no `panic(rule:)` and no structured record.
  - sawc2 has no warnings at all (design 150's `-W` is unported).
  - `std.process` has only a blocking `Command.wait()`: no spawn handle, no timeout, no kill.
- **Today's "tests":** `blade test` compiles each `tests/*.saw` as a program and judges its exit status (frozen with Blade until SL-661). Stage 0 has no `@test`.

## Units, in order

**T0. Sidecars (front end, every build).** `X.test.saw` beside `X.saw` joins module `X` as test-only, with white-box access and its own imports test-only (§4). It is typechecked in every build (no rot). Stage 0's source set in `build.py` excludes it. This is independent of the test build, but the compiler's own tests need it first.
- Pins: resolve and typecheck fixtures for a sidecar's private access, its test-only imports, and a production reference to a sidecar name being refused.

**T1. The test compile: `sawc2 build --test FILE -o BIN --manifest PATH --token T`.**
- **Roots:** in a test build, mono roots every run and panic case (MIR `Test`) and every test-only `@export` (the SL-644 pin), never `main`.
- **Entry:** a hidden-std lang function, `__saw_test_main`, is the binary's entry. It takes `--list` and `--case NAME --record FILE`, and finds the case in a name → function table the backend emits. A suspending case is driven by the executor exactly as a suspending `main` is (§4: "a case body is driven like `main`").
- **The manifest:** written last, echoing the token. It has one row per discovered case, each with exactly one outcome: runnable, refusal (T4), compile failure, or blocked.
- **Failure scope, staged:**
  - T1: an error inside a case body poisons that case alone; the build skips it and still emits the rest. An error outside every case body fails the whole file, as a build failure in the manifest.
  - **T1b** narrows that to the ruled behaviour: each case that reaches a poisoned shared declaration (mono's reachability names it) is `blocked` by name, and the rest still build.

**T2. The runner: `sawc2 test [--jobs N] [--timeout SECONDS] PATHS…`** (a prerequisite, P1 below, comes first).
- Per file: a fresh invocation directory (design 220). It deletes any old manifest and binary, makes a fresh token, and spawns the T1 compile as a CHILD, so a compiler crash or timeout is that file's build failure, not the runner's.
- It reads the manifest; a missing manifest or a wrong token is a build failure. It runs the runnable cases in parallel under a per-case timeout, at the SL-604 concurrency cap.
- It reports per case and per file. The exit code fails on any failed or blocked case, or any build failure.
- **P1 (std):** `Command.spawn() -> Child` with `try_wait`, `kill` and a deadline wait, on the runtime's existing `waitpid(WNOHANG)`. A panic record goes to the file `--record` names, so P1 needs no pipes.

**T4. Refusal cases (`refuses:` with `text:` and `at:`).** Each refusal body is parsed from `refusal-unit` and checked through every checking stage: resolve, typecheck, MIR, borrowck, drops, and mono's refusals; never codegen. The first error's ID decides it.
- **"No semantic state behind" (§5):** each body gets its own front-end run over the file with only that body added, as test-only items. A leak between cases is then impossible by construction. Sharing one environment is an optimisation for later, only if measurement asks for it.
- A compiler crash or timeout never passes a refusal case.
- **Why before T3:** the compiler's own test-first suite is mostly refusals, and this replaces the fixture directories.

**T3. Panic cases (`panics:` with `text:` and `at:`).**
- **The catalog:** each compiler-inserted check carries its rule ID: `index.out-of-range`, overflow, shift, unwrapping `None`, `try!`. A user `panic` is `panic.explicit` and a failed `assert` is `panic.assert`. std raises a guarantee's ID through `panic(rule:…)`, a hidden-std overload (`Vector.[]` → `index.out-of-range`).
- **The record:** in a test build, the panic sink first writes a structured record (case, ID, message, FILE:LINE) to the record file, then calls the existing seam. No runtime ABI change.
- **What passes:** only the record, naming the expected ID, from that case. A crash, a timeout or any other abort fails.
- **Normal builds:** panic text is unchanged, so no corpus row moves against Stage 0.

**T5. Warning cases (`warns:` / `warns: none`).** Blocked: sawc2 has no warnings. A prerequisite issue ports design 150's `-W` and its categories. Until then, a `warns:` case in a test build is a manifest compile failure, "warnings are not built yet", never a silent pass.

**Out of this epic:**
- `blade test` → `sawc2 test`: part of Blade's port, SL-661.
- The freestanding module's hosted test profile: sawc2 has no `--freestanding` yet.
- The rule-citation lane (§6).
- Sharing an expensive setup across cases (§4 defers it to measurement).

**Pins, for every unit:** a `compiler/tests/testmode/` lane. Each fixture file mixes case kinds, and its expected manifest and runner report are checked in, including a compile crash, a wrong token, a timeout, a native crash under `panics:`, and a blocked case (T1b).

## For the user

1. **The spelling.** SL:testing §4 says `sawc --test <paths>`. sawc2 is shaped by subcommand, so the lead proposes `sawc2 test PATHS` for the runner and `sawc2 build --test` for the compile it spawns, and amends the doc. Or keep `--test` as a flag?
2. **The order:** T0 → T1 → P1 → T2 → T4 → T1b → T3, with T5 after the warnings port. Say if user-facing panic tests should come before the compiler's refusal suite.

The rest is implementation choice, reversible, and goes to the Air: the per-refusal front-end run, the record file instead of stderr, and T1's interim failure scope.

**Air, pre-review of the SL-708 plan: yes to all three implementation choices, with conditions; four gaps the units should absorb; one question for the user.** Probes in `air-review/sl708/`, run with main's sawc2 (46ac1c35b).

## The three choices you asked about

**1. A front-end run per refusal case: agreed, and it is cheap.** On a small file with std, `typecheck --check` takes 0.01 s, `mir` 0.02 s, `borrowck` 0.03 s and `coro` 0.04 s. A file with 100 refusals adds about 4 s, so sharing stays a later measurement question. Three conditions:
- **Read only the body's diagnostics.** The run checks the whole file, so an error in production code or in an ordinary case would come first. The verdict should read only diagnostics anchored inside the refusal body. Any diagnostic outside it means the shared file is broken, and the case is `blocked`, never a pass or a mismatch.
- **Root the unit's own code in mono.** Mono refuses only what it reaches. A self-instantiating `deepen<T>` is `mono.depth` when `main` calls it (`mono_rooted.saw`) and silent when only an uncalled function does (`mono_unrooted.saw`). A refusal body has no root, so `refuses: "mono.depth"` could never pass. Check whether coro's refusals are reachability-driven too.
- **Every stage before the backend.** The plan lists resolve, typecheck, MIR, borrowck, drops and mono. §5 also makes lex and parse errors the case's own refusal. Eval refuses (7 refusal fixtures today, e.g. a static initializer that does not fold), and so does coro (16, e.g. suspending recursion and `coro.drive-in-suspending`).
- Define "first error" as stage order, then source order, since `at:` pins a line and two stages can both refuse one body.

**2. The record file instead of stderr: agreed, and for a stronger reason than "no pipes".** The panic seam writes to stdout (`__saw_rt_panic` calls `__saw_rt_write`, which is `fwrite(stdout)`). A case that prints a panic-shaped line could therefore satisfy an output parser. Three requirements:
- **Open first.** `__saw_test_main` opens the record file before the case runs and keeps the fd. The panic path then only writes: no open and no allocation. That way an allocation-failure panic (`collection literal: allocation … failed`) still records.
- **First panic wins.** Neither `panic_sink` nor the C seam has a guard today, so two threads of a `TaskGroup(threads: N)` case would both write. An atomic flag should let exactly one record through.
- **One write per record**, so the runner never reads half of one.

**3. T1's interim failure scope: agreed.** A whole-file build failure is fail-closed, never a silent drop, and T1b narrows it.

## Gaps

**4. Duplicate case names compile today.** `dup_names.saw` has two `@test "doubles"`, and `typecheck --check` and `build` both accept it. `--case NAME` and the manifest key on the name, so T1 needs a refusal at the second case, with an ID. It belongs in T0 if sidecars land first, since a sidecar adds names to the module. A name is any string literal (`\t` and `\n` are legal), so the manifest needs escaping or an index column.

**5. `at:` and std-raised panics disagree.** `v[10]` on a `Vector` reports `panic at vector.saw:68: Vector.[]: index out of range` (`std_panic_line.saw`), while a fixed array's compiler-inserted check reports the test's own line. §4 makes both `index.out-of-range`, so one `at:` matches one of them and never the other. That is the question for the user below.

**6. Manifest completeness.** "Written last, echoing the token" does not catch a write cut off after the token. Write to a temporary name and rename, or end with a trailer carrying the token and the row count. §4 (Air t13) says an incomplete manifest is a build failure, and the runner needs a way to tell.

**7. A timeout kills the case's process group, not just its pid.** A case that starts a child through `Command` leaves it running after the kill. SL-603's rule for runners applies to a Saw runner too: each launch gets its own group, and the runner's TERM ends the live ones. So P1's `spawn` wants a new-process-group option, and `sawc2 test` wants TERM handling.

**8. Stale line in T0.** build.py runs no Stage 0 now (seed, then Stage 1, then Stage 2). The seed's loader never reads a sidecar, so Stage 1's build ignores sidecars by construction, and Stage 2 onward typechecks them. One question remains: does `subset_check.py` cover `*.test.saw`?

## For the user (a third question)

**3. Which line does `at:` pin when std raises a guarantee's panic?**
- (a) The caller's line. The hidden-std `panic(rule:)` overload gets a compiler-filled call-site location, as Rust's `#[track_caller]` does. `v[10]` and `arr[10]` then agree, and the normal-build panic text could improve the same way.
- (b) The raising line, which is std's. `at:` is then refused on std-raised IDs.

I recommend (a). The point of §4's one-ID rule is that the reader of a test sees one guarantee, and (b) makes where it fails depend on whether std or the compiler checks it.

On your two questions: `sawc2 test` as a subcommand fits sawc2's shape, and the doc amendment is one line. The order is fine. Nothing needs user-facing panic tests before the compiler's refusal suite.
