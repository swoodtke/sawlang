## Description

**Closure types carry the `Send`/`Sync` their captures prove** (the user, Oct 19: "annotate closures with the Send + Sync properties of their closures and then informing the user when they do something which requires Send or Sync and their closure doesn't conform").

**Today:** a function type is structural (`() sync -> Int`) and erases what the closure captured, so every closure type is treated as not `Send` (spec: "a closure is not `Send` either"). A capture-less closure (a null environment) is trivially safe, yet `Vector<() sync -> Int>` held across a suspension in a `threads:` task is refused (SL-579's K02).

**Why `Send + Sync` is the right test** (spec, "Escaping-closure heap environments"): an escaping closure is a `Copy` value whose copies share ONE immutable heap environment behind an atomic refcount, so it's `Arc`-like over its captures. `Arc<T>` is `Send + Sync` iff `T: Send + Sync`: copies on two threads read the captures at once (Sync), and the last release tears them down on whichever thread drops last (Send). Escaping closures can't capture references or `self` (refused), so the captures are owned values, and their own `Send`/`Sync` decides.

**The design questions (for the brief; some may need the user):**
1. **Spelling:** a marker in the function type's effect slot (e.g. `() sync send -> Int`), or auto traits on function types inferred from the creating closure and carried through generics. Reader visibility vs. inference (doctrine: infer when accurate, reader visibility trumps).
2. **Subtyping:** a `Send` function type flows to an unmarked one; not the reverse.
3. **Where a closure's traits are computed:** at creation, from its capture list (the compiler already walks it for the env layout), with a capture-less closure always `Send + Sync`.
4. **Diagnostics:** "the closure is not `Send`: it captures `x: Rc…`/`p: UnsafePointer<T>`", naming the capture, at the use that needs it (a `threads:` frame, `Thread.spawn`, a `Channel<T>` element).
5. **Interaction:** `any` erasure; `Box<() -> T>`; the `Thread.spawn` brace's capture audit (already per capture), which should become a special case of this.

**Pins:** K02 (`Vector<() sync -> Int>` of capture-less closures across a suspension in a `threads:` task) becomes accepted, while one capturing a non-`Sync` value is refused, naming the capture. SL-788 option (a)'s over-refusal is measured with and without this.
