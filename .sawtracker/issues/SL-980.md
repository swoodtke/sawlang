**Where it's detected now:** only in `parse_let` (`compiler/parse/src/parser.saw`), for the statement `var _ = e`. Two other parse sites take `var IDENT` with no `_` check:
- `payload_pattern`, for `case Some(var _)`;
- `parse_optional_binding`, for `if var _` and `while var _`.

The `borrow var` forms are probably the same and are untested: `case Some(borrow var _)` and `borrow var _ = place { … }`. The census covers all of them, and the fix is one refusal helper called from every `var`-binding parse site, its docstring naming them.

**Air: SL-980 pre-review, a position matrix for `var _` on main** (a48985c2c, which includes SL-978). One small program per position, each built with `--emit-ll`.

**Accepted today, so the fix must refuse each one:**

| position | spelling |
|---|---|
| a payload | `case Some(var _)` |
| `if var` | `if var _ = o { … }` |
| `if var`, over a conditional lend | `if var _ = v.find(0) { … }` |
| `while var` | `while var _ = v.pop() { … }` |
| `guard var` | `guard var _ = o else { return }` |
| a `borrow` block | `borrow var _ = v[0] { … }` |
| a `borrow` payload | `case Some(borrow var _)` |

- **`guard var _` isn't in the census.** It may well be the same `parse_optional_binding` site as `if var`/`while var`, but please pin it.
- **Both `borrow var` forms are confirmed accepted**, not just probably.

**Refused already, nothing to do:**
- the statement `var _ = 5` (`parse_let`);
- a closure parameter, `{ var _ in 2 }`: the parser refuses it;
- tuple patterns, `let (var _, b) = …` and `case (var _, y)`: refused at parse, and with a named binding too (`var a`), so it isn't a `_` position.

**Not built yet:** `for var _ in v.iter()` gets `slice.not-yet` (`syntax.expr.for.var`). When `for var` lands, the refusal helper should cover it, so it's worth naming in the helper's docstring now.
