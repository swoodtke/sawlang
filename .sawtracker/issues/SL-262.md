## Description

A `move` in a `while` CONDITION whose body FALLS THROUGH is a use-after-move the move checker does not catch: the condition re-evaluates, consumes the same value again, and one value is destroyed once per iteration. Silent -- exit 0, no diagnostic. NO COROUTINE IS INVOLVED; this is the plain synchronous path.

Repro (single file, measured on origin/main c9991092 and unchanged by the SL-234 branch):

  struct Res { name: String }
  extension Res: NoCopy {
      func deinit(&var self) { print("drop {}", self.name) }
  }
  func consume_bool(r: Res) -> Bool { true }

  func while_falls_through() -> Int {
      var r = Res(name: "old")
      var n = 0
      while consume_bool(move r) {
          n = n + 1
          if n > 2 { break }
      }
      n
  }
  func main() { print("n {while_falls_through()}") }

Observed: "drop old" THREE TIMES, then "n 3", exit 0. Wanted: a compile error -- the second evaluation of the condition reads a binding that was moved on the first.

MECHANISM: the move checkpoint treats the condition as straight-line code evaluated once. A `while` CONDITION is the one head that re-evaluates, so the loop's back edge carries the move back to a point where the value is already gone -- the same loop-carried question the checker answers correctly for a move in the loop BODY ("value was moved at line N and can no longer be used"). Reassignment inside the body does not make it legal either, and the checker is right about that half: it refuses a subsequent READ after `while consume(move r) { r = Res(...)  break }` with exactly that message. So the hole is specifically the condition's own re-evaluation, not the binding's liveness in general.

FOUND WHILE FIXING SL-234, which needed the sync twin as its oracle: SL-234's driven cells now relinquish the frame's claim exactly once per condition evaluation, which is correct for every program in which the move is sound. This issue is the definition of "sound" -- programs where the condition can run twice have no correct behavior to match, in either the sync or the driven path. NOT caused by, not fixed by, and not worked around by SL-234; filed so the two are not confused.

Note for whoever takes it: the fix is in the move checker (a loop's condition is on the back edge, so a move there must be checked against the loop's own liveness), not in the coroutine transform. Once it refuses, SL-234's `while` arm keeps working unchanged -- its hoist fires only for conditions containing a move of a frame local, which would then be exactly the set this check rejects, and the arm becomes dead for unsound programs rather than wrong for them.
