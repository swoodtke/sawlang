**Ruled by the user (Oct 10): a package's module root is its `src/` directory, everywhere.** Logged in SL:open-questions.

**Today:** the spec says a bare import searches "the importing file's own directory, its package root and the configured search paths", but never defines "package root". Stage 0 takes it to be the directory holding `Saw.toml`, so a package's imports of its own modules spell `src.`: Blade writes `import src.layout.*` in `blade/src/builder.saw` and across `blade/tests/`. From outside, nothing leaks, because Blade passes `--module-path dep=<dep>/src`.

**The rule:**
- **Inside the package:** `import layout`, which already resolves through the importing file's own directory under Stage 0, or `import <package>.layout` by the package's own name.
- **A package's tests:** `import <package>.layout`, as a Rust test writes `use mycrate::layout`. Blade's tester passes the package's own `--module-path <name>=<root>/src`.
- **From outside:** unchanged.

**Work:**
1. **Spec:** define "package root" as the package's `src/` (the directory of its `lib.saw` or `main.saw`) in the import-search sentence and in Package Structure. Say how a package names itself.
2. **Blade:** the tester and builder pass the package's own module path. Rewrite `blade/` and `libs/` from `src.X` to `X` or `<package>.X`, which Stage 0 already accepts. Stage 0's extra search of the `Saw.toml` directory is frozen and harmless. Gate: `bootstrap`.
3. **sawc2's resolver** implements the defined rule, with fixtures for an in-package bare import, a self-named import, and a test importing its package. SL-518 does the same for `compiler/`'s own stage packages.

Do it after SL-518, which owns the compiler half.

Approved patch SL-519.p1 (revision 1)

Approving SL-519.p1. The spec now defines the package root, Blade and libs move to it, and sawc2's resolver makes a package file one module whichever spelling reaches it. The `import blade.X` deviation is the right call under SL-531's two Stage 0 limits. On your question about the entry-directory search: **yes, it's separate, but it's an import-hijack hazard, not only a spec divergence.** Repro below.

**What I checked**
- **The gate passed on the applied commit:** tested_commit == applied_commit == 9d2ebe2a. The tested tree, 9b4da913, is the tree I get when I apply the diff to 686a397b.
- **My own `run.py`** passes from the applied tree's root: 21 resolve golden cases (`package/shelf` among them), 47 resolve refusal fixtures (`import.src-path` among them), 27 rules, and 124 checker fixtures.
- **`battery.sh docverify bootstrap`** under the suite lock, on the review tree:
  - `docverify`: 538 blocks OK;
  - `bootstrap`: Blade 22/22 at stage 1 and at stage 2, toml 4/4, semver 4/4, imgformat 2/2.
- **The spec text:**
  - the package root is `src/`, and module paths start there;
  - a file outside `src/` has no package root;
  - the two in-package spellings name one module, so one type;
  - tests import their package by name;
  - `src` is never a path segment, and `import src.x` is refused with a hint.

  The `--module-path` entry says it's also how a package names itself.

**The entry-directory search, as a hazard** (`.build/scratch/air-review/sl519/hijack/`). A library module `libpkg/src/sub/a.saw` does a bare `import util`. Its own package root has `libpkg/src/util.saw` (`tag()` returns 2), and the application beside its entry file has `app/util.saw` (`tag()` returns 1).
- **The spec's search order** is the importing file's directory (`src/sub/`, nothing there), then the package root (`libpkg/src/util.saw`), so the answer is 2.
- **Both compilers answer 1.** Stage 0's binary prints 1, and sawc2's (built with this tree's `sawc2 build`) prints 1. In sawc2's resolve dump, `libpkg.sub.a` binds `util` to a module named plain `util`, the entry directory's file. Under this patch's identity rule the library's own file would be `libpkg.util`, and no such module is loaded.
- **So a dependency's bare import binds to whichever same-named file sits beside the program that compiles it.** A library's meaning then depends on its client, and an application can replace a dependency's module without meaning to.

That's more than a divergence. It wants its own issue: drop the entry-directory step from sawc2's search (the spec's order), plus a Stage 0 SL:hazards entry, since Stage 0 can't change. Both compilers' answer here is wrong by the spec.
