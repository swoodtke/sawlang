## Description

**ESP32-S3 (Xtensa LX7) as a freestanding target of `sawc`.** Asked by the user on Nov 12: "do the sweep of what's needed to support an esp32-s3 freestanding target. we can update sawos separately." This issue owns the sawlang side: the target model, the toolchain choice, the runtime and the freestanding suite. The kernel's Xtensa HAL is the sawos repo's.

**Context.**
- The ESP32-S3 is Xtensa, not RISC-V, so it is a new architecture, where the ESP32-C3 was a board under the existing `riscv32-unknown-none-elf` target.
- `sawc` knows five triples today (`compiler/target/src/layout.saw`): `arm64-apple-darwin`, `x86_64-unknown-linux-gnu`, `aarch64-unknown-linux-gnu`, `aarch64-unknown-none-elf`, `riscv32-unknown-none-elf`.
- The Aug 16 hardware-path entry (`designs/todo.md`, "HARDWARE PATH") names the two things the S3 needs: "the XTENSA CODEGEN SEAM (sawc emits .ll with the xtensa triple + hand-supplied datalayout; Espressif's LLVM fork lowers it)" and an Xtensa HAL.
- Espressif's toolchain is installed on the lead's machine under `~/.espressif/tools/`: `esp-clang`, `xtensa-esp-elf`, `qemu-xtensa`, `esp-rom-elfs`.

**Unit 1 (this issue's first step): a read-only sweep.** It changes no tracked file. Its report answers, with command output for every claim:

1. **Toolchain.** Which clang lowers Xtensa IR (version, the triple and `-mcpu` it wants, its datalayout, whether it passes `build.py`'s opaque-pointer check), which linker links it (ld.lld or GNU ld), what supplies the integer and soft-float helpers, and which QEMU machine runs it.
2. **The target model.** Every site in the compiler, the driver, `build.py`, the runtime and the freestanding runner that names a triple or branches on the architecture or the word width, as a table: site, what it decides, riscv32's answer, Xtensa's answer and its source.
3. **The C ABI**, read off what esp-clang itself emits for a probe set: sizes and alignments, how scalars, small and large aggregates, 64-bit integers and floats are passed and returned, extension of narrow integers, the stack alignment, and windowed versus call0.
4. **Atomics and floats:** what the S3 does inline and what goes through a libcall.
5. **A spike:** IR that `sawc` emits today for a riscv32 freestanding program, retargeted by hand in a scratch copy, through esp-clang at -O0 and -O2; then as far toward a boot in QEMU as an afternoon allows.
6. **The plan:** the units in order with a size each, what the server's gate machine would need installed, the decisions that are the user's, and the questions for the sawos lead.

Later units are filed as children once the sweep reports and the user rules on its open questions.


## Comments

**SL-1063 unit 1, the sweep's report (agent pxtensa, Opus, read-only; Nov 12).** Evidence is in the lead's checkout, `.build/scratch/pxtensa/`: `abi.md`, `sites.tsv` (86 sites), and the probes named below. No tracked file changed.

**Verdict.** sawc can target the ESP32-S3 with Espressif's clang, and nothing in the IR has to change. sawc's riscv32 IR for four freestanding cases (`hello`, `int64_operators`, `atomics_word`, `call_convention`), with only the `target triple` and the `"target-features"` changed, compiled with esp-clang to Xtensa objects in 24 of 24 builds (windowed, call0, no CPU named × -O0, -O2), rc 0, no diagnostic (`e/spike_summary.txt`). Every object leaves only the four `fs_*` HAL hooks undefined (`e/spike_objects.txt`). sawc writes no `target datalayout` line and esp-clang fills in its own, so the "hand-supplied datalayout" of the HARDWARE PATH note is not needed.

**Toolchain.**
- Espressif clang 20.1.1 (`esp-20.1.1_20250829`): backends riscv32, riscv64, xtensa; no aarch64. It passes `build.py`'s opaque-pointer probe for the Xtensa triple and fails it for aarch64 and the macOS host, so it can't be `SAWC_CLANG` (one override for every target).
- `choose_clang` never looks in `~/.espressif`. Homebrew's clang 23.1.5 and Apple's have no Xtensa backend; the Linux VM's clang-19 lists the backend but its driver refuses the triple.
- For IR input nothing on clang's command line picks the CPU: the module's function attributes are the only selector. With none, the backend still emits windowed code, FP instructions and S32C1I (`e_default_cpu.txt`).
- Linker: Homebrew's `ld.lld` (the freestanding runner's) fails, `unsupported e_machine value: 94`. esp-clang's own `ld.lld` and GNU `xtensa-esp-elf-ld` both link, windowed and call0 (`e/link_try.txt`). The split build's `clang -r -fuse-ld=lld` and `llvm-objcopy --localize-hidden` work with esp-clang's tools (`e/support_and_split.txt`).
- Helpers: as riscv32. 64-bit divide and the double soft-float routines are std's own weak definitions; a spike object needs nothing from outside.
- QEMU: Espressif's `qemu-system-xtensa` 9.2.2 has `-machine esp32s3` and ships the ROM; the one on PATH is Homebrew's 11.1.3, with no esp32 machine. Nothing was booted (sawos's SO-73 owns that).

**Triple.** `xtensa-esp-unknown-elf` with `-mcpu=esp32s3` is esp-clang's own multilib name and the only spelling that compiles with no warning; `xtensa-unknown-none-elf` and `xtensa-esp32s3-elf` print `no multilib found`, and the latter without `-mcpu` turns on `+dfpaccel`, which the S3 lacks.

**The target model (`sites.tsv`).**
- `compiler/target/src/layout.saw`: three constants (the triple list, the bare-metal list, a 4-byte word); one new rule (`target_native_atomics` must follow the `s32c1i` feature: with `-s32c1i` LLVM calls `__atomic_compare_exchange_4`, which today's function would report as native); one decision (the freestanding default features). The FPU funnel, the builtins funnel, `c_class` and `c_extends_narrow` already give Xtensa's answer.
- Driver: follows the target record; one decision, whether a `"target-cpu"` attribute reaches the IR.
- `compiler/tools/build.py`: `BARE_METAL_TARGETS`, and a way to find an Espressif clang or a per-target override.
- typecheck, llvm, mono, coro: keyed on the word width; nothing needed but the `atomics.target` message, which names riscv's `A` extension.
- `tools/freestanding_runner.py`: one `ld.lld` for every arch; tools found on PATH (the wrong QEMU, a linker that can't link Xtensa); any missing tool skips the whole suite, not one arch; `tools/test_freestanding_runner.py` assumes one clang compiles every arch.
- Blade: esp-clang refuses `-march` and `-mabi`; `[sos]` has no CPU key; `arch_for_target` and imgformat's `SosimgArch {Riscv32 = 1, Arm64 = 2}` need an Xtensa answer.

**ABI (`abi.md`).** ILP32, little-endian; `long long` and `double` aligned to 8; `char` unsigned; stack alignment observed as 16. Narrow integers carry signext/zeroext as on riscv32; six argument registers; an i64 takes an even register pair. sawc's plain IR scalars land where esp-clang's C puts them, so Xtensa needs no new C-convention rule for what sawc accepts at `extern` today (`c5_plain_vs_c.diff`). Aggregates differ from riscv32 (up to six words in registers) and esp-clang and esp GCC 15.2 disagree on a one-word struct result (`sret` versus a2); sawc refuses aggregates at `extern`, so neither is reachable yet.

**Atomics and floats.** Word atomics are inline (`wsr scompare1` + `s32c1i`); 8-byte ones would be `__atomic_*_8` calls, and sawc emits none. Single-precision uses the FPU under `+fp` except divide; every double operation is a libcall, and Saw's `Float` is 64-bit, so Saw code emits no FP instruction.

**call0** is `-windowed` in `"target-features"` and nothing else (`c3_windowed_vs_call0.diff`); esp-clang has no `-mabi`. No call0 multilib ships in either toolchain; code is 8 to 9% larger. **No FP** is `-fp`. **Special registers** touched by Saw code under `-windowed,-fp`: a0 to a15, SAR, SCOMPARE1.

**UNVERIFIED.** Stack alignment 16 (from frame sizes; the datalayout has no `S`). Whether any code shape makes this clang emit `loop` instructions (none at -O2, -O3, -Os). Whether the no-CPU backend default equals the S3's ISA in general. Whether an Xtensa target record gives exactly riscv32's IR apart from the triple (argued from the record's values; sawc refuses the triple today). Semihosting exit on `esp32s3` and S32C1I across the S3's memories (nothing booted). Whether the server's gate process can read `~/.espressif`. The clang/GCC aggregate disagreement, observed and not traced to a document. Whether the Linux VM has an Espressif toolchain.
