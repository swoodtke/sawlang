## Description

**An extern parameter of type `UnsafePointer<T>?` is `backend.not-yet`** (found by the sawtracker port measure, Oct 23; probe `st_measure/probes/p6_extern_optional_param.saw`).

`extern "C" func fflush(stream: UnsafePointer<Int8>?)` called as `fflush(None)` fails with `backend.not-yet`: "an extern parameter that crosses the C convention as an aggregate is not in the backend slice yet". The RESULT side works: `getenv -> UnsafePointer<Int8>?` builds and runs (p6b).

C's nullable pointer parameter (`fflush(NULL)`, `time(NULL)`, `setlocale(…, NULL)`) is routine FFI, and the spec's FFI section shows the optional pointer only as a result. The decision owed:
- an optional pointer crosses the C boundary as a nullable pointer (`None` is NULL) in BOTH directions, as the result already does;
- the message is wrong either way: the value isn't an aggregate at the C boundary.

**Obligation 4:** every position an `UnsafePointer<T>?` crosses the C convention (extern parameters, results, `@export` parameters and results, function-pointer types), and every optional of a pointer-shaped type that should have the same niche.

**Air: SL-848.p1 approved.** Reviewed r1 on 404231543.

**The narrow-integer rule, read off the IR** (`n1`: `extern "C" { func takes(a: Int8, b: UInt16) -> Int8 }`, `--emit-ll --target`):

| target | declaration |
|---|---|
| arm64-apple-darwin | `declare signext i8 @takes(i8 signext, i16 zeroext)` |
| x86_64-unknown-linux-gnu | `declare signext i8 @takes(i8 signext, i16 zeroext)` |
| aarch64-unknown-linux-gnu | `declare i8 @takes(i8, i16)` |

That's the platform conventions: Darwin's arm64 and System V extend at the sender, and AAPCS64 extends at the receiver. Parameters and the result both carry it.

**The funnel:** `c_class` decides an optional raw pointer by LAYOUT (`kind == Pointer`), so an `UnsafePointer<any P>?`, two words, is refused with the other aggregates rather than half-passed. That's the vtable-word fix. Its two entry points are listed.

**Gates:**
- `run.py --only census,fixture_whitespace,migrate,parallel_order,parser,programs,std,subset,typechecker,units,sanitize` passes, `programs` running the new C-helper probes.
- `docverify` and `citations` are green.

**One note, not blocking:** `c_extends_narrow` is a negative list, `not triple.equals("aarch64-unknown-linux-gnu")`. Every target sawc2 builds today comes out right. But the next one added inherits "extends" by default, and the planned freestanding `aarch64-unknown-none-elf` follows AAPCS64, which doesn't, so a C callee there would read garbage upper bits from a narrow argument it doesn't extend itself. Keying it positively (Darwin or x86_64 System V extend; anything else refused until it states its convention) would turn that into a loud refusal at the new target, not a wrong value.
