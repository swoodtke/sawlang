**SL-716.p1: Data's public API in the new std, summary for review.**

- **Surface:** the surface matches Stage 0's signatures: `init()`, `init(capacity:) -> Result`, `len`, `is_empty`, `capacity`, both `[]` lends (shared read; exclusive write that separates first), `get -> Byte?`, `set`/`push`/`append`/`append_bytes`/`reserve -> Result<Void, AllocError>` (all-or-nothing), `pop -> Byte?`, `clear`, `byte_ptr`, and `slice`, an O(1) retained window via the new `offset` field. A write to a shared block separates it first, and `d.append(d)` is well defined, because the argument's retain forces the separation before the copy. `iter` is left out (SL-703).
- **Pins:** nine run programs match Stage 0 at -O0 and -O2: `data_simple`, `data_cow_slice`, `data_cow_value_semantics`, `data_cow_self_append`, `data_place_shared_read`, `alloc_data_reports_oom`, `data_set_oob_panic`, `data_index_oob_panic` and the new `data_pop_clear_raw`. The two oob-panic programs carry `// differs:` for the panic location.
- **The std MIR pin `data_spare.mir`:** one line changed, `copy length` → `Add(offset, length)`, because `spare()` indexes `offset + length` (std/data.saw:99). The relaxed load and acquire fence it pins are unchanged. This was a lead ruling.
- **Lint fixes:** five std-profile lints fired on the new code: four `root-reuse` sites (the length is now bound to a `let` first) and one `borrowed-match-payload` site (now a `relocated` helper plus `self = fresh`).
- **Corpusdiff (SL-666):** the baseline was re-measured over main with Arc. About 20 programs move to pass, among them the data_* programs, T25, W03, M41 and the import150 forms. The other rows now stop at later refusals: `iter`, `Path`, `fromBytes`, `threads:`, and five on unsigned `format`, which SL-711 lowers. One row moves to `wrong`: `alloc_data_push_forced_panics_named`, which is SL-729 (`try!` prints no error rendering).
- **Gate (Sonnet, under the lock):** `run.py --only resolver,typechecker,std,programs,coro` ok, `corpusdiff gate` ok (all 2661), citations green. The diff also applies on main after SL-717.p1, whose tsv rows don't overlap.

Approved patch SL-716.p1 (revision 1)

**Air: SL-716.p1 r1 approved; arming it.** The surface is the spec's Data section on the new std's block layout: the uniqueness gate is one funnel (`ready`: sole owner at offset 0 with room, else `relocated` + `self = fresh`), every mutation passes it, the two `[]` declarations split the gate onto the exclusive one as the spec's two-accessor rule asks, `pop`/`clear` only narrow the window, `slice` retains, `detached` sizes to `len()`, and a refused allocation leaves every `Data` as it was.

Checked on a build of origin/main (5c5632041, the base) plus the diff:
- the run lane: 159 programs matching Stage 0, the nine new pins among them; re-recording the nine with `run_lane.py --stage0` left the records byte-identical;
- `run.py --only std` ok (the one `data_spare.mir` line is `offset + length`, the fence lines unchanged);
- the corpusdiff gate (`--no-build`): all 2661 hold; the moves are the passes the summary lists, the later stops (`iter`, `Path`, `fromBytes`, `threads:`, unsigned `format` = SL-711), and the one `wrong` row, `alloc_data_push_forced_panics_named`, which is SL-729; no `stage0-wrong` row added;
- my extra probe (`air-review/sl716/probe_extra.saw`: a slice of a slice and their capacities, pop/clear/push on a slice sharing a block, `+=` through a slice, `to_string`/`to_data` through an offset, `slice(0, 0)` and `reserve(0)` on an empty `Data`, `append_bytes` from a sibling's block across a growth, `append` of a self-slice then of self, push on a tail slice) prints the same 13 lines on Stage 0 and on the patch's sawc2 at -O0 and -O2;
- `leaks --atExit`: 0 leaks on the probe at both levels and on the seven non-panicking pins' -O0 binaries;
- grammar corpus: the nine new programs accepted; astdiff clean; the conformance rows that moved (K128, K129, M41, T25, W03, W04) are existing ledger rows, so no INDEX/CONFORMANCE edit is owed.

Two notes for the lead, neither blocking:
1. `append_bytes` with `src` inside this `Data`'s own block: `ready` releases the old block (freeing it when this was the last holder) before `place` reads `src`. Stage 0's Arc version has the same order, so it is no regression, but `append_bytes`'s doc could say `src` must not address this `Data`'s own bytes, or the copy could read before the old block goes.
2. The file now reports a refused allocation two ways: `data_of_string` names the block's true size (header + bytes, align 16) while the new ops report Stage 0's numbers (the bytes alone, align 1), which the `alloc_data_reports_oom` pin follows. One convention per file would be cleaner; changing the new ops moves that pin's output against Stage 0, so it is a ruling, not a fix.
