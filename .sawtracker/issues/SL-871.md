## Description

**Epic: finish borrowing structs** (the user, Oct 23: "Build the planned features"). LANGUAGE_SPEC.md §Borrowing structs is "partially implemented": the shared, `for`-headed form is built, and these parts are planned.

**Units, in order:**
1. **Exclusive borrowing structs:** `&var` reference fields, and a `&var self` origin (`lends self` from an exclusive accessor, the root charged exclusively for the struct's whole life). Today `type.reference-position` refuses a `&var` field (SL-738 c1). The spec already rules it sound: each `next` reborrows through the struct.
2. **The `borrow` head and temporary heads:** `borrow var it = grid.cells() { … }` / `borrow let it = v.iter() { … }` as the second legal position besides a `for` head; a temporary receiver kept alive for the window. Includes **SL-684** (call resolution must pick the `borrows` member at a borrow head).
3. **`LendingIterator`, `for borrow let/var`, and the `lends` expression:** **SL-738** and **SL-601**, after the trait-shape ruling (below).
4. **Map's entry iterator:** **SL-506** (its design: method names and item shape), on top of unit 3.

**The open language question (for the user, before unit 3):** the spec says `LendingIterator` lends "`&var Item?`, or `&Item?` for a shared one", but one trait can't state both. Options are recorded in the epic's comments.

Each unit: conformance rows first if it touches a safety guarantee (an exclusive borrowing struct does, obligation 3); a position matrix with leak and ASan checks; the spec's status line flipped as each lands.

**The trait-shape question (for the user, before unit 3).** The spec says `LendingIterator` lends `&var Item?`, or `&Item?` for a shared one; one requirement can't say both.
- **(a) One trait, the weaker requirement (the lead's recommendation):** `next(&var self) borrows -> &Item?`. An impl may lend MORE (`-> &var Item?`), since an exclusive lend meets a shared requirement. `for borrow var` requires the concrete `next` to lend `&var`. Borrowing structs are reached only by static dispatch (the spec: they can't instantiate a type parameter), so the concrete impl is always known at the `for`.
- **(b) Two traits,** e.g. `LendingIterator` (exclusive) and a shared one: explicit, but two names for one idea, and the impl picks its trait instead of its signature.
- **(c) One trait with a mode** (an associated constant or a type parameter): the most machinery, and borrowing structs can't instantiate type parameters anyway.

**Air: SL-871.p1 (unit 1) approved.** Reviewed r1 on a2fb4ee38.

**The exclusive charge holds in the loop body** (`s1_root_in_body.saw`). `for c in g.cells()` runs over a `borrows struct Cells { grid: &var Grid, index: Int }` filled with `lends self` from a `&var self` producer. Each use of the root inside the body is refused at its own line:

| use in the body | refusal |
|---|---|
| `total += g.visits` | `loan.window-root` |
| `g.cells.push(c)` | `loan.window-root` |
| a nested `for d in g.cells()` | `loan.window-root` |
| `look(&g)` (shared) | `loan.window-root` |
| `poke(&var g)` | `loan.window-root` |
| `take(move h)` inside `for c in h.cells()` | `loan.move-while-borrowed` |

The read after the loop (`total + g.visits`) is accepted.

**K212 has no indirect gap** (`s2_indirect_alias.saw`). A `&var`-field struct can't get a second reference through a nested borrowing struct either: each of these is `borrowing.containment` at the field, so no second reference can sit beside the writer:
- `inner: Peek`, where `borrows struct Peek { grid: &Grid }`;
- `inner: Peek?`;
- `pair: (Int, Peek)`.

The run side (writes through the field in `next`, and `deinit` on the end, `return` and `break` routes) is pinned by the patch's two probes in the sanitizer lane.
