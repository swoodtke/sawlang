## Unit A: SL-414, `move self` in a consuming body (the user's ruling, SL-414 c1)
**Ruling.** `move self` is Saw inside a `consumes` method only. It hands the whole receiver onward, and the end-of-body sweep then releases nothing. The type's deinit runs wherever the value finally ends. The move is decided on every path or on none, and it cannot follow `move self.<field>`. Outside a consuming body it is a type error, not a grammar refusal.

1. **The conformance ledger comes first** (obligation 3; SL-414 c2, adopted in c3, agreed by the user in c4):
   - In `examples/conformance/INDEX.md`, qualify V56: the hand-written body is skipped only where the consuming body ends the value. A body that ends with `move self` is not the value's endpoint.
   - Add four rows next to V51–V56:
     1. The value goes onward: the sweep releases nothing, and the deinit runs exactly once, where the value ends.
     2. `move self` on some paths but not others is refused.
     3. `move self` after `move self.<field>` is refused.
     4. `move self` outside a consuming body is a type error.
   - Mark each new row as owed to the self-hosted compiler, cross-referenced to the §16 row in step 3. The frozen sawc refuses `move self` at parse, so no passing test can cover these rows today. Follow INDEX.md's own conventions for an owed row. If it has none, add one and describe it in the file's legend.
2. **GRAMMAR.md:**
   - Keep `move-base.self`.
   - Retire `syntax.expr.refused-move-self` and `syntax.expr.move.refused-self`, together with the §13/refusal row that cites them. Follow GRAMMAR.md's own convention for retiring a production: look for how others are retired, and never reuse an id.
   - Say, where the move forms are described, that the consuming-body restriction is semantic.
3. **§16:** add a row. The frozen sawc refuses `move self` with a dedicated parse error, while GRAMMAR.md accepts it.
4. **LANGUAGE_SPEC.md, "Moving a field out" (consuming receivers):**
   - Add the whole-receiver case with the rules above.
   - Give one example of each: a consuming builder (`func with(&var self, n: Int) consumes -> Builder { self.count = self.count + n; move self }`, chained `(move b).with(n: 4).finish()`), forwarding (`(move self).close()`), and wrapping (`Wrapper(inner: move self)`).
   - Load the saw-docs skill before editing spec prose.
   - Mark the examples however the spec marks behaviour that the frozen compiler does not implement; check how existing unimplemented sections do it. The `docverify` lane must stay green.
5. **The corpus:** drop the two `move self` waivers from `compiler/tests/parse/waivers.tsv`. The generated `syntax.expr.move-base.self/alt` stays as a positive. Add golden cases for `move self` in a consuming body: the builder, forwarding and wrapping shapes.

## Unit C: SL-409, block-tail in the recognizer, and the closure line breaks
1. **Block-tail** (`syntax.rule.block-tail`): a loop (`while`, `while let`, `for`) that starts a statement is a statement. It never continues on its line as an operand. The recognizer refuses every continuation and names `syntax.rule.block-tail`:
   - a binary operator: `while a { } + 1`, `for x in y { } + 1`;
   - a postfix hop: `while a { }.b`;
   - `as T` and `?? b`;
   - a loop as a closure's tail value.

   `if`, `match`, `try` blocks and `borrow` blocks still continue.
   - Golden cases for both sides; negative cases for each continuation.
   - Drop the `trailing-call/cell:rend` waiver, and the generator's `loop_operand` filter if nothing else needs it.
   - Re-run the grammar corpus. A tracked file that now changes verdict is a finding: classify it against the rule, and record the reasoning in `corpus_expected.tsv`'s review note, or report it.
2. **The closure line breaks** (SL-409 c1): make the closure's line breaks derivable one way only. Newlines before a head attach to the head, the head ends at `in`, and the body's leading `NEWLINE*` takes the rest. For example: `closure-literal ::= "{" ( NEWLINE* closure-head )? block-body "}"`, with the trailing `NEWLINE*` removed from each `closure-head` alternative.
   - Check the lint's ambiguity and self-consistency checks, and look for the same double derivation anywhere else a construct's own `NEWLINE*` meets `block-body`'s. Fix those the same way, and list them.
   - Every program must parse as before: the grammar corpus verdicts are unchanged, and the dumps are unchanged.
   - Drop the 8 closure-head `case` waivers.

## Unit D: SL-408, numeric separators (the user's ruling, SL-408 c1)
**Ruling.** An `_` is a single separator between two digits, including inside a float's digit runs. §2.1's one optional `_` before a type suffix (`2_u8`) stays.
- **Accepted:** `1_0.5`, `1_000`, `0xFF_FF`, `2_u8`.
- **Refused:** `1__000`, `0b1__0`, `1.0__5`, `0x_FF`, `1_`, `0xFF_`, `1_000_`, `1.0_`, `1_.5` and `2__u8`.

1. **GRAMMAR.md §2.1:** state the rule in words and in the lexical EBNF. It must now allow a separator inside a float's digit runs.
   - The §16 row for the lexers' acceptance stays: `compiler/lex` changes in a later unit, and the frozen lexer never does.
   - Update that row's text to the ruled set.
2. **The corpus** (SL-408 c2): `compiler/tests/parse/dump/leaves.saw` keeps `2_u8` and `1_0.5`. `1_`, `0xFF_`, `2__u8` and `1.0_` move out of the pin.
   - While sawc2 still lexes them, the recognizer accepts them. So they cannot be recorded as refused yet.
   - Record them as owed lexical negatives: a list in the README or a waiver kind, whichever the corpus already has for "blocked on the lexer". Do not record a false expectation.
   - Update the README's Leaves sentence.
   - Add a golden case for `1_0.5`, `1_000`, `0xFF_FF` and `2_u8`.
