## Description

Found by SL-631's sweep (agent c631attr). The mechanism differs from SL-631's.

**Mechanism:** sawc2 has one build mode, and it emits test code. SL:testing §3 says a `@test func` and an `@test { … }` group are "typechecked, not emitted" in a normal build. But typecheck's export funnel (`tc_check_exports`, `compiler/typecheck/src/exports.saw`) records the C symbol of every `@export` it finds, test-only or not, and mono roots every recorded export (`add_roots`, `compiler/mono/src/worklist.saw`). So a test-only exported function is emitted, under its unmangled symbol, into an ordinary binary. Production code can then call test code through an `extern "C"` declaration. Name visibility doesn't see this, since the call goes through the C symbol, not the Saw name. That breaks "Test-only means test-only" and "Test code cannot change what production code means".

**Evidence** (`sawc2 build`, at SL-631's tree): this builds, links and prints `7`.

```saw
extern "C" {
    func c631_leak() -> Int32
}

@test {
    @export("c631_leak") func leak() -> Int32 { 7 }
}

func main() {
    print("{}", c631_leak())
}
```

On main before SL-631, the same program written with `@test` directly before the `@export` line fails to link: the attribute was lost (SL-631), so nothing was exported. SL-631 makes the two forms agree, so both now leak.

**Fix shape:** a normal build roots and emits no test-only declaration. A test-only export is either kept out of the export record in a normal build, or refused outright (GRAMMAR's syntax.rule.test-form: "a later stage refuses a combination that means nothing"). Which one needs a ruling: whether `@test @export` means anything (a C-side test harness calling into a test build) or is a combination to refuse. Sweep the other roots mono takes, the lang items and `main` among them, for a test-only declaration reaching them.

**Pins:** the program above, refused, or built with `c631_leak` undefined, in each form. Plus a run program under the future test build, if `@test @export` is kept.

**The user's ruling, Oct 15** (asked whether `@test @export` should be refused or kept): "if so then i would support @test { @export ... }", then, on the two spellings, "both are fine".

- **Kept, not refused.** A test-only `@export` means "export this symbol in a test build", which a C-side test harness can call. Both spellings mean the same: `@test @export func` and `@export` inside an `@test { … }` group.
- **A normal build emits no test-only declaration** (SL:testing: "emitted only in test builds"). No symbol is emitted, so an `extern "C"` call from production code fails to link. This half goes into SL-631's revision (the Air's suggestion on SL-631), with the `c631_leak` program pinned as a link failure in both spellings.
- **What stays here, in SL-644:** the sweep of mono's other roots (lang items, `main`) for a test-only declaration reaching them, and the test-build run pin once a test build exists.

SL:testing gains one sentence at landing: a test-only `@export` is exported only in a test build.
