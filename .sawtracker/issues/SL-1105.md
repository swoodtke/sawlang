## Description

**A run probe printed 305 of its 389 bytes and exited 0: the output stops two bytes into a line (`zo` of `zombies left for nobody: 0`), and the three last lines never arrive.** Seen once, on Nov 14, in agent p1037's gate run (`programs` step, the machine under load from other agents); the same step passed on the rerun.

**Evidence** (`.build/scratch/p1037/gate_run.log` line 167 in the lead's checkout; `probe_flake_line.py` beside it extracts the two strings):
```
run compiler/tests/run/probes/process_output_cancel_ends_its_drain.saw -O0: exit 0, prints b'...children still running after the cancels: true\nzo', not exit 0 printing b'...children still running after the cancels: true\nzombies left for nobody: 0\nchildren still running after the sweep: false\ndeinits=4\n'
```
What was printed is a strict prefix of what is expected. The exit status is 0. So the program ran to its end, by its own account, and 84 bytes of its standard output are missing, starting in the middle of one `print`.

**Why this is not filed as "a timing flake".** The probe's assertions are not timing margins (SL-977 swept those); a lost tail of standard output with a clean exit is a wrong result. A test that reports failure at random is a defect to fix (user, Nov 12), and this one may be showing a real one.

**What the program does that is unusual** (its header): each cell launches a child that inherits the program's standard descriptors; while launching, the program puts a pipe's write end at its OWN standard error and puts its own back afterwards; it cancels drains of `Command.output()`; it closes a gate pipe; it calls `waitpid(-1, WNOHANG)`. The missing output begins right after the line that follows the cancels and before the sweep's count.

**Candidates to test, none verified:**
- the write path: `saw_writev_all` (`runtime/shim.c`) resumes a partial write and waits on `EAGAIN`; is there a path where a write to fd 1 returns short or fails and the error is dropped (`print`'s result is discarded), for instance a `SIGPIPE`-like or `EBADF` moment while descriptors are being swapped, or fd 1 made non-blocking by a child that shares its open file description;
- the descriptor swap: can a concurrent task's `print` land while fd 2 (or, through an off-by-one, fd 1) is the pipe;
- the reader: the lane's `subprocess.run` capture is the control (a truncated capture with exit 0 would be the lane's, not the program's);
- output buffered in the process and lost at exit (does anything buffer standard output today; `leaks: none` runs the program under `/usr/bin/leaks`, which is a different launch).

**To do.**
1. Reproduce: run the probe's binary in a loop under load (the lane's own launch, `-O0` and `-O2`, a few thousand runs, with the gate's other steps or a CPU hog running), recording each short output with its length and the exit status. `dtruss`/`ktrace` is not available in the sandbox; a `SAW_`-less way is to wrap fd 1 in a pipe whose reader records each `read`'s size.
2. Name the mechanism (obligation 4) before any change, and sweep its siblings: every other place the runtime or std discards a write's result or swaps a standard descriptor.
3. Fix it there, with a test that fails without the fix more often than once in a few thousand runs (or a deterministic construction of the same interleaving).

**Until then** the probe stays as it is: its failure is the evidence. If it fails a server gate, the log line goes on this issue.

**Correction (lead, Nov 14): this issue's description is wrong about what happened, and the mistake was mine. No output was lost. The investigation (agent p1105) found a race in the PROBE and a failure message in the LANE that hid it. Implementation detail follows.**

**What the log line really says.** The stated-probe check prints the program's output cut to 300 bytes beside the whole expected output (`run_lane.py`: `"%s: exit %s, prints %r, not exit %d printing %r" % (where, code, out[:300], status, want)`). I read the cut as the program's. The program printed all 381 bytes and exited 0; the 300th byte falls two bytes into `zombies left for nobody`, and the difference that failed the check lay AFTER it, where the message does not show it. "305 of 389" were lengths of the two `repr`s.

**The real flake, reproduced** (`.build/scratch/p1105/` in the lead's checkout: `harness.py`, `results.jsonl`, `varA.saw`, `varB.saw`): about 1 run in 1,000 to 1,500 under load, at -O0 and -O2 alike, prints `zombies left for nobody: 1` (or 4) where 0 is expected; same length, exit 0. About 11,000 runs showed no short output, no lost line and no non-zero exit.

**Mechanism (shown).** The probe treats end of file on its "alive" pipe (each child holds the write end as its standard error) as "every child has exited". A process closes its descriptors while exiting, BEFORE it becomes a zombie that `waitpid` can reap. So after the end of file the probe's one extra spawn sweeps the orphan list with one `WNOHANG` poll each (`process_sweep`, as designed in SL-799), finds a child that is not a zombie yet, keeps it; the probe's own `waitpid(-1, WNOHANG)` then reaps it a moment later and counts it as left for nobody. `varB.saw` widens the window (the child closes its end, then exits 3 ms later): 14 of 40 runs print a non-zero count. `varA.saw` (a 30 ms sleep after the end of file) had 0 in 3,000.
- Not shown: that the ONE original failure was this (its differing bytes were behind the slice). Everything observed since is.
- The runtime's write path, the descriptor swap, the lane's capture and buffering were each read or run and show nothing wrong; no `runtime/` or `std/` change is indicated.

**What to fix: two things, one unit.**

**1. The probe states what std guarantees, without the race.** std's guarantee (SL-799) is that an orphan is reaped by a LATER spawn's sweep once it has exited, and that nothing is left for nobody. "Has exited" must be observed as exit, not as a closed descriptor. In `compiler/tests/run/probes/process_output_cancel_ends_its_drain.saw`: after the end of file, sweep in a bounded loop (one spawn of the sweeper per turn, a tick between turns, the existing deadline) until std reports no orphan still running; only then count with `waitpid(-1, WNOHANG)`. A child the sweeps did not reap is then a real leak, and the count stays the assertion it was meant to be. Read how the probe reads "children still running" today and use the same source; if the program cannot ask std for the orphan count, STOP and report what it can ask.
- The header's sentence "the second pipe then reads end of file exactly when every child holding it has exited" is false as a statement about reaping; reword it to what holds (every child has closed its standard error, which it does on the way out).
- **Siblings (obligation 4):** `process_output_cancel_closes_the_pipe.saw` and `process_output_cancel_reaps_child.saw` use `waitpid(-1` too. For each: does it take a descriptor's end of file (or any signal short of exit) as "the child has exited" before it counts? Show it with a widened-window copy as `varB` does (in the evidence directory, not tracked); fix those that race the same way; say why the others cannot.
- **Evidence the fix holds:** the widened-window variant of each fixed probe, with the fix applied to the copy, prints the expected lines in 200 of 200 runs; and the real probes pass the harness's content comparison in 3,000 runs under the same load as the reproduction (2 CPU hogs, 6 workers; at most 8 processes of yours).

**Lead's ruling on the stop (Nov 14): the probe peeks without reaping, and std does not change.** Agent p1105 is right that the detail's loop cannot be written: std exposes no orphan count, and the probe's own `waitpid(-1, WNOHANG)` reaps what it sees, which destroys the evidence the count is about. A leaked zombie and one that became a zombie a moment after the sweep look the same once the probe has reaped it. **What the probe asserts, restated:** std's sweeps, given the chance, reap every child the cancelled drains abandoned, so that the process ends with NO children of its own, and the probe reaped none of them. **How, race-free:** after the end of file on the alive pipe, loop under the existing deadline: (1) spawn the sweeper and wait for it (std sweeps what has exited); (2) PEEK with `waitid(P_ALL, 0, info, WEXITED | WNOHANG | WNOWAIT)`, which reaps nothing: a return of -1 means the process has no children left at all, so every one was reaped by std, and the loop ends; a return of 0 means some child is still running or is a zombie std has not swept yet, so tick and go round again (the next turn's sweep takes a child that has since become a zombie). Only AFTER the loop does the probe count with `waitpid(-1, WNOHANG)`: on the success path there is nothing to count (0, and "still running" is false); at the deadline whatever is left is a real leak or a child that never exited, and the existing two lines report it. No sleep stands in for an exit and no margin depends on machine speed. **`WNOWAIT` differs by host** (0x20 on macOS, 0x01000000 on Linux; `WEXITED` is 4 and `WNOHANG` 1 on both, `P_ALL` 0): the probe asks once, before any cell runs, with `Command(program: "uname")` and `-s` through `output()` (its child is reaped by the call), and picks the constant; an answer that is neither `Darwin` nor `Linux` panics naming it. `info` is a zeroed byte buffer of 256 bytes, larger than `siginfo_t` on both. Declare `waitid` beside `waitpid` in the probe's `extern "C"` block. **The Linux half cannot be run here:** say so; the Linux lane (opt-in, in the VM) is where it runs, and the constants above are from the two systems' headers, to be checked against `/usr/include` on macOS for the 0x20 and stated as read, not run, for Linux. **Siblings:** the same construction for each sibling probe that the widened-window copy shows racing. **The lane's message** (the detail's second half) is unchanged and goes ahead.
