## Description

Found while pinning design 275 U4's thread-body message (SL-318 U4 review,
lead FIX 1). Pre-existing keying property of the std seed, made visible by the
new refusal.

A `sync` violation reached through a SEEDED std method is not reported at the
FIRST settling of the effect graph — only at a later one — because the seed
table's node ids do not match the entry graph's edges yet:

    --- finalize round 1
        thread body closure: causes {} edges=[62190]
        seed 20761 `Command.output`: {cooperative, blocking}
        seed TABLE has 18 entries; 62190 present: False
    --- finalize round 3
        thread body closure: causes {cooperative, blocking} edges=[62190]
        seed 62190 `Command.output`: {cooperative, blocking}
        seed TABLE has 18 entries; 62190 present: True

(`.build/scratch/probe_dump_thread_nodes.py` in the sl318u4 worktree, over
`.build/scratch/probe_thread_output.saw`.) Design 206 keys the table by
`Method.node_id` because that identity is "preserved verbatim across the std
cache's pickle"; in round 1 the ids the ENTRY graph's edges carry are a
different generation (62190 vs 20761), and a later stage re-hands a table whose
keys do match.

THE CONSEQUENCE, and it is the reason this is worth a line: the pipeline stops
after a settling that REPORTED errors, so a program that has any OTHER compile
error never reaches the later round and the std-method violation is silently
dropped from that compile. Probed: `Thread.spawn { [move c] in c.output() }`
alone is refused; the same cell BESIDE a `Thread.spawn { boundary() }` (which is
refused at round 1) reports only the first, and the program compiles no further,
so the author sees the second violation only after fixing the first. A CLEAN
program always reaches the later round, so nothing is mis-compiled — what is
lost is diagnostic completeness in one compile.

Not caused by U4 (the seed's KEYING is design 206's, unchanged); U4 only made a
refusal exist that reaches through a seeded leaf in this context. Recorded here
so SL-318 U1's ledger, which takes the seeded-leaf population over, either keys
the table so round 1 matches or states why the first settling cannot.

Corpus effect: the conformance cell that pins the message lives in its OWN file
(`examples/conformance/K112_thread_body_refuses_a_multi_cause_std_method.saw`)
for exactly this reason — beside another refused cell its message would not be
emitted.

REPRODUCED and FIXED AT THE KEYING by design 275 U2 (branch sl318u2, commit 2a60ff36; not yet submitted — U2 goes out as SL-318.p6). Settling untouched.

My first pass reported this as non-reproducing: main and the branch, cold cache and warm, four program shapes, all reported both violations at round 1. Then the two-violation test I had just added PASSED in isolation and FAILED in the full suite twenty minutes later — same tree, same commit. The symptom is CACHE-STATE DEPENDENT. A freshly built std pair agrees with itself; a RESTORED one need not.

MEASURED: five of the eight blobs in .build/stdcache/ held a seed table keyed to an AST that was not the one stored beside them. Command.output keyed 20761 in the table and 62190 in both the restored AST and the namespace symbol the entry edges resolve through — this issue's own two numbers, now off the blob rather than off a round dump. Every inconsistent blob was written by a process whose node_id bound was an order of magnitude past a fresh std build's (37997 vs 182671-733519), i.e. by a process that had already compiled something — the state _prepared_builtins' own docstring says the pair must not be stored from. One blob holds an AST of TWELVE methods beside a full std namespace. A pickle round trip preserves node_id (probed directly), so the inconsistency is at the STORE, not the restore.

TWO KEYING FIXES: stdcache._pair_is_consistent — store declines to publish a pair whose seed keys are not in the AST it is about to pickle beside them (one walk per cache MISS; declining costs one cold std build, publishing costs every later compile a diagnostic). And sawc._rekeyed_std_seed — the handover re-keys a restored table onto the AST this compile actually holds, so blobs already on disk are harmless; the fallback key is (owner, method), the granularity every other std suspension census already uses, and an overloaded pair re-keys onto every match (the conservative direction). A consistent table is returned unchanged.

PROVEN against the real bad blob, kept at .build/scratch/badblob/: 18 dangling keys -> 0 after the re-key, and Command.output's namespace symbol id seeded after and not before. End to end, with that blob on disk the two-violation program reports BOTH errors on three consecutive runs.

TEST: examples/errors/thread_body_reports_both_violations.saw (a Thread.spawn { boundary() } beside a Thread.spawn reaching Command.output through four hops), asserting both messages and '2 error(s) generated'. K112 keeps its own file, as the ruling requires. _effect_seed_std_methods' docstring carries the measurement and what enforces the invariant.
