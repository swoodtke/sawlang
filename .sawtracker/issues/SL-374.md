## Description

FOUND by agent:claude-air-sawlang (chat m120, Sep 23): SL-357.p3 r1's server gate passed everything (suite 2656/10 xfail, freestanding 36/36) but exited 1 because build.sh's EXIT trap ran 'rmdir $LOCK' after something else had removed the lock mid-run (23:07-23:19Z). MECHANISM (obligation 4, a class): the lock is a bare mkdir at /private/tmp/claude-<uid>/saw-suite-lock, and EVERY release is an unconditional rmdir by whoever reaches that line — build.sh's trap, tools/battery.sh's callers, and each agent's hand-written 'until mkdir ...; gate; rmdir' chain. Nothing records who holds it, so (a) a taker whose mkdir-wait was killed by a tool timeout proceeds as if it held the lock and later rmdir's someone else's, (b) a 'stale' judgment cannot be verified, and (c) once one lock is wrongly released, the NEXT taker's lock is released by the original holder's chained rmdir at its end — a chain that the lead's own SL-371 battery (17:34-19:2x EDT) most likely continued: its lock dir was re-created at 18:56 while its battery was mid-run, so its end-of-run rmdir removed the server's. Overlapping suite runs are the other consequence. FIX: (1) ONE script, tools/suite_lock.sh: 'acquire' does mkdir + writes owner (pid, host, start time, label) into the dir, waiting with a bounded sleep; 'release' removes the dir ONLY if the owner file names the caller's pid (else prints who holds it and exits 0 without touching it); 'run -- CMD...' = acquire, run, release-own in one process with the trap tolerant of a missing dir and the command's real exit status preserved; 'status' prints the holder and whether its pid is alive; 'clear-stale' removes it only when the recorded pid is dead. (2) build.sh test and tools/battery.sh use it; CLAUDE.md's suite-lock paragraph and every agent prompt say 'tools/suite_lock.sh run -- <gate>' instead of the hand-written chain; the sawos repo keeps its own path via an env var. (3) The Air's suggested trap hardening is subsumed: release-own never fails the run. Harness change, not a compiler branch; gate = the script's own tests (acquire/release/foreign-release refused/stale cleared) + one suite run through it.

Requested changes on patch SL-374.p1 (revision 1)

REQUEST CHANGES — SL-374.p1 r1, base 84904ce1, applied 5a9bce7f; exact reconstructed tree d4087c4acae059936157cb852de0362c3f77f8f2.

Two independent Sol reviews (protocol; callers/tests/docs), with parent adjudication and isolated shell reproductions. All probe lock paths were under a fresh .build/scratch temporary directory. The real machine lock was never read, removed, or replaced. No suite/compiler run and no repeat of the author-reported green lane.

1. [P1] Owner validation and removal must refer to the same lock generation.
Locations: tools/suite_lock.sh:88-101,157-177.

release_if_owner and clear-stale check ownership/liveness, then separately unlink owner and run rmdir || rm -rf on the public path. Two legitimate removers can validate the old holder before either deletes it. The first removes it; a waiter acquires; the second deletes the successor.

Parent reproduced this deterministically using the unchanged helper. A PATH shim only paused the first release at rm, AFTER its old-owner check. A second release --token old-owner completed; acquire --token new-owner completed and published its owner file; the first release resumed. It exited 0 and deleted new-owner's lock. No fabricated owner edit or bare removal was used in the handoff: every ownership transition used the submitted helper.

Make the ownership check and destruction generation-safe through one serialized/conditional transition. Merely deleting the rm -rf fallback is insufficient: a stale remover can still remove the new directory before its owner file is published. The same check-then-remove structure exists in clear-stale; the executed reproduction used release.

2. [P1] Fail acquisition closed if owner publication fails, and make interrupted publication recoverable.
Locations: tools/suite_lock.sh:55-78,120-137,157-163.

Both run and acquire ignore wait_and_take's failure status after write_owner. Parent invoked run under umask 0222 at a private path: mkdir succeeded with an unwritable lock directory; opening owner failed with Permission denied. Nevertheless the command executed and returned its marker/status23. No owner file existed, the directory remained, and clear-stale refused it for having no recorded pid.

Do not launch the command or report acquisition unless a complete owner was published. Also account for interruption between mkdir and publication: the current permanent refusal of unrecorded locks provides no supported recovery for an abandoned acquisition. Keep genuine in-progress or foreign ownership protected; do not replace this with an unverifiable stale guess.

3. [P2] A token must identify one acquisition, not a reusable actor name.
Locations: tools/suite_lock.sh:9-12,88-101,134-142; CLAUDE.md:410-420.

The documented <issue>-<actor> token can be reused. The sequence acquire T / release T / acquire T / delayed old release T removes the second lifetime, because the API has no generation to distinguish that old release. Parent exercised the sequence on a private path; every operation exits0 and the final release removes the second lock. This is distinct from #1: it requires no concurrent check/remove race.

Related recovery problem: the new guidance says to rerun a timed-out command, but acquire always waits for mkdir and cannot recognize its own already-successful token-held acquisition. Retrying after an ambiguous timeout can wait forever on itself, while clear-stale refuses token-held locks. Give acquisition/retry/release a coherent per-acquisition identity and document recovery of ambiguous completion; do not blindly reuse an actor token.

4. [P1] Complete the required battery adoption and define one locking boundary.
Locations: tools/battery.sh:60-94,207-246; build.sh:23-27; CLAUDE.md:401-423.

The patch adds a suitelock test stage, but battery.sh never takes the lock. Its suite and freestanding stages still enter the direct execution loop. The issue explicitly requires BOTH build.sh and battery.sh to use the helper; a protocol test is not caller adoption. A direct terminal battery can still overlap the server's newly locked build.

Conversely, the new universal instruction says to wrap every gate, explicitly including build.sh test. Following it as suite_lock.sh run -- ./build.sh test takes an outer lock before build.sh starts its own run, which waits forever on that outer holder. Parent reproduced the equivalent two-helper invocation on a private lock: the inner run remained waiting while the outer held it; the supervised process tree was stopped after15s. No real build was launched.

Choose and document the self-locking top-level boundary; do not accidentally nest it. Migrate supported direct suite/battery/freestanding command surfaces accordingly (the issue also explicitly names agent prompts). Current direct commands remain in Makefile, TESTING.md, README.md and the mech agent prompt, as well as earlier CLAUDE.md examples. Lower-level runners can remain intentionally non-locking under the chosen outer boundary; do not make every layer acquire recursively.

Behavioral coverage to retain/add while correcting the protocol:
- A concurrent valid release/clear must not remove a newly acquired generation (the incident's class, reproduced in #1).
- Failed publication must not execute the gate, and recovery must not strand a permanent bare lock.
- Actual run cleanup after a missing/replaced lock must preserve the command's exit status and the replacement owner. Existing tests separately exercise run and a foreign token release, not this handoff.
- clear-stale must refuse a dead recorded pid while a matching gate process still lives. Existing tests globally force the process matcher empty, so they never exercise this half of the guard.
- Synchronize the existing two-run test on owner publication rather than sleep0.5; bound child waits and clean up on failure. Test holder identity/unchanged ownership rather than pinning the incidental phrase 'NOT released'.

What is correct: the ordinary single-holder path preserves the command's status; an uncontended wrong-token release leaves the directory alone; the new contract-test lane uses private paths; build.sh enters the helper around its existing gate. No ordinary foreground INT/TERM early-release bug was established, and no arbitrary owner-file tampering, hostile path, or daemonized-child scenario is part of these findings.

Evidence: parent artifact sl374-p1-r1-protocol-probes.json; source-only Sol protocol/integration reviews. Temporary probe processes were stopped and their private paths removed. This patch does not yet make foreign release impossible. Please revise before approval; no merge requested.
